API呼び出しがタイムアウトしやすい長時間実行タスク。Deep Research、複雑な推論、複数ステップのワークフローなど、数分単位で処理が続く場合、通常のリクエスト・レスポンスモデルでは限界に直面します。

**Gemini Interactions APIの Background Execution** を使えば、クライアントはレスポンスを待たずに即座に返却された Interaction ID を受け取り、サーバー側で非同期処理を継続させられます。この記事では、Background Executionの実装方法からポーリング戦略、Batch APIとの使い分けまでを解説します。

## Interactions API と Background Execution の基本

Gemini Interactions APIは、ステートフルな会話管理とツール実行を一つのAPIで統合する仕様です。2026年3月時点で、`background=True` パラメータを指定することで非同期実行が可能になります。

### Background Mode の特徴

- **即座にレスポンス**: 処理完了を待たずに Interaction ID を返す
- **サーバー側での処理継続**: クライアントはディスコネクト可能
- **ステート管理**: `store=true`（デフォルト）で会話コンテキストが保持される
- **ポーリング対応**: 別エンドポイントで完了確認と結果取得が可能

通常のリクエストは同期的です：

```python
# 同期的なInteractions API呼び出し
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=[{"role": "user", "parts": [{"text": "複雑な分析を実行してください"}]}],
)
# ここでクライアントはレスポンス完了まで待機
print(response.text)
```

Background Executionを使うと：

```python
# 非同期実行の例（実装詳細は後述）
interaction = client.models.background_execute(
    model="gemini-2.5-pro",
    contents=[{"role": "user", "parts": [{"text": "Deep Research を実行してください"}]}],
    background=True
)
# 即座に interaction_id を返して終了
print(f"Interaction ID: {interaction.id}")
# クライアントはここで次の処理へ進める
```

## Background Execution の実装パターン

### ステップ1：背景実行の開始

```python
import anthropic
import time

client = anthropic.Anthropic(api_key="YOUR_GEMINI_API_KEY")

def start_background_task(prompt: str, model: str = "gemini-2.5-pro") -> dict:
    """
    Background Executionで長時間タスクを開始

    Args:
        prompt: ユーザープロンプト
        model: 使用するモデル名

    Returns:
        - interaction_id: ポーリング用の識別子
        - created_at: タスク開始時刻
    """
    response = client.models.interactions.create(
        model=model,
        contents=[
            {
                "role": "user",
                "parts": [{"text": prompt}]
            }
        ],
        background=True,  # 非同期実行フラグ
        store=True,       # ステート管理を有効化
    )

    return {
        "interaction_id": response.name,  # "interactions/..."形式
        "created_at": response.create_time
    }

# 使用例
result = start_background_task("深いリサーチベースの分析を実行してください")
print(f"Started task: {result['interaction_id']}")
```

### ステップ2：ポーリングで進捗確認

```python
def poll_background_task(interaction_id: str, max_wait_seconds: int = 600) -> dict:
    """
    背景実行中のタスクをポーリングして完了を待つ

    Args:
        interaction_id: start_background_taskで返されたID
        max_wait_seconds: 最大待機時間（デフォルト10分）

    Returns:
        - status: "COMPLETED", "PROCESSING", "FAILED"
        - output: 完了時の結果テキスト
        - error: 失敗時のエラーメッセージ
    """
    start_time = time.time()
    poll_count = 0

    while True:
        elapsed = time.time() - start_time
        if elapsed > max_wait_seconds:
            return {"status": "TIMEOUT", "error": "Max wait time exceeded"}

        # ポーリング間隔は指数バックオフ
        poll_count += 1
        wait_time = min(2 ** poll_count, 30)  # 最大30秒

        try:
            # Interactions APIでステータス確認
            interaction = client.models.interactions.get(
                name=interaction_id
            )

            # ステータス判定
            if interaction.state == "COMPLETED":
                # 最後のメッセージから出力を抽出
                if interaction.messages:
                    last_msg = interaction.messages[-1]
                    if last_msg.parts:
                        return {
                            "status": "COMPLETED",
                            "output": last_msg.parts[0].text
                        }
                return {"status": "COMPLETED", "output": ""}

            elif interaction.state == "FAILED":
                return {
                    "status": "FAILED",
                    "error": interaction.error or "Unknown error"
                }

            elif interaction.state == "PROCESSING":
                print(f"Still processing... (elapsed: {elapsed:.1f}s)")
                time.sleep(wait_time)
                continue

        except Exception as e:
            return {"status": "ERROR", "error": str(e)}

# 使用例
task_result = start_background_task("大規模データセットの統計分析")
print(f"Task started: {task_result['interaction_id']}")

poll_result = poll_background_task(task_result['interaction_id'])
if poll_result['status'] == 'COMPLETED':
    print(f"Result: {poll_result['output']}")
else:
    print(f"Task failed: {poll_result.get('error')}")
```

### ステップ3：Deep Research エージェントとの統合

def run_deep_research_async(query: str) -> str:
    """
    Deep Researchを背景実行モードで実行

    Args:
        query: 調査対象のクエリ

        interaction_id: ポーリング用ID

    # Deep Research用の特化プロンプト

Requirements:
- Search for the most recent and reliable sources

## Batch API との使い分け

Background ExecutionとBatch APIは似ているようで、用途が異なります。

### Background Execution

- **レイテンシー**: 数秒〜数分のタスク
- **実行時間**: 最大30分程度
- **用途**: Deep Research、複雑な推論、リアルタイム性が若干必要
- **課金**: 通常料金
- **スケール**: 中規模バッチ（数十〜数百リクエスト）

### Batch API

- **レイテンシー**: 無視可（24時間内処理）
- **実行時間**: 無制限
- **用途**: 大量データ処理、コスト最適化重視、スケジュール実行
- **課金**: 50% ディスカウント
- **スケール**: 超大規模バッチ（数千〜数百万リクエスト）

### 選択フローチャート

```
タスクが開始されたか？
├─ YES → Background Executionを検討
│        結果が30分以内に必要か？
│        ├─ YES → Background Execution
│        └─ NO  → Batch APIも検討可
└─ NO  → 大量リクエスト？
         ├─ YES（>1000） → Batch API
         ├─ NO（<1000）  → Background Execution
         └─ コスト重視？
            ├─ YES → Batch API
            └─ NO  → Background Execution
```

通常の判断基準：

- **I need results in 5-30 minutes** → Background Execution
- **I can wait up to 24 hours, need to cut costs by 50%** → Batch API
- **I'm processing 100K+ requests** → Batch API必須

## エラーハンドリングと再試行戦略

```python
import random

def robust_background_execution(
    prompt: str,
    max_retries: int = 3,
    backoff_factor: float = 2.0
) -> dict:
    """
    エラーハンドリングと再試行ロジック付きの実行
    """
    for attempt in range(max_retries):
        try:
            # タスク開始
            task = start_background_task(prompt)

            # ポーリング
            result = poll_background_task(task['interaction_id'])

            if result['status'] == 'COMPLETED':
                return {"success": True, "data": result['output']}
            elif result['status'] == 'FAILED':
                # 失敗は再試行可能か判定
                error_msg = result.get('error', '')
                if is_retryable_error(error_msg):
                    raise Exception(f"Retryable error: {error_msg}")
                else:
                    return {"success": False, "error": error_msg}

        except Exception as e:
            if attempt < max_retries - 1:
                wait_time = (backoff_factor ** attempt) + random.uniform(0, 1)
                print(f"Attempt {attempt + 1} failed: {e}. Retrying in {wait_time:.1f}s...")
                time.sleep(wait_time)
            else:
                return {"success": False, "error": str(e)}

    return {"success": False, "error": "Max retries exceeded"}

def is_retryable_error(error_msg: str) -> bool:
    """再試行可能なエラーを判定"""
    retryable_keywords = [
        "timeout",
        "temporary",
        "unavailable",
        "rate_limit",
        "transient"
    ]
    return any(kw in error_msg.lower() for kw in retryable_keywords)

# 使用例
result = robust_background_execution("複雑な分析タスク")
if result['success']:
    print(f"Output: {result['data']}")
else:
    print(f"Failed: {result['error']}")
```

## 料金と最適化

Background Executionの料金モデル：

- **入力トークン**: $0.075 / 100万トークン（gemini-2.5-pro）
- **出力トークン**: $0.30 / 100万トークン
- **コンテキスト上限**: 100万トークン
- **実行時間制限**: 最大30分

コスト削減のコツ：

- **不要なコンテキスト削除**: ポーリング時に古い履歴をトリミング
- **段階的処理**: 1つの大きなタスクではなく複数の小さなステップに分割
- **Batch API への振り分け**: 結果不要な大規模処理はBatch APIへ

```python
def estimate_cost(input_tokens: int, output_tokens: int, model: str = "gemini-2.5-pro") -> float:
    """Background Execution のコスト推定"""
    if model == "gemini-2.5-pro":
        input_cost = (input_tokens / 1_000_000) * 0.075
        output_cost = (output_tokens / 1_000_000) * 0.30
        return input_cost + output_cost
    return 0.0

# 例：100万トークン入力、50万トークン出力
cost = estimate_cost(1_000_000, 500_000)
print(f"Estimated cost: ${cost:.3f}")  # 約$0.225
```

## よくある質問（FAQ）

**Q: Background Executionのポーリング頻度はどのくらい？**

A: 初期は5秒間隔から始め、指数バックオフで最大30秒に増やすのが推奨です。無限ループを避けるため、最大待機時間（通常30分）を設定します。

**Q: 完了通知（webhook）はサポートされている？**

A: 現在のところ、Interactions APIではポーリングのみです。Webhook機能は開発中のため、定期的に公式ドキュメントを確認してください。

**Q: Background Execution中にクライアントがクラッシュしたら？**

A: `interaction_id`を保存しておけば、後から別のクライアントでポーリング再開可能です。ステート管理が有効であれば、会話コンテキストも保持されます。

**Q: Deep Research のみ Background Execution が必要？**

A: いいえ。複数ツール呼び出し、複雑な推論、データベース検索など、数秒以上の処理ならBackground Executionの恩恵を受けます。

**Q: 同時に複数の Background Task を実行できる？**

A: はい。複数の`interaction_id`を管理して並列ポーリングすれば、スループットが向上します。
