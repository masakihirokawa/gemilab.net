「URL を貼ったのに、答えがどこにでも書いてある一般論で終わっている」——URL Context を組み込んだ要約機能を試していると、そんな夜が訪れることがあります。ログを開いても例外は出ていません。HTTP は 200 で、本文もそれらしく返ってきます。ただ、肝心の記事の中身がどこにも反映されていないのです。

最初のうち、私はこうした場面でプロンプトの言い回しばかりを直そうとしました。結果は芳しくありませんでした。原因はプロンプトではなく、**ツールが動いていない**か、**動いたけれど取得に失敗している**かのどちらかだったからです。

**「答えの質」を疑う前に、「取得の事実」を確認するのが先です。** いまはこの線引きで切り分けています。

導入の手順は公式ドキュメントの URL Context の章が一次情報になります。ここでは、動かないときの確認順と、公式に書かれている上限・非対応コンテンツを手元に置いておきます。

## 先に押さえる、公式ドキュメントの上限と非対応

切り分けの前に、「そもそも仕様として読めないもの」を確認しておくと、無駄な調査を省けます。公式ドキュメントには次の内容が記載されています（記載は執筆時点の確認で、モデル一覧や数値は変わる可能性があります）。

<table>
<thead><tr><th>項目</th><th>公式の記載</th></tr></thead>
<tbody>
<tr><td>1 リクエストの URL 数</td><td>最大 20 件</td></tr>
<tr><td>1 URL あたりの取得サイズ</td><td>最大 34MB</td></tr>
<tr><td>対応コンテンツ</td><td>HTML・JSON・プレーンテキスト・XML・CSS・JavaScript・CSV・RTF、画像（PNG / JPEG / BMP / WebP）、PDF</td></tr>
<tr><td>非対応</td><td>有料会員限定コンテンツ、YouTube 動画、Google ドキュメント／スプレッドシートなどの Workspace ファイル、動画・音声ファイル、ログインが必要なページ</td></tr>

この表で、症状の半分はほぼ片づきます。開発中に <code>localhost</code> の URL を渡していた、ログイン後のページを読ませようとしていた——そうした場合は、コードを直しても取得できません。**仕様の外にあるものは、仕様の内側へ持ってくる**しかないのです。

## まず確認する3つの基本

順番に確認するのがおすすめです。

**1. ツール宣言が正しく入っているか**

ツールの宣言形式は SDK のバージョンで書き方が変わります。公式ドキュメントでは現在、Interactions API 向けに <code>tools=[{"type": "url_context"}]</code> の形が示されています。従来の <code>generate_content</code> を使っている場合は、お使いの SDK のドキュメントに沿った書き方になっているかを確認してください。Function Calling と混在させる場合は、ツール配列の構造が崩れて URL Context だけが無視されていないかも見てください。

**2. プロンプトに URL が素のテキストで書かれているか**

URL Context は、プロンプト本文に含まれる URL を検出して取得します。独自タグで囲んだり、JSON にエンコードしたりすると、検出されない場合があります。`https://example.com/article` をそのまま書いてください。

**3. 取得結果のメタデータを毎回ログに出しているか**

応答の質を疑う前に、実際に取得できた URL と、そのステータスを確認します。ここが空なら、ツールが起動していないか、URL が検出されていません。

```python
from google import genai
from google.genai import types

client = genai.Client()

response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="次の記事の要点を3つに整理してください: https://ai.google.dev/gemini-api/docs/url-context",
    config=types.GenerateContentConfig(
        tools=[types.Tool(url_context=types.UrlContext())],
    ),
)

# 必ずメタデータを確認する（SDK のバージョンによりフィールド名が異なる場合があります）
meta = response.candidates[0].url_context_metadata
if meta is None or not meta.url_metadata:
    print("取得結果が空です。ツールが起動していません")
else:
    for entry in meta.url_metadata:
        print(entry.retrieved_url, entry.url_retrieval_status)
print("---")
print(response.text)
```

成功していれば、各 URL に <code>URL_RETRIEVAL_STATUS_SUCCESS</code> が並びます。<code>_ERROR</code> などが出ている場合は、後述のサイト側要因を疑います。

メタデータが <code>None</code> のまま返ることもあるため、上のコードのようにまず空の判定を入れておくと、肝心なときに <code>AttributeError</code> で止まらずに済みます。

## 症状別の原因切り分け

**症状A: 応答に URL の内容が反映されていない／一般論しか返ってこない**

メタデータが空であれば、ツール自体が呼ばれていません。疑う順番は次のとおりです。

- プロンプトの指示が弱く（「これを参考に」程度）、モデルが取得の必要性を感じなかった
- URL が短縮 URL（bit.ly 系）で、展開先まで追ってもらえなかった
- <code>system_instruction</code> に「外部リソースを参照しない」と書いてしまっている

「次の URL の内容を取得してから回答してください」と明示するだけで、挙動が変わることがあります。短縮 URL は事前に展開しておくのが確実です。

**症状B: メタデータに URL は出るが status が `_ERROR`**

URL は検出されたものの、取得に失敗したパターンです。

- 対象サイトの <code>robots.txt</code> がクローラーを拒否している
- 認証必須のページ（ログイン後の画面、社内 Wiki など）を渡している
- WAF が Bot トラフィックとして弾いている
- JavaScript で後から本文を描画する SPA で、初期 HTML が空に近い

社内ツールや限定公開ページは、上の表のとおり仕様上読めません。対象を公開ページへ書き出すか、Files API でファイルとして渡す方針に切り替えます。

**症状C: タイムアウトする／極端に遅い**

公式の上限は 1 リクエスト 20 件ですが、上限まで詰め込むかどうかは別の話です。件数が増えるほど、遅い 1 件に全体が引きずられる可能性が高まり、入力トークンも膨らみます。私は、まず少数の URL で成功を確認してから増やし、分割して投げる運用にしています。個人開発のアプリで、他社のストア規約や SDK の更新情報を要約させる用途でも、同じ考え方を採っています。件数の目安は、お使いのサイトの応答速度で変わりますので、ログで自分の数字を取ってください。

タイムアウトそのものの扱いは[Gemini API の DEADLINE_EXCEEDED エラー対処ガイド](/articles/gemini-api/gemini-api-deadline-exceeded-error-fix-guide)に整理してあります。

## 取得できないサイトの典型と回避策

「公式仕様では読めるはずなのに、特定のドメインだけ失敗する」という現象は、運用を始めると必ず出会います。

- **大手ニュースサイトの記事ページ**: アクセスポリシー上、クローラーに 401/403 を返す場合があります。RSS や提携 API が筋です
- **X や LinkedIn のタイムライン**: ログイン必須のため、取得できません
- **JS 描画中心の公開ページ**: URL は公開でも、本文が初期 HTML に存在しないことがあります
- **有料会員限定の記事**: 仕様上の非対応です

JS 描画のページは、自前のヘッドレスブラウザで描画済み HTML を保存し、Files API 経由で渡す構成が確実です。

## URL Context を使わない判断もある

動かないものを無理に動かす前に、タスクに合うかを見直す価値があります。

- 同じ URL を毎回取得する運用は、自前のキャッシュ層のほうが速く、入力トークンも減らせます
- 法的・規約上、自動取得が制限される情報は、そもそも使いません
- 構造化抽出が目的なら、<code>responseSchema</code> などと組み合わせる前提で設計します
- 検索を起点にしたい場合は、Grounding のほうが適しています。両者は同じ <code>tools</code> 配列に並べて使うこともできます

Grounding を使った抽出の組み立ては[Grounding と構造化出力でリアルタイムデータを抽出する](/articles/gemini-api/gemini-api-grounding-structured-output-realtime-data-extraction)が参考になります。

## 本番で入れておきたい防御的な実装

```python
def fetch_with_url_context(client, model, prompt: str, urls: list[str]) -> dict:
    """URL Context で要約し、URL ごとの取得結果も返す。"""
    full_prompt = f"{prompt}\n\n参考 URL:\n" + "\n".join(urls)

    resp = client.models.generate_content(
        model=model,
        contents=full_prompt,
        config=types.GenerateContentConfig(
            tools=[types.Tool(url_context=types.UrlContext())],
            temperature=0.2,
        ),
    )

    meta = resp.candidates[0].url_context_metadata
    entries = meta.url_metadata if meta and meta.url_metadata else []
    fetched = [
        {"url": m.retrieved_url, "status": str(m.url_retrieval_status)}
        for m in entries
    ]
    failed = [f for f in fetched if "SUCCESS" not in f["status"]]
    # 依頼した URL のうち、結果に現れなかったものも失敗として数える
    seen = {f["url"] for f in fetched}
    missing = [u for u in urls if u not in seen]
    return {"text": resp.text, "fetched": fetched, "failed": failed, "missing": missing}
```

ポイントは <code>missing</code> です。5 件渡して 3 件分の結果しか返らない状況は、<code>failed</code> だけ見ていると見落とします。呼び出し側に「どれが取れて、どれが取れなかったか」を必ず返し、画面には「このソースは取得できなかったためスキップしました」と出せるようにしておきます。**黙って 5 件中 2 件が落ちている状態が、いちばん怖い**のです。

## 観測の習慣

URL Context の不具合は、開発中はほとんど顔を出さず、利用が増えて初めて表に出る性質があります。

1 つ目は、取得ステータスを自由文のログに混ぜず、構造化フィールドで残すことです。ドメイン別のエラー率を出すパネルが 1 枚あれば、劣化に気づくのが早くなります。

2 つ目は、対象ドメインを許可リストで絞ることです。ユーザー入力から予期しない URL が流れ込むと、想定外のページを読んでしまいます。自社ドキュメントと、信頼できる参照先だけに限定します。

3 つ目は、「URL を渡したのにメタデータが 0 件」を通知対象にすることです。これはソフトエラーではなく、ツールが動いていない確実な異常です。

## 確認チェックリスト

上から順に確認し、1 つでも外れたらそこを先に直します。

- 取得結果のメタデータを毎回ログに出している
- ツール宣言が、お使いの SDK の書き方になっている
- URL が素のテキストで書かれている（タグ・JSON 化していない）
- 短縮 URL を使っていない
- <code>localhost</code>・社内ネットワーク・ログイン必須ページを渡していない
- 有料会員限定・YouTube・Workspace ファイル・動画／音声を渡していない
- <code>system_instruction</code> で外部参照を禁止していない
- 本文が JS 描画のみのページではない
- URL ごとの取得ステータスと、結果に現れなかった URL を呼び出し側へ返している

プロンプトの書き換えやモデルの変更に手を付けるのは、この 9 項目が揃ってからにします。

## 次のアクション

今日のうちにできることは 1 つです。手元の呼び出しコードに、メタデータが空だったときのログ出力を足してみてください。そこから見えるものが、原因の半分を教えてくれます。

仕組みが安定したら、公式の変更履歴から自分の使うモデルの廃止予告だけを拾う[廃止予告レーダーの組み立て](/articles/gemini-api/gemini-url-context-deprecation-radar-changelog-grounded-impact-diff)のように、URL Context の活かし方を一歩進めることもできます。「動かない」を一つずつ潰した経験が、そのまま応用の土台になっていくのだと思います。
