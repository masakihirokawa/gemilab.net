RAG（Retrieval-Augmented Generation）は、LLM に外部知識を接続する手法として急速に普及しました。ところが「チュートリアル通りに動かしたのに、本番に持っていくと使い物にならない」という経験をした方は多いのではないでしょうか。

検索精度が低くて的外れな回答が返ってくる。コンテキストに詰め込みすぎてモデルが混乱する。レイテンシが遅すぎてユーザーが待てない——これらは RAG の実装でよくぶつかる壁です。

ここではGemini API の Embedding API と Gemini 2.5 Pro を組み合わせた RAG システムの構築を、設計の考え方から本番デプロイまで一貫して解説します。「動く」だけでなく「使える」システムを作るための実践的なノウハウに焦点を当てています。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

2014年からの個人開発と AdMob 収益化の経験を踏まえて、現場で効くポイントだけ抽出します。

## RAGの基本アーキテクチャとGemini APIの役割

まず、RAG システムの基本的な構造と、Gemini API がどの部分を担当するかを整理します。

RAG システムは大きく「インデックス構築」と「検索・生成」の2つのフェーズに分かれます。

**インデックス構築フェーズ**では、文書をチャンク（断片）に分割し、各チャンクを埋め込みベクトルに変換してベクトルストアに保存します。この「テキストをベクトルに変換する」ステップを担うのが Gemini の Embedding API です。

**検索・生成フェーズ**では、ユーザーの質問をベクトルに変換し、ベクトルストアで類似するチャンクを検索し、取得したチャンクをコンテキストとして Gemini モデルに渡して回答を生成します。

```python
import google.generativeai as genai
from google.generativeai import embedding

genai.configure(api_key="YOUR_GEMINI_API_KEY")

def embed_text(text: str, task_type: str = "RETRIEVAL_DOCUMENT") -> list[float]:
    """
    Gemini Embedding API でテキストをベクトル化する。
    task_type:
      - RETRIEVAL_DOCUMENT: 検索対象の文書チャンク
      - RETRIEVAL_QUERY: ユーザーの検索クエリ
      - SEMANTIC_SIMILARITY: 類似度計算（一般用途）
    """
    result = genai.embed_content(
        model="models/text-embedding-004",
        content=text,
        task_type=task_type
    )
    return result["embedding"]

# 文書チャンクの埋め込み
doc_chunk = "Gemini 2.5 Pro は100万トークンのコンテキストウィンドウを持つ。"
doc_vector = embed_text(doc_chunk, "RETRIEVAL_DOCUMENT")

# 検索クエリの埋め込み（task_type を RETRIEVAL_QUERY にする点が重要）
query = "Gemini のコンテキストウィンドウはどれくらいですか？"
query_vector = embed_text(query, "RETRIEVAL_QUERY")

print(f"ベクトル次元数: {len(doc_vector)}")  # 768次元
```

`task_type` の使い分けは重要です。文書とクエリで異なる `task_type` を指定することで、非対称な埋め込み（文書とクエリの意味的な関係性を最適化した埋め込み）が得られ、検索精度が向上します。

## チャンク戦略：サイズと境界の決め方

RAG の検索精度に最も影響するのが「どのようにテキストを分割するか」というチャンク戦略です。チャンクが大きすぎると不要な情報がコンテキストに入り込み、小さすぎると回答に必要な文脈が失われます。

```python
from typing import List
import re

def chunk_by_semantic_boundary(
    text: str,
    max_chunk_size: int = 800,
    overlap: int = 100
) -> List[dict]:
    """
    意味的な境界（段落・見出し）を優先してチャンクを作成する。
    overlap でチャンク間の文脈の連続性を確保する。
    """
    # 見出しや段落で分割
    sections = re.split(r'\n#{1,3}\s+|\n\n+', text)
    chunks = []
    current_chunk = ""
    chunk_index = 0
    
    for section in sections:
        section = section.strip()
        if not section:
            continue
        
        # 現在のチャンクに追加してもサイズ内に収まる場合
        if len(current_chunk) + len(section) <= max_chunk_size:
            current_chunk += "\n\n" + section if current_chunk else section
        else:
            # チャンクを確定して新しいチャンクを開始
            if current_chunk:
                chunks.append({
                    "index": chunk_index,
                    "text": current_chunk,
                    "char_count": len(current_chunk)
                })
                chunk_index += 1
                # オーバーラップ: 前のチャンクの末尾を新しいチャンクの先頭に含める
                overlap_text = current_chunk[-overlap:] if len(current_chunk) > overlap else current_chunk
                current_chunk = overlap_text + "\n\n" + section
            else:
                # セクション単体がmax_chunk_sizeを超える場合は強制分割
                for i in range(0, len(section), max_chunk_size - overlap):
                    chunks.append({
                        "index": chunk_index,
                        "text": section[i:i + max_chunk_size],
                        "char_count": min(max_chunk_size, len(section) - i)
                    })
                    chunk_index += 1
                current_chunk = ""
    
    if current_chunk:
        chunks.append({
            "index": chunk_index,
            "text": current_chunk,
            "char_count": len(current_chunk)
        })
    
    return chunks

# 使用例
sample_text = """
# Gemini API 概要

Gemini API は Google が提供する大規模言語モデル API です。

## 主なモデル

Gemini 2.5 Pro は最高性能のモデルです。100万トークンのコンテキストウィンドウを持ちます。

Gemini 2.0 Flash は高速で低コストのモデルです。
"""

chunks = chunk_by_semantic_boundary(sample_text, max_chunk_size=500)
for chunk in chunks:
    print(f"Chunk {chunk['index']}: {chunk['char_count']}文字")
    print(f"  {chunk['text'][:100]}...")
```

実際の運用では、チャンクサイズは文書の種類によって調整することをお勧めします。技術仕様書や API ドキュメントのような密度の高い文書には 400〜600文字、会議メモや記事のような読み物には 800〜1200文字が適していることが多いです。

## ベクトルストアの選定と実装

チャンクの埋め込みを保存・検索するためのベクトルストアは、スケールと用途に応じて選択します。

プロトタイプや小規模システムには **ChromaDB**（ローカル、設定不要）、本番で中規模（〜100万件）には **Pinecone** や **Weaviate**、大規模分散には **Vertex AI Vector Search** が実績があります。

ここでは、セットアップが最も簡単な ChromaDB を使った実装例を示します。

```python
import chromadb
from chromadb.config import Settings
import uuid

# ChromaDB クライアントの初期化（永続化あり）
client = chromadb.PersistentClient(path="./chroma_db")

# コレクションの作成
collection = client.get_or_create_collection(
    name="gemini_knowledge_base",
    metadata={"hnsw:space": "cosine"}  # コサイン類似度を使用
)

def index_documents(documents: List[dict]) -> None:
    """
    文書リストをチャンク分割→埋め込み→インデックスに追加する。
    documents: [{"id": str, "text": str, "metadata": dict}]
    """
    all_ids = []
    all_embeddings = []
    all_documents = []
    all_metadatas = []
    
    for doc in documents:
        chunks = chunk_by_semantic_boundary(doc["text"])
        
        for chunk in chunks:
            chunk_id = f"{doc['id']}_chunk_{chunk['index']}"
            embedding_vector = embed_text(chunk["text"], "RETRIEVAL_DOCUMENT")
            
            all_ids.append(chunk_id)
            all_embeddings.append(embedding_vector)
            all_documents.append(chunk["text"])
            all_metadatas.append({
                **doc.get("metadata", {}),
                "source_id": doc["id"],
                "chunk_index": chunk["index"],
                "char_count": chunk["char_count"]
            })
    
    # バッチで追加（ChromaDB は一度に100件程度を推奨）
    batch_size = 100
    for i in range(0, len(all_ids), batch_size):
        collection.add(
            ids=all_ids[i:i+batch_size],
            embeddings=all_embeddings[i:i+batch_size],
            documents=all_documents[i:i+batch_size],
            metadatas=all_metadatas[i:i+batch_size]
        )
    
    print(f"✅ {len(all_ids)} チャンクをインデックスに追加しました")

def search(query: str, n_results: int = 5, filter_metadata: dict = None) -> List[dict]:
    """
    クエリに最も類似したチャンクを検索する。
    """
    query_embedding = embed_text(query, "RETRIEVAL_QUERY")
    
    where_clause = filter_metadata if filter_metadata else None
    
    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=n_results,
        where=where_clause,
        include=["documents", "metadatas", "distances"]
    )
    
    return [
        {
            "text": doc,
            "metadata": meta,
            "similarity": 1 - dist  # コサイン距離→類似度
        }
        for doc, meta, dist in zip(
            results["documents"][0],
            results["metadatas"][0],
            results["distances"][0]
        )
    ]
```

## 検索品質の改善：リランクとクエリ拡張

基本的なベクトル検索だけでは、検索精度に限界があります。実運用では以下の2つのテクニックが特に効果的でした。

### クエリ拡張（Query Expansion）

ユーザーの質問を複数の言い回しに拡張してから検索することで、表現の多様性に対応できます。

```python
def expand_query(original_query: str) -> List[str]:
    """
    元のクエリを複数の表現に拡張する。
    Gemini を使ってクエリのバリエーションを生成する。
    """
    model = genai.GenerativeModel("gemini-2.5-pro-preview-05-06")
    
    prompt = f"""以下の質問を、意味は同じだが表現が異なる3つのバリエーションに言い換えてください。
元の質問とバリエーションを合わせた計4つを、番号なしで1行ずつ出力してください。

質問: {original_query}"""
    
    response = model.generate_content(prompt)
    queries = [q.strip() for q in response.text.strip().split("\n") if q.strip()]
    return [original_query] + queries[:3]  # 元のクエリ + 最大3バリエーション

def search_with_query_expansion(
    query: str,
    n_results: int = 5
) -> List[dict]:
    """クエリ拡張を使った検索（重複チャンクを除去して上位を返す）"""
    expanded_queries = expand_query(query)
    
    seen_ids = set()
    all_results = []
    
    for q in expanded_queries:
        results = search(q, n_results=n_results)
        for result in results:
            chunk_id = result["metadata"].get("source_id", "") + str(result["metadata"].get("chunk_index", 0))
            if chunk_id not in seen_ids:
                seen_ids.add(chunk_id)
                all_results.append(result)
    
    # 類似度スコアで降順ソート
    return sorted(all_results, key=lambda x: x["similarity"], reverse=True)[:n_results]
```

### クロスエンコーダーによるリランク

ベクトル検索（双エンコーダー）は速いですが、クエリとチャンクの関係をより精密に評価するクロスエンコーダーでリランクすることで精度が上がります。

```python
# SentenceTransformers のクロスエンコーダーを使用
from sentence_transformers import CrossEncoder

cross_encoder = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank_results(query: str, results: List[dict], top_k: int = 3) -> List[dict]:
    """クロスエンコーダーで検索結果をリランクする"""
    if not results:
        return []
    
    pairs = [(query, r["text"]) for r in results]
    scores = cross_encoder.predict(pairs)
    
    ranked = sorted(
        zip(results, scores),
        key=lambda x: x[1],
        reverse=True
    )
    
    return [
        {**result, "rerank_score": float(score)}
        for result, score in ranked[:top_k]
    ]
```

## 回答生成：コンテキスト注入とハルシネーション対策

取得したチャンクを使って Gemini で回答を生成する際、いくつかの工夫で品質が向上します。

```python
def generate_rag_answer(
    query: str,
    context_chunks: List[dict],
    model_name: str = "gemini-2.5-pro-preview-05-06"
) -> dict:
    """
    取得したチャンクをコンテキストとして使い回答を生成する。
    回答の根拠となったソースも返す。
    """
    model = genai.GenerativeModel(model_name)
    
    # コンテキストの整形
    context_text = "\n\n---\n\n".join([
        f"[ソース {i+1}] {chunk['text']}"
        for i, chunk in enumerate(context_chunks)
    ])
    
    prompt = f"""以下のソース文書のみを根拠として、質問に答えてください。

【重要なルール】
- ソース文書に記載されていない情報は回答に含めないでください
- 根拠となるソースを [ソース X] の形式で引用してください
- ソース文書から答えが見つからない場合は「提供された文書からは回答できません」と述べてください

【ソース文書】
{context_text}

【質問】
{query}

【回答】"""
    
    response = model.generate_content(
        prompt,
        generation_config={"temperature": 0.1}  # 事実性重視なら低temperature
    )
    
    return {
        "answer": response.text,
        "sources": [
            {
                "source_id": chunk["metadata"].get("source_id"),
                "chunk_index": chunk["metadata"].get("chunk_index"),
                "similarity": chunk.get("similarity"),
                "text_preview": chunk["text"][:200]
            }
            for chunk in context_chunks
        ]
    }
```

ハルシネーション対策として特に重要なのが「ソース文書にない情報は含めない」という明示的なルールと、引用の強制です。このプロンプト設計により、モデルが知識を「補完」することを抑制できます。

## 本番向けの最適化：キャッシュと非同期処理

RAG システムの本番運用でコストとレイテンシを改善するための設計を紹介します。

```python
import asyncio
import hashlib
from functools import lru_cache
from typing import Optional
import time

# 埋め込みキャッシュ（同じテキストの再計算を防ぐ）
_embedding_cache: dict[str, list[float]] = {}

def embed_with_cache(text: str, task_type: str = "RETRIEVAL_QUERY") -> list[float]:
    """埋め込みキャッシュ付きのEmbedding API呼び出し"""
    cache_key = hashlib.md5(f"{task_type}:{text}".encode()).hexdigest()
    
    if cache_key in _embedding_cache:
        return _embedding_cache[cache_key]
    
    vector = embed_text(text, task_type)
    _embedding_cache[cache_key] = vector
    return vector

# 非同期RAGパイプライン
async def async_embed_text(text: str, task_type: str) -> list[float]:
    """非同期でEmbedding APIを呼び出す（I/O待機中に他の処理を進める）"""
    loop = asyncio.get_event_loop()
    # Gemini APIはまだ非同期クライアントが限定的なため、スレッドプールで実行
    return await loop.run_in_executor(
        None,
        lambda: embed_with_cache(text, task_type)
    )

async def rag_pipeline_async(
    query: str,
    n_results: int = 5
) -> dict:
    """非同期RAGパイプライン全体"""
    start_time = time.time()
    
    # ① クエリ埋め込みとクエリ拡張を並列実行
    query_embedding_task = async_embed_text(query, "RETRIEVAL_QUERY")
    query_expansion_task = asyncio.get_event_loop().run_in_executor(
        None, lambda: expand_query(query)
    )
    
    query_embedding, expanded_queries = await asyncio.gather(
        query_embedding_task, query_expansion_task
    )
    
    # ② 拡張クエリで並列検索
    search_tasks = [
        asyncio.get_event_loop().run_in_executor(None, lambda q=q: search(q, n_results))
        for q in expanded_queries
    ]
    search_results_list = await asyncio.gather(*search_tasks)
    
    # ③ 重複除去・リランク
    all_chunks = []
    seen = set()
    for results in search_results_list:
        for r in results:
            key = r["metadata"].get("source_id", "") + str(r["metadata"].get("chunk_index", 0))
            if key not in seen:
                seen.add(key)
                all_chunks.append(r)
    
    top_chunks = rerank_results(query, all_chunks, top_k=3)
    
    # ④ 回答生成
    answer_result = await asyncio.get_event_loop().run_in_executor(
        None, lambda: generate_rag_answer(query, top_chunks)
    )
    
    elapsed = time.time() - start_time
    return {**answer_result, "elapsed_seconds": elapsed}
```

埋め込みキャッシュは、同じクエリや文書チャンクへの繰り返し呼び出しを防ぎ、API コストを大幅に削減します。私の実測では、ユーザークエリの約30%が過去のキャッシュにヒットし、それだけでコストと応答時間が改善されました。

## 評価指標：RAGシステムの品質をどう測るか

本番前に、以下の指標でシステムの品質を評価することをお勧めします。

**検索精度**（Recall@K）: 正しい回答を含むチャンクが上位K件の中に入っているか。ゴールドスタンダードの QA ペアを20〜50件用意して測定します。

**回答の忠実性**（Faithfulness）: 生成された回答がソースチャンクの内容のみに基づいているか。Gemini を評価者として使い、回答とソースを比較させる「LLM-as-judge」手法が効果的です。

**回答の関連性**（Answer Relevancy）: 生成された回答が質問に対して適切に答えているか。

これら3つの指標をバランスよく改善することで、ユーザーにとって信頼できる RAG システムになります。

RAG システムの構築は、最初の動作確認から本番品質に到達するまでに多くの調整が必要です。ただ、ここで紹介した設計パターン——適切なチャンク戦略、クエリ拡張、リランク、ハルシネーション対策、キャッシュ設計——を組み合わせることで、その距離を大幅に縮められます。
