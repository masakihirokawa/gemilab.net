個人開発でチャット形式の問い合わせ補助を自動運用に組み込んで数週間が経った頃、月次のコスト内訳を眺めていて手が止まりました。全体は想定内なのに、一つの会話 ID だけが突出して重いのです。中身をたどると、ある一回のターンで差し込んだ製品カタログの抜粋が約 40KB あり、そのあと交わした十数往復のすべてが、その 40KB を律儀に引きずっていたのです。

`previous_interaction_id` に切り替えたのは「毎回履歴を送らなくて済むから安くなる」と考えたからでした。実際、送信ペイロードは小さくなります。けれど請求は減りませんでした。むしろ、手元で履歴を組み立てていた頃なら一行で捨てられたはずの重い一塊が、サーバーに預けたことで捨てられなくなっていたのです。

この記事は、その分岐点の設計についての記録です。会話状態をサーバーに預けるべきか、手元に置いて刈り込めるようにしておくべきか。Interactions API の `previous_interaction_id` が省いてくれるものと、代わりに預けてしまうものを切り分け、状況で使い分けるための薄いラッパーを、動くコードとともに残しておきます。

## previous_interaction_id が省くもの、預けるもの

Interactions API では、直前の応答が返す interaction の ID を次のリクエストの `previous_interaction_id` に渡すと、それまでの会話文脈をサーバー側が保持したまま続きを処理してくれます。手元で `messages` の配列を積み上げて毎回丸ごと送り直す、あの反復から解放される仕組みです。

省けるものは明快です。往復のたびに肥大していく履歴配列の送信、その組み立てとトリミングのロジック、そして「どこまで送ったか」を追う状態管理。single-turn の理解から状態を持つ会話まで、同じ入り口の下で扱えるようになります。

一方で、静かに預けてしまうものがあります。それは<strong>「文脈の編集権」</strong>です。手元に履歴を持っていれば、三ターン前のツール出力が不要になった瞬間に、その要素だけを配列から抜いて、あるいは短い要約に差し替えて次を送れます。ところが会話状態がサーバー側の連鎖として保持されていると、いったん連鎖に入った重い一塊を、あとから外科的に抜く手立てがありません。連鎖を継ぐ限り、それは文脈として生き続けます。

省けるのは「送信の手間」、預けてしまうのは「刈り込む自由」。この非対称が、冒頭のコスト膨張の正体でした。

## 直感に反した費用の増え方

サーバー側に状態を預ければ通信が減ります。だから安くなるはずでした。この推論のどこがずれていたのかを、トークンの動きで具体的に追ってみます。

課金されるのは通信量ではなく、各ターンでモデルが読むトークンの総量です。会話状態をサーバーが保持していても、モデルは応答生成のたびに保持された文脈を入力トークンとして読み直します。つまり<strong>「送らない」ことと「読まれない」ことは別</strong>です。ここを取り違えていました。

数字で置くと分かりやすくなります。あるターンで約 40KB、日本語混じりでおよそ 18,000 トークン相当のカタログ抜粋を差し込んだとします。その後 12 往復続けたなら、サーバー側連鎖ではこの 18,000 トークンが基本的に毎ターンの入力に乗り続けます。ごく粗い見積もりでも 18,000 × 12 で 21 万トークン超が、最初の一回で用が済んだはずの一塊のために積み上がる計算です。

手元で履歴を持っていれば、カタログ抜粋を「該当製品は型番 X・在庫あり」程度の一行要約に差し替え、以降のターンからは 400 トークン前後で済ませられます。要約後のおよそ400トークンに対し、引きずり続ければおよそ18,000トークン。同じ会話の同じ結論に至るのに、入力がおよそ45倍に膨らむ計算です。プレビュー段階の軽い会話では気づけず、実運用で長い会話が混ざり始めてから初めて表面化する種類のずれでした。

直感に反していたのは、<strong>「軽くするために預けた選択が、軽くするための手段を同時に手放していた」</strong>という点です。本番運用で長い会話が増えるほど効いてくる落とし穴で、通信量ではなく読まれるトークン量を基準に設計で回避するほかありません。

## 刈り込める設計に戻す — ハイブリッドの薄いラッパー

では常に手元で履歴を持てばよいかというと、それも極端です。短くて素直な会話では `previous_interaction_id` の身軽さが効きます。往復のたびに全履歴を送る設計は、それはそれで通信と組み立てのコストを払い続けます。

そこで、普段はサーバー側状態に任せ、重い一塊が入ったターンだけ連鎖を切って手元で組み直す、というハイブリッドに落ち着きました。判断の軸は一つ、<strong>「このターンの出力を、次のターン以降も丸ごと引きずる価値があるか」</strong>です。

以下は、その判断を一箇所に閉じ込めた薄いラッパーです。呼び出し側は会話 ID を渡すだけで、連鎖を継ぐか切り直すかを意識せずに済みます。API のメソッド名や引数は提供形態で変わり得るため、実際の呼び出しは公式ドキュメントで確認してください。ここで示したいのは、その一段上の「刈り込む判断をどこに置くか」の設計です。

```python
import re
from dataclasses import dataclass, field

# 1ターンのツール出力がこの推定トークン数を超えたら、
# 連鎖に載せ続けず要約へ差し替える判断に入る
HEAVY_TURN_TOKEN_THRESHOLD = 4000


def estimate_tokens(text: str) -> int:
    """日本語混在テキストの粗いトークン見積もり。
    厳密なトークナイザではなく、閾値判定に足る近似で十分。
    英数字は約4文字/トークン、それ以外(主に日本語)は約1.6文字/トークンとして合算する。"""
    ascii_chars = len(re.findall(r"[\x00-\x7F]", text))
    other_chars = len(text) - ascii_chars
    return int(ascii_chars / 4 + other_chars / 1.6)


@dataclass
class Conversation:
    """会話ごとの状態。server_interaction_id が生きていれば連鎖を継ぐ。
    切り直した場合はここに手元要約(carryover)を蓄える。"""
    server_interaction_id: str | None = None
    carryover: list[str] = field(default_factory=list)  # 手元に残す短い要約


def summarize_heavy_output(raw: str) -> str:
    """重い出力を、次ターン以降に引きずる価値のある最小限へ畳む。
    実際にはここに軽量モデルの1回呼び出しやルールベース抽出を置く。
    要点は「何が確定したか」だけを残し、原文は捨てること。"""
    head = raw.strip().splitlines()[0][:80] if raw.strip() else ""
    return f"[前ターンのツール出力を要約] {head} … 詳細は破棄済み"


def send_turn(conv: Conversation, user_text: str, tool_output: str | None,
              call_model, tool_roundtrip_open: bool = False
              ) -> tuple[str, Conversation]:
    """1ターンを送る。call_model は実際の Interactions API 呼び出しを包む関数で、
    (prompt_parts, previous_interaction_id) を受け取り (reply_text, interaction_id) を返す。
    tool_roundtrip_open=True は「モデルが関数呼び出しを返し、その結果をまだ返していない」
    途中状態を表す。この間に連鎖を切ると呼び出しと結果が離れ、応答が噛み合わなくなる。"""

    heavy = tool_output is not None and \
        estimate_tokens(tool_output) > HEAVY_TURN_TOKEN_THRESHOLD

    # 切り直してよいのは、ツールの往復が閉じたあとだけ
    if (heavy and not tool_roundtrip_open) or conv.server_interaction_id is None:
        # 連鎖を切り直す: これまでの carryover を手元で先頭に積み、
        # 重いツール出力はモデルに渡す前に要約へ差し替える
        parts: list[str] = list(conv.carryover)
        if tool_output is not None:
            folded = summarize_heavy_output(tool_output) if heavy else tool_output
            parts.append(folded)
            if heavy:
                conv.carryover.append(folded)  # 次回以降に引きずるのは要約だけ
        parts.append(user_text)
        reply, new_id = call_model(prompt_parts=parts, previous_interaction_id=None)
    else:
        # happy path: サーバー側連鎖に素直に継ぐ。手元は空でよい
        parts = [tool_output, user_text] if tool_output else [user_text]
        reply, new_id = call_model(prompt_parts=parts,
                                   previous_interaction_id=conv.server_interaction_id)

    conv.server_interaction_id = new_id
    return reply, conv
```

肝は `send_turn` の分岐だけです。普段はサーバー側連鎖に継ぐので手元は身軽なまま。重い出力が来たターンに限り、連鎖を一度切って `summarize_heavy_output` で畳んだ要約を `carryover` に移し、以降はその要約だけを引きずります。原文の 40KB は、そのターンでモデルに読ませた時点で役目を終えます。次のターンには連れて行きません。

## 運用して見えた勘所

実際に回してみると、コード以外のところで効いた判断がいくつかありました。

第一に、<strong>閾値は保守的に置く</strong>方が扱いやすいという点です。当初は 8,000 トークン相当で切っていましたが、切り直しのたびに要約用の軽量モデル呼び出しが一回増えるため、切り替えが多すぎると今度はその呼び出しコストが積もります。かといって高すぎれば、今度は引きずりが復活します。4,000 トークン前後に落として、「日本語で 2〜3 段落を超えるツール出力は畳む」という体感に合わせたところで安定しました。

第二に、<strong>要約の質より「原文を確実に捨てる」ことの方が効きます</strong>。要約を丁寧にしようとすると軽量モデルへの指示が膨らみ、そこがまた新たなコスト源になります。実務では「何が確定したか」の一行が残っていれば会話は続きます。凝った要約より、引きずらない設計そのものが利いていました。

第三に、切り直したターンの応答品質は、事前の心配ほど落ちませんでした。連鎖を切ると文脈が途切れて会話が破綻するのでは、と身構えていたのですが、`carryover` に確定事項の要約さえ積んでおけば、モデルは十分に続きを繋ぎます。むしろ不要な原文が消えたぶん、応答が要点に寄る場面すらありました。ここは予想と逆でした。

## 預けると見えなくなる per-user のコスト

もう一つ、サーバー側状態が気づかれないまま奪っていくものがあります。<strong>ユーザー単位のトークン帰属</strong>です。

手元で履歴を組み立てていた頃は、各リクエストの入力トークンを自分で数えられました。誰の会話がいくら使ったかを、そのまま社内の従量按分に使えます。ところが `previous_interaction_id` に任せると、あるターンの入力トークンには「サーバーが保持している見えない文脈」が含まれ、手元の送信サイズからは総量が読めなくなります。

2026 年 7 月 6 日から、Interactions API の対応呼び出しの実行ログが AI Studio のダッシュボードで確認できるようになりました。各実行ステップと消費が追えるので、まずはここが一次情報になります。ただしダッシュボードのログは保持期間やサンプリングの制約があり、これ自体を課金監査の正本にはできません。

そこで採ったのが二重帳簿です。応答が返すトークン使用量（usage 相当のフィールド）を毎ターン自前のカウンタに `会話ID → 累計トークン` で加算し、そちらを正本にしています。ダッシュボードのログは突き合わせ用の照合先に回します。こうしておくと、月次で「どの会話が重かったか」を自分の数字で言えるようになり、冒頭のような突出も翌月まで気づかない、ということがなくなります。

## 引きずりを数字で捕まえる — 会話IDごとの引きずり率

二重帳簿を始めてから、月次を待たずに異常へ手を伸ばしたくなりました。前の月の請求書で気づくのでは、気づいた時点でもう払い終わっています。

いま毎朝走らせているのは、自前カウンタの JSONL を読んで会話ごとの<strong>引きずり率</strong>を出すだけの小さなスクリプトです。最初のターンの入力トークンを「引きずりゼロの状態」と見なし、最終ターンがその何倍に膨らんだかを見ます。

```python
import json
from collections import defaultdict


def load_ledger(path: str) -> dict[str, list[int]]:
    """自前カウンタの JSONL を会話IDごとの入力トークン列に畳む。
    1行は {"conversation_id": "...", "turn": 3, "input_tokens": 21840} 程度を想定。"""
    per_conv: dict[str, list[int]] = defaultdict(list)
    with open(path, encoding="utf-8") as f:
        for line in f:
            if not line.strip():
                continue
            rec = json.loads(line)
            per_conv[rec["conversation_id"]].append(
                (int(rec.get("turn", 0)), int(rec["input_tokens"]))
            )
    # ターン順に並べ直してトークン列だけ返す
    return {cid: [t for _, t in sorted(turns)] for cid, turns in per_conv.items()}


def drag_report(per_conv: dict[str, list[int]], min_turns: int = 4) -> list[dict]:
    """引きずりが効いている会話を、累積で食われたトークンの多い順に並べる。"""
    rows = []
    for cid, inputs in per_conv.items():
        if len(inputs) < min_turns:
            continue  # 往復が短い会話は引きずる前に終わるので対象外
        base = max(inputs[0], 1)
        # 全ターンが初回と同じ重さだった場合との差分＝累積文脈が食べた分
        carried = sum(inputs) - base * len(inputs)
        rows.append({
            "conversation_id": cid,
            "turns": len(inputs),
            "base_in": base,
            "last_in": inputs[-1],
            "drag_ratio": round(inputs[-1] / base, 1),
            "carried_tokens": max(carried, 0),
        })
    rows.sort(key=lambda r: r["carried_tokens"], reverse=True)
    return rows


if __name__ == "__main__":
    report = drag_report(load_ledger("usage_ledger.jsonl"))
    for row in report[:10]:
        print("{conversation_id}\tturns={turns}\tx{drag_ratio}\t"
              "carried={carried_tokens}".format(**row))
```

並べ替えの軸を `drag_ratio` ではなく `carried_tokens` に置いているのには理由があります。比率だけを見ると、もともと数百トークンしかない軽い会話が桁外れの倍率で上位に来てしまい、請求書に効いていない会話を追いかけることになるのです。実際に払っている分で並べたいときは、絶対量で並べるほうが素直でした。

私の手元で一月分を通したとき、`drag_ratio` が 6 を超えた会話は全体の一割にも届きませんでした。それなのに `carried_tokens` の合計では過半を占めていました。<strong>引きずりは薄く広がらず、数本の会話に固まります。</strong>だとすれば閾値の調整より先に、この上位数本を見にいくほうが早いのだと思います。

もう一つ、切り直しで踏んだ失敗も書き残しておきます。モデルが関数呼び出しを返し、その結果をまだ返していない——ツールの往復が開いたままの状態で連鎖を切ってしまい、呼び出しと結果が離れて応答が噛み合わなくなったことがありました。上のラッパーに `tool_roundtrip_open` を足したのは、この一件があったからです。重さを理由に切ってよいのは、往復が閉じたあとだけでした。

## 状況別の落としどころ

ここまでを、判断の早見に畳んでおきます。

<table>
<thead>
<tr><th>会話の性質</th><th>推奨</th><th>理由</th></tr>
</thead>
<tbody>
<tr><td>短命・往復が少ない</td><td>previous_interaction_id に素直に任せる</td><td>引きずりが積もる前に終わる。身軽さが勝る</td></tr>
<tr><td>長い直線的な会話・重い出力なし</td><td>previous_interaction_id 中心</td><td>刈り込む対象がなく、送信削減の恩恵が大きい</td></tr>
<tr><td>途中で大きなツール出力・検索結果が入る</td><td>ハイブリッド（重いターンで切り直し）</td><td>原文を1ターンで消費し、要約だけ引きずる</td></tr>
<tr><td>分岐や巻き戻しが多い探索的な会話</td><td>手元履歴を基本に</td><td>枝ごとに文脈を編集できる自由が要る</td></tr>
</tbody>
</table>

大切なのは、`previous_interaction_id` を「常に安い選択」と思い込まないことだと考えています。安くなるのは、引きずる文脈が軽いあいだだけです。重い一塊が混ざる会話では、刈り込める設計を手元に残しておくほうを私は選びます。その一点が、そのまま請求書の桁を分けます。

## 次の一歩

まずは手元の会話ログで、一つの会話 ID あたりの累計入力トークンを出してみてください。突出した会話が一つでも見つかれば、そこにはたいてい「一回で用が済んだのに引きずられている重い一塊」が潜んでいます。それが見つかったら、この記事の `send_turn` の分岐だけを先に入れてみてください。閾値は 4,000 トークン前後から始めて、切り替え頻度を見ながら調整すれば十分です。

私自身、まだこの閾値を会話の種類ごとに詰めている最中です。同じように自動運用のコストと向き合っている方の参考になれば嬉しく思います。お読みいただきありがとうございました。
