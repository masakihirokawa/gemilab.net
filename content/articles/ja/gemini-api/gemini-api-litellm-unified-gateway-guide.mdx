複数のAI APIを使い分けているとき、こんな状況に心当たりはないでしょうか。

「タスクによってGeminiとClaudeを切り替えたいけど、呼び出し方がバラバラで管理が大変」
「本番環境でGemini APIがレート制限に引っかかったとき、自動でOpenAIに切り替えたい」

個人開発のアプリでも、いくつかのAI APIを組み合わせることが当たり前になってきた2026年において、この「マルチLLM管理の煩雑さ」は意外と見落とされがちな課題です。LiteLLMはまさにこの問題を解決するために生まれたライブラリで、Gemini・Claude・OpenAI・Mistralなど100以上のモデルを統一したインターフェースで呼び出せます。

Gemini API を実プロダクトで運用してきた知見から、この問題に普段から向き合ってきた立場で、要点を整理します。

累計5,000万ダウンロードのアプリ群に Gemini を組み込んできた経験から、本番運用のコツを整理します。

## LiteLLMとは何か

LiteLLMは、異なるLLMプロバイダーのAPIを共通インターフェースで扱えるPythonライブラリです。OpenAI互換の呼び出し形式を採用しているため、`model`パラメータを変えるだけで別のAIに切り替えられます。

Gemini APIとの相性が特に良い理由の一つは、Google自身がOpenAI互換エンドポイントを提供していることです（詳細は[Gemini APIのOpenAI互換エンドポイント活用ガイド](/articles/gemini-api/gemini-api-openai-compatible-endpoint-guide)を参照してください）。LiteLLMを使えば、この互換レイヤーを意識することなく、ネイティブな`google/gemini-2.5-pro`モデル名でそのまま呼び出せます。

主な特徴をまとめると:

- **統一インターフェース**: プロバイダーが変わっても呼び出しコードはほぼ同じ
- **フォールバック設定**: エラー時に別のモデルへ自動切り替え
- **コスト追跡**: 各モデルの使用量とコストをリアルタイムで把握
- **ロードバランシング**: 複数のAPIキーやモデルへのリクエスト分散

## インストールと初期設定

LiteLLMのインストールは1行です。

```bash
pip install litellm
```

APIキーは環境変数で設定します。複数プロバイダーを使う場合はそれぞれ設定しておきましょう。

```bash
export GEMINI_API_KEY="YOUR_GEMINI_API_KEY"
export ANTHROPIC_API_KEY="YOUR_ANTHROPIC_API_KEY"
export OPENAI_API_KEY="YOUR_OPENAI_API_KEY"
```

## Gemini APIをLiteLLM経由で呼び出す基本

最もシンプルな呼び出し方から見てみましょう。

```python
import litellm

# Gemini 2.5 Proを呼び出す
response = litellm.completion(
    model="gemini/gemini-2.5-pro",
    messages=[
        {"role": "user", "content": "Pythonでフィボナッチ数列を生成するコードを書いてください"}
    ]
)

print(response.choices[0].message.content)
# 期待する出力: フィボナッチ数列を生成するPythonコードと説明
```

`model`の名前が`"gemini/gemini-2.5-pro"`という形式になっているのがポイントです。LiteLLMはプロバイダー名をプレフィックスとして使い、ルーティングを自動処理します。

Gemini 2.5 Flashを使いたい場合は、`model`を変えるだけです。

```python
response = litellm.completion(
    model="gemini/gemini-2.5-flash",
    messages=[{"role": "user", "content": "簡潔に要約してください: ..."}]
)
```

### ストリーミングにも対応

長文生成やチャットUIでストリーミングが必要な場合も、`stream=True`を加えるだけです。

```python
response = litellm.completion(
    model="gemini/gemini-2.5-pro",
    messages=[{"role": "user", "content": "AIの将来について教えてください"}],
    stream=True
)

for chunk in response:
    # チャンクごとにテキストが届く
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)
```

## フォールバック設定でClaudeやOpenAIと並行運用する

LiteLLMの真価が発揮されるのが、フォールバック設定です。Gemini APIがレート制限（429エラー）に達したとき、自動でClaude Sonnetに切り替えるといった構成を、数行のコードで実現できます。

レート制限の対処法については[Gemini APIのレート制限と本番環境エラーハンドリング](/articles/gemini-api/gemini-api-production-error-handling-rate-limit-guide)でも詳しく解説していますが、LiteLLMのフォールバックを使うとより根本的に解決できます。

```python
import litellm

# フォールバックを設定した呼び出し
response = litellm.completion(
    model="gemini/gemini-2.5-pro",
    messages=[{"role": "user", "content": "このコードをレビューしてください: ..."}],
    fallbacks=[
        "anthropic/claude-sonnet-4-6",  # Geminiが失敗したらClaude
        "openai/gpt-4o"                  # Claudeも失敗したらGPT-4o
    ],
    num_retries=2  # 各モデルで2回リトライ
)

print(f"実際に使用したモデル: {response.model}")
print(response.choices[0].message.content)
```

`response.model`で実際にどのモデルが応答したかを確認できるため、ログやデバッグにも役立ちます。私がこの構成を本番に入れてから、Gemini APIのレート制限でユーザーに「エラーが出た」と言われることがほぼなくなりました。

## コスト追跡と使用量の可視化

LiteLLMはレスポンスにコスト情報を自動で付与してくれます。

```python
response = litellm.completion(
    model="gemini/gemini-2.5-pro",
    messages=[{"role": "user", "content": "テスト"}]
)

# トークン使用量とコストを確認
usage = response.usage
print(f"入力トークン: {usage.prompt_tokens}")
print(f"出力トークン: {usage.completion_tokens}")

# コストの計算（単位: USD）
cost = litellm.completion_cost(completion_response=response)
print(f"このリクエストのコスト: ${cost:.6f}")
```

複数リクエストの累積コストを管理したい場合は、コールバック機能を使うとシンプルに集計できます。

```python
import litellm

# コスト集計用のカスタムコールバック
class CostTracker:
    def __init__(self):
        self.total_cost = 0.0
    
    def log_success_event(self, kwargs, response_obj, start_time, end_time):
        cost = litellm.completion_cost(completion_response=response_obj)
        self.total_cost += cost
        print(f"累積コスト: ${self.total_cost:.4f}")

tracker = CostTracker()
litellm.callbacks = [tracker]

# 通常通り呼び出すだけで自動集計される
litellm.completion(
    model="gemini/gemini-2.5-flash",
    messages=[{"role": "user", "content": "Hello"}]
)
```

コスト最適化の観点では、タスクの複雑さに応じてGemini 2.5 ProとFlashを自動で使い分けるロジックと組み合わせるのが効果的です。コスト最適化の詳しい戦略は[Gemini APIのコスト最適化完全ガイド](/articles/gemini-api/gemini-api-cost-optimization-complete-guide)を参照してください。

## モデル選択の自動化パターン

応用として、タスクの種類によってモデルを自動で選ぶ関数を作っておくと便利です。

```python
import litellm

def call_ai(prompt: str, task_type: str = "general") -> str:
    """
    タスク種別に応じてモデルを自動選択する
    - coding: Gemini 2.5 Pro（コーディング精度が高い）
    - quick:  Gemini 2.5 Flash（速度重視・低コスト）
    - general: Gemini 2.5 Pro with Claude fallback
    """
    model_config = {
        "coding": {
            "model": "gemini/gemini-2.5-pro",
            "fallbacks": ["anthropic/claude-sonnet-4-6"]
        },
        "quick": {
            "model": "gemini/gemini-2.5-flash",
            "fallbacks": ["gemini/gemini-2.5-pro"]
        },
        "general": {
            "model": "gemini/gemini-2.5-pro",
            "fallbacks": ["anthropic/claude-sonnet-4-6", "openai/gpt-4o"]
        }
    }
    
    config = model_config.get(task_type, model_config["general"])
    
    response = litellm.completion(
        messages=[{"role": "user", "content": prompt}],
        num_retries=2,
        **config
    )
    
    return response.choices[0].message.content

# 使用例
code_result = call_ai("Pythonでファイルを非同期で読み込むコードを書いて", task_type="coding")
quick_result = call_ai("この文章を3行で要約して: ...", task_type="quick")
```

## 運用上の注意点

LiteLLMを実際に使っていくと、いくつかの点に気をつけた方が良いと感じています。

まずAPIキーの管理です。`.env`ファイルや環境変数への格納は当然として、フォールバック先のプロバイダーのキーも全て事前に設定しておかないと、肝心なときにフォールバックが動きません。本番では全プロバイダーのキー有効期限を一元管理するのをおすすめします。

次にモデル名の書き方です。`"gemini-2.5-pro"`ではなく`"gemini/gemini-2.5-pro"`と、プロバイダープレフィックスが必須です。ここを間違えると`AuthenticationError`になることがあり、最初は少し混乱するかもしれません。

それから、LiteLLMはバージョンアップが頻繁なライブラリです。`pip install litellm --upgrade`を定期的に実行し、新しいGeminiモデルがすぐ使えるようにしておくと良いでしょう。

## まとめ

LiteLLMを使うと、Gemini APIを中心に複数のAIプロバイダーを統一した方法で扱えます。`pip install litellm`から始めて、まずはフォールバック設定だけでも入れてみてください。本番でGemini APIのレート制限に悩んでいる方は、これだけで体験が大きく変わるはずです。

次のステップとして、LiteLLM Proxyサーバーを立てることでチーム全体のAPI使用量を一元管理する構成も検討してみてください。個人開発の範囲ではライブラリとしての利用で十分ですが、プロダクトが育ってきたときに選択肢として持っておくと心強いです。
