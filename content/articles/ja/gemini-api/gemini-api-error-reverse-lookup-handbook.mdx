Gemini API は成熟したサービスですが、商用に近い規模で使い込むと、必ずエラーハンドリングで時間を取られるフェーズがやってきます。同じ 404 でもモデル名の問題だったりリージョンの問題だったり、同じ 429 でも Free tier の上限だったりプロジェクト単位のクォータだったりと、パターンが広く、表面的なステータスコードだけでは原因が特定できません。このハンドブックは、私が個人アプリ運営や技術記事の運営で実際に踏み抜いてきた Gemini API のエラーパターンを、HTTP ステータス・エラーコード・症状の 3 軸で逆引きできる形に整理したものです。本番で詰まったときに、このページだけを開けば根本原因に辿り着ける実務資料として活用いただけます。

## このハンドブックの使い方

章はステータスコード別に分かれています。エラーが起きたら、レスポンスの HTTP ステータスから該当章に飛んでください。各項目は「症状 → 起きている場所 → 確認方法 → 復旧手順」の 4 段構成です。最後に、リトライ設計と可観測性についての実装ガイドラインも用意しています。

1. 401 Unauthorized と 403 Forbidden（認証・権限）
2. 404 Not Found（モデル名・リソース名）
3. 429 Resource Exhausted / Quota Exceeded
4. 500 Internal / 503 Service Unavailable
5. 4xx のうち特殊なもの（400 Invalid Argument、408 Timeout、413 Payload Too Large）
6. エラーではないが困る症状（空レスポンス、安全性フィルタ、ストリーミング切断）
7. リトライ設計と可観測性

## 1. 401 Unauthorized と 403 Forbidden

### 症状: `401 API key not valid` が全リクエストで返る

AI Studio で発行した API キーの入力ミス、または期限切れ・無効化・Quota Project との紐付け解除のどれかが起きています。

まず、キーが正しくヘッダまたはクエリで渡っているかを確認します。`generativelanguage.googleapis.com` ではクエリパラメータ `?key=` とヘッダ `x-goog-api-key` の両方が使えますが、片方だけを想定している SDK で別の方を渡していると 401 になります。

キーの文字列自体が正しい場合は、AI Studio の API Key 管理画面で「このキーが有効であるか」「プロジェクトと紐付いているか」を確認します。削除されたプロジェクトに紐付いたキーは自動的に無効化されるため、再発行が必要です。

### 症状: `403 Permission denied` で特定のモデルだけ弾かれる

Gemini API には、地域・アカウント種別・安全性審査の段階ごとに、モデルへのアクセス制限がかかっているケースがあります。特に、プレビュー段階のモデル（`-preview` サフィックス付きなど）は、明示的に early access を有効化していないと 403 になります。

AI Studio のモデル一覧画面で該当モデルの「利用可能状態」を確認し、必要であれば early access を申請してください。Google Cloud 側で Vertex AI モデル アクセス管理から有効化するケースもあります。

### 症状: `403 Billing not enabled` が返る

Free tier の制限を超えた、または課金対象のモデル（`gemini-2.5-pro` の大規模利用など）を請求設定なしで呼んだ場合に出ます。Google Cloud コンソールで該当プロジェクトの請求設定を有効化してから再試行します。

## 2. 404 Not Found

### 症状: `models/gemini-2.5-pro-latest is not found`

姉妹記事の無料版で詳しく扱っていますが、本稿でも要点を整理します。`-latest` エイリアスが 2.5 世代で不安定なため、ベース名（`gemini-2.5-pro`）か完全バージョン（`gemini-2.5-pro-001`）に切り替えるのが正解です。`ListModels` エンドポイントで、自分のキーから実際に見えるモデル一覧を確認するのが最も確実です。

### 症状: ファインチューニング済みモデルが 404 になる

独自にチューニングしたモデル（例: `tunedModels/my-model-abc123`）を呼び出して 404 が返る場合、モデル名の前に `tunedModels/` プレフィックスが必要な点を忘れているケースが大半です。さらに、チューニング済みモデルは作成時のプロジェクトからしか呼び出せないので、別プロジェクトの API キーで呼ぶと見えません。

### 症状: ファイル API でアップロード済みファイルが 404

`files.upload` でアップロードしたファイルには TTL があり、2 日（実装時点）で自動削除されます。時間が経ってから再度参照すると 404 になるのは正常動作です。長期保存が必要なファイルは、自分のストレージ（GCS 等）に置いてから `inline_data` で渡す方式に切り替えてください。

## 3. 429 Resource Exhausted / Quota Exceeded

Gemini API のクォータは、モデル別・プロジェクト別・時間窓別に多層構造になっています。429 が出たら、どのクォータに引っかかっているかを切り分ける必要があります。

### 症状: 連続リクエストですぐ 429 になる

RPM（Requests Per Minute）クォータに引っかかっている可能性が高いです。Free tier では `gemini-2.5-flash` で 15 RPM、`gemini-2.5-pro` では 2 RPM という非常に低い上限になっています。有料プランに移行するか、リクエストを 4 秒以上間隔で投げるよう調整します。

### 症状: 1 日単位で途中から 429 になる

これは RPD（Requests Per Day）の上限です。Free tier では `gemini-2.5-flash` で 1500 RPD 程度に制限されており、大規模な実験には明らかに足りません。有料プランに移行すれば 1 日の上限は実質なくなります。

### 症状: TPM（Tokens Per Minute）で弾かれる

長いコンテキストを送るアプリで起きやすく、RPM は余裕があるのにトークン量で詰まります。リクエストを分割するか、プロンプト側で不要な履歴を削るコンパクション処理を挟みます。

### 症状: エラーメッセージに「Quota exceeded for quota metric ... per project」と出る

プロジェクト単位のクォータで、この場合 Google Cloud コンソールの「IAM と管理 → 割り当て」から引き上げ申請を出せます。承認には数時間から数日かかります。

## 4. 500 Internal / 503 Service Unavailable

### 症状: 散発的に 500 が返る

一部のリクエストでのみ 500 が返る場合、モデル側の一時的な障害である可能性が高いです。ただし、同じ入力で確実に 500 になるなら、プロンプトが何らかの内部ガード（極端な長さ、特殊トークン、異常な入力形式）をトリガーしている可能性があります。入力を短くしたり、`generationConfig` の温度を下げたりして切り分けてください。

### 症状: 大規模な 503 が同時多発する

Google Cloud Status Dashboard で該当リージョンのインシデントを確認します。リージョン単位の障害の場合、別リージョンのエンドポイント（例: `us-central1-aiplatform.googleapis.com`）にフォールバックする構成にしておくと、体感ダウンタイムをほぼゼロにできます。

### 症状: 長時間リクエストで 504 Gateway Timeout

大規模なコンテキスト（数十万トークン）で `generateContent` を呼ぶと、同期モードでは処理時間が長すぎてゲートウェイタイムアウトに引っかかることがあります。この場合は `streamGenerateContent` に切り替えて、トークンを順次受け取る設計にしてください。ストリーミング化するだけで、体感応答時間と失敗率の両方が改善します。

## 5. 400 系の特殊なもの

### 症状: `400 Invalid argument: contents` で弾かれる

入力形式の不一致です。よくあるのは、マルチターン会話で `role` フィールドを `user` / `model` 以外の値（`assistant` や `system` など、他社 API の命名）にしているケースです。Gemini は `system` を `systemInstruction` という別フィールドで受け取る設計なので、マッピングを間違えると 400 になります。

### 症状: `400 Invalid image format`

画像入力で対応外のフォーマットを送っているか、`mimeType` が実データと一致していません。特に、画像のヘッダだけ変えて拡張子を偽装している場合（`.png` だが実際は `.heic` のような）は、Gemini 側のバリデーションで弾かれます。

### 症状: `413 Request payload too large`

単一リクエストのボディ上限は数十 MB ですが、画像や動画を大量にインライン埋め込みすると簡単に超えます。`files.upload` API 経由で事前アップロードし、ファイル参照だけをリクエストに含める形に変えてください。

## 6. エラーではないが困る症状

### 症状: `candidates` が空配列で返る

200 OK で返ってくるのに、レスポンスの `candidates` が空で、`promptFeedback.blockReason` に `SAFETY` と入っている — これは安全性フィルタでブロックされた状態です。`safetySettings` で各カテゴリ（`HARM_CATEGORY_HARASSMENT` など）の閾値を調整すると通るようになりますが、ブロックが強く設定される理由もあるので、闇雲に全カテゴリを緩めるのは避けてください。

### 症状: ストリーミングが途中で切れる

SSE 経由でトークンを受け取っているとき、中間プロキシがアイドルタイムアウトで接続を切ってしまうケースです。企業プロキシで特に起きやすく、`keep-alive` の許容時間を伸ばしてもらう必要があります。アプリ側では、切断を検知して自動再開するリトライロジックを入れておくと実務上は困りません。

### 症状: 日本語レスポンスで文字化けする

レスポンスの Content-Type と受信側のデコード設定がずれていると、特に UTF-8 以外を前提としているクライアントで文字化けします。`response.text()` を明示的に UTF-8 で読み込むか、JSON パース時に `content-type` を確認してください。

### 症状: CORS エラー（ブラウザから直接呼ぶ場合）

ブラウザから `generativelanguage.googleapis.com` を直接呼ぶと CORS で弾かれます。Gemini API はサーバーサイドでの利用を前提にしており、ブラウザから直接キーを使うのはセキュリティ上も推奨されません。Cloudflare Workers や Next.js API Routes などでプロキシを挟む設計にしてください。

## 7. リトライ設計と可観測性のガイドライン

以上のエラーを踏まえて、Gemini API を商用で使うときのリトライ方針を整理します。

**リトライ対象とすべきエラー**: 429（クォータ）、500（一時的な内部エラー）、503（一時的な可用性低下）、504（ゲートウェイタイムアウト）、ストリーミング切断。これらは時間経過で自然に回復することが多いです。

**リトライ対象外**: 400（入力不正）、401（認証）、403（権限）、404（モデル名・リソース不在）、413（サイズ超過）。これらは原因を直さない限り成功しないので、自動リトライは無駄です。

**バックオフ戦略**: 指数バックオフ（initial=1s, factor=2, max=30s）にジッター（±20%）を加えたものが実務的です。429 に関してはレスポンスヘッダの `Retry-After` を優先し、なければバックオフを使います。

**可観測性**: エラー率・ステータスコード別カウント・モデル別応答時間を Prometheus などで可視化しておくと、問題の兆候を早期に検知できます。私が運営しているサイト群では、Cloudflare Workers 側で Gemini API のレスポンスを集計し、Google Analytics のカスタムイベントに流す実装にしています。

## 最後に — エラーを「設定」として扱う発想

Gemini API のエラーの多くは、コードが間違っているというより、**モデル・プロジェクト・ネットワーク・クォータの組み合わせが想定と違う** ときに出ます。つまり、エラーそのものよりも「期待している設定が実際にどうなっているか」を可視化する仕組みを持っておくと、トラブル時の初動が桁違いに速くなります。

`ListModels` を定期的に叩いて使えるモデル一覧を記録する、`gcloud quota list` でプロジェクトのクォータを週次で把握する、エラーレスポンスの `error.details[]` を必ずログに残す — これらを習慣にしておくと、このハンドブックの多くのケースは「発生する前に」気付けるようになります。

次に Gemini API のエラーに遭ったときは、HTTP ステータスから該当章を開いて、4 段のチェックを順番に回してください。ほとんどのケースで、数分以内に根本原因に辿り着けるはずです。
