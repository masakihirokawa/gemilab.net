## 「キャッシュが効いているはずなのに請求額が変わらない」

Gemini API の Context Caching は、同じプロンプトプレフィックスを再利用することで入力コストを最大90%削減できる強力な機能だ。ところが実際に導入してみると、「キャッシュを設定したのにコストが下がらない」「`cached_content_token_count` が常にゼロ」「そもそもキャッシュの作成でエラーになる」という声が非常に多い。

問題の厄介なところは、キャッシュが効いていなくてもAPIはエラーを返さず正常にレスポンスを生成してしまう点にある。つまり、明示的に `usage_metadata` を確認しなければ、キャッシュミスに気づかないまま通常料金を払い続けることになる。

この記事では Context Caching が期待通りに動かない原因を5つのカテゴリに分類し、それぞれの診断方法と修正コードを示す。

## Explicit Caching と Implicit Caching — 混同が生むサイレント課金

まず根本的な誤解が多い2つの仕組みの違いを整理する。

**Explicit Caching**（明示的キャッシュ）は `caches.create` APIで手動作成するキャッシュだ。TTL（有効期限）を指定し、キャッシュされたトークンには確実に割引料金が適用される。Gemini 1.5 Pro、1.5 Flash、および2.5系モデルで利用可能。

**Implicit Caching**（暗黙的キャッシュ）は Gemini 2.5 以降のモデルで自動的に有効になる仕組みで、Googleのインフラ側で同一プレフィックスを検出した場合にキャッシュヒットが発生する。ただし、ヒットは保証されない。

ハマりやすいのが「Gemini 2.5 Pro を使っているからキャッシュは自動で効くはず」という前提で開発を進めるケースだ。Implicit Caching はベストエフォートであり、短いプロンプトや散発的なリクエストではほとんどヒットしない。月額の API 費用を確実に抑えたいなら Explicit Caching を明示的に使う必要がある。

```python
# ❌ よくある勘違い：Implicit Caching に依存してコスト削減を期待
from google import genai

client = genai.Client(api_key="YOUR_API_KEY")

# 毎回同じシステムプロンプトを送っているが、
# Implicit Caching のヒットは保証されない
for query in user_queries:
    response = client.models.generate_content(
        model="gemini-2.5-pro",
        contents=[long_system_context, query],
    )
    # usage_metadata.cached_content_token_count が 0 のまま
    print(response.usage_metadata)
```

```python
# ✅ Explicit Caching で確実にキャッシュを効かせる
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

# キャッシュを明示的に作成（TTL: 1時間）
cache = client.caches.create(
    model="gemini-2.5-flash",
    config=types.CreateCachedContentConfig(
        contents=[
            types.Content(
                role="user",
                parts=[types.Part(text=long_system_context)],
            )
        ],
        ttl="3600s",
    ),
)
print(f"キャッシュ作成完了: {cache.name}")
print(f"トークン数: {cache.usage_metadata.total_token_count}")

# キャッシュを指定してリクエスト
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="このドキュメントの要点を3つ挙げて",
    config=types.GenerateContentConfig(
        cached_content=cache.name,
    ),
)
# ここで cached_content_token_count > 0 を確認できる
print(f"キャッシュヒット: {response.usage_metadata.cached_content_token_count} tokens")
```

## キャッシュ作成エラー：`max_total_token_count=0` の正体

2026年に入ってから報告が増えているのが、Paid Tier のプロジェクトでも `INVALID_ARGUMENT: Cached content is too large. max_total_token_count=0` が返るという問題だ。Google AI Developer Forum にも複数のスレッドが立っている。

原因は Google 側でアカウントに対するキャッシュ枠が正しく割り当てられていないことにある。課金を有効にしているにもかかわらず、内部的にキャッシュの上限がゼロに設定されてしまうケースが存在する。

**診断スクリプト:**

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

# 最小限のコンテンツでキャッシュ作成を試みる
try:
    test_cache = client.caches.create(
        model="gemini-2.5-flash",
        config=types.CreateCachedContentConfig(
            contents=[
                types.Content(
                    role="user",
                    parts=[types.Part(text="テスト " * 20000)],
                )
            ],
            ttl="60s",
        ),
    )
    print(f"✅ キャッシュ作成成功: {test_cache.usage_metadata.total_token_count} tokens")
    # テスト用キャッシュを削除
    client.caches.delete(name=test_cache.name)

except Exception as e:
    error_msg = str(e)
    if "max_total_token_count=0" in error_msg:
        print("❌ キャッシュ枠がゼロ")
        print("   → Google AI Studio でプロジェクトの課金状態を確認")
        print("   → 別のプロジェクトを作成してAPIキーを再発行")
        print("   → 解消しなければ Google AI Developer Forum に報告")
    elif "too small" in error_msg.lower() or "minimum" in error_msg.lower():
        print("❌ トークン数が最低要件未満")
    else:
        print(f"❌ 予期しないエラー: {e}")
```

解決策として最も確実なのは、新しい Google Cloud プロジェクトを作成して API キーを再発行する方法だ。既知のバグとして報告されており、プロジェクト再作成で解消する事例が複数確認されている。

## 最小トークン数の罠：モデルごとに異なる閾値

Explicit Caching にはモデルごとの**最小トークン数**が設定されている。この閾値を下回るコンテンツでキャッシュを作成しようとすると、エラーが返る場合と、キャッシュは作成されるものの実際のリクエストでヒットしない場合がある。

2026年4月時点での目安は以下の通りだ:

- **Gemini 2.5 Pro / Flash**: 最小 4,096 トークン
- **Gemini 1.5 Pro**: 最小 32,768 トークン
- **Gemini 1.5 Flash**: 最小 1,024 トークン

特にハマりやすいのが Gemini 1.5 Pro のケース。「3万トークンのドキュメントをキャッシュしたが効かない」という相談をよく見かけるが、1.5 Pro の最小要件は 32,768 トークンなのでギリギリ足りていない。

```python
# キャッシュ作成前にトークン数を事前検証する
from google import genai

client = genai.Client(api_key="YOUR_API_KEY")

MODEL = "gemini-2.5-flash"
MIN_TOKENS = {
    "gemini-2.5-pro": 4096,
    "gemini-2.5-flash": 4096,
    "gemini-1.5-pro": 32768,
    "gemini-1.5-flash": 1024,
}

token_result = client.models.count_tokens(
    model=MODEL,
    contents=[long_document],
)
actual = token_result.total_tokens
required = MIN_TOKENS.get(MODEL, 4096)

if actual < required:
    print(f"⚠️ トークン数不足: {actual:,} < {required:,}")
    print(f"   あと {required - actual:,} トークン必要")
    print(f"   対策: コンテンツを追加するか、最小要件の低いモデルに切り替える")
else:
    print(f"✅ 要件クリア: {actual:,} >= {required:,} → キャッシュ作成可能")
```

私自身の経験では、最小トークン数ギリギリのキャッシュは不安定になりやすい。最小要件の1.5倍以上のコンテンツを入れておくと安定する。足りない場合は関連するリファレンスドキュメントを追加するとよい。キャッシュストレージのコストは保存量ではなくヒットした入力トークン単価で決まるため、多少大きくてもヒットさえすればコスト効率は向上する。

## TTL 切れの見落とし：バッチ処理の落とし穴

Explicit Caching のデフォルト TTL は1時間（3600秒）だ。バッチ処理を数時間かけて実行する場合、処理の途中でキャッシュが失効し、後半のリクエストだけ通常料金が適用されるという事態が起きる。

しかもキャッシュが失効しても API はエラーを返さない。単にキャッシュなしで処理が続行され、`cached_content_token_count` がゼロになるだけだ。レスポンス自体は正常に返るので、ログを確認しなければ気づかない。

```python
# ✅ TTL を監視しながらバッチ処理を実行する
from google import genai
from google.genai import types
import datetime

client = genai.Client(api_key="YOUR_API_KEY")
MODEL = "gemini-2.5-flash"
TTL_SECONDS = 3600
REFRESH_BUFFER = 300  # 期限の5分前に更新

def create_cache(content):
    """キャッシュを作成し、有効期限を返す"""
    cache = client.caches.create(
        model=MODEL,
        config=types.CreateCachedContentConfig(
            contents=[types.Content(role="user", parts=[types.Part(text=content)])],
            ttl=f"{TTL_SECONDS}s",
        ),
    )
    expire_at = datetime.datetime.now() + datetime.timedelta(seconds=TTL_SECONDS)
    return cache, expire_at

cache, expire_at = create_cache(system_context)
stats = {"cached": 0, "uncached": 0, "refreshes": 0}

for i, doc in enumerate(documents):
    # 期限が近づいたらキャッシュを自動再作成
    if datetime.datetime.now() > expire_at - datetime.timedelta(seconds=REFRESH_BUFFER):
        old_name = cache.name
        cache, expire_at = create_cache(system_context)
        stats["refreshes"] += 1
        try:
            client.caches.delete(name=old_name)
        except Exception:
            pass  # 既に期限切れの場合は無視

    response = client.models.generate_content(
        model=MODEL,
        contents=doc,
        config=types.GenerateContentConfig(cached_content=cache.name),
    )

    cached_tokens = response.usage_metadata.cached_content_token_count
    if cached_tokens > 0:
        stats["cached"] += cached_tokens
    else:
        stats["uncached"] += response.usage_metadata.prompt_token_count
        print(f"⚠️ [{i}] キャッシュミス — {doc[:40]}...")

print(f"\n📊 バッチ完了:")
print(f"   キャッシュヒット: {stats['cached']:,} tokens")
print(f"   キャッシュミス:   {stats['uncached']:,} tokens")
print(f"   キャッシュ再作成: {stats['refreshes']}回")
```

ポイントは TTL の5分前にキャッシュを再作成している点だ。ギリギリまで待つと、再作成のAPI呼び出し中にTTLが切れてしまうリスクがある。

## Implicit Caching のヒット率を上げる設計パターン

Gemini 2.5 系モデルの Implicit Caching は保証されないものの、リクエストの構造を工夫するとヒット率を大幅に向上させることができる。鍵は「プロンプトの先頭部分をリクエスト間で完全に一致させる」ことだ。

Implicit Caching はプレフィックスマッチで動作する。リクエストの先頭から何トークン目まで前回と一致しているかを見ており、途中に1バイトでも差異があるとそこ以降はキャッシュが効かない。

```python
# ❌ 毎回タイムスタンプを含めるとプレフィックスが変わる
import datetime

response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=[
        f"現在時刻: {datetime.datetime.now()}\n\n{system_prompt}",
        user_query,
    ],
)
# → プレフィックスが毎回変わるのでキャッシュヒットしない

# ✅ 固定部分を system_instruction に分離する
response = client.models.generate_content(
    model="gemini-2.5-pro",
    config=types.GenerateContentConfig(
        system_instruction=system_prompt,  # 不変の指示はここに
    ),
    contents=[user_query],  # 変化する部分だけ contents に
)
# → system_instruction は常にリクエストの先頭に配置される
# → 同一の system_instruction を使い続ければプレフィックスが一致しやすい
```

もう一つ見落としがちなのが、マルチターン会話での `contents` の組み立て方だ。会話履歴を毎回先頭から送り直す場合、会話が長くなるにつれて共通プレフィックスが伸びるため、Implicit Caching の恩恵を自然に受けられる。逆に、直近N件だけをウィンドウで切り出す方式だと、ウィンドウがスライドするたびにプレフィックスが変わりキャッシュが効きにくくなる。

Implicit Caching を最大限活用したいなら、会話履歴は先頭から全件送り、末尾に新しいメッセージを追加する方式が有利だ。ただしトークン上限との兼ね合いで全件送信が難しいケースもあるので、その場合は Explicit Caching に切り替える判断が必要になる。

## 次のアクション：キャッシュヒット率を計測する仕組みを入れる

Context Caching のトラブルは「動いているように見えて実は効いていない」パターンが大半を占める。本番環境に導入する際は、`usage_metadata.cached_content_token_count` をリクエストごとにログに記録し、日次でキャッシュヒット率を集計するモニタリングを組み込むことを勧める。ヒット率が50%を下回っていたら、この記事の診断手順を上から順に確認してみてほしい。
