Gemini API でSaaSを作る個人開発者から最も多く聞く悩みは、「いくらで売ればいいのか分からない」です。安すぎれば赤字、高すぎれば誰も買いません。多くの場合、競合の価格を真似て「とりあえず月額1,000円」と決めてしまいます。これが、ローンチ後に粗利率を計算して頭を抱えるパターンの始まりです。

Gemini APIを使ったSaaSの価格を「原価から逆算する」アプローチで決める方法を順番にご紹介します。私自身、複数のAI連携サービスを設計してきましたが、原価計算を最初に行うかどうかで、半年後の黒字・赤字がほぼ決まると感じています。

## なぜ「とりあえず月額1,000円」が破綻するのか

具体的な数字で考えてみます。Gemini 2.5 Flash の2026年4月時点の従量課金は、入力トークン100万あたり0.10ドル、出力トークン100万あたり0.40ドルです。

仮に1ユーザーが1ヶ月に「平均5,000トークン入力 × 200回」「平均1,000トークン出力 × 200回」のリクエストを発生させるサービスを作ったとします。1ユーザーあたりの月間原価は次のようになります。

- 入力: 5,000 × 200 = 100万トークン → 0.10ドル
- 出力: 1,000 × 200 = 20万トークン → 0.08ドル
- 合計: 約0.18ドル/月（約27円/月）

これだけ見ると「月額1,000円なら粗利率97%、楽勝じゃないか」と思えます。しかし現実は違います。実際にローンチすると、利用量の分布は極端に偏ります。

## 「ヘビーユーザー10%が原価の80%を消費する」現象

私が観測してきた個人開発SaaSのほぼ全てで、利用量の分布はパレート分布に近い形になります。具体的には、上位10%のユーザーが全体の70〜80%のトークンを消費します。

仮に100人の有料ユーザーがいて、平均月間原価が0.18ドルだと想定したとします。しかし実際には、上位10人は1人あたり1.5ドル相当のトークンを使い、残り90人は0.04ドル相当しか使いません。

合計原価: 10人 × 1.5ドル + 90人 × 0.04ドル = 18.6ドル
平均原価: 18.6 ÷ 100 = 0.186ドル/人

平均値だけ見れば「想定通り」ですが、ここに罠があります。月額1,000円で売っているとすると、上位10人からは1,000円 - 約230円 = 月額770円の粗利。しかし利用量がさらに伸びるユーザー（俗に「外れ値」と呼ばれる超ヘビーユーザー）が出てきた瞬間、彼ら1人で月額数千円の赤字を出す可能性があります。

定額課金SaaSの最大のリスクは、この「外れ値による損失」です。価格設計の段階でこのリスクを織り込まないと、ヘビーユーザーが増えるほど赤字が拡大します。

## 黒字化の方程式 — 4つの変数で組み立てる

価格設計に必要な変数は4つです。

1. **CPU**（Cost Per User）: 1ユーザーあたりの月間平均原価
2. **CPU_HEAVY**: 上位10%ユーザーの月間原価（多くの場合 CPU の8〜10倍）
3. **PRICE**: あなたが設定する月額価格
4. **MARGIN_TARGET**: 目標粗利率（個人開発SaaSなら最低70%を推奨）

これらの間に、次の関係式が成立すべきです。

```
PRICE >= CPU_HEAVY × (1 / (1 - MARGIN_TARGET))
```

つまり「ヘビーユーザーですら粗利率を確保できる価格」を最低ラインに設定します。先ほどの例なら、CPU_HEAVY = 1.5ドル、目標粗利率70%なら、最低価格は 1.5 ÷ 0.3 = 5ドル/月 となります。

「想定平均原価は0.18ドルだから月1,000円で十分」という直感が、いかに危ういかが分かります。

## 「上限つき定額」または「従量課金」の選択

上記の計算をすると、多くのSaaSが「定額月1,000円」では成立しないことが見えてきます。ここから取れる選択肢は2つです。

ひとつめは「上限つき定額」です。月額1,000円でも、月間の利用回数または合計トークン数に上限を設けます。例えば「月200回まで」「上限を超えたら追加で1回あたり10円」という設計です。これでヘビーユーザーからの損失を防げます。

ふたつめは「完全従量課金」です。前払いクレジットを購入してもらい、利用ごとに消費する形です。Stripeでは「customer balance」または独自のクレジット管理で実装できます。利用量が読めないユーザー（企業利用など）にも対応しやすいです。

私の経験では、個人ユーザー向けSaaSなら「上限つき定額」、開発者向けまたは企業向けなら「完全従量課金」が定石です。

## 月額価格の決め方 — 心理的価格帯の活用

原価から逆算した最低価格が決まったら、最終価格は心理的に受け入れやすいゾーンに調整します。2026年現在、個人ユーザー向けAI SaaSで観測される心理的価格帯は次の通りです。

- 試しやすい価格: 月額500〜980円
- 中堅価格: 月額1,500〜2,980円
- 高価格帯: 月額4,800〜9,800円

月額1,000円を割ると「気軽に試す」モードに入りますが、原価との戦いが厳しくなります。月額3,000円を超えると「本格的に検討する」モードになり、ターゲットユーザーが絞られます。

最低価格が5ドル（約750円）と算出されたなら、心理的に試しやすい980円に設定するのが私の推奨です。粗利率70%を維持しつつ、試しやすさも確保できます。

## 解約率を見越した粗利設計

価格設計でもうひとつ忘れてはいけないのが、解約率です。

個人ユーザー向けSaaSの解約率は、平均で月5〜10%です。これは「100人の有料ユーザーが、毎月5〜10人解約していく」という意味です。1人を獲得するためのコスト（広告、コンテンツ作成、サポート対応など）を仮に500円とすると、解約率10%のサービスでは、毎月100人を獲得するために50,000円が必要です。

LTV（顧客生涯価値）= 月額価格 × 平均継続月数 という単純な式で考えると、月額980円・解約率10%なら、平均継続月数 = 1 / 0.10 = 10ヶ月、LTV = 9,800円 となります。獲得コスト500円を引いた粗LTVは9,300円です。

この粗LTVから、原価（10ヶ月で約1.8ドル = 270円）を引いた純LTVは約9,030円です。これが「あなたが1人の有料ユーザーから得られる本当の利益」です。

価格を月額1,500円に上げると、解約率がやや上がる（仮に12%）としてもLTVは1,500 × 8.3 = 12,450円に増えます。同じコストで100人を獲得できるなら、月額を上げる方が総利益は大きくなります。

## Claude Code で価格設計を自動化する

ここまでの計算は手動で全部やる必要はありません。私はClaude Code に Supabase のクエリを書かせて、リアルタイムで原価分布を可視化しています。

```
Supabase の usage_logs テーブルから次の集計をしてください：
1. 過去30日間のユーザーごとの合計トークン消費量
2. 上位10%のユーザーの平均原価
3. 中央値ユーザーの原価
4. 全体平均原価

各値をドルとJPYで出してください（為替は150円/ドル）。
さらに、目標粗利率70%を維持するための最低月額価格も計算してください。
```

このクエリを毎日Cron実行し、Slackに通知すれば、価格設計の根拠が常に手元にあります。Gemini APIの価格は将来的に変動する可能性があるため、原価ベースのモニタリングは長期的にも有用です。

## まとめ — 価格は「決める」ものではなく「計算する」もの

個人開発のSaaSで黒字化できないケースの多くは、価格を直感や競合比較で決めた結果です。原価から逆算する習慣がつくと、ローンチ前に「このプロダクトは現状の価格設計では成立しない」と判断できるようになります。
