Gemini APIのレスポンスを処理するコードを書いていて、こんな経験はないでしょうか。期待していた `title` フィールドが `Title`（大文字始まり）で返ってきた。整数のはずだった `score` が文字列の `"85"` で届いた。絶対に `null` にならないと信じていたフィールドが突然 `None` になって、AttributeError で本番サーバーが落ちた——。

LLMの出力は本質的に確率的です。プロンプトを少し変えるだけで、モデルのアップデートが入るだけで、レスポンスの構造が微妙にずれることがあります。そしてその「微妙なずれ」が、型安全性のないコードにとっては致命傷になります。

Pydantic v2 と Gemini API の `response_schema` を組み合わせると、この問題を根本から解決できます。LLMに「このスキーマで返してください」と明示的に指示し、返ってきたレスポンスをPydanticモデルで自動バリデーションする——この2段構えのアプローチにより、ランタイムエラーの大部分を事前に防ぐことができます。

この記事では、基本的な構造化出力の実装から始めて、ネスト構造やOptionalフィールドの扱い、ストリーミングとの統合、そして本番環境で実際に使えるリトライ設計まで、実際に動くコードとともに解説します。

## LLMレスポンスに型安全性が必要な3つの理由

型安全性の話をすると「Gemini APIはちゃんと指定したフォーマットで返してくれる」という声をよく耳にします。確かにその通りです。でも「ちゃんと」が保証されているのはモデルの動作として、であって、コードの型システムとしてではありません。

**理由1: バリデーションコストの問題**

型なしのアプローチでは、APIから受け取ったデータを使う前に必ず手動でバリデーションを書く必要があります。

```python
# ❌ よくある（危険な）パターン
response = model.generate_content(prompt)
data = json.loads(response.text)

title = data["title"]          # KeyError のリスク
score = int(data["score"])     # ValueError のリスク（文字列が来たとき）
items = data.get("items", [])  # None が来たとき後続で TypeError
```

このような手動チェックを全APIレスポンスで繰り返すのは非効率ですし、見落としが起きます。

**理由2: モデルアップデートへの脆弱性**

Gemini 2.5 Pro から Gemini 3.x へのアップデート、あるいはシステムインストラクションの変更——これらがトリガーとなってレスポンス構造が変わることがあります。型安全なコードは、この変化を実行時ではなくコンパイル時（型チェック時）に検出できます。

**理由3: チーム開発での共通言語**

Pydanticモデルは「このAPIがどんなデータを返すか」のドキュメントとして機能します。`ArticleResponse`というクラスを見れば、フィールドの名前・型・必須/オプションが一目瞭然です。コメントや別途ドキュメントを書く必要がなくなります。

## Pydantic v2 × response_schema の基本構文

まずは動く最小構成から始めましょう。依存関係のインストールから確認します。

```bash
pip install google-genai pydantic
```

`google-genai` は新しいSDK（`google-generativeai` の後継）です。2026年時点では `google-genai` の使用が推奨されています。

```python
import os
from pydantic import BaseModel, Field
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

# Pydanticモデルの定義
class MovieReview(BaseModel):
    title: str = Field(description="映画のタイトル")
    rating: int = Field(description="10点満点の評価スコア", ge=1, le=10)
    summary: str = Field(description="200文字以内のレビュー要約")
    is_recommended: bool = Field(description="おすすめかどうか")

# response_schema にPydanticモデルを渡す
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="映画『インターステラー』のレビューを書いてください",
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=MovieReview,
    ),
)

# Pydanticモデルとしてパース
review = MovieReview.model_validate_json(response.text)

print(f"タイトル: {review.title}")
print(f"評価: {review.rating}/10")
print(f"要約: {review.summary}")
print(f"おすすめ: {'はい' if review.is_recommended else 'いいえ'}")

# 期待する出力例:
# タイトル: インターステラー
# 評価: 9/10
# 要約: 宇宙と時間の神秘を壮大なスケールで描いたSF叙事詩...
# おすすめ: はい
```

`response_schema=MovieReview` と指定することで、GeminiはこのPydanticモデルのJSON Schemaを自動的に解釈し、フォーマットに従ったレスポンスを生成します。返ってきたJSONを `model_validate_json()` でパースすれば、バリデーション済みのPydanticオブジェクトが手に入ります。

`Field` の `ge=1, le=10` のような制約は、JSON Schemaの `minimum`/`maximum` として変換され、Geminiへの指示に含まれます。ただし、LLMが制約を100%守る保証はないため、後述するバリデーション後の再試行パターンと組み合わせるのが理想です。

## ネスト構造とOptionalフィールドの実装

実際のプロダクションでは、フラットな構造だけでなく、ネストしたオブジェクトやリスト、Optionalフィールドを扱うことが多くあります。

```python
from typing import Optional, List
from pydantic import BaseModel, Field
from enum import Enum

class Sentiment(str, Enum):
    POSITIVE = "positive"
    NEGATIVE = "negative"
    NEUTRAL = "neutral"

class Author(BaseModel):
    name: str
    expertise_level: str = Field(description="beginner / intermediate / expert のいずれか")

class Comment(BaseModel):
    text: str
    sentiment: Sentiment
    helpful_votes: int = Field(default=0)

class ProductReview(BaseModel):
    product_name: str
    overall_score: float = Field(description="1.0〜5.0の評価", ge=1.0, le=5.0)
    author: Author
    pros: List[str] = Field(description="良い点のリスト（最低1項目）", min_length=1)
    cons: List[str] = Field(description="改善点のリスト（なければ空リスト）")
    top_comment: Optional[Comment] = Field(
        default=None,
        description="最も参考になったコメント。なければnull"
    )

# 使用例
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="MacBook Pro M4のレビューを書いてください",
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=ProductReview,
    ),
)

review = ProductReview.model_validate_json(response.text)

print(f"製品名: {review.product_name}")
print(f"スコア: {review.overall_score}")
print(f"著者: {review.author.name}（{review.author.expertise_level}）")
print("良い点:")
for pro in review.pros:
    print(f"  - {pro}")

if review.top_comment:
    print(f"トップコメント: {review.top_comment.text}")
    print(f"感情: {review.top_comment.sentiment.value}")

# 期待する出力例:
# 製品名: MacBook Pro M4
# スコア: 4.8
# 著者: Gemini Lab（expert）
# 良い点:
#   - M4チップによる圧倒的なパフォーマンス
#   - 最大24時間のバッテリー持続時間
# トップコメント: 開発環境として最高の選択です
# 感情: positive
```

`Optional[Comment]` フィールドの扱い方は特に注意が必要です。`Optional[X]` は `X | None` を意味しますが、Geminiに対してこれを正確に伝えるためには、Fieldの `description` で「なければnull」と明示することが実践的に有効です。単にOptional型を指定するだけでは、Geminiが空文字列や `{}` を返すことがあります。

Enumの使用も強くお勧めします。`str, Enum` を継承することで、Geminiに許可される値のリストを明示でき、想定外の文字列が入り込むリスクを大幅に下げられます。

## ストリーミングと構造化出力の統合

長い応答を生成する場合、ストリーミングを使うことでユーザー体験が向上します。ただし、構造化出力とストリーミングを組み合わせる際には、いくつかの注意点があります。

```python
import json
from pydantic import BaseModel, Field
from typing import List

class ArticleAnalysis(BaseModel):
    main_topic: str
    key_points: List[str] = Field(description="記事の要点（3〜5項目）")
    target_audience: str
    difficulty_level: str = Field(description="beginner / intermediate / advanced")
    word_count_estimate: int

def analyze_article_streaming(content: str) -> ArticleAnalysis:
    """ストリーミングで記事を分析し、完成時にPydanticモデルで返す"""
    
    chunks = []
    
    for chunk in client.models.generate_content_stream(
        model="gemini-2.5-pro",
        contents=f"以下の記事を分析してください:

{content}",
        config=types.GenerateContentConfig(
            response_mime_type="application/json",
            response_schema=ArticleAnalysis,
        ),
    ):
        if chunk.text:
            chunks.append(chunk.text)
            # リアルタイムに進捗を表示したい場合
            print(".", end="", flush=True)
    
    print()  # 改行
    
    # 全チャンクを結合してPydanticモデルにパース
    full_response = "".join(chunks)
    return ArticleAnalysis.model_validate_json(full_response)

# テスト用サンプル記事
sample_article = """
Python 3.12 の新機能：型ヒントの改善とパフォーマンス向上
この記事ではPython 3.12で追加された主要な機能について解説します...
"""

result = analyze_article_streaming(sample_article)
print(f"メイントピック: {result.main_topic}")
print(f"難易度: {result.difficulty_level}")
print(f"対象読者: {result.target_audience}")

# 期待する出力例:
# ....
# メイントピック: Python 3.12の新機能
# 難易度: intermediate
# 対象読者: Pythonの基本を知っている開発者
```

ストリーミングの場合、JSONはチャンクごとに断片的に届くため、各チャンクをそのままパースしようとしてもエラーになります。チャンクを蓄積して、最後に完全なJSONとしてパースするのが正しいアプローチです。

なお、ストリーミングで構造化出力を使うと、Geminiはまずテキストをゆっくり生成してから最後にまとめてJSONを完成させる傾向があります。プログレスインジケーターを表示しつつ、最終レスポンスだけをパースするパターンが最も実用的です。

## よくある落とし穴と回避パターン

実際に `response_schema` を使い始めると、いくつかのハマりどころがあります。私が経験した主なものを紹介します。

**落とし穴1: `response.text` が `None` になる**

構造化出力を指定したときに `response.text` が `None` になるケースがあります。これは安全フィルターが作動した場合や、モデルが指定スキーマで回答を生成できなかった場合に起きます。

```python
# ❌ そのままアクセスすると None で壊れる
result = MyModel.model_validate_json(response.text)  # AttributeError

# ✅ 正しい実装：候補とfinish_reasonを確認する
def safe_parse(response, model_class):
    if not response.candidates:
        raise ValueError("No candidates in response")
    
    candidate = response.candidates[0]
    
    # finish_reason の確認（STOP以外はエラー扱い）
    if candidate.finish_reason.name \!= "STOP":
        raise ValueError(f"Unexpected finish_reason: {candidate.finish_reason.name}")
    
    if not response.text:
        raise ValueError("Empty response text")
    
    return model_class.model_validate_json(response.text)
```

**落とし穴2: 深いネストでGeminiが構造を崩す**

ネストが3〜4階層になると、GeminiがJSON構造を「解釈」して独自にフラット化したり、フィールド名を変えてしまうことがあります。深いネストを避け、2階層以内に収めるか、複数のAPIコールに分割するのが安全です。

```python
# ❌ 深すぎるネスト（3階層以上）
class Level3(BaseModel):
    detail: str

class Level2(BaseModel):
    nested: Level3  # 3階層目

class Level1(BaseModel):
    data: Level2   # さらにネスト

# ✅ 推奨：フラットにするか2階層まで
class FlattenedResponse(BaseModel):
    detail: str
    summary: str
    category: str
```

**落とし穴3: Union型がJSON Schemaに正しく変換されない**

`Union[str, int]` のような型は、JSON Schemaの `anyOf` として変換されますが、Gemini APIがこれを正しく解釈しないことがあります。Union型は使わず、型を明示的に1つに絞るのが無難です。

```python
# ❌ Union型は避ける
class ProblematicModel(BaseModel):
    value: Union[str, int, None]  # GeminiがJSON Schemaを誤解するリスク

# ✅ 型を明示する
class ClearModel(BaseModel):
    value: Optional[str] = None  # 文字列またはNullのみに限定
    numeric_value: Optional[float] = None  # 数値の場合は別フィールド
```

**落とし穴4: Pydanticの `model_config` で `strict=True` を使いすぎる**

PydanticのStrict Modeを有効にすると、`1` を `"1"` として渡したときにバリデーションエラーになります。LLMは数値を文字列として返すことがあるため、strict=Trueはプロダクション環境では注意が必要です。

```python
# ❌ strict=True だとLLMの型変換が通らない
class StrictModel(BaseModel):
    model_config = {"strict": True}
    score: int  # "85" が来るとエラー

# ✅ デフォルト（coercion許可）が実用的
class FlexibleModel(BaseModel):
    score: int  # "85" -> 85 に自動変換される
```

## バリデーション失敗時のリトライ設計

Geminiは `response_schema` を高い精度で守りますが、100%ではありません。本番環境では、バリデーション失敗時に自動リトライする仕組みが不可欠です。

```python
import time
import logging
from typing import Type, TypeVar
from pydantic import BaseModel, ValidationError
from google import genai
from google.genai import types

T = TypeVar("T", bound=BaseModel)

logger = logging.getLogger(__name__)

def generate_structured(
    client: genai.Client,
    prompt: str,
    model_class: Type[T],
    model_name: str = "gemini-2.5-pro",
    max_retries: int = 3,
    retry_delay: float = 2.0,
) -> T:
    """
    構造化出力を生成し、バリデーション失敗時に自動リトライする。
    
    Args:
        client: Gemini APIクライアント
        prompt: 入力プロンプト
        model_class: Pydanticモデルのクラス
        model_name: 使用するGeminiモデル
        max_retries: 最大リトライ回数
        retry_delay: リトライ間隔（秒）
    
    Returns:
        バリデーション済みのPydanticモデルインスタンス
    
    Raises:
        ValueError: max_retriesを超えても成功しなかった場合
    """
    last_error = None
    
    for attempt in range(max_retries):
        try:
            response = client.models.generate_content(
                model=model_name,
                contents=prompt,
                config=types.GenerateContentConfig(
                    response_mime_type="application/json",
                    response_schema=model_class,
                ),
            )
            
            # 安全フィルターチェック
            if not response.candidates:
                raise ValueError("No response candidates")
            
            if response.candidates[0].finish_reason.name \!= "STOP":
                raise ValueError(
                    f"Bad finish_reason: {response.candidates[0].finish_reason.name}"
                )
            
            if not response.text:
                raise ValueError("Empty response")
            
            # Pydanticバリデーション
            return model_class.model_validate_json(response.text)
            
        except (ValidationError, ValueError, json.JSONDecodeError) as e:
            last_error = e
            logger.warning(
                f"Attempt {attempt + 1}/{max_retries} failed: {type(e).__name__}: {e}"
            )
            
            if attempt < max_retries - 1:
                # リトライ前に少し待機（Gemini APIのレート制限対策も兼ねる）
                time.sleep(retry_delay * (attempt + 1))  # 指数バックオフ
                
                # プロンプトにエラー情報を追加して再試行
                prompt = f"{prompt}

注意: 前回のレスポンスでJSONバリデーションエラーが発生しました。必ず指定されたスキーマに従ってください。エラー: {str(e)[:200]}"
    
    raise ValueError(
        f"Failed to generate valid structured output after {max_retries} attempts. "
        f"Last error: {last_error}"
    )

# 使用例
class SentimentAnalysis(BaseModel):
    text_snippet: str = Field(description="分析対象テキストの冒頭50文字")
    sentiment: str = Field(description="positive / negative / neutral のいずれか")
    confidence: float = Field(description="信頼度スコア 0.0〜1.0", ge=0.0, le=1.0)
    reason: str = Field(description="判定理由（100文字以内）")

analysis = generate_structured(
    client=client,
    prompt="『このサービスは使いにくく、サポートも最悪でした』というレビューを分析してください",
    model_class=SentimentAnalysis,
    max_retries=3,
)

print(f"感情: {analysis.sentiment}")
print(f"信頼度: {analysis.confidence:.2f}")
print(f"理由: {analysis.reason}")

# 期待する出力例:
# 感情: negative
# 信頼度: 0.97
# 理由: 「使いにくい」「最悪」という明確な否定表現が複数存在する
```

リトライ時にエラー情報をプロンプトに追加するのがポイントです。「前回のレスポンスでバリデーションエラーが発生した」という事実をGeminiにフィードバックすることで、2回目以降の成功率が大幅に上がります。

## 応用例：商品レビュー一括分析パイプライン

ここまでの知識を組み合わせて、実際のプロダクションで使えるレベルのパイプラインを構築します。ECサイトの商品レビューを一括で分析し、インサイトを抽出するシステムです。

```python
import asyncio
from typing import List
from pydantic import BaseModel, Field
from google import genai
from google.genai import types
import time

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

# ---- スキーマ定義 ----

class ReviewInsight(BaseModel):
    review_id: str
    sentiment: str = Field(description="positive / negative / neutral")
    main_issue: Optional[str] = Field(
        default=None,
        description="主な問題点。positiveの場合はnull"
    )
    main_praise: Optional[str] = Field(
        default=None,
        description="主な称賛点。negativeの場合はnull"
    )
    category_tags: List[str] = Field(
        description="関連カテゴリ（例: 配送, 品質, 価格, サポート）",
        max_length=5,
    )
    priority_score: int = Field(
        description="対応優先度 1-5（高いほど緊急）",
        ge=1, le=5
    )

class BatchAnalysisResult(BaseModel):
    insights: List[ReviewInsight]
    total_analyzed: int
    negative_ratio: float = Field(description="ネガティブ割合 0.0-1.0")
    top_issues: List[str] = Field(description="最頻出の問題点トップ3")

def analyze_reviews_batch(reviews: List[dict]) -> BatchAnalysisResult:
    """
    商品レビューのリストを一括分析する。
    
    Args:
        reviews: [{"id": "...", "text": "..."}, ...] 形式のレビューリスト
    
    Returns:
        BatchAnalysisResult: 分析結果とサマリー統計
    """
    # レビューをプロンプト形式に変換
    reviews_text = "

".join([
        f"レビューID: {r['id']}
内容: {r['text']}"
        for r in reviews
    ])
    
    prompt = f"""以下の{len(reviews)}件の商品レビューを分析してください。
各レビューの感情分析、問題点・称賛点の抽出、カテゴリタグ付け、対応優先度を判定し、
全体のサマリー統計も含めてください。

レビュー一覧:
{reviews_text}

注意: 
- sentiment は必ず "positive", "negative", "neutral" のいずれかのみ使用すること
- priority_score は1（低優先）〜5（高優先・即対応）の整数のみ
- negative_ratio は全レビューに対するネガティブの割合（0.0〜1.0）"""
    
    return generate_structured(
        client=client,
        prompt=prompt,
        model_class=BatchAnalysisResult,
        max_retries=3,
    )

# ---- テスト実行 ----

sample_reviews = [
    {"id": "R001", "text": "配送が2週間かかり、問い合わせても返答がなかった。二度と使わない"},
    {"id": "R002", "text": "商品の品質は素晴らしい！梱包も丁寧で大満足です"},
    {"id": "R003", "text": "価格は安いが品質も相応。特に不満はない"},
    {"id": "R004", "text": "サイズが説明と違った。返品対応は迅速だったが最初から正確な情報を"},
    {"id": "R005", "text": "リピート購入しています。品質が安定していて信頼できます"},
]

result = analyze_reviews_batch(sample_reviews)

print(f"分析件数: {result.total_analyzed}")
print(f"ネガティブ率: {result.negative_ratio:.1%}")
print(f"主な問題点: {', '.join(result.top_issues)}")
print()

# 高優先度レビューの抽出
high_priority = [i for i in result.insights if i.priority_score >= 4]
print(f"高優先度レビュー（要対応）: {len(high_priority)}件")
for insight in sorted(high_priority, key=lambda x: x.priority_score, reverse=True):
    print(f"  [{insight.priority_score}] {insight.review_id}: {insight.main_issue}")

# 期待する出力例:
# 分析件数: 5
# ネガティブ率: 40.0%
# 主な問題点: 配送遅延, サイズ情報の不正確さ, カスタマーサポートの反応
#
# 高優先度レビュー（要対応）: 2件
#   [5] R001: 配送が2週間遅延し、問い合わせへの返答なし
#   [3] R004: 商品サイズが説明と相違
```

このパイプラインを実際のプロダクションに組み込む際は、レビューの数が多い場合に1バッチあたり10〜20件に分割することをお勧めします。一度に100件以上を投げると、Geminiがスキーマに従いながらもデータの一部を省略するケースが増えます。

また、このシステムをCloud FunctionsやCloud RunなどのサーバーレスにデプロイしてPub/Sub経由で呼び出す構成にすると、ECサイトのレビュー投稿と連動したリアルタイム分析が実現できます。Gemini 2.5 Proであれば、このような複雑なバッチ分析でも概ね2〜5秒で安定したレスポンスが得られます。

## プロダクションへのデプロイ時の追加考慮事項

実際に本番サービスに組み込むにあたって、コード品質以外の観点でもいくつか把握しておきたいことがあります。

**レート制限への対処**

Gemini APIには1分あたりのリクエスト数（RPM）と1日あたりのトークン数（TPD）の制限があります。バッチ処理では `time.sleep()` による待機か、`asyncio.Semaphore` による同時リクエスト数の制限が有効です。

```python
import asyncio
from google import genai

async def analyze_reviews_async(
    reviews: List[dict],
    max_concurrent: int = 5  # 同時リクエスト数の上限
) -> List[ReviewInsight]:
    semaphore = asyncio.Semaphore(max_concurrent)
    
    async def analyze_one(review: dict) -> ReviewInsight:
        async with semaphore:
            # 非同期APIコール
            response = await client.aio.models.generate_content(
                model="gemini-2.5-flash",  # バッチ処理には Flash が費用対効果が高い
                contents=review["text"],
                config=types.GenerateContentConfig(
                    response_mime_type="application/json",
                    response_schema=ReviewInsight,
                ),
            )
            return ReviewInsight.model_validate_json(response.text)
    
    tasks = [analyze_one(r) for r in reviews]
    return await asyncio.gather(*tasks, return_exceptions=True)
```

**コストの見積もり**

`response_schema` を使うと、スキーマ情報がシステムプロンプトとして追加されるため、通常のテキスト生成よりも入力トークンが増えます。複雑なPydanticモデルでは数百トークンの追加が発生することがあるため、大量バッチ処理では `gemini-2.5-flash` の使用も検討してください。Flashはproより約10倍安価で、構造化出力の精度は実用上ほぼ同等です。

まずは Google AI Studio の [Gemini API 使い方ガイド](https://ai.google.dev/gemini-api/docs) でAPIキーを取得し、今日紹介したコードを試してみてください。小さな構造化出力から始めて、徐々に複雑なスキーマへ——その積み重ねが、壊れないLLMパイプラインへの最短ルートです。
