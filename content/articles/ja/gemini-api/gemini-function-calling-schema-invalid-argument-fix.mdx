OpenAI の Function Calling で動いていたツール定義をそのまま Gemini API に持ってきたら、初回リクエストで `400 INVALID_ARGUMENT: Invalid JSON payload received. Unknown name "..."` が返ってきた——そんな経験がある方は少なくないはずです。私自身、移植作業を5本ほど繰り返してようやくパターンが見えてきました。

Gemini の Function Calling は OpenAI 互換に見えて、実は受け付けるスキーマの方言が結構違います。同じ `type: "object"` を投げても、Gemini が静かに拒絶するキーワードが10個近くあります。ここでは私が実際に踏んだ落とし穴を「エラーメッセージ」と「修正前後のコード」のペアで整理しました。コピペで動く検証コード付きです。

## まず確認: Gemini が受け付けるのは「OpenAPI 3.0 サブセット」

Gemini の `tools.functionDeclarations.parameters` は、JSON Schema Draft-07 ではなく **OpenAPI 3.0 Schema Object のサブセット** を受け取ります。これが OpenAI 移植組がまず引っかかる根本原因です。

公式ドキュメントの一覧を読み解くと、**サポートされるキーワードは以下に限られます**。

- `type`（"string" / "number" / "integer" / "boolean" / "array" / "object" のいずれか）
- `description`
- `enum`（プリミティブ型のみ）
- `properties` / `required` / `items`
- `format`（"date-time" や "enum" など限定的）
- `nullable`（`null` を許す場合）

逆に、以下のキーワードは **そのまま渡すと INVALID_ARGUMENT になります**。

- `additionalProperties`
- `$ref` / `definitions` / `$defs`
- `anyOf` / `oneOf` / `allOf`
- `const`
- `pattern`（一部モデルでは無視される）
- `minimum` / `maximum`（受理されるが効果なし、というケースが報告されています）

この一覧を頭の片隅に置いておくと、この後のエラー解析がぐっと楽になります。

## ケース1: `additionalProperties` で 400 が返る

OpenAI の `strict: true` を真似て `additionalProperties: false` を明示すると、Gemini は次のエラーを返します。

```
400 INVALID_ARGUMENT: Invalid JSON payload received.
Unknown name "additionalProperties" at 'tools[0].function_declarations[0].parameters'
```

**修正前**:

```python
schema = {
    "type": "object",
    "properties": {"city": {"type": "string"}},
    "required": ["city"],
    "additionalProperties": False,  # ← Gemini はこのキーを知らない
}
```

**修正後**: そのキーを削除します。Gemini は OpenAPI 由来なので、定義していないプロパティは元々受け取りません。

```python
schema = {
    "type": "object",
    "properties": {"city": {"type": "string"}},
    "required": ["city"],
}
```

スキーマ生成ライブラリ（Pydantic や Zod）を使っている場合は、出力後に `additionalProperties` を再帰的に剥がす後処理を1つ挟むと安全です。

## ケース2: `anyOf` / `oneOf` を含むスキーマが弾かれる

「文字列または数値どちらでも受け取りたい」という Union 型を `anyOf` で書くと、ほぼ確実に拒否されます。

**修正前**:

```python
{"value": {"anyOf": [{"type": "string"}, {"type": "number"}]}}
```

Gemini は単一の `type` しか理解しないので、**どちらか一方の型に統一する**か、**string で受けてサーバー側でパース**する設計にするのが現実的です。私は後者を選ぶことが多く、`description` に「数値の場合は文字列で渡す（例: '42'）」と書いておくとモデルがほぼ意図通りに動いてくれます。

```python
{
    "value": {
        "type": "string",
        "description": "値。数値の場合も文字列として渡してください（例: '42', '3.14'）",
    }
}
```

「型安全を捨てるのか」と感じるかもしれませんが、Function Calling は出力を最終的にパースして検証する処理が必要な以上、入力スキーマでの型分岐に固執するメリットは薄いというのが私の実装感覚です。

## ケース3: `enum` の値に整数を混ぜると無視される

`enum` はサポートされていますが、配列の中身は **同一プリミティブ型** で揃える必要があります。

```python
# ❌ string と integer が混在 → モデルが enum を見ずに自由生成する
{"priority": {"type": "string", "enum": ["high", "low", 1, 0]}}

# ✅ 文字列のみで統一
{"priority": {"type": "string", "enum": ["high", "low"]}}
```

エラーは出ないのに、モデルが平気で `"medium"` を返してくるケースは大体この型不一致が原因です。`type` 指定と `enum` の中身が一致しているかを最初に疑ってください。

## ケース4: ネストしたオブジェクトで `properties` を省略する

`type: "object"` を書いたのに `properties` を一切定義しないと、Gemini は「中身が分からないオブジェクト」をうまく扱えず、空の `{}` を返してくることがあります。

```python
# ❌ object 宣言だけ
{"metadata": {"type": "object"}}

# ✅ 最低1つでも properties を持たせる
{
    "metadata": {
        "type": "object",
        "properties": {
            "source": {"type": "string", "description": "データの出所"}
        }
    }
}
```

「とりあえず任意の JSON を受け取りたい」という用途なら、`type: "string"` にして `description` で「JSON 文字列で渡す」と指示し、サーバー側で `json.loads()` する方が安定します。

## ケース5: `$ref` を含むスキーマを Pydantic から渡す

Pydantic v2 の `model_json_schema()` は、ネストしたモデルを `$ref` で参照する形式で出力します。Gemini はこれを解決できません。

```python
from pydantic import BaseModel

class Address(BaseModel):
    city: str

class User(BaseModel):
    name: str
    address: Address

print(User.model_json_schema())
# → {"$ref": "#/$defs/Address", ...} を含む辞書が出力される
```

**解決策**: Pydantic から渡す前に `$ref` を展開（dereference）します。簡易的には以下のようなヘルパーで対応できます。

```python
def dereference(schema: dict, defs: dict) -> dict:
    """$ref を再帰的に展開し、Gemini 互換の辞書に変換する"""
    if isinstance(schema, dict):
        if "$ref" in schema:
            ref_name = schema["$ref"].split("/")[-1]
            return dereference(defs.get(ref_name, {}), defs)
        return {k: dereference(v, defs) for k, v in schema.items() if k not in ("$defs", "additionalProperties")}
    if isinstance(schema, list):
        return [dereference(item, defs) for item in schema]
    return schema

raw = User.model_json_schema()
clean = dereference(raw, raw.get("$defs", {}))
# clean を tools.functionDeclarations.parameters に渡せば通る
```

このパターンは [Gemini API × Pydantic で型安全な構造化出力を作るガイド](/articles/gemini-api/gemini-api-pydantic-structured-output-type-safe-production) でも触れていますが、Function Calling 用にも同じ前処理を流用できます。

## 動作確認用の最小コード

修正後に「本当に通るか」を確認できる最小サンプルです。Python SDK（`google-genai`）を想定しています。

```python
from google import genai
from google.genai import types
import os

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

weather_tool = types.Tool(
    function_declarations=[
        types.FunctionDeclaration(
            name="get_weather",
            description="指定都市の天気を返す",
            parameters={
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "都市名（例: '東京'）"},
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "温度の単位",
                    },
                },
                "required": ["city"],
            },
        )
    ]
)

response = client.models.generate_content(
    model="gemini-3-pro",
    contents="東京の天気を摂氏で教えて",
    config=types.GenerateContentConfig(tools=[weather_tool]),
)

print(response.candidates[0].content.parts[0].function_call)
# 期待出力: name='get_weather' args={'city': '東京', 'unit': 'celsius'}
```

このコードが期待通り動けば、スキーマ側は問題ありません。それでも `function_call` が空で帰ってくる場合は、プロンプトで「ツールを使う必要性」が伝わっていない可能性が高く、`description` に呼び出し条件を1〜2行加えるだけで挙動が変わります。

## エラーが消えても挙動が安定しないときに見るべきポイント

スキーマが通ってもツール呼び出しがランダムに失敗する場合、原因はだいたい次の3つに集約されます。

ひとつ目は **モデルバージョン**。`gemini-2.5-flash` は Function Calling の挙動が `gemini-3-pro` よりも粗く、特に複数ツールを並列に並べると選択ミスが目立ちます。本番では Pro 系を選ぶ価値があります。

ふたつ目は **`description` の不足**。関数名やパラメータ名から推測できる情報しかないと、モデルは適当な引数を埋めてしまいます。ひとつのフィールドにつき「何を期待していて、どんな値が NG か」を1文ずつ添えるのがコツです。

みっつ目は **エラーハンドリング側の見落とし**。詳しくは [Gemini API エラーハンドリング完全ガイド](/articles/gemini-api/gemini-api-error-handling-troubleshooting) と [JSON 構造化出力エラーの直し方](/articles/gemini-api/gemini-api-json-structured-output-errors-fix) を読み合わせると、Function Calling 周辺のエラーが体系的に整理できると思います。Function Calling の基礎をまだ押さえていない方は、先に [Function Calling 完全入門ガイド](/articles/gemini-api/gemini-function-calling-guide) を読んでおくと、この記事の内容がより腹落ちするはずです。

## 次にやってみてほしいこと

OpenAI から移植したスキーマがあるなら、まずは「`additionalProperties` を削除」「`anyOf` を削除」「`$ref` を展開」の3点だけ機械的に適用してみてください。これだけで体感8割の INVALID_ARGUMENT は消えます。残った2割は description やネスト構造の問題なので、上記のケース別チェックリストを順に当てはめていけば必ず原因にたどり着けます。
