壁紙アプリのカテゴリ自動分類を作っていた夜のことです。数十枚をまとめて Gemini API に流したところ、処理の途中で `INVALID_ARGUMENT` が返り、バッチ全体が止まりました。API キーを疑い、モデル名を疑い、プロンプトを疑い、最後にようやく画像そのものに行き着きました。エラーコードが一つしかないせいで、原因の候補を全部疑う羽目になったのです。

この記事は、同じ場所で止まった方が「何を、どの順で確かめれば直るか」を持ち帰れるように書き直しました。2026年11月時点の公式ドキュメントに合わせ、旧世代の SDK（`google-generativeai`）で書いていたコードも `google-genai` に移してあります。

## まず結論：確かめる順番

**INVALID_ARGUMENT は、エラーメッセージ → 画像1枚での再現 → 送信前の検査、の順に絞ります。** バッチ全体を疑う前に、1枚だけを同じ経路で送って通るかどうかを見るのが、いちばん早い切り分けです。

次の表は、画像を扱うリクエストで私が実際に当たった原因を、見分ける手がかりと一緒に並べたものです。

エラーメッセージの文言は SDK の版やモデルで変わります。完全一致で分岐させず、「size」「mime」「parts」といった部分文字列で見るくらいがちょうどよいと考えています。

## なぜ INVALID_ARGUMENT は曖昧なのか

`INVALID_ARGUMENT`（HTTP 400）は、Google のエラーモデルで「リクエストの内容が受け付けられない」ことを表す大きな分類です。画像まわりでは、上の表の五つがほぼ全部を占めます。しかも一つのバッチに複数の原因が混ざることがあり、直したつもりなのに別の理由で失敗し続ける、ということが起きます。

だからこそ、事前検査を一か所にまとめておく設計が効きます。次の節から、原因ごとに検査コードを示します。

## 原因1：MIME タイプは中身から決める

最も見落としやすいのがこれです。保存元が複数あると、`.jpg` なのに中身は WebP、という画像が普通に混ざります。拡張子から MIME を決め打ちしたコードは、そうした画像を `image/jpeg` と宣言して送り、弾かれます。

以前の版では標準ライブラリの `imghdr` を使っていましたが、`imghdr` は Python 3.13 で標準ライブラリから外れました。外部ライブラリなしで済むよう、先頭バイトを自分で見る形にしています。

```python
from pathlib import Path

def sniff_mime(path: str) -> str:
    """拡張子ではなく先頭バイトから MIME タイプを判定する。判定できなければ例外。"""
    head = Path(path).read_bytes()[:16]
    if head.startswith(b"\xff\xd8\xff"):
        return "image/jpeg"
    if head.startswith(b"\x89PNG\r\n\x1a\n"):
        return "image/png"
    if head[:4] == b"RIFF" and head[8:12] == b"WEBP":
        return "image/webp"
    if head[:6] in (b"GIF87a", b"GIF89a"):
        return "image/gif"
    if head[4:8] == b"ftyp" and head[8:12] in (b"heic", b"heix", b"mif1"):
        return "image/heic"
    raise ValueError(f"未対応または破損の可能性: {path}")
```

判定できない画像は、黙って `image/jpeg` にフォールバックしないことがポイントです。フォールバックは一見親切ですが、破損ファイルを「通ったように見せて後で落とす」原因になります。例外にして、呼び出し側でスキップとログ記録に回します。

## 原因2：サイズは「合計」と「base64 の膨らみ」で見る

インラインで送る画像データは、base64 にするとバイナリより約 33% 大きくなります。そして上限は1枚ごとではなく、リクエスト全体に掛かります。1枚ずつなら問題のない画像でも、10枚まとめると超える、ということです。

**サイズの上限は、必ず公式の現行値を確かめてから決めます。** 以前の私の記事は「インラインは20MBまで」と書いていましたが、Google は Gemini API のファイル入力の上限を引き上げたと公式ブログで告知しています。数値は今後も動く可能性があるので、コードには固定値を埋め込まず、設定値として一か所に置きます。

```python
import os

# 公式の「File input methods」ページで現行の上限を確認し、余裕を持たせた値を入れる。
INLINE_BUDGET_BYTES = 15 * 1024 * 1024   # 1リクエストで inline に使う合計（保守的な値）

def b64_size(n_bytes: int) -> int:
    return (n_bytes + 2) // 3 * 4

def plan_request(paths: list[str]) -> dict:
    """inline で送る画像と File API に回す画像に振り分ける。"""
    inline, upload, used = [], [], 0
    for p in sorted(paths, key=os.path.getsize):
        cost = b64_size(os.path.getsize(p))
        if used + cost <= INLINE_BUDGET_BYTES:
            inline.append(p); used += cost
        else:
            upload.append(p)
    return {"inline": inline, "upload": upload, "inline_bytes": used}
```

小さい画像から順に inline の予算へ詰め、あふれた分を File API に回します。「15MB を超える1枚だけ File API」という単純な規則より、合計で見たほうがバッチでの失敗が減ります。

## 原因3：REST を直接叩くときの `contents` の構造

Python SDK を通している間は、SDK が構造を整えてくれます。REST を直接叩く場合は、テキストと画像を同じ `parts` の配列に入れる必要があります。

```python
# ❌ text と inline_data が別々の要素になっている
contents = [
    {"text": "画像のカテゴリを分類してください"},
    {"inline_data": {"mime_type": "image/jpeg", "data": encoded_img}},
]

# ✅ 一つの content の中に parts を作る
contents = [
    {
        "role": "user",
        "parts": [
            {"text": "画像のカテゴリを分類してください"},
            {"inline_data": {"mime_type": "image/jpeg", "data": encoded_img}},
        ],
    }
]
```

私がこれに当たったのは、処理時間を測るために SDK を一時的に外して REST を直接呼んだときでした。SDK が裏でやっていた変換を、自分で書き忘れていたのです。

## google-genai SDK で書き直した実装

旧世代の `google-generativeai` は、後継の `google-genai` に置き換わっています。移行時の注意は、別の記事（[google-genai SDK への移行で出るエラー](/articles/gemini-api/gemini-api-google-genai-sdk-migration-errors)）にまとめています。

次のコードは、上の三つの検査を一つにまとめたものです。**この環境では実際に API を呼んで動作を確認できていません。** SDK の呼び出し形は公式の移行ガイドと照らして書いていますが、手元で1枚だけ流して確かめてからバッチに使ってください。

```python
import time
from google import genai
from google.genai import types, errors

client = genai.Client()  # 環境変数のキーを読む。コードにキーを書かない
MODEL = "gemini-2.5-flash"  # 使っているモデル ID に置き換える

def to_part(path: str) -> types.Part:
    mime = sniff_mime(path)
    return types.Part.from_bytes(data=open(path, "rb").read(), mime_type=mime)

def upload_part(path: str) -> types.Part:
    f = client.files.upload(file=path)
    while f.state and f.state.name == "PROCESSING":
        time.sleep(2)
        f = client.files.get(name=f.name)
    if f.state and f.state.name == "FAILED":
        raise RuntimeError(f"アップロード失敗: {path}")
    return types.Part.from_uri(file_uri=f.uri, mime_type=f.mime_type)

def classify(paths: list[str], prompt: str) -> str:
    plan = plan_request(paths)
    parts = [types.Part.from_text(text=prompt)]
    parts += [to_part(p) for p in plan["inline"]]
    parts += [upload_part(p) for p in plan["upload"]]
    try:
        res = client.models.generate_content(model=MODEL, contents=parts)
        return res.text
    except errors.ClientError as e:
        # 400 は設定ミスなのでリトライしない。メッセージを残して呼び出し側で原因を読む
        print(f"HTTP {e.code} / {e.status}: {e.message}")
        raise
```

`errors.ClientError` は 4xx 系をまとめて受けるので、`e.code` が 400 のときだけ「リトライしても直らない」と扱い、429 のときはリトライの対象にします。429 の見分け方は、[リトライ可能な 429 と上限到達の 429 の違い](/articles/gemini-api/gemini-api-429-retryable-vs-spend-cap-exhaustion-retry-design)で詳しく書きました。

## inline・File API・URL の使い分け

<table>
<thead>
<tr><th>方法</th><th>向く場面</th><th>気をつける点</th></tr>
</thead>
<tbody>
<tr><td>inline（バイト列で送る）</td><td>小さい画像を少数、1回で終える処理</td><td>リクエスト全体のサイズに数える。base64 で約 33% 増える</td></tr>
<tr><td>File API</td><td>大きい画像、同じ画像を何度も参照する処理</td><td>アップロードに時間がかかる。保存期間が限られるので、長く使い回すなら再アップロードの仕組みが要る</td></tr>
<tr><td>公開 URL を渡す</td><td>すでに公開されている画像を分析するだけの処理</td><td>対応状況と上限は公式ページで確認する。限定公開の画像には使えない</td></tr>
</tbody>
</table>

私なら、一度きりの小さな画像は inline、同じ画像を何度も問い合わせる処理は File API を選びます。理由は単純で、再送のたびにバイト列を載せ直すコストと、アップロードの待ち時間を天秤にかけると、参照回数が増えるほど File API が有利になるからです。

## よくある誤解

**「INVALID_ARGUMENT が出たらキーを疑う」は的外れです。** キーの問題は 401 や 403 の系統で返るのが普通で、400 はリクエストの中身の問題です。認証まわりは別記事（[認証エラーの切り分け](/articles/gemini-api/gemini-api-authentication-error-solutions)）に切り分けてあります。

**「拡張子が合っていれば MIME も合っている」も誤りです。** 保存元が複数ある運用では、拡張子はあてになりません。中身を見るのが確実です。

**「画像は大きいほど精度が上がる」とは限りません。** 送る前に縮小するほうが、サイズエラーの回避にも、待ち時間の短縮にもなります。縮小の考え方は[送信前に Pillow で縮小しておく理由](/articles/gemini-api/gemini-api-image-resize-pillow-before-upload)で扱っています。

## バッチを組むときの運用メモ

1リクエストに載せる枚数を増やしすぎると、タイムアウトやレスポンスの遅延が起きます。壁紙アプリでは、最初に上限を5枚としましたが、大きな画像が混ざるときは3枚程度に絞るほうが安定しました。この数は環境ごとに違うので、小さく始めて増やすのが安全です。

失敗したバッチは、全体を捨てずに1枚ずつに分けて再送します。どの1枚で落ちたかが分かれば、その画像だけを検査して除外できます。夜間の無人実行では、この「失敗を1枚に絞り込む」処理が入っているかどうかで、翌朝の手間が大きく変わります。

## 次に詰まりやすいところ

画像の分析が通るようになると、次は件数が増えたときの上限（429）と、画像が認識されない・結果が的外れ、という問題に当たります。後者は[画像が認識されないときの確認手順](/articles/gemini-api/gemini-api-image-input-not-recognized-troubleshooting)に整理しました。エラー全体の地図が欲しいときは、[Gemini API エラー全般の診断ガイド](/articles/gemini-api/gemini-api-error-troubleshooting-guide)を手元に置くと迷いにくくなります。

最初に気づいたのは、止まったのがコードではなく自分の検査の不足だった、という点でした。**送る前に検査する関数を一つ置いておく。** その線引きだけは、画像を扱う処理を書くたびに守っています。まずは手元の画像を1枚、`sniff_mime` に通すところから試してみてください。
