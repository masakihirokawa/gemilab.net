Gemini API を試したい人がまず躓くのが「API キーの取得」です。Google AI Studio の画面はシンプルですが、項目の意味が初見ではわかりにくく、`AIzaSy...` で始まるキーが手に入った瞬間にどう扱うべきかも自明ではありません。

この記事では、API キーの取得手順だけでなく、**個人開発者が複数プロジェクトを並行運用する** という現実的な状況で破綻しない運用方法までまとめます。私自身、Dolice Labs シリーズで複数のサイトを動かしているため、キーの管理には早い段階から失敗してきました。その教訓も交えて整理します。

## API キーを取得する手順

最短手順は次のとおりです。

1. [Google AI Studio](https://aistudio.google.com/apikey) を開く
2. Google アカウントでログイン
3. 「Create API key」をクリック
4. 既存の Google Cloud プロジェクトを選択するか、新規プロジェクトを作成
5. 発行されたキーをコピーして、安全な場所に保管

ここで気付きにくいポイントが2つあります。

**ポイント1**: 発行後の画面ではキー全体が表示されますが、一度閉じると先頭の数文字しか見えなくなります。コピーを忘れたら再発行になるので、必ずパスワードマネージャや `.env` ファイルへ即座に保管してください。

**ポイント2**: API キーは Google Cloud プロジェクトに紐づきます。プロジェクトを後から切り替えることはできないので、用途を決めてから発行するのが安全です。後述する「プロジェクト分離設計」のために、テスト用と本番用は別プロジェクトで作るのが定石です。

## 無料枠と有料プランの境界線

Gemini API には無料枠があり、個人開発で試す程度であれば課金なしでもかなり遊べます。一方で、無料枠と有料枠では挙動が微妙に違うので、最初に把握しておくと混乱を避けられます。

| 項目 | 無料枠 | 有料枠 |
|---|---|---|
| 1分あたりリクエスト | 制限が厳しい | プロジェクト・モデルごとに設定可 |
| 1日あたりリクエスト | モデルごとに上限 | 実質的に高い上限 |
| データ取り扱い | Google が学習に使う場合あり | 学習に使われない |
| 利用可能モデル | 最新モデルが時々制限される | フルサポート |
| サポート対応 | コミュニティ | サポートチケット可 |

特に「Google が学習に使う」という点は商用サービスでは致命的なので、本番運用に乗せるなら必ず有料化してください。Google Cloud の請求アカウントを紐付けるだけで切り替わります。

## 複数プロジェクトを安全に管理する設計

私の運用ポリシーは「**1プロジェクト＝1キー**」です。これは少し面倒ですが、長期的には絶対に得をします。

### プロジェクト分離の原則

```
個人開発者のキー管理マトリクス（推奨）

├── プロジェクトA（claudelab.net）
│   ├── 開発用キー: AIzaSy...dev1
│   └── 本番用キー: AIzaSy...prod1
│
├── プロジェクトB（gemilab.net）
│   ├── 開発用キー: AIzaSy...dev2
│   └── 本番用キー: AIzaSy...prod2
│
└── プロジェクトC（実験・お試し用）
    └── 共有キー: AIzaSy...sandbox
```

なぜ分離するのか。理由は3つあります。

第一に、**漏洩時の被害範囲を限定するため**。開発中に誤って GitHub に push してしまっても、影響範囲がプロジェクト1つに留まります。

第二に、**コスト計測の精度を上げるため**。本番運用が始まると、サイトごとにいくら使っているかを正確に把握したくなります。プロジェクトを分けておくと、Google Cloud Console の請求画面でサイトごとの内訳がそのまま見えます。

第三に、**レート制限の独立性を保つため**。1つのキーに集中させると、片方のサイトでバズって API を食い潰した瞬間、他のサイトも巻き込まれてダウンします。プロジェクト分離はこの種の連鎖障害を防ぎます。

## キーの保管 — `.env` か Secret Manager か

キーを取得したら、コードに直接書かないのが鉄則です。選択肢は次の3つです。

### 選択肢1: `.env` ファイル（小規模個人開発向け）

最も手軽な方法です。

```bash
# .env （絶対に Git にコミットしない）
GEMINI_API_KEY=AIzaSy...your_actual_key_here
```

```python
import os
from google import genai

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])
```

`.gitignore` に `.env` を追加するのを忘れないでください。私は `.env*` で追加しています（`.env.local`, `.env.production` も巻き取れるため）。

### 選択肢2: GitHub Secrets / Cloudflare Workers Secrets（CI/CD 連携時）

CI/CD やサーバーレス環境にデプロイする場合は、各プラットフォームの Secrets 機能を使います。Cloudflare Workers では `wrangler secret put GEMINI_API_KEY` でセットできます。コードからは環境変数として読み取れます。

### 選択肢3: Google Secret Manager（本格運用向け）

複数の人が触る、あるいは権限管理を厳密にしたい場合は Google Secret Manager が向いています。アクセスログが残り、IAM で誰がどのキーを読めるかをコントロールできます。

個人開発の最初は選択肢1で十分です。ユーザー数が増えてきたら2、3へ段階的に移行する流れがおすすめです。

## 漏洩したときの対応

GitHub に誤って push してしまった、ログに残してしまった、誰かと共有してしまった、といった事故は遅かれ早かれ起きます。重要なのは「気付いた瞬間に何をするか」です。

### 即時対応の3ステップ

1. **キーを即時無効化** — Google AI Studio または Google Cloud Console から該当キーを削除します。これで漏れたキーは即座に使えなくなります。
2. **新しいキーを発行** — 同じプロジェクト内で新しいキーを発行し、本番環境のシークレットを差し替えます。
3. **使用履歴を確認** — Google Cloud Console の請求画面で、漏洩発覚前の数時間に異常な使用量がないかチェックします。

GitHub に push してしまった場合は、commit を `git revert` するだけでは足りません。Git の履歴に残るためです。BFG Repo-Cleaner などで履歴ごと削除する必要がありますが、いずれにせよキーは無効化してください。「履歴から消したから大丈夫」は通用しません。

### 漏洩を未然に防ぐ仕組み

GitHub には Secret Scanning という機能があり、`AIzaSy...` で始まる Gemini API キーのパターンが含まれた commit は自動検知されます。私の運営しているサイト群でも、この検知が一度発動して肝を冷やしたことがあります。それ以来、コード例を書くときは必ず `YOUR_GEMINI_API_KEY` のようなプレースホルダーを使うようにしています。

```python
# ❌ NG — 実フォーマットを書くとSecret Scanningが反応する
api_key = "AIzaSyA0B1C2D3E4F5G6H7I8J9K0L1M2N3O4P5"

# ✅ OK — プレースホルダーで書く
api_key = "YOUR_GEMINI_API_KEY"
```

## キーごとの利用状況をモニタリングする

複数キーを運用しはじめると、「どのキーが今いくら使っているか」を把握するのが重要になります。Google Cloud Console の「APIとサービス → 認証情報 → 各キー」を開くと、過去 30 日の使用量が確認できます。

私は週に1回、すべてのキーの使用量を一覧化するスプレッドシートを更新しています。急増しているキーがあれば、コードに無限ループや重複呼び出しが入っていないかを真っ先に疑います。

## 次のアクション

まだ API キーを取得していなければ、まずは [Google AI Studio](https://aistudio.google.com/apikey) で1つ作って `.env` で管理してみてください。すでに使っている場合は、本記事の「プロジェクト分離設計」を参考に、開発用と本番用が同じキーになっていないか見直してみる価値があります。
