数日前まで落ち着いて動いていたバックエンドが、ある朝から `504 DEADLINE_EXCEEDED` を返し始めました。ログを開くと、同じエラーが数分おきに並んでいます。レート制限のように「何を超えたか」を教えてくれるエラーではなく、ただ「期限切れ」とだけ告げられるので、最初の一手で迷いました。

私はその日、まずタイムアウトを伸ばし、次にリトライを増やし、半日たってから所要時間を測りました。順番が逆だったのだと気づいたのは、記録を眺め終えたあとでした。測ってみると、遅いのは全体のほんの一部の入力だけで、残りは数秒で返っていました。

ここでは、そのとき組み直した診断の順番を、副作用の少ない順に5つのポイントとして書き残します。2026年11月時点の公式ドキュメントと SDK のソースで、モデル名・既定値・単位を確かめ直してあります。

## 504 DEADLINE_EXCEEDED は「どこで切れたか」を教えてくれません

`DEADLINE_EXCEEDED` は gRPC 由来のステータス名で、HTTP では 504 に対応します。公式の API errors ページ（2026年11月時点）は、このエラーを「期限内にリクエストが終わらなかった」と説明し、対処として「クライアント側の期限設定を外すか伸ばして、サーバーの既定値を使う」ことを挙げています。

つまり公式の第一の推奨は、こちらの期限が短すぎないかを疑うことです。ただ、実際の運用では「こちらが短い」のか「向こうが長い」のかを見分けないまま、どちらかを決め打ちしてしまいがちです。見え方は実行環境ごとに少しずつ違います。

- Python の `google-genai`: `google.genai.errors.ServerError` が上がり、`e.code` が 504、`e.status` が `DEADLINE_EXCEEDED`
- Python でクライアント側の期限が先に切れた場合: API のエラーではなく、通信ライブラリ（httpx）のタイムアウト例外
- Node.js で `fetch` を直接使う場合: `AbortError`、または自前で投げる `HTTP 504` の例外
- AI Studio: 画面上の「The request timed out」

見落としやすいのが例外クラスの取り違えです。リトライ処理を旧ライブラリの `google.api_core.exceptions.DeadlineExceeded` で受けていても、`google-genai` が投げるのは `google.genai.errors` 側の例外なので、except 節には一度も入りません。ログには 504 が並んでいるのに、再試行は一度も走らない——芳しくない状態です。

**例外は、思い込みの型ではなく、実際に飛んできた型で受けます。** 最初に一度だけ `print(type(e), getattr(e, "code", None))` を出しておくと、この線引きを守りやすくなります。

## ポイント1: タイムアウトを触る前に、所要時間の分布を測ります

最初にやることは、同じプロンプトと同じモデルを AI Studio で実行してみることです。AI Studio で正常に返るのに自分のコードで切れるなら、こちらの期限が短い可能性が高くなります。AI Studio でも止まる、あるいは極端に遅いなら、入力かモデルの側を疑います。

次に、手元でも所要時間を記録します。平均だけを見ると見誤るので、ばらつき（p50 と p95）と、遅かったリクエストの中身を一緒に残すのが要点です。

```python
# 診断用: 呼び出しごとの所要時間・結果・入力の目安を記録し、分布を出す
import statistics
import time
from google import genai
from google.genai import errors

client = genai.Client(api_key="YOUR_API_KEY")
records = []  # (秒, 結果, モデル, ラベル)

def measured_generate(model: str, contents, label: str = ""):
    start = time.perf_counter()
    status = "OK"
    try:
        return client.models.generate_content(model=model, contents=contents)
    except errors.APIError as e:
        status = f"{e.code} {e.status}"       # 例: 504 DEADLINE_EXCEEDED
        raise
    except Exception as e:                    # httpx のタイムアウトなど、こちら側の打ち切り
        status = type(e).__name__
        raise
    finally:
        elapsed = time.perf_counter() - start
        records.append((elapsed, status, model, label))
        print(f"[{status}] {model} {label} {elapsed:.2f}s")

def summarize():
    times = sorted(r[0] for r in records)
    if len(times) < 2:
        return
    q = statistics.quantiles(times, n=20)     # 5% 刻みの区切り値
    p50, p95 = q[9], q[18]
    print(f"n={len(times)} p50={p50:.1f}s p95={p95:.1f}s max={times[-1]:.1f}s")
    for r in records:
        if r[0] >= p95:
            print("slow:", r)
```

`label` には「どの機能から呼んだか」や「入力の文字数・ページ数」を入れておきます。ここを空にすると、遅い行を見つけても何が重かったのかが分かりません。

出力はこの形になります（数値は例です）。

```text
[OK] gemini-3.8-flash faq:1200chars 3.42s
[504 DEADLINE_EXCEEDED] gemini-3.8-flash pdf:180pages 61.03s
n=120 p50=4.1s p95=58.7s max=61.0s
slow: (61.03, '504 DEADLINE_EXCEEDED', 'gemini-3.8-flash', 'pdf:180pages')
```

10〜20件では偏りが出るので、私は丸一日ぶんを貯めてから `summarize()` を呼ぶようにしています。p50 が数秒で p95 だけが期限に張り付いているなら、原因は全体ではなく一部の入力にあるのかもしれません。

## ポイント2: 入力の大きさ（長文・PDF・動画）を疑います

ランダムに見える `DEADLINE_EXCEEDED` も、ポイント1の記録を並べると「特定の入力だけが遅い」ことが多いです。私の手元で偏りが出やすかったのは次の3つでした。

- 長い文脈を毎回まるごと送る会話や要約
- ページ数の多い PDF・Office 文書
- 数分以上の動画

長いものを1リクエストで送る設計は、運用が落ち着くまで避けたほうが無難です。代わりに、ファイルは File API に上げておき、推論時は参照だけを渡します。公式の Files API ページ（2026年11月時点）では、アップロードしたファイルは 48 時間で自動削除され、PDF をリクエストに直接埋め込む場合は 50 MB が上限と書かれています。

```python
# Before: PDF を毎回リクエストに埋め込む（転送と解析が毎回走る）
from google.genai import types

with open("report.pdf", "rb") as f:
    pdf_bytes = f.read()
response = client.models.generate_content(
    model="gemini-3.8-flash",
    contents=[types.Part.from_bytes(data=pdf_bytes, mime_type="application/pdf"),
              "この資料の要点を5つに絞って教えてください。"],
)

# After: File API に一度だけ上げ、推論では参照を渡す（48 時間で消える点に注意）
uploaded = client.files.upload(file="report.pdf")
response = client.models.generate_content(
    model="gemini-3.8-flash",
    contents=[uploaded, "この資料の要点を5つに絞って教えてください。"],
)
```

こう書く理由は、転送の時間と推論の時間を分けて測れるようにするためです。アップロードで遅いのか、推論で遅いのかが分かれば、次に触る場所が一つに絞れます。48 時間を過ぎた参照は使えないので、長く使う資料は「上げ直す」処理も一緒に用意しておきます。

それでも遅い資料は、章ごとに分けて要約し、最後にまとめる二段構えにしています。1回あたりの所要時間が揃うので、期限の設定も決めやすくなります。

## ポイント3: クライアントのタイムアウトを、単位まで確かめて明示します

公式が第一に勧めているのがここです。`google-genai`（Python）と `@google/genai`（JavaScript）の `HttpOptions.timeout` は、どちらも**ミリ秒**です（2026年11月時点の SDK ソースで確認）。

```python
from google import genai
from google.genai import types

client = genai.Client(
    api_key="YOUR_API_KEY",
    http_options=types.HttpOptions(timeout=180_000),  # ミリ秒 = 180 秒
)

response = client.models.generate_content(
    model="gemini-4-argon",
    contents="長めの分析レポートを書いてください。",
)
```

JavaScript の SDK でも同じ考え方です。

```ts
import { GoogleGenAI } from "@google/genai";

const ai = new GoogleGenAI({
  apiKey: process.env.GEMINI_API_KEY,
  httpOptions: { timeout: 180_000 }, // ミリ秒 = 180 秒
});

const res = await ai.models.generateContent({
  model: "gemini-3.8-flash",
  contents: "長めの分析レポートを書いてください。",
});
console.log(res.text);
```

`fetch` で REST を直接呼んでいる場合は、`AbortController` で期限を自分で持ちます。

```ts
// Node.js / エッジ共通: AbortController で期限を管理する
const ctrl = new AbortController();
const timer = setTimeout(() => ctrl.abort(), 180_000); // 180 秒

try {
  const res = await fetch(
    "https://generativelanguage.googleapis.com/v1beta/models/gemini-3.8-flash:generateContent",
    {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-goog-api-key": process.env.GEMINI_API_KEY!,
      },
      body: JSON.stringify({ contents: [{ parts: [{ text: "..." }] }] }),
      signal: ctrl.signal,
    }
  );
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${await res.text()}`);
  const data = await res.json();
  console.log(data.candidates?.[0]?.content?.parts?.[0]?.text);
} finally {
  clearTimeout(timer);
}
```

エラー時に `await res.text()` を一緒に出しているのは、504 の本文に `DEADLINE_EXCEEDED` の status が入っているかどうかで、API が返したのか途中の中継が返したのかを見分けるためです。

私が以前ひやりとしたのは、秒のつもりで `timeout=180` と書きかけたことでした。これでは 0.18 秒で切れてしまい、すべてのリクエストが失敗します。症状は「全件が即座に失敗する」なので、ポイント1の記録で経過時間が 0 秒台に揃っていたら、まず単位を疑ってください。

ただし、期限を伸ばすのは「こちらが短かった」場合の直し方です。p95 だけが長い場合は、伸ばしても待ち時間が長くなるだけなので、ポイント2とポイント4に進みます。

## ポイント4: モデルと thinking_level を、待てる時間から選び直します

Gemini 3 以降のモデルは、既定で考える（thinking）時間を取ります。公式の Thinking ページ（2026年11月時点）では、`thinking_level` が品質・待ち時間・トークン量を決めるいちばんの調整つまみとして説明されています。難しい問いほど遅いという症状は、ここで解けることが多いです。

<table>
<thead>
<tr><th>用途</th><th>モデル ID</th><th>既定の thinking_level</th><th>こんなときに選びます</th></tr>
</thead>
<tbody>
<tr><td>短い分類・抽出・タグ付け</td><td>gemini-3.5-flash-lite</td><td>minimal</td><td>件数が多く、1件あたりの待ち時間を短く揃えたいとき</td></tr>
<tr><td>通常の文章生成・FAQ 応答</td><td>gemini-3.8-flash</td><td>medium</td><td>ユーザーが画面の前で待つ処理の標準として</td></tr>
<tr><td>長文の構造化・込み入った推論</td><td>gemini-4-argon</td><td>medium</td><td>Flash では質が足りないが、待ち時間はできるだけ抑えたいとき</td></tr>
<tr><td>最も深い推論が要る処理</td><td>gemini-4-carbon</td><td>medium</td><td>結果を後で受け取れる非同期の処理に限って</td></tr>

判断の基準は一文で言えます。**画面の前で人が待つ処理は Flash 系、待たせてよい処理だけを上位モデルへ。** 迷ったら、まず thinking_level を下げて測り、それでも質が足りないときにだけモデルを上げる順番にしています。

```python
# 同じ入力で thinking_level だけを変えて所要時間を比べる
import time
from google.genai import types

prompt = "この問い合わせを、返金・不具合・要望のどれかに分類してください: ..."
for level in ["low", "medium", "high"]:
    start = time.perf_counter()
    r = client.models.generate_content(
        model="gemini-3.8-flash",
        contents=prompt,
        config=types.GenerateContentConfig(
            thinking_config=types.ThinkingConfig(thinking_level=level)
        ),
    )
    print(level, f"{time.perf_counter() - start:.2f}s", (r.text or "")[:40])
```

公式は、待ち時間やコストを下げたいときに `max_output_tokens` を小さくするのではなく、thinking_level を下げるよう勧めています。`max_output_tokens` は思考のトークンも含めた上限なので、考えている途中で打ち切られると、空や途中までの出力が返り、思考ぶんの料金はかかります。

もう一つ、モデル名そのものも確かめます。公式の deprecations ページ（2026年11月時点）では、2026年12月1日から `gemini-2.5-pro` への API リクエストは `gemini-3.8-flash` へ、`gemini-2.5-flash` は `gemini-3.5-flash-lite` へ自動で振り替わり、料金も移行先のものになります。`gemini-2.5-flash-lite` は廃止対象ではありません。コードに 2.5 の名前が残っていると、12月以降は所要時間の分布そのものが変わるので、ポイント1の記録を振り替えの前後で取り直してください。

## ポイント5: リトライの持ち主を一つにします

待ちなしで即座に再試行するリトライは、混んでいるサーバーにさらに負荷をかけ、504 を増やすことがあります。指数バックオフ（待ち時間を少しずつ伸ばす）とジッタ（小さなランダムの揺れ）は必須です。

そのうえで、私がいちばん時間を使ったのは「誰がリトライしているのか」でした。自前のループと SDK の再試行が重なると、1件の失敗が何倍もの送信になります。

<table>
<thead>
<tr><th>方式</th><th>向いている場面</th><th>気をつけること</th></tr>
</thead>
<tbody>
<tr><td>SDK の HttpRetryOptions に任せる</td><td>再試行の条件が単純で、ログは件数だけ分かればよいとき</td><td>自前のループを重ねない。最悪の待ち時間を計算しておく</td></tr>
<tr><td>自前のループで書く</td><td>再試行のたびに入力を軽くしたり、モデルを落としたりしたいとき</td><td>SDK 側の再試行を切っておく。止める条件を必ず書く</td></tr>
</tbody>
</table>

SDK に任せる場合は、`HttpOptions` に `retry_options` を渡します。

```python
from google import genai
from google.genai import types

client = genai.Client(
    api_key="YOUR_API_KEY",
    http_options=types.HttpOptions(
        timeout=120_000,  # 1回の試行あたり 120 秒（ミリ秒指定）
        retry_options=types.HttpRetryOptions(
            attempts=3,               # 最初の1回を含めた回数
            initial_delay=2.0,        # 秒
            max_delay=30.0,           # 秒
            http_status_codes=[503, 504],
        ),
    ),
)
```

こう書いておくと、最悪の待ち時間は「試行回数 × タイムアウト ＋ 待機の合計」で見積もれます。上の例なら 3 × 120 秒に数秒の待機が加わり、6 分を少し超えます。手前にロードバランサやサーバーレスの実行上限があるなら、その値より短くなるように試行回数か期限を減らします。

再試行のたびに処理を変えたい場合は、自前で書きます。

```python
import random
import time
from google.genai import errors

def generate_with_fallback(contents, models=("gemini-4-argon", "gemini-3.8-flash"),
                           max_retries=3):
    last = None
    for attempt in range(max_retries):
        model = models[min(attempt, len(models) - 1)]  # 2回目以降は軽いモデルへ
        try:
            return client.models.generate_content(model=model, contents=contents)
        except errors.ServerError as e:
            if e.code not in (503, 504):
                raise
            last = e
            wait = (2 ** (attempt + 1)) + random.random()  # 2s, 4s, 8s ＋揺らぎ
            print(f"[retry {attempt + 1}/{max_retries}] {model} {e.code} {e.status} → {wait:.1f}s")
            time.sleep(wait)
    raise last
```

この形にしたのは、504 の多くが「その入力がそのモデルには重い」ことの表れだったからです。同じ条件で3回送るより、2回目で軽いモデルに落とすほうが、私の環境では回復が早くなりました。この関数を使うときは、`client` を作る際に `retry_options` を渡さないでおきます。

## よくある誤解を3つ

**1. 「SDK は何もしなくても 5xx を再試行してくれる」**
公式の troubleshooting ページには、SDK が一時的なエラーを既定で再試行すると書かれています。一方で、2026年11月時点の `google-genai`（Python）のソースを読むと、`retry_options` を渡さない場合、HTTP のステータスによる再試行はかからず、接続まわりのエラーだけが再試行される作りでした。版によって振る舞いが変わる可能性があるので、私は `retry_options` を明示して、持ち主をはっきりさせるようにしています。

**2. 「タイムアウトは秒で書く」**
`HttpOptions.timeout` はミリ秒です。一方で `HttpRetryOptions` の `initial_delay` と `max_delay` は秒です。同じ設定の中に単位の違う値が並ぶので、コメントに単位を書いておくのが安全です。

**3. 「ストリーミングにすれば 504 はなくなる」**
ストリーミングは最初の文字が届くまでの時間を縮め、途中の中継が「無通信」と見なして切るのを避けやすくします。ただ、生成にかかる合計の時間は変わりません。重い入力そのものはポイント2とポイント4で軽くします。

## それでも直らないときは、別の層で切れています

5つを試しても変わらない場合、Gemini API ではなく、手前の層で切れている可能性があります。私が実際に当たったのは次のようなものでした。

- ロードバランサや NGINX の `proxy_read_timeout` が 60 秒のままで、そこで切れていました
- API キーが別のプロジェクトのもので、クォータや設定が想定と違っていました
- Cloudflare Workers の CPU 時間の上限に当たっていました

Cloudflare Workers の公式 Limits ページ（2026年11月時点）では、CPU 時間の上限は無料プランで 10 ms、有料プランで既定 30 秒、設定で最大 5 分（300,000 ms）です。`fetch()` の応答を待っている時間は CPU 時間に数えられません。つまり Gemini の返事を待つだけなら上限には当たりにくく、当たるのは受け取った大きな本文の整形や JSON の加工のほうです。上限を超えると返るのは 504 ではなく Error 1102（Worker exceeded resource limits）なので、エラーの番号で層を見分けられます。

エッジやサーバーレスでの起動の遅さが重なっている場合は、[Gemini API のコールドスタート対策](/articles/gemini-api/gemini-api-cold-start-mitigation-serverless-production)で扱っている測り方が役に立ちます。また、エラーの status ごとの扱い全体は[Gemini API のエラーを status で見分ける記事](/articles/gemini-api/gemini-api-error-troubleshooting-guide)にまとめてあります。

## 次に詰まりやすいのは、12月1日の振り替え後の所要時間です

504 が落ち着いたあとに当たりやすいのは、「エラーは出ないのに、返事の調子や速さが変わった」という症状です。2.5 系の名前を使い続けている場合、12月1日以降は別のモデルが応答します。依頼したモデル名と、実際に応答したモデル名を並べて記録する方法は、[Flash の返事の調子が変わった朝に、最初に見るログの記事](/articles/gemini-updates/gemini-flash-auto-routing-requested-vs-served-model-log)に書きました。

同時実行が増えて 429 と 504 が混ざるようになったら、[Gemini API のレート制限と 429 対策の運用ノート](/articles/gemini-api/gemini-api-rate-limiting-quota-management-production-guide)で同時実行数の抑え方を、再試行が雪崩のように増える場合は[Circuit Breaker と Bulkhead による耐障害性設計](/articles/gemini-api/gemini-api-resilience-circuit-breaker-bulkhead-production-guide)を合わせて読んでいただければと思います。
