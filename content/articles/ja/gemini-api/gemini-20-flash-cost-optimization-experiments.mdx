## 「Pro で組んでおけば間違いない」の落とし穴

Gemini API を本格的に個人開発に組み込み始めたとき、私はほとんどのタスクを Gemini 2.5 Pro で試していました。性能が高いモデルを使っておけば失敗しない、という素朴な発想です。

ところが、月次の API 利用明細を眺めていて気付きました。タスクの量に対して請求額の伸びが明らかに速い。特に、夜間に回しているバッチ処理が Pro を大量に消費していて、「これ、本当にここまでの知性が必要だったか？」という疑問が出てきたのです。

そこで 3 ヶ月かけて、タスクを順番に Gemini 2.0 Flash に移しながら「どこまで Flash で十分か」を検証する実験をやりました。この記事は、その実験ノートをまとめ直したものです。抽象的な「安いモデルを使いましょう」論ではなく、どのタスクは問題なく移せて、どのタスクは精度が落ちたかを、個別具体に書いていきます。

## Flash に切り替えて支障がなかった仕事たち

結論から書くと、私の個人開発ワークフローにあったタスクの 6 割強が、Flash に切り替えても実用上の支障なく動きました。ここで「実用上の支障なく」というのは、出力の質が人間の目から見て差が分からないレベル、という意味です。

### 日本語記事の英語化（要約ではなく翻訳）

既に日本語で書いた技術記事を英語化するタスクは、Flash で十分すぎるほど機能します。最初は「微妙な言い回しの味が抜けるのでは」と心配していましたが、実際には Flash でも技術用語・名前・コードブロックはしっかり保持されます。唯一気になるのは、文体が平坦になりがちな点ですが、これは温度や指示文で補正可能です。

Pro を使っていた頃と比べて、トークン単価で 5 倍以上安く済むので、翻訳バッチは真っ先に移す対象です。

### ドキュメントから FAQ への整形

既存のドキュメントや自分のブログ記事から、FAQ 形式に整形するタスクも Flash で問題なく動きます。「この機能の意図は？」「こういう場合はどうすれば？」といった Q&A の抽出と整形は、Flash のほうが明確に速く、体感で 3 倍以上のスループットが出ます。

### 構造化データの抽出

与えられたテキストから特定のフィールドを抜き出して JSON 化する、といった仕事は Flash の得意分野です。スキーマを明示してあげれば、Pro と結果がほぼ変わりません。むしろ構造に忠実で素直な出力が返ってくるので、ダウンストリームのパースが楽になります。

### コードの小さな修正（行数が少ない）

1 ファイル内で完結する、20 行以下の修正や関数追加は、Flash でも安定して成功します。新規アイデアの検討ではなく、すでに方針が決まっている修正の実行は Flash で十分です。

## Flash では厳しかった仕事たち

逆に、Flash に移したら目に見えて品質が落ちたタスクもあります。これは「Flash が劣る」というより、「Pro クラスの推論が本当に必要だった」仕事が可視化されたという感覚です。

### 設計相談や議論の深掘り

「この機能の実装方針、A と B どちらが筋がよいか」といった設計相談は、Flash だとどちらか片方を推す回答が浅いまま返ってきます。Pro だと両方の利点・欠点を挙げた上で、プロジェクト固有の制約に合わせて判断してくれますが、Flash はその「両側を真剣に考える」段階を省きがちです。

この差はプロンプトの書き方では埋まりません。素直に Pro を使ったほうが早いと割り切っています。

### 長文からの矛盾点抽出

複数のドキュメントや会議ログから「矛盾している箇所」を列挙させるタスクは、Flash だと見落としが多くなります。長文に対して表面的なパターンマッチで答えを返す傾向があり、深い整合性チェックには向いていません。

### 複数ファイルにまたがるコード変更

リファクタリングで複数ファイルを横断的に修正するような仕事は、Flash だと個別ファイルの変更はこなせても、全体整合性で漏れが出ます。このタイプの仕事は、素直に Pro(できれば Thinking オン)で走らせたほうが結局安くつきます。再実行のコストを考えると、高いモデルで 1 回通したほうが総コストが安い、という場面が確実にあります。

## スループットの実感 — 「速い」をどう活かすか

Flash のメリットはコストだけではなく、応答速度も大きいです。体感で Pro の 3〜5 倍は速く、並列実行した場合の総スループットはさらに違いが出ます。

私がこの速度を生かしている例を挙げておきます。

### アイデアの多数評価

新しい機能のアイデアを 30 個書き出して、それぞれに「実装難易度」「期待されるインパクト」「類似競合」のコメントを付けさせる、といったバッチ処理は、Pro だと結果が全部返るまでコーヒー 3 杯飲めるくらい待ちますが、Flash だと 1 杯分で終わります。意思決定のペースが目に見えて変わります。

### 大量データの一次整理

アンケート回答、ログエントリ、スクレイピング結果のような「数千件の短いテキスト」を分類・タグ付けするタスクも、Flash の速度が効く領域です。Pro で一件ずつ丁寧に判断するより、Flash で全件を素早く一次分類してから、怪しいものだけ Pro で再判定するほうが総コストが安くなります。

### 編集中のリアルタイム補助

IDE から呼ぶような、リアルタイムでコード補完や短い提案を求める用途では、レイテンシが体験を決めます。Flash の応答の速さは、ここでは単なるコスト削減ではなく UX そのものの改善になります。

## レート制限との付き合い方

Flash は無料枠のレート制限も比較的緩く、個人開発には嬉しい設計になっています。ただし、バッチで大量に叩くと意外なところで上限に触れます。実験中に気をつけたいポイントをいくつか書いておきます。

1 分あたりのリクエスト数上限、1 分あたりのトークン数上限、1 日あたりのリクエスト数上限は、それぞれ独立に効きます。夜間バッチで数千件を走らせるときは、単純にリクエスト間に短い sleep を入れるだけでは不十分で、同時並列数も制限する必要があります。

私は Python の `asyncio.Semaphore` で同時実行を 10 本に絞り、一定の失敗率を観測したら自動で 5 本に減らす、といった単純な適応制御を入れています。凝った再試行ロジックより、素直に並列数を減らしてから再開するほうが安定します。

```python
import asyncio
from google import genai

client = genai.Client()
sem = asyncio.Semaphore(10)

async def call_flash(prompt: str) -> str:
    async with sem:
        response = await client.aio.models.generate_content(
            model="gemini-2.0-flash",
            contents=prompt,
        )
        return response.text
```

ここで注目してほしいのは、`async with sem` の 1 行です。これだけで「同時に 10 本まで」という制約が入るので、追加のロジックなしにレート制限と仲良くできます。

## プロンプトの書き方で Pro と Flash の差を縮める

同じタスクでも、プロンプトの構造によって Flash の出力品質が体感で変わります。Pro は多少ぼんやりした指示でも文脈を補完してくれますが、Flash は指示の構造にわりと素直です。

### 出力形式を先に書く

「以下の形式で答えてください」を最初に書き、そのあとに入力データを置くと、Flash の出力が安定します。形式を最後に書くと、Flash は入力データに引きずられて自由形式で返しがちです。

### 長文は「抜粋 → 質問」の順で

長文を渡して質問する場合、Flash は 30 万トークンを超えるあたりから精度が落ちる傾向があります。可能なら事前に関連部分を抽出してから渡したほうが、Flash の強みが出ます。Pro の 100 万トークン級のコンテキストは Pro に任せ、Flash には「切り出し済みの素材」を渡す、という分担が効きます。

### 推論ステップを明示する

Flash は暗黙の推論が苦手です。「まず X を判定、次に Y を列挙、最後に Z を答える」というように、やってほしいステップを明示すると、回答の質がかなり上がります。Chain-of-Thought を簡略化した形、と思うと分かりやすいです。

## コストだけで判断しない、という大事な話

最後に、この 3 ヶ月の実験で学んだ一番大きな教訓を書いておきます。それは「Flash に置き換えるかどうかを、トークン単価だけで決めてはいけない」ということです。

Flash は安いですが、品質が足りず再実行が必要になると、結局 Pro より高くつきます。私が一度やった失敗は、コード生成タスクを全部 Flash に移して、生成されたコードのバグが原因で 3 回呼び直しが発生し、Pro 一発より 2 倍のコストになった、というものです。

タスクを移すかどうかは、「Flash で成功する確率 × Flash のコスト」と「Pro で成功する確率 × Pro のコスト」を比較するのが正しい見方です。成功確率を無視した単純コスト比較は、ほぼ確実に後から効いてきます。

個人開発者にとって、Flash はコストとスピードの両面で強力な選択肢です。ただし「Pro の下位互換」ではなく、「仕事の性質が違う道具」として扱うと長く付き合えます。自分のワークフローの中に眠っている「Pro である必要がない仕事」を一つずつ Flash に明け渡していくと、毎月の API 予算にちょうどよい余裕が生まれてきます。次に書くプロンプトから、Flash でも通るか一度考えてみてください。
