Gemini APIは強力なAI機能を提供しますが、大量のリクエストを処理するとAPIコストが予想以上に膨らむことがあります。本記事では、**Redis**を使ったキャッシュ層を実装し、同一・類似クエリのAPI呼び出しをスキップすることで、**応答速度を最大10倍に向上させ、APIコストを最大80%削減**する方法を解説します。

## なぜGemini APIのレスポンスをキャッシュするのか

AIアプリケーションの多くは、同じあるいは非常に似た質問を繰り返し受け取ります。たとえばカスタマーサポートチャットボットでは「営業時間は？」「返品方法は？」といった定型的な問いが毎日何百回も届くことがあります。

このようなケースで毎回Gemini APIを呼び出すと、以下のコストが発生します。

- **トークンコスト**: Gemini 3.1 Flashでも入出力トークンごとに課金される
- **レイテンシ**: APIラウンドトリップで100〜500ms程度の遅延が生じる
- **クォータ消費**: 高頻度リクエストがレート制限に引っかかる可能性がある

Redisを使ったキャッシュ層を挟むことで、キャッシュヒット時は**0〜5ms**でレスポンスを返せるようになり、APIコストも劇的に下がります。

## Redisとセマンティックキャッシュの概要

### 従来のキャッシュ（完全一致）

最も単純なキャッシュは、クエリ文字列をそのままキーにしてRedisに保存する方法です。「今日の天気は？」というクエリのレスポンスを保存しておき、次に同じ文字列が来たらそのまま返します。

### セマンティックキャッシュ（意味的な類似度一致）

「本日の気温を教えて」と「今日は何度ですか？」は文字列としては異なりますが、**意味的には同じ質問**です。セマンティックキャッシュでは、クエリをベクトル埋め込みに変換し、コサイン類似度でキャッシュヒットを判定します。

## 基本的なキャッシュ実装（完全一致）

まずはシンプルなキャッシュから始めましょう。

```python
import hashlib
import json
import redis
import google.generativeai as genai

# 初期化
genai.configure(api_key=GEMINI_API_KEY)
model = genai.GenerativeModel("gemini-3-flash")
cache = redis.Redis(host=REDIS_HOST, port=REDIS_PORT, decode_responses=True)

# キャッシュのTTL（秒）: 24時間
CACHE_TTL = 86400

def get_gemini_response_cached(prompt: str) -> str:
    """
    Redisキャッシュ付きでGemini APIを呼び出す。
    キャッシュヒット時はAPIを呼び出さず即座に返す。
    """
    # プロンプトのハッシュをキーに使用
    cache_key = f"gemini:v1:{hashlib.sha256(prompt.encode()).hexdigest()}"

    # キャッシュチェック
    cached = cache.get(cache_key)
    if cached:
        print(f"✅ キャッシュヒット: {cache_key[:20]}...")
        return json.loads(cached)["text"]

    # APIを呼び出し
    print("🌐 API呼び出し実行...")
    response = model.generate_content(prompt)
    result_text = response.text

    # Redisに保存（TTL付き）
    cache.setex(
        cache_key,
        CACHE_TTL,
        json.dumps({"text": result_text, "prompt": prompt})
    )
    print(f"💾 キャッシュ保存完了（TTL: {CACHE_TTL}秒）")

    return result_text

# 使用例
if __name__ == "__main__":
    query = "Gemini APIのFunction Callingとは何ですか？"

    # 1回目: API呼び出しが発生
    response1 = get_gemini_response_cached(query)
    print(response1[:100])

    # 2回目: キャッシュから即座に返す（API呼び出しなし）
    response2 = get_gemini_response_cached(query)
    print(response2[:100])
```

**期待する出力**:
```

💾 キャッシュ保存完了（TTL: 86400秒）
Gemini APIのFunction Callingは、モデルが...

✅ キャッシュヒット: gemini:v1:3a7b2c...
Gemini APIのFunction Callingは、モデルが...
```

## セマンティックキャッシュの実装

同じ意味を持つ異なる表現も同一のキャッシュにヒットさせるには、埋め込みベクトルを使った類似度検索が必要です。

```python
import numpy as np
from typing import Optional

class SemanticCache:
    """
    Gemini Embeddingsを使ったセマンティックキャッシュ。
    コサイン類似度が閾値以上の既存エントリを返す。
    """

    SIMILARITY_THRESHOLD = 0.92  # 類似度の閾値（0.0〜1.0）
    EMBED_MODEL = "models/text-embedding-004"
    CACHE_PREFIX = "gemini:semantic:"
    INDEX_KEY = "gemini:semantic:index"

    def __init__(self, redis_client: redis.Redis):
        self.cache = redis_client

    def _embed(self, text: str) -> list[float]:
        """テキストをベクトル埋め込みに変換"""
        result = genai.embed_content(
            model=self.EMBED_MODEL,
            content=text,
            task_type="retrieval_query"
        )
        return result["embedding"]

    def _cosine_similarity(self, vec_a: list, vec_b: list) -> float:
        """コサイン類似度を計算"""
        a = np.array(vec_a)
        b = np.array(vec_b)
        return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

    def get(self, query: str) -> Optional[str]:
        """
        セマンティック的に類似したキャッシュエントリを検索。
        見つかった場合はキャッシュされたレスポンスを返す。
        """
        query_vec = self._embed(query)

        # インデックスに登録済みのキーを全て取得
        all_keys = self.cache.smembers(self.INDEX_KEY)

        best_score = 0.0
        best_response = None

        for key in all_keys:
            entry_data = self.cache.hgetall(key)
            if not entry_data:
                continue

            stored_vec = json.loads(entry_data["embedding"])
            score = self._cosine_similarity(query_vec, stored_vec)

            if score > best_score:
                best_score = score
                best_response = entry_data.get("response")

        if best_score >= self.SIMILARITY_THRESHOLD:
            print(f"✅ セマンティックキャッシュヒット（類似度: {best_score:.3f}）")
            return best_response

        return None

    def set(self, query: str, response: str, ttl: int = 86400):
        """クエリとレスポンスのペアをキャッシュに保存"""
        query_vec = self._embed(query)
        cache_key = f"{self.CACHE_PREFIX}{hashlib.sha256(query.encode()).hexdigest()}"

        # ハッシュとして保存
        self.cache.hset(cache_key, mapping={
            "query": query,
            "embedding": json.dumps(query_vec),
            "response": response
        })
        self.cache.expire(cache_key, ttl)

        # インデックスに登録
        self.cache.sadd(self.INDEX_KEY, cache_key)
        print(f"💾 セマンティックキャッシュ保存: {cache_key[:30]}...")

def get_response_with_semantic_cache(query: str) -> str:
    """セマンティックキャッシュ付きGemini呼び出し"""
    semantic_cache = SemanticCache(cache)

    # セマンティックキャッシュを確認
    cached_response = semantic_cache.get(query)
    if cached_response:
        return cached_response

    # キャッシュミスの場合はAPI呼び出し
    print("🌐 API呼び出し実行...")
    response = model.generate_content(query)
    result = response.text

    # セマンティックキャッシュに保存
    semantic_cache.set(query, result)

    return result

# 動作確認
if __name__ == "__main__":
    # 1回目: API呼び出し
    r1 = get_response_with_semantic_cache("Gemini APIのコストを下げる方法は？")

    # 2回目: 別の表現でも類似度が高ければキャッシュヒット
    r2 = get_response_with_semantic_cache("Gemini APIの料金を節約するコツを教えて")
    # 出力: ✅ セマンティックキャッシュヒット（類似度: 0.947）
```

## TTL設計とキャッシュ無効化戦略

キャッシュの鮮度管理は重要です。コンテンツの種類に応じてTTLを設計しましょう。

```python
# コンテンツ種別ごとのTTL設定
CACHE_TTL_CONFIG = {
    "faq": 7 * 24 * 3600,        # FAQ: 7日間（変更頻度低）
    "product_info": 24 * 3600,    # 商品情報: 24時間
    "news_summary": 3600,         # ニュース要約: 1時間
    "realtime": 300,              # リアルタイム系: 5分
}

def get_ttl_for_query_type(query_type: str) -> int:
    return CACHE_TTL_CONFIG.get(query_type, 86400)

# タグベースのキャッシュ無効化
def invalidate_cache_by_tag(tag: str):
    """特定タグに関連するキャッシュを一括削除"""
    pattern = f"gemini:*:{tag}:*"
    keys = cache.scan_iter(match=pattern)
    deleted = 0
    for key in keys:
        cache.delete(key)
        deleted += 1
    print(f"🗑️ {deleted}件のキャッシュを削除しました（タグ: {tag}）")
```

### キャッシュ統計のモニタリング

```python
class CacheMetrics:
    """キャッシュのヒット率と節約コストを追跡"""

    def __init__(self, redis_client: redis.Redis):
        self.cache = redis_client
        self.hits_key = "gemini:metrics:hits"
        self.misses_key = "gemini:metrics:misses"

    def record_hit(self):
        self.cache.incr(self.hits_key)

    def record_miss(self):
        self.cache.incr(self.misses_key)

    def get_stats(self) -> dict:
        hits = int(self.cache.get(self.hits_key) or 0)
        misses = int(self.cache.get(self.misses_key) or 0)
        total = hits + misses
        hit_rate = (hits / total * 100) if total > 0 else 0

        # Gemini 3 Flash: 入力$0.075/100万トークン、出力$0.30/100万トークン（概算）
        avg_tokens_per_request = 500
        cost_per_request = (avg_tokens_per_request / 1_000_000) * 0.30
        estimated_savings = hits * cost_per_request

        return {
            "hits": hits,
            "misses": misses,
            "hit_rate": f"{hit_rate:.1f}%",
            "estimated_savings_usd": f"${estimated_savings:.4f}"
        }
```

コスト削減の詳細な計算方法については、[Gemini APIコスト完全最適化ガイド](/articles/gemini-api/gemini-api-cost-optimization-complete-guide)も参考にしてください。

## よくあるエラーと対処法

**ConnectionError: Error 111 connecting to localhost:6379**

Redisが起動していないか、接続先が間違っています。Dockerで起動している場合は`docker ps`でコンテナが稼働中かを確認し、ホスト名・ポートを再確認してください。

**ResponseError: WRONGTYPE Operation**

既存のキーのデータ型と操作が一致していません。キー名の衝突が原因の場合があります。`FLUSHDB`でキャッシュをリセットするか、キープレフィックスを変更してください。

**セマンティックキャッシュのヒット率が低い**

`SIMILARITY_THRESHOLD`を下げてみてください（例: 0.92→0.88）。ただし低すぎると関係のないレスポンスが返る可能性があるため、0.85程度を下限の目安にしてください。

また、Gemini APIのContext Caching機能（組み込みのプロンプトキャッシュ）と組み合わせると、さらなるコスト削減が期待できます。詳しくは[Gemini API Context Cachingによるコスト最適化](/articles/gemini-api/gemini-api-context-caching-cost-optimization)をご覧ください。

## FAQ

**Q: セマンティックキャッシュのために毎回Embeddingを生成するとコストがかかりませんか？**

A: Embedding APIのコストは生成APIに比べて約1/10程度です。キャッシュヒット率が50%以上であれば、Embeddingコストを差し引いてもトータルで大幅なコスト削減になります。ヒット率が低い初期段階では、まず完全一致キャッシュから始めるのが無難です。

**Q: Redisのメモリが不足した場合はどうなりますか？**

A: `maxmemory`と`maxmemory-policy`を適切に設定することで対応できます。`allkeys-lru`（最近最も使われていないキーを削除）が多くのケースで推奨されます。`redis.conf`に`maxmemory 512mb`と`maxmemory-policy allkeys-lru`を追加してください。

**Q: ユーザーごとにパーソナライズされた回答はキャッシュできますか？**

A: パーソナライズされた回答はキャッシュすべきではありません。キャッシュキーにユーザーIDを含める方法もありますが、ユーザー数が多いとメモリ効率が悪くなります。「汎用的な質問」と「ユーザー固有の質問」を分離し、前者だけをキャッシュするアーキテクチャが推奨です。
