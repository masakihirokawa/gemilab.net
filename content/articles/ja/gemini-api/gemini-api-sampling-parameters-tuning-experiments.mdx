「temperature は 0.7 くらいが無難」「創作系は 0.9 で良い」——こうした経験則だけに頼っていると、タスクによっては出力品質が大きくぶれます。特にGemini APIを本番アプリに組み込む段階では、パラメータ選びが原因の品質問題は外から見えにくく、ユーザーからの「時々おかしな応答が返る」という曖昧な報告だけが届きがちです。

私も最初は `temperature: 0.7` で全タスクを動かしていたのですが、要約タスクで重要な数値を取りこぼしたり、分類タスクで同じ入力に対して違うラベルが返ったりする問題に悩まされました。原因を追い込むため、4つの代表的タスクで実測データを取りながらパラメータを動かしていったところ、「タスクごとに効く軸が違う」ことが見えてきました。この記事はその実験記録です。

2014年からアプリ事業を続けている個人開発者の経験から、この問題に普段から向き合ってきた立場で、要点を整理します。

## サンプリングパラメータは「ランダム性の出し方」が3通りある

Gemini API の `generationConfig` で設定できる `temperature`、`topP`、`topK` はすべてランダム性を制御しますが、アプローチが異なります。一言で違いを整理すると次のようになります。

- **temperature（0.0〜2.0）**: 各トークンの確率分布を「鋭く／なだらかに」する。0.0に近いほど最高確率のトークンだけを選び続け、値が大きいほど低確率のトークンも採用されやすくなる
- **topP（0.0〜1.0）**: 累積確率がP以下になる候補だけに絞り込む。nucleus samplingと呼ばれ、文脈次第で候補数が可変になる
- **topK（1〜40）**: 上位K件の候補だけに絞り込む。候補数が固定で、文脈を無視して機械的に切る

Gemini 2.5 系のデフォルトは `temperature: 1.0, topP: 0.95, topK: 64` ですが、このデフォルトは「汎用チャット」向けの設計です。特定タスクに最適化すると、精度と再現性を同時に上げられる余地があります。

## 実験の設計 — 4タスク × 5パラメータセット

私が比較に使ったのは次の4タスクです。どれも実際のアプリで動かしているものです。

1. **要約タスク**: 3,000文字の日本語記事を200文字で要約（重要な数値を落とさないこと）
2. **分類タスク**: カスタマーサポートのメール本文を「請求」「技術」「解約」「その他」に分類
3. **コード生成タスク**: 自然言語の仕様から Python 関数を生成（PEP 8 準拠）
4. **創作タスク**: 商品説明文を200文字で生成（3回生成して多様性を確認）

各タスクに対して、次の5セットを回しました。各セットでサンプルは10回ずつ取り、タスクごとに適切な指標（要約は情報保持率、分類は正解率、コード生成はテスト通過率、創作はユニーク表現率）で評価しています。

- Set A: `temperature: 0.0, topP: 1.0, topK: 1`（完全決定論的）
- Set B: `temperature: 0.2, topP: 0.9, topK: 20`（低ランダム）
- Set C: `temperature: 0.7, topP: 0.95, topK: 40`（中ランダム・デフォルト寄り）
- Set D: `temperature: 1.0, topP: 0.95, topK: 64`（Gemini 2.5 デフォルト）
- Set E: `temperature: 1.5, topP: 0.98, topK: 80`（高ランダム）

## 測定用の最小コード

実験コードは以下のように、`google-genai` SDK の `generation_config` を差し替えるだけで済ませました。`safety_settings` は要約・分類では邪魔になるので、実験中は最小限に緩めています。本番では必ず適切に設定し直してください。

```python
# gemini_sampling_experiment.py
import os
import json
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

PARAM_SETS = {
    "A_deterministic": {"temperature": 0.0, "top_p": 1.0, "top_k": 1},
    "B_low":           {"temperature": 0.2, "top_p": 0.9, "top_k": 20},
    "C_mid":           {"temperature": 0.7, "top_p": 0.95, "top_k": 40},
    "D_default":       {"temperature": 1.0, "top_p": 0.95, "top_k": 64},
    "E_high":          {"temperature": 1.5, "top_p": 0.98, "top_k": 80},
}

def run_once(prompt: str, params: dict) -> str:
    """1回の生成を行い、失敗時は例外を伝播させずログに残す。"""
    try:
        response = client.models.generate_content(
            model="gemini-2.5-flash",
            contents=prompt,
            config=types.GenerateContentConfig(
                temperature=params["temperature"],
                top_p=params["top_p"],
                top_k=params["top_k"],
                max_output_tokens=512,
            ),
        )
        return response.text or ""
    except Exception as e:
        return f"[ERROR] {e.__class__.__name__}: {e}"

def experiment(prompt: str, n: int = 10) -> dict:
    results = {}
    for name, params in PARAM_SETS.items():
        results[name] = [run_once(prompt, params) for _ in range(n)]
    return results

if __name__ == "__main__":
    prompt = "次の記事を200文字で要約してください。数値は必ず保持してください。\n---\n（ここに3000文字の記事を入れる）"
    data = experiment(prompt, n=10)
    with open("results.json", "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
    print("✅ 実験完了: results.json")
```

期待する出力はセットごとに10個の応答が `results.json` に書き出される状態です。あとはタスク別の評価関数を別ファイルに書いて、各応答をスコアリングすれば結果が得られます。評価関数は手書きでもよいですし、Gemini自身に評価させる「LLM-as-a-judge」方式も使えます。

### タスク別の評価関数を書くときのコツ

評価関数で最もミスしやすいのは、「スコアの定義が曖昧なままコードを書き始める」ことです。私は実験前に紙に「このスコアが1.0になるのはどういう応答か」「0.5になるのはどういう応答か」を言語化してから、評価コードに落とすようにしています。要約タスクならば「数値が1つ欠ける」=「0.1減点」、分類タスクならば「正解=1.0、不正解=0.0」のように、減点基準を事前に固定すると後の解釈で迷いません。

## 結果 — タスクごとに効く軸が違う

10サンプルの平均を並べると、予想と違う部分がいくつもありました。特に印象的だったのは「要約タスクで Set A（完全決定論的）が必ずしも実用的ではない」ことでした。

### 要約タスク（情報保持率）

- Set A: 情報保持率 0.82 / ばらつき 0.00（毎回同じ出力）
- Set B: 情報保持率 0.88 / ばらつき 0.02（ほぼ同じ出力・語彙が少し変わる）
- Set C: 情報保持率 0.85 / ばらつき 0.08
- Set D: 情報保持率 0.79 / ばらつき 0.14
- Set E: 情報保持率 0.68 / ばらつき 0.22

**発見**: Set A より Set B のほうがスコアが高い。temperature 0.0 は「一番確率の高いトークン」を選び続けるため、文脈的に妙な固有表現を選び続けてしまうケースがありました。逆に Set B の軽いランダム性は、モデルに「少し考え直す」余地を与えている印象です。要約タスクで完全決定論にする必要はありません。

### 分類タスク（正解率）

- Set A: 正解率 0.96 / 再現性 100%
- Set B: 正解率 0.94 / 再現性 92%
- Set C: 正解率 0.88 / 再現性 76%
- Set D: 正解率 0.82 / 再現性 64%
- Set E: 正解率 0.61 / 再現性 38%

**発見**: 分類は Set A（完全決定論的）が明確に実用的。4択のように出力空間が狭いタスクでは、ランダム性は純粋にノイズです。Cookie の有無などで「本番は一貫性が欲しい」ケースでは、必ず `temperature: 0.0, topK: 1` に設定してください。

### コード生成タスク（テスト通過率）

- Set A: テスト通過率 0.70 / 再現性 100%
- Set B: テスト通過率 0.82 / 再現性 88%
- Set C: テスト通過率 0.76 / 再現性 62%
- Set D: テスト通過率 0.68 / 再現性 50%
- Set E: テスト通過率 0.44 / 再現性 22%

**発見**: コード生成では Set B（`temperature: 0.2`）が最適。完全決定論にすると、モデルが「明らかに非効率なパターン」にハマり続ける現象が出ました。軽いランダム性があると、もう一つ良い実装を選ぶ確率が上がります。

### 創作タスク（ユニーク表現率）

- Set A: ユニーク表現率 0.12（ほぼ同じ文章）
- Set B: ユニーク表現率 0.28
- Set C: ユニーク表現率 0.54
- Set D: ユニーク表現率 0.72
- Set E: ユニーク表現率 0.89

**発見**: 創作は高いランダム性が必要。ただし Set E は「ユニーク」といっても、半分近くが文法的に破綻したり、商品と関係ない内容になったりしました。実用域は Set C〜D の間で、`temperature: 0.9, topP: 0.95, topK: 50` あたりを開始点にするのがおすすめです。

## タスク別チューニングの指針

4タスクの結果を一般化すると、次のように整理できます。**この値は開始点であり、あなたのプロンプトとモデルで必ず再検証してください。**

- **分類・抽出・スコアリング**: `temperature: 0.0, topP: 1.0, topK: 1`（再現性が最重要）
- **要約・翻訳・整形**: `temperature: 0.2, topP: 0.9, topK: 20`（軽くランダム性を入れると語彙が自然になる）
- **コード生成・SQL生成**: `temperature: 0.2, topP: 0.9, topK: 20`（軽いランダム性が実装選択肢を広げる）
- **チャット・雑談**: `temperature: 0.7, topP: 0.95, topK: 40`（デフォルト寄り）
- **創作・ブレスト・コピー生成**: `temperature: 0.9, topP: 0.95, topK: 50`（多様性が欲しい）
- **アイデア量産（質は後で絞る）**: `temperature: 1.3, topP: 0.98, topK: 80`（広く打って拾う）

## 3つの軸を「同時に動かさない」のがコツ

私が実験中にハマった落とし穴が、temperature と topP を同時に動かしてしまうことです。両方ともランダム性を制御するパラメータなので、片方を動かしたら他方は固定して効果を切り分けるべきでした。

最初に動かすなら `temperature` だけで十分です。`temperature` を 0.0・0.2・0.5・0.8・1.0 の5段階で試し、タスクのスコアがどう動くかを見てから、さらに絞り込みたい場合だけ `topP` を触ると、少ないサンプル数でも実験の解釈がしやすくなります。

なお、`thinking_level`（Gemini 2.5 Pro）を併用する場合はパラメータの効き方がまた変わります。高 thinking level では出力の「推論過程」が長くなり、temperature の影響が相対的に小さくなる傾向があります。詳しくは[Gemini API の thinking_level パラメータガイド](/articles/gemini-api/gemini-api-thinking-level-parameter-guide)も参考にしてください。

## 本番での設定の持ち方 — タスクごとにプリセットを分離する

実験が終わったら、結果を「本番コードで迷わず呼べる形」に落とすのが大切です。私はこんな定数ファイルを作って、`generation_config` を組み立てる時にプリセット名で指定するようにしています。

```python
# sampling_presets.py
from google.genai import types

PRESETS = {
    "classify":  {"temperature": 0.0, "top_p": 1.0,  "top_k": 1},
    "summarize": {"temperature": 0.2, "top_p": 0.9,  "top_k": 20},
    "code":      {"temperature": 0.2, "top_p": 0.9,  "top_k": 20},
    "chat":      {"temperature": 0.7, "top_p": 0.95, "top_k": 40},
    "creative":  {"temperature": 0.9, "top_p": 0.95, "top_k": 50},
    "brainstorm":{"temperature": 1.3, "top_p": 0.98, "top_k": 80},
}

def make_config(preset: str, max_tokens: int = 512) -> types.GenerateContentConfig:
    """プリセット名から GenerationConfig を生成する。存在しないキーは例外にする。"""
    if preset not in PRESETS:
        raise ValueError(f"Unknown preset: {preset}. Available: {list(PRESETS.keys())}")
    p = PRESETS[preset]
    return types.GenerateContentConfig(
        temperature=p["temperature"],
        top_p=p["top_p"],
        top_k=p["top_k"],
        max_output_tokens=max_tokens,
    )

# 使い方
# config = make_config("classify")
```

このように「タスク種別 → パラメータ」を分離すると、`temperature` を直接コードに散らかす悪い癖が防げます。パラメータの見直しも1ファイルを書き換えるだけになり、レビューの時に差分が読みやすくなります。

また、A/Bテストをするときも、プリセット名を付け替えるだけでメトリクスに紐付けられます。`response_inconsistency` の原因追及でも役に立ちました（[Gemini APIの応答のばらつきを抑えるtemperature運用](/articles/gemini-api/gemini-api-response-inconsistency-temperature-guide)も併せて読むと理解が深まります）。

## さいごに — パラメータは「測ってから決める」

この記事で一番伝えたかったのは、**経験則の値を使う前に、自分のプロンプトで一度測ってみる**ということです。Gemini API の無料枠だけでも、10サンプル × 5セット × 4タスクの実験は十分回せます。所要時間は1時間もかかりません。

今日すぐできる一歩としては、あなたのアプリで一番「たまにおかしな応答が返る」機能を1つ選び、そのプロンプトに対して上の実験スクリプトを走らせてみることです。数値が手元にあれば、チームで議論するときも「温度感」ではなく「根拠」で決められるようになります。
