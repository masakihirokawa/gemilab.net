# Gemini API Embeddingエラー解決ガイド：RAG精度低下・次元不一致・429エラーの原因と対処法

Gemini APIのEmbeddingモデルを使ってRAG（Retrieval-Augmented Generation）システムや類似検索を構築しようとすると、意外と多くのところで詰まります。

「ベクトルDBへの挿入でエラーが出る」「似ているはずのテキストが類似度ゼロになる」「バッチ処理中に429エラーが連発する」——これらは正しいアプローチで対処すれば解決できるものばかりです。

この記事では、Gemini Embeddingを使う上でよくあるトラブルと、実際のコードを交えた解決策をお伝えします。

## Gemini Embeddingの基本と対応モデル

まず、現在利用できる主なEmbeddingモデルを整理しておきましょう。

- **text-embedding-004**: 768次元。多目的で最もよく使われる汎用モデル
- **gemini-embedding-exp-03-07**: 実験的な新モデル。次元数は最大3072（設定可能）
- **embedding-001**: 旧世代。新規開発では非推奨

混乱の多くは、異なるモデルで生成したEmbeddingを混在させること、またはモデルの次元数を把握せずにベクトルDBを設定することから生じます。

## エラー①：次元数の不一致でベクトルDBへの挿入が失敗する

**症状**: `chromadb.errors.InvalidDimensionException: Embedding dimension 768 does not match collection dimensionality 1536` のようなエラーが出る。

これは最もよくあるエラーです。ベクトルDBのコレクション（またはインデックス）を作成するとき、モデルの出力次元と一致させていないことが原因です。

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_API_KEY")

# まずモデルの実際の次元数を確認する
def check_embedding_dimensions(text: str = "テスト", model: str = "text-embedding-004") -> int:
    result = genai.embed_content(
        model=f"models/{model}",
        content=text,
        task_type="RETRIEVAL_DOCUMENT"
    )
    dims = len(result["embedding"])
    print(f"モデル: {model} → 次元数: {dims}")
    return dims

# 確認してからコレクションを作成する
dims = check_embedding_dimensions()  # → 768

import chromadb
client = chromadb.Client()
# ✅ 次元数を明示してコレクションを作成
collection = client.create_collection(
    name="my_docs",
    metadata={"hnsw:space": "cosine"},
    # ChromaDBはembeddingの次元を自動検出するが、
    # Pinecone/Qdrantなど他のDBでは明示的に指定が必要
)
```

**Pineconeを使う場合の例:**

```python
import pinecone

# ✅ 次元数を先に確認してからインデックス作成
EMBEDDING_DIMS = 768  # text-embedding-004の場合

pc = pinecone.Pinecone(api_key="YOUR_PINECONE_KEY")
pc.create_index(
    name="gemini-docs",
    dimension=EMBEDDING_DIMS,  # ← ここをモデルに合わせる
    metric="cosine",
    spec=pinecone.ServerlessSpec(cloud="aws", region="us-east-1")
)
```

**既存のインデックスを使い回す場合の注意点**: モデルを変更した（例：embedding-001からtext-embedding-004に変更）場合、既存のインデックスをそのまま使うと次元数が合わなくなります。必ずインデックスを再作成し、全データを再Embeddingしてください。

## エラー②：類似検索の精度が極端に低い

**症状**: 明らかに似ているテキスト同士の類似度が低く、関係のないテキストが上位に来る。

これはほぼ必ず `task_type` の設定ミスが原因です。Gemini Embeddingには`task_type`という重要なパラメータがあり、用途によって使い分ける必要があります。

```python
# ❌ task_typeを設定しないとデフォルト値（SEMANTIC_SIMILARITY）になる
# RAGシステムではこれが精度低下の原因になることが多い
result = genai.embed_content(
    model="models/text-embedding-004",
    content=text
)

# ✅ RAGシステムでの正しい使い分け
# ドキュメント（インデックスに格納する側）
def embed_document(text: str) -> list[float]:
    result = genai.embed_content(
        model="models/text-embedding-004",
        content=text,
        task_type="RETRIEVAL_DOCUMENT"  # ← ドキュメントにはこれ
    )
    return result["embedding"]

# クエリ（検索する側）
def embed_query(query: str) -> list[float]:
    result = genai.embed_content(
        model="models/text-embedding-004",
        content=query,
        task_type="RETRIEVAL_QUERY"  # ← 検索クエリにはこれ
    )
    return result["embedding"]
```

**task_typeの選び方:**

- `RETRIEVAL_DOCUMENT`: データベースに格納するドキュメント向け
- `RETRIEVAL_QUERY`: ユーザーが検索するクエリ向け（RAGで最も重要）
- `SEMANTIC_SIMILARITY`: 2つのテキストの意味的類似度を比較する場合
- `CLASSIFICATION`: テキスト分類タスク向け
- `CLUSTERING`: クラスタリング向け

**既存のデータベースにtask_typeが混在している場合**: ドキュメントとクエリで異なるtask_typeを使ってEmbeddingを生成した場合、類似度が正しく計算されません。データベースを再構築する際は、統一した設定で全データを再Embeddingしてください。

## エラー③：429 レートリミットでバッチ処理が中断する

**症状**: 大量のテキストをEmbeddingしようとすると途中で `429 Resource Exhausted` エラーになる。

```python
import time
import google.generativeai as genai
from google.api_core import exceptions

def embed_with_retry(
    texts: list[str],
    model: str = "text-embedding-004",
    task_type: str = "RETRIEVAL_DOCUMENT",
    batch_size: int = 100,  # 1バッチの上限は100テキスト
    retry_delay: float = 2.0
) -> list[list[float]]:
    """レートリミット対応のバッチEmbedding処理"""
    
    all_embeddings = []
    
    for i in range(0, len(texts), batch_size):
        batch = texts[i:i + batch_size]
        
        for attempt in range(3):
            try:
                # バッチリクエスト（最大100件を1リクエストで処理可能）
                results = genai.embed_content(
                    model=f"models/{model}",
                    content=batch,  # リストを渡すとバッチ処理
                    task_type=task_type
                )
                all_embeddings.extend(results["embedding"])
                
                # バッチ間に少し待機してレートリミットを回避
                if i + batch_size < len(texts):
                    time.sleep(0.5)
                break
                
            except exceptions.ResourceExhausted:
                wait_time = retry_delay * (2 ** attempt)
                print(f"レートリミット。{wait_time:.1f}秒待機... (バッチ {i//batch_size + 1})")
                time.sleep(wait_time)
            
            except Exception as e:
                print(f"予期しないエラー: {e}")
                raise
    
    return all_embeddings

# 使い方
documents = ["テキスト1", "テキスト2", ...]  # 何千件でもOK
embeddings = embed_with_retry(documents)
```

**無料枠でのレートリミット回避のコツ**: Gemini APIの無料枠はリクエスト数（RPM）に制限があります。`batch_size`を小さくして`time.sleep`を長めに設定するか、有料プランへの切り替えが根本的な解決策です。

## エラー④：テキストが長すぎてEmbeddingに失敗する

**症状**: 長い文書をそのままEmbeddingしようとすると `InvalidArgument: 400 Request payload size exceeds the limit` エラーが出る。

text-embedding-004の入力上限は約2,048トークンです。日本語では概ね800〜1,200文字が目安です。

```python
import tiktoken  # またはsentencepieceで推定

def split_and_embed_long_text(
    text: str,
    max_chars: int = 800,
    overlap: int = 100,
    task_type: str = "RETRIEVAL_DOCUMENT"
) -> list[dict]:
    """長文を分割してEmbeddingするチャンク処理"""
    
    # チャンク分割（オーバーラップ付き）
    chunks = []
    start = 0
    while start < len(text):
        end = start + max_chars
        chunk = text[start:end]
        
        # 文の途中で切らないよう、句読点で調整
        if end < len(text):
            for sep in ["。", "\n\n", "\n", "。"]:
                last_sep = chunk.rfind(sep)
                if last_sep > max_chars // 2:
                    chunk = chunk[:last_sep + 1]
                    end = start + last_sep + 1
                    break
        
        chunks.append({
            "text": chunk,
            "start_pos": start,
            "end_pos": end
        })
        start = end - overlap  # オーバーラップで文脈を保持
    
    # 各チャンクをEmbedding
    for chunk in chunks:
        result = genai.embed_content(
            model="models/text-embedding-004",
            content=chunk["text"],
            task_type=task_type
        )
        chunk["embedding"] = result["embedding"]
    
    return chunks

# 使い方（長い文書の場合）
long_text = "非常に長い文書テキスト..."
chunks = split_and_embed_long_text(long_text)
print(f"{len(chunks)}個のチャンクに分割してEmbedding完了")
```

## よくある質問

**Q: 日本語テキストのEmbeddingは英語より精度が低いですか？**
A: text-embedding-004は多言語対応で、日本語でも十分な精度が出ます。ただし、英語と日本語を混在させたベクトルDBで検索する場合、言語をまたいだ検索精度は文脈によって異なります。同じ言語でクエリとドキュメントを揃えると精度が安定します。

**Q: embedding-001からtext-embedding-004に移行するときは？**
A: 次元数が変わる（768次元）ため、既存のベクトルDBのインデックスを再作成する必要があります。段階的に移行する場合は、新旧モデルのインデックスを別々に持ち、切り替えが完了したら旧インデックスを削除してください。

**Q: Embeddingのキャッシュは有効ですか？**
A: はい、同じテキストを何度もEmbeddingするのはAPIコストの無駄遣いです。Redis等を使って結果をキャッシュするか、インデックスへの追加時に重複チェックを行うことをおすすめします。

## まとめ

Gemini Embedding APIのトラブルは、次のチェックリストで大半が解決できます。

- 次元数の不一致 → モデルの次元を確認してからベクトルDBを作成する
- 類似精度が低い → ドキュメントは `RETRIEVAL_DOCUMENT`、クエリは `RETRIEVAL_QUERY` を使い分ける
- 429エラー → バッチ処理＋指数バックオフリトライで対応
- テキスト超過 → チャンク分割（800文字目安、オーバーラップ付き）で処理

RAGシステムの品質はEmbeddingの正確さに大きく依存します。task_typeの設定を正しくするだけで、検索精度が劇的に改善するケースが多いので、まずここから確認してみてください。
