「昨日まで動いていた Gemini API への呼び出しが、突然 404 を返し始めた」という報告を最近よく聞きます。特に `gemini-2.5-pro-latest` のように `-latest` サフィックス付きのモデル名を使っていたコードで起きやすい症状です。`generativelanguage.googleapis.com/v1beta/models/gemini-2.5-pro-latest:generateContent` のようなリクエストが `{ "error": { "code": 404, "message": "models/gemini-2.5-pro-latest is not found..." } }` を返してきます。

この症状は、Gemini API のモデル命名規則とエイリアス仕様を理解していないと、なかなか原因に辿り着けません。ここではなぜ 404 になるのか、正しいモデル名の指定方法は何か、そして本番コードでバージョンをどう固定すべきかを、具体的なエンドポイント呼び出しの例を交えて整理します。

## まず起きていることを正確に把握する

Gemini API は、モデル識別子として 3 種類の書き方を許容しています。それぞれで挙動が微妙に異なります。

ひとつ目は**完全バージョン指定**、例えば `gemini-2.5-pro-001` のようにサフィックスが数字で固定されたもの。これは特定のリリースを指します。

ふたつ目は**ベース名**、例えば `gemini-2.5-pro` のようにサフィックスなしのもの。Gemini API はこれを受け取ると、内部で「このベース名の最新安定版」を自動選択します。

みっつ目は `-latest` 付きのエイリアス、例えば `gemini-2.5-pro-latest` のような書き方です。これは従来の Gemini 1.5 系では広く使われていましたが、**Gemini 2.5 世代では `-latest` サフィックスのサポート状況が変わっています**。モデル名によってはすでに 404 を返す形になっており、これが現在多くのユーザーが遭遇している症状の正体です。

つまり、404 になっているのは「API が壊れた」のではなく、「指定したモデル名が現在の正式な識別子として認識されていない」という状態です。

## 正しいモデル名を特定する手順

まず自分の API キーで、今どのモデルが使えるのかを確認するのが一番確実です。`ListModels` エンドポイントを呼ぶと、現在のプロジェクトで利用可能なモデル一覧が返ってきます。

```bash
curl "https://generativelanguage.googleapis.com/v1beta/models?key=$GEMINI_API_KEY"
```

返ってくる JSON の `models[].name` に、実際に呼べるモデル識別子がすべて列挙されています。`models/gemini-2.5-pro` のようなベース名が並んでいれば、そのまま使って問題ありません。`gemini-2.5-pro-latest` がそこに含まれていなければ、それがこの API では使えないモデル名だということです。

一覧を見るのが面倒であれば、まず `gemini-2.5-pro`（`-latest` 抜き）でリクエストを投げ直してみてください。大抵の場合、これだけで 404 は解消します。

## なぜ `-latest` が問題になるのか

`-latest` エイリアスは「常に最新版」を指しますが、本番運用の観点からは危険を伴います。モデルの挙動が予告なく変わる可能性があるためです。Google DeepMind 側もこの点を意識して、Gemini 2.5 世代ではベース名（サフィックスなし）の方を「安定版ルーティング先」として案内しています。

私自身、個人アプリでこの罠にはまった経験があります。Gemini 1.5 Pro を `-latest` 指定で呼んでいたコードを 2.5 Pro に移行する際、単純に `1.5` を `2.5` に置換したところ、`gemini-2.5-pro-latest` は 404 になり、旧コードが壊れる形になりました。正しい移行は「ベース名に切り替える」ことで、これだけで復旧します。

## 本番コードでのバージョン固定の考え方

個人開発や社内ツールでは `gemini-2.5-pro`（ベース名）指定で十分です。Gemini API 側が安定版にルーティングしてくれるため、突然挙動が変わる心配はほぼありません。

一方で、金融・医療・法務など再現性が求められる領域では、完全バージョン指定（`gemini-2.5-pro-001` のようなもの）を推奨します。これなら Google 側が新バージョンをリリースしても、自分たちが明示的に切り替えない限り古いバージョンが使われ続けます。

完全バージョン指定を使う場合でも、そのバージョンは将来サポート終了（deprecation）する可能性があるため、`ListModels` のレスポンスに含まれる `deprecationDate` を定期的に確認するワークフローを組んでおくのが実務的です。

## `generativelanguage.googleapis.com` そのものにつながらないケース

404 ではなく、そもそもリクエストが届かない・タイムアウトするという場合は、別の原因を疑います。

最もよくあるのは、**API キーが Vertex AI 用のもので Gemini Developer API 用ではない** というパターンです。Google Cloud には「Gemini Developer API（`generativelanguage.googleapis.com`）」と「Vertex AI（`aiplatform.googleapis.com`）」の 2 系統があり、両者は API キーもエンドポイントも別です。AI Studio で取得したキーは Developer API 用、gcloud CLI で発行した認証は Vertex 用、と覚えておくと混乱しません。

次によくあるのは、企業プロキシやファイアウォールで `generativelanguage.googleapis.com` への TLS 接続が遮断されているケース。`curl -v` で実際のハンドシェイクを確認し、途中で切れているならネットワーク管理者に相談してください。

## Python / Node.js SDK の場合の落とし穴

Python の `google-generativeai` SDK や Node.js の SDK を使っている場合、モデル名をコードから渡している箇所を確認します。

Python の例:

```python
import google.generativeai as genai
genai.configure(api_key=API_KEY)
# 404 になる書き方
model = genai.GenerativeModel("gemini-2.5-pro-latest")
# 推奨される書き方
model = genai.GenerativeModel("gemini-2.5-pro")
```

Node.js の `@google/genai` も同様で、`model` パラメータにベース名を渡すだけで解決します。SDK のバージョンが古いとベース名指定がうまく動かない場合があるので、SDK を最新に更新することも合わせて行ってください。

## この症状に遭ったときのチェックリスト

404 を見たら、順番に次を確認してください。

- モデル名に `-latest` が含まれていないか（含まれている = 外してみる）
- ベース名（例: `gemini-2.5-pro`）で投げ直して通るか
- `ListModels` エンドポイントで現在使えるモデル一覧を取得する
- API キーが Developer API 用か Vertex AI 用かを区別できているか
- 企業ネットワーク越しの場合、`generativelanguage.googleapis.com` への到達性に問題はないか

この 5 点を順番に見れば、Gemini API の 404 は大半が数分で解消します。本番コードではベース名または完全バージョン指定のどちらかに統一しておくと、将来のモデル更新で壊れる心配もなくなります。
