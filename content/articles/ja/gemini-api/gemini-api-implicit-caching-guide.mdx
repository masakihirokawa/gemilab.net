長いシステムプロンプトや大きなドキュメントコンテキストを毎回フルに送信していて、「なぜこんなにトークン費用がかさむのか」と感じたことはないだろうか。Gemini 2.5 Pro / 2.5 Flash が導入した **Implicit Caching（暗黙キャッシュ）** は、コードを1行も変えずに、繰り返しのプレフィックスを自動的にキャッシュしてくれる機能だ。

この記事では、その仕組みから実際の確認方法、最大限に活用するための設計パターンまでを体系的に解説する。

## Implicit Caching とは何か：明示的キャッシュとの根本的な違い

Gemini API には現在、2種類のキャッシュ機能が存在する。

**明示的コンテキストキャッシュ（Explicit Context Caching）** は、開発者が `caches.create()` を使ってキャッシュオブジェクトを作成し、`cache_name` をリクエストに渡す方式だ。事前に「このコンテンツをキャッシュして」と宣言する必要がある。最小32,768トークン以上が必要で、TTLも自分で管理する。

一方、**Implicit Caching（暗黙キャッシュ）** はその名の通り、何も宣言しなくていい。Gemini 2.5 モデルは同一セッション内で同じ先頭プレフィックス（システムプロンプト＋ドキュメントなど）を検出すると、自動的に2回目以降のリクエストにキャッシュ済みトークンを適用する。

```python
# 明示的キャッシュ：事前設定が必要
from google import genai
from google.genai import types

client = genai.Client()

# キャッシュを作成（最小32,768トークン以上）
cache = client.caches.create(
    model="gemini-2.5-pro",
    contents=[large_document_content],
    ttl="3600s"
)

# キャッシュを参照してリクエスト
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=user_query,
    config=types.GenerateContentConfig(
        cached_content=cache.name
    )
)
```

```python
# 暗黙キャッシュ：コードは通常通りでよい
from google import genai
from google.genai import types

client = genai.Client()

# 1回目：通常通り送信
response_1 = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=[
        {"role": "user", "parts": [
            {"text": LONG_SYSTEM_CONTEXT},  # 数万トークンの前置コンテキスト
            {"text": "最初の質問は何ですか？"}
        ]}
    ]
)

# 2回目以降：同じLONG_SYSTEM_CONTEXTが自動的にキャッシュされる
response_2 = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=[
        {"role": "user", "parts": [
            {"text": LONG_SYSTEM_CONTEXT},  # 同じプレフィックス → キャッシュヒット
            {"text": "次の質問です"}
        ]}
    ]
)

# キャッシュが効いているか確認
print(response_2.usage_metadata.cached_content_token_count)  # 0より大きければキャッシュヒット
```

## キャッシュヒットを確認する方法

暗黙キャッシュが実際に機能しているかを確認するには、レスポンスの `usage_metadata` を見る。

```python
import google.generativeai as genai

client = genai.Client(api_key="YOUR_API_KEY")

SYSTEM_CONTEXT = """
あなたは[ここに大きなシステム指示やドキュメント内容を入れる。
数万トークン規模のコンテンツが対象。
...]
"""

def ask_with_cache_check(question: str, session_id: str = "") -> dict:
    """質問を送信し、キャッシュ使用状況を返す"""
    response = client.models.generate_content(
        model="gemini-2.5-pro",
        contents=[
            {"role": "user", "parts": [
                {"text": SYSTEM_CONTEXT},
                {"text": question}
            ]}
        ]
    )
    
    usage = response.usage_metadata
    total_tokens = usage.total_token_count
    cached_tokens = usage.cached_content_token_count or 0
    prompt_tokens = usage.prompt_token_count or 0
    
    cache_ratio = (cached_tokens / prompt_tokens * 100) if prompt_tokens > 0 else 0
    
    return {
        "text": response.text,
        "total_tokens": total_tokens,
        "cached_tokens": cached_tokens,
        "prompt_tokens": prompt_tokens,
        "cache_ratio": f"{cache_ratio:.1f}%",
        "cache_hit": cached_tokens > 0
    }

# 1回目（キャッシュなし）
result_1 = ask_with_cache_check("このドキュメントの要点を教えてください")
print(f"1回目 - キャッシュ: {result_1['cached_tokens']} トークン ({result_1['cache_ratio']})")

# 2回目（キャッシュヒット期待）
result_2 = ask_with_cache_check("次に重要な箇所はどこですか？")
print(f"2回目 - キャッシュ: {result_2['cached_tokens']} トークン ({result_2['cache_ratio']})")

# 出力例（期待値）:
# 1回目 - キャッシュ: 0 トークン (0.0%)
# 2回目 - キャッシュ: 48320 トークン (94.3%)
```

`cached_content_token_count` が0より大きければ、暗黙キャッシュが機能している証拠だ。

## コスト計算：実際にどれだけ節約できるか

Gemini 2.5 Pro の料金体系（2026年4月時点）では、キャッシュ済みトークンは通常の入力トークン料金の **25%** で処理される。つまり最大75%のコスト削減になる。

具体的に計算してみよう。

- **ドキュメント分析チャットボットの例**
  - システムコンテキスト: 50,000トークン（100ページのPDF相当）
  - 1日のリクエスト数: 200回
  - 1リクエストあたりのユーザー質問: 平均100トークン

キャッシュなしの場合、1日のプロンプトトークン = (50,000 + 100) × 200 = **10,020,000トークン**

暗黙キャッシュが効いた場合（2回目以降は50,000トークンが25%の料金）:
- 1回目: 50,100トークン（通常料金）
- 2〜200回目: 100トークン（通常料金）+ 50,000トークン（25%料金）× 199回

実質的なコストは元の約**28%**程度まで削減できる計算になる。大規模なドキュメント分析システムでは、月間のAPI費用が数十万円削減されるケースも珍しくない。

## Implicit Caching が有効になる条件

暗黙キャッシュが機能するには、いくつかの条件がある。理解していないと「なぜキャッシュされないのか」でハマる。

**対応モデル**: Gemini 2.5 Pro（`gemini-2.5-pro`）と Gemini 2.5 Flash（`gemini-2.5-flash`）。Gemini 2.0 系や古いモデルでは無効。

**プレフィックスの一致**: コンテキストの「先頭部分」が完全に一致する必要がある。末尾のユーザー質問が変わっても、先頭の共通部分がキャッシュされる。

**最小トークン数の目安**: 公式には明記されていないが、実際の挙動から推測すると概ね1,000〜4,000トークン以上のプレフィックスが対象になりやすい。短すぎるプレフィックスではキャッシュが発動しない場合がある。

**リクエスト間隔**: キャッシュには有効期限がある（通常数分〜数十分）。間隔が空きすぎると再度フル料金が発生する。

```python
# ❌ キャッシュが効きにくいパターン：プレフィックスが毎回変わる
def bad_pattern(user_query: str, timestamp: str):
    # timestampが毎回変わるとプレフィックスが一致しない
    prompt = f"現在時刻: {timestamp}\n\n{LARGE_DOCUMENT}\n\n{user_query}"
    return client.models.generate_content(model="gemini-2.5-pro", contents=prompt)

# ✅ キャッシュが効くパターン：変動要素を末尾に配置
def good_pattern(user_query: str, timestamp: str):
    # 固定コンテキストを先頭にまとめる
    contents = [
        {"role": "user", "parts": [
            {"text": LARGE_DOCUMENT},  # 固定部分（先頭）
            {"text": f"現在時刻: {timestamp}\n質問: {user_query}"}  # 変動部分（末尾）
        ]}
    ]
    return client.models.generate_content(model="gemini-2.5-pro", contents=contents)
```

## 明示的キャッシュと暗黙キャッシュ：どちらを使うべきか

この判断は「コンテキストの再利用頻度」と「コンテキストのサイズ」によって変わる。

暗黙キャッシュが向いているのは以下のケースだ。コンテキストが1万〜10万トークン程度で、同一セッション内で複数の質問をするチャットボット。RAGシステムで同じ検索結果を連続して参照するケース。プロトタイプ段階でキャッシュの恩恵を試したいとき。

明示的キャッシュが向いているのはこういうケースだ。10万トークン以上の非常に大きなドキュメントを長期間（数時間〜数日）再利用するとき。TTLを自分でコントロールしてキャッシュコスト自体を最適化したいとき。複数ユーザーが同じコンテキストを共有するサービス（プロンプトテンプレートの共有など）。

実際の運用では、両者を組み合わせる戦略が有効なことも多い。

## マルチターン会話での活用パターン

チャットボットで暗黙キャッシュを最大限に活用するには、会話履歴の扱い方が重要になる。

```python
class CachedChatSession:
    """暗黙キャッシュを最大活用するチャットセッション管理"""
    
    def __init__(self, system_context: str):
        self.client = genai.Client(api_key="YOUR_API_KEY")
        self.model = "gemini-2.5-pro"
        self.system_context = system_context  # 大きな固定コンテキスト
        self.conversation_history = []
        self.total_cached_tokens = 0
        self.total_prompt_tokens = 0
    
    def chat(self, user_message: str) -> str:
        # 固定コンテキストを先頭に置き、会話履歴をその後に続ける
        # これにより system_context 部分がキャッシュされやすくなる
        contents = [
            {
                "role": "user",
                "parts": [{"text": self.system_context}]  # 固定プレフィックス
            },
            {
                "role": "model", 
                "parts": [{"text": "承知しました。ご質問をどうぞ。"}]
            }
        ]
        
        # 会話履歴を追加（固定プレフィックスの後）
        contents.extend(self.conversation_history)
        
        # 今回のユーザーメッセージを追加
        contents.append({
            "role": "user",
            "parts": [{"text": user_message}]
        })
        
        response = self.client.models.generate_content(
            model=self.model,
            contents=contents
        )
        
        # キャッシュ統計を更新
        usage = response.usage_metadata
        cached = usage.cached_content_token_count or 0
        prompt = usage.prompt_token_count or 0
        self.total_cached_tokens += cached
        self.total_prompt_tokens += prompt
        
        # 会話履歴に追加
        self.conversation_history.append({
            "role": "user",
            "parts": [{"text": user_message}]
        })
        self.conversation_history.append({
            "role": "model",
            "parts": [{"text": response.text}]
        })
        
        return response.text
    
    def get_cache_stats(self) -> dict:
        ratio = (self.total_cached_tokens / self.total_prompt_tokens * 100) \
            if self.total_prompt_tokens > 0 else 0
        return {
            "total_cached_tokens": self.total_cached_tokens,
            "total_prompt_tokens": self.total_prompt_tokens,
            "cache_ratio": f"{ratio:.1f}%",
            "estimated_savings": f"約{ratio * 0.75:.1f}% のコスト削減"
        }


# 使用例
LARGE_SYSTEM_CONTEXT = """
[50,000トークン規模のシステム指示・ドキュメント内容]
"""

session = CachedChatSession(LARGE_SYSTEM_CONTEXT)

reply1 = session.chat("第1章の要点を教えてください")
reply2 = session.chat("第2章との関係は？")
reply3 = session.chat("実装する際の注意点は？")

stats = session.get_cache_stats()
print(stats)
# 出力例: {'total_cached_tokens': 96480, 'total_prompt_tokens': 102300,
#           'cache_ratio': '94.3%', 'estimated_savings': '約70.7% のコスト削減'}
```

## よくある疑問と注意点

**暗黙キャッシュは無効化できるか？**

API パラメータとして無効化オプションは提供されていない（2026年4月時点）。キャッシュはサーバー側で透過的に処理され、開発者が制御する手段はない。コスト計算を正確に行うためにも、`usage_metadata` で実際のキャッシュ状況を常に確認することを習慣にしよう。

**コンテキストを少し変えてもキャッシュは効くか？**

プレフィックスが完全一致しないとキャッシュは無効だ。例えばシステムプロンプトの1文字を変更しただけで、その変更以降の全トークンが再計算される。「動的に生成するシステムプロンプト」は暗黙キャッシュと相性が悪い。テンプレート変数は末尾または別の `contents` エントリに分離するのがベストプラクティスだ。

**Vertex AI でも使えるか？**

Vertex AI 経由の Gemini API でも同様の暗黙キャッシュが適用される。ただし Vertex AI では明示的キャッシュのコントロールが細かくできる分、暗黙キャッシュとの組み合わせ設計は若干複雑になる。コスト最適化を徹底したい場合は Vertex AI の Explict Cache に移行することも検討する価値がある。

## まとめ：まず `cached_content_token_count` を計測することから始めよう

Implicit Caching の最大のメリットは「ゼロコスト導入」だ。既存のコードを変えず、ただ `usage_metadata.cached_content_token_count` をログに記録するだけで現状を把握できる。

キャッシュヒット率が低ければ、プレフィックスの設計を見直す（変動要素を末尾に移動する）。大規模かつ長期再利用なら明示的キャッシュへの移行を検討する。この2ステップで、多くのケースで月間API費用を大幅に削減できる。

「毎回フルに送っているのに速くなっている気がする」という経験がある人は、すでに暗黙キャッシュの恩恵を受けているかもしれない。ぜひ `usage_metadata` を確認して、実際のキャッシュ効果を数値で把握してほしい。
