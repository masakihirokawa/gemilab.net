Gemini に写真を渡して、「ここから必要なフィールドだけ JSON で抜き出して」と頼むと、最初の数枚は気持ちいいほど綺麗に動きます。自分で綺麗に撮ったサンプル画像だからです。ところが、いざユーザーがアプリの中で撮った写真を流し始めると、斜めに撮られ、暗く、指が写り込み、別の紙が重なっている、といった現実の写真が混ざってきます。精度は一気に下がり、JSON は欠けたり、余計なフィールドが混じったり、型が壊れたりします。

Gemini API を使って「現実の写真から構造化データを取り出す」機能を本番運用するときに、何が落ちるのか、どこで潰すのか、を実例とともに整理しました。私自身が個人開発で運用しているアプリのコードと設計を、具体例としてそのまま書きます。完璧を目指す内容ではなく、99% 動く状態を作ったうえで、残り 1% を正直に割り切るための記事です。

## 本番で落ちる写真を 5 種類に分けて見る

まず、失敗写真をひとまとまりで扱うのをやめます。私は次の 5 種類に分けて、それぞれ別の戦略で対処しています。

1. 幾何学的歪み（斜め撮影、台形歪み、回転）
2. 光学的ノイズ（影、反射、極端な露光）
3. 部分隠れ（指、他の紙、モノの陰）
4. テキストの品質（低解像度、手書き、かすれ、汚れ）
5. 期待と違う被写体（そもそも目的の書類が写っていない）

この 5 つは、どのレイヤーで対処すべきかが異なります。1 は前処理（画像処理）で、2 も前処理寄り、3 はプロンプトと検証で、4 は Gemini の処理能力を信じつつ検証層で救う、5 はそもそも早期に弾く、という配分です。雑に「モデルの精度が足りない」と結論付けるのではなく、どの種類の崩れが起きているかを分類して初めて、正しい手段が選べます。

## レイヤー 1: クライアント側の前処理で幾何と光学を整える

Gemini に渡す前に、クライアント側（アプリまたは最初のバックエンド）で 3 つの処理を入れます。これで失敗の半分くらいは消えます。

### 処理 A: 自動トリミングと台形補正

スマホで撮った書類は、たいてい斜めに写っています。OpenCV の輪郭検出で紙のエッジを見つけ、4 点を決めて透視変換で正対させる、という定番処理を入れます。Python 側で実装するなら次のような流れです。

```python
import cv2
import numpy as np

def deskew_document(image_bytes: bytes) -> bytes:
    arr = np.frombuffer(image_bytes, np.uint8)
    img = cv2.imdecode(arr, cv2.IMREAD_COLOR)
    gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
    edges = cv2.Canny(gray, 50, 150)
    contours, _ = cv2.findContours(
        edges, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE
    )
    if not contours:
        return image_bytes

    largest = max(contours, key=cv2.contourArea)
    peri = cv2.arcLength(largest, True)
    approx = cv2.approxPolyDP(largest, 0.02 * peri, True)
    if len(approx) != 4:
        return image_bytes

    pts = np.array([p[0] for p in approx], dtype="float32")
    # 4 点を順序付けして透視変換（順序付け関数は省略）
    warped = four_point_transform(img, pts)
    ok, buf = cv2.imencode(".jpg", warped, [cv2.IMWRITE_JPEG_QUALITY, 90])
    return buf.tobytes() if ok else image_bytes
```

エッジが 4 点にならない写真（紙の端が写っていないなど）は、黙って元画像を返すのが大切です。強引に処理すると、逆に歪みが増えます。

### 処理 B: 明るさとコントラストのノーマライズ

影が強い、極端に暗いといった写真は、ヒストグラム均等化や CLAHE でコントラストを上げると Gemini が文字を拾いやすくなります。やりすぎるとノイズが乗るので、輝度分散が一定以下の写真だけ補正を適用する、というガードを入れます。

### 処理 C: 解像度の揃え

解像度が極端に低い写真（長辺 500px 未満）は、そもそも手を打っても情報量が足りません。この段階で「解像度が足りないので撮り直してください」とユーザーに返すのが、コストも品質も最適です。長辺 2000 〜 3000px 程度に揃えて送ると、Gemini のトークン消費とレイテンシのバランスが良いです。

## レイヤー 2: プロンプトで「抽出の契約」を明示する

前処理で整えた画像を Gemini に渡すプロンプトは、構造を持たせて書きます。私は次の 4 要素を必ず入れます。

1. このタスクが何であるか（「レシート画像から構造化データを抽出する」）
2. 期待するフィールドのリストと型、必須 / 任意の区別
3. 各フィールドの「現実的な制約」（金額は円建て、日付は YYYY-MM-DD、等）
4. 情報が見えないときの振る舞い（「推測せず null」と明示）

最後の 4 が重要です。指示しないと、Gemini は読めなかったフィールドに対して、それらしい値を「補完」してきます。推測されたデータが本番で金額計算に入り込むと、静かに壊れる系のバグになります。明示的に「見えない → null、かつ `confidence` フィールドで低い値を返す」というルールを書いておきます。

```text
画像はレシートの写真です。以下のスキーマに従って JSON を返してください。

スキーマ:
{
  "merchant": { "value": string | null, "confidence": 0-1 },
  "total_amount": { "value": integer | null, "confidence": 0-1 },
  "purchased_at": { "value": "YYYY-MM-DD" | null, "confidence": 0-1 },
  "items": [
    { "name": string, "price": integer, "confidence": 0-1 }
  ],
  "rejection_reason": string | null
}

ルール:
- 画像から読み取れないフィールドは value を null にし、confidence を 0.3 未満にすること
- 推測での補完は禁止
- 画像がそもそもレシートではない場合は、全フィールド null、rejection_reason に理由を書くこと
- 金額はすべて円の整数で返すこと
```

`confidence` フィールドを返させるのは、後段の検証層で使うためです。Gemini の自己申告する信頼度は完全ではありませんが、「低い値と言ったフィールドは実際に怪しい」という相関は強く、検証の優先順位付けに役立ちます。

## レイヤー 3: スキーマ検証とビジネスルール検証を挟む

Gemini の返す JSON は、モデル側の `response_schema` を使って型を強制します。Gemini 2.5 以降では `response_schema` に JSON Schema を渡せるので、これだけで型崩れの大半は防げます。しかし、型が合っていても値がおかしいケースは残ります。

私は戻ってきた JSON に対して、ビジネスルール層の検証を必ず挟みます。例えば次のような規則です。

- `total_amount` が `sum(items[].price)` と ±10% 以上ずれていたら警告
- `purchased_at` が未来の日付だったら reject
- `merchant` と `items[].name` に、明らかに意味のない文字列（`aaaa`、記号だけなど）が入っていたら reject
- 全フィールドの `confidence` 平均が 0.5 未満なら「読み取り不能」として扱う

この検証層を通ったデータだけが本番データベースに入ります。通らなかったデータは、後ほど人間が見る仕分けキューに送るか、ユーザーに撮り直しを促します。

## レイヤー 4: 本当に難しい 1 〜 2% を「却下する」設計

どれだけ前処理・プロンプト・検証を重ねても、最後まで残る「どうしても読めない」写真が 1 〜 2% は残ります。ここで精度 100% を目指すと、モデルを変える、独自 OCR を混ぜる、人間の目視を入れる、など急にコストが上がります。私は早い段階で「読めない写真は正直に却下する」設計に倒しました。

ユーザー側の UX としては、次の 3 点を守ります。

1. 却下を「失敗」ではなく「撮り直しが必要」と表現する
2. 却下理由を簡潔に伝える（「影が強すぎる」「文字の解像度が足りない」など）
3. 何度却下されても心が折れない導線を用意する（例: 「手動で入力する」選択肢を並列に置く）

ここを丁寧にやると、ユーザーのアプリ体験全体は落ちません。読めない写真を無理に読んで間違った値を返すほうが、却下するよりよほど重い事故につながります。

## コストとレイテンシの設計

最後に実務的な話をします。Gemini Flash と Gemini Pro を使い分けてコストを押さえる運用をしています。大枠は次のとおりです。

- 初回抽出は Flash で実行。必要なフィールドだけ要求して、トークンを絞る。
- `confidence` の平均が閾値未満だった場合だけ Pro で再試行。2 回目で良くなるケースが一定あるが、3 回目以降は収束しないので打ち止める。
- 画像のリサイズは前処理で 2000px 程度に落としておく。Gemini は大きすぎる画像を与えてもトークン以上の価値を返さない。

この段階的アプローチで、全体のコストをシングル呼び出しより約 30% 抑えつつ、精度は上げられました。本番運用では精度とコストは表裏で、どちらかを固定して考えると詰まるので、両方を同じダッシュボードで見る癖を付けるのをお勧めします。

## 明日から試せる最初の一歩

大きく組み替えなくても、最初の効果を出すなら次の 2 つだけで十分です。

1. プロンプトに「見えないフィールドは null、推測禁止」を明示して `confidence` を返させる
2. 戻ってきた JSON の平均 confidence が 0.5 未満なら「撮り直し」に倒す

これだけで、ユーザーの見える品質がかなり変わります。クライアント前処理や Pro へのフォールバックは、運用の数字を見ながら段階的に足していけば良いと思います。完璧なパイプラインを最初から組むより、悪い写真を正直に却下できる状態まで最短で到達するほうが、個人開発では結果として強いです。
