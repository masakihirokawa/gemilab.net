## Gemini API の料金体系

Gemini API の費用は以下の3つの要素で決まります：

### モデル別の価格（2026年4月時点）

- **Flash**: ¥0.075 / 100万入力トークン、¥0.3 / 100万出力トークン（最速・最安）
- **Pro**: ¥0.15 / 100万入力トークン、¥0.6 / 100万出力トークン（バランス型）
- **Ultra**: ¥1.5 / 100万入力トークン、¥4.5 / 100万出力トークン（最高精度、高価）

### キャッシュによる割引

- **Context Cache**: 入力トークン 50% 割引（キャッシュ化の1時間以内に使用）
- **Response Cache**: 同一入力への応答を キャッシュ、60秒以内の再利用で入力トークン 100% 割引

### 具体的なコスト比較

100万トークンの入力で月10回処理する場合：

- **キャッシュなし**: ¥1.5 × 10回 = ¥15
- **Context Cache 利用**: ¥1.5 × 1回 + ¥0.75 × 9回 = ¥8.25（45% 削減）
- **Response Cache 利用**: ¥0（100% 削減、同一入力の場合のみ）

つまり、キャッシュを上手く活用すれば、 **同じ機能で費用を 10分の1 以下** にできます。

## コスト最適化の5つの柱

1. **Context Caching** — 長い文脈（ドキュメント、ナレッジベース）を再利用

## 柱①：Context Caching の完全活用

Context Cache は、長い文脈を Gemini に一度送信し、**その後の複数リクエストで再利用** する機能です。

### ユースケース

- 長編ドキュメント（マニュアル、論文、小説）の要約や質問応答
- 会社の規則集・ポリシー集から情報検索
- コードベース全体のレビュー（ソースコード数千行）
- 医学論文データベースの検索

**キャッシュなし**:
- 1日あたり：¥0.15 × 100万トークン × 100人 = ¥15,000

**Context Cache 使用**:

## 柱②：モデルの自動使い分け

Gemini API には3つのモデルがあり、**タスクの複雑度に応じて自動切り替え** することで、コストを40〜60% 削減できます。

### モデル選択の判断基準

- **Flash**: 質問応答、テキスト生成、雑談（推奨利用率：70%）
- **Pro**: 複雑な推論、コード生成、複数ステップの分析（推奨利用率：20%）
- **Ultra**: 最高品質が必須な場合のみ（推奨利用率：10%以下）

### 実装コード：複雑度に応じた自動ルーティング

```python
import anthropic
import json

client = anthropic.Anthropic(api_key="YOUR_GEMINI_API_KEY")

def detect_query_complexity(user_query: str) -> str:
    """ユーザーの質問の複雑度を判定し、モデルを選択"""

    # 複雑度の判定基準（シンプル実装）
    keywords_simple = ["天気", "日付", "簡単", "何？"]
    keywords_complex = ["理由", "分析", "比較", "複雑"]
    keywords_ultra = ["論文要約", "法的分析", "医学判断"]

    query_lower = user_query.lower()

    if any(kw in query_lower for kw in keywords_ultra):
        return "gemini-2.0-pro-exp"  # Ultra（最高精度）
    elif any(kw in query_lower for kw in keywords_complex):
        return "gemini-2.0-pro"  # Pro（バランス型）
    else:
        return "gemini-2.0-flash"  # Flash（最速・最安）

def query_with_auto_routing(user_query: str):
    """自動ルーティングで最適なモデルを選択"""

    selected_model = detect_query_complexity(user_query)

    response = client.messages.create(
        model=selected_model,
        max_tokens=1000,
        messages=[
            {
                "role": "user",
                "content": user_query
            }
        ]
    )

    # 費用計算
    model_prices = {
        "gemini-2.0-flash": {"input": 0.000075, "output": 0.0003},
        "gemini-2.0-pro": {"input": 0.00015, "output": 0.0006},
        "gemini-2.0-pro-exp": {"input": 0.0015, "output": 0.0045}
    }

    prices = model_prices[selected_model]
    cost = (response.usage.input_tokens * prices["input"]) + (response.usage.output_tokens * prices["output"])

    return {
        "model": selected_model,
        "response": response.content[0].text,
        "cost": cost,
        "input_tokens": response.usage.input_tokens,
        "output_tokens": response.usage.output_tokens
    }

# テスト
queries = [
    "今日の天気を教えてください",
    "GPTとGeminiの複数条件での比較分析をしてください",
    "医学論文から主要な知見を抽出してください"
]

total_cost = 0
for query in queries:
    result = query_with_auto_routing(query)
    print(f"質問: {query}")
    print(f"選択モデル: {result['model']}")
    print(f"入力トークン: {result['input_tokens']}, 出力トークン: {result['output_tokens']}")
    print(f"このリクエストの費用: ¥{result['cost']:.4f}\n")
    total_cost += result['cost']

print(f"合計費用: ¥{total_cost:.4f}")
```

このアプローチでは、シンプルな質問は Flash で即座に処理（0.3円程度）し、複雑な分析だけ Pro や Ultra を使うため、 **平均コストを40% 削減** できます。

## 柱③：バッチ処理による費用削減

バッチ API は、リアルタイム性が不要な処理に対して **50% の割引** を提供します。

### ユースケース

- 毎日の営業レポート要約（100件）
- 顧客からのメール回答（非同期）
- ログファイルの異常検知（夜間バッチ）
- 定期的なデータ分析（週1回）

### 実装例：バッチ処理の構築

```python
import anthropic
import json
import time

client = anthropic.Anthropic(api_key="YOUR_GEMINI_API_KEY")

def create_batch_jobs(queries: list[str]):
    """複数のクエリをバッチ化し、API に送信"""

    requests = []
    for idx, query in enumerate(queries):
        requests.append({
            "custom_id": f"query-{idx}",
            "params": {
                "model": "gemini-2.0-flash",
                "messages": [
                    {
                        "role": "user",
                        "content": query
                    }
                ],
                "max_tokens": 1000
            }
        })

    # バッチ API に投入
    batch = client.beta.batch.submit(requests)

    print(f"バッチジョブ ID: {batch.id}")
    print(f"処理予定数: {len(requests)}")
    print(f"割引: 50% (通常の半額で実行)\n")

    return batch.id

def poll_batch_status(batch_id: str):
    """バッチ処理の完了を待機"""

    while True:
        batch = client.beta.batch.retrieve(batch_id)
        print(f"ステータス: {batch.status}")
        print(f"完了: {batch.request_counts.completed}, 処理中: {batch.request_counts.processing}\n")

        if batch.status == "completed":
            return batch

        time.sleep(10)  # 10秒ごとにポーリング

def retrieve_batch_results(batch_id: str):
    """バッチ処理の結果を取得"""

    batch = client.beta.batch.retrieve(batch_id)

    if batch.status != "completed":
        print(f"バッチ未完了: {batch.status}")
        return

    # 結果の取得
    results = client.beta.batch.results(batch_id)

    for result in results:
        print(f"ID: {result.custom_id}")
        print(f"回答: {result.result.message.content[0].text}")
        print(f"トークン: 入力 {result.result.usage.input_tokens}, 出力 {result.result.usage.output_tokens}\n")

# 実行例
queries = [
    "Gemini APIの主な特徴を箇条書きで",
    "クラウド API の最高の実装例を教えて",
    "AIコストを50%削減するテクニックは？"
]

# バッチ投入
batch_id = create_batch_jobs(queries)

# 完了まで待機
batch = poll_batch_status(batch_id)

# 結果取得
retrieve_batch_results(batch_id)
```

**コスト削減の実感**

100件のメール回答を処理する場合：

- **リアルタイム処理**: ¥15,000
- **バッチ処理**: ¥7,500（50% 削減）

月1回であれば ¥7,500、週1回であれば月 ¥30,000 削減できます。

## 柱④：トークン使用量の最適化

同じ機能でも、 **入力トークンの削減** で大幅にコストを下げられます。

### テクニック 1: System Instruction の短縮化

```python
# 非効率な System Instruction（長い）
system_instruction_long = """
あなたはカスタマーサービス代理人です。
顧客からのメールに対して、以下のルールに従って回答してください:
1. 敬語を使う
2. 問題を明確に理解する
3. 解決策を提案する
4. フォローアップの予定を提示する
...(以下100行)
"""

# 効率的な System Instruction（短い、実質同じ機能）
system_instruction_short = """
カスタマーサービス代理人: 顧客メールに敬語で返信。
問題理解 → 解決策 → フォローアップ日程の順で記述。
"""

# 両者のトークン数を比較
def estimate_tokens(text: str) -> int:
    """テキストの概算トークン数（1語≈4文字が目安）"""
    return len(text) // 4

long_tokens = estimate_tokens(system_instruction_long)
short_tokens = estimate_tokens(system_instruction_short)

print(f"長いバージョン: {long_tokens} トークン (¥{long_tokens * 0.00015:.4f})")
print(f"短いバージョン: {short_tokens} トークン (¥{short_tokens * 0.00015:.4f})")
print(f"削減: {((long_tokens - short_tokens) / long_tokens) * 100:.1f}%")
```

実際には、短い指示の方が AI の応答も高速になり、出力トークンも削減される傾向があります。

## 柱⑤：トークン使用量の可視化ダッシュボード構築

月額費用を **見える化** することで、チーム全体で意識が高まり、自然と最適化が進みます。

### Python ダッシュボード実装（Plotly 使用）

```python
import os
import json
from datetime import datetime, timedelta
from typing import list, dict
import anthropic
import plotly.graph_objects as go
from plotly.subplots import make_subplots

# Gemini API 呼び出しログを記録（本番では DB に保存）
api_call_log = []

client = anthropic.Anthropic(api_key="YOUR_GEMINI_API_KEY")

def log_api_call(model: str, input_tokens: int, output_tokens: int, cache_tokens: int = 0):
    """API 呼び出しを記録"""
    api_call_log.append({
        "timestamp": datetime.now().isoformat(),
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "cache_tokens": cache_tokens
    })

def calculate_cost(model: str, input_tokens: int, output_tokens: int, cache_tokens: int) -> float:
    """モデル別の費用を計算"""
    prices = {
        "gemini-2.0-flash": {"input": 0.000075, "output": 0.0003, "cache": 0.0000375},
        "gemini-2.0-pro": {"input": 0.00015, "output": 0.0006, "cache": 0.000075},
        "gemini-2.0-pro-exp": {"input": 0.0015, "output": 0.0045, "cache": 0.00075}
    }

    if model not in prices:
        model = "gemini-2.0-flash"

    price = prices[model]
    return (input_tokens * price["input"]) + (output_tokens * price["output"]) + (cache_tokens * price["cache"])

def create_cost_dashboard():
    """Plotly でコスト可視化ダッシュボードを生成"""

    # ダミーデータを生成（実際には DB から読み込む）
    models = ["gemini-2.0-flash", "gemini-2.0-pro", "gemini-2.0-pro-exp"]
    daily_costs = {}
    daily_models = {}

    for day in range(30):
        date = (datetime.now() - timedelta(days=day)).date()
        daily_costs[str(date)] = {m: 0 for m in models}
        daily_models[str(date)] = {m: 0 for m in models}

    # 各モデルの利用状況をシミュレート
    for log in api_call_log:
        date = log["timestamp"][:10]
        model = log["model"]
        cost = calculate_cost(model, log["input_tokens"], log["output_tokens"], log["cache_tokens"])

        if date in daily_costs:
            daily_costs[date][model] += cost
            daily_models[date][model] += 1

    # サブプロット作成
    fig = make_subplots(
        rows=2, cols=2,
        subplot_titles=("Daily Cost by Model", "Model Usage Count", "Cost Trend", "Cache Hit Rate")
    )

    # グラフ 1: 日別コスト（モデル別）
    dates = sorted(daily_costs.keys())
    for model in models:
        costs = [daily_costs[d][model] for d in dates]
        fig.add_trace(
            go.Scatter(x=dates, y=costs, name=model.replace("gemini-2.0-", ""), mode='lines+markers'),
            row=1, col=1
        )

    # グラフ 2: モデル別利用数
    model_totals = {m: sum(daily_models[d][m] for d in daily_models) for m in models}
    fig.add_trace(
        go.Bar(
            x=[m.replace("gemini-2.0-", "") for m in models],
            y=list(model_totals.values()),
            marker_color=['rgb(26, 118, 255)', 'rgb(50, 171, 96)', 'rgb(255, 0, 0)']
        ),
        row=1, col=2
    )

    # グラフ 3: コスト累積グラフ
    cumulative_cost = 0
    cumulative_costs = []
    for date in dates:
        day_cost = sum(daily_costs[date].values())
        cumulative_cost += day_cost
        cumulative_costs.append(cumulative_cost)

    fig.add_trace(
        go.Scatter(x=dates, y=cumulative_costs, name="Cumulative Cost", mode='lines', fill='tozeroy'),
```

## よくある落とし穴と対策

### 落とし穴 1: キャッシュが効かないケース

**問題**: Context Cache を導入したが、キャッシュヒット率が 10% 以下

**原因**: キャッシュ有効期間（1時間）より、クエリ間隔が長い

**対策**: 同じテンプレートに対するクエリを **バッチ処理化** し、1時間以内に複数回処理する

### 落とし穴 2: モデル切り替えによる品質劣化

**問題**: Flash に切り替えたら、出力品質が低下

**原因**: Flash の入力コンテキストで、重要な指示が欠落している

**対策**: System Instruction を **短くするのではなく、構造化** する。重要な指示は JSON で渡す。

### 落とし穴 3: バッチ処理の遅延問題

**問題**: バッチ API の処理時間が 1〜2時間掛かり、ユーザーが待たされる

**原因**: バッチ API は非同期処理（リアルタイムが保証されない）

**対策**: リアルタイムが必須な処理（チャット、API レスポンス）はリアルタイム API を使い、レポート生成などの非同期処理だけバッチ化

## FAQ

**Q1: Vertex AI との費用比較は？**

A: Vertex AI（Google Cloud の Gemini）は Gemini API より **2倍安い** ですが、セットアップが複雑です。個人開発者や小規模プロジェクトなら Gemini API、エンタープライズなら Vertex AI を選択するのが目安です。

**Q2: Context Caching と Prompt Caching の違いは？**

A: Context Caching は Gemini API の機能。Prompt Caching は Claude API の機能。概念は同じ（長い文脈を再利用）ですが、API 仕様が異なります。

**Q3: モデルの自動切り替えでユーザー体験は低下しないか？**

A: Flash の品質は Pro に遜色ありません。むしろ、不要に複雑な指示を使わない分、Flash の方が高速になります。体感品質は変わりません。

**Q4: キャッシュを活用できない業務は？**

A: リアルタイムチャット、ユーザーごとに異なるコンテキスト、毎回異なる入力（例：メール返信）。これらはキャッシュが効きません。
