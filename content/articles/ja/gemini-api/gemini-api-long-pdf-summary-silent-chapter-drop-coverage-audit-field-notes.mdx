先日、480 ページの技術仕様書を章ごとに要約させ、その要約だけを根拠に「この製品は上限まわりの制約が緩い」と判断しかけました。実際にはページ番号でいう真ん中あたりに、制限事項をまとめた一章がまるごと存在していました。要約にはその章の名残がどこにもありません。パイプラインはエラーひとつ吐かず、最後まで完走していました。

個人開発でアプリや資料を一人で回していると、長尺のドキュメントを機械にまとめさせたい場面は毎週のように訪れます。章ごと要約 → 全体再結合というパターン自体は、長尺 PDF に対してよく効きます。ただ「章に分けて並列で要約する」という構造そのものが、一章が静かに欠けても気づけない盲点を抱えています。ここでは、その取りこぼしを被覆率という一つの数字で捕まえ、消えた章だけを自動で再実行する監査つきパイプラインを、実装とあわせて整理します。

## 要約は、章が消えても素知らぬ顔で完走する

一括要約が「後半が薄くなる」形で崩れるのに対し、章分割方式の崩れ方はもっと厄介です。章を集合として扱うため、集合から要素がひとつ抜けても、残りの要素だけで文章としては綺麗に仕上がってしまいます。読み手には欠落が見えません。

私が観測した「章が消える」経路は、大きく三つに分かれます。

<table>
<thead>
<tr><th>経路</th><th>何が起きているか</th><th>典型的な症状</th></tr>
</thead>
<tbody>
<tr><td>アウトライン欠落</td><td>PDF のしおりに一部の章が登録されておらず、章リストにそもそも入らない</td><td>章数が目次より少ない。前後の章に本文が吸収される</td></tr>
<tr><td>空テキスト</td><td>該当ページが画像スキャンで <code>extract_text()</code> が空文字を返す</td><td>本文ゼロの章が「付録には各種情報が記載されています」の一行に化ける</td></tr>
<tr><td>再結合での溶解</td><td>全体再結合の段で、要点の薄い章がモデルに切り捨てられる</td><td>章要約には残っているのに、最終要約から章の主張が消える</td></tr>
</tbody>
</table>

いずれもモデルの能力の問題ではなく、パイプラインの構造上の問題です。だからこそ、モデルを賢くしても直りません。直すべきは「全部の章が最終成果物に届いているか」を測って、届いていない章を名指しする仕組みのほうです。

## 被覆率という一つの数字を置く

複雑な品質指標を並べる前に、まず一つだけ数字を決めます。ソースの章のうち、最終要約に主張が反映されている章の割合。これを被覆率と呼びます。

<table>
<thead>
<tr><th>記号</th><th>定義</th></tr>
</thead>
<tbody>
<tr><td>S</td><td>ソース PDF から抽出した章の集合（本文が空でないもの）</td></tr>
<tr><td>R</td><td>最終要約に主張が反映されていると判定できた章の集合（R ⊆ S）</td></tr>
<tr><td>被覆率</td><td>|R| / |S|。1.0 が全章反映</td></tr>
</tbody>
</table>

被覆率が 1.0 を割った瞬間、どこかの章が最終成果物に届いていません。大事なのは、この数字を「良し悪しの総合評価」にしないことです。被覆率はあくまで取りこぼしの検知器であり、要約の質そのものは別に測ります。一つの数字に多くを背負わせると、閾値の意味が曖昧になって運用で形骸化します。

あわせて、抽出段でのもう一つの安全網として、章ごとの本文長も見ておきます。本文が極端に短い章（たとえば全体中央値の一割未満）は、空テキスト経路の候補として警告に回します。要約に入る前に、そもそも入力が壊れていないかを弾く関門です。

## 監査つきパイプラインを実装する

以下は、章を抽出して並列要約し、最後に被覆率を計測して閾値割れの章だけ再実行する最小構成です。本要約には推論の強いモデルを、検証パスには軽量モデルと埋め込みを割り当て、監査のコストを抑えます。

処理は三段に分かれます。

1. 章を抽出し、本文の薄い章に印をつける
2. 章ごとに並列で要約する（同時実行は4並列に絞る）
3. 被覆率を測り、落ちた章だけを再結合する

素朴な一括要約に比べ、章分割はリクエスト数が10倍以上に膨らみます。だからこそ検証パスは安く済ませたく、本番運用では私はこの非対称な構成を推奨します。

```python
# pip install google-genai pypdf numpy
# 環境変数: GOOGLE_API_KEY="YOUR_API_KEY"
import asyncio
import os
import statistics
from dataclasses import dataclass, field
import numpy as np
from pypdf import PdfReader
from google import genai

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])
SUMMARY_MODEL = "gemini-2.5-pro"       # 章要約・全体再結合
VERIFY_MODEL = "gemini-flash-latest"   # 被覆判定（安く速く）
EMBED_MODEL = "gemini-embedding-2"     # 章⇄要約の意味的近さ

@dataclass
class Chapter:
    idx: int
    title: str
    body: str
    summary: str = ""
    covered: bool = False
    notes: list[str] = field(default_factory=list)

def extract_chapters(pdf_path: str) -> list[Chapter]:
    reader = PdfReader(pdf_path)
    top = [o for o in reader.outline if not isinstance(o, list)]
    chapters: list[Chapter] = []
    for i, entry in enumerate(top):
        start = reader.get_destination_page_number(entry)
        end = (reader.get_destination_page_number(top[i + 1])
               if i + 1 < len(top) else len(reader.pages))
        body = "\n".join(reader.pages[p].extract_text() or "" for p in range(start, end))
        chapters.append(Chapter(idx=i, title=entry.title, body=body))
    return chapters

def flag_thin_chapters(chapters: list[Chapter]) -> None:
    """空テキスト経路を入力段で弾く"""
    lengths = [len(c.body) for c in chapters if c.body.strip()]
    if not lengths:
        return
    floor = statistics.median(lengths) * 0.1
    for c in chapters:
        if len(c.body.strip()) < floor:
            c.notes.append(f"本文が短すぎます（{len(c.body.strip())}字）。抽出漏れの疑い")
```

抽出の時点で `flag_thin_chapters` を通し、本文が薄い章に印をつけておきます。ここで弾いておかないと、空の本文がそのまま要約に流れ、後段で「消えたのか、もともと中身が無いのか」の区別がつかなくなります。

次に、章要約と全体再結合、そして被覆判定です。再結合では章の通し番号を明示的に持たせ、最終要約に「どの章に触れたか」を機械的に照合できる形を作ります。

```python
async def summarize_chapter(ch: Chapter) -> None:
    prompt = (
        f"次は技術文書の第{ch.idx}章『{ch.title}』の本文です。\n"
        "主張を3〜5項目でまとめてください。他章への参照は避けてください。\n\n"
        f"本文:\n{ch.body[:120000]}"
    )
    resp = await asyncio.to_thread(
        client.models.generate_content, model=SUMMARY_MODEL, contents=prompt)
    ch.summary = resp.text.strip()

async def merge_summaries(chapters: list[Chapter]) -> str:
    joined = "\n\n".join(f"[章{c.idx}] {c.title}\n{c.summary}" for c in chapters)
    prompt = (
        "以下は文書を章ごとに要約したものです。全体の主張を400字でまとめ、\n"
        "本文の最後に、言及した章を [章0, 章3, ...] の形式で必ず列挙してください。\n\n"
        f"{joined}"
    )
    resp = await asyncio.to_thread(
        client.models.generate_content, model=SUMMARY_MODEL, contents=prompt)
    return resp.text.strip()

def embed(texts: list[str]) -> np.ndarray:
    resp = client.models.embed_content(model=EMBED_MODEL, contents=texts)
    return np.array([e.values for e in resp.embeddings])

def audit_coverage(chapters: list[Chapter], final: str, threshold: float = 0.62) -> float:
    """章要約と最終要約の意味的近さで被覆を判定する"""
    live = [c for c in chapters if c.summary]
    vecs = embed([c.summary for c in live] + [final])
    final_vec = vecs[-1]
    for c, v in zip(live, vecs[:-1]):
        sim = float(v @ final_vec / (np.linalg.norm(v) * np.linalg.norm(final_vec)))
        c.covered = sim >= threshold
        if not c.covered:
            c.notes.append(f"最終要約への反映が弱い（類似度{sim:.2f}）")
    covered = sum(c.covered for c in live)
    return covered / len(live) if live else 0.0
```

被覆判定に埋め込みを使うのは、生成モデルに「この章は含まれていますか」と問い直すよりも安く、判定が安定するためです。類似度の閾値 0.62 は保守的な初期値で、実データで数本流して分布を見ながら調整します。文書のジャンルによって最適値は動くので、固定値を信じ切らないのが肝心です。

## 消えた章だけを、名指しで再実行する

被覆率が 1.0 を割ったら、全体をやり直すのではなく、被覆されなかった章だけを対象に再結合をもう一度回します。ここが監査を入れる旨味です。全再実行はコストも待ち時間も跳ね上がりますが、落ちた一章を拾い直すだけなら安く済みます。

```python
async def summarize_pdf(pdf_path: str, max_retries: int = 2) -> dict:
    chapters = extract_chapters(pdf_path)
    flag_thin_chapters(chapters)
    sem = asyncio.Semaphore(4)  # 無料枠の429を避ける保守的な同時実行数

    async def bounded(c: Chapter):
        async with sem:
            await summarize_chapter(c)

    await asyncio.gather(*(bounded(c) for c in chapters if c.body.strip()))

    final = await merge_summaries(chapters)
    coverage = audit_coverage(chapters, final)

    attempt = 0
    while coverage < 1.0 and attempt < max_retries:
        dropped = [c for c in chapters if c.summary and not c.covered]
        emphasis = "、".join(f"第{c.idx}章「{c.title}」" for c in dropped)
        final = await merge_summaries(chapters) + (
            f"\n\n（補足指示: {emphasis} の主張を必ず本文に含めること）")
        coverage = audit_coverage(chapters, final)
        attempt += 1

    return {
        "coverage": coverage,
        "dropped": [c.title for c in chapters if c.summary and not c.covered],
        "thin": [c.title for c in chapters if any("短すぎ" in n for n in c.notes)],
        "summary": final,
    }

if __name__ == "__main__":
    report = asyncio.run(summarize_pdf("./spec.pdf"))
    print(f"被覆率: {report['coverage']:.0%}")
    if report["dropped"]:
        print("再結合から落ちた章:", report["dropped"])
    if report["thin"]:
        print("抽出が怪しい章:", report["thin"])
    print(report["summary"])
```

返り値をレポートにしているのは、被覆率だけでなく「どの章が落ちたか」「どの章の抽出が怪しいか」を人が読める形で残すためです。数字が緑でも、`thin` に章が並んでいれば入力そのものを疑います。監査は合否を出すためではなく、次に何を直すべきかを指し示すために置いています。

## 閾値と運用の落としどころ

被覆率を導入すると、次に迷うのは「どこで止めるか」です。私の手元では、次の切り分けに落ち着いています。

<table>
<thead>
<tr><th>状況</th><th>扱い</th></tr>
</thead>
<tbody>
<tr><td>被覆率 1.0・thin なし</td><td>そのまま採用</td></tr>
<tr><td>被覆率 &lt; 1.0（再結合で溶解）</td><td>落ちた章を名指しで再結合。2回まで再試行</td></tr>
<tr><td>thin に章が残る</td><td>抽出をやり直す。スキャン章はページ範囲を絞ってマルチモーダル入力へ</td></tr>
<tr><td>再試行後も 1.0 未満</td><td>人手レビューに回す。要約を自動採用しない</td></tr>
</tbody>
</table>

コストの内訳も見ておく価値があります。検証パスを軽量モデルと埋め込みに寄せているため、監査に乗る追加コストは本要約の 10% にも届きません。落ちた一章を拾い直す再結合は入力が章要約だけなので、これも安価です。つまり「全部やり直すのは高いが、落ちた章を検知して拾い直すのは安い」という非対称性を、そのまま設計に写しています。

## 繰り返し引っかかったところ

実装を重ねる中で、同じ轍を何度も踏みました。書き残しておきます。

埋め込みの閾値を一つの魔法の数字だと思い込むと、ジャンルが変わった瞬間に取りこぼします。契約書のような定型文の多い文書は章間の類似度が全体に高く出るため、閾値も上げないと「全部含まれている」と誤判定します。数本流して分布を見る手間を省かないことです。

再結合の補足指示を強くしすぎると、今度は落ちた章だけが不自然に長くなり、全体のバランスが崩れます。補足はあくまで「必ず含める」に留め、分量の指定は元の指示に委ねるのが安定しました。

そして一番の教訓は、被覆率が 1.0 でも安心しきらないことです。反映されている、と、正しく反映されている、は別の話です。被覆率は「消えていないこと」しか保証しません。中身が正しいかは、結局その文書を知る人が最後に一度目を通す工程を残しておくのが誠実だと感じています。

## 次の一歩

お手元に 200 ページを超える PDF が一冊あれば、まず章数を数え、素朴な一括要約と、この監査つきパイプラインの両方に通してみてください。一括では気づけなかった「消えた章」が `dropped` に名前で並ぶ瞬間に、この数字を置く意味が腑に落ちると思います。

被覆率という一つの数字は、要約を賢くするための道具ではありません。要約が黙って何かを落としたときに、それを黙らせないための道具です。取りこぼしが見えるようになれば、長尺ドキュメントを機械に任せる不安は、ずいぶん小さくなるはずです。私自身まだ調整を続けている途中ですが、みなさんの手元の一冊にも役立てば嬉しいです。お読みいただきありがとうございました。
