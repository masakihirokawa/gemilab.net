「ユーザーが送信ボタンを押してから応答が表示されるまでに、もっさりとした2〜3秒の沈黙が流れる」— この沈黙はチャットUIにとって致命的です。私自身、個人開発のアプリで Gemini API を使い始めたとき、ローカルでは快適だった応答が本番環境で急に遅く感じられて頭を抱えた経験があります。

公式ドキュメントには「Flash を使えば速くなる」と書かれていますが、実際には**モデルを変えるだけで解決するケースの方が少ない**のが正直なところです。ここでは開発現場で実際に効いた6つのレイテンシ削減テクニックを、計測と実装の両面から共有します。

iOS/Android アプリを 6 本並行運用してきた個人開発者として、この問題に普段から向き合ってきた立場で、要点を整理します。

## レイテンシは「TTFT」「TPS」「E2E」の3層で見る

闇雲に最適化を始める前に、まず計測する箇所を分けて考えるのが近道です。私は次の3つの指標で切り分けています。

- **TTFT（Time To First Token）**: リクエスト送信から最初のトークンが返るまでの時間。モデルのウォームアップ・入力トークンの処理時間に左右されます
- **TPS（Tokens Per Second）**: 出力トークンの生成速度。モデルサイズと出力長で決まります
- **E2E（End-to-End）**: 完全な応答が完了するまでの総時間。`E2E ≒ TTFT + (出力トークン数 / TPS)` で近似できます

体感速度を改善するときに重要なのは TTFT です。E2E が同じでも、TTFT が短いとユーザーには「速い」と感じられます。逆に、E2E が短くても TTFT が長いと「固まった」ように感じられてしまいます。まずは下記のような最小限の計測コードを仕込んで、自分のアプリの数値を把握することをおすすめします。

```python
# pip install google-genai
import time
from google import genai

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

def measure_latency(model: str, prompt: str):
    """Gemini API のレイテンシ3指標を計測する"""
    t_start = time.perf_counter()
    t_first = None
    total_tokens = 0

    stream = client.models.generate_content_stream(
        model=model,
        contents=prompt,
    )
    for chunk in stream:
        if t_first is None:
            t_first = time.perf_counter()  # 最初のトークン到着時刻
        if chunk.text:
            total_tokens += len(chunk.text.split())

    t_end = time.perf_counter()
    ttft = (t_first - t_start) * 1000      # ミリ秒
    e2e = (t_end - t_start) * 1000
    tps = total_tokens / (t_end - t_first) if t_first else 0

    print(f"[{model}] TTFT={ttft:.0f}ms  E2E={e2e:.0f}ms  TPS={tps:.1f}")
    return ttft, e2e, tps

measure_latency("gemini-2.5-flash", "Pythonで素数判定の関数を書いてください。")
# 期待出力例: [gemini-2.5-flash] TTFT=520ms  E2E=2150ms  TPS=98.4
```

このコードを Pro / Flash / Flash-Lite で動かすだけで、自分のユースケースで何が一番効くかが見えてきます。

## モデル選択で TTFT を半分にする

「とりあえず Pro」をやめるだけで、レイテンシは大きく変わります。私の手元の検証では、日本語の200トークン程度の入力で、Flash-Lite と Pro では TTFT に2〜3倍の差が出ました。

判断軸は単純で、**「ユーザーが応答の質よりも速度を重視するか」**です。次のような割り当てが個人的には実用的でした。

- チャットUIの初回挨拶・FAQ応答 → `gemini-2.5-flash-lite`
- 一般的な対話・コード補完 → `gemini-2.5-flash`
- 長文要約・複雑な推論・コーディングエージェント → `gemini-2.5-pro`

特にチャットUIでは、最初のメッセージだけ Flash-Lite、ユーザーが深い質問を投げてきたら Pro に切り替える、といった**動的なモデル選択**も効果的です。詳しい使い分けの判断基準は[Gemini 2.5 Pro と Flash の使い分けガイド](/articles/gemini-basics/gemini-25-pro-vs-flash)にもまとめています。

## ストリーミングで体感速度を劇的に変える

E2E が同じでも、ストリーミングの有無で「速さ」の感じ方は別物になります。実装は数行の変更で済むため、コストパフォーマンスが非常に高い改善です。

```python
# Before: 完全な応答を待ってから表示する（体感が遅い）
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="Reactでカウンターを作る最小コードを教えてください。",
)
print(response.text)

# After: トークンを受け取った順に表示する（体感が速い）
stream = client.models.generate_content_stream(
    model="gemini-2.5-flash",
    contents="Reactでカウンターを作る最小コードを教えてください。",
)
for chunk in stream:
    if chunk.text:
        print(chunk.text, end="", flush=True)
```

ブラウザ側で受ける場合は Server-Sent Events か WebSocket でフロントエンドまで流すのが定石です。実装パターンは[Gemini API ストリーミングとチャット実装ガイド](/articles/gemini-api/streaming-and-chat)で詳しく扱っています。

ひとつ注意したいのは、ストリーミング中にユーザーが画面を離れると無駄な計算が走り続ける点です。私はクライアント側で `AbortController` を使い、ページ離脱・タブ非表示時にストリームを切るようにしています。これだけでもクラウド料金が体感1〜2割は減りました。

## Context Caching で長いコンテキストの初動を圧縮する

長いシステムプロンプトや、参照ドキュメントを含む RAG 構成では、毎回同じ入力トークンを処理し直すことになります。Context Caching を使うと、繰り返し参照する部分を**事前に処理した状態で保持**できるため、TTFT が大きく短縮されます。

```python
# 長いシステムプロンプトをキャッシュする
cache = client.caches.create(
    model="gemini-2.5-flash",
    config={
        "system_instruction": "あなたは丁寧な日本語のテクニカルライターです。回答は3段落以内、専門用語には括弧で英語表記を添えてください。",
        "ttl": "3600s",  # 1時間
    },
)

# 以降のリクエストではキャッシュ参照のみで済む
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="Reactのカスタムフックとは何ですか?",
    config={"cached_content": cache.name},
)
print(response.text)
# 期待動作: キャッシュ未使用時より TTFT が 30〜50% 短くなる
```

私が実装したRAGシステムでは、参照する社内ドキュメントを Context Caching に乗せることで、TTFT が平均900msから380msまで縮みました。**入力トークン数が多い構成ほど効果が大きい**ので、まず長いプロンプトから検証してみてください。詳しくは[Gemini API Context Caching ガイド](/articles/gemini-api/context-caching-guide)も参考になります。

## Thinking Budget でレイテンシと精度のトレードオフを制御する

Gemini 2.5 シリーズには「Thinking」機能があり、モデルが内部で推論ステップを踏んでから応答を返すようになりました。精度は上がりますが、その分レイテンシも増えます。

ここで便利なのが **`thinkingBudget`** パラメータです。0 を指定すると Thinking を無効化でき、簡単な質問に対する応答を素早く返せます。

```python
# Thinking を無効化して速度を優先する
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="今日の天気を一言で答えてください。",
    config={
        "thinking_config": {"thinking_budget": 0},
    },
)
print(response.text)
# 期待動作: Thinking 有効時より 200〜500ms 程度速く返る
```

私の使い分けは次の通りです。

- 雑談・FAQ・定型応答 → `thinking_budget: 0`
- 一般的な対話 → 既定値（モデル任せ）
- 数学・コーディング・複雑な意思決定 → `thinking_budget: 4096` 以上

「全部速くしたい」と思って `thinking_budget: 0` にしてしまうと、コーディング系のタスクで明らかに品質が落ちるので注意してください。タスクの種類で分岐させるのが現実的です。

## プロダクションで詰まりがちな落とし穴

最後に、計測値が良いのに本番でだけ遅い、というケースで私が踏み抜いた落とし穴を紹介します。

**1. リージョンとクライアントの距離を見落としている**

Vertex AI 経由で使う場合は、サーバーのリージョンとモデルのエンドポイントを揃えるだけで TTFT が100ms単位で変わります。日本リージョンに寄せられるなら寄せたほうがよいです。

**2. HTTPコネクションが毎回張られている**

Cloud Run など短命なコンテナでは、リクエストごとに TLS ハンドシェイクが走ることがあります。`google-genai` の `Client` インスタンスはモジュールレベルで使い回すと、コネクションが再利用されて TTFT が短くなります。

**3. レート制限のリトライがレイテンシに化けている**

429エラーを内部的にリトライしている場合、ユーザーから見ると「応答が遅い」現象になります。指数バックオフの最大回数とタイムアウトは必ず明示的に設定してください。コスト削減と組み合わせて考えるなら[Gemini API コスト最適化完全ガイド](/articles/gemini-api/gemini-api-cost-optimization)も合わせて読むと判断しやすくなります。
