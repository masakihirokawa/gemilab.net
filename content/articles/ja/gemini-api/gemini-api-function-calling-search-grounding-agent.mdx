Gemini APIを使ってエージェントを作るとき、「Function Calling（ツール呼び出し）」と「Search Grounding（Google検索による根拠付け）」をどう使い分けるかに迷ったことはありませんか。私も最初はこの2つが競合する機能だと思っていましたが、正しく組み合わせると互いを補完し合う設計ができると気づきました。

このエントリでは、両機能を同一のエージェントループ内で使い分ける設計パターンと、実際のPythonコードを紹介します。ユースケースは「競合サービスの価格動向をリアルタイムに調査し、構造化レポートを生成するエージェント」です。

## Function Calling と Search Grounding の違いを整理する

まず整理しておきたいのは、この2つが解決する問題が異なるということです。

**Function Calling** は、AIがあなたの定義した関数（ツール）を呼び出す仕組みです。データベースへの問い合わせ・外部APIの呼び出し・ファイルの読み書きなど、「事前に定義した処理」を実行させるときに使います。レスポンスの構造を完全にコントロールできる点が強みです。

**Search Grounding** は、Geminiが回答を生成する際にGoogle検索を内部で実行し、その結果を根拠として使う機能です。最新情報を扱う・ハルシネーションを減らす・情報源を示す、といった目的に使います。ただし、検索結果をどう処理するかはGeminiに委ねられます。

この違いを踏まえると、「いつ何を使うか」の判断軸が見えてきます。

- 構造化されたデータが必要 → Function Calling
- 最新の自然言語情報が必要 → Search Grounding
- その両方が必要 → 組み合わせ

## アーキテクチャ：2段階のエージェントループ

今回設計したのは「2段階エージェント」です。

**第1段階（リサーチフェーズ）**：Search Grounding を使って最新情報を収集する。この段階では構造化を意識せず、まず生の情報を取得することに集中する。

**第2段階（抽出・構造化フェーズ）**：第1段階で取得した情報を Function Calling を使って構造化データに変換する。この段階では検索は行わず、既に手元にある情報を整形することに集中する。

この分離によって「最新情報取得」と「構造化処理」の責務が明確になり、各段階でプロンプトを最適化しやすくなります。

## 実装：第1段階（Search Grounding で情報収集）

```python
import google.generativeai as genai
from google.generativeai.types import Tool, GoogleSearchRetrieval

genai.configure(api_key="YOUR_GEMINI_API_KEY")

# Search Grounding を有効にしたモデル設定
search_tool = Tool(
    google_search_retrieval=GoogleSearchRetrieval(
        dynamic_retrieval_config={
            "mode": "MODE_DYNAMIC",
            "dynamic_threshold": 0.3  # 0〜1: 低いほど積極的に検索
        }
    )
)

research_model = genai.GenerativeModel(
    model_name="gemini-2.0-flash",
    tools=[search_tool],
    system_instruction="""あなたは競合調査の専門家です。
ユーザーが指定したサービスについて、最新の価格情報・機能情報を収集してください。
回答は必ず最新の検索結果に基づいてください。情報を推測・補完しないでください。
収集した情報は、後続の処理が解析しやすいよう、箇条書きで構造的にまとめてください。"""
)

def research_phase(service_name: str, focus_area: str) -> str:
    """第1段階：最新情報を検索して収集する"""
    prompt = f"""
    以下のサービスについて調査してください：
    サービス名: {service_name}
    調査対象: {focus_area}
    
    最新の情報を収集し、以下の形式でまとめてください：
    - 料金プランと価格
    - 主要な機能・特徴
    - 最近の変更・アップデート
    - ユーザーレビューで言及される長所・短所
    """
    
    response = research_model.generate_content(prompt)
    return response.text
```

`dynamic_threshold` の値が重要です。0に近いほど積極的に検索を実行し、1に近いほど既存の学習データのみを使います。リアルタイム性が求められる調査では 0.3 前後に設定するのが効果的でした。

## 実装：第2段階（Function Calling で構造化）

```python
import json
from typing import Any

# 構造化に使うツール定義
extraction_tools = [
    {
        "function_declarations": [
            {
                "name": "extract_pricing_data",
                "description": "テキストから価格情報を構造化データとして抽出する",
                "parameters": {
                    "type": "object",
                    "properties": {
                        "service_name": {
                            "type": "string",
                            "description": "サービス名"
                        },
                        "plans": {
                            "type": "array",
                            "items": {
                                "type": "object",
                                "properties": {
                                    "plan_name": {"type": "string"},
                                    "monthly_price_jpy": {"type": "number"},
                                    "annual_price_jpy": {"type": "number"},
                                    "key_features": {
                                        "type": "array",
                                        "items": {"type": "string"}
                                    }
                                }
                            },
                            "description": "料金プラン一覧"
                        },
                        "last_updated": {
                            "type": "string",
                            "description": "情報の最終更新日（推定）"
                        },
                        "confidence_level": {
                            "type": "string",
                            "enum": ["high", "medium", "low"],
                            "description": "情報の確度（high: 公式情報確認済み / medium: 信頼できるソース / low: 不確実）"
                        }
                    },
                    "required": ["service_name", "plans", "confidence_level"]
                }
            }
        ]
    }
]

extraction_model = genai.GenerativeModel(
    model_name="gemini-2.0-flash",
    tools=extraction_tools,
    system_instruction="""あなたはデータ抽出の専門家です。
提供されたテキストから指定された情報を正確に抽出し、ツールを呼び出してください。
テキストに明示されていない情報は推測で補完しないでください。
不明な数値は null としてください。"""
)

def extraction_phase(research_text: str, service_name: str) -> dict[str, Any]:
    """第2段階：収集した情報を構造化データに変換する"""
    prompt = f"""
    以下の調査結果から {service_name} の価格情報を抽出し、
    extract_pricing_data ツールを使って構造化してください。
    
    調査結果:
    {research_text}
    """
    
    response = extraction_model.generate_content(prompt)
    
    # Function Calling レスポンスの処理
    for part in response.candidates[0].content.parts:
        if hasattr(part, "function_call"):
            fc = part.function_call
            if fc.name == "extract_pricing_data":
                # proto.MapComposite を通常のdictに変換
                return dict(fc.args)
    
    return {"error": "Function Calling が実行されませんでした"}
```

第2段階では意図的に Search Grounding を無効にしています。既に手元にある情報を構造化するフェーズで余計な検索が実行されると、第1段階で取得した情報と矛盾するデータが混入するリスクがあるからです。

## 2段階を組み合わせた完全なパイプライン

```python
import asyncio
from dataclasses import dataclass

@dataclass
class CompetitorReport:
    service_name: str
    raw_research: str
    structured_data: dict[str, Any]
    
async def analyze_competitor(service_name: str) -> CompetitorReport:
    """競合サービスの分析パイプライン"""
    print(f"[1/2] {service_name} の調査中...")
    raw_research = research_phase(
        service_name=service_name,
        focus_area="料金プラン・主要機能・最近のアップデート"
    )
    
    print(f"[2/2] {service_name} のデータ構造化中...")
    structured = extraction_phase(raw_research, service_name)
    
    return CompetitorReport(
        service_name=service_name,
        raw_research=raw_research,
        structured_data=structured
    )

async def run_competitor_analysis(competitors: list[str]) -> list[CompetitorReport]:
    """複数の競合を並列分析"""
    tasks = [analyze_competitor(name) for name in competitors]
    return await asyncio.gather(*tasks)

# 使用例
if __name__ == "__main__":
    competitors = ["ServiceA", "ServiceB", "ServiceC"]
    reports = asyncio.run(run_competitor_analysis(competitors))
    
    for report in reports:
        print(f"\n=== {report.service_name} ===")
        print(json.dumps(report.structured_data, ensure_ascii=False, indent=2))
```

並列実行することで、3サービスの調査が順次実行の1/3の時間で完了します。

## ハルシネーション対策：`confidence_level` フィールドの活用

Function Calling の schema に `confidence_level` フィールドを設けることで、Geminiが「この情報はどれだけ確かか」を自己評価するよう促せます。

実際に使ってみると、公式サイトの料金ページが検索で確認できた情報は `high`、ニュース記事や比較サイトからの情報は `medium`、学習データのみの推測は `low` として返ってくることが多く、その後の処理で信頼度フィルタリングをかけられます。

```python
def filter_high_confidence(reports: list[CompetitorReport]) -> list[dict]:
    """確度が high のデータのみを抽出"""
    return [
        r.structured_data for r in reports
        if r.structured_data.get("confidence_level") == "high"
    ]
```

`low` になった場合は「なぜ確度が低いか」をGeminiに説明させ、再調査が必要かどうかを判断するフローも作れます。

## 運用で気づいた注意点

**レート制限への対処**：複数の競合を並列調査する場合、Search Grounding を有効にしたリクエストはそうでないものより消費トークンが多くなります。無料枠の場合は並列数を3以下に抑えることを推奨します。

**検索結果の鮮度**：Search Grounding の検索結果には必ずしも「今日の情報」が含まれるわけではありません。特定の日付以降の情報のみを対象にしたい場合は、プロンプトに「2026年以降の情報のみを参照してください」と明示する必要があります。

**Function Calling の schema 設計**：schema が複雑すぎると Gemini が正確にツールを呼び出せないことがあります。ネストは2〜3段階まで、1ツールのプロパティは10個以下に抑えるのが安定動作の目安です。

このパターンを応用すると、価格調査以外にも「求人情報の収集と構造化」「ニュースの収集とカテゴリ分類」「製品レビューの収集と感情分析」など、「検索→構造化」の2段階が有効なユースケース全般に使えます。Gemini APIの2つの機能を競合ではなく補完として使う設計が、実用的なエージェントへの近道です。
