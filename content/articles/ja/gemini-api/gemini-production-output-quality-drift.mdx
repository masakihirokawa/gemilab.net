Gemini API を本番サービスに組み込んだ直後は、「思ったより賢い」と感じることが多いです。ところが数週間から数ヶ月運用していると、「なんとなく最初ほど冴えない気がする」と感じる瞬間が訪れます。ユーザーからのクレームではなく、自分自身の体感です。こういう曖昧な劣化を「気のせい」で済ませるか、数字で捉えるかは、本番運用の品質を左右する重要な分岐点です。

ここでは私が実際に本番のGeminiベースのサービスで運用している出力品質ドリフトの検知と対処の仕組みを共有します。公式ドキュメントでは語られない、運用現場ならではの判断基準を含めて順にお話しします。

Gemini API を実プロダクトで運用してきた知見から、この問題に普段から向き合ってきた立場で、要点を整理します。

累計5,000万ダウンロードのアプリ群に Gemini を組み込んできた経験から、本番運用のコツを整理します。

## ドリフトが起きる3つの原因

そもそも出力品質がなぜ劣化するのか。私が観測している原因は主に3つです。

**原因1: モデルの挙動変化**

Gemini は継続的に改善されていますが、改善は常に好影響とは限りません。特定のプロンプトパターンに対して、以前よりも冗長な返答をするようになる、あるいは以前より厳しめに断るようになる、といった変化が起こります。バージョンを明示的に固定していない場合（`gemini-2.5-pro` のような最新エイリアスを使っている場合）、この影響を静かに受け続けます。

**原因2: 入力データの分布変化**

サービスが成長すると、最初に想定していなかった使い方をするユーザーが増えます。初期はエンジニア中心だったのに、半年後には一般ユーザーが過半数、というパターンはよくあります。プロンプトは変わっていなくても、実際に投げられる内容の性質が変われば、モデルの応答品質も変わります。

**原因3: プロンプトの静かな腐食**

「改善のために」と小さく変更したプロンプトが、実は一部の入力パターンに対して品質を落としている、というケースです。A/Bテストせずに本番プロンプトを変更すると、気づかぬうちに劣化を引き起こします。

## 指標設計 — 体感を数字にする

「なんとなく悪くなった」を数字にするには、ユーザー体感と相関する指標を設計する必要があります。私が運用で使っているのは以下の3層です。

### レイヤ1: 直接指標

ユーザーの行動から取れる、最も信頼できる指標です。

- **リトライ率**: ユーザーが同じ質問を言い換えて再送信する割合
- **離脱率**: 応答を受け取ってから一定時間内にセッションを終了する割合
- **明示的な低評価**: 応答に Thumbs Down がついた割合

リトライ率は特に強力で、品質劣化が始まるとすぐに上がります。5%から7%への上昇は、統計的に有意な劣化のサインです。

### レイヤ2: 間接指標

応答内容そのものから自動で計算できる指標です。

- **平均応答長**: 同じ種類のプロンプトに対する文字数の平均
- **JSON パース成功率**: 構造化出力を要求している場合
- **禁止フレーズ出現率**: 「申し訳ありません」「お答えできません」などの拒否系フレーズの出現頻度

平均応答長は地味ですが、劣化の早期検知に役立ちます。モデルが自信を失うと、応答が急に長くなったり短くなったりするからです。

### レイヤ3: 抜き打ち評価

日次で一定サンプルを抜き取り、ゴールドスタンダードと比較します。私は、本番トラフィックから1日50件程度をランダムサンプリングし、以下を別プロセスで実行します。

1. 同じ入力をチャンピオンプロンプト（直近で最も良好だったプロンプト）で再実行
2. 両者の出力を別のLLM（例: Gemini 2.5 Flash）でペア評価
3. 本番出力がチャンピオンに負ける率を集計

負け率が30%を超えた日が3日連続すれば、ドリフトが始まっているサインです。

## モデル変化とプロンプト変化を切り分ける

劣化を検知したとき、原因がモデル側なのかプロンプト側なのかを切り分ける点が肝心です。切り分け方法は以下の2段階です。

**ステップ1: プロンプトバージョンを固定して再実行**

直近1週間の本番入力サンプルを、変更前と変更後のプロンプトで再実行し、出力を比較します。ここで差が出れば、プロンプト変更が原因です。

**ステップ2: モデルバージョンを固定して再実行**

`gemini-2.5-pro-002` のような明示的なバージョン指定ができる場合、そのバージョンと現在のエイリアスで同じ入力を実行します。差が出れば、モデル側の変化が主因です。

本番運用では、常にモデルの明示バージョンを使うのが鉄則だと私は考えています。エイリアスは便利ですが、ある日いきなり挙動が変わるリスクを受け入れることになります。

## アラート閾値の設計

「どこまで劣化したら対応するか」の閾値設計も重要です。私の運用では以下のような段階を設けています。

- **黄色**: リトライ率が先週比で +20% 上昇 → 監視強化
- **橙色**: 黄色状態が3日継続、または拒否系フレーズが +50% 増加 → ロールバック検討
- **赤色**: 明示的な低評価率が先月平均の2倍 → 即時ロールバック

赤色アラートが出たら、私はまず直前のプロンプト変更をリバートし、同時にモデルバージョンを1世代前に固定します。原因究明は後回しで、まずユーザー影響を止めるのが優先です。

## ロールバック戦略

プロンプトもモデルもバージョン管理することが、信頼できるロールバックの前提です。私は以下のような構造で管理しています。

- プロンプトは Git でバージョン管理し、本番のプロンプトIDをConfigServiceで切り替える
- モデルバージョンは環境変数で明示指定し、エイリアスは絶対に使わない
- 重要な変更は feature flag で一部ユーザーにだけ段階的に適用

段階的ロールアウトは、コードの本番デプロイと全く同じ考え方をプロンプト変更にも適用することです。「プロンプトだから」と軽く扱うと、深いトラブルに繋がります。

## 運用で学んだこと

この仕組みを運用して1年近くになりますが、最も大きな気づきは「Geminiの品質は、単体では測れない」ということでした。モデル・プロンプト・入力分布の3つの掛け算で決まるので、どれか1つだけを監視しても劣化は捉えきれません。

逆に言えば、3つを同時に記録して比較する仕組みさえあれば、かなり軽量な実装でも十分な運用監視になります。AIサービスの品質管理は、重厚なMLOpsを入れる前に、まず「体感を数字にする」ところから始めるのが実用的です。

## 次にやってみてほしいこと

もしあなたが Gemini API を本番で使っているなら、今すぐ1つだけやってほしいことがあります。過去1週間の応答ログを適当なスプレッドシートに出力して、平均応答長と拒否系フレーズの出現率を日別にグラフにしてみてください。見事に横一直線なら健全です。何かが揺れていたら、それがあなたのシステムにとっての「品質ドリフト」の最初のサインです。

品質は守りに入った瞬間から劣化します。守りに入るのではなく、劣化を前提として仕組みを作る。それがAIサービスの本番運用で私が学んだ一番大切なことです。
