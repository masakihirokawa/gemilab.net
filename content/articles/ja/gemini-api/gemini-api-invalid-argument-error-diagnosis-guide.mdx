Gemini API を使っていて、ふいに返ってくる `INVALID_ARGUMENT`(HTTP 400) のエラー。認証エラーのように原因がハッキリしていればまだ救いがあるのですが、このエラーはかなり幅広いケースで発生するため、メッセージを読んだだけでは何を直せばいいのか分からないことがよくあります。

私自身、モデル名をひとつ書き間違えただけで同じエラーが出ることに気づくまで、30 分近く `generationConfig` を疑って時間を溶かしたことがありました。この記事は、そのときに「原因別にチェックリスト化しておけばよかった」と反省して作った手順をまとめたものです。ここに挙げる 7 つの原因パターンを上から順に確認していけば、多くの場合は数分で原因にたどり着けるはずです。

iOS/Android アプリを 6 本並行運用してきた個人開発者として、この問題に普段から向き合ってきた立場で、要点を整理します。

## なぜ INVALID_ARGUMENT は「原因が特定しづらい」のか

Gemini API のエラーは、HTTP ステータスと `status` フィールドの組み合わせでざっくり分類されます。`INVALID_ARGUMENT` は 400 系の代表格ですが、「リクエストのどこかに Gemini が解釈できない値が入っている」という広い意味なので、実際の原因は多岐にわたります。

典型的なレスポンスはこのような形です。

```json
{
  "error": {
    "code": 400,
    "message": "Request contains an invalid argument.",
    "status": "INVALID_ARGUMENT"
  }
}
```

`message` が `Request contains an invalid argument.` だけのときは、本当に「どこが悪いか」をサーバー側では詳しく返してくれません。一方で `message` に `Please use a valid role: user, model` のように具体的な文言が含まれているときは、そこに大きなヒントがあります。まずは `message` を 1 行ずつ読むこと、そして読めるキーワードがあるかをチェックすることが出発点です。

## リクエストの基本項目で起きやすい 3 パターン

体感として最も多いのが、リクエストの基本項目（モデル名・generationConfig・contents の並び）で起きるミスです。ここはほぼ「見ればわかる」ミスなので、最初に潰しておくと効率が良いです。

### 原因 1: モデル名のタイプミス・世代違い

最初に疑ってほしいのはモデル名です。Gemini は世代交代が早く、以下のようなミスがよくあります。

- `gemini-2.5-pro` を `gemini-25-pro` と書いてしまう（ピリオドの有無）
- `models/gemini-2.5-flash-001` のような古いバージョン付きを指定してしまう
- 存在しないエイリアス（`gemini-flash-latest` など）を書いてしまう

```python
# 動作するモデル指定（2026年4月時点）
import google.generativeai as genai
import os

genai.configure(api_key=os.environ["GEMINI_API_KEY"])

# NG: gemini-25-pro / gemini-2-5-pro / gemini-pro（旧世代）
# OK: gemini-2.5-pro / gemini-2.5-flash / gemini-3-pro
model = genai.GenerativeModel("gemini-2.5-pro")
resp = model.generate_content("こんにちは")
print(resp.text)
# 期待出力例: こんにちは！どのようなことをお手伝いしましょうか？...
```

「モデル名が無効」という厳密なエラーは `NOT_FOUND`（404）が返ることもありますが、SDK やバージョンによっては `INVALID_ARGUMENT` に丸められることがあります。モデルのデプリケーションで詰まった場合は、[Gemini API モデル廃止とマイグレーション手順の完全ガイド](/articles/gemini-api/gemini-api-model-not-found-error-fix-2026) も合わせて参考にしてください。

### 原因 2: generationConfig のパラメータが有効範囲外

次に多いのが `generationConfig` の値が範囲外というパターンです。`temperature` は 0.0〜2.0、`top_p` は 0.0〜1.0、`top_k` は 1 以上の整数など、各パラメータには仕様で決まった範囲があります。UI のスライダー値や環境変数から値を受け取るアプリでは、そのまま渡すと事故につながります。

```python
# 有効範囲外の値を渡した例（400 INVALID_ARGUMENT になる）
bad_config = {
    "temperature": 3.0,      # NG: 2.0 までしか指定できない
    "top_p": 1.5,            # NG: 1.0 までしか指定できない
    "max_output_tokens": 0,  # NG: 1 以上である必要がある
}

# 修正版
good_config = {
    "temperature": 1.0,
    "top_p": 0.95,
    "top_k": 40,
    "max_output_tokens": 2048,
}

model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config=good_config,
)
```

外部入力を受け取るアプリでは、API を呼ぶ直前に簡単なバリデーションを挟むのがおすすめです。本番で散発的に 400 が出てデバッグが面倒になる状況を避けられます。

### 原因 3: `contents` の role の並びが不正

チャット形式で送るときにハマりやすいのが、`contents` 配列の `role` の並びです。Gemini API は基本的に `user` と `model` が交互に現れることを期待しています。同じ role が 2 回続いたり、先頭が `model` で始まっていたりすると、`Please use a valid role` や `First content must have role user` のようなメッセージで INVALID_ARGUMENT が返ります。

```python
# NG: user が連続している
bad_contents = [
    {"role": "user", "parts": ["質問1"]},
    {"role": "user", "parts": ["質問2"]},  # モデル応答を挟まずに再度 user
]

# OK: user → model → user の順に並べる
good_contents = [
    {"role": "user", "parts": ["こんにちは"]},
    {"role": "model", "parts": ["こんにちは！何をお手伝いしましょうか？"]},
    {"role": "user", "parts": ["Python の非同期処理を教えてください"]},
]

resp = model.generate_content(good_contents)
print(resp.text)
```

会話履歴を自前で管理するときは、新しいメッセージを追加する前に「直前の role が自分（user）と違うか」をチェックする一行を入れておくと事故が減ります。履歴まわりで他にも詰まる場合は [Gemini API Chat History 管理でよくあるエラーの修正ガイド](/articles/gemini-api/gemini-api-chat-history-management-errors-fix) にポイントをまとめています。

## マルチモーダルと構造化出力で起きやすい 2 パターン

入力にファイルを添えたり、JSON で応答を受け取ったりする場面でも INVALID_ARGUMENT は頻出します。このあたりは「仕様そのものを読まないと気づきにくい」地雷が多い領域です。

### 原因 4: ファイル添付時の MIME タイプ・サイズ違反

マルチモーダル入力でよくある失敗は次の 3 つです。

- サポート外の MIME タイプを指定している（たとえば `text/x-markdown` は不可）
- 20 MB を超えるファイルを `inline_data` で直接送っている
- `mime_type` とファイル中身の実際のフォーマットが一致していない（PNG なのに `image/jpeg` と書いた等）

サイズが大きいファイルは Files API を使ってアップロードし、返ってきたオブジェクトを `contents` に渡すのが正しい流れです。Files API 側のエラーで詰まっている場合は [Gemini API Files API でよくあるエラーと解決策まとめ](/articles/gemini-api/gemini-api-files-api-troubleshooting-guide) も参考になります。

```python
# 20MB 超の画像を inline で送ってしまう典型的な NG コード
import base64

with open("huge_image.png", "rb") as f:
    data = base64.b64encode(f.read()).decode("utf-8")

bad_parts = [
    {"inline_data": {"mime_type": "image/png", "data": data}},
    {"text": "この画像を説明して"},
]
# → 400 INVALID_ARGUMENT: Request payload size exceeds limit

# OK: Files API でアップロードして URI で参照する
uploaded = genai.upload_file(path="huge_image.png", mime_type="image/png")
resp = model.generate_content([uploaded, "この画像を説明して"])
print(resp.text)
```

アップロード前にファイルサイズと MIME を自前で検査する小さな関数を 1 つ用意しておくと、本番での 400 エラーを体感で半分くらいに減らせます。

### 原因 5: response_mime_type と response_schema の組み合わせミス

JSON 出力を使いたいときは、`response_mime_type` と `response_schema` の組み合わせでエラーが出るケースが多いです。`application/json` 以外の値を書いてしまうと、スキーマ全体が拒否されます。

```python
# NG: mime_type のスペル間違い
bad = {
    "response_mime_type": "applications/json",  # typo
    "response_schema": {"type": "OBJECT", "properties": {}},
}

# OK
good = {
    "response_mime_type": "application/json",
    "response_schema": {
        "type": "object",
        "properties": {
            "title": {"type": "string"},
            "score": {"type": "number"},
        },
        "required": ["title"],
    },
}

model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config=good,
)
```

スキーマ自体のミス（JSON Schema として成立していない・OpenAPI 方言で書いている）でも INVALID_ARGUMENT になることがあります。構造化出力まわりの詳細は [Gemini API 構造化出力エラーを解消する方法](/articles/gemini-api/gemini-api-json-structured-output-errors-fix) を組み合わせて読むと理解が早いと思います。

## Function Calling とデプロイで起きやすい 2 パターン

最後に、Function Calling まわりと本番デプロイ環境の組み合わせで起きる盲点を紹介します。これらは開発環境では出ないのに本番で初めて踏むことがあり、見つけづらいのが特徴です。

### 原因 6: systemInstruction やツール定義のフォーマット違反

Function Calling を使うときの `tools` / `functionDeclarations`、そして `systemInstruction` も、意外と細かいフォーマット違反で弾かれます。

- `systemInstruction` の値が文字列ではなく `{parts: [...]}` でない（モデルによって受け付けが違う）
- `functionDeclarations` の `parameters` が OpenAPI 形式の JSON Schema になっていない
- ツールの `name` に `-` やスペースが入っている（英数字とアンダースコアのみが安全）

エラーメッセージが `Function declaration "xxx" is invalid` のようになっていたら、ここが原因です。関数名は英数字とアンダースコアに限定する、パラメータは必ず `type: "object"` から書き始める、この 2 つを守るだけで事故の大半が防げます。

### 原因 7: 地域・モデル・機能の組み合わせ制限

盲点になりやすいのが、リージョン制限と機能制限です。たとえば以下のようなケースがあります。

- Vertex AI 経由で特定リージョンでは有効でないモデルを呼んでいる
- 特定モデルでは `thinking_config` や `tools` の一部がサポートされていない
- Preview 版のモデルで商用利用できないリクエストを送っている

ローカルでは動くのに Cloud Run や Cloudflare Workers にデプロイしたら突然 400 が出る、というのが典型です。デプロイ先のリージョンが違うので、同じコードでもエラーが出ることがあります。本番のログで実際に呼んでいるエンドポイントと、リージョン・モデル・機能の組み合わせを確認してみてください。

## 調査を速くする 3 つの小さな習慣

原因特定までの時間を短くするために、私が日頃から実践しているのは次の 3 つです。

1. **`message` の文言を必ず読む**: `Please use a valid role`、`Request payload size exceeds limit` など、具体的な手がかりが含まれていることが多いです。ツールのログに `message` を必ず出力しておきましょう。
2. **最小再現リクエストを作る**: 失敗するリクエストから引数を 1 つずつ削って、何を外すとエラーが消えるかを切り分けます。`curl` か `httpx` で手動リクエストを投げるのが確実です。
3. **変更履歴をすぐ戻せるようにする**: モデル名・generationConfig・schema の変更はプルリクエストの別コミットに分け、エラーが出たときに `git bisect` で犯人コミットを絞り込めるようにしておきます。

エラーハンドリングの設計そのものを体系的に見直したいときは、[Gemini API 実運用のためのエラー処理とリトライパターン](/articles/gemini-api/gemini-api-error-handling-retry-patterns) も参考にしてみてください。API を使い始めたばかりで全体像を整理したい方は、[『実践 AI エージェント開発入門』（吉川隼人）](https://www.amazon.co.jp/dp/B0DTR3WTVZ/?tag=pinocchio-22) のような書籍を 1 冊手元に置いておくと、エラー対処だけでなく設計の引き出しが増えます。

## まずは 7 項目の目視チェックから始めましょう

`INVALID_ARGUMENT` は原因が広いぶん、1 つずつ潰していけば必ず犯人にたどり着けるエラーです。新しいエラーに出会ったら、まずこの記事の 7 項目を上から順番に眺めて、ひとつずつリクエストと突き合わせてみてください。多くの場合、モデル名か `generationConfig` か role の並びで決着がつきます。原因を早く絞り込めるほど、アプリの開発スピードも自然に上がっていきます。
