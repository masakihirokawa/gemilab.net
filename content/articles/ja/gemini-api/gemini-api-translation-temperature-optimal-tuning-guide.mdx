「Gemini API で翻訳機能を作っているのですが、`temperature` を 0 に下げると硬すぎる訳になり、0.7 のままだと固有名詞が揺れて困っています」——先日、開発者の方から似たような相談を立て続けに受けました。

ドキュメントには「決定論的な出力には低い値を、創造的な出力には高い値を」という一般論しか書かれておらず、翻訳という具体的なユースケースで「結局いくつにすればいいのか」を答えてくれる資料が驚くほど少ないのが現状です。

ここでは私が実際に多言語アプリ開発で使い分けている temperature 値を、技術ドキュメント・マーケティングコピー・カジュアル会話・文芸的なテキスト・コードコメントの5つの用途ごとに、検証コードと出力サンプルとあわせて公開します。`top_p` や `top_k` との組み合わせ方、固有名詞の安定化テクニックまで含めて、コピーすればそのまま本番で使える形にまとめました。

## 翻訳タスクが temperature 調整を必要とする理由

翻訳は、要約やコード生成と並んで「temperature の影響が結果に直接出やすい」タスクの代表例です。理由は2つあります。

ひとつめは「正解の幅が用途によって大きく変わる」こと。法律文書なら一字一句正確であるべきですが、ゲームのセリフなら原文のニュアンスを保ちつつ自然な日本語に意訳する方が好まれます。同じ「翻訳」という言葉でも、求められる柔軟性は10倍以上違うのです。

ふたつめは「固有名詞・専門用語の安定性が品質を左右する」こと。temperature が高いと「Apple」が「アップル社」「Apple」「林檎社」のように回答ごとにブレます。プロダクトの翻訳では、この揺れがそのままユーザー体験の質を落とします。

つまり翻訳における temperature 設定は、「自然さ」と「一貫性」のトレードオフを意図的にコントロールする操作だと考えると分かりやすくなります。

## 用途別ベストバリュー早見表

これまで実装してきた翻訳機能で安定して結果を出している値を、用途ごとにまとめます。**最初の試行ではこの値から始めて、出力を見ながら ±0.1 ずつ微調整するのがおすすめです。**

- **技術ドキュメント・API リファレンス**: `temperature: 0.1` / `top_p: 0.8`
- **マーケティングコピー・キャッチコピー**: `temperature: 0.7` / `top_p: 0.95`
- **カジュアル会話・チャットボット応答**: `temperature: 0.4` / `top_p: 0.9`
- **文芸・小説・脚本**: `temperature: 0.8` / `top_p: 0.95`
- **コードコメント・コミットメッセージ**: `temperature: 0.0` / `top_p: 0.7`
- **法律・契約書・医療文書**: `temperature: 0.0` / `top_p: 0.5`

迷ったら、まず `0.3` から始めて結果を見ることをおすすめします。0.3 は「翻訳としての安定感」と「日本語としての自然さ」のバランスがちょうど取れる値で、実用範囲の8割をカバーできます。

## 出力の違いを実際に検証するコード

論より証拠です。同じ英文を temperature だけ変えて翻訳させ、出力を比較するスクリプトを共有します。手元の API キーで動かせば、自分のユースケースに最適な値を一目で判断できるようになります。

```python
# pip install google-generativeai
import google.generativeai as genai
import os

genai.configure(api_key=os.environ["GEMINI_API_KEY"])
model = genai.GenerativeModel("gemini-2.5-flash")

source_text = (
    "Effective error handling is the foundation of a reliable API. "
    "When integrating Gemini, you should always wrap calls in a retry "
    "block with exponential backoff."
)

prompt_template = (
    "次の英文を、技術ブログの読者向けに自然な日本語に翻訳してください。"
    "技術用語はそのまま英語のままで構いません。\n\n"
    "原文: {text}"
)

for temp in [0.0, 0.3, 0.5, 0.7, 1.0]:
    response = model.generate_content(
        prompt_template.format(text=source_text),
        generation_config=genai.types.GenerationConfig(
            temperature=temp,
            top_p=0.9,
            max_output_tokens=200,
        ),
    )
    print(f"\n=== temperature={temp} ===")
    print(response.text)
```

実行すると、低い temperature では原文の構造に忠実な訳が、高い temperature では意訳が含まれる訳が出てきます。同じプロンプトを3回ずつ実行して「揺れの大きさ」も観察すると、自分のプロダクトに必要な安定性のレベルがはっきり見えてきます。

なお、上記の `top_p: 0.9` は「累積確率の上位 90% の語彙からサンプリング」する設定です。temperature だけでは制御しきれない極端なトークンを除外する役割を果たすため、本番環境では temperature と top_p をセットで設定するのが私の定番パターンになっています。

## 固有名詞の揺れを抑える3つのテクニック

temperature を下げても、製品名や人名の表記揺れは完全には消えません。実践で効果のあった3つの方法を紹介します。

### 1. プロンプトで用語集を明示する

System Instructions に「固有名詞の翻訳ルール」を明記すると、temperature が中程度でも揺れが大幅に減ります。

```python
system_instruction = """
あなたは技術翻訳の専門家です。以下のルールを厳守してください。

【固有名詞ルール】
- "Gemini" → "Gemini"（カタカナ化しない）
- "Google" → "Google"（カタカナ化しない）
- "Apple" → "Apple"（「アップル社」と訳さない）
- "API" → "API"（「エーピーアイ」と訳さない）
- 製品名・サービス名はすべて英語表記を維持する

【スタイル】
- 敬体（です/ます調）で統一する
- 1文を50字以内に収めるよう努める
"""

model = genai.GenerativeModel(
    "gemini-2.5-flash",
    system_instruction=system_instruction,
)
```

このパターンを取り入れただけで、私のアプリでは固有名詞のブレが体感で7〜8割減りました。

### 2. seed パラメータで再現性を確保する

A/B テストや回帰テストで「同じ入力に対して同じ出力」を保証したいときは、`seed` パラメータが効きます。temperature を下げても完全な決定論性は保証されないため、テスト基盤では seed を併用するのが確実です。詳しくは [Gemini API の seed パラメータで応答を再現可能にする](/articles/gemini-api/gemini-api-seed-parameter-reproducibility-guide) で解説していますので、テスト戦略を整える方は合わせて参照ください。

### 3. 用語集を Function Calling で参照させる

長期的な運用を考えるなら、用語集をプロンプトに直書きするのではなく、Function Calling 経由で都度参照する設計が拡張性に優れます。新しい固有名詞が追加されてもプロンプトを書き換えずに済むため、運用コストが下がります。

## ストリーミング配信時の注意点

`stream=True` でストリーミング配信するときも、temperature の影響は同じように出ます。ただし、ユーザー体験としては「途中で訳語が切り替わって見える」ことを避けたいので、ストリーミングではむしろ `temperature: 0.1〜0.3` に下げて安定性を優先する設計が向いています。

リアルタイム翻訳チャットのように WebSocket でつなぐ構成でも考え方は同じで、配信の途中で訳語が切り替わって見えないよう、ストリーミング側はあえて低めの temperature に寄せておくと表示が安定します。

## よくある落とし穴

実装時に何度も踏みそうになった落とし穴を共有します。

**落とし穴1: temperature=0 でも「完全に同じ出力」にはならない**

数学的には decoding は決定論的になるはずですが、Gemini API は内部で複数のリクエストを並列処理しているため、`temperature=0` でも稀に出力がブレます。完全な再現性が必要なら seed パラメータを併用してください。

**落とし穴2: モデルによって最適値が違う**

`gemini-2.5-pro` と `gemini-2.5-flash` では、同じ temperature でも出力の傾向が異なります。Flash は元々ややランダム性が低めなので、Pro より 0.1 ほど高めに設定しても同程度の安定性が得られる印象です。モデルを切り替えたら必ず再チューニングしてください。

**落とし穴3: 多言語混在文では低 temperature が裏目に出る**

「英文中に日本語の固有名詞が混じる」ような文を翻訳するとき、temperature を 0 にすると「日本語の部分を英語に翻訳し直す」誤動作が起きやすくなります。多言語混在の場合は `0.3〜0.5` の範囲で試すと安定します。

## 「感覚」ではなく「数値」で品質を測定する

「0.3 のほうがしっくりくる」は出発点としては悪くないのですが、本番のパラメータ決定にはやはり数値が欲しくなります。新しい翻訳機能で temperature を選ぶときに私が使っている、軽量な評価ハーネスを共有します。

考え方はシンプルです。プロダクトの代表的な原文を 20〜30 文ほど用意し、各 temperature で翻訳させて、自分が大事にしている3つの軸 — 意味の正確さ・日本語としての自然さ・固有名詞の一貫性 — でスコアをつけます。30 文あれば、傾向をつかむには十分なサンプル数になります。

```python
import google.generativeai as genai
from collections import defaultdict

genai.configure(api_key=os.environ["GEMINI_API_KEY"])
model = genai.GenerativeModel("gemini-2.5-flash")

# 「保持されるべき固有名詞」を一緒に持たせて一貫性を測定する
test_set = [
    ("Apple announced a new iPhone today.", ["Apple", "iPhone"]),
    ("Use the Gemini API to integrate AI into your app.", ["Gemini", "API"]),
    # 自分のプロダクト領域に合わせて 20〜30 文追加してください
]

results = defaultdict(list)
for temp in [0.0, 0.3, 0.5, 0.7]:
    for source, must_keep in test_set:
        translations = []
        for _ in range(3):  # 3回サンプリングしてブレを測定
            r = model.generate_content(
                f"次の英文を日本語に翻訳してください: {source}",
                generation_config=genai.types.GenerationConfig(temperature=temp),
            )
            translations.append(r.text)
        unique = len(set(translations))
        kept = all(token in t for t in translations for token in must_keep)
        results[temp].append((unique, kept))

for temp, rows in results.items():
    drift = sum(u for u, _ in rows) / len(rows)
    consistency = sum(1 for _, k in rows if k) / len(rows)
    print(f"temp={temp}: 平均ブレ={drift:.2f}, 固有名詞保持率={consistency:.0%}")
```

`unique` は3回のサンプルがいくつ異なる結果になったかを表し、値が高いほどブレが大きいことを示します。`kept` は固有名詞が3回ともすべて維持されたかを記録します。この2つを組み合わせると「自然さ」と「安定性」のトレードオフを定量的に可視化でき、関係者から「なぜ 0.3 にしたの？」と聞かれたときも数値で答えられるようになります。

実際、最近のプロジェクトではこのハーネスで「カジュアル会話の翻訳では `temperature=0.5` のほうが `0.3` より自然さの評価が高かった」という結果が出ました。「低いほど安全」という直感が、計測すれば覆ることもあるのが面白いところです。

## 実例: SaaS ダッシュボードのローカライゼーション

理論だけでは抽象的なので、ひとつの SaaS プロダクト内で文字列の種類ごとに temperature をどう使い分けるかをご紹介します。

**文字列タイプ1: エラーメッセージ。** トーンは事務的、正確性が最優先で、固有名詞も完全に固定したい用途です。私は `temperature: 0.0` に `top_p: 0.6` を組み合わせ、System Instructions に厳密な用語集を載せます。ここでブレが出ると、サポートチケットに直結してしまいます。

**文字列タイプ2: オンボーディング用のツールチップ。** 親しみやすく、ややくだけたトーンが望まれる場面です。`temperature: 0.5` / `top_p: 0.9` あたりがちょうどよく、自然なバリエーションは歓迎しつつも、ボタンラベル（「始める」「あとで」など）は安定させたいバランスです。

**文字列タイプ3: ランディングページのヒーローコピー。** ここはむしろ創造性が欲しい領域です。`temperature: 0.8` / `top_p: 0.95` で、直訳では出てこない自然な日本語の言い回しを引き出します。私は3つほど候補を生成して人が最終選定する運用にしており、Gemini を「決定論的なツール」ではなく「創造のパートナー」として使う方針です。

ひとつのプロダクト内でも、文字列の種類ごとに2〜3種類の temperature プロファイルを使い分ける必要があると考えています。「アプリ全体で1つの temperature 値」という設計が、本番コードでもっとも見かける単純化のしすぎパターンです。

## 用途別プロファイルをコードに固定する

前節の使い分けは、決めた直後はうまく回ります。難しいのは半年後です。

新しい画面を追加するとき、開発者が参照できるのはコードだけです。プロファイルの根拠がレビューのコメントや誰かの記憶にしか残っていないと、新しく足された文字列は静かにライブラリの既定値へ落ちていきます。私も個人開発でアプリの画面が増えていく中で、エラーメッセージ用に決めたはずの 0.0 が、追加した画面だけ既定値のまま動いていたことがありました。翻訳の質を疑って原文を読み直し、設定を確認して初めて気づいた、という順序でした。

そこで今は、文字列キーの接頭辞から生成設定を引くだけの小さなモジュールを1つ置いています。

```python
# i18n_profiles.py
from dataclasses import dataclass

@dataclass(frozen=True)
class Profile:
    temperature: float
    top_p: float
    glossary_strict: bool

PROFILES = {
    "error": Profile(0.0, 0.6, True),
    "legal": Profile(0.0, 0.5, True),
    "ui.label": Profile(0.1, 0.7, True),
    "onboarding": Profile(0.5, 0.9, True),
    "release_note": Profile(0.3, 0.9, True),
    "marketing": Profile(0.8, 0.95, False),
}

# 未割り当てのキーが落ちてくる先。API の既定値ではなく保守側に寄せる
FALLBACK = Profile(0.2, 0.8, True)

def resolve(key: str) -> tuple[Profile, bool]:
    """'error.network.timeout' → PROFILES['error'] を返す。
    長い接頭辞から順に探すので 'ui.label' は 'ui' より優先される。
    2番目の戻り値は「明示的に割り当てられたか」"""
    parts = key.split(".")
    for depth in range(len(parts), 0, -1):
        prefix = ".".join(parts[:depth])
        if prefix in PROFILES:
            return PROFILES[prefix], True
    return FALLBACK, False
```

`resolve()` が2つ目に返す真偽値が、このモジュールで一番働いている部分です。設定を引けたかどうかではなく、「人が用途を判断した結果なのか、ただ落ちてきただけなのか」を呼び出し側に伝えます。

フォールバックを 0.2 に置いているのも同じ考え方からです。未割り当ての文字列は、定義上「まだ誰も用途を考えていない文字列」です。そこにライブラリの既定値をそのまま当てると、いちばん検討されていない箇所がいちばん揺れる配置になってしまいます。

あとは、未割り当てのキーをプルリクエストの時点で表に出すだけです。

```python
# tools/check_profiles.py
import json
import sys
from i18n_profiles import resolve

def main(catalog_path: str, allowlist_path: str) -> int:
    keys = json.load(open(catalog_path, encoding="utf-8")).keys()
    allowed = set(json.load(open(allowlist_path, encoding="utf-8")))
    unassigned = sorted(k for k in keys if not resolve(k)[1] and k not in allowed)
    if not unassigned:
        return 0
    print("プロファイルが割り当てられていないキー:")
    for k in unassigned:
        print(f"  - {k}")
    print("i18n_profiles.py に接頭辞を追加するか、"
          "当面フォールバックでよい場合は allowlist に登録してください。")
    return 1

if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))
```

allowlist を用意しているのは、抜け道を残すためではありません。フォールバックのまま出すこと自体は問題ないのですが、それを黙って通すか、1行足してレビューに乗せるかで意味が変わります。後者なら「この文字列は当面これでよい」という判断がファイルに残り、次に触る人が経緯を追えます。

## 出荷前に逆翻訳でリグレッションを止める

用途別に temperature を決めても、文字列を入れ替えるたびに品質が保たれている保証はありません。私自身、個人開発のアプリで多言語化を回すときは、出荷前に逆翻訳（back-translation）で意味のズレと用語違反を機械的に拾う小さなゲートを挟んでいます。

考え方は単純です。日本語へ訳した文をもう一度英語へ訳し戻し、元の英文と意味が大きく離れていないか、保持すべき固有名詞が消えていないかを確認します。完全一致は求めません。あくまで「明らかにおかしい訳」を本番前に止めるための歯止めです。

```python
import google.generativeai as genai

model = genai.GenerativeModel("gemini-2.5-flash")

def back_translate_gate(source_en, translated_ja, must_keep):
    # 1) 用語集違反のチェック（モデル不要・確実・速い一次フィルタ）
    missing = [w for w in must_keep if w not in translated_ja]
    if missing:
        return ("FAIL", f"用語が欠落: {missing}")
    # 2) 逆翻訳して意味のズレを確認する
    back = model.generate_content(
        f"次の日本語を英語に訳し戻してください（説明は不要）:\n{translated_ja}",
        generation_config=genai.types.GenerationConfig(temperature=0.0),
    ).text
    verdict = model.generate_content(
        "次の2つの英文が同じ意味かを yes/no だけで答えてください。\n"
        f"A: {source_en}\nB: {back}",
        generation_config=genai.types.GenerationConfig(temperature=0.0),
    ).text.strip().lower()
    return ("PASS", back) if verdict.startswith("yes") else ("FAIL", f"意味のズレ: {back}")
```

用語集違反はモデルを使わず文字列の有無だけで判定し、確実で速い一次フィルタにしています。意味のズレの確認だけ、逆翻訳と yes/no 判定にモデルを1回ずつ使います。ゲート自体の判定がぶれないよう、検証側の temperature は 0.0 で固定しておきます。

App Store と Google Play に出しているアプリのストア説明文や課金まわりのヘルプ文を多言語化する際、このゲートで「固有名詞まで訳し込まれてしまった訳」を本番前に何度も止められました。手元の運用では、ゲートに引っかかるのは全体の数パーセント程度ですが、その数パーセントがちょうどレビューでの指摘や問い合わせにつながる箇所だったので、費用対効果は高いと感じています。

ゲートに落ちた文字列だけを一段高いモデルで再翻訳する設計にしておくと、コストを抑えながら品質の底を引き上げられます。すべての訳に上位モデルを使うのではなく、機械チェックに落ちたものだけを拾い直す——この絞り込みが、運用コストと品質のちょうどよい折り合いになります。

## temperature では直らない「訳文の長さ」

用途別に値を決め、逆翻訳ゲートも通した訳文が、実機で確認するとボタンからはみ出している。ローカライズで最後まで残るのは、この種の不具合でした。

これは翻訳の質の問題ではなく、レイアウトの問題です。temperature を上げると訳文の長さのばらつきも一緒に広がりますが、下げれば収まるとも限りません。日本語もドイツ語も、丁寧に訳すほど原文より長くなる方向に伸びます。短くしたいのであれば、短くしてほしいと明示するほうが確実です。

そこで、表示幅の予算を文字列タイプごとに決めて、超えたものだけを拾い直しています。

```python
import unicodedata

def display_width(s: str) -> int:
    """全角を2、半角を1として表示幅をおおまかに測る"""
    return sum(
        2 if unicodedata.east_asian_width(ch) in ("F", "W", "A") else 1
        for ch in s
    )

# 原文の表示幅に対して、どこまで膨らむことを許すか
BUDGET_RATIO = {
    "ui.label": 1.1,     # ボタン・タブ。ほぼ余白がない
    "error": 1.6,        # 2行までは許容できる
    "onboarding": 1.8,
    "marketing": 2.2,    # 改行できる領域なので緩めてよい
}

def fit_translation(key, source_en, translate, max_attempts=2):
    ratio = BUDGET_RATIO.get(key.split(".")[0], 1.5)
    budget = int(display_width(source_en) * ratio)
    profile, _ = resolve(key)
    temp = profile.temperature

    text = translate(source_en, temperature=temp)
    for _ in range(max_attempts):
        if display_width(text) <= budget:
            return text, "ok"
        temp = max(0.0, temp - 0.2)
        text = translate(
            source_en,
            temperature=temp,
            extra=(
                f"訳文の表示幅を {budget}（全角1文字を2として計算）以内に収めてください。"
                "意味は落とさず、冗長な修飾から削ってください。"
            ),
        )
    return text, "over_budget"
```

大事なのは、1回目の翻訳には長さの制約を入れないことです。すべての文字列に「N文字以内」と指示すると、もともと収まっていた訳文まで不自然に切り詰められます。制約は、実際にはみ出した文字列にだけ後から効かせます。

2回試しても収まらないものは、切り詰めずに人の確認へ回します。レイアウトが少し崩れるより、意味の欠けた訳がそのまま画面に出るほうが厄介です。

このバジェットを入れてから、思わぬ副産物がありました。繰り返し予算を超える文字列を並べてみると、訳文が長いのではなく、原文の英語のほうが冗長だったケースが目立ったのです。"Please make sure that you have completed..." のような書き出しは、日本語にすると容赦なく伸びます。

直すべき場所が訳文ではなく原文だと分かるのは、測ってみるまで気づけない種類のことでした。原文を短く書き直すと、対応するすべての言語の訳文が同時に収まるようになります。翻訳側で粘るより、はるかに効率のよい直し方です。

## 全体を振り返って — 今日から試せる一歩

長々と書いてきましたが、最も実用的な提案はシンプルです。**今お使いのアプリで `temperature=0.7` のまま動かしている翻訳機能があれば、まず `0.3` に下げて1日運用してみてください。** 多くの場合、ユーザーから「翻訳の品質が上がった」というフィードバックが返ってくるはずです。

そこから用途に応じて、技術文書なら 0.1、マーケティングコピーなら 0.7、と微調整していくのが私のおすすめのアプローチです。temperature は「設定したら終わり」のパラメータではなく、ユーザー体験を継続的に改善する手綱だと捉えると、運用の楽しみがひとつ増えるかもしれません。
