「Google AI Studio 上で何度試しても完璧に動いたプロンプトを、そのままコードに落とし込んだら急にエラーになった」——Gemini API を触り始めた方からよく聞く相談です。私自身も最初のうちは、Studio で動いたコードを `Get code` ボタンでコピーしたのに、なぜかローカルで 404 が返ってきてかなり戸惑いました。

実はこの「Studio では動くのに API では動かない」現象には、ほぼ決まったパターンがあります。どれも一度ハマると気づきにくいのですが、診断手順を知っていれば数分で原因を切り分けられます。ここでは私が開発現場で実際に遭遇したケースをもとに、順番にチェックすべきポイントを整理しました。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

## Studio と API では何が違うのか

そもそもの前提として、Google AI Studio と Gemini API は「同じモデルを呼んでいる」ように見えて、実は振る舞いが完全には一致しません。これを理解しておくだけで、エラーの半分は見通しが立つようになります。

Google AI Studio はあなたの Google アカウントでログインしたセッション上で動作しており、プレビュー中のモデルや社内向けの実験的なモデルも触れることがあります。一方、API キーで呼び出す `generativelanguage.googleapis.com` は、公開されている GA（一般提供）モデルや、API キーのプロジェクトに紐づいた権限の範囲でしか呼べません。さらに Safety Settings、System Instructions、`temperature` などのデフォルト値も、Studio の UI が裏で補ってくれている分、コード側は明示指定が必要になるケースが多くあります。

つまり、Studio はいくつもの気の利いた初期化を肩代わりしてくれているため、**「Studio で動いた ≠ 何も設定しなくても API で動く」** という前提に立つ必要があります。

## 最初に必ずやるべきこと — Studio の「Get code」と差分を取る

診断の第一歩は、思いつきでコードを書き換えないことです。まずは Studio の右上にある `Get code` ボタンから、動作するコード一式をエクスポートしてください。Python / Node.js / cURL の3形式で出せるので、自分の実装言語に合わせて選びます。

そのうえで、以下の4点を自分のコードと突き合わせます。

- **モデル名**: `model="gemini-2.5-pro"` のように完全一致しているか
- **システム指示**: Studio で入力した `System instructions` がコード側にも同じ文字列で渡っているか
- **generationConfig**: `temperature`・`topP`・`maxOutputTokens` が Studio の右サイドバーの値と一致しているか
- **safetySettings**: Studio で `BLOCK_NONE` にしていた場合、コード側も同じ値を明示しているか

この4点が揃うまで、複雑なロジックに手を入れるのは後回しにしてください。経験上、ここで再現するだけで7〜8割の「Studio では動くのに」は解決します。

## よくある失敗パターン①：モデル名の微妙な違い

最も多いのがモデル名のタイプミスに近い問題です。特に次の3つは混同しがちです。

- `gemini-2.5-pro` — 通常の API から呼べる GA モデル
- `gemini-2.5-pro-latest` — 最新バージョンを常に追従するエイリアス（提供されないリージョンあり）
- `gemini-2.5-pro-preview` — プレビュー版（Studio でのみ見えることが多い）

Studio のモデルドロップダウンには `(preview)` が小さく添えられていることがあり、見落として Preview モデルをそのままコードにコピーすると、404 で `model not found` になります。詳しくは [Gemini API「モデルが見つからない」エラーの原因と解決方法](/articles/gemini-api/gemini-api-model-not-found-error-fix-2026) でも原因別に整理していますので、あわせて確認してみてください。

なお Gemini CLI や Vertex AI 経由だと、同じ名前でも呼び出せるモデルの集合が変わります。エラーメッセージに `models/... is not found for API version v1beta` と書かれていた場合は、モデル名ではなく API バージョン（`v1beta` / `v1`）側を疑ってみる価値があります。

```python
# ❌ Studio からコピーしただけの状態（Preview モデルが残っている）
from google import genai
client = genai.Client(api_key="YOUR_API_KEY")
res = client.models.generate_content(
    model="gemini-2.5-pro-preview-01-15",  # Preview は API で呼べないことがある
    contents="今日のニュースを要約して",
)

# ✅ 安定 API で呼べる GA モデル名に置き換える
res = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="今日のニュースを要約して",
)
print(res.text)
# 期待する出力: 要約テキストが返る
```

## よくある失敗パターン②：API キーとリージョンの思い込み

次に多いのが、API キーが実は別プロジェクトのものだったり、そのキーに紐づくプロジェクトで Gemini API が有効化されていない、というケースです。Studio はブラウザのログインセッションで動くため、プロジェクトの権限問題が見えにくくなっています。

確認手順は次の通りです。

- Google AI Studio の上部メニューから `Get API key` を開き、自分が今使っているキーが Studio と同じプロジェクト配下のものかを確認する
- Google Cloud Console で該当プロジェクトの `APIs & Services` → `Enabled APIs` に **Generative Language API** が並んでいるかを確認する
- Workspace アカウントをお使いの場合は、管理者が Gemini API をブロックしていないかを IT 管理者に確認する

また、EU / 日本リージョンでは先行公開されていない機能があります。返ってくるエラーが `PERMISSION_DENIED` や `FAILED_PRECONDITION` の場合、権限・地域の観点で疑ってみるのが近道です。認証周りで詰まった場合は [Gemini API 認証エラーの原因と解決策](/articles/gemini-api/gemini-api-authentication-error-solutions) が参考になると思います。

## よくある失敗パターン③：Safety Filter と空応答

「エラーは出ないのに `response.text` が空文字列で返ってくる」という症状も、Studio との差分でよく発生します。これは Safety Filter が応答をブロックしたまま、SDK が黙って空文字を返しているのが原因です。

Studio ではデフォルトで Safety Filter がやや緩めに設定されていることがある一方、API 経由ではデフォルトが中程度以上になることが多く、同じ入力でもブロックされるラインが違います。以下のように `safety_settings` を明示し、`response.prompt_feedback` と `response.candidates[0].finish_reason` を必ずログに残しておくと、原因の特定が一気に楽になります。

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

res = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="暴力描写を含む小説の一節を書いて",
    config=types.GenerateContentConfig(
        safety_settings=[
            types.SafetySetting(
                category="HARM_CATEGORY_DANGEROUS_CONTENT",
                threshold="BLOCK_ONLY_HIGH",
            ),
        ],
    ),
)

# 空応答のときに見るべき2つの情報
print("finish_reason:", res.candidates[0].finish_reason)
print("safety_ratings:", res.candidates[0].safety_ratings)
print("text:", res.text or "(blocked)")
```

`finish_reason` が `SAFETY` になっていれば Safety Filter が原因、`MAX_TOKENS` ならトークン制限、`OTHER` なら Grounding や Function Calling 周りの可能性が高い、という切り分けができます。より細かいブロック解除の指針は [Gemini API の Safety Filter で応答がブロックされるときの対処法](/articles/gemini-api/gemini-api-safety-filter-blocked-response-fix) にまとめています。

## 診断の締めくくり — 「Studio 側を変更してもう一度再現」が実用的

ここまでで原因が特定できない場合、私がおすすめしているのは「Studio 側で失敗ケースを再現できるか確認する」というアプローチです。API 側の設定を Studio に戻していき、どこで挙動が変わるかを二分探索で追っていきます。

- まず、Studio を新しいセッションで開き、同じプロンプト・同じモデルで再実行する
- 次に、Studio の `System instructions` や `generationConfig` を一つずつ自分のコードの値に近づけていく
- どこかで Studio 側でも失敗・空応答が再現したら、その変更点が真犯人

この手順は、サポートに問い合わせるときの再現手順としてもそのまま使えるので、チームで共有しておくと便利です。「API 側にだけ存在する問題」か「プロンプト設計そのものの問題」かを切り分けられるので、次回から悩む時間がぐっと減ると思います。

まずは一度、Studio の `Get code` から吐き出されたコードに戻して、差分ゼロの状態を作るところから始めてみてください。そこまで来れば、あとは一項目ずつ自分のアプリの仕様に寄せていくだけなので、手戻りも最小で済みます。
