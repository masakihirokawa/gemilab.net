「ローカルで完璧に動いているのに、本番サーバーにデプロイした途端に動かなくなった」——Gemini API を Python で使い始めた開発者なら、一度はこの壁にぶつかるのではないでしょうか。エラーメッセージがローカルと異なったり、同じコードなのに挙動が変わったりして、原因の特定に時間がかかることがあります。

ここでは本番環境でよく起きるパターンを原因別に整理し、それぞれの解決策を具体的なコードとともにご紹介します。「なぜローカルで動いて本番で動かないのか」を理解することで、次回以降のデプロイがずっとスムーズになると思います。

iOS/Android アプリを 6 本並行運用してきた個人開発者として、この問題に普段から向き合ってきた立場で、要点を整理します。

2014年から個人開発でモバイルアプリを続けてきた立場で見ると、API の選び方は AdMob を含む既存スタックとの相性が鍵です。

## なぜローカルと本番で挙動が変わるのか

そもそも、なぜ同じコードが環境によって異なる動作をするのでしょうか。主な原因は次の3つです。

まず **実行環境の差異** です。ローカルでは自分の PC の Python バージョン、インストール済みパッケージ、システム設定がそのまま使われます。一方、本番サーバーは別の OS、別の Python バージョン、最小限のパッケージしか入っていないことが多いです。

次に **環境変数の有無** です。ローカルでは `.env` ファイルや `export` コマンドで設定した API キーが使われますが、本番サーバーにはそれらが存在しないことがほとんどです。

最後に **ネットワーク・タイムアウトの設定差** です。ローカルから Gemini API に接続するのと、クラウドサーバーから接続するのとでは、レイテンシやタイムアウト挙動が異なります。

以下、具体的なエラーパターンごとに見ていきましょう。

## エラー1: 環境変数が読み込まれていない

### 症状

本番環境で `google.auth.exceptions.DefaultCredentialsError` や `GOOGLE_API_KEY` が `None` になるエラーが出る場合、環境変数が設定されていない可能性が高いです。

### よくある原因

ローカルでは `.env` ファイルに API キーを書いて `python-dotenv` で読み込んでいても、本番では `.env` ファイルを配置していなかったり、そもそも `python-dotenv` が使われていなかったりします。

```python
# ❌ ローカルでは動くが、本番では GOOGLE_API_KEY が None になるケース
from dotenv import load_dotenv
import os
import google.generativeai as genai

load_dotenv()  # .env ファイルがなければ何も読み込まれない

api_key = os.environ.get("GOOGLE_API_KEY")
# 本番で .env がなければ api_key は None のまま
genai.configure(api_key=api_key)
```

### 解決策

本番環境では `.env` ファイルではなく、プラットフォーム固有の **シークレット管理機能** を使って環境変数を設定します。

```python
# ✅ 環境変数が取得できなかった場合に早期エラーを出す
import os
import google.generativeai as genai

api_key = os.environ.get("GOOGLE_API_KEY")
if not api_key:
    raise RuntimeError(
        "GOOGLE_API_KEY が設定されていません。"
        "本番環境の環境変数設定を確認してください。"
    )

genai.configure(api_key=api_key)
```

各プラットフォームでの設定方法は以下の通りです。

- **Railway / Render**: ダッシュボードの「Environment Variables」から設定
- **Heroku**: `heroku config:set GOOGLE_API_KEY=YOUR_API_KEY`
- **AWS Lambda**: 関数の「設定 → 環境変数」から設定
- **Cloud Run**: `gcloud run deploy --set-env-vars GOOGLE_API_KEY=YOUR_API_KEY`

本番環境では絶対に API キーをコードにハードコードしないようにしてください。Git リポジトリに含まれると、GitHub Secret Scanning 等で検出されます。

## エラー2: asyncio のイベントループエラー

### 症状

FastAPI や Flask の非同期ハンドラの中で Gemini API を使うと `RuntimeError: This event loop is already running` や `asyncio.exceptions.CancelledError` が発生することがあります。

### よくある原因

`google-genai` の新 SDK では非同期 API（`client.aio`）が提供されていますが、同期・非同期の混在が原因でイベントループが衝突するケースがあります。

```python
# ❌ FastAPI のハンドラ内で同期クライアントを使うと衝突する場合がある
from fastapi import FastAPI
import google.generativeai as genai

app = FastAPI()

@app.get("/chat")
async def chat(message: str):
    model = genai.GenerativeModel("gemini-2.5-flash")
    # 同期メソッドを async ハンドラから呼ぶと場合によっては問題になる
    response = model.generate_content(message)
    return {"response": response.text}
```

### 解決策

FastAPI など非同期フレームワークを使う場合は、`google-genai` SDK の **非同期クライアント** を使います。

```python
# ✅ 非同期クライアントで FastAPI と正しく統合する
from fastapi import FastAPI
from google import genai
import os

app = FastAPI()
client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

@app.get("/chat")
async def chat(message: str):
    # client.aio を使って非同期で呼び出す
    response = await client.aio.models.generate_content(
        model="gemini-2.5-flash",
        contents=message,
    )
    return {"response": response.text}
```

どうしても同期コードを非同期ハンドラから呼ばなければならない場合は、`asyncio.get_event_loop().run_in_executor()` でスレッドプールに逃がすのがおすすめです。

## エラー3: タイムアウトと接続切れ

### 症状

ローカルではすぐ返ってくる応答が、本番では `ReadTimeout` や `ConnectionError` になる場合があります。

### よくある原因

Gemini 2.5 Pro のような思考モードを使うモデルは、応答生成に時間がかかることがあります。本番サーバーの HTTP クライアントやロードバランサーのデフォルトタイムアウトが短いと、応答が返ってくる前に接続が切れてしまいます。

```python
# ❌ デフォルトタイムアウトのままだと長い応答で切れることがある
from google import genai
import os

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])
# gemini-2.5-pro は思考に時間がかかるため、タイムアウトに引っかかりやすい
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="この複雑な問題を詳しく分析してください...",
)
```

### 解決策

クライアント初期化時に明示的にタイムアウトを設定します。また、長時間かかるリクエストにはストリーミングを使うことで、接続が切れにくくなります。

```python
# ✅ タイムアウトを設定 + ストリーミングで長い応答に対応する
from google import genai
import httpx
import os

# カスタムタイムアウトを設定したHTTPクライアントを渡す
http_client = httpx.Client(timeout=httpx.Timeout(300.0))  # 5分
client = genai.Client(
    api_key=os.environ["GOOGLE_API_KEY"],
    http_client=http_client,
)

# ストリーミングで応答を受け取る（長い処理の接続切れを防げる）
for chunk in client.models.generate_content_stream(
    model="gemini-2.5-pro",
    contents="この複雑な問題を詳しく分析してください...",
):
    if chunk.text:
        print(chunk.text, end="", flush=True)
# 期待する動作: 応答が少しずつ出力され、タイムアウトで切れなくなる
```

Cloud Run を使っている場合は、デプロイ時に `--timeout` オプションも忘れずに設定してください。

```bash
# Cloud Run のリクエストタイムアウトを延長する（デフォルトは60秒）
gcloud run deploy my-service \
  --timeout=300 \
  --image=gcr.io/my-project/my-image
```

## エラー4: Docker コンテナ固有の問題

### 症状

Docker コンテナ内で `SSL: CERTIFICATE_VERIFY_FAILED` が出たり、`Name or service not known`（DNS 解決失敗）が発生するケースがあります。

### よくある原因

最小構成の Docker イメージ（`python:3.12-slim` など）では CA 証明書や DNS 設定が不完全な場合があります。また、`requirements.txt` にパッケージが抜けていてビルドは通るが実行時に失敗するケースもあります。

```dockerfile
# ✅ CA証明書を確実にインストールする Dockerfile
FROM python:3.12-slim

# CA証明書をインストール（SSL エラー対策）
RUN apt-get update && apt-get install -y \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# 環境変数はビルド時ではなく実行時に渡す（APIキーをイメージに含めない）
CMD ["python", "main.py"]
```

`requirements.txt` に必要なパッケージが明記されているかも確認してください。

```
# requirements.txt の例
google-genai>=0.8.0
httpx>=0.27.0
```

## エラー5: サーバーレス環境（Lambda・Cloud Run）での注意点

### 症状

AWS Lambda でコールドスタート後の最初のリクエストだけ失敗したり、実行時間制限（デフォルト3秒）でタイムアウトになったりします。

### 解決策

サーバーレス環境では **クライアントをグローバルスコープで初期化** することで、コンテナ再利用時の初期化コストを削減できます。また、Lambda のタイムアウト設定を必ず延長してください。

```python
# ✅ グローバルスコープで初期化してコンテナ再利用の恩恵を受ける
import os
from google import genai

# Lambda コンテナが再利用される限りクライアントも再利用される
client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

def lambda_handler(event, context):
    message = event.get("message", "")

    try:
        response = client.models.generate_content(
            model="gemini-2.5-flash",
            contents=message,
        )
        return {
            "statusCode": 200,
            "body": response.text,
        }
    except Exception as e:
        # エラーをログに残して 500 を返す
        print(f"Gemini API エラー: {e}")
        return {
            "statusCode": 500,
            "body": f"エラーが発生しました: {type(e).__name__}",
        }
```

AWS Lambda のタイムアウトは AWS コンソールまたは Infrastructure as Code（Terraform・SAM 等）から設定できます。Gemini API を使う場合は **30〜60秒** を目安に設定するとよいでしょう。

## 本番デプロイ前の確認チェックリスト

本番環境で問題が起きたとき、まず確認すべき項目をまとめます。

- 環境変数 `GOOGLE_API_KEY` がサーバー側で正しく設定されているか（`echo $GOOGLE_API_KEY` で確認）
- 使用している `google-genai` のバージョンがローカルと一致しているか（`pip show google-genai`）
- サーバー/コンテナから `generativelanguage.googleapis.com` に接続できるか
- ロードバランサーやプロキシのタイムアウト設定がリクエスト時間より長いか
- 非同期フレームワークを使っている場合、`client.aio` を使っているか
- Docker イメージに CA 証明書が含まれているか

認証エラーの詳しい対処法は[Gemini API 認証エラーの解決策](/articles/gemini-api/gemini-api-authentication-error-solutions)を、レート制限エラーの対応は[Gemini API 429エラーのトラブルシューティング](/articles/gemini-api/gemini-api-quota-429-error-troubleshooting)もあわせてご参照ください。

## 全体を振り返って

「ローカルでは動くのに本番で動かない」問題の根本は、ほぼ例外なく「環境の差異」です。最初に確認すべきは **環境変数の設定** で、これだけで半数以上のケースが解決します。

次のステップとして、デプロイ直後に `/healthz` のようなヘルスチェックエンドポイントを設けて「環境変数は読めているか」「Gemini API に疎通できるか」を自動確認する仕組みを入れておくと、問題の早期発見に役立ちます。ぜひ試してみてください。
