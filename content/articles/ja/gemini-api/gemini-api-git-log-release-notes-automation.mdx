v2.1.0 のリリース準備をしていたとき、ふと「リリースノートに、自分はどれだけ時間を使っているのだろう」と思いました。コミットを読み返し、技術の言葉を利用者の言葉に直し、日本語と英語の両方に揃えていきます。大きなリリースでは、その作業だけで 1〜2 時間かかります。

この記事は、そのとき作った「`git log` から日英のリリースノート下書きを作る」仕組みの記録です。初版は 2026 年 5 月に旧 SDK（`google-generativeai`）と `gemini-2.5-flash` で書きました。2026 年 11 月に読み直したところ、そのままでは動かない箇所があったため、新しい SDK とモデルの選び方に合わせて全面的に書き直しています。

想定している読者は、自分のアプリのリリースノートを毎回手で書いていて、コミットメッセージはそれなりに書いている方です。読み終えたときには、手元のリポジトリで下書きを出すところまで進められるはずです。

## 先に結論です

下書きを作る作業は Gemini に任せて、貼る前の確認は自分でやる——この分け方に落ち着きました。**文面を作るのは機械、ストアに出す責任は自分。** 全自動にしなかった理由は、後半の「気になった点」に書いています。

## 初版のコードが、いまは動かない理由

初版のコードは、次の三点でいまの環境には合いません。

2.5 系の停止の扱いは、別の記事に詳しく書きました。公式の表の読み方を誤ると痛い目に遭うので、モデルを固定する前に目を通していただければと思います。[gemini-2.5-flash が「no longer available」で404を返しても、公式表の停止日は未告知のままです](/articles/gemini-api/gemini-25-flash-404-no-longer-available-shutdown-date-unannounced)

## なぜ git log を入力にするのか

コミットメッセージは、何を、なぜ変えたかを、変更の直後に書いた一次情報です。リリース直前に思い出して書く文面より、はるかに正確です。

v2.1.0 では、一覧画面の `IndexOutOfBoundsException`、ライブラリ更新に伴う古い端末での起動不具合、戻るボタンの広告表示の見直しなどを、それぞれコミットに理由つきで残していました。これを利用者向けの言葉に直す作業は、構造化された断片を別の形に変換する仕事で、言語モデルの得意な領域に入ります。

**コミットメッセージの質が、そのままリリースノートの質の上限になります。** 次の節のスクリプトを動かす前に、そこだけは覚えておいてください。

## 動くスクリプト（新 SDK 版）

先に、検証できた範囲と、できていない範囲を分けておきます。

- 確認済み: `git log` の取得部分、`--dry-run` で作られるプロンプト、存在しないタグを渡したときのエラー、内部用語を検出する `check()` の動作です。使い捨てのリポジトリで実行しました。
- 未確認: `generate()` の API 呼び出し部分です。この書き直しを行った環境では、自分のキーで新しい SDK を通して実行していません。公式ドキュメントの書き方に沿っていますが、貼り付けて最初に動かすときは、後述の `--dry-run` の次に、短いタグ範囲で一度だけ試してください。

事前の準備です。

```bash
pip install google-genai
export GEMINI_API_KEY="YOUR_API_KEY"
# models.list に出るモデルIDを入れます（次の節で確かめ方を書きます）
export RELEASE_NOTES_MODEL="gemini-3.6-flash"
```

スクリプト本体です。モデル ID は環境変数から読み、出力は JSON スキーマで縛り、返ってきた文面は内部用語の混入を機械でも点検します。

```python
#!/usr/bin/env python3
"""git log からストア向けリリースノート（日英）の下書きを作る。

使い方:
  export GEMINI_API_KEY=...                       # 手元のキー（コードに書かない）
  export RELEASE_NOTES_MODEL=<models.list に出るモデルID>
  python release_notes.py v2.0.0 --version 2.1.0
  python release_notes.py v2.0.0 --version 2.1.0 --dry-run   # API を呼ばずに入力だけ確認
"""
import argparse
import json
import os
import re
import subprocess
import sys

MODEL = os.environ.get("RELEASE_NOTES_MODEL", "gemini-3.6-flash")
BANNED = re.compile(r"RecyclerView|Glide|NullPointer|IndexOutOfBounds|desugar|AGP|ViewModel|Exception", re.I)
MAX_BULLETS = 5


def get_commits(from_tag: str, to_ref: str = "HEAD") -> str:
    r = subprocess.run(
        ["git", "log", f"{from_tag}..{to_ref}", "--no-merges", "--pretty=format:- %s%n%b"],
        capture_output=True, text=True,
    )
    if r.returncode != 0:
        sys.exit(f"git log が失敗しました: {r.stderr.strip()}")
    return r.stdout.strip()


def build_prompt(commits: str, version: str) -> str:
    return (
        f"以下はアプリ v{version} のコミットメッセージです。"
        "ストアの「新機能」欄に貼るリリースノートを、日本語(ja)と英語(en)で作ってください。\n"
        "条件:\n"
        f"- 各言語 3〜{MAX_BULLETS} 項目の文字列配列にする\n"
        "- 利用者が画面で体験できる変化だけを書く\n"
        "- クラス名・ライブラリ名・例外名など内部の用語は書かない\n"
        "- コミットに無いことは書かない\n\n"
        f"コミット:\n{commits}\n"
    )


def generate(commits: str, version: str) -> dict:
    from google import genai          # pip install google-genai
    from google.genai import types

    client = genai.Client()           # GEMINI_API_KEY を環境変数から読む
    resp = client.models.generate_content(
        model=MODEL,
        contents=build_prompt(commits, version),
        config=types.GenerateContentConfig(
            response_mime_type="application/json",
            response_schema={
                "type": "OBJECT",
                "properties": {
                    "ja": {"type": "ARRAY", "items": {"type": "STRING"}},
                    "en": {"type": "ARRAY", "items": {"type": "STRING"}},
                },
                "required": ["ja", "en"],
            },
        ),
    )
    return json.loads(resp.text)


def check(notes: dict) -> list[str]:
    problems = []
    for lang in ("ja", "en"):
        items = notes.get(lang, [])
        if not 1 <= len(items) <= MAX_BULLETS:
            problems.append(f"{lang}: 項目数が {len(items)} 件です")
        for line in items:
            if BANNED.search(line):
                problems.append(f"{lang}: 内部用語が残っています -> {line}")
    return problems


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("from_tag")
    ap.add_argument("--version", required=True)
    ap.add_argument("--dry-run", action="store_true")
    a = ap.parse_args()

    commits = get_commits(a.from_tag)
    if not commits:
        sys.exit("対象のコミットがありません。タグ名を確認してください: git tag -l")
    if a.dry_run:
        print(build_prompt(commits, a.version))
        sys.exit(0)

    notes = generate(commits, a.version)
    for p in check(notes):
        print("要確認:", p, file=sys.stderr)
    for lang in ("ja", "en"):
        print(f"=== {lang} ===")
        print("\n".join(f"・{x}" for x in notes[lang]))
```

設計で意識したのは三つです。

1. **`--dry-run` を最初に置いています**。API を呼ぶ前に、モデルに渡る入力を目で確かめられます。コミットの取りこぼしや、タグの指定ミスはここで見つかります。
2. **形はスキーマで縛っています**。`ja` と `en` を文字列の配列にしているので、貼る前に項目数を数えられます。
3. **点検は機械にも任せています**。`BANNED` の正規表現は、私のアプリで実際に出てきた用語を入れています。自分のプロジェクトの言葉に差し替えてください。

使い方はこうです。

```bash
python release_notes.py v2.0.0 --version 2.1.0 --dry-run
python release_notes.py v2.0.0 --version 2.1.0
```

使い捨てのリポジトリで `--dry-run` を実行したときの出力は、次のとおりでした（コミットは 2 件）。

```
以下はアプリ v2.1.0 のコミットメッセージです。ストアの「新機能」欄に貼るリリースノートを、日本語(ja)と英語(en)で作ってください。
条件:
- 各言語 3〜5 項目の文字列配列にする
- 利用者が画面で体験できる変化だけを書く
- クラス名・ライブラリ名・例外名など内部の用語は書かない
- コミットに無いことは書かない

コミット:
- Redesign back button ad gate

- Fix RecyclerView IndexOutOfBoundsException with defensive copy
list crashed on fast scroll
```

## モデル ID は、コードに埋めない

初版では `gemini-2.5-flash` をコードに直接書いていました。いまなら環境変数にします。理由は、モデルの停止が、表に書かれた日付どおりには起きないことがあるからです。

使えるモデル ID は、キーごとに `models.list` で確かめられます。

```bash
curl -s "https://generativelanguage.googleapis.com/v1beta/models?pageSize=200" \
  -H "x-goog-api-key: $GEMINI_API_KEY" \
  | grep -o '"name": "models/[^"]*"' | sed 's|.*models/||; s|"$||' | sort
```

出てきた一覧から、軽くて安い Flash 系を選んで `RELEASE_NOTES_MODEL` に入れます。2026 年 11 月の時点で、公式の廃止一覧を読み直した範囲では、`gemini-2.0-flash` の置き換え先に `gemini-3.6-flash` が挙がっていました。ただし、これは日々変わる表です。**表に書かれた名前より、自分のキーの一覧に出てきた名前を優先してください。**

停止したモデルを呼び続けるとどうなるかは、実測を別の記事にまとめています。再試行の設計を考えているときに役立つと思います。[停止済みモデルの再試行は、成功レイテンシには出ませんでした](/articles/gemini-api/gemini-retired-model-permanent-error-queue-wait-measured)

## 実際に出た文面と、貼る前に見るところ

初版を書いた 5 月の v2.1.0 では、約 40 件のコミットから、次のような日本語の下書きが出ました（旧 SDK と 2.5 系での出力です）。

```
・壁紙の読み込みで稀に発生していたクラッシュを修正しました
・古い Android 端末での表示不具合を改善しました
・カテゴリ切り替え時の反応が向上しました
・画面上部のスライドショーの動きを滑らかにしました
・一部のアニメーションを最適化しました
```

このうち、貼る前に疑うべきなのは最後の一行です。「一部のアニメーションを最適化しました」は、コミットに裏付けがあるか分からず、利用者にも何も伝わりません。こういう曖昧な一行は、出典のコミットを探して、見つからなければ削ります。**確かめずに貼ると、書いていない改善を約束してしまうことがあります。** 下書きを人間が読む工程を残している理由は、ここにあります。

## よくある誤解を三つ

**「プロンプトに『JSON のみ』と書けば JSON が返る」**。たいていは返りますが、保証ではありません。初版で私が踏んだのは、まさにここでした。形を保証したいなら、設定側で縛るのが筋です。構造化出力の仕様は、公式の[Structured outputs](https://ai.google.dev/gemini-api/docs/structured-output)に書かれています。

**「コミットは短くてよい。AI が補ってくれる」**。補ってもらった内容は、書いていない事実になり得ます。下書きが良く見えるのは、入力が丁寧だったときだけです。

**「Pro のほうが必ず良い文になる」**。この用途では、私の体感では差が小さく、料金差のほうが目立ちました。ただし、複数のモデルを同じ入力で比べた測定はしていません。気になる方は、同じ 40 件のコミットで二つのモデルを並べて、貼れる行の数を数えるのが早いです。

## 次に詰まる一歩：多言語に広げる

日英の二言語で回り始めると、次に当たるのが言語数の壁です。三十言語に広げるときは、日英の確定版を原文にして、別の呼び出しで翻訳するほうが、一度に全部を作らせるより、用語がそろいやすいと感じています。ストア向けのメタデータを多言語で作る流れは、別の記事に書きました。

文字数の上限にも注意してください。ストアの「新機能」欄には言語ごとの上限があります（Google Play は短めです）。数値は変わることがあるので、公式のヘルプで最新の値を確認し、`check()` に文字数の点検を足しておくと安心です。

## 次の一手

まずは `--dry-run` を、直前のタグから今日までの範囲で動かしてみてください。モデルに渡る入力が、自分のコミットの質をそのまま映します。それを眺めて「これでは書けない」と感じた箇所が、次のコミットで直すべきところです。

その確認を終えてから、短いタグ範囲で一度だけ API を呼んでみてください。私も次のリリースでは、この順番で試すつもりです。
