知人の個人開発者から「寝て起きたら Gemini API の請求が数万円になっていた」という連絡を受けたことがあります。原因は、GitHub の個人リポジトリに誤ってコミットしていた API キーが、自動スキャンツールに拾われていた、というものでした。個人開発は小さなチームでもなく、自分ひとりで全工程を見なければなりません。だからこそ、漏洩の入り口を減らす「当たり前」を仕組みで押さえておくことが大切です。

この記事では、Gemini API キーを個人開発で使うときに最低限やっておきたい 5 つのチェック項目を、実際のコード例と設定手順つきでまとめました。難しい運用ではなく、30 分以内で一通り整えられる範囲に絞っています。

## なぜ個人開発では特に漏洩リスクが高いのか

企業の開発では、シークレット管理サービス、監視体制、請求アラートなどが最初から整備されています。一方で個人開発の場合、こうした仕組みを「自分で選び、自分で入れる」必要があり、省略してしまいがちです。

とくに次の 3 点は、個人開発者が実際に踏みやすい落とし穴です。

- 手元の `.env` ファイルをそのまま GitHub に push してしまう
- フロントエンドから直接 Gemini API を叩く構成にしてしまう（ブラウザ開発者ツールでキーが丸見えになる）
- 月の支出上限を設定せず、事故が起きてから気づく

これらは初心者のミスではなく、いつも開発している人でも「今日は時間がないから」と省いた瞬間に発生します。ですので、仕組みで防げる部分は仕組みに任せるのが現実的です。

## チェック 1 — `.gitignore` と環境変数の置き場所を固定する

最初のチェックは、そもそも API キーを Git の追跡対象から外すことです。プロジェクトを新規作成したら、まず以下の 3 つを決めてから最初のコミットを打ってください。

1. API キーは `.env.local`（または `.env`）に保存し、コード内に直書きしない
2. `.gitignore` に `.env*` を登録する（`.env.example` のみ例外でコミット）
3. 読み込みは `process.env.GEMINI_API_KEY` 経由に統一する

具体的には次のように書いておくと、Next.js・Vite・Node.js いずれの構成でも同じ感覚で扱えます。

```bash
# .gitignore
.env
.env.local
.env.*.local

# .env.example（こちらはコミットしてOK）
GEMINI_API_KEY=your-api-key-here
```

```ts
// Node.js / Next.js server-side からの呼び出し例
import { GoogleGenAI } from "@google/genai";

// 環境変数から読み込む。undefined のままコード内でハードコードしない
const apiKey = process.env.GEMINI_API_KEY;
if (!apiKey) {
  throw new Error("GEMINI_API_KEY is not set");
}

const ai = new GoogleGenAI({ apiKey });
```

「どうせ自分しか見ないリポジトリだから」と思っていても、将来的に OSS 化したい時や、他の開発者に手伝ってもらう時に、履歴にキーが残っていると面倒です。最初から履歴に載せないのが一番シンプルです。

もし既にコミットしてしまった場合は、キーの失効（無効化）→ 新規発行 → `.gitignore` 追加、の順で対応します。履歴から消すことにこだわるよりも、先にキーを失効させることが優先です。

## チェック 2 — クライアントサイドから直接叩かない（薄いプロキシを通す）

意外と多いのが、React や Vue の Web アプリから直接 Gemini API を呼び出している構成です。この場合、ビルド時にキーを埋め込むことになり、ブラウザの DevTools で誰でも確認できてしまいます。

個人開発でサーバーレスを使いたくない気持ちはわかるのですが、Cloudflare Workers や Vercel の API Routes、Firebase Functions のいずれかを「薄いプロキシ」として挟むだけで、キーを隠しつつ同じ体験が維持できます。

Vercel の API Route を使う例を挙げます。

```ts
// app/api/generate/route.ts (Next.js App Router)
import { GoogleGenAI } from "@google/genai";
import { NextRequest } from "next/server";

const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY! });

export async function POST(req: NextRequest) {
  const { prompt } = await req.json();

  // ここでシンプルな入力検証を挟むと事故を減らせる
  if (typeof prompt !== "string" || prompt.length > 2000) {
    return new Response("Invalid prompt", { status: 400 });
  }

  const result = await ai.models.generateContent({
    model: "gemini-2.5-flash",
    contents: prompt,
  });

  return Response.json({ text: result.text });
}
```

```ts
// フロントエンドからの呼び出しはこのプロキシ経由にする
const res = await fetch("/api/generate", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ prompt: "こんにちは" }),
});
const { text } = await res.json();
```

たったこれだけで、ブラウザのネットワークタブから API キーが見える状態は防げます。加えて、入力サイズ上限や簡易的なレート制限をプロキシ側で入れておくと、悪意のある利用者にループ呼び出しをされても被害が抑えられます。

## チェック 3 — Usage Alerts と Spend Caps を最初に設定する

API キーが万一漏れても、「月の支出上限」を先に設定しておけば、被害額を有限にできます。Google AI Studio と Google Cloud Console の両方で、以下を確認しておきましょう。

- Google Cloud Console → 「お支払い」→ 「予算とアラート」 で、月 1,000 円や月 5,000 円といった上限アラートを設定する
- 高負荷が想定されるプロジェクトは、Usage Cap（上限を超えたら停止）の活用も検討する
- Gemini API 以外のサービス（Vertex AI など）も合わせて対象にしておく

アラートは「キーが漏洩した時の保険」だけでなく、「想定より早くコストが伸びている時の気づき」としても役立ちます。個人開発では、自分が実装中のバグで無限ループを作ってしまうこともありますから、保険は自分のためでもあるのです。

関連する詳しい運用は[Gemini API の無料枠を本当に理解する：制限と料金の全体像](/articles/gemini-api/gemini-api-free-tier-complete-guide-2026)が参考になります。

## チェック 4 — キーを定期的にローテーションし、漏洩時の手順を決めておく

もう一歩踏み込むなら、API キーを 3 か月ごとなどに入れ替える「ローテーション」を習慣化することをおすすめします。人間は忘れる生き物ですので、カレンダーに登録しておくか、リマインダーに頼るのが現実的です。

合わせて、漏洩を発見した時の手順を、普段から紙ベースでも書いておくと慌てずに済みます。私の場合は次のような 4 ステップにしています。

1. Google AI Studio で該当キーを即座に削除（これが最優先）
2. 新しいキーを発行し、デプロイ先の環境変数を更新する
3. Cloud Console で直近 24 時間の利用量を確認し、不審な使い方があれば Google にレポートする
4. 漏洩経路（Git 履歴、クライアントサイド、ログ等）を特定して、再発を仕組みで防ぐ

エラー対応の基本的な考え方については[Gemini API のエラー処理：再試行パターンと本番実装](/articles/gemini-api/gemini-api-error-handling-retry-patterns)もあわせてご覧ください。

## まとめ — まず 30 分、今日のうちに 5 つだけ

API キーのセキュリティは、派手な話題ではありませんが、個人開発を続けていく上での土台です。完璧を目指す必要はなく、今日のうちに以下の 5 つだけ確認しておけば、現実的なリスクの多くを抑えられます。

- `.gitignore` に `.env*` が入っているか
- コードに API キーを直書きした箇所が残っていないか
- クライアントサイドから Gemini API を直接呼び出していないか
- Google Cloud の予算アラートが設定されているか
- 漏洩時の初動手順をどこかに書いてあるか

もし一つでも「やっていなかった」ものがあれば、今日の作業が終わる前に手を動かしておくと安心です。安全な土台ができれば、次は機能開発にもっと集中して取り組めるはずです。

API の具体的な使い方や実装パターンをさらに深めたい方は、[Gemini API クイックスタート：最初の実装で押さえる基本](/articles/gemini-api/gemini-api-quickstart)もあわせてご参照ください。実践的なセキュリティとコード設計の両輪を意識することで、個人開発でも安定した運用が実現できます。
