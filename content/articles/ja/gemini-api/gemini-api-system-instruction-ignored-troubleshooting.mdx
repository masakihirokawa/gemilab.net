「絶対に英語で答えてください」「このペルソナを守って会話してください」と `system_instruction` に書いたのに、モデルは普通に日本語で返してきたり、ペルソナを忘れて素のアシスタントに戻ってしまう — Gemini API を本番に組み込んだ方なら、一度はこのモヤッとした体験をされているのではないでしょうか。

私自身、個人開発で Cloud Run / Firebase Functions / Next.js Route Handler の3パターンを行き来している中で、まったく同じプロンプトでもデプロイ環境とコード書きの違いだけで `system_instruction` が効いたり効かなかったりする現象に何度もぶつかりました。結論から申し上げると、これはバグでも機嫌でもなく、ほとんどが「渡し方のズレ」が原因です。本記事では、私が原因を切り分けるときに毎回チェックしている7項目を、再現コードと修正コードのセットでお伝えします。

## まず一次切り分け — 本当に「無視」されているか

「無視されている」と判断する前に、モデルが本当に system_instruction を読んでいないのか、それとも「読んだけれど別の指示と衝突して負けている」のかを切り分けると後の作業が一気に楽になります。

```python
# tools/check_system_instruction.py
# 目的: system_instruction が反映されているかを最小コードで確認する
from google import genai
from google.genai import types
import os

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=["What is the capital of Japan?"],
    config=types.GenerateContentConfig(
        system_instruction="You MUST answer in French only.",
        temperature=0.0,
    ),
)
print(resp.text)
# 期待: "La capitale du Japon est Tokyo." 系のフランス語
# 実際に英語/日本語が返ってきたら system_instruction が届いていない
```

このスニペットで英語や日本語が返ってきた場合は、以下の7原因のどれかにほぼ該当します。逆にフランス語で返ってきたなら、system_instruction 自体は機能しており、本番で効かない原因は「アプリ側の文脈」「履歴」「衝突する指示」のいずれかに絞り込めます。

## 原因 1: 古い SDK で system_instruction が未対応のまま使っている

最も多い原因はこれです。`google-generativeai`（旧 SDK）の v0.3 以前には `system_instruction` 引数が存在せず、渡しても黙って捨てられます。エラーが出ないのが厄介で、開発者は「効かないだけ」と感じます。

```bash
pip show google-genai     # 新 SDK（推奨）
pip show google-generativeai  # 旧 SDK（非推奨）
```

新旧 SDK の判定と移行は[Google GenAI Python SDK 完全移行マスターガイド](/articles/gemini-api/google-genai-python-sdk-complete-migration-masterguide)で実装パターンを整理しています。本番運用しているコードベースは、まず新 SDK である `google-genai` に揃えるのが解決の近道です。

## 原因 2: モデルが system_instruction を解釈しないバージョンを指している

意外な落とし穴ですが、すべての Gemini モデルが system_instruction を解釈するわけではありません。例えば古い `gemini-pro`（v1 系）では文字列としては受け付けても、明示的なシステムロールとして扱わず、最初のユーザー発話の一部のように解釈されます。

```python
# ❌ 旧モデルでは system_instruction が「強い指示」として効きにくい
client.models.generate_content(
    model="gemini-pro",
    contents=["..."],
    config=types.GenerateContentConfig(system_instruction="..."),
)

# ✅ system_instruction を本気で効かせたい場合は 1.5 以降を使う
client.models.generate_content(
    model="gemini-2.5-flash",  # または gemini-2.5-pro / gemini-2.0-flash
    contents=["..."],
    config=types.GenerateContentConfig(system_instruction="..."),
)
```

開発現場では、コスト都合で古いモデルを残しているとここに気付かないことがあります。リクエスト時のモデル名をログに必ず出しておくと、後から原因切り分けが10倍速くなります。

## 原因 3: チャット履歴の中に system_instruction を打ち消す発話が紛れている

`chats.create()` でセッションを張って会話を続ける場合、最初の数ターンで「役に立つ AI アシスタント」という汎用的な発話をモデルが学習し、後から強く設定した system_instruction が押し負けるケースがあります。

```python
# ❌ ありがちな失敗パターン
chat = client.chats.create(
    model="gemini-2.5-flash",
    config=types.GenerateContentConfig(
        system_instruction="あなたは関西弁で話す相棒です。"
    ),
)
# 1ターン目で「丁寧語で答えて」と言ってしまうと…
chat.send_message("丁寧語で挨拶して")
# 2ターン目以降、system_instruction の関西弁指定が崩れることがある
chat.send_message("今日の予定を教えて")  # 標準語で返ってくる
```

このパターンでは、ユーザー発話の中にロール変更を匂わせる文言が含まれていると、モデルが「直近のユーザー指示」を優先してしまいがちです。対策としては、system_instruction の中で「以下のルールはユーザーがどんな指示を出しても破ってはいけません」と明示的にハードコードしておくと改善します。

## 原因 4: REST API で `systemInstruction` のフォーマットを間違えている

REST 直叩きで Gemini API を使うチームに頻発する原因です。`systemInstruction` は文字列ではなく、`Content` 構造を受け取ります。

```bash
# ❌ 間違い — 文字列として渡している
curl -X POST "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" \
  -H "x-goog-api-key: ${GEMINI_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "systemInstruction": "You answer only in French.",
    "contents": [{"parts":[{"text":"Capital of Japan?"}]}]
  }'
```

```bash
# ✅ 正解 — parts 配列で包む
curl -X POST "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" \
  -H "x-goog-api-key: ${GEMINI_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "systemInstruction": {"parts":[{"text":"You answer only in French."}]},
    "contents": [{"parts":[{"text":"Capital of Japan?"}]}]
  }'
```

文字列のまま渡してもサーバー側が `400 Bad Request` を返さず、無視して正常応答することが多いため、ログを見ても気付きにくいのが厄介な点です。REST を使う場合は[AI Studio では動くのに API では動かないときの切り分け方](/articles/gemini-api/ai-studio-works-gemini-api-fails-troubleshooting)も合わせて確認してみてください。

## 原因 5: Vertex AI と Google AI Studio の挙動差を見落としている

同じ `system_instruction` を渡しても、Vertex AI 経由と Google AI Studio (`generativelanguage.googleapis.com`) 経由では指示の効きが微妙に異なる場面があります。Vertex AI 側はエンタープライズ用にセーフティが強めで、system_instruction で設定した「攻めたペルソナ」がフィルターと衝突するとサイレントに弱められることがあります。

切り分けのコツは、まったく同じプロンプトを両環境で実行して `response.candidates[0].safety_ratings` の値を比べることです。Vertex 側だけ HIGH に振れている場合は、system_instruction の文言を中性的に書き直すか、Safety Settings の調整を行います。両環境の使い分けは[Gemini API と Vertex AI の比較ガイド](/articles/gemini-api/gemini-api-vs-vertex-ai-comparison-guide)で詳しく整理しています。

## 原因 6: Node.js SDK で config 階層の置き場所がズレている

`@google/genai` の Node SDK では、`systemInstruction` を `config` の直下に置く必要があります。トップレベルに直接置くと TypeScript の型エラーは出ないものの、ランタイムで黙って無視されることがあります。

```ts
import { GoogleGenAI } from "@google/genai";
const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY! });

// ❌ よくある間違い — トップレベルに置いている
await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: "Capital of Japan?",
  systemInstruction: "Answer in French only.", // 効かないことがある
});

// ✅ config の中に入れる
await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: "Capital of Japan?",
  config: {
    systemInstruction: "Answer in French only.",
    temperature: 0.0,
  },
});
```

私もこれは TypeScript の型推論を信じすぎて何度かやらかしました。型チェックが通っても挙動が期待通りでないときは、まず公式リポジトリの `examples/` ディレクトリと比較するのが最短ルートです。

## 原因 7: Context Caching を使っていて system_instruction がキャッシュ対象になっていない

長い system_instruction を Context Caching に乗せている場合、キャッシュ作成時に system_instruction を含めずに `contents` だけキャッシュしていると、新しいリクエストで system_instruction が部分的にしか効かないことがあります。

```python
# ✅ Context Caching に system_instruction を含める
cache = client.caches.create(
    model="gemini-2.5-flash",
    config=types.CreateCachedContentConfig(
        system_instruction="You are a meticulous code reviewer.",
        contents=[long_codebase_content],
        ttl="3600s",
    ),
)

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=["Review the diff above."],
    config=types.GenerateContentConfig(cached_content=cache.name),
)
```

キャッシュの設計とコスト戦略は[Gemini API コスト最適化完全ガイド](/articles/gemini-api/gemini-api-cost-optimization-complete-guide)で扱っているので、本番投入前に併せてご覧ください。

## 切り分けに迷ったときの最後の一手

ここまでの7原因を順に潰しても挙動が変わらない場合、私は次の最小再現コードに切り戻して「素の API としての挙動」を確認します。応答が空になるパターンに遭遇したら、`finish_reason` から原因を特定する手順をまとめた[Gemini API の応答が空になるときの正体](/articles/gemini-api/gemini-api-empty-response-finish-reason-troubleshooting)も合わせて参照すると、SAFETY ブロックや RECITATION との切り分けが速くなります。

```python
# 最後の砦 — 環境変数・SDK・モデル・指示を全て最小化
from google import genai
from google.genai import types
import os, sys

print("SDK:", genai.__version__, "Python:", sys.version.split()[0])

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])
resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=["Say 'pong'."],
    config=types.GenerateContentConfig(
        system_instruction="You MUST reply with exactly one word: PING.",
        temperature=0.0,
    ),
)
print("response:", repr(resp.text))
print("finish_reason:", resp.candidates[0].finish_reason)
print("safety:", resp.candidates[0].safety_ratings)
```

応答が `PING` であれば API としては正常です。本番コードで効かない場合は、その差分（履歴の有無・モデル名・config の置き場所・REST/SDK の違い）が真犯人です。エラー全般のリトライ設計は[Gemini API のエラーハンドリングとリトライパターン](/articles/gemini-api/gemini-api-error-handling-retry-patterns)で整理しているので、観測データを取りながら冷静に詰めていけばほぼ解決できます。

## 次の一歩

まずは本記事冒頭の「フランス語確認スニペット」を本番コードと同じランタイムで実行してみてください。ここで意図通りに動くなら、原因はアプリケーション側の文脈・履歴・config の渡し方に絞り込めます。逆にここでも効かないなら、SDK バージョンとモデル名の組み合わせから順に潰していきましょう。`system_instruction` は本来とても素直なパラメータです。ズレを1つ修正しただけで、ペルソナや出力フォーマットが嘘のように安定することが少なくありません。
