Gemini 2.0 Flash は低価格のまま十分な品質を出すモデルで、RAG（Retrieval-Augmented Generation）との相性が良いと私は感じています。ただし「安いから気にしなくていい」とは残念ながらなりません。ユーザーが増えてアクセスが線形に伸びると、月額請求も線形に伸びます。そして気づくと「Flash なのに月〇万円」という予算会議の議題になってしまう — これは私自身が通った道です。

ここではGemini 2.0 Flash を使った RAG のコストを「3層のキャッシュ」で段階的に下げる設計を共有します。最初の1層を入れるだけでコストが 30% 下がり、3層すべてで組むと半分以下になるケースも珍しくありません。実装は意外と素直で、既存の RAG に割り込ませる形で導入できます。

## なぜ「3層」なのか

RAG の1リクエストは、おおよそ次の順でコストを発生させます。

1. **クエリ埋め込み**: ユーザーの質問をベクトル化する API コール
2. **ベクトル検索**: ベクトル DB に問い合わせる（自前 or Managed）
3. **プロンプト生成**: 取得した文脈と質問をモデルに投げる

コスト構造を見ると、2と3がほとんどを占めます。3層キャッシュはこの各段階でヒット率を積み上げていく設計です。

- **L1: レスポンスキャッシュ** — 同じ質問が来たら LLM をスキップして即返す
- **L2: リトリーバルキャッシュ** — 意味的に近い質問で同じ文脈が使えるなら検索をスキップする
- **L3: 埋め込みキャッシュ** — まったく同じクエリ文字列の埋め込みを再計算しない

上から順にヒットすればコスト削減効果が大きい設計です。L1 が効けばすべての API が節約でき、L3 は埋め込み計算だけが節約される、という段階構造になっています。

## L1: レスポンスキャッシュ — 最も効く一手

最初に入れるべきは「まったく同じ質問に対する回答キャッシュ」です。RAG では驚くほど多くのユーザーが似た質問をします。FAQ 寄りのアプリでは 30% 以上がキャッシュヒットすることもあります。

```python
import hashlib
import json
import redis

r = redis.Redis(decode_responses=True)
CACHE_TTL = 60 * 60 * 24 * 7  # 7日間

def make_cache_key(query: str, filters: dict) -> str:
    """クエリとフィルタの組み合わせから決定的にキーを作る。"""
    payload = json.dumps({"q": query.strip().lower(), "f": filters}, sort_keys=True)
    return "rag:resp:" + hashlib.sha256(payload.encode()).hexdigest()

def rag_query_with_l1(query: str, filters: dict):
    key = make_cache_key(query, filters)
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    # キャッシュミス — 実際に RAG を走らせる
    result = run_rag_pipeline(query, filters)
    r.setex(key, CACHE_TTL, json.dumps(result))
    return result
```

3つのポイントがあります。第一に、大文字小文字と空白を正規化する（`query.strip().lower()`）。これがないと「python とは？」と「Python とは？」が別のキャッシュになります。第二に、`filters` もキーに含める。ユーザーごとの権限やテナントが違えば回答も違うからです。第三に、TTL を必ず設定する。ドキュメントが更新されたのに古い回答を返し続けると信頼を失います。

**注意点**: 機密情報を含むレスポンスをキャッシュする場合、Redis を暗号化した状態で保存する、キャッシュキーにユーザー ID を含めるなどのアクセス制御が必要です。私は以前、テナント ID をキーに含め忘れて別のテナントの回答が混ざる事故を起こしかけたことがあります。設計段階でこの問題を潰しておくのが一番です。

## L2: リトリーバルキャッシュ — 意味的に近い質問をまとめる

L1 は完全一致でしか効きません。「Python の型ヒントの書き方」と「Python で type hints をつけるには」は別のキーになるので、両方で LLM を呼ぶことになります。ここで L2 の出番です。

L2 はクエリの埋め込みベクトルを使って「意味的に近い過去のクエリ」を探し、十分に近ければ検索結果を再利用します。埋め込みキャッシュ用の小さなベクトル DB を別に立て、L1 でミスしたときだけチェックします。

```python
from typing import Optional
import numpy as np

# 別の軽量ベクトル DB（FAISS/Chroma）に「クエリベクトル → 検索結果」を保存する
QUERY_VECTOR_INDEX = load_query_index()

SIMILARITY_THRESHOLD = 0.92  # このコサイン類似度以上なら「同じクエリ」扱い

def l2_lookup(query_embedding: np.ndarray) -> Optional[dict]:
    """意味的に近い過去のクエリから検索結果を再利用する。"""
    result = QUERY_VECTOR_INDEX.query(query_embedding, top_k=1)
    if not result.matches:
        return None
    top = result.matches[0]
    if top.score < SIMILARITY_THRESHOLD:
        return None
    return top.metadata  # 過去の検索結果（文脈のリスト）

def rag_query_with_l1_l2(query: str, filters: dict):
    # L1: レスポンスキャッシュ
    cached = r.get(make_cache_key(query, filters))
    if cached:
        return json.loads(cached)

    # 埋め込みを取得（これは L3 でさらにキャッシュされる）
    qvec = embed_query(query)

    # L2: 類似クエリの検索結果を再利用
    l2_hit = l2_lookup(qvec)
    if l2_hit is not None:
        docs = l2_hit["docs"]
    else:
        docs = vector_search(qvec, filters)
        # 将来の再利用のために保存
        QUERY_VECTOR_INDEX.upsert([(str(uuid.uuid4()), qvec, {"docs": docs})])

    # LLM で回答生成（これは L1 でキャッシュされる次の回から効く）
    answer = generate_with_context(query, docs)
    result = {"answer": answer, "docs": docs}
    r.setex(make_cache_key(query, filters), CACHE_TTL, json.dumps(result))
    return result
```

類似度閾値 0.92 は私のドメイン（技術的な Q&A）での実測値です。アプリケーションによって最適値は違うので、0.85〜0.95 の間で自分のデータで試してみてください。閾値を下げすぎると「似ているけど別の質問」に古い文脈で答えてしまい、品質が下がります。

「検索はスキップできたけど回答生成はスキップできない」のがもどかしいところですが、ベクトル検索 API を呼ばない分だけでもコストは下がります。Managed なベクトル DB では検索回数でも課金されるため、効果は侮れません。

## L3: 埋め込みキャッシュ — 最も軽いが効く層

L3 は埋め込みベクトルの計算結果をそのままキャッシュします。同じ文字列を再度埋め込まないためだけの単純な層ですが、FAQ サイトや入力補完のように「同じ語が何度も入力される」アプリでは地味に効きます。

```python
def embed_query(query: str) -> np.ndarray:
    """埋め込みを Redis にキャッシュしてから返す。"""
    normalized = query.strip().lower()
    cache_key = "rag:emb:" + hashlib.sha256(normalized.encode()).hexdigest()
    cached = r.get(cache_key)
    if cached:
        return np.frombuffer(bytes.fromhex(cached), dtype=np.float32)
    vec = genai_embed(normalized)  # 実際の API コール
    r.setex(cache_key, CACHE_TTL, vec.tobytes().hex())
    return vec
```

シンプルですが、埋め込み API は 1M トークンあたりの単価が意外と無視できません。1日1万クエリのアプリで 40% がリピート語句なら、月に数千〜数万円の差になります。

## ヒット率を観測する

キャッシュ設計は「どれだけヒットしているか」を測らないと改善できません。各層で必ずメトリクスを出しておきます。

```python
from collections import Counter
stats = Counter()

def record_hit(layer: str):
    stats[f"hit:{layer}"] += 1

def record_miss(layer: str):
    stats[f"miss:{layer}"] += 1

def dump_stats():
    total = sum(stats.values()) or 1
    for k, v in sorted(stats.items()):
        pct = v / total * 100
        print(f"{k}: {v} ({pct:.1f}%)")
```

私のプロダクトでは次のような数字が出ています（1週間分の運用データ）。

- L1 ヒット率: 34%
- L2 ヒット率: 18%（L1 ミス中の）
- L3 ヒット率: 42%（L2 まで行った場合の埋め込みキャッシュ）

L1 だけで 34% の LLM 呼び出しが消えていて、これが一番効果的です。L2 は閾値のチューニングでヒット率が上下するので、運用しながら調整するのがよいです。

## よくある落とし穴

**古いデータを返し続ける**: ドキュメント更新時に L1 キャッシュを無効化する仕組みを入れ忘れると、古い回答を返し続けます。私はドキュメント ID を L1 のメタデータに含め、更新時にそのドキュメントを参照している回答をまとめて破棄する構造にしています。

**テナント混線**: キャッシュキーにテナント ID を含め忘れると、別テナントの情報が漏れる事故になります。L1・L2 ともにキーにテナント ID を必ず入れてください。

**埋め込みモデルの切替時**: 埋め込みモデルをバージョンアップしたとき、既存の L2 インデックスのベクトルが新しい埋め込みと互換性を失います。モデルのバージョンをキーに含めるか、切替時に全 L2 を破棄する運用が必要です。

## まとめ

Gemini 2.0 Flash のコスト削減は「モデルを変える」以上に「キャッシュを入れる」で大きく動きます。まずは L1（レスポンスキャッシュ）を1週間入れてみてください。ヒット率を見るだけで、あなたのアプリの RAG コストがどれだけ最適化の余地を持っているかがはっきり分かるはずです。その数字が出てくれば、L2・L3 に投資する判断もしやすくなります。
