## ニッチ SaaS という選び方 — なぜ「広く浅く」を避けるか

Gemini API で個人開発の SaaS を作るとき、最初の落とし穴は「**広く浅く使えるサービス**」を狙ってしまうことです。AI チャット、AI ライティング、AI コーディング支援といった汎用ジャンルは、すでに大手競合が無料に近い価格で提供しているため、個人開発で勝負するのは事実上不可能です。

これに対して、私が長年運営してきて「効く」と確信しているのは、**特定の職業・趣味・ライフスタイルに特化したニッチ SaaS**です。具体例を挙げると、「学習塾の講師向け、生徒の答案を AI で添削する補助ツール」「同人誌作家向け、自分の文体を保ちながら誤字脱字をチェックするツール」「個人不動産投資家向け、物件情報の 1 行サマリを自動生成するツール」など、ターゲットが明確に絞れて、かつ既存の大手汎用 AI では手が届かないジャンルです。

この記事では、Gemini API でこの種のニッチ SaaS を**月5万円規模（月額¥1,000 × 50名前後の継続）まで育てるための設計図**を、私自身の運用パターンを抜粋しながらご紹介します。月100万円規模の話ではなく、個人開発でリアルに到達できる数字を扱います。

## アーキテクチャの全体像 — 個人開発で運用できる最小構成

ニッチ SaaS のための最小構成は、私の場合は次のようになります。

- **フロントエンド**: Next.js 16 + Cloudflare Pages
- **API レイヤー**: Cloudflare Workers
- **AI 呼び出し**: Gemini API（2.5 Flash または Flash Lite）
- **状態管理**: Cloudflare KV
- **課金**: Stripe Checkout（Subscription mode）
- **メール**: Resend

これらを全部組み合わせても、月の固定費は¥0〜¥1,000程度に収まります。Cloudflare の無料枠と Gemini API の Free Tier、Stripe の決済手数料（売上の3.6%程度）以外には、ほとんどお金が出ていきません。

### なぜ Cloudflare Workers なのか

ニッチ SaaS では、Gemini API のレスポンス時間を吸収しつつ、ユーザーへの応答を素早く返す必要があります。Cloudflare Workers のエッジ実行は、ユーザーの近い場所からリクエストを受けて、そこから Gemini API にルーティングするだけで、体感速度が驚くほど変わります。

加えて、Workers は KV や Durable Objects といったストレージとの統合が深いので、ユーザーのクォータ管理や課金状態の保存も同じプラットフォームで完結します。これは個人開発の運用負担を大きく下げてくれる選択です。

## Free Tier 卒業のタイミングを「ユーザー数」で決めない

多くの方が誤解しているのは、「ユーザーが Free Tier の上限を超えたら有料 Tier に切り替える」という考え方です。これは正しいようで、実は**収益化観点では遅すぎる**判断基準です。

正しい判断軸は、**収益が Gemini 有料 Tier の月額料金を超えたら、その時点で有料 Tier に切り替える**ことです。具体的には次のような順序になります。

第一フェーズ（収益¥0〜¥10,000）: Free Tier のみで運用。コスト¥0、利益＝収益。

第二フェーズ（収益¥10,000〜¥30,000）: Free Tier の上限に近づいてきたら、Pay-as-you-go の有料 Tier に切り替える。月の API コストは¥1,000〜¥3,000程度。

第三フェーズ（収益¥30,000〜¥50,000）: Context Caching と日次クォータを本格導入。月の API コストは¥3,000〜¥5,000で頭打ちにできる。

このフェーズ分けの肝は、**収益が増えるにつれて、API コストの増加率を意図的に抑える設計に切り替える**ことです。

## コスト爆発を防ぐ3層クォータ設計

月5万円規模になってくると、悪意あるユーザーまたは想定外のヘビーユーザー1名で、月の API コストが2〜3倍に跳ね上がる事故が起きやすくなります。これを防ぐのが、**ユーザー単位 × 日次 × 月次**の3層クォータです。

### 実装の骨格

```typescript
const DAILY_CAP = 50_000;
const MONTHLY_CAP = 1_000_000;
const GLOBAL_DAILY_BUDGET = 500_000;

async function quotaGate(env: Env, userId: string, estimatedTokens: number) {
  const today = new Date().toISOString().slice(0, 10);
  const month = today.slice(0, 7);

  // Layer 1: 個人 × 日次
  const userDayKey = `q:u:${userId}:${today}`;
  const userDayUsed = parseInt((await env.KV.get(userDayKey)) ?? "0", 10);
  if (userDayUsed + estimatedTokens > DAILY_CAP) {
    throw new QuotaError("日次上限に達しました");
  }

  // Layer 2: 個人 × 月次
  const userMonthKey = `q:um:${userId}:${month}`;
  const userMonthUsed = parseInt((await env.KV.get(userMonthKey)) ?? "0", 10);
  if (userMonthUsed + estimatedTokens > MONTHLY_CAP) {
    throw new QuotaError("月次上限に達しました");
  }

  // Layer 3: 全体 × 日次（緊急時の最後の砦）
  const globalKey = `q:g:${today}`;
  const globalUsed = parseInt((await env.KV.get(globalKey)) ?? "0", 10);
  if (globalUsed + estimatedTokens > GLOBAL_DAILY_BUDGET) {
    throw new QuotaError("本日のサービス利用枠が満杯です");
  }

  // 全層通過したら加算
  await Promise.all([
    env.KV.put(userDayKey, String(userDayUsed + estimatedTokens), { expirationTtl: 60 * 60 * 26 }),
    env.KV.put(userMonthKey, String(userMonthUsed + estimatedTokens), { expirationTtl: 60 * 60 * 24 * 32 }),
    env.KV.put(globalKey, String(globalUsed + estimatedTokens), { expirationTtl: 60 * 60 * 26 }),
  ]);
}
```

`GLOBAL_DAILY_BUDGET` は緊急時の最後の砦です。これがないと、想定外のバズや攻撃で月のコストが10倍に跳ねる事故を防げません。

## Context Caching を最大活用する設計

ニッチ SaaS のユースケースの多くは、「**特定のドメインに関する長いシステムプロンプトを、毎リクエスト送る**」パターンです。たとえば添削ツールであれば「この採点基準に従って答案を採点してください」という長いルール文を毎回送ります。これは Context Caching が劇的に効く典型例です。

### キャッシュの粒度をどうするか

Context Caching を効果的に使うコツは、**キャッシュ単位を「全ユーザー共通」と「ユーザー個別」に分ける**ことです。

```typescript
// 全ユーザー共通: 採点基準・ガイドライン・出力フォーマット
const sharedCache = await ai.caches.create({
  model: "gemini-2.5-flash",
  contents: SHARED_SYSTEM_PROMPT,
  ttl: "86400s", // 24時間
});

// ユーザー個別: 過去の採点履歴・好み
const userCache = await ai.caches.create({
  model: "gemini-2.5-flash",
  contents: userSpecificContext,
  ttl: "3600s", // 1時間
});

const response = await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: userInput,
  cachedContent: [sharedCache.name, userCache.name],
});
```

共通キャッシュは長めの TTL、個別キャッシュは短めの TTL にするのが運用上のバランスです。

## Stripe 統合 — 個人開発に最適な最小構成

ニッチ SaaS の課金は、Stripe Checkout の Subscription モードを単純に使うだけで十分です。複雑な課金ロジックは最初から組まないのがコツです。

### Checkout Session の作成

```typescript
const session = await stripe.checkout.sessions.create({
  mode: "subscription",
  line_items: [
    {
      price_data: {
        currency: locale === "ja" ? "jpy" : "usd",
        recurring: { interval: "month" },
        unit_amount: locale === "ja" ? 1000 : 9,
        product_data: {
          name: locale === "ja" ? "Pro プラン" : "Pro Plan",
          description: locale === "ja"
            ? "AI 添削機能の月額利用"
            : "Monthly access to the AI proofreader",
          images: ["https://example.com/images/stripe-product.png"],
        },
      },
      quantity: 1,
    },
  ],
  success_url: `${origin}/${locale}/thanks?session_id={CHECKOUT_SESSION_ID}`,
  cancel_url: `${origin}/${locale}/pricing`,
  metadata: { plan_type: "pro", locale },
});
```

`product_data.images` を必ず指定することで、Stripe Checkout のページに商品画像と説明文が表示されます。これがないと、Checkout 画面が無味乾燥に見えてコンバージョン率が下がります。

### Webhook の最小実装

```typescript
if (event.type === "checkout.session.completed") {
  const session = event.data.object as Stripe.Checkout.Session;
  const email = session.customer_email ?? session.customer_details?.email;
  if (email) {
    await env.KV.put(
      `member:${email}`,
      JSON.stringify({ plan: "pro", expiresAt: Date.now() + 31 * 24 * 60 * 60 * 1000 }),
      { expirationTtl: 60 * 60 * 24 * 35 }
    );
  }
}

if (event.type === "invoice.paid") {
  const invoice = event.data.object as Stripe.Invoice;
  const email = invoice.customer_email;
  if (email) {
    await env.KV.put(
      `member:${email}`,
      JSON.stringify({ plan: "pro", expiresAt: Date.now() + 31 * 24 * 60 * 60 * 1000 }),
      { expirationTtl: 60 * 60 * 24 * 35 }
    );
  }
}
```

`invoice.paid` を独立して処理することで、毎月の自動更新時に権限が延長されます。これを忘れると、2ヶ月目以降のユーザーが「会員なのに使えない」状態に陥ります。

## ニッチ SaaS 特有の継続率改善 — 「ジャンルへの愛」を可視化する

ニッチ SaaS で月5万円を維持するうえで、もっとも重要なのは継続率です。汎用 SaaS と違うのは、**ユーザーがそのジャンルに対して強い愛着を持っている**点です。この愛着を可視化する設計が、解約防止に直結します。

### 「あなたの記録」を毎月メールで送る

たとえば添削ツールなら、「今月、あなたは78件の答案を添削しました。先月と比べて+12件です。先月のあなたが一番苦労していた『生徒の答案の意図を汲み取る』点について、今月は精度が上がっています」のような、個別化された月次サマリをメールで送ります。

このメールを送ったあとの解約率は、送らなかった場合と比べて30〜40%下がる傾向があります。Gemini API を使えば、こうした個別メッセージの自動生成は驚くほど安価に実装できます。

```typescript
async function generateMonthlyReview(env: Env, userId: string, stats: UserStats) {
  const prompt = `次のユーザー統計から、励ましと振り返りの月次メッセージを200字以内で生成してください。\n\n${JSON.stringify(stats, null, 2)}`;
  return await callGemini(env, prompt, { maxOutputTokens: 256 });
}
```

## ニッチ SaaS が陥りがちな落とし穴

最後に、私自身が運用してきて何度もハマった、ニッチ SaaS 固有の落とし穴を3つ挙げておきます。

第一は、**ニッチを狭めすぎてユーザーが集まらない**問題です。「学習塾講師の中でも、特に小学校4年生の算数を教えている個人塾の先生だけ」のように細分化しすぎると、市場が小さすぎて月5万円に届きません。最初は「1ジャンル全体」をターゲットにし、運用の中で自然にニッチに絞り込むのが正解です。

第二は、**プロンプトの品質が API コストを左右する**問題です。「この答案を採点してください」だけのプロンプトと、「この採点基準に従い、JSON 形式で次の項目を出力してください」と明示的に出力フォーマットを指定するプロンプトでは、出力トークン数が3〜5倍違うことがあります。

第三は、**ユーザーからのフィードバックを聞きすぎる**問題です。ニッチ SaaS のユーザーは熱心なので、要望をどんどん挙げてくれます。それに全部応えていると、ニッチの軸がブレてしまい、結果として誰のためのサービスか分からなくなります。**核となる5機能だけに集中し、それ以外は「次のバージョンで検討します」で受け流す**勇気が必要です。
