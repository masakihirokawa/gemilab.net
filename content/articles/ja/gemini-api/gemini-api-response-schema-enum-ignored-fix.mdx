壁紙アプリに届いたユーザー投稿画像を「landscape／portrait／abstract／other」の4つに振り分けていた夜のことです。`enum` に4値を書いたのに、ログを眺めると `"natural"` や `"scenery"` が混ざっておりました。仕様変更を疑って同じ画像を何度も投げ直しましたが、原因は仕様ではなく、私の「schema を書けば守られるはず」という思い込みのほうでした。

分類ミスは、そのまま検索結果の並びの乱れとして利用者の目に触れます。同じ症状に当たった方が短時間で手を打てるよう、再現条件、原因の見立て、3つの対処、そして「自分のデータで混入率を測る」ための小さな計測スクリプトを書き残します。

## 症状の最小再現

次のコードで、本来は4値しか返らないはずの `label` に想定外の値が混ざります。

```python
from google import genai
from pydantic import BaseModel
from typing import Literal

MODEL = "gemini-2.5-flash"  # 使う前に公式の deprecations ページで提供状況を確認してください

class Classification(BaseModel):
    label: Literal["landscape", "portrait", "abstract", "other"]
    confidence: float

client = genai.Client()
response = client.models.generate_content(
    model=MODEL,
    contents=["Classify this wallpaper image.", image_part],
    config={
        "response_mime_type": "application/json",
        "response_schema": Classification,
    },
)

result = Classification.model_validate_json(response.text)
# 期待: label は4値のいずれか
# 実際: ときどき "natural" や "scenic" が返り、pydantic.ValidationError
```

`Literal` で縛っているのに `ValidationError` が飛ぶ——この食い違いに気づいたのは、本番に近いデータで流してからでした。サンプル数枚では、まず再現しません。

## なぜ enum が守られないのか

公式の構造化出力のページには、出力は構文として有効な JSON になる一方で「値は必ずアプリケーション側で検証する」こと、そして schema には合っていても意味として誤った出力への備えを持つことが書かれています。schema は形を整える力は強くても、意味まで保証する約束ではない、という読み方になります。

内部のデコードの仕組みは公開されていないため、断言は避けます。そのうえで、私の手元では次の3条件が重なるときに外れ値が目立ちました（傾向であり、保証ではありません）。

ここで一度、手を止めました。「減った気がする」では判断できないからです。そこで、対処に入る前に、混入率を数字で見るための計測から始めました。

## 対処0: まず自分のデータで混入率を測る

プロンプトを直す前後で比べられるよう、同じ画像セットを複数回流して、許可値の外に出た割合を数えるだけの小さなスクリプトです。

```python
from collections import Counter

ALLOWED = ["landscape", "portrait", "abstract", "other"]

def measure_drift(images, make_contents, runs: int = 3):
    """make_contents(image) -> contents を返す関数。プロンプト違いを比較するときに差し替えます。"""
    total, drift = 0, 0
    bad_values = Counter()
    for image in images:
        for _ in range(runs):
            response = client.models.generate_content(
                model=MODEL,
                contents=make_contents(image),
                config={
                    "response_mime_type": "application/json",
                    "response_schema": Classification,
                },
            )
            total += 1
            try:
                label = Classification.model_validate_json(response.text).label
            except Exception:
                # ValidationError のときは生の値を拾って集計する
                import json
                label = json.loads(response.text).get("label", "<missing>")
            if label not in ALLOWED:
                drift += 1
                bad_values[label] += 1
    return {"total": total, "drift": drift, "rate": drift / total, "values": bad_values.most_common(5)}
```

出力の `values` が重要です。外れ値が `scenic` のような類義語ばかりなら、対処1（定義の明示）が効く型です。`<missing>` が多いなら、enum ではなく別の schema 違反を疑う段階です。

## 対処1: プロンプトに許可値と定義を置く

いちばん手応えがあったのは、schema に加えて、プロンプト本文に許可値と各ラベルの定義を置くことでした。

```python
prompt = f"""\
Classify the wallpaper image into exactly one of these labels:
- landscape (natural scenery, mountains, sea, sky)
- portrait (a person or animal as the main subject)
- abstract (pattern, gradient, geometric art)
- other (anything that does not fit the above)

Return JSON. The "label" field MUST be exactly one of: {ALLOWED}.
Do NOT invent new labels.
"""
```

「許可値の意味的な定義」と「逸脱の禁止」を言葉にして渡すだけで、ラベルの境界をモデルが推測する余地が減ります。schema との二重書きは冗長に見えますが、先ほどの `measure_drift` に `lambda image: [prompt, image]` を渡して前後を比べれば、効果が自分のデータで確かめられます。

## 対処2: 受け取り側で検証し、リトライは1回まで

それでも外れることはあるため、受け取った値を検証して、不一致のときだけ自己訂正の指示を1回だけ投げます。上限を設けないリトライは、費用が静かに膨らむ原因になります。

```python
def classify_with_retry(image_part, max_retry: int = 1) -> Classification:
    last_text = ""
    for attempt in range(max_retry + 1):
        instruction = prompt if attempt == 0 else (
            f"Your previous label '{last_text}' was not in {ALLOWED}. "
            f"Re-classify using ONLY these four labels."
        )
        response = client.models.generate_content(
            model=MODEL,
            contents=[instruction, image_part],
            config={
                "response_mime_type": "application/json",
                "response_schema": Classification,
            },
        )
        last_text = response.text
        try:
            result = Classification.model_validate_json(last_text)
            if result.label in ALLOWED:
                return result
        except Exception:
            pass

    # フォールバック: other 扱い（パイプラインを止めない）
    return Classification(label="other", confidence=0.0)
```

最後まで弾けなかった値は `other` に倒し、`confidence=0.0` で「確信のない分類」と分かる印を付けておきます。あとから該当行だけ拾い直せるようにするためです。

## 対処3: SDK のバージョン差を疑う

`google-genai` は更新が速く、`response_schema` に Pydantic のモデルを直接渡せるかどうかなど、バージョンによって受け付ける形が変わってきました。CI や本番の環境だけ古いバージョンのまま、ということは珍しくありません。

```bash
pip show google-genai | grep Version
pip install --upgrade google-genai
```

「手元では出ないのに本番だけ出る」ときは、プロンプトより先に、環境ごとの SDK のバージョンを見比べてみてください。

## 外れ値を早く見つけるログ

混入を完全にゼロにはできないため、割合を観測できる状態にしておきます。

```python
def log_classification(label: str):
    print({
        "event": "enum_classification",
        "label": label,
        "is_drift": label not in ALLOWED,
    })
```

出力先は Cloud Logging でも BigQuery でも構いません。割合が急に動いたときは、次の3つのどれかであることが多いと感じています。

- モデルのバージョンやスナップショットの変更
- 入力の分布の変化（新しいシリーズの画像を入れたとき、など）
- SDK の更新

## 似た症状との切り分け

enum の逸脱は、ほかの schema 違反と見た目が似ており、私も取り違えて時間を使いました。

- `response_mime_type` の未指定：JSON ではなく Markdown のコードフェンス付きで返ってきます
- ネストした `oneOf`：子フィールドだけ第一候補に寄ることがあります
- `propertyOrdering` の未指定：長い JSON でフィールド順が揺れます

まず `response.text` を加工せずに表示して、JSON か Markdown か、enum の逸脱か順序の乱れかを見分けてください。順序の問題は [propertyOrdering でフィールド順を安定させる方法](/articles/gemini-api/gemini-structured-output-propertyordering-field-order-stability) に、本番での検証の組み方は [responseSchema の検証を本番で回す設計](/articles/gemini-api/gemini-api-response-schema-validation-production) にまとめています。

**schema は形の約束で、意味の責任はプロンプトと受け取り側が持ちます。** この線引きを決めてから、分類まわりの障害対応はずいぶん落ち着きました。まずは `measure_drift` を30枚ほどの画像で一度だけ回し、いまの混入率を数字で控えておくところから始めていただければと思います。
