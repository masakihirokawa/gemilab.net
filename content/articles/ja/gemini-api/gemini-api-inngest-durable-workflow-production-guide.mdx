サンプルを手元の Next.js に貼って `npm install` したら、最新の `inngest` が入りました。ダッシュボードを開く前に、エディタがすでに赤い波線だらけになっていました。2 番目の引数に置いたトリガーが「型が合わない」と言われ、`EventSchemas` は見つからないと言われる——書いた当時の私は v3 のつもりで、npm の向こうではもう v4 が標準になっていたのです。

最初のうち、私はエラーをひとつずつ潰す方向に流れていました。型を `any` で逃がし、動いたところで満足しかけたのですが、翌朝ログを読み返すと、ローカルの Dev Server ではなく Cloud モードで起動しようとして署名鍵を探していました。**動いて見えることと、意図したモードで動いていることは別物**だと気づいたのは、そのときでした。

このガイドは、その書き直しの記録を土台にしています。Gemini API を含む長時間ジョブを「途中で落ちても、払ったトークンを捨てずに再開できる」かたちで組むための、2026年11月時点で動く構成をお伝えします。

モデルについては、公式の廃止スケジュールに、`gemini-2.5-pro` への API リクエストは 2026年12月1日から `gemini-3.8-flash` へ、`gemini-2.5-flash` は `gemini-3.5-flash-lite` へ自動で転送され、転送先の料金で請求されると明記されています。初版のサンプルは 2.5 系で書いていたため、今回すべて書き換えました。モデル ID は環境変数に逃がしておくと、次の切り替えでもコードに触れずに済みます。

## なぜ Gemini API には durable execution が必要なのか

durable execution（永続実行）の要点は、**関数の途中の状態をエンジンが保存し、失敗したステップだけをやり直せる**ことです。Inngest のほかに Temporal や Restate が同じ考え方で作られています。

Gemini API を本番で呼んでいると、次のような場面に何度も出会います。

- 瞬間的な HTTP 429（`RESOURCE_EXHAUSTED`）で、リトライしないと処理が止まる場面
- ストリーミングが途中で切れ、最後の chunk だけが届かない場面
- 動画や PDF の解析中にタイムアウトする場面
- Function Calling の戻り値で別の API を呼ぶ箇所が、Gemini とは無関係に落ちる場面

`try/catch` と `setTimeout` で素朴にリトライを書くと、**リトライのたびに、成功済みの呼び出しのトークンまで払い直す**ことになります。1万件のバッチが5,000件目で落ちて最初からやり直せば、その分の API 費用はそのまま上乗せです。失敗した箇所だけをやり直す仕組みが要るのは、このためなのです。

私が Inngest を選んだ理由は三つあります。`step.run('name', fn)` で囲んだ処理は成功すると結果が保存され、再実行時は飛ばされること。`npx inngest-cli@latest dev` でステップの流れを時系列で見られること。そして、イベントの型を一度決めれば、関数側で補完が効き、キー名の食い違いをビルドの段階で拾えることです。

## Step 1: 最小構成を v4 で書く（v3 からの書き換えつき）

まずは「記事生成のリクエストを受け、Gemini でアウトラインと本文を作り、DB に保存する」最小の流れを、Next.js App Router で組みます。

```bash
npm install inngest @google/genai
npm install -D typescript @types/node
```

### Before: v3 の書き方（いまの npm では型エラーになります）

初版で載せていたのは、この形でした。トリガーが2番目の引数にあり、型はクライアントの `EventSchemas` にまとめています。

```typescript
// v3 の書き方（参考・v4 では動きません）
import { Inngest, EventSchemas } from "inngest";

export const inngest = new Inngest({
  id: "content-pipeline",
  schemas: new EventSchemas().fromRecord<Events>(),
});

inngest.createFunction(
  { id: "generate-article" },
  { event: "article/generate.requested" },
  async ({ event, step }) => { /* ... */ },
);
```

公式の v3→v4 移行ガイドには、トリガーを第1引数の options へ移すこと、`EventSchemas` を廃止して `eventType()` と `staticSchema()` に置き換えること、`event.user` を削除したこと、`signingKey` などを `serve` からクライアントへ移したこと、既定のモードを `cloud` にしたことが、破壊的変更として並んでいます。

### After: v4 の書き方

イベントの型は `eventType()` で1か所に置き、送信・待機・トリガーのすべてで使い回します。実行時の検証まで要らなければ `staticSchema()` で十分です。

```typescript
// src/inngest/client.ts
import { Inngest, eventType, staticSchema } from "inngest";

// 開発中は Dev Server に向ける。本番は INNGEST_SIGNING_KEY を環境変数で渡す
export const inngest = new Inngest({
  id: "content-pipeline",
  isDev: process.env.NODE_ENV !== "production",
});

type GenerateRequested = {
  userId: string;
  topic: string;
  lengthHint: "short" | "medium" | "long";
  requestId: string; // 冪等性キー。クライアント側で発行する
};

export const articleRequested = eventType("article/generate.requested", {
  schema: staticSchema<GenerateRequested>(),
});

export const approvalReceived = eventType("article/approval.received", {
  schema: staticSchema<{ draftId: string; approved: boolean }>(),
});
```

`staticSchema` に渡すのは `interface` ではなく `type` です。公式のヒントにもそう書かれていて、私は最初 interface のまま渡して型が付かず、しばらく手が止まりました。

モデル ID は1か所にまとめます。

```typescript
// src/lib/gemini.ts
import { GoogleGenAI } from "@google/genai";

export const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY }); // 値は YOUR_API_KEY 形式で .env に置く

// モデルの切り替えはここだけで済むようにしておく
export const MODEL_MAIN = process.env.GEMINI_MODEL_MAIN ?? "gemini-4-hydrogen";
export const MODEL_LIGHT = process.env.GEMINI_MODEL_LIGHT ?? "gemini-3.5-flash-lite";
```

関数本体です。外部に触れる処理は、ひとつずつ `step.run` で囲みます。

```typescript
// src/inngest/functions/generate-article.ts
import { inngest, articleRequested } from "../client";
import { ai, MODEL_MAIN } from "@/lib/gemini";

export const generateArticle = inngest.createFunction(
  {
    id: "generate-article",
    triggers: [articleRequested],
    // 同じ userId の同時実行は 3 件まで（暴走防止）
    concurrency: { key: "event.data.userId", limit: 3 },
    retries: 4, // 既定値も 4。明示しておくと読み手に伝わる
  },
  async ({ event, step, logger }) => {
    const { topic, lengthHint, requestId } = event.data;

    // 1. アウトライン。失敗してもここだけがやり直される
    const outline = await step.run("generate-outline", async () => {
      const res = await ai.models.generateContent({
        model: MODEL_MAIN,
        contents: `次のトピックの記事アウトラインを H2 見出し5つで提案してください。\nトピック: ${topic}\n長さの目安: ${lengthHint}`,
        config: { temperature: 0.4 },
      });
      return res.text ?? "";
    });

    // 2. 本文。outline が保存済みなら、再実行時に 1 は呼ばれない
    const body = await step.run("generate-body", async () => {
      const res = await ai.models.generateContent({
        model: MODEL_MAIN,
        contents: `以下のアウトラインに沿って記事本文を書いてください。\n\n${outline}`,
        config: { temperature: 0.6, maxOutputTokens: 8000 },
      });
      return res.text ?? "";
    });

    // 3. 保存。応答を確かめないと、失敗が成功として記録される
    await step.run("save-to-db", async () => {
      const r = await fetch(`${process.env.API_BASE_URL}/articles`, {
        method: "POST",
        headers: { "content-type": "application/json", "idempotency-key": requestId },
        body: JSON.stringify({ requestId, topic, body }),
      });
      if (!r.ok) throw new Error(`save failed: ${r.status}`);
    });

    logger.info("article generated", { requestId });
    return { requestId, bodyLength: body.length };
  },
);
```

初版との違いは三つです。トリガーを options に入れたこと、モデル ID を定数にしたこと、そして保存の応答を確かめるようにしたことです。`fetch` は 500 が返っても例外を投げないため、`r.ok` を見ないと、Inngest は「成功した」と記録して先へ進んでしまいます。

最後に、Next.js から関数を公開します。

```typescript
// src/app/api/inngest/route.ts
import { serve } from "inngest/next";
import { inngest } from "@/inngest/client";
import { generateArticle } from "@/inngest/functions/generate-article";

export const { GET, POST, PUT } = serve({ client: inngest, functions: [generateArticle] });
```

ローカルでは `npx inngest-cli@latest dev` を起動し、`http://localhost:3000/api/inngest` を登録します。`isDev` を指定し忘れると、v4 では次のエラーで止まります。移行ガイドに載っている文言そのままです。

```text
Error: Inngest error: A signing key is required to run in Cloud mode, but no signing key was found.
```

`isDev: true` をクライアントに書くか、`INNGEST_DEV=1 npm run dev` で起動すれば解消します。私の手元で Gemini を実際に呼んだときの所要時間や出力は、モデルの混み具合で毎回変わるため、ここでは数値を載せません。ダッシュボードで `generate-outline` と `generate-body` が別々の行として並び、片方を失敗させたときにもう片方が再実行されないことを確かめていただくのが、いちばん確実な検証です。

## Step 2: fan-out / fan-in で並列処理を組む

本番のワークフローは「1つのリクエストから多数のサブタスクへ」広がりがちです。ニュースのダイジェストなら、100件のソースを取得し、1件ずつ要約し、最後にまとめる流れになります。v4 では `step.invoke` に関数オブジェクトを渡し、`Promise.all` で待ちます（移行ガイドのとおり、文字列の関数 ID は受け付けなくなりました）。

```typescript
// src/inngest/functions/digest-pipeline.ts
import { inngest } from "../client";
import { eventType, staticSchema } from "inngest";
import { ai, MODEL_MAIN, MODEL_LIGHT } from "@/lib/gemini";

const summarizeRequested = eventType("digest/summarize.requested", {
  schema: staticSchema<{ url: string }>(),
});
const digestRequested = eventType("digest/build.requested", {
  schema: staticSchema<{ urls: string[]; digestId: string }>(),
});

// 子関数: 1件の要約
export const summarizeOne = inngest.createFunction(
  {
    id: "summarize-one",
    triggers: [summarizeRequested],
    // 子関数全体の起動を毎分 60 件までに抑え、Gemini の RPM を超えないようにする
    throttle: { limit: 60, period: "1m" },
    retries: 3,
  },
  async ({ event, step }) => {
    const { url } = event.data;
    // HTML 全文は返さず、必要な長さに切ってから保存する（ステップの戻り値は 4MiB まで）
    const text = await step.run("fetch", async () => {
      const r = await fetch(url, { signal: AbortSignal.timeout(20_000) });
      if (!r.ok) throw new Error(`fetch ${r.status}`);
      return (await r.text()).slice(0, 50_000);
    });
    const summary = await step.run("summarize", async () => {
      const res = await ai.models.generateContent({
        model: MODEL_LIGHT,
        contents: `次の HTML から要点を3行で抜き出してください:\n${text}`,
      });
      return res.text ?? "";
    });
    return { url, summary };
  },
);

// 親関数: fan-out して fan-in
export const buildDigest = inngest.createFunction(
  { id: "build-digest", triggers: [digestRequested], retries: 2 },
  async ({ event, step }) => {
    const { urls, digestId } = event.data;

    const summaries = await Promise.all(
      urls.map((url, i) =>
        step.invoke(`summarize-${i}`, { function: summarizeOne, data: { url } }),
      ),
    );

    const digest = await step.run("compose-digest", async () => {
      const joined = summaries.map((s) => `- ${s.summary}`).join("\n");
      const res = await ai.models.generateContent({
        model: MODEL_MAIN,
        contents: `以下の要約からニュースダイジェストを書いてください:\n${joined}`,
      });
      return res.text ?? "";
    });

    await step.run("publish", async () => {
      const r = await fetch(`${process.env.API_BASE_URL}/digest`, {
        method: "POST",
        headers: { "content-type": "application/json", "idempotency-key": digestId },
        body: JSON.stringify({ digestId, digest }),
      });
      if (!r.ok) throw new Error(`publish ${r.status}`);
    });

    return { count: summaries.length };
  },
);
```

ここでのポイントは二つです。`throttle` が「子関数全体の毎分の起動数」を抑えていること、そして `step.invoke` で起動した子関数がそれぞれ独立にリトライされることです。100件のうち3件だけ 429 になっても、やり直されるのはその3件で、成功した97件には触れません。

一方で、上限もあります。公式の制限表では、1つの関数のステップ数は1,000まで、1ステップの戻り値は4MiBまで、1回の実行状態（イベント・各ステップの戻り値など）の合計は32MiBまでです。URL が数千件になるなら、親関数を分けるか、子関数の結果を外部ストレージに置いて参照だけを返す形に変えてください。

## Step 3: 人による承認を待つ（waitForEvent）

生成した文章をそのまま公開せず、人が確かめてから次へ進める——AI の出力を扱う本番では、この形をほぼ避けられません。`step.waitForEvent` を使うと、数日単位の待機を関数の中にそのまま書けます。v4 では、待つイベントにも Step 1 で作った `eventType` を渡せるので、戻り値に型が付きます。

```typescript
// src/inngest/functions/article-with-approval.ts
import { inngest, articleRequested, approvalReceived } from "../client";

export const articleWithApproval = inngest.createFunction(
  { id: "article-with-approval", triggers: [articleRequested], retries: 2 },
  async ({ event, step }) => {
    // ... outline / body は Step 1 と同じ ...

    // requestId から決まる ID にしておくと、再実行でも同じ値になる
    const draftId = await step.run("save-draft", async () => {
      const id = `draft_${event.data.requestId}`;
      // ここでドラフトを保存する
      return id;
    });

    await step.run("notify-reviewer", async () => {
      const r = await fetch(process.env.SLACK_WEBHOOK_URL!, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ text: `レビュー待ち: /draft/${draftId}` }),
      });
      if (!r.ok) throw new Error(`slack ${r.status}`);
    });

    // 最大3日待つ。同じ draftId の承認イベントだけを受け取る
    const approval = await step.waitForEvent("wait-approval", {
      event: approvalReceived,
      timeout: "3d",
      if: `async.data.draftId == "${draftId}"`,
    });

    if (!approval || !approval.data.approved) {
      await step.run("reject", async () => {
        await fetch(`${process.env.API_BASE_URL}/draft/${draftId}/reject`, { method: "POST" });
      });
      return { status: approval ? "rejected" : "auto-rejected", draftId };
    }

    await step.run("publish", async () => {
      await fetch(`${process.env.API_BASE_URL}/draft/${draftId}/publish`, { method: "POST" });
    });
    return { status: "published", draftId };
  },
);
```

レビュー画面で「承認」が押されたら、サーバーから `inngest.send(approvalReceived.create({ draftId, approved: true }))` を送るだけで、関数の続きが再開します。`if` は CEL で書く式で、`async` が待っている側のイベントを指します。

初版では `draftId` を `crypto.randomUUID()` で作っていました。`step.run` の戻り値は保存されるので実害は出にくいのですが、読み返したときに「再実行で値が変わらないか」を毎回考え直すことになります。リクエストから決まる ID にしておけば、その心配ごと消えます。

裏で Inngest が状態を保存しているので、待機中にサーバーを再起動しても続きから動きます。**人を待つことと、障害から戻ることを、同じ考え方で扱える**——私が durable execution をいちばん手放せない理由は、ここにあります。ただし待てる長さには上限があり、公式の制限表では、待機時間を含めた1回の実行の長さは Free プランで30日、Pro で90日までです。

## Step 4: 予算ガードレールと暴走防止

Gemini API の本番運用でいちばん胃が痛くなるのは、費用の暴走です。Function Calling のループや再帰的なエージェントは、止める仕組みがないと、気づいたときには想定の何倍も呼び出しを重ねています。Inngest の `concurrency`・`throttle`・`rateLimit` を使い分けると、この不安をかなり小さくできます。

```typescript
import { inngest } from "../client";
import { eventType, staticSchema } from "inngest";

const agentRequested = eventType("agent/run.requested", {
  schema: staticSchema<{ userId: string; task: string }>(),
});

export const safeAgent = inngest.createFunction(
  {
    id: "safe-agent",
    triggers: [agentRequested],
    concurrency: [
      { scope: "fn", limit: 50 },                          // 関数全体で 50 並列まで
      { scope: "fn", key: "event.data.userId", limit: 1 }, // ユーザーごとに 1 並列
    ],
    throttle: { limit: 30, period: "1m" },                 // 起動は毎分 30 件。超えた分は待たせる
    rateLimit: { limit: 1, period: "10s", key: "event.data.userId" }, // 連打は捨てる
    retries: 3,
  },
  async ({ event, step }) => {
    const used = await step.run("check-budget", async () => {
      const r = await fetch(`${process.env.API_BASE_URL}/usage/${event.data.userId}`);
      if (!r.ok) throw new Error(`usage ${r.status}`);
      return (await r.json()) as { tokensUsedThisMonth: number };
    });

    if (used.tokensUsedThisMonth > 5_000_000) {
      return { status: "budget-exceeded", used: used.tokensUsedThisMonth };
    }
    // ... ここから Gemini の呼び出し ...
  },
);
```

三つの違いは、私は次のように覚えています。`concurrency` は「同時に走る数」、`throttle` は「一定時間に起動できる数（超えた分は待たせる）」、`rateLimit` は「一定時間に起動できる数（超えた分は捨てる）」です。Gemini の RPM・TPM を守りたいなら `throttle`、同じ人の連打を抑えたいなら `rateLimit` が向いています。

そのうえで、Gemini を呼ぶ前に毎回 `check-budget` で使用量を確かめる設計をおすすめします。月の予算を超えたらここで早めに return すれば、ループがどれだけ回ろうとしても、次の呼び出しには進みません。

## Step 5: 最後に失敗したものを受け止める（onFailure と dead-letter）

リトライを使い切っても失敗するイベントは、必ず出ます。本番では、**何が・いつ・なぜ失敗したかを別の通知先へ送る**仕組みを最初から組んでおくのが安全です。

初版のコードには、二つの誤りがありました。`onFailure` に届く `event` を元のイベントだと思い込んでいたこと、そしてエラーの判定を `e.message.includes("INVALID_ARGUMENT")` という文字列一致で済ませていたことです。公式の説明では、`onFailure` の `event` は `inngest/function.failed` というシステムイベントで、元のイベントは `event.data.event` に入っています。また、エラーは直列化を経て届くため、`onFailure` の中では `instanceof` で種類を見分けられません。

```typescript
import { inngest, articleRequested } from "../client";
import { NonRetriableError, RetryAfterError } from "inngest";
import { ApiError } from "@google/genai";
import { ai, MODEL_MAIN } from "@/lib/gemini";

export const robustGeneration = inngest.createFunction(
  {
    id: "robust-generation",
    triggers: [articleRequested],
    retries: 5,
    onFailure: async ({ event, error, step }) => {
      const original = event.data.event; // 失敗した関数を起動した元のイベント
      await step.run("notify-deadletter", async () => {
        await fetch(process.env.OPS_WEBHOOK_URL!, {
          method: "POST",
          headers: { "content-type": "application/json" },
          body: JSON.stringify({
            functionId: "robust-generation",
            failedRunId: event.data.run_id,
            requestId: original.data.requestId,
            error: error.message, // instanceof は使えないので文字列で残す
          }),
        });
      });
    },
  },
  async ({ event, step }) => {
    return step.run("generate", async () => {
      try {
        const res = await ai.models.generateContent({
          model: MODEL_MAIN,
          contents: event.data.topic,
        });
        return res.text ?? "";
      } catch (e) {
        // 判定は本体側で行う。ここなら ApiError の status が読める
        if (e instanceof ApiError) {
          if (e.status === 429) {
            throw new RetryAfterError("rate limited", 30_000, { cause: e }); // 30 秒置いてから再試行
          }
          if (e.status >= 400 && e.status < 500) {
            throw new NonRetriableError(`gemini ${e.status}`, { cause: e }); // 直らないので即座に止める
          }
        }
        throw e; // 5xx やネットワーク断は通常のリトライに任せる
      }
    });
  },
);
```

`@google/genai` は API の失敗を `ApiError` として投げ、`status` に HTTP ステータスが入ります。400（`INVALID_ARGUMENT`）や 404（モデルが見つからない）は、何度やり直しても結果が変わりません。即座に `NonRetriableError` で止めて人に判断を渡すほうが、無駄な課金を抑えられます。12月1日の自動転送が済んだあとに古いモデル ID を使っている箇所があれば、本文の応答は返ってきても、想定とは違うモデルの料金で請求されることになります。404 を待つのではなく、Step 1 の定数を確かめておくほうが確実です。

## よくある落とし穴

**落とし穴1: `step.run` の外で、毎回変わる値を作る**

`step.run` の戻り値は保存され、再実行時はそこから返ります。逆に言えば、`step.run` の**外**で `Date.now()` や `Math.random()` を呼ぶと、関数が再開されるたびに別の値になります。毎回同じであってほしい値は、ステップの戻り値として固定してください。

```typescript
// ❌ 再開のたびに timestamp が変わり、保存済みのステップと食い違う
const timestamp = Date.now();
await step.run("save", async () => db.save({ value, timestamp }));

// ✅ ステップの戻り値として固定する
const timestamp = await step.run("get-timestamp", async () => Date.now());
await step.run("save", async () => db.save({ value, timestamp }));
```

**落とし穴2: ストリーミングを `step.run` で囲む**

`generateContentStream` は async iterator を返します。これを `step.run` の中で最後まで読んでから返すと、最初の文字が早く届くという利点が消えます。Inngest は裏側のジョブ実行に割り切り、利用者への逐次表示は SSE や WebSocket の別経路で行うのが自然です。

**落とし穴3: `event.data` に大きなデータを載せる**

イベントには最大サイズがあり、公式の制限表では Free プランが256KiB、Pro と Business が3MiBです（初版では512KBと書いていましたが、誤りでした）。PDF や動画の本体はストレージに置き、`event.data` には URL だけを入れてください。Gemini の Files API に渡すときも、この形のほうが素直に書けます。

## よくある誤解

**誤解1: 「Inngest のリトライがあれば、Gemini の 429 は気にしなくてよい」**

リトライはステップの単位で効きますが、`throttle` を置かなければ、失敗した呼び出しが一斉にやり直されて、また 429 を受けます。429 を受けたら `RetryAfterError` で待ち時間を指定し、そもそもの起動数は `throttle` で抑える——この二段で考える必要があります。

**誤解2: 「`step.run` で囲めば、外部への書き込みは一度しか起きない」**

保存されるのは、ステップが**成功して戻ったあと**の結果です。外部への書き込みが終わった直後、戻り値を返す前に落ちれば、そのステップはもう一度実行されます。だからこそ、次の節の冪等性が土台になります。

**誤解3: 「`onFailure` で `instanceof NonRetriableError` を見れば分岐できる」**

公式の説明どおり、`onFailure` に届くエラーは直列化を経た `Error` で、独自のクラスは失われます。分岐が必要なら、本体の側で投げる前にメッセージやメタデータへ種類を書き込んでおきます。

## 冪等性 — 見えにくいけれど、いちばん下の土台

`step.run` の保存は Gemini を二重に呼ばないことを守ってくれますが、DB への書き込みや外部 API が「2回呼ばれても安全」でなければ、その価値は大半が消えてしまいます。

実務では、三つの習慣でほとんどの場面を覆えます。クライアントから受け取った冪等性キー（ここでは `requestId`）を、すべての外部呼び出しに引き継ぐこと。Postgres なら `INSERT ... ON CONFLICT DO NOTHING`、BigQuery なら `MERGE` のように、そのキーで書き込むこと。そして、Stripe のように `Idempotency-Key` を受け付ける API には、同じキーをそのまま渡すことです。

```typescript
await step.run("persist", async () => {
  await db.execute(
    `INSERT INTO articles (request_id, topic, body)
     VALUES ($1, $2, $3)
     ON CONFLICT (request_id) DO NOTHING`,
    [requestId, topic, body],
  );
});

// Stripe: 冪等性キーつきで PaymentIntent を作る
const intent = await step.run("create-payment-intent", async () => {
  const pi = await stripe.paymentIntents.create(
    { amount: 250, currency: "jpy", customer: customerId },
    { idempotencyKey: `pi_${requestId}` },
  );
  return { id: pi.id, status: pi.status };
});
```

初版では古い Charges API（`stripe.charges.create` と `tok_visa`）で書いていました。いま新しく組むなら PaymentIntents が素直です。また、ステップの戻り値には Stripe のオブジェクト全体ではなく、後で使う値だけを返すようにしました。保存される量が減り、実行状態の上限にも近づきにくくなります。

書き込み側を冪等にできない古い API には、「claim パターン」が使えます。`step.run("claim-or-skip", ...)` で、リクエストを原子的に「処理中」にし、初回かどうかを真偽値で返します。再実行では `false` が返るので、そこで短絡できます。

## 観測 — ダッシュボードで毎日見ているもの

日々見ているのは、ほんの少しのグラフです。いちばん役に立つのは `generate-body` のステップの p50 / p95 で、ここがじわじわ伸びていれば、コードではなく上流の遅延を疑います。二つ目は関数ごとのリトライ回数の分布で、増えたまま戻らないときは、クォータや認証の問題が育ちつつある合図です。

もう一歩踏み込むなら、Gemini の呼び出しごとに OpenTelemetry のスパンを切り、モデル名とトークン数を属性に入れます。

```typescript
import { trace } from "@opentelemetry/api";
const tracer = trace.getTracer("content-pipeline");

const summary = await step.run("summarize", async () =>
  tracer.startActiveSpan("gemini.generateContent", async (span) => {
    span.setAttribute("gemini.model", MODEL_LIGHT);
    try {
      const res = await ai.models.generateContent({ model: MODEL_LIGHT, contents: prompt });
      span.setAttribute("gemini.tokens.total", res.usageMetadata?.totalTokenCount ?? 0);
      return res.text ?? "";
    } finally {
      span.end();
    }
  }),
);
```

モデル名を属性に入れておくと、12月1日のような切り替えの前後で、待ち時間とトークン数がどう動いたかを同じグラフで比べられます。私がこの形にしたのは、まさにモデルを差し替えた週に「遅くなった気がする」を数字で確かめられなかったからでした。

## テスト — `@inngest/test` で分岐を確かめる

v4 向けには `@inngest/test` があり（`inngest` 4.0.0 以上が必要です）、関数をそのまま実行し、ステップの差し替えや呼び出しの検証ができます。

```typescript
// __tests__/generate-article.test.ts
import { InngestTestEngine } from "@inngest/test";
import { generateArticle } from "@/inngest/functions/generate-article";

const t = new InngestTestEngine({
  function: generateArticle,
  events: [{
    name: "article/generate.requested",
    data: { userId: "u1", topic: "durable execution", lengthHint: "short", requestId: "req_1" },
  }],
});

test("生成の2ステップが済んでから保存する", async () => {
  const { ctx, result } = await t.execute({
    steps: [
      { id: "generate-outline", handler: () => "## A\n## B" },
      { id: "generate-body", handler: () => "本文" },
      { id: "save-to-db", handler: () => undefined },

  });
  expect(ctx.step.run).toHaveBeenCalledWith("save-to-db", expect.any(Function));

```

Gemini を呼ぶステップを差し替えれば、API キーなしで分岐だけを確かめられます。`step.waitForEvent` や `step.sleep` を含む関数は、公式の説明どおり必ず差し替えてください。そのままだと待機に入ってしまいます。リトライの挙動そのものは、`setTimeout` を偽装するより、Dev Server で実際に失敗させて記録を見るほうが確かです。

## デプロイ時に気をつけること

`/api/inngest` は、Inngest Cloud（またはセルフホストの制御プレーン）から届く場所に置く必要があります。厳しいファイアウォールの内側なら、リバースプロキシで公開するか、制御プレーンを自前で動かすことになります。

関数のバージョンは `id` で見分けられます。`id` を変えると別の関数として扱われ、走っている実行は古い `id` のまま最後まで進みます。破壊的な変更のときには都合がよいのですが、そのあいだは古い関数もデプロイしたままにしておく必要があります。

署名鍵とイベントキー（`INNGEST_SIGNING_KEY`・`INNGEST_EVENT_KEY`）は環境ごとに分けてください。開発環境の不具合が本番のイベントを送ってしまう事故は、鍵を使い回したときに起きます。サーバーレスで動かす場合、移行ガイドは checkpointing の `maxRuntime` を設定するよう案内しているので、ホストの実行時間の上限とあわせて確かめておくと安心です。

## 本番投入前のチェックリスト

- 外部呼び出しごとに個別の `step.run` があり、再実行時に Gemini を余計に呼ばない構成
- すべてのイベントに安定した `requestId` があり、書き込みはそのキーで冪等
- `concurrency` をユーザー（テナント）単位で設定済み
- `throttle` を関数全体に設定し、Gemini の RPM・TPM の範囲内
- 関数の冒頭で月の予算を確かめ、超過時は早めに return
- 429 は `RetryAfterError`、直らない 4xx は `NonRetriableError` という分け方
- `onFailure` から別の通知先へ、元の `requestId` つきで送る仕組み
- モデル ID は定数か環境変数に集約し、2.5 系が残っていない状態
- クライアントの `isDev` と本番の `INNGEST_SIGNING_KEY` を環境ごとに分離
- `@inngest/test` で主要な分岐を、Dev Server でリトライを確認済み

どれか一つが欠けていると、durable execution だけでは守りきれない穴が残ります。Inngest は車台であって、安全装置は別に取り付ける必要があるのです。

## 次に詰まりやすいところと、最初の一歩

ここまで組めると、次に当たるのはたいてい「429 がどのクォータから来ているのか」と「同じ処理をキューで組んだ場合との違い」です。前者は [Gemini API レート制限とクォータ管理の本番ガイド](/articles/gemini-api/gemini-api-rate-limiting-quota-management-production-guide)、リトライの外側の守りは [Gemini API リトライとサーキットブレーカーの本番設計](/articles/gemini-api/gemini-api-resilience-circuit-breaker-bulkhead-production-guide)、キュー側の組み方は [Gemini API + Cloud Tasks 非同期ジョブキュー本番ガイド](/articles/gemini-dev/gemini-api-cloud-tasks-async-ai-job-queue-production-guide) と [Cloud Pub/Sub でつくるイベント駆動の AI ワークフロー](/articles/gemini-api/gemini-api-cloud-pubsub-event-driven-ai-workflow) が手がかりになります。

まずは、手元のプロジェクトで `npm ls inngest` と、コード内の `gemini-2.5` の検索を、それぞれ1回ずつ実行してみていただければと思います。どちらかに引っかかったら、この記事の Step 1 から書き換えるのが近道です。私も、赤い波線だらけのエディタを前に、そこから始め直しました。
