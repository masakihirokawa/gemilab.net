月曜の朝、App Store Connect を開くと、週末のあいだに届いたレビューが画面を埋めておりました。英語、ドイツ語、フランス語、韓国語——一件ずつ読み、それぞれの言語で返事を考えているうちに、コーヒーが冷めて、最初の一時間が終わっていました。

アプリを複数運営していると、この光景が毎週のように繰り返されます。そこで Gemini API を使い、返信の下書きと投稿を半自動化することにしました。その途中で行き当たったのが、公式ドキュメントに見当たらない「8秒ルール」です。同じ場所で足止めされている方の手間を、少しでも減らせれば幸いです。

最初にお伝えしたいのは、**生成の部分はあっけないほど簡単で、時間を取られたのは「投稿が本当に反映されたか」を確かめる部分だった**ということです。

## なぜレビュー返信の自動化を考えたか

Beautiful HD Wallpapers（iOS / Android）や浮世絵壁紙など、私が運営しているアプリには、世界各地のユーザーからレビューが届きます。返信は早く、丁寧にするに越したことはない、と私は考えています。ただ、数が増えるほど手作業の限界がはっきりしてきました。

とくに重かったのが多言語です。ドイツ語やフランス語のレビューには、その言語で返したくなります。翻訳ツールを挟み、不自然でないかを読み直し、貼り付けて投稿するという流れでした。この往復が、一件あたりの時間をじわじわ押し上げていったのです。

「レビューの言語を自動で見分けて、同じ言語で自然な返信を書いてくれるなら、下書きの工程は任せられるのではないか」というのが出発点でした。

## 基本の実装

Python で、Google Play Developer API と App Store Connect API からレビューを取得し、Gemini API で返信文を作り、確認を経て投稿する流れにしています。

プロンプトの要点は、言語判別を Gemini に任せることです。レビュー本文をそのまま渡し、「同じ言語で返信する」と指示するだけで、日本語には日本語、ドイツ語にはドイツ語の返信が返ってきます。言語検出 API を別に呼ばずに済むので、工数がそのぶん減ります。

```python
import os
from google import genai

# API キーは環境変数 GEMINI_API_KEY から読み込まれます
client = genai.Client()
MODEL = "gemini-2.5-flash"  # 利用前に、公式のモデル一覧で現行の名前を確認します

def generate_reply(review_text: str, app_name: str, rating: int) -> str:
    """レビューと同じ言語で、評価に応じた返信文を作る。"""
    prompt = f"""以下のアプリレビューに対する返信を作成してください。

アプリ名: {app_name}
評価: {rating}星
レビュー内容:
{review_text}

要件:
- レビューと同じ言語で返信する
- 丁寧かつ自然な口調で
- 高評価（4〜5星）: 感謝を伝え、継続利用を歓迎する
- 低評価（1〜3星）: 謝罪と具体的な改善意志を伝える
- 150文字以内を目安に簡潔に
- 定型文にならないよう、レビューの内容に具体的に触れる

返信文のみを出力する。"""

    response = client.models.generate_content(model=MODEL, contents=prompt)
    return response.text.strip()
```

以前は `google.generativeai` を使っておりましたが、現在は `google-genai`（`from google import genai`）が現行の SDK です。古い書き方のまま写すと、非推奨の警告が出るので、本稿では新しい側に揃えました。

文字数にも注意が要ります。Google Play の返信には文字数の上限があり（350文字）、プロンプトで「150文字以内を目安」と伝えているのは、その手前に余裕を持たせるためです。念のため、投稿の直前に長さを数え、超えていたら再生成に回す一行を入れています。

Claude Haiku や GPT-4o Mini にも同じプロンプトを試しました。品質の差は決め手になるほどではなく、短文の多言語生成では Gemini Flash の応答時間が安定していました。月に数千件を処理しても、API 費用は数百円台に収まっています。

## 落とし穴: App Store の「8秒ルール」

Google Play への返信は、最初から滑らかに動きました。App Store Connect API で同じことをすると、一定数を超えたあたりから 403 エラーが返ったり、場合によっては何も起きないまま失敗したりしました。

返信が画面に反映されないのに、手元のログは成功に見える——この状況を十回ほど繰り返して、ようやく「レート制限に近い何かが働いている」と気づきました。送信間隔を変えて試すと、各返信のあいだに8秒以上空けると安定します。1セッションの上限は、安全側に35件としています。

公式ドキュメントも探しましたが、この制約に触れた記述は見つかりませんでした。Apple 側の暗黙の制限として扱うほかありません。

```python
import time
import requests

API_URL = "https://api.appstoreconnect.apple.com/v1/customerReviewResponses"

def post_reply_to_app_store(review_id: str, reply_text: str, token: str) -> bool:
    """App Store Connect API で返信を投稿する。201 が返れば受理。"""
    payload = {
        "data": {
            "type": "customerReviewResponses",
            "attributes": {"responseBody": reply_text},
            "relationships": {
                "review": {"data": {"type": "customerReviews", "id": review_id}}
            },
        }
    }
    headers = {"Authorization": f"Bearer {token}", "Content-Type": "application/json"}
    r = requests.post(API_URL, json=payload, headers=headers, timeout=30)
    return r.status_code == 201

def batch_reply_app_store(reviews: list, replies: list, token: str):
    WAIT_SECONDS = 8       # 実験で落ち着いた間隔
    MAX_PER_SESSION = 35   # 安全マージン込みの上限

    targets = list(zip(reviews, replies))[:MAX_PER_SESSION]
    for i, (review_id, reply_text) in enumerate(targets):
        ok = post_reply_to_app_store(review_id, reply_text, token)
        print(f"{'OK' if ok else 'NG'} [{i + 1}/{len(targets)}] {review_id[:8]}...")
        if i < len(targets) - 1:
            time.sleep(WAIT_SECONDS)
```

6秒以下に縮めると、30件を超えたあたりから失敗が出はじめました。8秒にしてからは安定しています。Google Play には同様の待機要件がなく、連続で投稿しても問題ありませんでした。

## 「成功に見える」を信じない: 投稿後の読み戻し

8秒を入れても、まだ不安が残りました。ステータスコードが 201 でも、画面に出ていなかった経験があるからです。

そこで、投稿のあとで返信が実際に付いたかを読み戻す工程を足しました。App Store Connect API には、レビューに紐づく返信を取得するエンドポイントがあります。

```python
def reply_is_visible(review_id: str, token: str) -> bool:
    """投稿した返信が、レビューに紐づいて読み出せるかを確認する。"""
    url = f"https://api.appstoreconnect.apple.com/v1/customerReviews/{review_id}/response"
    r = requests.get(url, headers={"Authorization": f"Bearer {token}"}, timeout=30)
    return r.status_code == 200 and bool(r.json().get("data"))
```

読み戻しに失敗した件は、その場で再投稿せず、未反映リストに積みます。次のセッションで、まとめて確認してから出し直します。その場で何度も叩くと、制限に触れる回数をいたずらに増やしてしまうからです。

**成功の記録は、サーバーが返した値ではなく、読み戻せた事実に付けます。** 自動化が増えるほど、この線引きだけは外さないようにしています。

## 多言語の返信品質にはばらつきがある

数か月運用して気づいたのは、返信の自然さが言語によって違うことです。英語・日本語・スペイン語は十分に自然でした。一方、ドイツ語とフランス語には、機械翻訳らしい堅さが残る場面があり、とくに低評価への返信が「謝りすぎ」の文体になりがちでした。

対策は、問題のある言語にだけ、補足の指示を足すことです。全言語に同じ指示を当てるより、効きがはっきりしていました。ドイツ語のネイティブの知人に読んでもらいながら調整し、いまの文面に落ち着いています。

```python
LANGUAGE_HINTS = {
    "de": "Schreiben Sie auf natürlichem Deutsch. Vermeiden Sie übermäßige Entschuldigungen.",
    "fr": "Répondez en français naturel et chaleureux, sans style trop formel.",
    "ko": "자연스러운 한국어로 답변해 주세요. 지나치게 공식적인 표현은 피해주세요.",
}
```

## 人が確認する設計は残す

この仕組みを入れてから、返信にかける時間は週に数時間から30分ほどになりました。ただし、生成した返信は毎回目で読んでから投稿しています。

翻訳と下書きの手間が消えたぶん、「この文は、いまのユーザーに失礼ではないか」という確認だけに集中できるようになりました。想定していなかった副産物です。ユーザーとの接点であるレビュー返信については、最後の判断だけは手元に残しておきたいと、いまも感じています。

## Google Play と App Store の違い

二つのプラットフォームで挙動が違ったので、並べておきます。

<table>
<thead><tr><th>項目</th><th>Google Play</th><th>App Store Connect</th></tr></thead>
<tbody>
<tr><td>連続投稿</td><td>問題なし</td><td>8秒以上の間隔を空ける</td></tr>
<tr><td>返信の文字数</td><td>350文字まで</td><td>十分に長い（150文字目安で運用）</td></tr>
<tr><td>制限の透明性</td><td>ドキュメントに比較的記載あり</td><td>実際に試して見つける部分が多い</td></tr>
<tr><td>投稿後の確認</td><td>一覧で反映を確認</td><td>読み戻しの API で確認</td></tr>
</tbody>
</table>

同じ仕組みで両方を回すなら、生成の部分は共通にして、投稿の部分だけをプラットフォームごとに分けるのがおすすめです。分岐が投稿処理の中で閉じるので、保守も楽になります。

Gemini API 側のレート制限については、[Gemini APIのレート制限エラーを回避する実践パターン](/articles/gemini-api/gemini-api-rate-limit-error-fix)も合わせてご覧ください。

次の一歩としては、まず投稿の直後に読み戻しを一行だけ足し、翌朝その結果を眺めてみていただければと思います。8秒の待機は小さな数字ですが、知っているかどうかで、数時間のデバッグが要らなくなります。
