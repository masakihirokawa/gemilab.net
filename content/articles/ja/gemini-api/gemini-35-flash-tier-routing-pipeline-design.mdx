Gemini 3.5 Flash が一般提供になった日、私が最初にやってしまったのは、自動運用しているパイプラインのモデル指定を片端から最上位ティアへ書き換えることでした。最新で一番賢いと案内されると、つい全部そこへ寄せたくなります。

数日後、API の請求見込みが普段の二倍近くに膨らんでいることに気づきました。記事の本文を磨くのと、タグを5個に分類するのと、見出しの誤字を拾うのとを、同じ最上位ティアに投げていたからです。

個人開発で複数のサイトを回していると、月のコストは「一番賢いモデルが使えるか」ではなく「どの作業にどのティアを当てたか」で決まります。Flash 系の軽量ティアが GA で安定してきた今こそ、最上位に寄せるのではなく、工程ごとに振り分ける設計を組み直す好機だと考えています。

## 1本の生成を工程に分解する

「記事を1本書く」という作業は、実際にはいくつもの小さな工程の連なりです。私のパイプラインでは、ひとつの記事生成を次の4工程に分けています。

### 分類・抽出

カテゴリの判定、タグの付与、参照データからのキーワード抽出。入力に対して短い構造化された答えを返すだけの工程で、推論の深さはほとんど要りません。

### 下書き

見出し構成の案出しと、各セクションの一次ドラフト。量は多いものの、この段階の文章はあとで必ず書き直します。完成度より、たたき台が速く安く出ることのほうが大切です。

### 仕上げ

文体プロファイルに沿って本文を整え、論理の飛びを埋め、読者への語り口を揃える工程。ここが記事の価値を決めるので、推論力の高い上位ティアを惜しまず当てます。

### 検証

誤字、禁止語、常体の混入、裸URL、日英の整合といった機械チェック。多くは正規表現で片付きますが、文意の確認が要る箇所だけモデルを呼びます。

工程を分けてみると、4つのうち推論力が本当に要るのは「仕上げ」だけだと見えてきます。残りは速度と単価で選んでよい工程です。

## ティアと工程の対応を表にする

工程が見えたら、どのティアを当てるかの対応表を作ります。私が今運用している割り当ては次のとおりです。料金は相対的な目安として、最も安いティアを 1 とした倍率で書いています。

<table>
<thead>
<tr><th>工程</th><th>割り当てるティア</th><th>必要な推論力</th><th>相対単価の目安</th></tr>
</thead>
<tbody>
<tr><td>分類・抽出</td><td>Flash-Lite 系</td><td>低</td><td>1x</td></tr>
<tr><td>下書き</td><td>Flash 系</td><td>中</td><td>3〜5x</td></tr>
<tr><td>仕上げ</td><td>Pro 系（上位）</td><td>高</td><td>15〜25x</td></tr>
<tr><td>検証（文意確認のみ）</td><td>Flash 系</td><td>中</td><td>3〜5x</td></tr>
</tbody>
</table>

ここで効いてくるのは、回数の多い工程ほど安いティアに寄っているという点です。分類や下書きは1記事あたり何度も呼びますが、仕上げは原則1回。高い単価のティアを、最も回数の少ない工程に閉じ込めているわけです。

## 工程を振り分けるルーターを置く

対応表をコードに落とすと、生成のたびに「どのモデルを呼ぶか」を考えずに済みます。私は工程名を受け取ってモデル名を返すだけの薄いルーターを1枚かませています。

```python
from enum import Enum

class Stage(str, Enum):
    CLASSIFY = "classify"
    DRAFT = "draft"
    FINALIZE = "finalize"
    VERIFY = "verify"

# 工程 → モデルの対応表。ティア名は環境変数で差し替え可能にしておく
STAGE_MODEL = {
    Stage.CLASSIFY: "gemini-flash-lite-latest",
    Stage.DRAFT:    "gemini-flash-latest",
    Stage.FINALIZE: "gemini-pro-latest",
    Stage.VERIFY:   "gemini-flash-latest",
}

def model_for(stage: Stage) -> str:
    # 未知の工程は安全側（安いティア）に倒す。高いティアへの誤爆を防ぐ
    return STAGE_MODEL.get(stage, "gemini-flash-lite-latest")
```

ポイントは、未知の工程を渡されたときに最上位ではなく最も安いティアへ倒している点です。ルーターの取りこぼしが請求に直結するので、デフォルトは常に安全側に置いています。

呼び出し側は工程を宣言するだけになります。

```python
def run_stage(client, stage: Stage, prompt: str) -> str:
    model = model_for(stage)
    resp = client.models.generate_content(model=model, contents=prompt)
    return resp.text
```

## 失敗したときだけ上位ティアへ逃がす

工程分担の弱点は、安いティアが期待した品質に届かないときです。ここで全工程を上位ティアへ戻すと、せっかくの分担が崩れます。

私が置いているのは、検証に落ちた工程だけを一段上のティアで一度だけ再実行する条件付きエスカレーションです。

```python
def run_with_escalation(client, stage, prompt, validate) -> str:
    out = run_stage(client, stage, prompt)
    if validate(out):
        return out
    # 検証に落ちた場合のみ、一段上のティアで1回だけ再実行する
    escalated = {
        Stage.CLASSIFY: "gemini-flash-latest",
        Stage.DRAFT:    "gemini-pro-latest",
    }.get(stage)
    if escalated is None:
        raise ValueError(f"escalation exhausted for {stage}")
    resp = client.models.generate_content(model=escalated, contents=prompt)
    return resp.text
```

再実行を「1回だけ」「一段だけ」に限るのが肝心です。無制限に上へ逃がすと、難しい入力のたびに最上位ティアへ雪崩れ込み、コストが跳ねます。`validate` には正規表現の機械チェックを渡し、モデルの主観で合否を決めさせないようにしています。

## コスト差を呼び出し回数から試算する

設計の良し悪しは、感覚ではなく月額の試算で確かめます。1サイトあたり1日4本、4サイトで1日16本を生成すると仮定し、1本あたりの工程別呼び出し回数を次のように見積もります。

- 分類・抽出: 3回
- 下書き: 4回
- 仕上げ: 1回
- 検証: 2回

最も安いティアの単価を 1 単位として、対応表の倍率を掛けると、1本あたりの相対コストは次のようになります。全工程を上位ティア（20x と仮定）に寄せた場合は (3+4+1+2) × 20 = 200 単位。工程分担した場合は 3×1 + 4×4 + 1×20 + 2×4 = 47 単位です。

同じ16本/日でも、相対コストは 200 対 47、おおよそ4分の1に収まります。最上位ティアへ寄せていたときに請求が二倍近くまで膨らんだ体感は、この比率と符合していました。絶対額は各ティアの実単価で置き換えれば、自分の運用に当てはめて計算できます。

## 公式の料金表に出てこない運用上の落とし穴

ティア振り分けを長く回していると、料金表だけ見ていては気づけない注意点が出てきます。

ひとつは、既定モデルの変更です。Flash 系が既定で有効になると、明示的にモデルを指定していない呼び出しの出力の癖が静かに変わります。文体プロファイルやテンプレ検出を回している場合は、既定が動いた直後に出力を一度見直すようにしています。ルーターでモデル名を必ず明示しておくと、この影響をルーター内に閉じ込められます。

もうひとつは、期限つきの非推奨です。画像プレビュー系のモデルのように停止日が決まっているものは、参照しているコードを後継へ切り替える期日を運用カレンダーに入れておかないと、ある日静かに失敗します。私は非推奨の通知を見たらルーターの対応表にコメントで期日を書き込み、切替漏れを物理的に見えるようにしています。

## 状況別に、どこから手をつけるか

最後に、いま全工程を上位ティアへ寄せている方が、どこから振り分けを始めればよいかをまとめます。

呼び出し回数が最も多い工程から着手するのが効きます。多くの場合それは分類・抽出か下書きです。ここを Flash 系へ落とすだけで、品質の体感をほとんど変えずにコストの山が削れます。

仕上げは最後まで上位ティアに残してください。読者が課金して読む価値はこの工程が作るので、ここを安いティアへ落とすのは本末転倒です。

検証は、正規表現で済む部分とモデルが要る部分を分け、モデル呼び出しを必要最小限に絞ります。多くの機械チェックはモデルなしで通せます。

私自身、Dolice Labs の複数サイトを個人で回しながら、AdMob の収益でこの API 予算をまかなっています。だからこそ「一番賢いモデルを使えること」よりも「どの工程にどのティアを当てたか」のほうを、毎月の数字で見るようにしています。

まずは自分のパイプラインの1本を工程に分解し、回数の多い工程から1つだけ Flash 系へ落としてみてください。月末の請求の差が、設計を続けるかどうかの何よりの判断材料になります。
