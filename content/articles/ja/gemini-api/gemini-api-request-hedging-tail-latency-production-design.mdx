ある朝、私が運営している壁紙アプリの解析画面を眺めていて、Gemini API への呼び出しの 0.3% が 8 秒以上待たされていることに気づきました。中央値は 1.2 秒で、平均値だけ見ているとまったく問題は見えません。けれども、AdMob のインタースティシャル広告と AI 応答の表示順が前後しはじめると、ユーザー体感としてのアプリの「重さ」が露骨に変わります。アーティスト・個人開発者の廣川政樹です。Dolice Labs の 4 サイトと、2014 年から続けている累計 5,000 万 DL の個人アプリ事業の両方で同じ問題を観測し、最終的にリクエストヘッジング（hedged requests）という古典的な手法に着地しました。本稿はその実装メモになります。

## 長尾レイテンシは「中央値」では絶対に見えない

Gemini API のレスポンスタイムを単純な平均で計測していると、99 パーセンタイルの「ユーザーが本当に怒っている瞬間」を見落とします。私のアプリでは Day 7 リテンションが 1 週間で 2.1% 落ちる期間が二度あり、原因をたどると毎回「特定の時間帯に p99 が 7 秒を超えていた日」と一致していました。

平均値や中央値はほぼ動きません。長尾だけが沈み、リテンションが静かに戻りました。コストは 8% 増。これがリクエストヘッジングの典型的なトレードオフです。

## ヘッジングとはどういう発想か

Google の "The Tail at Scale"（Dean & Barroso, 2013）が原典で、一定時間応答が返ってこなかった場合に「同じリクエストを別のレプリカに対してもう一発撃つ」発想です。先に返ってきた方を採用し、遅い方は破棄します。LLM API は内部的に複数のサービングインスタンスに散らばっているため、片方が偶然遅いインスタンスに当たった場合でも、もう一方がスムーズに返ってくる確率が高い、というのが効く理由です。

私の場合、Gemini 2.5 Flash で生成タスクを走らせるとき、最初のリクエストから 1,800 ms 経っても応答がなければ「もう一回投げる」設計にしています。1,800 ms は p95 の値から逆算しています（p95 = 3.4 秒の場合、その手前で打つ）。

## 最小実装 — Promise.race ベースのヘッジ関数

実装は驚くほど短く済みます。TypeScript で約 40 行です。実プロダクションで使っているコードから、機密に関わる部分（KV キーやリトライ層）を削った最小版を貼ります。

```typescript
import { GoogleGenerativeAI } from "@google/generative-ai";

const client = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);

export async function hedgedGenerate(
  prompt: string,
  options: {
    hedgeAfterMs: number;  // 例: 1800
    model?: string;        // 例: "gemini-2.5-flash"
    maxAttempts?: number;  // 既定 2（最大 2 並列）
  }
): Promise<string> {
  const model = client.getGenerativeModel({
    model: options.model ?? "gemini-2.5-flash",
  });

  const abortControllers: AbortController[] = [];

  const launch = async (attemptIndex: number): Promise<string> => {
    const ctrl = new AbortController();
    abortControllers.push(ctrl);
    try {
      const res = await model.generateContent({
        contents: [{ role: "user", parts: [{ text: prompt }] }],
        // @ts-expect-error: signal は SDK の請求書外オプション
        requestOptions: { signal: ctrl.signal },
      });
      return res.response.text();
    } catch (e) {
      if (ctrl.signal.aborted) throw new Error("aborted-loser");
      throw e;
    }
  };

  const winners: Promise<string>[] = [launch(0)];

  // hedgeAfterMs 経過後に 2 本目を投げる
  const hedgeTimer = new Promise<string>((_, reject) => {
    setTimeout(() => {
      winners.push(launch(1).catch(reject));
    }, options.hedgeAfterMs);
  });

  const winner = await Promise.race([winners[0], hedgeTimer]);
  // 勝者が決まったら、敗者を確実に中断
  abortControllers.forEach((c, i) => {
    if (!c.signal.aborted) c.abort();
  });
  return winner;
}
```

実装ポイントは三つです。第一に、敗者側の AbortController を必ず叩くこと。これを忘れると Gemini 側で 2 倍課金されます。第二に、`hedgeAfterMs` を固定値にせず、後述のように p95 から動的に決めること。第三に、`maxAttempts` を 2 にすること。3 本以上にしてもレイテンシ改善は飽和する一方、コストだけが線形に伸びます。私の運用では 2 本固定です。

## 適応的ヘッジング — p95 をリアルタイム追跡する

固定の閾値だと、混雑時間帯に「全リクエストがヘッジされる」状態になってしまい、コストが青天井になります。p95 をローリング集計しておき、ヘッジ閾値をその実測値に追随させると、コスト増を 8% 程度に抑えられます。

```typescript
class P95Tracker {
  private samples: number[] = [];
  private readonly windowSize = 200;

  record(latencyMs: number) {
    this.samples.push(latencyMs);
    if (this.samples.length > this.windowSize) this.samples.shift();
  }

  hedgeThresholdMs(): number {
    if (this.samples.length < 50) return 2500; // ウォームアップ中はデフォルト値
    const sorted = [...this.samples].sort((a, b) => a - b);
    const idx = Math.floor(sorted.length * 0.95);
    return Math.max(1200, sorted[idx]); // 1.2 秒未満には絶対に下げない
  }
}
```

下限を 1.2 秒に置いているのは、これより短い閾値だとほぼ全リクエストがヘッジされて、コストの増分が 30% を超えるためです。実測ベースで決めています。

## AdMob インタースティシャルとの隙間設計

私のアプリでは、インタースティシャル広告が表示されてからユーザーが閉じるまでの平均が 4.8 秒です。この間に Gemini の応答を裏で確定させておけば、広告が閉じた瞬間にコンテンツを出せます。p99 が 6.8 秒だった頃は、広告を閉じた後に「まだ生成しています…」のローディングが出てしまうケースが 2.6% ありました。ヘッジ導入後はこれが 0.4% に下がっています。

この「広告表示中に裏で確定する」設計は、AdMob を使っている個人開発者の現場では汎用的に効く考え方です。広告で時間を稼げる秒数（私の場合は 4.8 秒）からバッファ（1 秒）を引いた値が、許容できる p99 の上限になります。私は 3.5 秒を内部 SLO に置き、ヘッジ閾値を逆算しています。

## ヘッジングが向かないケース

万能ではないので、避けたほうがよい局面を整理しておきます。第一に、Function calling と組み合わせる場合。同じ関数呼び出しが二度発火する事故が起きやすく、副作用のある関数では特に注意が必要です。私のアプリでは Function calling 経路だけはヘッジを外し、ストリーミング応答に切り替えました。

第二に、ストリーミング応答そのもの。ストリーミングは最初のトークンが返るまでの時間（TTFT）が短いため、ヘッジしても勝者を判定する前に「中途半端な応答が二つ流れる」状態になります。ストリーミング側にはバックプレッシャー制御で対処すべきで、ヘッジは適しません。

第三に、コンテキストキャッシュとの併用時。キャッシュヒット時のレイテンシは中央値 0.4 秒程度に下がっており、ヘッジしても効果が薄い一方、キャッシュキーの再計算でかえって遅くなります。キャッシュ命中前提のパスはヘッジを通さないルーティングにしています。

## 運用上の落とし穴と対処

実運用で 6 週間動かして遭遇した落とし穴を 3 つ挙げます。

まず、レート制限カウントが体感の倍になる問題です。ヘッジ率が 12% だった月では、リクエスト数の課金は単純に 1.12 倍ではなく 1.18 倍まで膨らみました。理由は、敗者側を abort しても Gemini 側のクォータカウンタには「投げた」事実が残るためです。RPM の上限近くで運用している場合は、ヘッジ率を上限から逆算して制御する必要があります。私は RPM の 75% に達した時点でヘッジを完全停止するサーキットを入れています。

次に、ログ集計の混乱です。勝者と敗者の両方を残してしまうと、平均レイテンシが二重カウントされて見かけ上悪化します。私は OpenTelemetry のスパン属性に `hedge.role = "winner" | "loser"` を仕込み、`role = "winner"` だけを集計対象にしています。これだけでダッシュボードの数値が読めるようになります。

最後に、コスト試算の難しさです。ヘッジ率は時間帯と曜日でゆらぎます。私の運用では平日 14 時台に 18%、深夜 3 時に 4% という分布で、月平均ではコスト増が 8% ですが、最悪日は 14% でした。財務的に許容できる上限を予算ガードレールとして別途設定し、超えたら自動でヘッジを止める運用にしています。

## 個人開発で導入を検討する判断基準

最後に、私の経験から導入をおすすめできる条件と、しない方がよい条件をまとめます。導入をおすすめできるのは、月間 API 課金が 5,000 円以上あり、p99 と p50 の比が 4 倍を超えていて、かつ AdMob などで「広告表示中に裏で確定させたい」明確な要件があるアプリです。これら 3 つが揃っているなら、コスト 8% 増で p99 を半分以下に下げられる施策はあまり他にありません。

逆に、個人開発の小規模なチャットボット程度であれば、ヘッジよりもまずキャッシュとモデル選択（Flash と Pro の使い分け）を先に詰めた方が費用対効果が高いです。私の場合は、4 サイトのうちトラフィック最上位の Dolice Labs 系では入れていますが、立ち上げたばかりの実験的なアプリには入れていません。

次に進めるなら、まず自分のアプリの p95 / p99 を 1 週間ぶん測ってみるところからです。Google Cloud の Monitoring か、Cloudflare Workers なら Analytics Engine で 30 分ほどで仕込めます。p99 と p50 の比を見て、4 倍を超えていたら、本記事のヘッジ実装をそのまま動かしてみてください。私自身もまだ最適閾値の探索を続けている途中ですが、長尾を抑える設計に同じ問題意識を持つ方の助けになれば嬉しく思います。
