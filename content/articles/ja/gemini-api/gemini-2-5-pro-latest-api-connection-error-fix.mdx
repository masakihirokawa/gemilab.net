「`gemini-2.5-pro-latest` を呼び出したら 404 で弾かれた」——これは Gemini API を本格的に使っている開発者なら、ほぼ全員が一度は通る道です。SDK のドキュメントには `latest` エイリアスが載っているのに、実際にリクエストすると `models/gemini-2.5-pro-latest is not found` と返ってくる。原因を理解していないと、その場しのぎでバージョンを直書きしてしまい、後でモデル更新に追従できなくなります。

このガイドでは、`-latest` エイリアスの仕様、404 や 400 が出る具体的な条件、そして本番環境で安全に使うためのフォールバック戦略を整理します。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

累計5,000万ダウンロードのアプリ群に Gemini を組み込んできた経験から、本番運用のコツを整理します。

## まず把握すべき: `-latest` エイリアスは「全モデルに用意されているわけではない」

Google の Generative Language API には、便利な `-latest` というエイリアスがいくつかあります。たとえば `gemini-1.5-pro-latest` や `gemini-1.5-flash-latest` は確実に存在し、最新のスナップショットを参照できます。

しかし `gemini-2.5-pro-latest` は、API のバージョンや有効化されているプロジェクト設定によって、解決できる時とできない時があります。これが多くの開発者を混乱させる原因です。

実際のレスポンス例（404 のケース）:

```json
{
  "error": {
    "code": 404,
    "message": "models/gemini-2.5-pro-latest is not found for API version v1beta",
    "status": "NOT_FOUND"
  }
}
```

このエラーが出た時、原因は次のいずれかです。

1. **API バージョンが合っていない**: `v1beta` と `v1` でモデル一覧が違います
2. **プロジェクトで Gemini 2.5 系がまだ有効化されていない**: 新規プロジェクトでは AI Studio から明示的に有効化が必要なケースがあります
3. **そもそも `gemini-2.5-pro-latest` というエイリアスが存在しない**: `gemini-2.5-pro` のような正式名のみが許可されている地域・SDK バージョンがあります

## 確実に存在するモデル名を確認する方法

まず、自分のプロジェクトで実際に使えるモデル一覧を取得してください。これが最も確実な切り分け方法です。

```bash
curl "https://generativelanguage.googleapis.com/v1beta/models?key=${GEMINI_API_KEY}" \
  | jq '.models[] | select(.supportedGenerationMethods[]? == "generateContent") | .name'
```

返ってくるリストが、あなたのプロジェクトで利用可能なモデルです。`gemini-2.5-pro-latest` がリストになければ、そのエイリアスはこの環境では使えません。

代わりに次のような正式名が出てきているはずです。

```
"models/gemini-2.5-pro"
"models/gemini-2.5-flash"
"models/gemini-2.0-flash"
"models/gemini-1.5-pro-latest"
```

この場合、`gemini-2.5-pro-latest` ではなく `gemini-2.5-pro` を直接指定してください。

## v1 と v1beta のモデル差分

API バージョンによって露出されるモデルが異なります。安定版（`v1`）は機能が限定される代わりにモデル一覧が安定しており、`v1beta` は最新機能（Function Calling のスキーマ拡張、Code Execution など）が使える代わりに、モデル名が頻繁に変わります。

私の運用経験では、本番アプリは `v1` の正式名（`gemini-2.5-pro` のように `-latest` を付けない）で固定し、開発用ツールやプロトタイプだけ `v1beta` を使うのが現実的です。`-latest` エイリアスは「便利そう」ですが、本番で使うとモデル更新タイミングで挙動が変わるリスクがあります。

## 400 Bad Request が出るケース

404 ではなく 400 が返る場合は、別の原因です。よくあるのが次の 3 パターンです。

**パターン A: `generationConfig` が古い形式**

`temperature` などのパラメータを `generationConfig` ブロックに入れていない場合、新しいモデルでは弾かれます。

```javascript
// ❌ 古い形式（モデルによっては動くが非推奨）
const response = await model.generateContent({
  contents: [{ role: "user", parts: [{ text: prompt }] }],
  temperature: 0.7
});

// ✅ 推奨形式
const response = await model.generateContent({
  contents: [{ role: "user", parts: [{ text: prompt }] }],
  generationConfig: { temperature: 0.7, maxOutputTokens: 2048 }
});
```

**パターン B: `safetySettings` のスレッショルド名が古い**

Gemini 2.5 系では、`HARM_BLOCK_THRESHOLD_UNSPECIFIED` を明示する必要があるケースがあります。`OFF` を設定したい場合は `BLOCK_NONE` を使います（`OFF` という値は無効）。

**パターン C: `system_instruction` を `contents` に混ぜてしまう**

Gemini 2.5 では `system_instruction` は専用フィールドに渡します。`contents` に `role: "system"` で混ぜると 400 になります。

```javascript
// ✅ 正しい形式
const result = await genAI.getGenerativeModel({
  model: "gemini-2.5-pro",
  systemInstruction: "あなたは丁寧な日本語のアシスタントです。"
}).generateContent(prompt);
```

## 本番で使える「壊れないモデル指定」戦略

私が個人開発のアプリで採用している方針は次の通りです。

```typescript
// config/gemini.ts
const PRIMARY_MODEL = "gemini-2.5-pro";
const FALLBACK_MODEL = "gemini-2.5-flash";
const LEGACY_FALLBACK = "gemini-1.5-pro-latest";

export async function generateWithFallback(prompt: string) {
  for (const modelName of [PRIMARY_MODEL, FALLBACK_MODEL, LEGACY_FALLBACK]) {
    try {
      const model = genAI.getGenerativeModel({ model: modelName });
      return await model.generateContent(prompt);
    } catch (e: any) {
      if (e.status === 404 || e.status === 400) {
        console.warn(`[Gemini] ${modelName} 失敗 → 次のモデルへ`);
        continue;
      }
      throw e;
    }
  }
  throw new Error("すべてのモデルで失敗しました");
}
```

ポイントは 3 つです。

1. **`-latest` を本番のプライマリにしない**: 正式名で固定する
2. **同世代の Flash をフォールバックに置く**: Pro が落ちても Flash は生きていることが多いです
3. **前世代の安定版をラストリゾートに**: `gemini-1.5-pro-latest` は長期間安定して提供されています

## それでも 404 が消えない時の最終確認

ここまで試しても 404 が出続ける場合、確認すべきことは次の通りです。

- API キーが正しいプロジェクトに紐づいているか（複数プロジェクトを使っている場合に間違えやすい）
- そのプロジェクトで Generative Language API が有効化されているか
- 課金アカウントが有効か（無料枠が切れていると一部モデルが使えなくなります）
- リージョン制限に引っかかっていないか（一部モデルは特定地域からのリクエストを受け付けません）

特に最後の「リージョン制限」は盲点になりがちです。VPN 経由のアクセスや、海外サーバーから日本のリージョン専用モデルを呼び出すと、ドキュメントに載っていない理由で 404 が返ることがあります。

## 次のアクション

まず curl でモデル一覧を取得して、自分のプロジェクトで使えるモデル名を確認してください。これで「`-latest` エイリアスが使えるかどうか」が一目でわかります。本番運用ではフォールバック戦略を組み込んで、Google 側のモデル更新やリージョン制限の変化に振り回されない構造にしておくと、夜中の障害対応が一気に減ります。
