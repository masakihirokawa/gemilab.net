月末にクラウドの請求画面を開くと、API の行だけ数字が少し増えていました。壁紙アプリや癒し系アプリを長く個人で運営していると、そういう朝が何度かあります。一件あたりの費用は小さくても、リクエスト数が積み上がれば、無視できない額になっていきます。

ひとりで開発している以上、費用も運用の手間も、できるだけ減らしておきたかったのです。それが、Gemini API を主力バックエンドとして試した最初の動機でした。

そこで、既存のアプリとは別に、Gemini API を最初から主力に据えたアプリを一つ立ち上げました。3ヶ月が経った今、何が予想どおりで、何が予想外だったのかを書き残しておきます。「自分のアプリに Gemini API を組み込もうか迷っている」という個人開発者の方に、少しでも参考になれば幸いです。

## 採用に至った経緯と判断の根拠

もともと同種の機能は、OpenAI の GPT-4o Mini で動かしていました。用途は、アプリ内の「今日の言葉」の自動生成と、ユーザーのテキスト入力に対する返答の2つです。月に数万件のリクエストが発生する構成で、当時の API 費用はおよそ月4〜6ドルでした。

切り替えた理由は3つあります。

**理由1: 無料枠の大きさ。** 当時の Gemini 2.5 Flash の無料枠は、1日あたり 1,500 リクエスト（RPD）、1分あたり 10 リクエスト（RPM）でした。個人開発のスモールスタートでは、この枠に収まるかどうかから試せることが大きな利点でした。ただし、この数値は私が検証した時点のものです。改定されることがあるため、実装の前に公式のレート制限のページで確かめてください。

**理由2: コンテキストウィンドウの広さ。** 引き寄せ系のアプリでは、ユーザーの過去の入力履歴をある程度踏まえた返答が求められます。Gemini 2.5 Pro の 100 万トークンというコンテキストは、会話履歴の圧縮や切り捨てをほとんど意識しなくてよいという、実装上の楽さに直結しました。

**理由3: Google のインフラへの信頼。** アプリの規模が育つほど、API が安定して提供され続けるかどうかは重くなります。月に数万件の呼び出しを支えてもらっている範囲では、少なくとも今のところ、困った場面はありません。

## 3ヶ月間のコストの実態

数字が一番正直な指標だと思うので、まず費用から書きます。

採用から3ヶ月のアプリ内 API 呼び出し数は、月平均で約 8,000〜12,000 件でした。Gemini 2.5 Flash で処理した場合のコストは次のとおりです。

```
月 10,000 リクエスト × 平均 500 トークン/リクエスト
= 500万 トークン / 月

Flash の料金（入力 $0.075/100万トークン、出力 $0.30/100万トークン）
= 入力費用: $0.375
+ 出力費用: 出力が平均 300 トークンとして $0.90
= 合計 約 $1.28 / 月
```

実際には、無料枠を超えた月が1ヶ月あり、その月は $1.50 程度を支払いました。残りの2ヶ月は無料枠に収まっています。

GPT-4o Mini の頃と比べると、費用は 1/3〜1/4 になった計算です。ただし、これは「同じ品質であれば」という前提の話です。料金の単価も改定されるため、上の計算は当時の価格表を置いた一例として読んでいただければと思います。

## 品質と精度：正直なところ

品質は、用途によって評価が分かれました。

**コンテンツ生成（今日の言葉）**：短い励ましのメッセージやアファメーション文を作るタスクでは、Gemini 2.5 Flash と GPT-4o Mini で体感できる差はほぼありませんでした。どちらも「人が書いたような自然な文」と「いかにも AI らしいパターン」のあいだを行き来していて、差を生んでいたのはモデルよりもプロンプトの設計でした。

**ユーザー入力への応答**：20〜50文字ほどの短い入力に対しては、Gemini のほうが少し「説明的すぎる」返答になることがありました。「なぜそう感じるのか」という理由を、長々と添えてくる傾向です。日本語のニュアンスを細かく整えたい場面では、いまも GPT-4o を使っています。

**日本語の自然さ**：全体として、Gemini 2.5 Flash の日本語は自然です。敬語のブレや、ですます調とだ・である調の混在も、システムプロンプトでおおむね抑えられます。「Gemini は英語寄り」という先入観を持っていましたが、少なくとも私の使い方では、日本語の品質に不満はありませんでした。

## レイテンシの実測値

個人開発でユーザー体験を左右するのは、コスト以上にレイテンシです。モバイルアプリでは、「返答が遅い」という感覚がそのままアプリの評価に響きます。

実測した中央値（p50）と95パーセンタイル（p95）は次のとおりです。

- **Gemini 2.5 Flash（非ストリーミング）**：p50 ≒ 900ms、p95 ≒ 2,800ms
- **Gemini 2.5 Flash（ストリーミング）**：最初のトークンまで p50 ≒ 400ms
- **GPT-4o Mini（非ストリーミング）**：p50 ≒ 700ms、p95 ≒ 2,200ms

Flash は、やや遅い傾向がありました。ただ、ストリーミングで最初のトークンを早く返す設計にすると、体感的な遅さはほとんど気にならなくなりました。

当時の記事では旧 SDK（`google-generativeai`）で書いていましたが、いまは新しい `google-genai` が現行です。以下はそちらに書き直したものです。

```python
from google import genai

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

# ストリーミングで最初のトークンを早く返す
for chunk in client.models.generate_content_stream(
    model="gemini-2.5-flash",
    contents="今日の朝に読みたい、短い前向きな言葉をひとつ教えてください",
):
    print(chunk.text, end="", flush=True)
```

モバイルのチャット UI では、ストリーミングにすると「返答が来ている」とユーザーが認識するまでの体感時間が大きく縮まります。

## Claude や GPT-4o との使い分け

いま、私のアプリ群では3つの API を目的別に使い分けています。

**Gemini 2.5 Flash**：短いコンテンツ生成、アファメーション文、ユーザーへの短い返答です。リクエスト数が多く、コストを抑えたい経路に置いています。

**Claude Sonnet 4.5**：アプリの設計判断の相談、プロンプトの改善、コードレビューです。「考えながら会話する」作業では、Claude のほうが折り合いがよいと感じています。

**GPT-4o**：微妙な日本語のニュアンスが要る場面や、ユーザーの感情的な投稿への対応です。数は少ないものの、ここだけは差が出ます。

「Gemini がいちばん優れている」と断言することは、私にはできません。大切なのは、どの API が何に向いているかを見極める、適材適所の感覚なのだと思います。

私自身、最初のうちはモデルの優劣ばかりを気にしていました。横並びの比較表をつくっては、どれが勝つかを眺めていたのです。結果は芳しくありませんでした。新しいモデルが出るたびに、比べ直しの作業が増えただけだったからです。

いまは、モデルを選ぶ前に、自分のアプリのどの経路がコスト律速で、どの経路が品質律速なのかを先に切り分けています。**比べるのはモデルではなく、経路です。** この仕分けさえできていれば、モデルが新しくなっても、差し替えは一行で済みます。

## 採用して良かったこと・想定外だったこと

**良かったこと**：

- 無料枠内で本番運用できる期間が、思ったより長く続きました。
- Google AI Studio でプロンプトを検証しやすく、モバイルからも開けました。
- コンテキストキャッシュを使うと、繰り返し使うシステムプロンプトの費用が大きく下がりました。

**想定外だったこと**：

- レート制限（RPM）の壁が、思ったより早く来ました。無料枠は RPM が低いため、バーストのある使い方には向きません。
- Gemini 2.5 Pro と Flash で、JSON モードの挙動に小さな差がありました。Pro は安定して構造化出力を返しますが、Flash は稀に形式が崩れます。
- SDK のバージョンアップの頻度が高く、小さな破壊的変更が入ることがありました。依存を固定していなかったために、ある朝、突然動かなくなったのです。

最後の点は、胃が痛くなる思いをしました。`requirements.txt` や `package.json` では、バージョンを明示的に固定しておくことをお勧めします。

```text
# requirements.txt
google-genai==<動作確認した版>  # 範囲指定ではなく、確認した版に固定する
```

## 無料枠の RPM 制限にぶつかったときの実装

想定外に挙げた「RPM の壁」について、実際にどう対処したかを書き添えます。Gemini 2.5 Flash の無料枠は、1分あたり10リクエスト（RPM）でした。1日 1,500 件（RPD）には余裕があっても、ユーザーの操作が特定の時間帯に集中すると、毎分の上限のほうが先に効いてきます。

私のアプリでは朝7〜8時台にアクセスが集まるため、この時間だけ 429（RESOURCE_EXHAUSTED）が散発するようになりました。最初のうちは、失敗したら即座に再送する実装にしていて、かえって 429 を増やしてしまいました。いまは指数バックオフ付きの再送に切り替え、ほぼ解消しています。

```python
import time
import random
from google import genai
from google.genai import errors

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

def generate_with_backoff(prompt, max_retries=5):
    for attempt in range(max_retries):
        try:
            return client.models.generate_content(
                model="gemini-2.5-flash", contents=prompt
            )
        except errors.APIError as e:
            if e.code != 429:
                raise  # 429 以外は待っても直らないので、そのまま上へ返す
            # 待ち時間は指数関数的に伸ばし、
            # 同時再送が重ならないよう乱数（ジッター）を足す
            time.sleep((2 ** attempt) + random.uniform(0, 1))
    raise RuntimeError("リトライ上限に達しました")
```

ポイントは、429 とそれ以外のエラーを区別することです。認証エラーや不正な引数まで一律でリトライすると、無駄な待ち時間が増えるだけで、何も解決しません。429 だけを拾って待つことが、無料枠を使い切らずに済ませるコツでした。

もう一段踏み込むなら、生成をキューに載せて、1分あたりの送信数を自前で8件ほどに絞る方法もあります。上限ぎりぎりを攻めるより、少し余裕を持たせたほうが、突発的なアクセス増にも耐えられるのだと感じています。

## 次のフェーズへ

3ヶ月使ってみた今の結論は、「個人開発のスモールスタートには、Gemini API は合理的な選択だった」というものです。

とくに月間リクエスト数が 10,000 件前後までの段階では、ほぼ無料で本番品質の生成 AI 機能を動かせます。費用を気にせず試行錯誤できる環境は、個人開発者にとって、失敗してもやり直せるという余白をつくってくれました。

次は、Gemini 2.5 Pro の Thinking Mode と、コンテキストキャッシュを組み合わせた費用設計を試すつもりです。まずは手元のアプリの経路を、コスト律速と品質律速に二つに分けるところから始めていただければ、と思います。
