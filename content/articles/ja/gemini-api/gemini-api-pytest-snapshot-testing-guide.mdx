Gemini API を使ったコードをテストしようとすると、すぐにある問題にぶつかります。**生成AIのレスポンスは毎回変わる**ので、通常のアサーションが使えないのです。

```python
# これは毎回失敗する可能性がある
assert response.text == "Pythonは汎用プログラミング言語です。"
```

解決策として最初に思いつくのが「レスポンスをモックにする」ですが、これだとAPIの動作が本当に変わったときに気づけません。モックのテストはモックをテストしているだけです。

私がたどり着いたのが、**スナップショットテスト**という手法です。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

2014年からの個人開発と AdMob 収益化の経験を踏まえて、現場で効くポイントだけ抽出します。

## スナップショットテストとは

スナップショットテストは「期待値を最初の実行時に記録して、以後の実行ではそれと比較する」テスト手法です。

```
初回実行 → レスポンスを記録（スナップショット作成）
2回目以降 → 前回のスナップショットと比較
```

完全一致ではなく、**構造と重要フィールドの一致**を検証するのがポイントです。これにより、テキスト内容が変わっても構造が壊れていないことを確認できます。

Python では [syrupy](https://github.com/syrupy-project/syrupy) が定番のライブラリです。

## セットアップ

```bash
pip install syrupy pytest
```

`conftest.py` にスナップショット用のフィクスチャを追加します。

```python
# conftest.py
import pytest
from syrupy.assertion import SnapshotAssertion

@pytest.fixture
def snapshot(snapshot):
    return snapshot
```

## 基本的なスナップショットテスト

まず、Gemini API のレスポンス全体をスナップショットとして保存するシンプルな例から始めます。

```python
# test_gemini_basic.py
import pytest
import google.generativeai as genai

def test_gemini_response_structure(snapshot):
    """レスポンスの構造が変わっていないことを検証する"""
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.0-flash")
    
    response = model.generate_content(
        "What is 2 + 2?",
        generation_config=genai.types.GenerationConfig(
            temperature=0,    # 再現性のために temperature=0 を設定
            max_output_tokens=100
        )
    )
    
    # レスポンスのキー構造だけをスナップショットで検証
    snapshot_data = {
        "has_text": response.text is not None,
        "finish_reason": str(response.candidates[0].finish_reason),
        "safety_ratings_count": len(response.candidates[0].safety_ratings),
    }
    
    assert snapshot_data == snapshot
```

初回実行時は `--snapshot-update` フラグで実行します。

```bash
pytest test_gemini_basic.py --snapshot-update
```

これで `__snapshots__/test_gemini_basic.ambr` というファイルが生成され、スナップショットが記録されます。2回目以降は通常の `pytest` コマンドで実行するだけです。

## 実用的なパターン：構造検証

実際のアプリでよく使うパターンは、テキスト内容ではなくスキーマ（構造）を検証することです。

```python
# test_gemini_structured.py
import pytest
import json
import google.generativeai as genai

def test_gemini_json_output_schema(snapshot):
    """JSON形式の出力スキーマが維持されているかを検証する"""
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.0-flash")
    
    prompt = """
    Analyze the sentiment of this text and respond in JSON format:
    Text: "I really enjoyed using this product."
    
    Required JSON fields: sentiment (positive/negative/neutral), confidence (0.0-1.0), explanation
    """
    
    response = model.generate_content(
        prompt,
        generation_config=genai.types.GenerationConfig(
            temperature=0,
            response_mime_type="application/json"
        )
    )
    
    parsed = json.loads(response.text)
    
    # スキーマ（フィールドの存在と型）だけを検証
    schema_snapshot = {
        "has_sentiment": "sentiment" in parsed,
        "sentiment_valid": parsed.get("sentiment") in ["positive", "negative", "neutral"],
        "has_confidence": "confidence" in parsed,
        "confidence_is_float": isinstance(parsed.get("confidence"), float),
        "has_explanation": "explanation" in parsed,
    }
    
    assert schema_snapshot == snapshot
```

## temperature=0 にしてもテキストが変わる問題

`temperature=0` を設定してもレスポンスのテキストが毎回変わることがあります。これはGeminiの内部サンプリング処理が完全に決定論的ではないためです。

そのため、**テキスト内容ではなく構造・メタデータを検証する**設計が安定します。

```python
def test_gemini_response_metadata(snapshot):
    """テキスト内容ではなくメタデータを検証する"""
    # ...
    
    metadata_snapshot = {
        # テキスト内容は含めない
        "finish_reason": str(response.candidates[0].finish_reason),
        "model_used": "gemini-2.0-flash",  # モデル名は変わらないはず
        "has_prompt_feedback": hasattr(response, "prompt_feedback"),
    }
    
    assert metadata_snapshot == snapshot
```

## APIコール数を削減するキャッシュ戦略

テストのたびにAPIを呼ぶとコストと時間がかかります。`pytest-recording` と `vcrpy` を組み合わせると、最初の実行時だけ本物のAPIを叩いて、以後はキャッシュを使えます。

```bash
pip install pytest-recording vcrpy
```

```python
# pytest.ini に設定
[pytest]
addopts = --record-mode=none  # デフォルトはキャッシュ使用

# テストに @pytest.mark.vcr デコレーターを付ける
@pytest.mark.vcr
def test_gemini_with_cache(snapshot):
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.0-flash")
    
    response = model.generate_content("What is the capital of Japan?")
    
    snapshot_data = {
        "has_response": response.text is not None,
        "finish_reason": str(response.candidates[0].finish_reason)
    }
    
    assert snapshot_data == snapshot
```

初回は `--record-mode=new_episodes` で実行して録画、以後は `--record-mode=none` でキャッシュを再生します。

## スナップショットを更新するタイミング

スナップショットは以下の場合に更新が必要です。

- Gemini API のバージョンを上げて、レスポンス構造が変わったとき
- 意図的にプロンプトを変更して、出力の構造も変えたとき
- 検証項目を追加・変更したとき

更新は `--snapshot-update` フラグだけでできます。更新後は必ず diff を確認して、意図しない変更が含まれていないかチェックします。

```bash
pytest --snapshot-update
git diff __snapshots__/  # スナップショットの変更内容を確認
```

## テスト設計の考え方

Gemini API のテストで大切なのは「何を保護したいか」を明確にすることです。

- **テキストの内容** → スナップショットには向かない（毎回変わる）
- **レスポンスの構造** → スナップショットが有効
- **エラーハンドリング** → 通常のアサーションが有効
- **レイテンシ・コスト** → ベンチマークテストが必要

スナップショットテストは「構造の監視」として使い、内容のテストは別の方法と組み合わせるのが現実的です。この考え方がはっきりすると、どこにテストを書くかの迷いが減ります。
