スマートフォンで撮った写真を、何の前処理もせず Gemini API に投げていた時期がありました。商品画像から名前と推定価格を JSON で取り出す個人プロジェクトで、レスポンスが返るまで毎回 8〜12 秒かかります。

気になって `usage_metadata` を開くと、画像 1 枚で文字だけのリクエストとは桁違いのトークンを消費していました。長辺を 1024px に縮小してから送るようにしたところ、同じ用途で返答は 2〜3 秒まで縮んでいます（いずれも手元の環境での体感に近い計測です）。

ここでは、なぜそうなるのかを公式ドキュメントの数え方から辿り直し、私が落ち着いた前処理のかたちを書き残します。

**縮める前に、まず数えます。** この順番を守るだけで、前処理の失敗はかなり減ったと感じています。

## 画像は「ファイル単位」ではなく「タイル単位」で数えられる

最初にお伝えしたいのは、Gemini API が画像を 1 枚いくら、という単位では数えていないことです。

Google の公式ドキュメント（Image understanding）には、次の趣旨が書かれています。

- 縦横とも 384px 以下の画像は 258 トークン
- それより大きい画像は 768×768 のタイルに分けて処理し、タイル 1 枚あたり 258 トークン
- タイル数は、短辺を 1.5 で割った切り出し単位（crop unit）で縦横を割って掛け合わせる考え方で、例として 960×540 の画像は 6 タイル

ドキュメントの記述はあくまで目安の説明です。そこで私は、この式を小さな関数にして手元で見積もるようにしました。切り出し単位を 256〜768 に収めているのは、私が見積もりのために置いた近似です。

```python
import math

def estimate_image_tokens(width: int, height: int) -> tuple[int, int]:
    """公式ドキュメントのタイル計算に基づく見積もり。(タイル数, トークン数)

    あくまで目安です。正確な値は後述の count_tokens で確認してください。
    """
    if max(width, height) <= 384:
        return 1, 258
    unit = math.floor(min(width, height) / 1.5)
    unit = min(max(unit, 256), 768)  # 見積もり用の近似
    tiles = math.ceil(width / unit) * math.ceil(height / unit)
    return tiles, tiles * 258
```

表を作って意外だったのは、1280px・1024px・768px の 3 行が同じ値に並んだことです。この見積もりが正しければ、長辺を 1024px から 768px に削っても、トークンは減りません。減るのは、タイル数が階段状に落ちる境目をまたいだときだけです。

「小さければ小さいほど安い」と思い込んで縮めすぎると、精度だけが落ちて料金は同じ、という結果になりかねません。

## なぜクライアント側での縮小が効くのか

API 側でも、大きすぎる画像は内部で調整されます。ただ、それはリクエストを通すための仕組みであって、料金を抑えてくれる仕組みではありません。クライアント側で先に整えると、3 つの効果がはっきり出ます。

1. **トークン消費が減る** — タイル数がそのまま料金に効きます。4032×3024 から 1024px にすれば、見積もり上は 24 タイルが 4 タイルです
2. **アップロードが速くなる** — 数 MB の JPEG が 200KB 前後になり、家庭用回線では数秒の差が出ます
3. **リクエストが上限に近づきにくくなる** — インラインで送る場合、プロンプトとバイト列を合わせたリクエスト全体が 20MB までです。1 リクエストに複数枚を載せるなら、この余裕が効きます

## 私が普段使っている前処理関数

Pillow の `thumbnail()` は、アスペクト比を保ったまま長辺を指定サイズに収めてくれます。`resize()` のように縦横比を自分で計算せずに済み、元の画像オブジェクトをその場で縮める点も扱いやすいところです。

```python
from PIL import Image, ImageOps
from io import BytesIO

def prepare_image_for_gemini(
    src_path: str,
    max_side: int = 1024,
    jpeg_quality: int = 85,
) -> tuple[bytes, str]:
    """Gemini API に渡すための画像前処理。

    - 長辺 max_side ピクセルに縮小（アスペクト比は保持）
    - JPEG として再エンコード（透過は捨てる）
    - 戻り値: (バイト列, mime_type)
    """
    with Image.open(src_path) as img:
        # EXIF の向きを実ピクセルに反映しておく
        img = ImageOps.exif_transpose(img)
        # RGBA / P モードは RGB に変換（JPEG にするため）
        if img.mode != "RGB":
            img = img.convert("RGB")
        img.thumbnail((max_side, max_side), Image.Resampling.LANCZOS)
        buf = BytesIO()
        img.save(buf, format="JPEG", quality=jpeg_quality, optimize=True)
        return buf.getvalue(), "image/jpeg"
```

呼び出し側は、次のように書いています。

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")
image_bytes, mime = prepare_image_for_gemini("photo.jpg", max_side=1024)

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=[
        types.Part.from_bytes(data=image_bytes, mime_type=mime),
        "この商品の名前と推定価格を JSON で返してください。",
    ],
)
print(resp.usage_metadata)
```

`Image.Resampling.LANCZOS` は Pillow 9.1.0 以降の書き方です。それ以前のバージョンでは `Image.LANCZOS` を使ってください。

`ImageOps.exif_transpose()` を入れているのは、向きの情報を実ピクセルに焼き込んでおくためです。公式ドキュメントは EXIF の扱いに触れておらず、「画像が正しい向きになっていることを確認する」という注意があるだけです。横向きに撮った写真が縦扱いで渡ると読み取りが乱れるので、確認の手間を一行で省いている、という位置づけです。私も一度、向きのずれで商品ラベルを読み違えられて、原因探しに手間取りました。

## 縮める前に count_tokens で数える

見積もりの表は、あくまで私の手元の計算です。モデルの世代が変われば数え方も変わりうるため、実際に使うモデルで数えて確かめる癖をつけています。

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

for size in (4032, 1280, 1024, 768, 384):
    data, mime = prepare_image_for_gemini("test.jpg", max_side=size)
    counted = client.models.count_tokens(
        model="gemini-2.5-flash",
        contents=[types.Part.from_bytes(data=data, mime_type=mime)],
    )
    print(size, len(data), counted.total_tokens)
```

`count_tokens` はテキストだけでなく画像を含む `contents` も数えられるので、本番のリクエストを送る前に同じ入力で比べられます。実際の入力画像を 1 枚使って回すと、トークン数が階段状に下がる位置が見えるはずです。見積もりの表と食い違ったら、表ではなく実測のほうを信じます。

`count_tokens` の推定と実際の請求がずれたときの切り分けは、[count_tokens の推定と実課金のズレをまとめた別記事](/articles/gemini-api/gemini-api-count-tokens-billing-mismatch-fix) が参考になります。

## 「小さすぎて精度が落ちる」境目を知る

縮小しすぎると、認識精度のほうが先に落ちます。私が手元の商品画像 200 枚ほどで試したときの目安は、次のとおりでした（あくまで私の用途での目安です）。

- **商品ラベル・OCR が目的のとき**: 長辺 1280px 以上を保ちます（細かい文字が潰れません）
- **物体識別・カテゴリ分類**: 長辺 1024px で十分
- **シーン理解・全体の状況把握**: 長辺 768px でも精度はほぼ変わりませんでした
- **顔の特徴を扱う用途**（プライバシーに配慮した範囲のみ）: 長辺 1280px 以上

先ほどの表を重ねると、1280px・1024px・768px はどれも見積もり上は同じ 4 タイルです。であれば、トークンの面では 768px に縮めても得るものがなく、精度の余裕を残せる 1024px か 1280px を選ぶほうが理にかなっています。

OCR 用途では、文字部分だけを切り出してから縮小するとさらに安定します。`pytesseract` でおおまかな文字領域を検出し、その周辺だけを送る形を併用しています。

[画像が認識されないときの診断記事](/articles/gemini-api/gemini-api-image-input-not-recognized-troubleshooting) と組み合わせて読むと、`mime_type` の付け方や向きのトラブルも合わせて整理できます。

## iPhone の HEIC 写真はどう扱うか

iPhone の写真は、設定によっては HEIC 形式で保存されます。公式ドキュメントの対応形式には `image/heic` と `image/heif` も含まれているので、HEIC のまま送ること自体は可能です。

ただし、縮小したいなら Pillow で開く必要があります。標準の Pillow は HEIC を読めないため、`pillow-heif` を追加して登録しておくと、前処理関数をそのまま使えます。

```python
from pillow_heif import register_heif_opener

register_heif_opener()  # これ以降、Image.open() が HEIC を扱える
image_bytes, mime = prepare_image_for_gemini("IMG_0001.HEIC", max_side=1024)
```

縮小後は JPEG で再エンコードするので、送る側の `mime_type` は常に `image/jpeg` に揃います。形式ごとの分岐を呼び出し側に持ち込まずに済むのが、この形のいちばんの利点です。

## File API か inline_data か

インラインで送る場合は、プロンプト・システム指示・画像バイト列を合わせたリクエスト全体が 20MB に収まる必要があります。収まらないときは File API を使います。長辺を 1024px に縮めておけば、単発の画像認識でインラインが足りなくなることはまずありません。

私が File API を選ぶのは、次の 2 つに限っています。

- 同じ画像を複数回のリクエストで使い回したいとき（アップロードしたファイルは 48 時間保持されます）
- 動画や大容量 PDF など、インラインでは収まらないファイルを扱うとき

単発の画像認識なら、インラインのほうが往復が 1 回少なく、体感も速いです。なお 1 リクエストに載せられる画像は最大 3,600 枚までで、枚数が多いバッチでは先にこの上限と 20MB のどちらに先に当たるかを見ておくと安心です。

## Gemini 3 世代では media_resolution も選べる

Gemini 3 世代のモデルでは、`media_resolution` というパラメータで、画像や動画フレーム 1 枚に割り当てる最大トークン数を指定できます。公式ドキュメントによれば、解像度を上げると細部の認識は良くなる一方で、トークン消費とレイテンシも増えます。

ここで私が決めている線引きは、次のとおりです。

- 送る画像そのものの大きさは、Pillow で自分が決めます
- 1 枚あたりに許すトークンの上限は、`media_resolution` で API に伝えます

役割が違うので、片方だけで済ませず両方を意識しています。レベルごとの具体的なトークン数は、ドキュメントの現行の表で確認してください。

## 自分のプロジェクトで効果を確認する

前処理を入れたあとは、バッチ処理の所要時間にも差が出ます。数百枚の商品画像をまとめて処理するスクリプトで、前処理を入れる前は 3 時間ほどかかっていたものが、`prepare_image_for_gemini` を挟んだあとは 40 分前後になりました。アップロード時間とトークン数の両方が効いた結果だと見ています。

実測するときは、次の順で進めるのがおすすめです。

1. 手元の代表的な画像を 5〜10 枚選びます
2. `count_tokens` で、元のサイズと 1024px の両方を数えます
3. 精度が必要な用途なら、同じプロンプトで出力の違いも見比べます

数字と出力の両方を並べて初めて、縮めてよいサイズの線が引けます。
