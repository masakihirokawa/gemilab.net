「ローカル環境では問題なく動いていた Gemini API のコードが、Vercel にデプロイした途端に 500 エラーを返すようになる」— このパターンで半日潰した経験がある方は多いのではないでしょうか。私も個人アプリの API を Cloudflare Workers に移した初日に同じ現象でハマりました。

サーバーレス環境で Gemini API が動かない時の原因は、ほとんどが次の3つに集約できます。環境変数の扱い、ランタイム（Node vs Edge）の違い、そして応答時間の上限です。これらを順番に潰していけば、9割のケースは解決します。

## まず切り分ける: ローカルと同じコードが本当に動いているか

サーバーレスでの失敗は、ログが十分に出ない環境で起きるとデバッグが一気に難しくなります。原因の切り分けを始める前に、最小構成のテストエンドポイントを用意しておくと後が楽です。

```ts
// app/api/gemini-health/route.ts (Next.js App Router)
import { GoogleGenerativeAI } from "@google/generative-ai";

export async function GET() {
  const apiKey = process.env.GOOGLE_API_KEY;
  if (\!apiKey) {
    return Response.json(
      { ok: false, reason: "GOOGLE_API_KEY is not defined" },
      { status: 500 }
    );
  }

  try {
    const genai = new GoogleGenerativeAI(apiKey);
    const model = genai.getGenerativeModel({ model: "gemini-2.5-flash" });
    const t0 = Date.now();
    const result = await model.generateContent("ping とだけ返してください");
    return Response.json({
      ok: true,
      text: result.response.text(),
      ms: Date.now() - t0,
      keyPrefix: apiKey.slice(0, 6), // 値そのものは露出させない
    });
  } catch (e: unknown) {
    const err = e as Error;
    return Response.json({ ok: false, name: err.name, message: err.message }, { status: 500 });
  }
}
```

このヘルスチェックを叩いて `ok: false` が返ってきた時の `reason` と `message` が、後続の切り分けの起点になります。`keyPrefix` は API キーの先頭数文字だけを返しているので、環境変数が別の値に上書きされていないかの確認にも使えます。

## 原因1: 環境変数が本番で読めていない

サーバーレス障害の体感 5〜6 割はこれです。ローカルでは `.env.local` から自動で読み込まれるので、デプロイ先で改めて設定する必要があることを忘れがちです。

### Vercel の場合

プロジェクトダッシュボードの「Settings → Environment Variables」で `GOOGLE_API_KEY`（またはあなたが使っているキー名）を設定します。ここで注意したいのが **Preview と Production の環境を分けて登録する必要がある** 点です。Production だけに登録して Preview デプロイで API 呼び出しが失敗するケースは典型的な落とし穴です。

また、Vercel では環境変数を設定した後に **再デプロイしないと反映されません**。既存のデプロイの Environment を更新するだけでは、ランタイムの環境変数は古いままです。Vercel CLI なら `vercel --prod` で再デプロイ、GitHub 連携なら空コミットを push するのが一番早いです。

### Cloudflare Workers の場合

`wrangler.toml` に平文で書くとリポジトリに秘密が残るので、必ず `wrangler secret put GOOGLE_API_KEY` でシークレットとして登録します。

```bash
# Cloudflare Workers にシークレットを登録
wrangler secret put GOOGLE_API_KEY
# プロンプトが出るので値を貼り付ける

# 登録されているシークレット一覧の確認
wrangler secret list
```

Workers の場合、環境変数は `process.env` ではなく、関数の引数経由（`export default { fetch(req, env) { env.GOOGLE_API_KEY } }`）で渡されるのが一番の違いです。Next.js からそのまま移植すると、`process.env.GOOGLE_API_KEY` が `undefined` になります。

### AWS Lambda の場合

AWS コンソールの関数設定から Environment variables を設定するか、SAM / Serverless Framework / CDK の設定に書きます。Lambda の場合は KMS で暗号化できるのでシークレット管理の観点では楽ですが、**SDK のバージョンによっては関数のコールドスタート時にしか環境変数を読まない** ものもあります。リクエストごとに `process.env` を再評価するコードを書いておくと事故を防げます。

## 原因2: Edge ランタイムで Node.js 前提の SDK が動いていない

2番目に多いのがこれです。Vercel の Edge Functions や Cloudflare Workers は V8 isolate ベースで動いていて、Node.js の標準ライブラリ（`fs`, `crypto`, `stream` など）の一部が使えません。

Gemini 公式 SDK の中でも `@google/generative-ai`（JavaScript / TypeScript 用）は Edge ランタイムでも動きますが、サーバーサイド用の `@google-cloud/vertexai` は Node.js 依存が強いのでそのままでは動きません。Python の `google-generativeai` は Edge ランタイム（Vercel Python 関数など）とは相性が悪く、基本的に Node.js 用のサーバーレス関数で動かすのが無難です。

Next.js のルートハンドラで Edge ランタイムに切り替えてしまっていないかも確認しましょう。

```ts
// ❌ これが付いているとEdgeランタイム扱い
export const runtime = "edge";

// ✅ Node.jsランタイムに明示的に戻す
export const runtime = "nodejs";
```

Edge で動かしたい理由がなければ、`nodejs` に戻すのが最も簡単な解決策です。Edge のコールドスタートの速さと引き換えに失うものが多く、特にストリーミングや長時間のリクエストで痛みます。

Edge をどうしても使いたい場合は、`fetch` を直接叩いて REST API として Gemini を呼び出すのが最も堅実です。

```ts
// Edge ランタイムでも動く fetch ベースの呼び出し
export const runtime = "edge";

export async function POST(req: Request) {
  const { prompt } = await req.json();
  const url =
    "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" +
    `?key=${process.env.GOOGLE_API_KEY}`;

  const res = await fetch(url, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      contents: [{ parts: [{ text: prompt }] }],
    }),
  });

  if (\!res.ok) {
    return Response.json({ error: await res.text() }, { status: res.status });
  }
  return Response.json(await res.json());
}
```

SDK を使うと便利ですが、Edge 環境では「SDK が何をしているか」を把握しておかないとブラックボックスなエラーに悩まされます。fetch 直叩きは冗長ですが、トラブル時の切り分けは明確に楽です。

## 原因3: プラットフォームのタイムアウト上限に引っかかっている

ローカルでは 10 秒以上かかっても平気な処理が、本番で 504 を返すようになる。これはほぼ確実にプラットフォームのタイムアウト制限に引っかかっています。

主要サービスのデフォルト上限は次のとおりです。Vercel Hobby プランの Serverless Functions は 10 秒、Pro プランで 60 秒まで、Fluid Compute 対応関数で最大 300 秒。Cloudflare Workers の CPU 時間は無料プランで 10ms、有料 Paid プランで 30 秒まで（ただし壁時計時間は無制限）。AWS Lambda はデフォルト 3 秒で最大 15 分まで設定可能。

Gemini 2.5 Pro は複雑なプロンプトだと平気で 20 〜 40 秒かかることがあります。Hobby プランの Vercel でそのまま動かすとほぼ確実に失敗するので、対策が必要です。

### 対策1: ストリーミングレスポンスにする

ストリーミングにすると、最初のトークンが返ってきた時点でレスポンスが開始されるので、タイムアウトに引っかかりにくくなります。

```ts
import { GoogleGenerativeAI } from "@google/generative-ai";

export async function POST(req: Request) {
  const { prompt } = await req.json();
  const genai = new GoogleGenerativeAI(process.env.GOOGLE_API_KEY\!);
  const model = genai.getGenerativeModel({ model: "gemini-2.5-pro" });

  const stream = await model.generateContentStream(prompt);

  // Web 標準の ReadableStream に変換
  const readable = new ReadableStream({
    async start(controller) {
      const encoder = new TextEncoder();
      for await (const chunk of stream.stream) {
        controller.enqueue(encoder.encode(chunk.text()));
      }
      controller.close();
    },
  });

  return new Response(readable, {
    headers: { "Content-Type": "text/plain; charset=utf-8" },
  });
}
```

### 対策2: 軽いモデルに切り替える

すべての処理に Gemini 2.5 Pro は必要ありません。短い要約や分類なら Gemini 2.5 Flash が 3 〜 5 倍速く、料金も 10 分の 1 以下で済みます。ユーザー体験を左右しない後処理だけを Pro に残し、リクエストパスは Flash で捌く構成にすると、タイムアウト問題もコストも同時に解決します。

モデル選択の基準については [Gemini 2.5 Pro と Flash の使い分け](/articles/gemini-api/gemini-api-production-error-handling-rate-limit-guide) も参考になります。

### 対策3: 非同期ジョブ化する

30 秒を超えることが明らかな処理（長文生成、大量データの分析など）は、そもそもリクエスト・レスポンスのサイクル内で完結させない設計にします。Vercel なら `waitUntil` を使ってバックグラウンドで処理し、結果は Webhook や DB ポーリングで受け取る。Cloudflare Workers なら Queue や Durable Objects を使う。最初の設計で割り切るのが一番コスパが良いです。

## デバッグを楽にする小さな工夫

サーバーレスのログは出るまでタイムラグがあったり、巻き戻りが難しかったりします。トラブルが起きた時に初動を早めるために、API キーの指紋と SDK バージョンを起動時にログに出しておくのがおすすめです。

```ts
console.log("[gemini-api] key prefix:", process.env.GOOGLE_API_KEY?.slice(0, 6));
console.log("[gemini-api] sdk version:", require("@google/generative-ai/package.json").version);
console.log("[gemini-api] runtime:", typeof EdgeRuntime \!== "undefined" ? "edge" : "node");
```

この3行があるだけで、「環境変数が別物になっている」「ランタイムが意図と違う」といった事故を数秒で特定できます。

サーバーレス開発を効率化する書籍としては、[AWSではじめるサーバーレスアプリケーション開発（佐々木拓郎 ほか）](https://www.amazon.co.jp/dp/4297128802/?tag=pinocchio-22) が日本語で体系的にまとまっており、Lambda 経由での API 構築パターンを学ぶのに役立ちます。Cloudflare Workers に特化するなら [Serverless Architectures on AWS（Peter Sbarski）](https://www.amazon.co.jp/dp/1617295825/?tag=pinocchio-22) の考え方も応用できます。

## まずやること

もしいま本番で動かないなら、最初に疑うのは環境変数です。`wrangler secret list` や Vercel ダッシュボードで `GOOGLE_API_KEY` が本当に登録されているか、しかも Preview / Production の両方に入っているかを確認してください。これだけで体感 6 割は解決します。

それでも失敗する場合は本記事のヘルスチェックエンドポイントを設置し、ランタイムとタイムアウトを順に潰していけば、ほぼ必ず原因に辿り着きます。Gemini API 側の問題であることは経験上かなり少なく、ほとんどが手元の環境の問題です。落ち着いて一つずつ切り分けていけば大丈夫です。

デプロイ時のエラーハンドリング全般については [Gemini API のレスポンスが遅い・タイムアウトする時の対処法](/articles/gemini-api/gemini-api-slow-response-timeout-fix) も合わせて読むと、本番環境での安定運用の引き出しが増えます。
