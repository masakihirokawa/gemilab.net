日本語で書いた原稿を Gemini API に渡して英語サマリーを返してもらう、そんな単純な処理を書いたはずなのに、出力の末尾だけ日本語が顔を出してしまう——。私は個人開発で多言語ブログを運営しており、この現象に何度も遭遇しました。公式ドキュメントには「System Instructions で言語を指定してください」とだけ書かれていますが、実際にはそれだけでは止められないケースがあります。

Gemini API で「出力言語が意図せず混ざる」問題を、再現性の高い方法で抑え込むための実装パターンを実例とともに整理しました。特別な最新機能ではなく、System Instructions・Few-shot プロンプト・`response_schema`・出力後のバリデーションという、今日から使える組み合わせで対処します。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

2014年からの個人開発と AdMob 収益化の経験を踏まえて、現場で効くポイントだけ抽出します。

## なぜ英語を指示しても日本語が混ざるのか

Gemini は大量の多言語コーパスで学習されており、「入力言語に引っ張られる」傾向があります。入力が日本語で、プロンプトの末尾に英語で「Answer in English」と添えると、モデルの注意（attention）の大半は日本語の入力本文に向いており、指示文の強度が相対的に弱くなります。特に、入力が長く、指示が短い場合ほど起きやすいのが特徴です。

もう一つの要因が「固有名詞の流入」です。日本語の人名・地名・商品名がそのまま残るだけならまだしも、一文まるごと日本語で挿入されてしまうことがあります。これは、モデルが「この部分は翻訳できない／そのまま保持したほうが正確」と判断した結果で、指示を強めない限り止まりません。

私が試した範囲では、短いプロンプトならどのモデルでも安定するのですが、2,000 トークンを超えるあたりから Gemini 2.0 Flash でも混入が目立ち始めます。2.5 Pro / 3.1 Pro でも完全にゼロにはならないため、「モデルの能力を上げれば直る」という発想は捨てたほうが現実的です。

## System Instructions で「出力言語」を最優先制約として書く

まず基本となるのが System Instructions での明示です。ここで重要なのは、「英語で答えてください」と本文の末尾に添えるのではなく、System Instructions に「This assistant must respond in English only」のような強い制約として書くことです。System Instructions は本文プロンプトよりも重みが強く扱われる設計になっています。詳しい仕組みは [System Instructions 完全マスター](/articles/gemini-api/system-instructions-guide) に書きましたので、併せて参照してください。

書き方の推奨は次の通りです。

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

system_instruction = """
You are a professional English-language technical editor.
RULES:
1. You MUST respond entirely in English.
2. Do not include any Japanese characters (hiragana, katakana, or kanji) in your output.
3. If a Japanese term is essential (e.g. a product name), render it in romaji with an English gloss in parentheses.
4. If you cannot comply, respond with "UNABLE_TO_COMPLY" and stop.
"""

response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="以下の日本語記事を英語で300語以内に要約してください。\n\n" + article_body,
    config=types.GenerateContentConfig(
        system_instruction=system_instruction,
        temperature=0.2,
    ),
)
print(response.text)
```

ポイントは、許可リスト（ローマ字なら可）と違反時の動作（`UNABLE_TO_COMPLY` と返す）まで書いてしまうことです。こうすると、混入が避けられないケースでモデルが「がんばって日本語を混ぜる」のではなく、明示的な失敗で返してくれるため、後段でリトライ処理に回しやすくなります。

`temperature` は 0.2〜0.4 あたりに下げておくと、言語指示への追従性が高まります。クリエイティブさよりも一貫性が欲しいタスクなので、ここは低めで良いと考えています。

## Few-shot プロンプトで期待する出力パターンを見せる

System Instructions だけで止まらない場合、Few-shot exemplar を 1〜2 組入れると安定します。これは「ルールを書く」よりも「例を見せる」ほうがモデルの追従性が高いという、プロンプトエンジニアリングの一般論をそのまま適用しています。

```python
few_shot_examples = [
    {
        "input": "東京の天気について教えて",
        "output": "Tokyo has four distinct seasons with hot humid summers (around 30 degC) and mild winters. Annual rainfall averages 1,500 mm."
    },
    {
        "input": "このアプリの料金プラン",
        "output": "The app offers three pricing tiers: Free, Pro (USD 5/month), and Team (USD 20/month per seat)."
    },
]

few_shot_block = "\n\n".join([
    f"### Example\nInput (Japanese): {e['input']}\nOutput (English only): {e['output']}"
    for e in few_shot_examples
])

prompt = f"""{few_shot_block}

### Task
Input (Japanese): {user_input}
Output (English only):"""

response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=prompt,
    config=types.GenerateContentConfig(
        system_instruction=system_instruction,
        temperature=0.2,
    ),
)
```

Few-shot を入れる効果は、短いプロンプトよりも「長文＋複雑タスク」のときに顕著です。私が運営している英語ブログの翻訳パイプラインでは、Few-shot を 2 組入れるだけで混入率が体感で 1/10 以下になりました。ただし Few-shot はトークンを消費するので、シンプルなタスクなら System Instructions だけで十分です。

## `response_schema` で言語フィールドを強制する

出力を構造化データとして受け取る場合、`response_schema` に `language` フィールドを入れて「英語であること」をメタデータレベルで確認する方法があります。これは Pydantic と組み合わせると強力で、受け取った瞬間にバリデーションできるのが利点です。実装詳細は [Gemini API × Pydantic 型安全な構造化出力](/articles/gemini-api/gemini-api-pydantic-structured-output-type-safe-production) が詳しいので、こちらも参考にしてください。

```python
from pydantic import BaseModel, Field, field_validator
import re

class EnglishSummary(BaseModel):
    language: str = Field(description="Must be 'en'")
    title: str = Field(description="English title")
    summary: str = Field(description="English summary, 100-300 words")

    @field_validator("language")
    @classmethod
    def must_be_en(cls, v: str) -> str:
        if v.lower() \!= "en":
            raise ValueError(f"Expected language='en', got '{v}'")
        return v

    @field_validator("title", "summary")
    @classmethod
    def no_japanese(cls, v: str) -> str:
        if re.search(r"[\u3040-\u30ff\u4e00-\u9fff]", v):
            raise ValueError("Japanese characters detected in output field")
        return v

response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="以下の記事を英語で要約してください:\n\n" + article_body,
    config=types.GenerateContentConfig(
        system_instruction=system_instruction,
        response_mime_type="application/json",
        response_schema=EnglishSummary,
    ),
)

parsed = response.parsed  # EnglishSummary インスタンス
```

`field_validator` で「ひらがな・カタカナ・漢字の Unicode 範囲」を検出しているのがポイントです。検出されたら `ValidationError` が投げられるので、`try/except` で捕捉してリトライに回せます。`response.parsed` は Gemini SDK が Pydantic で自動パースしてくれるため、手作業の JSON デコードは不要です。

## 混入を検出したら「再生成」ではなく「再指示」を試す

バリデーションで日本語混入を検出したとき、単純に同じプロンプトをもう一度投げても同じ結果になりがちです。そこで私が使っている工夫が「指示を強めた二段階リトライ」です。

```python
def generate_english_with_retry(article_body: str, max_retries: int = 2) -> EnglishSummary:
    base_prompt = f"以下の記事を英語で要約してください:\n\n{article_body}"

    for attempt in range(max_retries + 1):
        try:
            response = client.models.generate_content(
                model="gemini-2.5-pro",
                contents=base_prompt,
                config=types.GenerateContentConfig(
                    system_instruction=system_instruction,
                    response_mime_type="application/json",
                    response_schema=EnglishSummary,
                    temperature=0.2,
                ),
            )
            return response.parsed

        except Exception as e:
            if attempt == max_retries:
                raise
            # リトライ時は指示を強化する
            base_prompt = (
                "IMPORTANT: Your previous response contained Japanese characters. "
                "This is forbidden. Respond ONLY in English this time.\n\n"
                f"{base_prompt}"
            )

    raise RuntimeError("Should not reach here")
```

「前回の応答に日本語が含まれていました。今回は英語のみで応答してください」と明示的に伝えると、モデルの挙動が変わります。これは自動プロンプトチューニングの簡易版と言えます。3 回目以降も失敗するようなら、その入力は `UNABLE_TO_COMPLY` として人間レビューに回すのが現実的です。

## 全体を振り返って — まず System Instructions、次に Few-shot、最後にバリデーション

Gemini API の言語混入は、モデルのバージョンを上げるだけでは止まりません。System Instructions で強い制約を書き、Few-shot で期待する出力を見せ、`response_schema` とバリデータで機械的にチェックする、という三段構えが現実的です。

次に試すなら、まずは自分のコードの System Instructions を「英語のみ」「違反時は `UNABLE_TO_COMPLY`」という形式に書き換えてみてください。Few-shot や Pydantic 検証までは入れなくても、System Instructions を強めるだけで混入率が大幅に下がるはずです。多言語アプリ全般のプロンプト設計は [Gemini プロンプトエンジニアリング完全ガイド](/articles/gemini-basics/gemini-prompt-engineering-guide) もあわせて読むと、言語制御の勘所がつかみやすいと思います。

多言語 LLM アプリの設計思想をもっと深く理解したい方には、[大規模言語モデル入門（山田育矢、鈴木正敏）](https://www.amazon.co.jp/dp/4297136333/?tag=pinocchio-22)が参考になります。モデルがなぜ入力言語に引っ張られるのか、注意機構の観点から丁寧に解説されており、プロンプト設計の直感が深まる一冊です。
