個人開発でアプリを作っていると、「ユーザーにもっと関連コンテンツを見せたい」という要望が必ず出てきます。でも、推薦システムというと機械学習の専門知識が必要そうで、つい後回しにしていませんか。

実は、Gemini Embedding APIを使えば、複雑なモデルのトレーニングなしに、テキストの「意味的な近さ」を数値として扱える環境が整っています。壁紙アプリや音声アプリに実装した経験から言うと、ユーザーの閲覧履歴を数件ベクトル化するだけで、体感できるレベルの推薦精度が出るようになりました。

ここではGemini Embedding APIを核に据えた**パーソナライズドレコメンドシステム**の設計から本番運用まで、実際に動くコードとともに解説します。

累計5,000万ダウンロードのアプリ群に Gemini を組み込んできた経験から、本番運用のコツを整理します。

## レコメンドシステムの設計思想と Gemini Embedding の使い所

推薦システムには大きく3つのアプローチがあります。

**協調フィルタリング**は「似たユーザーが好むものを推薦する」手法です。Netflixが有名ですが、ユーザー数と行動データが少ないとコールドスタート問題（新規ユーザーに何も推薦できない）が深刻になります。

**コンテンツベースフィルタリング**は「ユーザーが過去に好んだコンテンツと似た内容のものを推薦する」手法です。コンテンツの特徴量をどう定義するかが鍵になりますが、ここにGemini Embeddingが効きます。

**ハイブリッドアプローチ**は両者を組み合わせたものです。個人開発でいきなりフルのハイブリッドを実装するのは難しいですが、コンテンツベースで始めて後から協調フィルタリングを加える設計にしておくと拡張が楽です。

今回はコンテンツベースフィルタリングを主軸に、「ユーザーがこれまで見たコンテンツの埋め込みベクトルを平均化してユーザープロファイルを作り、そのプロファイルに近いコンテンツを推薦する」システムを構築します。

```
[ユーザー行動ログ]
  ↓ 閲覧コンテンツのIDリスト
[Gemini Embedding API]
  ↓ 各コンテンツをベクトル化（768次元）
[ユーザープロファイルベクトル]
  ↓ 閲覧コンテンツの埋め込み平均
[コサイン類似度計算]
  ↓ 全コンテンツと一括比較
[推薦結果]
  ↓ 上位N件を返す
```

この設計のいいところは、新規ユーザーでも最初の1アクションから推薦が始まる点です。「何も見ていないユーザーには人気コンテンツを表示」という初期状態も自然に組み込めます。

Gemini Embedding APIでテキストをベクトル化する基本実装です。

```python
# embedder.py
from google import genai
from google.genai.types import EmbedContentConfig
import numpy as np
import time
from config import GEMINI_API_KEY, EMBEDDING_MODEL

client = genai.Client(api_key=GEMINI_API_KEY)

def embed_text(text: str, task_type: str = "RETRIEVAL_DOCUMENT") -> list[float]:
    """
    テキストを埋め込みベクトルに変換する。

    task_type の指定は推薦精度に直結するため必ず明示すること:
      - RETRIEVAL_DOCUMENT: コンテンツ登録時（インデックス側）
      - RETRIEVAL_QUERY: ユーザープロファイル・クエリ時（検索側）
      - SEMANTIC_SIMILARITY: 対称的な類似度計算
    """
    try:
        response = client.models.embed_content(
            model=EMBEDDING_MODEL,
            contents=text,
            config=EmbedContentConfig(task_type=task_type)
        )
        return response.embeddings[0].values
    except Exception as e:
        # レート制限エラー時は指数バックオフで再試行
        if "429" in str(e) or "RESOURCE_EXHAUSTED" in str(e):
            print(f"⚠️ レート制限 — 5秒後にリトライ")
            time.sleep(5)
            return embed_text(text, task_type)
        raise

def embed_texts_batch(texts: list[str], task_type: str = "RETRIEVAL_DOCUMENT") -> list[list[float]]:
    """
    複数テキストをバッチで埋め込む。
    Gemini Embedding APIは1リクエストあたり最大100件対応。
    """
    embeddings = []
    BATCH_SIZE = 100

    for i in range(0, len(texts), BATCH_SIZE):
        batch = texts[i:i + BATCH_SIZE]
        try:
            response = client.models.embed_content(
                model=EMBEDDING_MODEL,
                contents=batch,
                config=EmbedContentConfig(task_type=task_type)
            )
            embeddings.extend([e.values for e in response.embeddings])
        except Exception as e:
            if "429" in str(e) or "RESOURCE_EXHAUSTED" in str(e):
                print(f"⚠️ レート制限 — 10秒待機してリトライ")
                time.sleep(10)
                # バッチを個別処理にフォールバック
                for text in batch:
                    embeddings.append(embed_text(text, task_type))
            else:
                raise

    return embeddings
```

`task_type` の指定は地味に重要です。指定しないと推薦精度が目に見えて下がります。コンテンツ登録側は `RETRIEVAL_DOCUMENT`、クエリ側（ユーザープロファイル）は `RETRIEVAL_QUERY` を使いましょう。

## コンテンツカタログのベクトル化とストレージ設計

コンテンツ（記事・商品・動画など）を一括でベクトル化してストレージに保存します。初期インポートは一度だけ、以降は新規コンテンツ追加時に差分処理します。

```python
# content_indexer.py
import sqlite3
import numpy as np
from embedder import embed_texts_batch
from datetime import datetime

def init_db(db_path: str = "recommendations.db") -> sqlite3.Connection:
    """SQLiteでコンテンツインデックスとユーザープロファイルを管理する"""
    conn = sqlite3.connect(db_path, timeout=10)  # timeout必須（並列アクセス対策）
    cur = conn.cursor()

    cur.executescript("""
        CREATE TABLE IF NOT EXISTS content_embeddings (
            id TEXT PRIMARY KEY,
            title TEXT NOT NULL,
            text_for_embedding TEXT NOT NULL,
            embedding BLOB NOT NULL,
            category TEXT DEFAULT '',
            created_at TEXT DEFAULT CURRENT_TIMESTAMP
        );

        CREATE TABLE IF NOT EXISTS user_profiles (
            user_id TEXT PRIMARY KEY,
            profile_embedding BLOB NOT NULL,
            viewed_content_ids TEXT NOT NULL,
            updated_at TEXT DEFAULT CURRENT_TIMESTAMP
        );

        CREATE TABLE IF NOT EXISTS embedding_cache (
            text_hash TEXT PRIMARY KEY,
            embedding BLOB NOT NULL,
            created_at TEXT DEFAULT CURRENT_TIMESTAMP
        );
    """)
    conn.commit()
    return conn

def index_contents(contents: list[dict], db_path: str = "recommendations.db"):
    """
    コンテンツリストを一括インデックス化する（差分処理対応）。

    contents: [{"id": "slug", "title": "...", "description": "...", "category": "..."}]
    """
    conn = init_db(db_path)
    cur = conn.cursor()

    # 未登録コンテンツのみ処理
    existing_ids = {row[0] for row in cur.execute(
        "SELECT id FROM content_embeddings"
    ).fetchall()}
    new_contents = [c for c in contents if c["id"] not in existing_ids]

    if not new_contents:
        print(f"新規コンテンツなし（既存 {len(existing_ids)} 件）")
        conn.close()
        return

    print(f"新規 {len(new_contents)} 件をベクトル化中...")

    # 埋め込み用テキストは「タイトル + 説明文」を連結
    texts = [
        f"{c['title']}\n{c.get('description', '')}"
        for c in new_contents
    ]
    embeddings = embed_texts_batch(texts, task_type="RETRIEVAL_DOCUMENT")

    for content, emb, text in zip(new_contents, embeddings, texts):
        emb_bytes = np.array(emb, dtype=np.float32).tobytes()
        cur.execute("""
            INSERT OR REPLACE INTO content_embeddings
            (id, title, text_for_embedding, embedding, category)
            VALUES (?, ?, ?, ?, ?)
        """, (
            content["id"],
            content["title"],
            text,
            emb_bytes,
            content.get("category", "")
        ))

    conn.commit()
    conn.close()
    print(f"✅ {len(new_contents)} 件のインデックス完了")
```

SQLiteを選んだのは、個人開発のスケール感（コンテンツ10万件以下）では十分で、外部DBの管理コストが不要だからです。10万件を超えるなら後述するpgvectorへの移行パスを使ってください。

## ユーザープロファイルの動的更新

ここがこのシステムの核心です。ユーザーがコンテンツを閲覧するたびに、そのコンテンツのベクトルをユーザープロファイルに加算平均します。

```python
# user_profiler.py
import json
import sqlite3
import numpy as np
from datetime import datetime
from content_indexer import init_db

def update_user_profile(
    user_id: str,
    viewed_content_id: str,
    db_path: str = "recommendations.db",
    max_history: int = 50
):
    """
    ユーザーがコンテンツを閲覧したときにプロファイルを更新する。

    max_history: プロファイルに反映する最新の閲覧件数上限。
    古い閲覧ほど今の興味を反映しないため、最新50件に絞ることを推奨する。
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    # 閲覧コンテンツの埋め込みを取得
    row = cur.execute(
        "SELECT embedding FROM content_embeddings WHERE id = ?",
        (viewed_content_id,)
    ).fetchone()

    if not row:
        print(f"⚠️ コンテンツ '{viewed_content_id}' が未インデックス — スキップ")
        conn.close()
        return

    # 既存プロファイルを取得
    profile_row = cur.execute(
        "SELECT viewed_content_ids FROM user_profiles WHERE user_id = ?",
        (user_id,)
    ).fetchone()

    viewed_ids = json.loads(profile_row[0]) if profile_row else []

    # 閲覧履歴を更新（重複排除・最新max_history件に制限）
    if viewed_content_id not in viewed_ids:
        viewed_ids.append(viewed_content_id)
    if len(viewed_ids) > max_history:
        viewed_ids = viewed_ids[-max_history:]

    # プロファイルを全閲覧コンテンツの平均で再計算
    embeddings_to_average = []
    for cid in viewed_ids:
        r = cur.execute(
            "SELECT embedding FROM content_embeddings WHERE id = ?", (cid,)
        ).fetchone()
        if r:
            embeddings_to_average.append(
                np.frombuffer(r[0], dtype=np.float32)
            )

    if embeddings_to_average:
        new_profile = np.mean(embeddings_to_average, axis=0)

        # L2正規化（推薦時のコサイン類似度計算を内積だけで済ませるため）
        norm = np.linalg.norm(new_profile)
        if norm > 0:
            new_profile = new_profile / norm

        cur.execute("""
            INSERT OR REPLACE INTO user_profiles
            (user_id, profile_embedding, viewed_content_ids, updated_at)
            VALUES (?, ?, ?, ?)
        """, (
            user_id,
            new_profile.tobytes(),
            json.dumps(viewed_ids),
            datetime.now().isoformat()
        ))

    conn.commit()
    conn.close()
```

L2正規化（ベクトルの長さを1に揃える）を更新時に行っておくことで、推薦時のコサイン類似度計算がベクトルの内積だけで済むようになり、大幅に高速化できます。これを省くと推薦時の計算コストが約3倍になります。

## リアルタイム推薦エンジンと FastAPI エンドポイント

```python
# recommender.py
import sqlite3
import numpy as np
import json
from dataclasses import dataclass

@dataclass
class RecommendedContent:
    id: str
    title: str
    category: str
    similarity: float

def get_recommendations(
    user_id: str,
    n: int = 10,
    exclude_viewed: bool = True,
    category_filter: str | None = None,
    db_path: str = "recommendations.db"
) -> list[RecommendedContent]:
    """
    ユーザーへの推薦コンテンツを返す。

    プロファイルがまだない場合（新規ユーザー）は空リストを返す。
    呼び出し側でフォールバック（人気コンテンツなど）を用意すること。
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    profile_row = cur.execute(
        "SELECT profile_embedding, viewed_content_ids FROM user_profiles WHERE user_id = ?",
        (user_id,)
    ).fetchone()

    if not profile_row:
        conn.close()
        return []

    user_profile = np.frombuffer(profile_row[0], dtype=np.float32)
    viewed_ids = set(json.loads(profile_row[1])) if exclude_viewed else set()

    # カテゴリフィルタ付きで全コンテンツ取得
    query = "SELECT id, title, category, embedding FROM content_embeddings"
    params: list = []
    if category_filter:
        query += " WHERE category = ?"
        params.append(category_filter)

    rows = cur.execute(query, params).fetchall()
    conn.close()

    # NumPy行列演算で一括コサイン類似度計算
    content_ids, content_titles, content_categories, embedding_list = [], [], [], []

    for cid, title, category, emb_bytes in rows:
        if cid in viewed_ids:
            continue
        content_ids.append(cid)
        content_titles.append(title)
        content_categories.append(category)
        embedding_list.append(np.frombuffer(emb_bytes, dtype=np.float32))

    if not embedding_list:
        return []

    # 行列積でコサイン類似度を一括計算（L2正規化済みなので内積=コサイン類似度）
    # 10万件でも100ms以内に完了する
    matrix = np.array(embedding_list)       # shape: (N, 768)
    similarities = matrix @ user_profile    # shape: (N,)

    top_indices = np.argsort(similarities)[::-1][:n]

    return [
        RecommendedContent(
            id=content_ids[i],
            title=content_titles[i],
            category=content_categories[i],
            similarity=float(similarities[i])
        )
        for i in top_indices
    ]
```

```python
# api.py
from fastapi import FastAPI, BackgroundTasks
from pydantic import BaseModel
from recommender import get_recommendations
from user_profiler import update_user_profile

app = FastAPI(title="Gemini Recommendation API")

class ViewEvent(BaseModel):
    user_id: str
    content_id: str

class RecommendRequest(BaseModel):
    user_id: str
    n: int = 10
    category: str | None = None

@app.post("/events/view")
async def record_view(event: ViewEvent, background_tasks: BackgroundTasks):
    """
    閲覧イベントを記録し、バックグラウンドでプロファイルを更新する。
    プロファイル更新は非同期で行い、レスポンスを即返すことでUXを損なわない。
    """
    background_tasks.add_task(
        update_user_profile,
        user_id=event.user_id,
        viewed_content_id=event.content_id
    )
    return {"status": "accepted"}

@app.post("/recommendations")
async def recommend(req: RecommendRequest):
    """
    ユーザーへの推薦コンテンツを返す。
    新規ユーザー（プロファイル未生成）には fallback: true を返す。
    """
    results = get_recommendations(
        user_id=req.user_id,
        n=req.n,
        category_filter=req.category
    )

    if not results:
        return {
            "user_id": req.user_id,
            "recommendations": [],
            "fallback": True,
            "message": "プロファイル未生成。フォールバックコンテンツを使用してください"
        }

    return {
        "user_id": req.user_id,
        "recommendations": [
            {
                "id": r.id,
                "title": r.title,
                "category": r.category,
                "score": round(r.similarity, 4)
            }
            for r in results
        ],
        "fallback": False
    }
```

閲覧イベントの受付とプロファイル更新を分離することで、ユーザーが記事を開いた瞬間のレスポンスを犠牲にせずにプロファイルを最新状態に保てます。

## よくある間違いと落とし穴

実装していて何度もハマったポイントをまとめます。

**① task_type を指定しないまま運用してしまう**

Gemini Embedding APIでは `task_type` の指定が推薦精度に直結します。コンテンツ登録時に `RETRIEVAL_DOCUMENT`、ユーザープロファイル作成時に `RETRIEVAL_QUERY` を使わないと、同じテキストでも「向き」が違うベクトルが生成されて類似度計算がちぐはぐになります。後から全件再ベクトル化が必要になるので、最初から必ず指定してください。これは公式ドキュメントには書かれていますが、サンプルコードに省略されているケースが多く見落としやすいです。

**② 閲覧履歴を無制限に増やしてしまう**

3年前に見たコンテンツが今の興味を反映しているとは限りません。プロファイル計算に含める履歴を `max_history=50` 程度に制限することで、時事的な興味の変化にも追従できます。これを設定しないと「最初期のユーザーの趣味」がずっとプロファイルを支配し続けます。

**③ 人気コンテンツへの偏りが起きる**

多く閲覧されたコンテンツに引っ張られてプロファイルが全ユーザーで同じ方向に収束していく問題です。軽い対策としては、推薦スコアに「カテゴリダイバーシティボーナス」を加算する方法があります。同じカテゴリのコンテンツが3件以上推薦される場合は4件目以降のスコアを下げる、といったロジックです。

**④ 新規コンテンツが推薦されない**

公開直後のコンテンツは誰にも閲覧されていないため、推薦スコアが出にくい問題があります。「公開から7日以内の記事には+0.05のボーナスを加算する」ようなエクスプロレーション要素を意図的に組み込むことを推奨します。

**⑤ SQLiteのwrite競合**

並列リクエストが同時に `user_profiles` に書き込む場合、SQLiteのデフォルト設定ではロックタイムアウトが発生します。`sqlite3.connect(db_path, timeout=10)` を明示的に指定するか、スケールが必要になったらPostgreSQL + pgvectorへ移行してください。

## APIコストの最適化とキャッシング戦略

Gemini Embedding APIの料金は `text-embedding-004` で約$0.00002/1,000トークンです。コスト最適化で最も効果的な施策は**テキストハッシュによるベクトルキャッシング**です。

```python
# embedding_cache.py
import hashlib
import sqlite3
import numpy as np
from google import genai
from google.genai.types import EmbedContentConfig
from config import GEMINI_API_KEY, EMBEDDING_MODEL

client = genai.Client(api_key=GEMINI_API_KEY)

def get_cached_or_embed(
    text: str,
    task_type: str = "RETRIEVAL_DOCUMENT",
    db_path: str = "recommendations.db"
) -> list[float]:
    """
    同一テキストへのAPIコールをキャッシュで防ぐ。
    テキストが変わればハッシュが変わるため、古いキャッシュが使われることはない。
    """
    text_hash = hashlib.sha256(f"{task_type}:{text}".encode()).hexdigest()

    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    row = cur.execute(
        "SELECT embedding FROM embedding_cache WHERE text_hash = ?",
        (text_hash,)
    ).fetchone()

    if row:
        conn.close()
        return list(np.frombuffer(row[0], dtype=np.float32))

    # キャッシュミス — API呼び出し
    response = client.models.embed_content(
        model=EMBEDDING_MODEL,
        contents=text,
        config=EmbedContentConfig(task_type=task_type)
    )
    embedding = response.embeddings[0].values

    cur.execute(
        "INSERT OR IGNORE INTO embedding_cache (text_hash, embedding) VALUES (?, ?)",
        (text_hash, np.array(embedding, dtype=np.float32).tobytes())
    )
    conn.commit()
    conn.close()

    return embedding
```

コンテンツのタイトルと説明文が変わらない限り、同じベクトルを再利用できます。記事100本のサイトなら初期ベクトル化のAPIコストは数円以下です。ユーザープロファイルの更新時は既存コンテンツのベクトルをDBから読み出すだけなのでAPIコールは発生しません。

## スケールアップ時の移行パス

SQLiteで始めて問題が出たら、以下の順で移行を検討してください。

**フェーズ1（コンテンツ〜1万件、MAU〜1,000）**: SQLite + 本記事の実装。追加インフラコストほぼゼロ。

**フェーズ2（〜10万件、MAU〜10,000）**: PostgreSQL + pgvectorへ移行。Supabaseを使えばマネージドで運用できます。詳細は[セマンティック検索の本番設計](/articles/gemini-api/gemini-embeddings-semantic-search-production)を参照してください。

**フェーズ3（10万件〜）**: Vertex AI Vector SearchかFirestore Vector Searchへ移行。[Gemini Embedding APIの基本ガイド](/articles/gemini-api/embeddings-api-guide)でオプション比較をまとめています。

いずれのフェーズでも、埋め込みモデルとtask_typeの組み合わせさえ統一していれば、ベクトルデータをそのままマイグレーションできます。

## まとめ — 今日から始めるための一歩

まず手元にあるコンテンツ（記事・商品・動画）を10〜20件だけ使って、`index_contents()` と `get_recommendations()` を動かしてみてください。それだけで「意味的に近いものが推薦される」感覚を体験できます。

本番投入前に確認すべきことは3つです。コンテンツのベクトル化に `task_type="RETRIEVAL_DOCUMENT"` を使っているか。ユーザープロファイルのL2正規化を忘れていないか。閲覧履歴の件数制限（`max_history`）を設定しているか。この3点さえ押さえれば、最初のバージョンとして十分機能します。

コストをさらに抑えたい方は、[Gemini APIコスト最適化の完全ガイド](/articles/gemini-api/gemini-api-cost-optimization-complete-guide)でContext Cachingと組み合わせるパターンも参考になります。
