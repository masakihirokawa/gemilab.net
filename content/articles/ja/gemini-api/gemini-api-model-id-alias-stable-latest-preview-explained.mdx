「先週まで普通に動いていたスクリプトが、今朝突然 JSON のフォーマットを無視するようになった」— 本番で Gemini API を使っていると、ある日こういう現象に遭遇することがあります。コードは 1 行も変えていないのに出力だけが変わる。原因の多くは、モデル ID に `gemini-2.5-pro-latest` のような「エイリアス」を指定していて、裏側で別のバージョンに差し替わっていた、というものです。

Google の API ドキュメントには `stable` / `latest` / `preview` / `experimental` の 4 種類のタグが登場しますが、それぞれの「本当の意味」と「本番でどれを選ぶべきか」は公式ページでは一文にしか書かれていません。本記事では、実際の API レスポンスを見ながら 4 つの識別子の違いと、個人開発の現場で私が実際にぶつかった落とし穴を整理します。

## Gemini API で使える 4 種類のモデル識別子

まず `https://generativelanguage.googleapis.com/v1beta/models` を叩くと、返ってくる `name` フィールドは次のようなパターンに分類できます。

- **バージョン固定**: `models/gemini-2.5-pro-002` — 特定バージョンに固定
- **`-latest` エイリアス**: `models/gemini-2.5-pro-latest` — 同ファミリーで最も新しい安定版に自動追従
- **短縮名（stable）**: `models/gemini-2.5-pro` — 現在の推奨安定版へのエイリアス
- **`-preview` / `-exp` タグ**: `models/gemini-3-pro-preview-02-05` — プレビュー版、実験版

呼び出し時は `model="gemini-2.5-pro"` のように `models/` プレフィックスを省略して指定することが多いですが、意味としては同じものです。

### それぞれの挙動を 1 行でまとめると

- **バージョン固定 (`-002` 等)**: 同じ入力 → 同じ分布の出力。ただし廃止期限が来ると **404 で止まる**
- **`-latest` エイリアス**: 自動でマイナーバージョンアップを受け取る。**出力が突然変わる可能性あり**
- **短縮名**: `-latest` と挙動は似ているが、Google が「今の標準」と決めたものを指す。プロダクトのデフォルト想定
- **`-preview` / `-exp`**: 予告なしに廃止される。SLA なし。本番投入は非推奨

## なぜ「gemini-2.5-pro-latest」と「gemini-2.5-pro」で挙動が変わるのか

ここが多くの方が混乱するポイントです。どちらも「最新の 2.5 Pro を指すエイリアス」に見えますが、実際には指している先が違います。

`models.list` の結果を Python で比較すると分かりやすいので、まず実物を見てみましょう。

```python
# 何を解決するコード: 同じ「Gemini 2.5 Pro」でも、呼び出し名によってどのバージョンに
# ルーティングされるかを一覧化する。これが分かると latest と短縮名の挙動差が理解できます。
import os
import google.generativeai as genai

genai.configure(api_key=os.environ["GOOGLE_API_KEY"])

for m in genai.list_models():
    if "gemini-2.5-pro" in m.name:
        print(f"{m.name:50s}  display={m.display_name}")
```

期待する出力（例）:

```
models/gemini-2.5-pro                          display=Gemini 2.5 Pro
models/gemini-2.5-pro-002                      display=Gemini 2.5 Pro 002
models/gemini-2.5-pro-latest                   display=Gemini 2.5 Pro Latest
models/gemini-2.5-pro-preview-04-17            display=Gemini 2.5 Pro Preview 04-17
```

同じ `2.5 Pro` ファミリーに **少なくとも 4 つの入口** があるのが分かります。このうち `-latest` は「Google が同ファミリーの中で最新と判断したもの」に自動追従するエイリアスで、短縮名 `gemini-2.5-pro` は「プロダクトの推奨版」として明示的に指定されている安定版を指します。

両者のズレが起きるのはマイナーバージョンがリリースされた直後です。新しい `-003` が出た時点で `-latest` は即座に `-003` を返しますが、短縮名 `gemini-2.5-pro` が `-003` を指すように切り替わるのは、Google 内部で検証とドキュメント更新が完了した数日〜数週間後になります。この時間差が「先週まで動いていたのに」の正体です。

## 本番環境で推奨するモデル識別子の選び方

私自身が複数の個人アプリで Gemini API を使っていて、今は次のように使い分けています。

- **本番の決済・自動メール・外部 API へのリクエスト生成**: **バージョン固定（`-002` 等）を第一候補に**。予期せぬ出力変化で金銭的損失が出る処理は、このルートが一番安全です
- **ユーザー向けのチャット UI や検索補助**: **短縮名（`gemini-2.5-pro`）を使用**。ユーザーは常に「今の最新」を期待しているため、Google が推奨版を差し替えたタイミングでこちらも追従するのが自然です
- **社内ツール・実験・プロトタイプ**: **`-latest` でもよい**。挙動変化に気づいても影響範囲が小さいですし、新機能を真っ先に試せます
- **`-preview` / `-exp`**: **本番では使わない**。私は検証用の Jupyter Notebook 専用にしています

「なぜバージョン固定が第一候補なのか」とよく聞かれますが、理由は単純で、Gemini API のモデル廃止予告は通常 **最低 6 ヶ月前にアナウンス**されるからです。廃止通知を受けてから別のバージョンに切り替えるまで十分な時間があり、その間に品質評価もやり直せます。代償として小さな改善の恩恵は受けられませんが、本番のコードベースが静かに壊れるリスクと比べれば小さなものです。

## ハマりやすい 3 つの落とし穴

### 1. `-latest` を固定するつもりが固定されていなかった

次のコードは `.env` に書いたモデル名を読み込む、よくあるパターンです。

```python
# 何を解決するコード: .env からモデル名を読み、genai.GenerativeModel を生成する
import os
import google.generativeai as genai

MODEL_NAME = os.environ.get("GEMINI_MODEL", "gemini-2.5-pro-latest")
model = genai.GenerativeModel(MODEL_NAME)
```

`.env` で `GEMINI_MODEL=gemini-2.5-pro-latest` と書いていれば安心、と思いきや、これは「毎回 Google が決めた最新版に自動追従する」設定です。本番で安定性が欲しい場合はここを `gemini-2.5-pro-002` のように **バージョン番号まで明示する**のが正解です。

### 2. プロンプトとモデルが世代ズレを起こす

Gemini の世代間（2.0 系 → 2.5 系、2.5 系 → 3 系）では、同じプロンプトに対する出力の分布がはっきり変わります。特に JSON モードや Function Calling の挙動は世代差が大きく、Function スキーマの解釈が厳密になった結果、旧世代では通っていた曖昧な定義がエラーになることがあります。モデルを上げるときは、代表的な 20〜30 件のプロンプトで回帰テストを回すのが安全です。

### 3. リージョン別にエイリアスの解決先が違うことがある

`generativelanguage.googleapis.com` ではなく Vertex AI 経由（`us-central1-aiplatform.googleapis.com` など）で Gemini を使っている場合、`-latest` エイリアスのロールアウトが地域によって数日ずれることがあります。マルチリージョンでデプロイしている方は、バージョン固定にしておく方が後々の比較がしやすくなります。

### エイリアスが今どのバージョンを指しているか確認する

`-latest` の実体がどれなのかを知りたいときは、`get_model()` の戻り値から解決先を読めます。レスポンスと一緒にどのバージョンが応答したかを記録しておくと、「ある日突然挙動が変わった」と言われた時の調査が一気に楽になります。

```python
# 何を解決するコード: 実際にリクエストを処理したモデルのバージョンをログに残し、
# エイリアスが裏で差し替わっても、どのバージョンが出力を生成したかを
# 後から追跡できるようにする。
import google.generativeai as genai

meta = genai.get_model("models/gemini-2.5-pro-latest")
print(f"resolved_to={meta.name} version={meta.version}")
```

リリース直後の 1 ヶ月だけでも、この 1 行をリクエストログに混ぜておくと、後追いでのデバッグが驚くほど短くなります。

## 廃止期限に備える実装パターン

バージョン固定を選ぶと必ずついて回るのが「廃止されたときどうするか」です。私はフェイルオーバー用の候補リストを持たせるパターンを使っています。

```python
# 何を解決するコード: プライマリのモデルが 404 になったら、同ファミリーの
# 次のバージョンに自動的にフォールバックする。本番中に廃止期限が来ても
# サービスが即停止しないようにする安全装置です。
import os
from google.api_core import exceptions
import google.generativeai as genai

genai.configure(api_key=os.environ["GOOGLE_API_KEY"])

MODEL_CANDIDATES = [
    "gemini-2.5-pro-003",   # primary（本番想定バージョン）
    "gemini-2.5-pro-002",   # fallback 1（一つ前）
    "gemini-2.5-pro",       # fallback 2（短縮名）
]

def generate_with_fallback(prompt: str) -> str:
    last_error = None
    for name in MODEL_CANDIDATES:
        try:
            model = genai.GenerativeModel(name)
            res = model.generate_content(prompt)
            return res.text
        except exceptions.NotFound as e:
            # モデルが廃止されていれば次の候補へ
            last_error = e
            continue
    raise RuntimeError(f"All model candidates failed: {last_error}")
```

期待する出力の流れ:

```
# gemini-2.5-pro-003 が生きている間
→ 003 で成功、レスポンス返却

# 003 が廃止された直後
→ 003 が 404 → 002 で成功（サービス停止せず、ログに警告）
```

ポイントは、短縮名 `gemini-2.5-pro` を最後に置いている点です。短縮名はしばらく存続するため、万一ファミリーの個別バージョンがすべて廃止されても最後の砦として機能します。ログ監視で「fallback 発動」を検知したら、そのタイミングで次の `-004` 等に更新するワークフローに組み込むと運用が安定します。

## モデル選択と合わせて見直したい項目

モデル ID の選定は API 設計の入口にすぎません。あわせて、レート制限の扱いやキー管理も整理しておくと、本番で慌てずに済みます。廃止予告への対応を時系列で把握したい方は[Gemini API モデル廃止と移行の完全ガイド](/articles/gemini-api/gemini-api-model-deprecation-migration-guide)を、6 月の 2.0 Flash 廃止の具体的な移行手順は[Gemini 2.0 Flash 廃止対応ガイド](/articles/gemini-api/gemini-2-0-flash-deprecation-june-2026-migration-guide)が参考になります。API キーの安全な運用についても[個人開発者向け API キー運用チェックリスト](/articles/gemini-api/gemini-api-key-safe-operations-indie-developer-checklist)に実践手順をまとめています。

LLM のバージョン管理を体系的に学びたい方には、[『大規模言語モデル入門II』（山田 育矢 ほか 著）](https://www.amazon.co.jp/dp/4297143933/?tag=pinocchio-22)がモデルの振る舞い差分を検証する視点を与えてくれる一冊です。

## バージョン切り替え時にやっている回帰テスト

新しい pinned ビルドが出たときに私が回している手順は、とても地味です。本番で流れているプロンプトを 30 件ほど CSV にスナップショットし、旧バージョンと新バージョンに同じ入力で流し込んで出力を diff する、それだけです。見ているのは生の品質スコアよりも、**出力フォーマットの変化**（JSON 構造・リストの長さ・Markdown と平文の比率）と、**refuse（回答拒否）の発生率**の 2 点です。どちらがズレても下流のパーサーが壊れるため、「賢くなった」だけでは合格点にならない、という感覚を持っておくのが安全です。

30 件という数字は、それ以下だとノイズに埋もれ、それ以上だと自分でレビューしきれないという私の経験則です。規模感はご自身のプロダクトに合わせて調整してください。

## まとめ

モデル ID の選び方は、最初の一行を書き換えるだけで本番の安定性が大きく変わるテーマです。今日すぐ実行できる一歩として、手元のコードで `gemini-2.5-pro-latest` のような `-latest` エイリアスを使っている箇所を `grep` してみてください。本番で使うコードパスなら、まずそこをバージョン番号付きの識別子に置き換え、廃止通知を受け取れるログの仕組みを入れる。これだけで「ある日突然壊れる」事故の大半は防げます。
