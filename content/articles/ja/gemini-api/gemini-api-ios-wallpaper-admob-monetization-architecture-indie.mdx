2014年に初めてiOSアプリをリリースしたとき、壁紙アプリというジャンルはとてもシンプルな構造でした。画像を選んで、広告を表示して、収益化する。それだけでした。

10年以上個人開発を続け、累計5,000万ダウンロードを超えた今、自分のアプリにGemini APIを組み込む設計を本格的に考え始めました。最初にぶつかった壁は予想と違う場所にありました。「Gemini APIのコストがAdMob収益を食い潰さないか」という不安です。

AdMobのCPMは1,000インプレッションあたり数十〜数百円。一方でGemini 2.5 FlashのAPIコストは入力1Mトークンあたり$0.10、出力は$0.40です。ユーザーが1回AI壁紙リクエストを行うたびに数セントのコストが発生するとすれば、月間アクティブユーザーが多いアプリでは広告収益をあっという間に超えてしまいます。

でも実際に設計を詰めてみると、思い込みが間違っていました。「全ユーザーに全AI機能を無制限で提供する」という前提を疑うことで、コストを抑えながらプレミアム体験を提供できる構造が見えてきました。この記事ではその設計思想と実装パターンを共有します。

## AIを壁紙アプリに追加するときの本質的な問題

壁紙アプリにGemini APIを組み込もうとすると、最初に「何のためにAPIを使うのか」という問いに直面します。よくある誤りは「できること全部やろう」という発想です。

- ユーザーが写真を撮ったらAIでスタイルを分析して壁紙を生成する
- 気分に合わせてAIが最適な壁紙を推薦する
- テキスト入力から壁紙を自動生成する

これを全部APIで動かすと、1ユーザーあたりの月間API消費量が予測不能になります。個人開発者の視点から言えば、**AIを使う場面を3分類してコストの性質を変える**ことが先決です。

**クラスA（毎回発生・高頻度）**: ユーザーが壁紙を閲覧・スクロールするたびに発火する処理
**クラスB（意図的操作時・中頻度）**: ユーザーがAI壁紙生成ボタンを押したときの処理
**クラスC（初回または週次・低頻度）**: ユーザープロファイル分析・好み学習の処理

クラスAにGemini APIを使うのは個人開発では現実的ではありません。ここはオンデバイス推論（Gemini Nanoまたは軽量MLモデル）で賄い、クラウドAPIはクラスBとCに限定するのが実用的な設計です。

## Gemini APIコストとAdMob収益の試算

設計の前提となる数字を整理します。これは私が実際に試算したものです。

**AdMob収益の現実（壁紙アプリ）**

壁紙アプリのCPMは日本国内で平均100〜300円程度です。月間100万インプレッションがあれば、10〜30万円程度の収益になります。ただし壁紙アプリのインプレッション単価は低め。高CPMを狙うにはリワード広告をうまく組み込む必要があります。

```
例）月間アクティブユーザー5万人の壁紙アプリ
- 1ユーザー = 1日3〜5回起動
- 1起動 = バナー2〜3インプレッション
- 月間推定インプレッション: 5万 × 4 × 2.5 × 30 = 1,500万imp
- CPM 150円として: 1,500万 ÷ 1,000 × 150 = 225万円/月
（現実はこの6〜7割が収益として入る）
→ 実質約140〜160万円/月
```

一方、Gemini API（Gemini 2.5 Flash）のコストは：

```
1リクエストの想定トークン数（壁紙スタイル分析 + 推薦）:
- 入力: システムプロンプト500 + 画像特徴量テキスト300 + ユーザー要求200 = 約1,000トークン
- 出力: 推薦壁紙IDリスト + 理由文 = 約200トークン

1リクエストコスト:
- 入力: 1,000 × ($0.10 / 1,000,000) = $0.0001
- 出力: 200 × ($0.40 / 1,000,000) = $0.00008
- 合計: 約$0.00018 = 約0.027円/リクエスト

もし5万DAUが1日1回APIを叩くと:
- 日次コスト: 5万 × 0.027円 = 1,350円
- 月次コスト: 約4万円
```

月160万円の収益に対して月4万円のAPIコスト。率にして2.5%です。これは許容範囲内です。ただしこれは「1日1リクエスト/ユーザー」の前提です。無制限にすると状況は変わります。

**重要な設計判断**: Freemiumゲートで「AI壁紙生成は1日3回まで無料、それ以上はプレミアム」という制限を設けることで、コストを予測可能な範囲に収めます。

## 設計の核心 — オンデバイスAIとクラウドAPIの分担

実際の実装では、3層構造でAI処理を分担させています。

**Layer 1: オンデバイス（コスト0）**
- 壁紙サムネイルのスタイル分類（明るい/暗い/カラフル/モノクロ等）
- ユーザーのお気に入りパターンのローカル学習
- 閲覧履歴に基づくローカルフィルタリング

**Layer 2: Gemini 2.5 Flash（低コスト）**
- テキストプロンプトからの壁紙タグ生成
- ユーザーリクエストの意図解釈
- 壁紙の詳細説明文生成（SEO・App Store向け）

**Layer 3: Gemini 2.5 Pro with Imagen 4（高コスト、プレミアムのみ）**
- オリジナル壁紙の画像生成
- アート作品風スタイル変換
- シーズン・トレンドに合わせたカスタム壁紙生成

この3層を意識するだけで、APIコストの設計が根本的に変わります。

## 実装パターン1 — Gemini Nanoによるオンデバイス壁紙分類

Layer 1の実装例です。iOSのOn-Device推論（Core MLまたはMediaPipe）を使ってGemini Nanoモデルをデバイス上で実行し、壁紙のスタイル分類をAPIコスト0で行います。

```swift
import CoreML
import Vision

class WallpaperStyleClassifier {
    private let model: VNCoreMLModel
    
    // 簡略化した壁紙スタイル分類器
    // 実際はGemma 3B on-deviceまたはカスタムモデルを使用
    init() throws {
        let mlModel = try WallpaperClassifierV2(configuration: MLModelConfiguration()).model
        model = try VNCoreMLModel(for: mlModel)
    }
    
    /// APIコスト0でデバイス上でスタイルを分類
    func classify(image: UIImage) async throws -> WallpaperStyle {
        guard let cgImage = image.cgImage else {
            throw ClassifierError.invalidImage
        }
        
        return try await withCheckedThrowingContinuation { continuation in
            let request = VNCoreMLRequest(model: model) { request, error in
                if let error = error {
                    continuation.resume(throwing: error)
                    return
                }
                
                guard let results = request.results as? [VNClassificationObservation],
                      let topResult = results.first else {
                    continuation.resume(throwing: ClassifierError.noResults)
                    return
                }
                
                let style = WallpaperStyle(rawValue: topResult.identifier) ?? .unknown
                continuation.resume(returning: style)
            }
            
            let handler = VNImageRequestHandler(cgImage: cgImage)
            try? handler.perform([request])
        }
    }
}

enum WallpaperStyle: String {
    case nature, minimal, abstract, cityscape, pattern, unknown
}
```

このオンデバイス処理で壁紙の基本分類をAPIコスト0で行い、ユーザーへの即時フィードバックを実現します。Gemini APIはこの後の「より高度な意図解釈」にだけ使います。

## 実装パターン2 — Gemini 2.5 Flashによる壁紙タグ最適化

Layer 2の実装例です。ユーザーが「朝の公園みたいな明るい壁紙」とテキスト入力した場合、Gemini 2.5 Flashでタグに変換して検索精度を上げます。

```python
import google.generativeai as genai
import json
import time

genai.configure(api_key="YOUR_GEMINI_API_KEY")

def optimize_wallpaper_tags(user_query: str, max_retries: int = 3) -> dict:
    """
    ユーザーの自然言語クエリを壁紙検索タグに変換する。
    Gemini 2.5 Flash を使用してコストを抑える。
    
    入力例: "朝の公園みたいな明るい壁紙"
    出力例: {"tags": ["morning", "park", "bright", "nature", "green"], 
             "mood": "peaceful", "time_of_day": "morning"}
    """
    model = genai.GenerativeModel(
        "gemini-2.5-flash",
        system_instruction="""あなたは壁紙アプリの検索最適化AIです。
ユーザーの自然言語クエリを英語の検索タグに変換してください。
必ずJSON形式で返してください。タグは5個以内で、具体的かつ検索に使えるものにしてください。
mood: peaceful/energetic/romantic/minimalist/dramatic のいずれか
time_of_day: morning/afternoon/evening/night/any のいずれか"""
    )
    
    for attempt in range(max_retries):
        try:
            response = model.generate_content(
                user_query,
                generation_config=genai.GenerationConfig(
                    response_mime_type="application/json",
                    max_output_tokens=150,  # タグ変換は短い出力で十分
                    temperature=0.3  # 一貫性を優先
                )
            )
            
            result = json.loads(response.text)
            
            # バリデーション
            if "tags" not in result or not isinstance(result["tags"], list):
                raise ValueError("Invalid response format")
            
            # タグ数を制限（コスト・品質のバランス）
            result["tags"] = result["tags"][:5]
            return result
            
        except Exception as e:
            if attempt < max_retries - 1:
                time.sleep(2 ** attempt)  # 指数バックオフ
                continue
            # 最終リトライ失敗時はフォールバック
            return {"tags": user_query.split()[:3], "mood": "any", "time_of_day": "any"}

# 使用例
query = "朝の公園みたいな明るい壁紙"
tags = optimize_wallpaper_tags(query)
print(tags)
# 出力例:
# {"tags": ["morning", "park", "bright", "nature", "sunlight"],
#  "mood": "peaceful", "time_of_day": "morning"}
```

このパターンのポイントは `max_output_tokens=150` という制限です。タグ変換に長い回答は不要なので、トークン数を絞ってコストを抑えます。実測では1リクエストあたり約0.015円（出力150トークン想定）で動いています。

## 実装パターン3 — FreemiumゲートによるAPI使用量制御

Layer 2/3のAPI呼び出しをFreemiumゲートで制御する実装です。無料ユーザーは1日3回、プレミアムユーザーは無制限という設計です。

```swift
import Foundation
import StoreKit

class AIUsageManager {
    private let userDefaults = UserDefaults.standard
    private let premiumCheckKey = "isPremiumUser"
    private let dailyUsageKey = "aiDailyUsage"
    private let lastResetKey = "aiLastResetDate"
    
    static let shared = AIUsageManager()
    
    // 無料プランの1日あたり上限
    private let freeUserDailyLimit = 3
    
    var isPremiumUser: Bool {
        // App内課金の購入状態を確認
        // 実際はStoreKit 2のTransaction.currentEntitlementsを使用
        return userDefaults.bool(forKey: premiumCheckKey)
    }
    
    /// AI機能の利用可否チェック（API呼び出し前に必ず確認）
    func canUseAIFeature() -> AIUsageResult {
        if isPremiumUser {
            return .allowed(remainingCount: Int.max)
        }
        
        resetDailyCountIfNeeded()
        
        let currentCount = userDefaults.integer(forKey: dailyUsageKey)
        let remaining = freeUserDailyLimit - currentCount
        
        if remaining > 0 {
            return .allowed(remainingCount: remaining)
        } else {
            return .limitReached(upgradeURL: "https://gemilab.net/membership")
        }
    }
    
    /// API呼び出し成功後にカウントを増加
    func recordUsage() {
        guard !isPremiumUser else { return }
        let current = userDefaults.integer(forKey: dailyUsageKey)
        userDefaults.set(current + 1, forKey: dailyUsageKey)
    }
    
    private func resetDailyCountIfNeeded() {
        let today = Calendar.current.startOfDay(for: Date())
        if let lastReset = userDefaults.object(forKey: lastResetKey) as? Date,
           Calendar.current.isDate(lastReset, inSameDayAs: today) {
            return // 今日はまだリセット不要
        }
        userDefaults.set(0, forKey: dailyUsageKey)
        userDefaults.set(today, forKey: lastResetKey)
    }
}

enum AIUsageResult {
    case allowed(remainingCount: Int)
    case limitReached(upgradeURL: String)
}

// 使用例（壁紙生成ボタンのタップ処理）
func handleAIGenerationTap() {
    let usageResult = AIUsageManager.shared.canUseAIFeature()
    
    switch usageResult {
    case .allowed(let remaining):
        // API呼び出しを実行
        Task {
            await generateAIWallpaper()
            AIUsageManager.shared.recordUsage()
            
            if remaining == 1 {
                showUpgradeHintBanner() // 残り1回でアップグレード訴求
            }
        }
    case .limitReached(let url):
        showUpgradePrompt(upgradeURL: url)
    }
}
```

この設計の重要な点は `remaining == 1` のときにアップグレード訴求を表示することです。「今日の無料枠を使い切る前」のタイミングでアップグレードを提案すると、転換率が上がります。「使い切った後」では手遅れです。

## App Store審査とAI生成コンテンツのガイドライン対策

壁紙アプリにAI生成機能を追加したとき、App Store審査で思わぬ指摘を受けることがあります。2026年現在、AppleのAI生成コンテンツに関するガイドラインは以下のポイントに注目しています。

**審査で指摘されやすいポイント**

**1. 成人向けコンテンツの混入リスク**

Gemini APIのImagenで画像を生成する場合、プロンプトにフィルターをかけていないとNSFWコンテンツが生成されるリスクがあります。Appleは「AIが生成したコンテンツがペアレンタルコントロールをバイパスする可能性がある」と判断した場合、審査を通しません。

対策として、生成リクエスト時にGemini APIのセーフティ設定を必ず有効化します。

```python
from google.generativeai.types import HarmCategory, HarmBlockThreshold

# 壁紙生成専用の安全設定（最も厳格なセーフティ設定を使用）
safety_settings = {
    HarmCategory.HARM_CATEGORY_HARASSMENT: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE,
    HarmCategory.HARM_CATEGORY_HATE_SPEECH: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE,
    HarmCategory.HARM_CATEGORY_SEXUALLY_EXPLICIT: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE,
    HarmCategory.HARM_CATEGORY_DANGEROUS_CONTENT: HarmBlockThreshold.BLOCK_LOW_AND_ABOVE,
}

# Imagen 4 での壁紙生成（プレミアムユーザー向け）
def generate_safe_wallpaper(prompt: str) -> bytes | None:
    """
    壁紙専用のセーフティ設定でImagen 4を使用して画像生成。
    SAFETY_BLOCKEDの場合はNoneを返してフォールバック処理へ。
    """
    model = genai.ImageGenerationModel("imagen-4.0")
    
    # 壁紙専用のシステムプロンプトを前置き
    safe_prompt = f"Beautiful, family-friendly wallpaper image: {prompt}. No people, no text, natural or abstract design only."
    
    try:
        response = model.generate_images(
            prompt=safe_prompt,
            number_of_images=1,
            safety_filter_level="block_most",
            aspect_ratio="9:16"  # スマートフォン縦向き
        )
        
        if response.images:
            return response.images[0].image_bytes
        return None
        
    except Exception as e:
        # セーフティブロック含む全エラーをキャッチしてNone返却
        print(f"Image generation failed: {e}")
        return None
```

**2. AIであることの明示義務**

2025年以降、AppleはAIが生成したコンテンツにラベル表示を求めるケースが増えています。壁紙アプリでも「AI Generated」のウォーターマークまたはメタデータを付与することで審査通過率が上がります。

重要な点は**プレミアムユーザーのAPI使用コストはプレミアム収益でカバーし、無料ユーザーのコストは広告収益でカバーする**というシンプルな原則です。

## リクエストキャッシュで重複コストを削除する

最後に、実装上のコスト削減テクニックです。同じようなリクエストが頻発するケースでは、Gemini APIのContext Cachingまたはアプリ側のキャッシュ層が効果的です。

壁紙アプリの場合、「似たようなキーワードで何度も検索する」ユーザーが多いため、タグ変換結果をRedisなどでキャッシュするだけで重複API呼び出しを大幅に削減できます。

```python
import hashlib
import json
import redis
from typing import Optional

class CachedGeminiTagOptimizer:
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.cache_ttl = 86400  # 24時間キャッシュ
    
    def optimize_with_cache(self, user_query: str) -> dict:
        """
        同一クエリはキャッシュから返し、Gemini API呼び出しを削減。
        実測でAPI呼び出しを40〜60%削減できる。
        """
        cache_key = f"wallpaper_tags:{hashlib.md5(user_query.encode()).hexdigest()}"
        
        # キャッシュ確認
        cached = self.redis.get(cache_key)
        if cached:
            return json.loads(cached)
        
        # キャッシュなし → API呼び出し
        result = optimize_wallpaper_tags(user_query)
        
        # 結果をキャッシュに保存
        self.redis.setex(
            cache_key,
            self.cache_ttl,
            json.dumps(result, ensure_ascii=False)
        )
        
        return result
```

Redisが使えない場合は、Swiftのアプリ側でNSCacheを使ったメモリキャッシュで代替できます。壁紙アプリで実測したところ、よく使われる検索ワード上位100件をキャッシュするだけで、API呼び出し回数が約45%削減できました。

## 個人開発者として感じること

宮大工だった祖父が「手を動かすことが一つの信心」と言っていたことを、アプリ開発をしながらよく思い出します。2014年から10年以上、毎日コードを書いてきた経験から言えば、新しい技術を取り入れるときに重要なのは「技術のすごさ」より「自分のアプリで使う意味」だと感じています。

Gemini APIは確かに強力です。でも個人開発者として大切なのは、そのパワーを適切な場所に絞って使うことです。全画面にAIを詰め込もうとすると、コストも設計の複雑さも爆発します。「ここだけAPIを使えば、ユーザー体験が劇的に良くなる」という一点に絞ることが、長く続けられる個人開発の秘訣だと思っています。

まず一つの機能 — たとえば検索クエリのタグ最適化だけ — をGemini 2.5 Flashで実装してみてください。それだけでユーザーの検索体験は変わります。大きな変化は、小さな実装の積み重ねから生まれます。
