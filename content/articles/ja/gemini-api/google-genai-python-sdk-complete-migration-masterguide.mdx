プロジェクトで `import google.generativeai as genai` と書いてきた方は、そろそろ「なぜ新しいコードと動きが違うんだろう」と感じ始めているかもしれません。

2024年後半に Google が公開した新しい Python SDK `google-genai` は、旧ライブラリ `google-generativeai` と名前が似ているにもかかわらず、API の設計思想が大きく異なります。単純な名前の置き換えでは動かず、多くの開発者が移行時に思わぬエラーに直面しています。

## 1. なぜ今すぐ移行が必要なのか

### google-generativeai の非推奨化という現実

`google-generativeai` パッケージは、Gemini API の初期ベータ段階から提供されてきたライブラリです。しかし Google は 2024 年末から `google-genai` への移行を積極的に推奨し始め、新機能の追加対象を新 SDK のみに限定しています。

旧 SDK のまま使い続けると、以下の問題が生じます。

- **Gemini 2.5 Pro の Thinking mode が使えない**: `thinkingConfig` パラメータは新 SDK 専用です
- **Context Caching の最新 API が利用不可**: 新しいキャッシュ作成インターフェースが未実装です  
- **Files API の非同期処理に非対応**: 大容量ファイルのアップロードフローが異なります
- **セキュリティパッチの遅延**: バグ修正・パッチが新 SDK 優先で適用されます

実際に `pip show google-generativeai` でバージョンを確認すると、多くのプロジェクトがかなり古いバージョンを使い続けていることがわかります。

### 2つのパッケージの根本的な違い

表面上の変化はパッケージ名だけに見えますが、内部設計は別物です。

旧 SDK（`google-generativeai`）の設計哲学は「関数ベースの手続き的 API」でした。`genai.configure(api_key=...)` で初期化し、`genai.GenerativeModel()` でモデルを取得するシンプルな構造です。

新 SDK（`google-genai`）は「クライアントベースのオブジェクト指向 API」に移行しています。`genai.Client()` でクライアントオブジェクトを作成し、そのメソッドを通じてすべての操作を行う設計です。この違いが、移行時のつまずきの根本原因です。

```python
# ── 旧 SDK（google-generativeai） ──
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-1.5-pro")
response = model.generate_content("こんにちは")
print(response.text)

# ── 新 SDK（google-genai） ──
from google import genai

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")
response = client.models.generate_content(
    model="gemini-2.5-pro-latest",
    contents="こんにちは",
)
print(response.text)
```

インポート文が `import google.generativeai as genai` から `from google import genai` に変わり、モデルの使い方も `model.generate_content()` から `client.models.generate_content()` に変わっています。この 2 つの違いを理解するだけで、移行エラーの大半が解消されます。

## 2. 移行前の準備：影響範囲の把握

### 現在の依存関係を棚卸しする

移行作業を始める前に、まず現在のプロジェクトで旧 SDK がどこで使われているかを把握します。

```bash
# プロジェクト内の google-generativeai 使用箇所を一括検索
grep -r "google.generativeai\|import genai\|GenerativeModel\|genai.configure" . \
  --include="*.py" \
  -l

# 使用頻度の多いファイルを確認
grep -rh "google.generativeai\|GenerativeModel" . \
  --include="*.py" | \
  sort | uniq -c | sort -rn | head -20
```

このコマンドで影響を受けるファイルのリストが得られます。ファイル数が少なければ一括移行を、多ければモジュールごとの段階的移行を選びましょう。

### パッケージのインストール

```bash

# ただし混乱を避けるため、移行完了後に削除推奨

```

新 SDK はインストール後、`from google import genai` でインポートします。旧 SDK の `import google.generativeai as genai` と共存できますが、同じファイル内で混在させると予期せぬ動作の原因になるため避けましょう。

## 3. コア API の移行：基本パターン

### テキスト生成の移行

最も基本的な変更点から確認します。

```python
import os
from google import genai
from google.genai import types

# クライアント初期化（環境変数から API キーを読み込む）
client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

# 基本的なテキスト生成
def generate_text(prompt: str, model: str = "gemini-2.5-pro-latest") -> str:
    """テキスト生成の基本実装（エラーハンドリング付き）"""
    try:
        response = client.models.generate_content(
            model=model,
            contents=prompt,
            config=types.GenerateContentConfig(
                temperature=0.7,
                max_output_tokens=2048,
                top_p=0.9,
            ),
        )
        return response.text
    except genai.errors.APIError as e:
        # API エラー（429, 503 等）を明示的に処理
        print(f"API エラー: {e.status_code} - {e.message}")
        raise
    except Exception as e:
        print(f"予期せぬエラー: {e}")
        raise

# 使用例
result = generate_text("Python の async/await を初心者向けに説明してください")
print(result)
```

旧 SDK では `GenerativeModel` オブジェクトに `temperature` 等を渡していましたが、新 SDK では `GenerateContentConfig` で一元管理します。この変更によって、設定オブジェクトの再利用が簡単になりました。

### ストリーミングの移行

ストリーミングは特に変更が大きい部分です。

```python
import asyncio
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

# 同期ストリーミング（Webサーバー以外での使用）
def stream_sync(prompt: str) -> None:
    """同期ストリーミング実装"""
    for chunk in client.models.generate_content_stream(
        model="gemini-2.5-pro-latest",
        contents=prompt,
    ):
        if chunk.text:
            print(chunk.text, end="", flush=True)
    print()  # 改行

# 非同期ストリーミング（FastAPI, asyncio ベースのアプリ向け）
async def stream_async(prompt: str) -> None:
    """非同期ストリーミング実装（FastAPI等での使用に最適）"""
    async_client = genai.AsyncClient(api_key=os.environ.get("GEMINI_API_KEY"))
    
    async for chunk in await async_client.aio.models.generate_content_stream(
        model="gemini-2.5-pro-latest",
        contents=prompt,
    ):
        if chunk.text:
            print(chunk.text, end="", flush=True)
    print()

# 実行例
stream_sync("マルチエージェントシステムの設計原則を解説してください")
asyncio.run(stream_async("RAG（Retrieval-Augmented Generation）の仕組みを説明してください"))
```

旧 SDK では `model.generate_content(stream=True)` と引数で制御していましたが、新 SDK では `generate_content_stream()` という専用メソッドが用意されています。また、非同期クライアント `AsyncClient` が明示的に分離されたことで、FastAPI などの非同期フレームワークとの統合が格段にクリーンになりました。

### チャット（マルチターン会話）の移行

```python
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

# 会話の管理（旧SDKの ChatSession に相当）
def create_chat_session():
    """チャットセッションの作成"""
    return client.chats.create(
        model="gemini-2.5-pro-latest",
        config=types.GenerateContentConfig(
            system_instruction="あなたは親切な AI アシスタントです。日本語で簡潔に回答してください。",
            temperature=0.8,
        ),
    )

# 実際の会話ループ
chat = create_chat_session()

user_messages = [
    "Gemini 2.5 Pro の主な特徴を教えてください",
    "その中で実際のアプリ開発で最も役立つ機能はどれですか？",
    "その機能を使った具体的なコード例を見せてください",
]

for message in user_messages:
    print(f"User: {message}")
    response = chat.send_message(message)
    print(f"Gemini: {response.text}\n")
```

旧 SDK の `ChatSession` は新 SDK では `client.chats.create()` で得られるセッションオブジェクトに置き換わります。会話履歴の管理方法も変わっており、`chat.history` でアクセスできます。

## 4. Function Calling・構造化出力の移行

Function Calling は旧 SDK からも利用できましたが、新 SDK ではより直感的な記法に変わっています。

### Function Calling の新しい書き方

```python
from google import genai
from google.genai import types
from typing import Any

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

# ツール定義（旧SDKの FunctionDeclaration に相当）
def get_weather(city: str, unit: str = "celsius") -> dict[str, Any]:
    """指定した都市の天気を取得する（モック実装）"""
    # 実際の実装では天気APIを呼び出す
    weather_data = {
        "tokyo": {"temp": 22, "condition": "晴れ", "humidity": 60},
        "osaka": {"temp": 24, "condition": "曇り", "humidity": 65},
    }
    city_lower = city.lower()
    if city_lower in weather_data:
        data = weather_data[city_lower]
        temp = data["temp"]
        if unit == "fahrenheit":
            temp = temp * 9 / 5 + 32
        return {"city": city, "temperature": temp, "unit": unit, **data}
    return {"error": f"{city} のデータが見つかりません"}

# 新SDKでは Python 関数をそのままツールとして渡せる
response = client.models.generate_content(
    model="gemini-2.5-pro-latest",
    contents="東京と大阪の今の気温を教えてください",
    config=types.GenerateContentConfig(
        tools=[get_weather],  # Python関数を直接渡す（新SDKの強み）
        automatic_function_calling=types.AutomaticFunctionCallingConfig(
            disable=False,  # True にすると手動でツール呼び出しを制御
        ),
    ),
)

print(response.text)
# → 「東京は22°C（晴れ）、大阪は24°C（曇り）です。」のような回答が返る
```

旧 SDK では `FunctionDeclaration` で関数のスキーマを手動で定義する必要がありましたが、新 SDK では **Python 関数の型ヒントを自動でスキーマに変換**します。この改善により、ツール定義のコード量が大幅に削減されます。

詳しい Function Calling の実装パターンは [Function Calling 実践ガイド](/articles/gemini-api/gemini-function-calling-practical-guide) も合わせてご参照ください。

### 構造化出力（JSON mode）の移行

```python
from google import genai
from google.genai import types
from pydantic import BaseModel

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

# Pydantic モデルで出力スキーマを定義
class ArticleSummary(BaseModel):
    title: str
    main_points: list[str]
    difficulty: str  # "beginner", "intermediate", "advanced"
    estimated_read_time: int  # 分

def summarize_article(article_text: str) -> ArticleSummary:
    """記事を構造化 JSON として要約する"""
    response = client.models.generate_content(
        model="gemini-2.5-pro-latest",
        contents=f"以下の記事を要約してください：\n\n{article_text}",
        config=types.GenerateContentConfig(
            response_mime_type="application/json",
            response_schema=ArticleSummary,  # Pydanticモデルを直接渡す
        ),
    )
    # レスポンスを Pydantic モデルに変換
    return ArticleSummary.model_validate_json(response.text)

# 使用例
sample_article = """
Gemini 2.5 Pro は Google が 2025 年に発表した最新の大規模言語モデルです。
100 万トークンのコンテキストウィンドウ、Thinking モードによる高度な推論、
マルチモーダル入力（テキスト・画像・音声・動画）に対応しています。
"""

result = summarize_article(sample_article)
print(f"タイトル: {result.title}")
print(f"主なポイント: {result.main_points}")
print(f"難易度: {result.difficulty}")
print(f"読了時間: {result.estimated_read_time}分")
```

Pydantic モデルを `response_schema` に直接渡せるようになったのは新 SDK の大きな強みです。型安全な出力が保証され、後続の処理でパース処理が不要になります。

## 5. Gemini 2.5 Pro 新機能の活用

新 SDK に移行することで初めて利用できる Gemini 2.5 Pro の主要機能を解説します。

### Thinking mode（深い推論）の実装

Thinking mode は Gemini 2.5 Pro が段階的な推論を行う機能です。複雑な数学問題・コードデバッグ・論理的な分析に特に効果を発揮します。

```python
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

def solve_with_thinking(problem: str, thinking_budget: int = 8000) -> dict:
    """
    Thinking mode を使った高精度な問題解決
    
    Args:
        problem: 解いてほしい問題
        thinking_budget: 思考トークン上限（0 で無効化、-1 で制限なし）
    
    Returns:
        {"thinking": 思考過程, "answer": 最終回答}
    """
    response = client.models.generate_content(
        model="gemini-2.5-pro-latest",
        contents=problem,
        config=types.GenerateContentConfig(
            thinking_config=types.ThinkingConfig(
                thinking_budget=thinking_budget,
                include_thoughts=True,  # 思考過程をレスポンスに含める
            ),
        ),
    )
    
    thinking_text = ""
    answer_text = ""
    
    for part in response.candidates[0].content.parts:
        if hasattr(part, "thought") and part.thought:
            thinking_text += part.text
        else:
            answer_text += part.text
    
    return {
        "thinking": thinking_text,
        "answer": answer_text,
        "thinking_tokens": response.usage_metadata.thoughts_token_count,
        "total_tokens": response.usage_metadata.total_token_count,
    }

# 使用例：複雑なコードレビュー
result = solve_with_thinking("""
以下の Python 関数にはバグがあります。バグを特定し、修正してください。

def find_duplicate(nums):
    seen = set()
    for num in nums:
        if num in seen:
            return num
        seen.add(num)
    return None

# テストケース: find_duplicate([3,1,3,4,2]) → 3 が期待値
# しかし find_duplicate([1,2,3,4]) → None が返るべきところ -1 が返る
""")

print(f"思考過程（{result['thinking_tokens']} tokens）:")
print(result["thinking"][:500] + "...")
print(f"\n最終回答:")
print(result["answer"])
```

`thinking_budget` の設定は重要です。値が大きいほど精度が上がりますが、コストと応答時間も増加します。実用的には 4,000〜16,000 の範囲で調整するのが一般的です。

### Context Caching による大幅なコスト削減

大きなシステムプロンプトや参照ドキュメントを繰り返し使う場合、Context Caching は必須の最適化です。

```python
import datetime
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

# 大きなシステムプロンプト（通常は外部ファイルから読み込む）
LARGE_SYSTEM_PROMPT = """
あなたは 10 年以上の経験を持つシニアバックエンドエンジニアです。
以下の技術スタックに精通しています：
- Python / FastAPI / Django / SQLAlchemy
- PostgreSQL / Redis / Elasticsearch
- Kubernetes / Docker / Terraform
- 分散システム設計・マイクロサービス・イベント駆動アーキテクチャ
（中略... この部分が数千〜数万トークンになるケースを想定）
""" * 50  # 実際のプロンプトは非常に長い

# キャッシュ作成（1回だけ実行する）
def create_system_cache():
    """高コストなシステムプロンプトをキャッシュする"""
    cache = client.caches.create(
        model="gemini-2.5-pro-latest",
        config=types.CreateCachedContentConfig(
            contents=[LARGE_SYSTEM_PROMPT],
            ttl=datetime.timedelta(hours=1),  # 1時間キャッシュを保持
            display_name="senior-engineer-system-prompt",
        ),
    )
    print(f"キャッシュ作成: {cache.name}")
    print(f"トークン数: {cache.usage_metadata.total_token_count}")
    return cache.name

# キャッシュを使ったコンテンツ生成
def ask_with_cache(cache_name: str, question: str) -> str:
    """キャッシュされたコンテキストを使って質問に答える"""
    response = client.models.generate_content(
        model="gemini-2.5-pro-latest",
        contents=question,
        config=types.GenerateContentConfig(
            cached_content=cache_name,  # キャッシュ名を指定
        ),
    )
    
    # コスト確認（キャッシュヒット時はトークン単価が下がる）
    usage = response.usage_metadata
    print(f"プロンプトトークン: {usage.prompt_token_count}")
    print(f"キャッシュヒット: {usage.cached_content_token_count}")
    
    return response.text

# 使用例
cache_name = create_system_cache()

questions = [
    "PostgreSQL でページネーションを効率的に実装する方法を教えてください",
    "Redis を使ったセッション管理の設計パターンは？",
    "Kubernetes での Blue-Green デプロイメントの手順を教えてください",
]

for q in questions:
    print(f"\nQ: {q}")
    print(f"A: {ask_with_cache(cache_name, q)}\n")
```

キャッシュを使うと、大きなシステムプロンプトの処理コストが最大 75% 削減されます。リクエストのたびに同じ長いプロンプトを送っていた場合、Context Caching への移行は費用対効果が非常に高い投資です。詳しいコスト最適化は [Context Caching コスト最適化ガイド](/articles/gemini-api/gemini-api-context-caching-cost-optimization) をご覧ください。

## 6. よくある移行エラーと解決パターン

実際に移行作業を行うと、以下のエラーが頻発します。原因と解決策をまとめます。

### エラー 1：`AttributeError: module 'google.generativeai' has no attribute 'Client'`

**原因**: 旧 SDK の `google.generativeai` に対して `Client()` を呼び出そうとしています。

**解決策**: インポート文を変更してください。

```python
# ❌ 間違い（旧SDKのインポートで新SDKのメソッドを使おうとしている）
import google.generativeai as genai
client = genai.Client(api_key="...")  # AttributeError が発生

# ✅ 正しい（新SDKのインポート）
from google import genai
client = genai.Client(api_key="...")  # 正常に動作
```

### エラー 2：`TypeError: generate_content() got an unexpected keyword argument 'generation_config'`

**原因**: 旧 SDK の `generation_config` 引数が新 SDK では `config` に変更されています。

```python
# ❌ 旧SDK の書き方
model.generate_content(
    prompt,
    generation_config={"temperature": 0.7}  # TypeError
)

# ✅ 新SDK の書き方
from google.genai import types
client.models.generate_content(
    model="gemini-2.5-pro-latest",
    contents=prompt,
    config=types.GenerateContentConfig(temperature=0.7)  # 正常
)
```

### エラー 3：`AttributeError: 'GenerateContentResponse' object has no attribute 'parts'`

**原因**: レスポンスオブジェクトの構造が変わっています。

```python
# ❌ 旧SDK の書き方
response = model.generate_content(prompt)
text = response.parts[0].text  # AttributeError

# ✅ 新SDK の書き方（シンプルなケース）
response = client.models.generate_content(
    model="gemini-2.5-pro-latest",
    contents=prompt,
)
text = response.text  # 直接 .text でアクセス可能

# ✅ マルチパート・Thinking モードの場合
for part in response.candidates[0].content.parts:
    if hasattr(part, "thought") and part.thought:
        print(f"[思考]: {part.text}")
    else:
        print(f"[回答]: {part.text}")
```

### エラー 4：`google.auth.exceptions.DefaultCredentialsError`（Vertex AI バックエンド使用時）

**原因**: Vertex AI バックエンドを使う場合、Google Cloud の認証が必要。

```python
# Vertex AI バックエンドに切り替える場合
import os
from google import genai

# ① 環境変数で制御（推奨）
os.environ["GOOGLE_CLOUD_PROJECT"] = "your-project-id"
os.environ["GOOGLE_CLOUD_LOCATION"] = "us-central1"

client = genai.Client(
    vertexai=True,  # Vertex AI バックエンドを使用
    project="your-project-id",
    location="us-central1",
)

# ② API キーで利用する場合は vertexai=False（デフォルト）
client_api_key = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))
```

### エラー 5：非同期処理での `RuntimeError: This event loop is already running`


### 環境変数の安全な管理

```python
import os
from pathlib import Path
from dotenv import load_dotenv  # python-dotenv パッケージ

def load_config():
    """環境設定の安全な読み込み"""
    # 開発環境: .env ファイルから読み込み
    env_file = Path(".env")
    if env_file.exists():
        load_dotenv(env_file)

    if not api_key:

        "api_key": api_key,
        "project_id": os.environ.get("GOOGLE_CLOUD_PROJECT"),

def create_client():
```

### レート制限とリトライの実装

本番環境では必ずリトライ処理を実装します。

```python
import time
import random
from google import genai
from google.genai import errors

client = genai.Client(api_key=os.environ.get("GEMINI_API_KEY"))

def generate_with_retry(
    prompt: str,
    model: str = "gemini-2.5-pro-latest",
    max_retries: int = 3,
    base_delay: float = 1.0,
) -> str:
    """
    指数バックオフ付きリトライ実装
    
    本番環境では必ずこのパターンを使うこと。
    特に 429（レート制限）エラーは頻繁に発生します。
    """
    for attempt in range(max_retries + 1):
        try:
            response = client.models.generate_content(
                model=model,
                contents=prompt,
            )
            return response.text
            
        except errors.APIError as e:
            if e.status_code == 429:
                # レート制限エラー → 指数バックオフで再試行
                if attempt < max_retries:
                    delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
                    print(f"レート制限 (429)。{delay:.1f}秒後にリトライ... ({attempt + 1}/{max_retries})")
                    time.sleep(delay)
                    continue
                else:
                    print(f"最大リトライ回数に達しました ({max_retries} 回)")
                    raise
            elif e.status_code in (500, 503):
                # サーバーエラー → 短い待機後にリトライ
                if attempt < max_retries:
                    delay = base_delay * (attempt + 1)
                    print(f"サーバーエラー ({e.status_code})。{delay:.1f}秒後にリトライ...")
                    time.sleep(delay)
                    continue
                raise
            else:
                # その他のエラーはリトライしない（400, 401, 403 等）
                print(f"回復不可能なエラー ({e.status_code}): {e.message}")
                raise
    
    raise RuntimeError("リトライループから抜け出せませんでした")
```

レート制限の詳しい管理については [Gemini API レート制限・クォータ管理本番ガイド](/articles/gemini-api/gemini-api-rate-limiting-quota-management-production-guide) も参考にしてください。
