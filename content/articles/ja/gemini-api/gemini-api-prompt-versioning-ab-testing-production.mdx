Gemini APIを本番で運用していると、あるとき「ユーザーからのポジティブ反応が減っている」「カスタマーサポートに届く問い合わせの内容が微妙に変わっている」といった現象にぶつかることがあるのではないでしょうか。原因を追ってログを開いても、「プロンプトは3週間前に微修正しました」「でもその前後でモデルはGemini 2.5 Proのままです」という状況では、何が効いて何が効かなかったのかを数値で説明できません。私自身、個人開発しているチャット系のアプリでプロンプトを少し短く書き直しただけのつもりが、一部のユーザー層で応答品質が目に見えて落ちたことがあり、再現と切り戻しに半日近くかかったことがありました。

## ある日突然、ユーザー満足度が落ちた理由を説明できるか

プロンプトを変える動機は、だいたい次のいずれかです。応答が冗長だから短くしたい、日本語の敬体に揃えたい、ツール呼び出しの成功率を上げたい、コスト削減のためにモデルを一段軽くしたい。いずれも正当な動機ですが、変更した結果が「本当に狙い通りに動いたか」を数値で検証せずに本番へ流し続けると、気づかないうちに品質が静かに劣化していきます。

やっかいなのは、チャットのように正解が一つではないワークロードではユニットテストが効きにくいことです。エラーが出ていないから問題なく動いている、ように見えてしまいます。そこで必要になるのが、プロンプトを一つの「バージョン」として明示的に扱い、複数バージョンを本番トラフィックで比較しながら段階的に切り替えていく仕組みです。

## プロンプトに「バージョン」という概念が必要な3つの理由

### 理由1: モデル側のサイレントアップデート

Geminiに限らず、クラウドのLLMは背後でチェックポイントが更新されることがあります。同じ`gemini-2.5-pro`を呼び出しているつもりでも、ある時期を境に応答のトーンや長さが変わる、というのは現場では珍しくありません。プロンプトを変えていなくても品質指標は動きうる前提で監視を組んでおくと、モデル側の変化に由来する劣化を切り分けやすくなります。

### 理由2: コンテキスト肥大によるじわじわとした精度低下

System Instructionsに「こういう時はこう答えてください」を追記していくと、半年後には数千トークンのモンスターに育ちます。2Mトークンが入るからといって入れれば入れるほど良いわけではなく、命令同士が競合し始めるとモデルは優先順位を揺らします。バージョン管理をしないまま追記だけ続けると、どの追記が良く働いていて、どの追記が邪魔しているのかが最後まで分からなくなります。

### 理由3: チーム（あるいは自分自身）による同時編集のリグレッション

個人開発でも、週をまたぐと自分が前週書いたプロンプトの意図を覚えていない、ということが起きます。関連する記事として[Gemini 2.5 Pro System Instructions 運用ガイド](/articles/gemini-api/gemini-25-pro-system-instructions-mastery-guide)でも触れましたが、System Instructionsは「誰が・いつ・なぜ書いたか」が後から分かる状態で保管するのが原則です。GitのコミットメッセージだけではUI文言とロジックの関係が追いきれないので、専用のレジストリで持つ方が健全だと考えています。

## 本稿で作るアーキテクチャの全体像

完成形は4つの部品で構成します。ここから1つずつコードを書いていきます。

- Prompt Registry: Firestoreにプロンプトのバリアントをドキュメントとして保管する小さなレジストリです。`status`フィールドで配信中か退役済みかを制御します。
- Traffic Splitter: ユーザーIDと`prompt_key`からハッシュを計算し、決定論的にバリアントを選ぶロジックです。同じユーザーには常に同じバリアントが返るので、比較が崩れません。
- Metrics Collector: アプリ側の薄いラッパーで、Gemini API呼び出しごとにバリアントIDとレイテンシ、トークン消費、エラー情報を必ず記録します。
- Evaluation Loop: 本番ログを日次・週次でサンプリングし、LLM-as-judgeで採点して、バリアント別の平均スコアの差を確認する評価バッチです。

設計上のポイントは、「バリアント = プロンプト + モデル + サンプリングパラメータ」を一つの単位として扱うことです。プロンプトだけ版管理しても、裏でモデルを差し替えられたら比較が成立しないため、最初からまとめて括る形にしておきます。

## Step 1: Firestore でプロンプトレジストリを作る

まずFirestoreに`prompt_variants`コレクションを用意し、Pythonから読み出す薄いクラスを書きます。このレジストリは60秒だけキャッシュする、くらいの雑なTTLで十分です。プロンプト変更は1日に何度もあるものではないので、過剰なリアルタイム性は要りません。

```python
# prompt_registry.py
# Firestore でプロンプトの複数バリアントをドキュメントとして管理する
from google.cloud import firestore
from dataclasses import dataclass
import time

@dataclass
class PromptVariant:
    variant_id: str         # 例: v3 / v3-rewrite
    model: str              # 例: gemini-2.5-pro / gemini-2.5-flash
    system_instruction: str
    temperature: float
    thinking_budget: int    # 0 で無効化
    weight: int             # 配信比率(整数。active のものだけ合計して分母に使う)
    status: str             # active / shadow / archived

class PromptRegistry:
    def __init__(self, collection: str = "prompt_variants"):
        self._db = firestore.Client()
        self._collection = collection
        self._cache: dict[str, list[PromptVariant]] = {}
        self._cache_refreshed_at = 0.0
        self._cache_ttl = 60  # 秒

    def _refresh(self, prompt_key: str) -> None:
        docs = (self._db.collection(self._collection)
                .where("prompt_key", "==", prompt_key)
                .where("status", "in", ["active", "shadow"])
                .stream())
        self._cache[prompt_key] = [PromptVariant(**doc.to_dict()) for doc in docs]
        self._cache_refreshed_at = time.time()

    def get_variants(self, prompt_key: str) -> list[PromptVariant]:
        if (time.time() - self._cache_refreshed_at) > self._cache_ttl:
            self._refresh(prompt_key)
        if prompt_key not in self._cache or not self._cache[prompt_key]:
            raise RuntimeError(f"prompt_key not found or empty: {prompt_key}")
        return self._cache[prompt_key]

# 期待する動作:
#   registry = PromptRegistry()
#   variants = registry.get_variants("chat_reply")
#   → [PromptVariant(variant_id=v3, weight=80, status=active, ...),
#      PromptVariant(variant_id=v3-rewrite, weight=20, status=active, ...)]
```

ポイントは、`status`に`active`と`shadow`の2つを用意していることです。`active`はユーザートラフィックに参加しますが、`shadow`は実トラフィックには出さず、後述のオフライン評価だけに回す扱いにします。勝負をかける前に少数のサンプルで評価できる「控え室」を持っておくと、本番投入が格段に安全になります。

## Step 2: 決定論的ハッシュでトラフィックを分割する

A/Bテストの肝は、同じユーザーに常に同じバリアントを返すことです。毎回ランダムに振ってしまうと、あるユーザーが同じ質問を3回投げたときに毎回別バリアントが返り、比較どころかユーザー体験が壊れます。Pythonの組み込み`hash()`はプロセス起動ごとにシード化されるので、決定論的な分割には使えません。SHA-256のような普通のハッシュを使います。

```python
# traffic_split.py
# user_id と prompt_key から SHA-256 を取り、weight の比率で区間を切る
import hashlib
from typing import Iterable
from prompt_registry import PromptVariant

def pick_variant(user_id: str, prompt_key: str,
                 variants: Iterable[PromptVariant]) -> PromptVariant:
    actives = [v for v in variants if v.status == "active"]
    if not actives:
        raise RuntimeError("No active variants configured")
    total = sum(v.weight for v in actives)
    if total <= 0:
        raise ValueError("Sum of weights must be positive")

    seed = f"{prompt_key}:{user_id}".encode()
    bucket = int(hashlib.sha256(seed).hexdigest(), 16) % total

    cumulative = 0
    for v in actives:
        cumulative += v.weight
        if bucket < cumulative:
            return v
    return actives[-1]  # 到達しないはずだが丸めへのフォールバック

# 期待する動作:
#   同じ user_id と prompt_key は、プロセスを再起動しても同じバリアントを返す
#   全体として weight の比率(例: 80/20)どおりに分布する
```

ここで`prompt_key`も種に入れているのは、別の`prompt_key`で同じユーザーを同じ側に偏らせないためです。例えば「チャット応答」と「要約生成」で常に同じユーザーが`v3-rewrite`側に落ちると、そのユーザーの体験が偏ります。`prompt_key`を混ぜるだけで、タスクごとに独立に分割できます。

## Step 3: メトリクス収集をアプリ層の薄いラッパーに閉じ込める

「ログを取る」仕組みをアプリのあちこちに書くと、徐々に忘れ漏れが発生します。Gemini APIを叩く場所は一つのラッパーに寄せて、そこで必ずバリアントIDとレイテンシ、トークン数を記録する規律にします。関連して[Gemini APIの本番オブザーバビリティ構成](/articles/gemini-api/gemini-api-observability-production-monitoring)で触れたメトリクス設計と揃えておくと、ダッシュボード側の可視化がそのまま流用できて楽になります。

```python
# gemini_client.py
# Gemini API 呼び出しをバリアント選択とログ書き込みで包むラッパー
import time, uuid
from google import genai
from google.cloud import firestore
from prompt_registry import PromptRegistry
from traffic_split import pick_variant

_client = genai.Client()
_registry = PromptRegistry()
_logs = firestore.Client().collection("prompt_logs")

def generate(user_id: str, prompt_key: str, user_input: str) -> tuple[str, str]:
    variants = _registry.get_variants(prompt_key)
    variant = pick_variant(user_id, prompt_key, variants)

    log_id = uuid.uuid4().hex
    started = time.monotonic()
    error = None
    usage = {}
    text = ""
    try:
        resp = _client.models.generate_content(
            model=variant.model,
            contents=user_input,
            config={
                "system_instruction": variant.system_instruction,
                "temperature": variant.temperature,
                "thinking_config": {"thinking_budget": variant.thinking_budget},
            },
        )
        text = resp.text or ""
        um = resp.usage_metadata
        if um:
            usage = {
                "prompt_tokens": um.prompt_token_count,
                "output_tokens": um.candidates_token_count,
                "cached_tokens": getattr(um, "cached_content_token_count", 0) or 0,
            }
    except Exception as e:
        # クラス名と短い内容だけ残す(個人情報を含みうる stack trace は別ルートへ)
        error = f"{type(e).__name__}: {str(e)[:200]}"
        raise
    finally:
        # 例外が出ても必ずログを残す。エラー率の急増がリグレッション検知の一次シグナルになる
        _logs.document(log_id).set({
            "log_id": log_id,
            "user_id": user_id,
            "prompt_key": prompt_key,
            "variant_id": variant.variant_id,
            "model": variant.model,
            "user_input": user_input,
            "output_text": text,
            "latency_ms": int((time.monotonic() - started) * 1000),
            "error": error,
            "usage": usage,
            "created_at": firestore.SERVER_TIMESTAMP,
        })
    return text, log_id

# 期待する動作:
#   text, log_id = generate("u_1234", "chat_reply", "英語で簡単に返してください")
#   Firestore の prompt_logs にバリアントIDとレイテンシ、トークン数が1レコード書かれる
```

`finally`でログを書いているのは意図的です。例外が出たケースこそ「ある変更でエラーが増えていないか」を追う一次情報になるので、成功パスと同じ形式でそろえておきます。

## Step 4: オフライン評価で回帰を検知する

ログが溜まったら、日次・週次でサンプリングしてバリアント別に採点します。採点は人手だと続かないので、評価自体もGeminiに任せます。ここで大事なのは、**評価モデルは応答モデルよりワンランク強いものを使う**ことです。同じモデルで自己評価すると、バイアスがかかって現状肯定的な点数が出がちです。応答を`gemini-2.5-flash`で出しているなら、採点は`gemini-2.5-pro`に回します。

```python
# eval_regression.py
# 本番ログをサンプリングし、LLM-as-judge でバリアント別のスコア平均を出す
import json, statistics
from google import genai
from google.cloud import firestore

_client = genai.Client()
_db = firestore.Client()

JUDGE_SYSTEM = """あなたは応答品質の厳格な評価者です。
次の観点で 1〜5 の整数で採点してください(5が最高)。
- accuracy: 事実として正しいか
- helpfulness: 質問者の目的を満たしているか
- conciseness: 冗長でないか
出力は JSON のみ、キーは上記3つ。説明文は出力しないでください。"""

def judge(user_input: str, output_text: str) -> dict:
    resp = _client.models.generate_content(
        model="gemini-2.5-pro",
        contents=f"【質問】\n{user_input}\n\n【応答】\n{output_text}",
        config={
            "system_instruction": JUDGE_SYSTEM,
            "response_mime_type": "application/json",
            "temperature": 0.0,
        },
    )
    try:
        return json.loads(resp.text)
    except (json.JSONDecodeError, TypeError):
        # JSON になっていない場合は採点失敗として明示的にマークする
        return {"accuracy": 0, "helpfulness": 0, "conciseness": 0, "parse_error": True}

def evaluate(prompt_key: str, sample: int = 200) -> dict:
    logs = (_db.collection("prompt_logs")
            .where("prompt_key", "==", prompt_key)
            .order_by("created_at", direction=firestore.Query.DESCENDING)
            .limit(sample)
            .stream())
    buckets: dict[str, list[int]] = {}
    for log in logs:
        d = log.to_dict()
        if d.get("error") or not d.get("output_text"):
            continue
        score = judge(d["user_input"], d["output_text"])
        if score.get("parse_error"):
            continue
        buckets.setdefault(d["variant_id"], []).append(score["accuracy"])

    return {
        vid: {
            "n": len(s),
            "mean": round(statistics.mean(s), 2),
            "stdev": round(statistics.stdev(s), 2) if len(s) > 1 else 0.0,
        }
        for vid, s in buckets.items() if s
    }

# 期待する動作(例):
#   evaluate("chat_reply")
#   → {"v3": {"n": 160, "mean": 4.21, "stdev": 0.58},
#      "v3-rewrite": {"n": 40, "mean": 3.67, "stdev": 0.81}}
#   → 新バリアントの平均が明確に下がっていたら、status を archived に戻して撤退する
```

差が有意かどうかを厳密に見たい場合は、標準誤差を出して$\bar{x}_a - \bar{x}_b$の差を$\sqrt{s_a^2/n_a + s_b^2/n_b}$で割り、2を超えたら有意、といったざっくり基準で運用しても十分です。関連して[プロンプト評価パイプラインの構築ガイド](/articles/gemini-api/gemini-api-prompt-evaluation-optimization-pipeline)では評価データセットの作り方まで踏み込んで書いていますので、より厳密に比較したい方はあわせてご覧ください。

## 本番運用で実際に踏んだ落とし穴

仕組みを組んでも、運用側の設計ミスで計測が崩れることがよくあります。私が実際に踏んだ4つを共有します。

### 落とし穴1: プロンプトとモデルIDを別々のフィーチャーフラグで管理してしまう

プロンプト側のフラグで`v3-rewrite`を20%に回しつつ、モデル側のフラグを独立に切り替えた結果、`v3-rewrite`のサンプルが`2.5-flash`と`2.5-pro`に散らばってしまい、スコアのばらつきが説明できなくなる——という事故がありました。「バリアント = プロンプト + モデル + パラメータ」を1つのドキュメントに束ねる設計にしておくと、こういう分裂が物理的に起きません。

### 落とし穴2: サンプルサイズが小さいまま勝ち判定する

20件のログを見て「新バリアントの方が平均0.3点高いから勝ち」としてしまうと、実はそれは誤差の範囲でした、というのが頻発します。私の運用では、**最低200件・片側50件以上**が揃うまで判定しないルールにしています。Geminiの応答は確率的なので、信頼区間の広さをなめると痛い目に遭います。

### 落とし穴3: キャッシュ戦略とA/B分割が衝突する

Gemini APIの[コンテキストキャッシング](/articles/gemini-api/gemini-api-context-caching-cost-optimization)を使っている場合、バリアントごとに別キャッシュが作られてヒット率が下がり、コストが跳ねることがあります。新バリアントの`weight`を10〜20%以下に抑えてカナリア的に入れるか、キャッシュ対象はSystem Instructionsのうち「共通部分だけ」に限定して、バリアント固有の差分をコンテンツ側に置く、といった再構成が必要になります。

### 落とし穴4: 多言語・多地域ユーザーの分布を考慮しない

ユーザーIDだけでハッシュしていると、週末に日本語ユーザーが多い、平日昼は英語ユーザーが多い、といった時系列の偏りがバリアント間に漏れます。スコアの差に見えたものが実は言語差だった、ということも起きます。`prompt_key`に`lang:ja`のような補助キーを含めてハッシュすると、言語別に独立にA/B分割でき、比較がクリーンになります。

## この仕組みを運用に乗せるための、最初の一歩

いきなり4部品すべてを作ろうとすると重く感じますが、**まずはStep 3のラッパーだけ入れて、バリアントIDを`default`固定でログに残し始める**のが最も費用対効果が高いです。1週間分のログが溜まると、それだけでレイテンシ分布やトークン消費の実態が見え、どこを改善するとコストが下がるか判断できるようになります。レジストリとトラフィック分割は、次に試したい変更が出てきたタイミングで追加しても遅くありません。

プロンプト運用をさらに本格化させたい場合、[本番環境でのレート制限とクォータ管理](/articles/gemini-api/gemini-api-rate-limiting-quota-management-production-guide)と[誤応答の自動検知パイプライン](/articles/gemini-api/gemini-wrong-answer-detection-production-auto-eval)を組み合わせると、異常検知から再学習前の仮説検証までを一本の流れで扱えるようになります。書籍で腰を据えて学びたい方には[AIエンジニアのための機械学習システムデザインパターン（澁井雄介）](https://www.amazon.co.jp/dp/4798183652/?tag=pinocchio-22)が、MLシステム全般の設計思想を整理するのに役立ちました。
