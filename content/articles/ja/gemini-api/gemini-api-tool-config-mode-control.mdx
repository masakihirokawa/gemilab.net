Gemini API に関数（ツール）を登録したら、こちらが何も指示していない雑談の場面でも勝手に関数が呼ばれてしまった、という経験はないでしょうか。私も初めて Function Calling を本番アプリに組み込んだとき、ユーザーが単に「ありがとう」と返しただけなのに `search_products` が呼ばれて、無駄な API コールが走ってしまう事態に直面しました。

この「呼んでほしくないときに呼ばれる」問題を、コードの if 文で弾くのではなくモデル側で制御するための仕組みが、Gemini API の `tool_config` です。AUTO・ANY・NONE の 3 つのモードを正しく使い分けると、エージェントらしい自律的な挙動と、厳密なデータ抽出のような決定論的な挙動を同じ API で切り替えられます。

この記事では `tool_config` の各モードがどう動くのかを実装例とあわせて整理し、開発現場でよく遭遇するつまずきを減らすための設計指針をまとめます。

## tool_config は「誰が関数呼び出しを決めるか」を切り替えるスイッチ

Gemini API の Function Calling はデフォルトだとモデルが自律的に判断します。ユーザーの発話から「これはツールを使うべきだ」と推論したら関数呼び出し（Function Call）のメッセージを返し、ツール不要だと判断すればそのまま自然言語で返答します。この「判断の主体」を切り替えるのが `tool_config.function_calling_config.mode` の役割です。

3 つのモードはそれぞれ次のような役割を持ちます。

- **AUTO**: モデルが関数を呼ぶかどうかを自分で決めます。通常のチャットエージェントで使うデフォルトの挙動です。
- **ANY**: モデルは必ずいずれかの関数を呼び出します。自然言語で答えることはできません。構造化データを抽出したい、フォームの空欄を埋めたい、といった用途で威力を発揮します。
- **NONE**: モデルは関数を一切呼び出さず、必ず自然言語で応答します。同じアプリで「今はツール禁止のフェーズ」を一時的に作りたいときに便利です。

つまりエージェントの自律性を最大化したいときは AUTO、逆に確実に構造化された結果がほしいときは ANY、会話の前半だけは素直に話を聞きたいときは NONE、という使い分けになります。

## AUTO で起きる「勝手に呼ばれる」問題の現場感覚

AUTO で運用していて最初にぶつかりがちなのが、先ほどの例のように雑談や短い確認発話でも関数が呼ばれてしまうケースです。これはモデルが「ユーザーの発話に対しては基本的にツールを活用するのが親切だ」と過度に学習していることが背景にあります。

このとき最初にやるべきは tool_config をいじることではなく、`system_instruction` で「どういう発話のときにツールを使うか」を言語化することです。それでも抑えきれない場合や、アプリのフェーズごとに厳密に制御したい場合に初めて `tool_config` が登場します。

```python
# 動作確認: google-genai>=0.6.0 / Python 3.10+
# pip install google-genai
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

# 商品検索ツールの定義
search_products = types.FunctionDeclaration(
    name="search_products",
    description="ECサイトの商品をキーワード検索します",
    parameters=types.Schema(
        type="OBJECT",
        properties={"query": types.Schema(type="STRING")},
        required=["query"],
    ),
)
tools = [types.Tool(function_declarations=[search_products])]

# ① デフォルトの AUTO — モデルが判断して呼ぶ / 呼ばない を決める
config_auto = types.GenerateContentConfig(
    tools=tools,
    tool_config=types.ToolConfig(
        function_calling_config=types.FunctionCallingConfig(mode="AUTO"),
    ),
    system_instruction=(
        "あなたは商品検索アシスタントです。"
        "ユーザーが商品を探している意図が明確なときだけ search_products を呼び出し、"
        "挨拶やお礼には自然言語で短く応じてください。"
    ),
)

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="ありがとう、助かったよ",
    config=config_auto,
)
# 期待出力: function_call は含まれず、素直なお礼の文章が返る
print(resp.candidates[0].content.parts[0])
```

`system_instruction` で境界を明示し、そのうえで `tool_config=AUTO` を組み合わせるのが、AUTO 運用でのスタンダードな書き方です。

## ANY モードで Gemini を「構造化抽出器」として使い切る

ANY モードは発想を転換すると一気に便利になります。ポイントは「関数が必ず 1 回呼ばれる」という制約を、そのまま構造化データの返却チャネルとして使うことです。Gemini のレスポンスから JSON を抽出するためだけに `responseSchema` を書くよりも、抽出ロジックそのものを関数定義として書けるので、Python の dataclass や TypedDict と相性が良いという利点があります。

```python
# 議事録から ToDo をきれいに取り出す実装例
extract_todos = types.FunctionDeclaration(
    name="extract_todos",
    description="議事録テキストから ToDo のリストを抽出します",
    parameters=types.Schema(
        type="OBJECT",
        properties={
            "todos": types.Schema(
                type="ARRAY",
                items=types.Schema(
                    type="OBJECT",
                    properties={
                        "task": types.Schema(type="STRING"),
                        "owner": types.Schema(type="STRING"),
                        "due": types.Schema(type="STRING", description="YYYY-MM-DD"),
                    },
                    required=["task", "owner"],
                ),
            )
        },
        required=["todos"],
    ),
)

config_any = types.GenerateContentConfig(
    tools=[types.Tool(function_declarations=[extract_todos])],
    tool_config=types.ToolConfig(
        function_calling_config=types.FunctionCallingConfig(mode="ANY"),
    ),
)

resp = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=(
        "以下の議事録から ToDo を抽出してください:\n"
        "・山田: 見積りを金曜までに提出\n"
        "・佐藤: API 設計書レビュー、来週月曜\n"
    ),
    config=config_any,
)

fc = resp.candidates[0].content.parts[0].function_call
# 期待出力: fc.name == "extract_todos"
#          fc.args["todos"] に 2 件の構造化 ToDo が入る
print(fc.args)
```

ANY モードは「必ず関数を呼ぶ」という強い制約のおかげで、モデルが「抽出対象がなさそうなので自由文で答えておきます」と逃げる挙動を封じられます。人の手で作ったルールベースでは取りこぼしていたバリエーション豊かな入力にも、粘り強く構造化してくれる印象です。

## allowed_function_names で呼べる関数をさらに絞る

モードを ANY にすると「何かしらの関数を呼ぶ」ことまでは保証されますが、ツールが複数登録されていると「どの関数を呼ぶか」はモデル任せです。たとえば `search_products` と `add_to_cart` の両方を登録しているチャットアプリで、ユーザーがまだ商品を特定していない段階では必ず `search_products` 側だけを呼ばせたい、という場面があります。

こういうときに使うのが `allowed_function_names` です。リストに渡した関数だけが候補になるので、アプリのフェーズに応じて候補集合を絞り込むと、無駄な呼び出しや不適切な呼び出しを構造的に防げます。

```python
config_any_restricted = types.GenerateContentConfig(
    tools=[types.Tool(function_declarations=[search_products, add_to_cart])],
    tool_config=types.ToolConfig(
        function_calling_config=types.FunctionCallingConfig(
            mode="ANY",
            allowed_function_names=["search_products"],
        ),
    ),
)
# このフェーズでは add_to_cart は呼ばれず、必ず search_products が選ばれる
```

`allowed_function_names` は AUTO モードでも使えます。AUTO のまま「呼ばれる可能性がある関数はこのサブセットだけ」と絞ると、ツールリストが大きくなっても挙動のコントロールがしやすくなります。既存アプリのツールを段階的に本番投入していくときにも重宝する設計です。

## 本番に載せる前に確認したい設計チェックリスト

tool_config は強力ですが、モード選択だけで全てを解決しようとすると苦しくなる場面もあります。実装を本番に載せる前に、次の観点でいつも確認するようにしています。

- **system_instruction と役割分担しているか**: 「いつツールを使うか」はまず自然言語で明示し、`tool_config` は最後の安全装置として使う方が、プロンプトの変更にも強くなります。詳しくは [Gemini API の system_instruction 設計ガイド](/articles/gemini-api/gemini-api-system-instruction-prompt-engineering-showcase) を参考にしてください。
- **フェーズごとにモードを切り替えているか**: 会話の前半は AUTO、情報が出そろったら ANY に切り替えて構造化データを取り出す、といった 2 段構えにすると体験が安定します。
- **呼ばれなかったときのフォールバックを書いているか**: AUTO の場合は関数呼び出しが発生しないケースがあります。`parts` をループして `function_call` の有無を毎回確認する、というシンプルなルールを守るだけで、例外処理のバグがかなり減ります。運用中に遭遇した典型的な失敗例は [関数呼び出しがうまく動かないときの診断フロー](/articles/gemini-api/gemini-function-calling-not-working-troubleshooting) にまとめました。
- **ストリーミングと併用するときの挙動を把握しているか**: Function Call はチャンクの最後にまとめて届くことが多く、テキストと同じ感覚で UI に流すと見栄えが崩れます。ストリーミング時の扱いは [Gemini API ストリーミング × Function Calling 実装ガイド](/articles/gemini-api/gemini-api-streaming-function-calling-guide) を参照してください。

設計の引き出しを増やしたいときは、書籍で体系的に Function Calling の思想を学ぶのもおすすめです。とくに [LLM のプロンプトエンジニアリング（Louis-François Bouchard 著）](https://www.amazon.co.jp/dp/4814400950/?tag=pinocchio-22) は、ツール呼び出しを含む LLM 設計の前提知識を丁寧に押さえられる一冊で、今回のような「どこまでをモデルに任せ、どこからルールで縛るか」を考える視点が得られます。

## 次に試すこと

まずは既存の AUTO ベースのエージェントに対して、議事録抽出や問い合わせ分類のような「必ず構造化されたデータが欲しい箇所」を 1 つだけ切り出し、ANY モード + 単一の関数で書き換えてみてください。この小さな置き換えだけでも、従来の `responseSchema` + JSON 解析に比べて失敗時のデバッグが格段に楽になるはずです。慣れてきたら `allowed_function_names` でフェーズごとの候補集合を設計し、エージェントのふるまいを段階的に引き締めていくと、ユーザー体験が崩れずに機能を増やしていけます。
