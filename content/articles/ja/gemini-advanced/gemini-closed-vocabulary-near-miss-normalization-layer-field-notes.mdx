壁紙アプリに投稿された画像を30カテゴリへ振り分けるバッチを回していたとき、`responseSchema` の `enum` に無い文字列が返ってくること自体は覚悟していました。想定していなかったのは、その外れ値をリトライで直そうとすると、二度目もほとんど同じ言葉が返ってくることです。「風景」を期待した画像に `"scenery"` が返り、もう一度投げても `"scenery"`。モデルは壊れているのではなく、その画像に対しては本気でその語がいちばん近いと考えていました。

つまりこれはランダムな揺らぎではなく、語彙のズレでした。ズレをリトライで殴っても、往復のコストと待ち時間が増えるだけで、返ってくる答えは変わりません。個人開発でバッチを夜間に流している身としては、この一往復が積み重なると翌朝の完了時刻にそのまま効いてきます。ここでは、外れ方をまず測り、リトライの前に「正規化する層」を挟んだときに何がどれだけ変わったのかを、実測値とともに残しておきます。

enum が無視される仕組みそのものと最初の回避策は、以前 [responseSchema の enum 指定なのに違う文字列が返る現象の記事](/articles/gemini-api/gemini-api-response-schema-enum-ignored-fix) にまとめました。本稿はその続きにあたり、「バリデーションして1回リトライする」という素直な対処が、規模が出たときになぜ割に合わなくなるのかを掘り下げます。

## リトライを疑う前に、外れ方の分布を見た

対処を決める前に、まず一度だけ全件を素通しして、enum を外したラベルがどう外れているのかを数えました。判断材料が「たまに変な値が返る」という体感のままだと、正しい打ち手が選べないからです。

対象は壁紙8,142枚、`responseSchema` に30カテゴリの `enum` を指定した1パスの結果です。enum に一致しなかったのは312件（全体の約3.8%）。その312件を手作業で見ていくと、外れ方はきれいに3つの山に分かれました。

  </thead>

    <tr><td>別名・表記ゆれ（機械的に解決可能）</td><td>231件</td><td>scenery → 風景、night view → 夜景、花 → 植物</td></tr>
    <tr><td>意味は近いが別名表に無い</td><td>49件</td><td>「渓谷の写真」→ 自然、「街の明かり」→ 夜景</td></tr>
    <tr><td>本当に曖昧・複数該当</td><td>32件</td><td>「自然・動物」複合、抽象度が高く判断保留すべきもの</td></tr>

231件、つまり約74%は、モデルが返した語と手元の正解ラベルが「同じものを別の言葉で言っている」だけでした。ここに気づいた瞬間、リトライという発想が的外れだと分かりました。同じ画像を投げ直しても、モデルの語彙観は変わらないので、二度目も `"scenery"` が返ってきます。直すべきは受け取り側であって、モデルへの問い合わせ回数ではありませんでした。

もう一つ大事だったのは、いちばん右下の32件です。これは正規化してはいけないグループでした。機械的に最も近いラベルへ寄せてしまうと、本来「その他」や人手確認に回すべき画像を、それらしいカテゴリに押し込んでしまいます。分類の信頼を落とすのは、実はこの押し込みのほうです。これは本番運用でいちばん静かに効く落とし穴で、精度の数字には表れません。

## 近ミスを機械的に解く二段構え

方針はシンプルです。out-of-set のラベルが来たら、まず決定的な別名表で引き、引けなければ埋め込みの最近傍で寄せ、それでも自信が持てなければ正規化せずに保留へ回す。モデルへの再問い合わせは、この保留の中でも「もう一度だけ視点を変えて訊く価値がある」ものに限定します。

別名表は、実際に観測した外れ値からしか作りません。想像で網羅しようとすると保守できない辞書になるので、逸脱ログに出てきた語だけを、確認しながら少しずつ canonical へ結びつけていきます。

```python
import unicodedata
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

# 手元の正解語彙（30カテゴリのうち一部を抜粋）
CANONICAL = ["風景", "夜景", "植物", "動物", "自然", "抽象", "宇宙", "海", "その他"]

# 実際に逸脱ログで観測した語だけを結びつける。想像で足さない
ALIASES = {
    "scenery": "風景", "landscape": "風景", "けしき": "風景",
    "night view": "夜景", "夜の街": "夜景",
    "花": "植物", "flower": "植物", "plant": "植物",
    "animal": "動物", "nature": "自然",
}

def _norm(s: str) -> str:
    # 全角半角・大文字小文字・前後空白の揺れを吸収してから引く
    return unicodedata.normalize("NFKC", s).strip().lower()

_ALIAS_INDEX = {_norm(k): v for k, v in ALIASES.items()}
```

第一段の別名表で引けたものは、そのまま canonical として受け入れます。ここで解決できるのが先ほどの231件の大半です。

第二段は、別名表に無い語（49件のグループ）を `gemini-embedding-2` で最近傍のカテゴリへ寄せます。ポイントは、いちばん近いカテゴリとの距離だけで決めず、一位と二位の差（マージン）を見ることです。マージンが小さいときは「どちらとも言えない」ので、無理に寄せずに保留へ落とします。

```python
import numpy as np

def _embed(texts: list[str]) -> np.ndarray:
    resp = client.models.embed_content(
        model="gemini-embedding-2",
        contents=texts,
        config=types.EmbedContentConfig(task_type="SEMANTIC_SIMILARITY"),
    )
    vecs = np.array([e.values for e in resp.embeddings], dtype=np.float32)
    # コサイン類似度で比べるため単位ベクトルへ
    return vecs / np.linalg.norm(vecs, axis=1, keepdims=True)

# canonical 側のベクトルは起動時に一度だけ作って使い回す
_CANON_VECS = _embed(CANONICAL)

def nearest_canonical(label: str, margin: float = 0.06):
    v = _embed([label])[0]
    sims = _CANON_VECS @ v            # 各カテゴリとの類似度
    order = np.argsort(sims)[::-1]
    top, second = order[0], order[1]
    if sims[top] - sims[second] < margin:
        return None, float(sims[top])  # 一位と二位が僅差 → 寄せない
    return CANONICAL[top], float(sims[top])
```

この二段を、一つの受け入れゲートにまとめます。戻り値には「どう解決したか」の経路を必ず添えて、後でログとして残せるようにしておきます。経路が見えないと、別名表を育てるべきか、マージンを調整すべきかの判断ができません。

```python
def resolve_label(raw: str):
    if raw in CANONICAL:
        return raw, "in_set"

    hit = _ALIAS_INDEX.get(_norm(raw))
    if hit:
        return hit, "alias"

    canon, sim = nearest_canonical(raw)
    if canon is not None and sim >= 0.82:
        return canon, f"embedding:{sim:.3f}"

    # ここまで来たものは機械的に確定しない。保留に回す
    return None, "unresolved"
```

`resolve_label` が `None` を返した画像だけが、人手確認か、視点を変えた再問い合わせの候補になります。ここで初めて、限定的にモデルへ投げ直す価値が出てきます。全件を無条件にリトライするのとは、往復回数がまるで違います。

## あえて正規化しない、という判断

実装より難しかったのは、しきい値をどこに置くかでした。`0.82` という類似度の下限も、`0.06` のマージンも、最初から正解が分かっていた数字ではありません。312件を目で見ながら、寄せてよかったものと、寄せると事故るものを分ける線を探しました。

たとえば「渓谷の写真」は「自然」に寄せて問題ありませんでしたが、「自然・動物」のように二つのカテゴリを跨ぐ返り値は、機械的にどちらかへ寄せた瞬間に片方の情報を捨てることになります。こういうものは正規化せず、`その他` でも `動物` でもなく、明示的に「保留」という状態を持たせました。分類台帳に確信度と一緒に保留フラグを残しておくと、後から人手でまとめて見直せます。

私はこの「寄せない勇気」を、精度と同じくらい大事な設計判断だと考えています。近ミスを全部それらしく埋めてしまう分類器は、数字の上では欠損が減って見えますが、検索体験の中では静かに間違いを増やします。壁紙アプリの場合、「動物」で探した人に自然風景が混ざるのは、分類が空欄なことよりも体験を損ないます。保留はサボりではなく、後で正しく直すための余白です。

保留に回った画像を、意味的な近さで既存カテゴリと突き合わせて選別する具体的なやり方は、[カテゴリを増やしたときの差分再分類の記事](/articles/gemini-advanced/gemini-taxonomy-expansion-selective-reclassification-ledger) でも触れています。語彙そのものを増やすかどうかの判断とも地続きの話です。

## 再問い合わせを最後の手段に回した結果

正規化層を挟んだ後の内訳が、この設計の答えでした。同じ8,142枚を通したときの312件の行き先を並べます。

  <thead>
    <tr><th>解決経路</th><th>件数</th><th>モデルへの再問い合わせ</th></tr>
  </thead>
  <tbody>
    <tr><td>別名表で確定</td><td>231件</td><td>不要</td></tr>
    <tr><td>埋め込み最近傍で確定</td><td>41件</td><td>不要（埋め込み1回のみ）</td></tr>

  </tbody>
</table>

素直に「バリデーションして1回リトライ」を回していたときは、312件すべてを投げ直していました。正規化層を入れた後にモデルへ再度投げたのは8件だけです。バッチ全体で見ると、再分類のための追加呼び出しは312回から実質82回（埋め込み49回＋生成8件＋確認のための少数）へ落ち、夜間バッチの後半で発生していた再試行の渋滞がほぼ消えました。体感で言えば、翌朝ログを見たときに「昨夜も詰まらずに流れた」という静かな安心があります。

埋め込みの往復はモデル生成より桁違いに安く速いので、312件を生成でリトライするのと、49件を埋め込みで寄せて8件だけ生成に回すのとでは、コストも待ち時間も比べるまでもありませんでした。数字そのものは私の語彙とデータに依存しますが、「近ミスは埋め込みで寄せ、生成の再問い合わせは残った少数に限る」という順序は、閉じた語彙の分類なら再現性があると感じています。

## 逸脱ログを、語彙を育てる材料にする

最後に、この層を入れっぱなしにしないための仕組みです。`resolve_label` が返した経路（`alias` / `embedding` / `unresolved`）を、生の返り値と一緒に必ず記録します。このログが、別名表とカテゴリ設計を育てる一次資料になります。

同じ out-of-set の語が繰り返し `embedding` 経由で寄っているなら、それは別名表に昇格させる候補です。逆に `unresolved` が特定の語で増え続けるなら、既存カテゴリでは受け止めきれない新しい塊が育っている合図で、カテゴリ追加を検討する材料になります。正規化層は、外れ値をその場で吸収するだけでなく、語彙のどこが足りないかを教えてくれる観測点にもなります。

```python
# 経路つきで残しておくと、別名表の昇格とカテゴリ追加の両方に使える
def log_resolution(image_id: str, raw: str, resolved, route: str):
    record = {
        "image_id": image_id,
        "raw_label": raw,
        "resolved": resolved,      # None なら保留
        "route": route,            # in_set / alias / embedding:0.87 / unresolved
        "taxonomy_version": "v30",
    }
    # 実運用では台帳（SQLite など）へ追記する
    return record
```

## まとめ

閉じた語彙の分類で enum を外した値が返ってきたら、投げ直す前に一度だけ外れ方の分布を数えてみてください。近ミスがリトライで直らない性質のものなら、別名表と埋め込み最近傍で受け取り側を正規化するほうが、往復も待ち時間もはるかに軽く済みます。私はまず、生成でのリトライに頼る前にこの正規化層を挟むことを推奨します。まず手元のバッチで、外れた値を経路つきでログに残すところから始めると、次の一手が数字で見えてきます。

しきい値の置き方や「寄せない」判断は、私自身もデータを見ながらまだ少しずつ調整している途中です。同じように閉じた語彙で分類を回している方と、うまくいった線引きを持ち寄れたら嬉しく思います。お読みいただきありがとうございました。
