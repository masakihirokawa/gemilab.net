個人でアプリを開発していると、「この設計、本当に大丈夫かな」と思いながらも、シニアエンジニアにレビューを頼める状況にないことがほとんどではないでしょうか。私も長年そんな状況の中でコードを書いてきました。

転機になったのは、Gemini 2.5 Pro の100万トークンコンテキストウィンドウです。試しに個人プロジェクトのソースコードを全部まとめて投入してみたところ、「このモジュールは単一責任の原則を違反しています」「認証ロジックとデータ取得が密結合しており、テストが困難です」という指摘が次々と出てきました。有料のコードレビューサービスと遜色ない品質で、しかも数秒で。

この記事では、その経験をもとに構築した「コードベース全体解析パイプライン」の実装を紹介します。アーキテクチャレビュー・技術的負債スコアリング・リファクタリング提案の3段階を、Pythonスクリプト一本で自動化する方法です。

## コードベース全体解析で何が変わるか

従来のAIコードレビューは、ファイル単位あるいはコード断片単位が主流でした。ChatGPTやClaude に「このファイルをレビューして」と渡す使い方が典型的です。

この方法の限界は、**文脈の断絶**にあります。特定のファイルだけを見せても、「なぜここで this.authService を直接呼んでいるのか」「このデータモデルが3箇所で微妙に違う形で定義されている」といった**プロジェクト横断的な問題**は検出できません。

Gemini 2.5 Pro の1Mトークン（約75万ワード相当）は、中規模のWebアプリケーションであれば**プロジェクト全体のソースコード**を一度に渡せるサイズです。私のプロジェクト（Swift + Node.js バックエンド、約3万行）を計測したところ、おおよそ180,000〜220,000トークン程度に収まりました。

全体を渡すことで可能になるレビューの例：
- 「`UserRepository` と `UserService` の責任範囲が重複しています。具体的には `fetchAndCacheUser()` メソッドが Service 層にあるべきロジックを持っています」
- 「エラーハンドリングのパターンが3種類混在しています（try-catch、Promise.catch、コールバックエラー）。`src/api/` は一貫してPromise.catchを使っているのに、`src/workers/` はtry-catchです」
- 「環境変数の参照箇所が7ファイルに分散しています。`process.env.DATABASE_URL` が `db.ts`、`config.ts`、`migration.ts` で個別に参照されており、型安全性がありません」

これは部分的なレビューでは絶対に出てこない指摘です。

## 環境セットアップとファイル収集スクリプト

まず、必要なライブラリをインストールします。

```bash
pip install google-generativeai tiktoken pathlib
```

次に、コードベースをまとめてテキスト化するスクリプトを作成します。`.gitignore` に記載されたファイルを除外し、バイナリファイルをスキップするロジックを含めています。

```python
# collect_codebase.py
import os
import sys
from pathlib import Path
from typing import Optional
import subprocess

# 除外するディレクトリとファイル拡張子
EXCLUDE_DIRS = {
    '.git', 'node_modules', '.next', 'dist', 'build',
    '__pycache__', '.venv', 'venv', 'coverage', '.nyc_output'
}
EXCLUDE_EXTENSIONS = {
    '.png', '.jpg', '.jpeg', '.gif', '.svg', '.ico',
    '.pdf', '.zip', '.tar', '.gz', '.mp4', '.mp3',
    '.lock', '.map', '.min.js', '.min.css'
}
# 含めるファイル拡張子（明示的に指定する方が安全）
INCLUDE_EXTENSIONS = {
    '.py', '.ts', '.tsx', '.js', '.jsx', '.swift',
    '.kt', '.java', '.go', '.rs', '.cpp', '.c', '.h',
    '.json', '.yaml', '.yml', '.toml', '.env.example',
    '.md', '.sql', '.graphql'
}

def get_gitignore_patterns(root: Path) -> list[str]:
    """リポジトリルートの .gitignore からパターンを読み込む"""
    gitignore = root / '.gitignore'
    if not gitignore.exists():
        return []
    patterns = []
    with open(gitignore, 'r') as f:
        for line in f:
            line = line.strip()
            if line and not line.startswith('#'):
                patterns.append(line)
    return patterns

def collect_codebase(root_dir: str, max_tokens: int = 800_000) -> tuple[str, int]:
    """
    コードベースを収集して1つの文字列に結合する。
    
    Returns:
        (コード全体の文字列, 推定トークン数)
    """
    root = Path(root_dir).resolve()
    collected = []
    total_chars = 0
    skipped_files = []
    
    for file_path in sorted(root.rglob('*')):
        # ディレクトリはスキップ
        if not file_path.is_file():
            continue
        
        # 除外ディレクトリのチェック
        relative = file_path.relative_to(root)
        parts = set(relative.parts[:-1])  # ファイル名を除いたパーツ
        if parts.intersection(EXCLUDE_DIRS):
            continue
        
        # 拡張子チェック
        suffix = file_path.suffix.lower()
        if suffix not in INCLUDE_EXTENSIONS:
            continue
        
        # ファイルサイズチェック（1MB超はスキップ）
        if file_path.stat().st_size > 1_000_000:
            skipped_files.append(str(relative))
            continue
        
        try:
            content = file_path.read_text(encoding='utf-8', errors='ignore')
        except Exception as e:
            skipped_files.append(f"{relative} ({e})")
            continue
        
        # ファイルをヘッダー付きで追加
        file_block = f"\n\n{'='*60}\nFILE: {relative}\n{'='*60}\n{content}"
        total_chars += len(file_block)
        
        # 推定トークン数チェック（4文字≈1トークンの簡易計算）
        estimated_tokens = total_chars // 4
        if estimated_tokens > max_tokens:
            print(f"⚠️ 推定トークン数が {max_tokens:,} を超えたため収集を停止しました")
            print(f"   収集済み: {len(collected)} ファイル")
            break
        
        collected.append(file_block)
    
    if skipped_files:
        print(f"スキップされたファイル: {len(skipped_files)} 件")
    
    full_text = ''.join(collected)
    estimated_tokens = len(full_text) // 4
    return full_text, estimated_tokens

if __name__ == '__main__':
    root = sys.argv[1] if len(sys.argv) > 1 else '.'
    code, tokens = collect_codebase(root)
    print(f"収集完了: 推定 {tokens:,} トークン ({len(code):,} 文字)")
    
    output_path = Path('codebase_collected.txt')
    output_path.write_text(code, encoding='utf-8')
    print(f"保存先: {output_path}")
```

このスクリプトを実行すると、プロジェクト全体が1つのテキストファイルにまとまります。推定トークン数も表示されるので、Gemini に渡す前にコスト感をつかめます。

## アーキテクチャレビューの自動化

コードベースが用意できたら、最初のステップとして**アーキテクチャレビュー**を行います。単純に「レビューしてください」と渡すのではなく、レビューの観点を明確に指定することが重要です。

```python
# architecture_review.py
import google.generativeai as genai
import json
import time
from pathlib import Path

def run_architecture_review(codebase_text: str, project_name: str) -> dict:
    """
    コードベース全体のアーキテクチャレビューを実行する。
    
    Returns:
        レビュー結果の構造化データ
    """
    genai.configure(api_key='YOUR_GEMINI_API_KEY')
    model = genai.GenerativeModel(
        model_name='gemini-2.5-pro',
        generation_config={
            'temperature': 0.2,  # 一貫性を重視するため低めに設定
            'max_output_tokens': 8192,
        }
    )
    
    prompt = f"""
あなたはシニアソフトウェアアーキテクトです。
以下のコードベース全体を解析し、アーキテクチャ上の問題点を報告してください。

プロジェクト名: {project_name}

【解析の観点】
1. レイヤー分離（Presentation / Business Logic / Data Access の分離度）
2. 単一責任の原則（SRP）違反
3. 依存関係の逆転（DIの実装状況）
4. 横断的関心事（認証・ロギング・エラーハンドリング）の一貫性
5. 命名規則の一貫性
6. 循環依存やデッドコードの有無

【出力形式】
以下のJSON形式で出力してください：
{{
  "overall_score": 1-10の整数,
  "summary": "全体評価（200文字以内）",
  "critical_issues": [
    {{
      "title": "問題のタイトル",
      "location": "ファイル名または関数名",
      "description": "問題の詳細説明",
      "severity": "critical|high|medium|low",
      "fix_suggestion": "修正方針"
    }}
  ],
  "positive_patterns": ["良いパターンの列挙"],
  "priority_refactoring": ["優先度順のリファクタリング候補"]
}}

コードベース:
{codebase_text}
"""
    
    print("🔍 アーキテクチャレビューを実行中...")
    start_time = time.time()
    
    try:
        response = model.generate_content(prompt)
        elapsed = time.time() - start_time
        print(f"✅ 完了（{elapsed:.1f}秒）")
        
        # JSONの抽出（コードブロック内に含まれている場合の対処）
        text = response.text
        if '```json' in text:
            text = text.split('```json')[1].split('```')[0].strip()
        elif '```' in text:
            text = text.split('```')[1].split('```')[0].strip()
        
        result = json.loads(text)
        return result
        
    except json.JSONDecodeError as e:
        print(f"⚠️ JSON解析エラー: {e}")
        return {
            "overall_score": 0,
            "summary": "解析に失敗しました",
            "raw_response": response.text,
            "error": str(e)
        }
    except Exception as e:
        print(f"❌ エラー: {e}")
        raise

def format_report(review: dict) -> str:
    """レビュー結果を読みやすいMarkdown形式に変換する"""
    lines = [
        f"# アーキテクチャレビュー結果",
        f"",
        f"**総合スコア**: {review.get('overall_score', 'N/A')}/10",
        f"",
        f"## 全体評価",
        review.get('summary', ''),
        f"",
        f"## 重要な問題点",
    ]
    
    for issue in review.get('critical_issues', []):
        severity_emoji = {'critical': '🔴', 'high': '🟠', 'medium': '🟡', 'low': '🟢'}.get(
            issue.get('severity', 'medium'), '⚪'
        )
        lines.extend([
            f"",
            f"### {severity_emoji} {issue.get('title', '')}",
            f"- **場所**: `{issue.get('location', '')}`",
            f"- **詳細**: {issue.get('description', '')}",
            f"- **修正方針**: {issue.get('fix_suggestion', '')}",
        ])
    
    lines.extend([
        f"",
        f"## 優れているパターン",
    ])
    for p in review.get('positive_patterns', []):
        lines.append(f"- {p}")
    
    lines.extend([
        f"",
        f"## 優先的なリファクタリング候補",
    ])
    for i, item in enumerate(review.get('priority_refactoring', []), 1):
        lines.append(f"{i}. {item}")
    
    return '\n'.join(lines)

if __name__ == '__main__':
    from collect_codebase import collect_codebase
    
    code, tokens = collect_codebase('.')
    print(f"収集完了: 推定 {tokens:,} トークン")
    
    review = run_architecture_review(code, project_name="MyApp")
    report = format_report(review)
    
    Path('architecture_review.md').write_text(report, encoding='utf-8')
    print("レポートを architecture_review.md に保存しました")
```

実際にこのスクリプトを私のプロジェクトに実行したとき、特に刺さった指摘がこれでした。「`APIClient` クラスがネットワーク処理・レスポンス変換・エラーロギングを1クラスに担当しており、単体テストが事実上不可能な設計になっています」。自分では当然と思っていた設計が、外の目から見るとアンチパターンだったことに気づきました。

## 技術的負債スコアリングと優先度付け

アーキテクチャレビューで全体像をつかんだら、次は**技術的負債の定量化**です。感覚的に「このコードは汚い」と思っていた部分を、スコアとして可視化します。

```python
# tech_debt_scorer.py
import google.generativeai as genai
import json
from pathlib import Path
from dataclasses import dataclass
from typing import Optional
import time

@dataclass
class DebtItem:
    file_path: str
    debt_type: str          # "complexity" | "duplication" | "coupling" | "dead_code" | "naming"
    severity: int           # 1-10
    estimated_fix_hours: float
    description: str
    code_snippet: Optional[str] = None

def analyze_tech_debt(codebase_text: str, focus_areas: list[str] = None) -> list[DebtItem]:
    """
    コードベース全体の技術的負債を分析してスコアリングする。
    
    Args:
        codebase_text: コードベース全体のテキスト
        focus_areas: 集中して分析するファイルパスのリスト（Noneの場合は全体）
    
    Returns:
        技術的負債アイテムのリスト（重大度順）
    """
    genai.configure(api_key='YOUR_GEMINI_API_KEY')
    model = genai.GenerativeModel(
        model_name='gemini-2.5-pro',
        generation_config={
            'temperature': 0.1,
            'max_output_tokens': 16384,
        }
    )
    
    focus_hint = ""
    if focus_areas:
        focus_hint = f"\n特に以下のファイルに注目してください:\n" + "\n".join(f"- {p}" for p in focus_areas)
    
    prompt = f"""
以下のコードベースを解析し、技術的負債を特定してスコアリングしてください。{focus_hint}

【技術的負債の種類】
- complexity: 複雑度が高い（認知的複雑度が高い、ネストが深い）
- duplication: コードの重複（DRY原則違反）
- coupling: 不適切な結合（密結合、循環依存）
- dead_code: 使われていないコード（未使用変数・関数・インポート）
- naming: 命名の問題（意図が不明瞭、略語の乱用）

【出力形式】
以下のJSON配列を出力してください。最大20件まで：
[
  {{
    "file_path": "相対パス",
    "debt_type": "complexity|duplication|coupling|dead_code|naming",
    "severity": 1-10,
    "estimated_fix_hours": 修正に要する推定時間（小数可）,
    "description": "問題の具体的な説明（100文字以内）",
    "code_snippet": "問題のあるコードの断片（50文字以内、省略可）"
  }}
]

重大度（severity）基準:
- 9-10: 本番バグのリスクがある、即対応必要
- 7-8: 機能拡張時に大きな障害になる
- 5-6: 可読性・保守性に影響、計画的に対処
- 1-4: あれば直した方がいい程度

コードベース:
{codebase_text}
"""
    
    print("📊 技術的負債分析を実行中...")
    start_time = time.time()
    
    try:
        response = model.generate_content(prompt)
        elapsed = time.time() - start_time
        print(f"✅ 完了（{elapsed:.1f}秒）")
        
        text = response.text
        if '```json' in text:
            text = text.split('```json')[1].split('```')[0].strip()
        elif '```' in text:
            text = text.split('```')[1].split('```')[0].strip()
        
        raw_items = json.loads(text)
        
        # DebtItem に変換
        items = []
        for item in raw_items:
            try:
                items.append(DebtItem(
                    file_path=item['file_path'],
                    debt_type=item['debt_type'],
                    severity=int(item['severity']),
                    estimated_fix_hours=float(item.get('estimated_fix_hours', 1.0)),
                    description=item['description'],
                    code_snippet=item.get('code_snippet'),
                ))
            except (KeyError, ValueError) as e:
                print(f"⚠️ アイテムのパース失敗: {e}, item={item}")
                continue
        
        # 重大度順にソート
        items.sort(key=lambda x: x.severity, reverse=True)
        return items
        
    except json.JSONDecodeError as e:
        print(f"⚠️ JSON解析エラー: {e}")
        print(f"レスポンス: {response.text[:500]}")
        return []
    except Exception as e:
        print(f"❌ エラー: {e}")
        raise

def print_debt_summary(items: list[DebtItem]) -> None:
    """負債サマリーをコンソールに出力する"""
    if not items:
        print("技術的負債は検出されませんでした")
        return
    
    total_hours = sum(i.estimated_fix_hours for i in items)
    critical = [i for i in items if i.severity >= 8]
    
    print(f"\n{'='*60}")
    print(f"技術的負債サマリー")
    print(f"{'='*60}")
    print(f"合計: {len(items)} 件 | 修正推定時間: {total_hours:.1f}h | 重大: {len(critical)} 件")
    print()
    
    # 種類別集計
    from collections import Counter
    type_counts = Counter(i.debt_type for i in items)
    print("種類別:")
    for debt_type, count in type_counts.most_common():
        print(f"  {debt_type:15s}: {count} 件")
    
    print(f"\n--- 重大な問題（severity >= 8）---")
    for item in critical:
        print(f"[{item.severity}/10] {item.file_path}")
        print(f"  {item.description}")
        if item.code_snippet:
            print(f"  > {item.code_snippet}")
        print()
```

このスコアリングで出てきた「修正推定時間の合計」が可視化されると、プロジェクトの健康状態を数字で把握できるようになります。私の場合、最初の実行で「推定修正時間: 47.5時間」と出て、かなり衝撃を受けました。ただ、全部一気に直す必要はありません。次のステップで優先順位を付けます。

## リファクタリング提案の生成と適用

技術的負債リストができたら、最後は**具体的なリファクタリング提案の自動生成**です。ここでは重大度の高い項目から順に、「before/after」形式のコード修正案を生成します。

```python
# refactoring_suggester.py
import google.generativeai as genai
from pathlib import Path
import time
import re

def generate_refactoring_suggestion(
    file_path: str,
    original_code: str,
    debt_description: str,
    context_code: str = ""
) -> dict:
    """
    特定のファイルに対するリファクタリング提案をコード付きで生成する。
    
    Args:
        file_path: 対象ファイルのパス
        original_code: リファクタリング対象のコード
        debt_description: 技術的負債の説明
        context_code: 関連する他ファイルのコード（依存関係の把握用）
    
    Returns:
        {
            "explanation": "修正の理由・方針",
            "refactored_code": "修正後のコード",
            "breaking_changes": ["破壊的変更のリスト"],
            "test_suggestions": ["追加すべきテストのリスト"]
        }
    """
    genai.configure(api_key='YOUR_GEMINI_API_KEY')
    model = genai.GenerativeModel(
        model_name='gemini-2.5-pro',
        generation_config={
            'temperature': 0.3,
            'max_output_tokens': 8192,
        }
    )
    
    context_section = ""
    if context_code:
        context_section = f"\n\n【関連ファイルのコード（依存関係の把握用）】\n{context_code}"
    
    prompt = f"""
以下のコードに対するリファクタリング提案を作成してください。

**対象ファイル**: {file_path}
**問題**: {debt_description}

【対象コード】
```
{original_code}
```
{context_section}

【出力形式】
以下の4点を含む回答をしてください：

1. **修正の説明**（なぜこの修正が必要か、修正によってどう改善するか）

2. **修正後のコード**（コードブロックに包んで提示。コメントで変更箇所を明記）

3. **破壊的変更のリスク**（呼び出し側に影響する変更があれば列挙）

4. **追加すべきテスト**（この修正を安全に行うために書くべきテストケース）

修正は段階的に適用できる形にしてください。一度に全部書き直すのではなく、最初の一歩として最小限の変更で最大の効果が得られるアプローチを優先してください。
"""
    
    print(f"🔧 リファクタリング提案を生成中: {file_path}")
    start_time = time.time()
    
    try:
        response = model.generate_content(prompt)
        elapsed = time.time() - start_time
        print(f"✅ 完了（{elapsed:.1f}秒）")
        
        text = response.text
        
        # コードブロックを抽出
        code_blocks = re.findall(r'```(?:\w+)?\n(.*?)```', text, re.DOTALL)
        refactored_code = code_blocks[0] if code_blocks else ""
        
        # 破壊的変更を抽出（"破壊的変更" 以降のリスト項目）
        breaking_changes = []
        if '破壊的変更' in text:
            section = text.split('破壊的変更')[1].split('\n\n')[0]
            breaking_changes = [
                line.strip().lstrip('- ').lstrip('・')
                for line in section.split('\n')
                if line.strip() and line.strip() not in ('のリスク', ':')
            ][:5]
        
        # テスト提案を抽出
        test_suggestions = []
        if 'テスト' in text:
            for keyword in ['追加すべきテスト', 'テストケース', 'テスト提案']:
                if keyword in text:
                    section = text.split(keyword)[1].split('\n\n')[0]
                    test_suggestions = [
                        line.strip().lstrip('- ').lstrip('・')
                        for line in section.split('\n')
                        if line.strip() and len(line.strip()) > 5
                    ][:5]
                    break
        
        return {
            "explanation": text,
            "refactored_code": refactored_code,
            "breaking_changes": breaking_changes,
            "test_suggestions": test_suggestions,
            "elapsed_seconds": elapsed,
        }
        
    except Exception as e:
        print(f"❌ エラー: {e}")
        return {
            "explanation": f"エラーが発生しました: {e}",
            "refactored_code": "",
            "breaking_changes": [],
            "test_suggestions": [],
        }

def apply_suggestions_to_project(
    debt_items: list,
    codebase_root: str,
    top_n: int = 5
) -> None:
    """
    上位N件の技術的負債に対してリファクタリング提案を生成し、
    提案ファイルとして保存する。
    
    Args:
        debt_items: DebtItem のリスト（重大度順）
        codebase_root: コードベースのルートディレクトリ
        top_n: 処理する件数の上限
    """
    output_dir = Path('refactoring_suggestions')
    output_dir.mkdir(exist_ok=True)
    
    for i, item in enumerate(debt_items[:top_n], 1):
        print(f"\n[{i}/{top_n}] 処理中: {item.file_path}")
        
        file_full_path = Path(codebase_root) / item.file_path
        if not file_full_path.exists():
            print(f"⚠️ ファイルが見つかりません: {file_full_path}")
            continue
        
        original_code = file_full_path.read_text(encoding='utf-8', errors='ignore')
        
        suggestion = generate_refactoring_suggestion(
            file_path=item.file_path,
            original_code=original_code,
            debt_description=item.description,
        )
        
        # 提案をMarkdownファイルとして保存
        safe_name = item.file_path.replace('/', '_').replace('.', '_')
        output_path = output_dir / f"{i:02d}_{safe_name}.md"
        
        content = f"""# リファクタリング提案: {item.file_path}

**重大度**: {item.severity}/10
**種類**: {item.debt_type}
**推定修正時間**: {item.estimated_fix_hours}時間
**問題**: {item.description}

---

{suggestion['explanation']}

## 適用前の注意事項

**破壊的変更リスク:**
{chr(10).join(f'- {c}' for c in suggestion['breaking_changes']) if suggestion['breaking_changes'] else '- 特になし'}

**追加すべきテスト:**
{chr(10).join(f'- {t}' for t in suggestion['test_suggestions']) if suggestion['test_suggestions'] else '- テスト提案なし'}
"""
        output_path.write_text(content, encoding='utf-8')
        print(f"💾 保存: {output_path}")
        
        # APIレート制限への配慮（1分間60リクエスト制限のため）
        if i < top_n:
            time.sleep(10)
    
    print(f"\n✅ 完了。{top_n} 件の提案を {output_dir} に保存しました")
```

重要な設計上の判断として、`time.sleep(10)` を入れています。Gemini API には1分あたりのリクエスト数制限があり、大量のファイルを短時間に処理しようとすると `429 Too Many Requests` エラーになります。[Gemini API のレート制限と対処法](/articles/gemini-api/gemini-api-rate-limiting-quota-management-production-guide)についてはこちらの記事で詳しく解説しています。

## よくある落とし穴と対処法

実際にこのパイプラインを使い始めたとき、私がつまずいたポイントを3つ紹介します。

**落とし穴1: トークン数の過小見積もり**

「推定トークン数 = 文字数 ÷ 4」という簡易計算は日本語コメントが多いコードで大きくずれます。日本語は1文字が2〜3トークンになることがあるため、混在コードベースでは「実際のトークン数 = 推定の1.5〜2倍」と見ておく方が安全です。正確なカウントが必要なときは `tiktoken` ライブラリのCL100K_BASEエンコーダーを使うか、Gemini APIのtoken countingエンドポイントを使ってください。

**落とし穴2: JSONパースエラーが思ったより多い**

Gemini が出力するJSONが完全に正しいフォーマットでないことがあります。特に、説明文の中に「"」や「\n」が含まれるとJSON構造が壊れます。`response.text` をそのまま `json.loads()` に渡すのではなく、コードブロック抽出 → 前後の余計なテキスト除去 → パース、という3段階のパースロジックが必要です。上記コード内にこのロジックを含めています。

**落とし穴3: 毎回フルスキャンはコストが高い**

100万トークン近いコードベースをGeminiに渡すと、1回のAPIコールで$2〜5程度のコストになります。毎回フルスキャンをCIに組み込むのは現実的ではありません。私の推奨は「週次のフルスキャン + プルリクエスト時の差分スキャン」という組み合わせです。差分スキャンには [Gemini API のContext Caching](/articles/gemini-api/context-caching-guide) を活用すると、変更のないファイル部分のコストを大幅に削減できます。

**落とし穴4: 長時間リクエストのタイムアウト**

100万トークン規模のリクエストは応答に30〜60秒かかることがあります。デフォルトのタイムアウト設定（多くのHTTPクライアントで30秒）では途中で切断されます。SDKを使う場合は `request_options` でタイムアウトを明示的に延ばしてください。

```python
# タイムアウトを延長する設定例
model = genai.GenerativeModel('gemini-2.5-pro')
response = model.generate_content(
    prompt,
    request_options={"timeout": 300}  # 5分に延長
)
```

## 継続的なコード品質管理への応用

一度セットアップしたパイプラインは、継続的な品質管理にも応用できます。以下は私が実際に使っている運用パターンです。

**週次レポートの自動生成**: GitHub Actions で毎週日曜の深夜にフルスキャンを実行し、前週比でスコアが悪化した箇所をSlackに通知する仕組みを作っています。「新規コードを書いたら負債スコアが上がった」を早期に検知できます。

**プルリクエスト時のスポットレビュー**: 変更されたファイルに絞ったレビューをCIに組み込んでいます。フルスキャンではなく差分だけを送るため、コストは1回あたり数円〜数十円程度に収まります。

**月次アーキテクチャサマリー**: 毎月のサマリーをMarkdownファイルとしてリポジトリにコミットしています。「このプロジェクトがどう成長してきたか」の設計上の変遷を記録として残せるので、半年後の自分が助かります。

Gemini の [Long Context の効果的な活用パターン](/articles/gemini-advanced/gemini-long-context-practical-patterns)についての記事も参考にしてみてください。大量テキストを扱う際の実践的なノウハウをまとめています。

## コスト試算と費用対効果

Gemini 2.5 Pro のAPIコスト（2026年4月時点）:
- 入力: $1.25 / 1Mトークン（200Kトークン以下）、$2.50 / 1Mトークン（超過分）
- 出力: $10.00 / 1Mトークン

200,000トークンのコードベースをフルスキャンした場合、1回あたりの入力コストは約$0.25（≒37円）、出力が8,192トークンとすると出力コストは約$0.08（≒12円）。合計で1回あたり約50円程度です。

週次で実行すれば月に4回で約200円。シニアエンジニアに1時間のレビューを依頼するコストが数千円〜数万円であることを考えると、コストパフォーマンスは圧倒的です。
