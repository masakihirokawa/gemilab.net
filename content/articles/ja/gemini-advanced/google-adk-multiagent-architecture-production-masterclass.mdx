## はじめに：なぜマルチエージェント設計が2026年の必修スキルなのか

単一のAIエージェントで解決できる問題には限界があります。複雑なビジネスロジック、長大なコンテキスト、並列処理が求められるタスクでは、複数のエージェントが協調して動作するマルチエージェントシステムが不可欠です。

Google Agent Development Kit（ADK）は、Gemini APIを核としたマルチエージェントシステムを本番レベルで構築するためのフレームワークです。2026年に入り、ADKはA2A（Agent-to-Agent）プロトコルの標準化、セッション永続化の改善、Vertex AIとの深い統合など、大きな進化を遂げました。

本記事では、以下の4つの設計パターンと本番運用に必要な全知識を体系的に解説します。

- **オーケストレーター・ワーカーパターン**: 中央制御型の階層構造
- **スペシャリストチームパターン**: 専門特化エージェントの協調
- **パイプラインパターン**: データ変換・加工の連鎖処理
- **リフレクション・クリティックパターン**: 自己改善ループ

この記事を読み終えると、実際のビジネス要件をどのパターンに当てはめるべきか判断でき、安全にスケールする本番システムを設計・実装できるようになります。

## Google ADKの基本構成と2026年の最新機能

### ADKのコアコンセプト

Google ADKは以下の3層で構成されています。

**エージェント層（Agent Layer）**: 個々のAIエージェントを定義する層。各エージェントはGemini APIを通じて推論を行い、ツールを呼び出し、他エージェントと通信します。

**オーケストレーション層（Orchestration Layer）**: エージェント間の通信、タスクの委譲、状態の管理を担当する層。ADKのRunnerとSessionがこの役割を担います。

**永続化層（Persistence Layer）**: セッション状態、会話履歴、エージェントメモリを保存する層。DatabaseSessionServiceやFirestoreSessionServiceが使われます。

### 2026年の主要アップデート

**A2A Protocol v2**: エージェント間通信の標準プロトコルが刷新され、型安全なメッセージパッシングが可能になりました。リモートエージェントとの通信もHTTPS経由でセキュアに行えます。

**Adaptive Thinking統合**: ADKエージェントが内部でGeminiの思考プロセスを動的に調整できるようになりました。複雑なタスクには長い思考時間を、単純なタスクには即答を割り当てます。

**マルチモーダルルーティング**: テキスト・画像・音声・動画を判別し、適切な専門エージェントに自動ルーティングする機能が追加されました。

## 設計パターン1：オーケストレーター・ワーカーパターン

このパターンは、中央の「オーケストレーター」エージェントが全体の計画を立て、複数の「ワーカー」エージェントにサブタスクを委譲する構造です。

### いつ使うか

メインタスクを明確にサブタスクに分解できる場合、各サブタスクが独立して実行できる場合、進捗管理・品質確認が必要な場合に適しています。

### 実装コード

```python
import asyncio
from google.adk.agents import LlmAgent
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types

# ワーカーエージェント：データ収集担当
research_agent = LlmAgent(
    name="research_agent",
    model="gemini-2.5-pro",
    instruction="""あなたはデータ収集の専門家です。
    与えられたトピックについて信頼性の高い情報を収集し、
    構造化されたJSON形式で返してください。
    必ず情報ソースと確信度（0〜1）を含めること。""",
    tools=[google_search_tool, web_fetch_tool],
)

# ワーカーエージェント：分析担当
analysis_agent = LlmAgent(
    name="analysis_agent",
    model="gemini-2.5-pro",
    instruction="""あなたはデータ分析の専門家です。
    収集されたデータを分析し、主要なインサイト、トレンド、
    リスクをまとめてください。数値には必ず単位を付けること。""",
)

# ワーカーエージェント：レポート生成担当（Flashでコスト削減）
report_agent = LlmAgent(
    name="report_agent",
    model="gemini-2.5-flash",
    instruction="""あなたはビジネスレポートの専門家です。
    分析結果を元に、経営層向けの簡潔なサマリーと
    技術チーム向けの詳細レポートを作成してください。""",
)

# オーケストレーターエージェント
orchestrator = LlmAgent(
    name="orchestrator",
    model="gemini-2.5-pro",
    instruction="""あなたはプロジェクトマネージャーです。
    ユーザーのリクエストを分析し、research_agent → analysis_agent → report_agent
    の順にタスクを委譲してください。各ステップの結果を検証し、
    品質が不十分な場合は再実行を指示してください。""",
    sub_agents=[research_agent, analysis_agent, report_agent],
)

async def run_orchestrated_pipeline(query: str) -> str:
    session_service = InMemorySessionService()
    session = await session_service.create_session(
        app_name="orchestrator_demo",
        user_id="user_001",
    )
    runner = Runner(
        agent=orchestrator,
        app_name="orchestrator_demo",
        session_service=session_service,
    )

    result_parts = []
    async for event in runner.run_async(
        user_id="user_001",
        session_id=session.id,
        new_message=types.Content(
            role="user",
            parts=[types.Part(text=query)],
        ),
    ):
        if event.is_final_response() and event.content:
            for part in event.content.parts:
                if part.text:
                    result_parts.append(part.text)

    return "\n".join(result_parts)

# 実行例
if __name__ == "__main__":
    result = asyncio.run(
        run_orchestrated_pipeline(
            "2026年第1四半期のAIエージェント市場動向を分析し、レポートを作成してください"
        )
    )
    print(result)
    # 期待する出力:
    # [サマリー]
    # AIエージェント市場は前年比340%成長... (経営層向けサマリー)
    # [詳細レポート]
    # 1. 市場規模: $12.5B (2026 Q1)... (技術チーム向け詳細)
```

`sub_agents`パラメータにワーカーエージェントを登録することで、オーケストレーターは自動的にそれらをツールとして認識します。Geminiの推論能力を使って、どのエージェントにいつ委譲するかを判断します。

## 設計パターン2：スペシャリストチームパターン

このパターンでは、各ドメインに特化したエージェントが対等な立場で協調します。人間のチームと同様に、専門家が議論・合意形成を行います。

### いつ使うか

複数の専門領域にまたがる判断が必要な場合（法務・財務・技術の3観点での評価など）に最適です。

### 実装コード

```python

# 法務専門家エージェント
legal_agent = LlmAgent(
    name="legal_specialist",
    model="gemini-2.5-pro",
    instruction="""法務の専門家として、提案内容の法的リスクと
    コンプライアンス要件を評価してください。
    日本の法律・規制に基づいて判断し、リスクレベル（高/中/低）を明示すること。""",
)

# 財務専門家エージェント
financial_agent = LlmAgent(
    name="financial_specialist",
    model="gemini-2.5-pro",
    instruction="""財務の専門家として、提案内容のROI、
    キャッシュフロー影響、財務リスクを評価してください。
    3年間の財務予測を含めること。""",
)

# 技術専門家エージェント
technical_agent = LlmAgent(
    name="technical_specialist",
    model="gemini-2.5-pro",
    instruction="""技術の専門家として、実装可能性、
    技術的リスク、必要なリソースを評価してください。
    スプリント見積もりを含めること。""",
)

# 並列評価 → 統合エージェント
evaluation_pipeline = SequentialAgent(
    name="evaluation_pipeline",
    sub_agents=[
        # 3専門家が並列で評価（約1/3の時間で完了）
        ParallelAgent(
            name="parallel_evaluation",
            sub_agents=[legal_agent, financial_agent, technical_agent],
        ),
        # 全評価を統合して最終判断
        LlmAgent(
            name="decision_maker",
            model="gemini-2.5-pro",
            instruction="""3人の専門家の評価を総合し、
            最終的な推奨（承認/修正/却下）と理由を提示してください。
            各専門家の懸念事項と対応策も含めること。""",
        ),
    ],
)
```

`ParallelAgent`を使うと複数のエージェントが同時実行されるため、処理時間を大幅に短縮できます。3つの専門家評価を逐次実行すると約90秒かかるところを、並列実行では約30秒に短縮できます。

## 設計パターン4：リフレクション・クリティックパターン

エージェントが自身のアウトプットを別のエージェント（クリティック）に批評させ、品質を反復的に向上させるパターンです。高品質な出力が求められる場面で特に有効です。

### 実装コード

```python
import asyncio
import json
import re
from typing import Optional

class ReflectionSystem:
    """生成エージェントとクリティックエージェントの自己改善ループ"""

    def __init__(self, max_iterations: int = 3, quality_threshold: float = 8.5):
        self.max_iterations = max_iterations
        self.quality_threshold = quality_threshold

        self.generator = LlmAgent(
            name="generator",
            model="gemini-2.5-pro",
            instruction="ユーザーの要件を満たす高品質なアウトプットを生成してください。",
        )

        self.critic = LlmAgent(
            name="critic",
            model="gemini-2.5-pro",
            instruction="""提出されたアウトプットを厳格に評価してください。
            評価基準（各10点満点）：
            1. 要件充足度：ユーザーの要件を満たしているか
            2. 品質：内容の正確性と深さ
            3. 明瞭さ：わかりやすさと構成

            JSON形式で返す:
            {
              "scores": {"requirement": 0-10, "quality": 0-10, "clarity": 0-10},
              "average": 0-10,
              "feedback": "改善点の詳細",
              "approved": true/false
            }""",
        )

    async def run(self, task: str) -> dict:
        """改善ループを実行し、品質基準を超えたアウトプットを返す"""
        current_output = ""
        history = []

        for iteration in range(self.max_iterations):
            # 生成フェーズ
            if iteration == 0:
                prompt = task
            else:
                prompt = f"""
                タスク: {task}

                前回のアウトプット:
                {current_output}

                クリティックからのフィードバック:
                {history[-1]['feedback']}

                上記フィードバックを完全に反映した改善版を生成してください。
                """

            current_output = await self._run_agent(self.generator, prompt)

            # 批評フェーズ
            critique_prompt = f"""
            以下のアウトプットを評価してください。

            元のタスク: {task}
            アウトプット: {current_output}
            """
            critique_raw = await self._run_agent(self.critic, critique_prompt)

            json_match = re.search(r'\{.*\}', critique_raw, re.DOTALL)
            critique = json.loads(json_match.group()) if json_match else {}

            history.append({
                "iteration": iteration + 1,
                "output": current_output,
                "feedback": critique.get("feedback", ""),
                "average_score": critique.get("average", 0),
            })

            print(f"Iteration {iteration + 1}: スコア {critique.get('average', 0):.1f}/10")

            if critique.get("approved") or critique.get("average", 0) >= self.quality_threshold:
                print(f"✅ 品質基準達成（{iteration + 1}回目）")
                break

        return {
            "final_output": current_output,
            "iterations": len(history),
            "final_score": history[-1]["average_score"],
            "history": history,
        }

# 使用例
async def main():
    system = ReflectionSystem(max_iterations=3, quality_threshold=8.5)
    result = await system.run(
        "Gemini APIを使った収益化戦略を、具体的な数値根拠と実装ステップを含めて提案してください"
    )
    print(f"\n最終スコア: {result['final_score']:.1f}")
    print(f"反復回数: {result['iterations']}回")
    # 期待する出力:
    # Iteration 1: スコア 7.2/10
    # Iteration 2: スコア 8.8/10
    # ✅ 品質基準達成（2回目）
    # 最終スコア: 8.8
    # 反復回数: 2回
```

## セッション管理と状態永続化

本番環境では、セッション状態をFirestoreに保存することで、サーバー再起動やスケールアウト後も会話を継続できます。

### セッション状態の設計指針

セッション状態に保存すべき情報はユーザーコンテキスト（プラン・言語設定・権限レベル）、タスク状態（現在の進捗・完了したサブタスクの結果）、エラー情報（リトライ回数・最後のエラー内容）、統計情報（使用トークン数・経過時間・コスト）です。

セッション状態が大きくなると読み書きコストが増大するため、1セッションあたり10KB以内を目標に設計してください。

## コスト最適化：本番で60%削減を実現する戦略

マルチエージェントシステムでは、複数のエージェントが並列でAPIを呼び出すためコストが急増しやすいです。以下の戦略を組み合わせることで、品質を維持しながら大幅なコスト削減が可能です。

### 戦略1：モデル階層化（最大40%削減）

```python
class ModelRouter:
    """タスク複雑度に応じてモデルを動的選択"""

    @staticmethod
    def select_model(task_complexity: str, requires_reasoning: bool = False) -> str:
        if requires_reasoning or task_complexity == "high":
            return "gemini-2.5-pro"      # 複雑な推論・長文生成
        elif task_complexity == "medium":
            return "gemini-2.5-flash"    # 一般的な処理
        else:
            return "gemini-2.5-flash-lite"  # 単純な分類・抽出
```

### 戦略2：コンテキストキャッシング（最大75%削減）

システムプロンプトや固定コンテキストが長い場合、Context Cachingを使うと劇的なコスト削減になります。

```python
from google import genai
from google.genai import types

client = genai.Client()

# 長いシステムプロンプトをキャッシュ（最小32,768トークン）
cached_content = client.caches.create(
    model="gemini-2.5-pro",
    config=types.CreateCachedContentConfig(
        system_instruction="""あなたは100ページのビジネス分析フレームワーク資料を
        熟知した上級ビジネスアナリストです。...[長大なコンテキスト]...""",
        ttl="3600s",  # 1時間キャッシュ
    ),
)

print(f"キャッシュ名: {cached_content.name}")
print(f"キャッシュトークン: {cached_content.usage_metadata.total_token_count:,} tokens")
# → キャッシュトークン: 52,430 tokens
# このキャッシュを100回呼び出す場合:
# キャッシュなし: 52,430 × 100 × $3.50/1M = $18.35
# キャッシュあり: 52,430 × 100 × $0.875/1M = $4.59 → 75%削減！

# キャッシュを使ったエージェント実行
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="最新の市場データを分析してください",
    config=types.GenerateContentConfig(
        cached_content=cached_content.name,
    ),
)
```

### 戦略3：セマンティックキャッシング（重複リクエスト対策）

```python
import hashlib
import json
import numpy as np
from redis import asyncio as aioredis

class SemanticCache:
    """意味的に類似したリクエストを検出してキャッシュから返す"""

    def __init__(self, similarity_threshold: float = 0.95):
        self.redis = aioredis.from_url("redis://localhost:6379")
        self.threshold = similarity_threshold

    async def get(self, query: str) -> str | None:
        query_embedding = await self._embed(query)
        cached_keys = await self.redis.keys("cache:embedding:*")
        for key in cached_keys:
            cached_data = json.loads(await self.redis.get(key))
            similarity = np.dot(query_embedding, cached_data["embedding"]) / (
                np.linalg.norm(query_embedding) * np.linalg.norm(cached_data["embedding"])
            )
            if similarity >= self.threshold:
                print(f"キャッシュヒット（類似度: {similarity:.3f}）")
                return cached_data["response"]
        return None

    async def set(self, query: str, response: str, ttl: int = 3600):
        embedding = await self._embed(query)
        key = f"cache:embedding:{hashlib.md5(query.encode()).hexdigest()}"
        await self.redis.setex(
            key, ttl,
            json.dumps({"embedding": embedding.tolist(), "response": response})
        )
```

### コスト削減効果のまとめ

モデル階層化で約35〜40%、コンテキストキャッシングで約50〜75%（長いシステムプロンプトがある場合）、セマンティックキャッシングで約15〜25%の削減が見込めます。組み合わせにより**合計50〜65%のコスト削減**を多くのケースで実現できます。

## 障害設計：サーキットブレーカーパターン

```python
import time
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"      # 正常
    OPEN = "open"          # 遮断中
    HALF_OPEN = "half_open"  # 回復確認中

class CircuitBreaker:
    """エージェントAPIの障害を検出して自動的に保護する"""

    def __init__(
        self,
        failure_threshold: int = 5,
        recovery_timeout: float = 60.0,
        success_threshold: int = 2,
    ):
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.success_threshold = success_threshold
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.success_count = 0
        self.last_failure_time = 0.0

    async def call(self, func, *args, **kwargs):
        if self.state == CircuitState.OPEN:
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = CircuitState.HALF_OPEN
                print("⚡ サーキットブレーカー：回復確認モードへ移行")
            else:
                raise Exception("サーキットブレーカーが開いています。しばらくお待ちください。")

        try:
            result = await func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise e

    def _on_success(self):
        self.failure_count = 0
        if self.state == CircuitState.HALF_OPEN:
            self.success_count += 1
            if self.success_count >= self.success_threshold:
                self.state = CircuitState.CLOSED
                self.success_count = 0
                print("✅ サーキットブレーカー：正常状態に復帰")

    def _on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN
            print(f"🔴 サーキットブレーカー：遮断（{self.failure_count}回連続失敗）")
```

## モニタリングと可観測性

本番運用において、マルチエージェントシステムの挙動を把握するには専用のモニタリングが必要です。

```python
import time
import structlog
from opentelemetry import trace

logger = structlog.get_logger()
tracer = trace.get_tracer(__name__)

class AgentMetrics:
    """エージェント実行メトリクスの収集"""

    def __init__(self, agent_name: str):
        self.agent_name = agent_name
        self.total_calls = 0
        self.total_latency = 0.0
        self.errors = 0

    async def tracked_run(self, runner, user_id: str, session_id: str, message: str):
        with tracer.start_as_current_span(f"agent.{self.agent_name}") as span:
            start = time.time()
            self.total_calls += 1
            try:
                result = await collect_response(runner, user_id, session_id, message)
                latency = time.time() - start
                self.total_latency += latency
                span.set_attribute("agent.name", self.agent_name)
                span.set_attribute("agent.latency_ms", latency * 1000)
                logger.info(
                    "agent_success",
                    agent=self.agent_name,
                    latency_ms=f"{latency*1000:.0f}",
                    total_calls=self.total_calls,
                )
                return result
            except Exception as e:
                self.errors += 1
                span.record_exception(e)
                logger.error("agent_error", agent=self.agent_name, error=str(e))
                raise

    @property
    def avg_latency(self) -> float:
        return self.total_latency / max(self.total_calls, 1)

    @property
    def error_rate(self) -> float:
        return self.errors / max(self.total_calls, 1)
```

## よくある質問（FAQ）

**Q1. オーケストレーターパターンとパイプラインパターンはどう使い分ければよいですか？**

オーケストレーターパターンは「計画と委譲」が必要な場合に適しています。サブタスクの順序が動的に変わる、条件分岐がある、品質チェックが必要な場合はオーケストレーターを選びましょう。一方、パイプラインパターンは処理ステージが固定されており、データが一方向に流れる場合に最適です。コンテンツ生成、ETL処理、書類審査のような定型的な連鎖処理に向いています。

**Q2. マルチエージェントシステムのデバッグが難しいのですが、どうすればよいですか？**

ADKにはAgent Tracing機能があります。`GOOGLE_ADK_TRACING=true`環境変数を設定すると、各エージェントの入出力、ツール呼び出し、思考プロセスが詳細にログ出力されます。また、本記事で紹介したOpenTelemetryによる分散トレーシングと組み合わせることで、どのエージェントがどのタイミングで何を実行したか追跡できます。本番前は必ずローカルで`InMemorySessionService`を使った単体テストを実施してください。

**Q3. Vertex AI上のADKとGemini API直接利用はどちらを選ぶべきですか？**

エンタープライズ用途や厳格なデータ居住地要件がある場合はVertex AI上のADKを推奨します。Vertex AIはVPC Service Controls、カスタムVPC接続、コンプライアンス認証（ISO 27001、SOC 2等）に対応しています。個人開発やスタートアップでは、Gemini API + ADKの組み合わせがコスト効率とシンプルさで優れています。月間API呼び出しが100万回を超えたらVertex AIへの移行を検討しましょう。

## まとめ：マルチエージェント設計の選択指針

本記事で紹介した4つのパターンの選択指針を整理します。

- **オーケストレーター・ワーカー**: 複雑なタスクを複数のサブタスクに分解する必要がある場合
- **スペシャリストチーム**: 複数の専門領域にまたがる評価・判断が必要な場合
- **パイプライン**: データ変換・加工が定型的に連鎖する場合
- **リフレクション・クリティック**: 高品質なアウトプットを反復的に生成する必要がある場合

コスト最適化では、モデル階層化・コンテキストキャッシング・セマンティックキャッシングの組み合わせにより、実際のプロダクションシステムで50〜65%のコスト削減を達成した事例があります。

本番運用において障害設計（サーキットブレーカー）とモニタリング（分散トレーシング）は必須です。これらを最初から組み込んで設計することで、安定したシステムを運用できます。
