Gemini Gems を本格的に業務で使い始めると、「同じ指示を書いているのに、Gem によって回答品質が大きく違う」という現象に出会います。これは Gemini のカスタム指示が、ChatGPT の Custom GPT とは挙動が微妙に異なるためです。

このガイドは、私が個人開発のサポート業務、執筆業務、画像生成プロンプトの整理など、複数の Gem を運用する中で見つけた「効くカスタム指示の書き方」をまとめたものです。テンプレートのコピペで終わらせず、自分の業務に合わせて磨ける形にしています。

## Gem のカスタム指示は「2,000 文字の System Prompt」と考える

まず構造的な理解です。Gemini Gems のカスタム指示は、内部的には毎回の会話に prepend される System Prompt として動作します。実質的な上限は約 8,000 文字ですが、安定して効くのは 2,000 文字前後までです。

これは ChatGPT の Custom GPT（約 8,000 文字）と比べると体感で短く、長文の指示を入れると「指示を覚えていない」ように見える挙動が増えます。Gemini は長い指示の前半・後半を覚えていても、中盤の指示が薄れる傾向があります（"lost in the middle" 問題）。

実用上は次の構造で組むのが安定します。

```
1. 役割定義（200-400文字）
2. 厳守すべき制約（200-400文字）
3. 出力形式の指定（300-500文字）
4. 拒否すべき要求（100-200文字）
5. 例示（500-800文字）
```

合計 1,300〜2,300 文字。これより長くすると、指示の遵守率が下がり始めます。

## 失敗する書き方の典型例

最初に「やってはいけない書き方」を共有します。これは私が最初の Gem を作った時に全部やってしまったものです。

**失敗例 1: ふわっとした人格設定で終わる**

```
あなたは親切で頼りになるアシスタントです。
丁寧で分かりやすい回答を心がけてください。
```

これではほぼ何も指示していないのと同じです。Gemini は元から丁寧に答えます。Gem を作る意味が消えます。

**失敗例 2: 否定語を多用する**

```
コードに余計なコメントを付けないでください。
冗長な説明はしないでください。
不要な前置きを書かないでください。
```

否定形は LLM の指示遵守率を下げます。「〜しないで」を 3 つ並べると、3 つとも守られないことが頻繁に起きます。

**失敗例 3: 長すぎる前提説明**

社内の業務フローを 5,000 文字書き出して「これを踏まえて回答してください」とする Gem を見ますが、これも機能しません。前提情報は別途ナレッジとしてファイルアップロードする方が、検索精度も指示遵守も上がります。

## 効くテンプレートの全体像

私が現在運用している、業務向け Gem の標準テンプレートを共有します。

```markdown
# 役割

あなたは [具体的な職種] です。
[業界・分野] における [年数・経験] レベルの専門知識を持ち、
[対象読者] に対して [価値提供の方向性] で支援します。

# 厳守事項

1. 不確実な情報には必ず「私の理解では」「正確な確認が必要ですが」を付けて回答する
2. 法律・税務・医療に関する判断は「専門家に確認してください」と明示する
3. 数値や日付を回答に含める時は、出典を明示するか「概算」と断る
4. 個人情報・機密情報を含む可能性のある記述は受け取り段階で警告する

# 出力形式

- 結論を最初の 2 文で示す
- 根拠や手順は箇条書きで 3-5 項目に絞る
- コード例がある場合は ```言語名 で始まるコードブロックで囲む
- 最後に「次に試すこと」を 1 項目だけ提案する

# 拒否すべき要求

- 法的助言、医療診断、個別の投資推奨
- 個人を特定する文書の作成
- 既存のコンテンツの全文転載

# 応答例

ユーザー: [想定質問1]
あなた:
[期待する回答スタイルで具体的に書く]
```

このテンプレートのうち、特に重要なのが **「応答例」のセクション** です。Gemini は抽象的な指示よりも、実例から学習する方が遥かに正確に指示を守ります。応答例を 1〜2 個入れるだけで、出力の安定度が一気に上がります。

## Gemini 特有の挙動を踏まえた書き方

### Gemini は「数値の根拠」を要求すると素直に断る

ChatGPT は「2025 年の市場規模は約 X 兆円」のような数値を、根拠が曖昧でも回答する傾向があります。Gemini は同じ質問に「正確な数値は確認できませんが、概算では…」と断りを入れる確率が高いです。

これは Gemini の安全性設計の一部であり、業務 Gem ではむしろ歓迎すべき挙動です。「不確実な数値は明示する」をカスタム指示に入れると、ハルシネーションリスクが大幅に減ります。

### 日本語の敬語レベルを明示すると安定する

「丁寧に答えてください」では足りません。「ですます調を使い、〜である調は使わない。謙譲語は基本使わない（社内向けのため）」のように、具体的に指定すると敬語のブレが減ります。

### Markdown の使用範囲を限定する

放置すると Gemini はあらゆる回答に H1〜H3 を付けたがります。Slack や Notion に貼り付けて使う Gem では、「見出し記号は使わない。箇条書きとコードブロックのみ Markdown を使用」と書いておくと、貼り付け先で崩れません。

## ファイルアップロードとの組み合わせ

Gem は最大 10 ファイルまでナレッジとしてアップロードできます。これは Custom GPT の知識ファイルに相当しますが、Gemini の場合は **「カスタム指示で参照を明示する」** とより安定して使われます。

```markdown
# 知識ベース

このGemには以下のファイルが添付されています:
- 「2025年版_社内コーディング規約.pdf」: コーディング関連の質問はまずこれを参照
- 「サービス仕様書.docx」: 機能に関する質問はこれを根拠にする

回答する前に、必ず該当ファイルを検索してください。
矛盾があれば、添付ファイルを優先してください。
```

これがないと、Gemini は内部知識（学習済みデータ）から答えがちで、せっかく添付したファイルが活用されません。

## 業務での運用フロー

私が業務 Gem を運用する際のフローを共有します。

**1. 月初に Gem の振り返り**

過去 1 ヶ月で「指示通りに動かなかった会話」を 3〜5 件選び、原因を分析します。多くは「カスタム指示に書いていない暗黙の前提」が原因です。これを次月のカスタム指示に追加します。

**2. テストプロンプトのセットを保持する**

Gem を更新する時は、毎回同じ「テストプロンプト 5 個」を流して挙動が変わっていないか確認します。これがないと、改善のつもりがデグレを起こすことがよくあります。

**3. バックアップは Notion か Git に保存**

Gem の編集履歴は Gemini 側に残らないため、過去版を別の場所にバックアップしておきます。私は Notion のページに「Gem 名 / 更新日 / カスタム指示の全文 / 変更理由」を残しています。

## プライバシーと共有の設計

Gem は個人内で使うか、共有するかで設計が変わります。

**個人 Gem**: 業務知識を遠慮なく書ける。ただし退職時にアカウント移行できないので、外部バックアップ必須。

**共有 Gem（組織内）**: チームメンバー全員が見ます。固有名詞や顧客情報は書かない。「具体的なクライアント名はファイルアップロードに退避」が定石。

**社外公開する Gem**: カスタム指示は公開されないが、添付ファイルからの引用が回答に出る可能性がある。NDA に抵触する内容は絶対に添付しない。

## 「動く Gem」と「動かない Gem」の違い

ここまでの内容を実践しても、すべての Gem が成功するわけではありません。私の経験では「動く Gem」と「動かない Gem」の最大の違いは、**役割の解像度** です。

「コーディングを助ける Gem」より「Next.js 16 + TypeScript + Tailwind の小規模アプリで、TypeScript 型エラーの解決を助ける Gem」の方が圧倒的に動きます。守備範囲が狭いほど、カスタム指示の各行が効きます。

最初の Gem を作る時、つい「広く使える Gem」を狙いがちですが、これは罠です。一つの業務、一つの相手、一つの形式に絞った Gem を 5 つ作る方が、生産性は何倍も上がります。

## 次のアクション

このガイドを読んだ後、まず一つだけ Gem を作るなら、**「自分が週に 3 回以上やっている定型業務」を一つ選び、それ専用の Gem を作ってください**。汎用的な Gem は作っても使われません。狭い業務にフィットさせた Gem だけが、本当に開いてくれる Gem になります。

カスタム指示を書く時は、上のテンプレートをコピーして埋めるところから始めてください。最初から完璧を目指さず、1 ヶ月運用して 3 回更新すれば、自分の業務にフィットした「効く Gem」が手元に残ります。
