## アップロード画像を Gemini に「そのまま」渡してはいけない理由

2014年から個人開発でアプリを作り続けていますが、その一本に Gemini のビジョン機能で画像分類を組み込んだとき、最初に肝を冷やしたのは、テストで使ったユーザー提供の写真の EXIF に GPS 座標が残っていたことでした。撮影場所がそのまま緯度経度で埋め込まれている。これを何も考えずにログやプロンプトのコンテキストへ流していたら、利用者の自宅を推定できるデータを自分のサーバーに溜め込んでいたことになります。

マルチモーダル入力の怖さは、テキストと違って「中身が見えにくい」点にあります。拡張子が `.jpg` でも実体は別形式かもしれませんし、見た目はただの写真でもメタデータに個人情報がぶら下がっています。ここでは、ユーザー由来のメディアを Gemini に渡す前段に置くべき検証層を、実際に動く Python コードで一つずつ組み立てます。題材は Gemini API（`google-genai` SDK）単体で、外部の特別なフレームワークは使いません。

## まず押さえる3つのリスク

ユーザー提供メディアを扱うとき、現場で実際にぶつかるのは次の3つです。

1. **拡張子と中身の不一致（MIME 偽装）** — `photo.jpg` が実は HTML や実行ファイル、あるいは Gemini が解釈できない形式。拡張子を信じた時点で検証が破綻します。
2. **メタデータ経由の情報漏洩** — EXIF の GPS・撮影日時・端末名。画像そのものは無害でも、付帯情報が漏洩ベクトルになります。
3. **リソース枯渇** — 高解像度動画をインラインで送ろうとして、リクエストサイズ上限やメモリを超過する。

順に、検証で潰していきます。

## 拡張子ではなく「先頭バイト」で形式を判定する

最も多い間違いが、ファイル名の拡張子で MIME タイプを決めることです。攻撃者にとって拡張子の書き換えはコストゼロなので、必ずファイルの先頭バイト（マジックナンバー）を読んで実体を確認します。

```python
# ファイルの先頭バイトから実際の形式を判定する。
# 拡張子は信用しない。
MAGIC_SIGNATURES = {
    b"\xff\xd8\xff": "image/jpeg",
    b"\x89PNG\r\n\x1a\n": "image/png",
    b"RIFF": "image/webp",          # 8バイト目以降の "WEBP" で最終確認
    b"\x00\x00\x00\x18ftyp": "video/mp4",
    b"\x00\x00\x00\x20ftyp": "video/mp4",
}

ALLOWED = {"image/jpeg", "image/png", "image/webp", "video/mp4"}

def sniff_mime(path: str) -> str | None:
    with open(path, "rb") as f:
        head = f.read(32)
    for sig, mime in MAGIC_SIGNATURES.items():
        if head.startswith(sig):
            # WebP は RIFF コンテナなので追加確認
            if mime == "image/webp" and head[8:12] != b"WEBP":
                continue
            return mime
    return None

def validate_or_reject(path: str) -> str:
    mime = sniff_mime(path)
    if mime is None or mime not in ALLOWED:
        raise ValueError(f"許可されない形式です: {path}")
    return mime
```

ポイントは、判定不能（`None`）も許可外も等しく拒否することです。「分からないものは通さない」を既定にしておくと、未知の形式が紛れ込んでも安全側に倒れます。本番で `python-magic` を使う手もありますが、扱う形式が数種類なら上記のように自前で持つほうが依存も減り、何を許可しているかがコードから一目で分かります。

## EXIF を除去してから渡す

JPEG の EXIF には GPS 座標、撮影日時、端末の機種名まで入り得ます。Gemini に画像内容だけを解釈させたいなら、メタデータは送る前に落とします。Pillow でピクセルデータだけを新しい画像に移し替えるのが確実です。

```python
from PIL import Image

def strip_metadata(src_path: str, dst_path: str) -> None:
    with Image.open(src_path) as img:
        # ピクセルデータのみを新規画像へコピーし、EXIF を含む
        # 付帯情報を一切引き継がない
        clean = Image.new(img.mode, img.size)
        clean.putdata(list(img.getdata()))
        clean.save(dst_path, format="PNG")  # PNG 化で EXIF を確実に排除
```

`img.save(dst, exif=b"")` のように EXIF を空にするやり方もありますが、ICC プロファイルやコメント領域が残ることがあります。新規画像へピクセルだけ移し替える方法なら、付帯情報を構造的に持ち越さないため、漏洩の取りこぼしがありません。除去前に何が入っていたか確認したいときは `img.getexif()` で中身を覗けます。最初に GPS 座標を見つけたのもこれでした。

## 20MB を超える動画は Files API を使う

Gemini のリクエストでは、インライン（`bytes` を直接 contents に入れる方式）に総量の上限があり、目安として 20MB を超えるメディアは Files API でアップロードしてから参照します。動画は一瞬でこの閾値を超えるので、サイズで分岐させます。

```python
import os
from google import genai

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

INLINE_LIMIT = 20 * 1024 * 1024   # 20MB
HARD_LIMIT = 500 * 1024 * 1024    # これ以上は受け付けない

def build_content(path: str, mime: str):
    size = os.path.getsize(path)
    if size > HARD_LIMIT:
        raise ValueError("ファイルが大きすぎます")
    if size <= INLINE_LIMIT and mime.startswith("image/"):
        # 小さい画像はインラインで十分
        with open(path, "rb") as f:
            return genai.types.Part.from_bytes(data=f.read(), mime_type=mime)
    # 大きいメディア・動画は Files API 経由
    uploaded = client.files.upload(file=path)
    return uploaded

def analyze(path: str, prompt: str) -> str:
    mime = validate_or_reject(path)       # 形式チェック
    part = build_content(path, mime)      # サイズで送信方式を分岐
    resp = client.models.generate_content(
        model="gemini-2.5-pro",
        contents=[part, prompt],
        config=genai.types.GenerateContentConfig(
            safety_settings=[
                genai.types.SafetySetting(
                    category="HARM_CATEGORY_DANGEROUS_CONTENT",
                    threshold="BLOCK_MEDIUM_AND_ABOVE",
                ),
            ],
            max_output_tokens=1024,
        ),
    )
    return resp.text
```

検証（`validate_or_reject`）・送信方式の分岐（`build_content`）・安全設定（`safety_settings`）を一つの呼び出し経路にまとめておくと、新しい入力形式を足すときも一箇所を直すだけで済みます。`HARM_CATEGORY_DANGEROUS_CONTENT` 以外にもハラスメントや性的表現のカテゴリがあり、サービスの性質に応じて閾値を調整します。

## つまずきやすい点：Files API のファイルは消える

Files API でアップロードしたファイルには保持期限（おおむね 48 時間）があり、期限切れのファイル名を参照すると `403` や `not found` になります。バッチ処理で前日のアップロードを使い回そうとして失敗したことがありました。長期に同じメディアを参照したいなら、アップロード時刻を自分で記録し、期限が近ければ再アップロードする仕組みを噛ませます。

```python
import time

def get_or_reupload(path: str, cache: dict):
    rec = cache.get(path)
    # 40時間を超えていたら作り直す（48時間の手前で安全に）
    if rec and (time.time() - rec["uploaded_at"]) < 40 * 3600:
        return rec["file"]
    uploaded = client.files.upload(file=path)
    cache[path] = {"file": uploaded, "uploaded_at": time.time()}
    return uploaded
```

## 出力側も素通しにしない

入力を固めても、生成結果にユーザーが送った機密が引き写されて戻ってくることがあります。とくに OCR 的な使い方では、画像内の電話番号やメールアドレスがそのままテキスト化されます。用途に応じて、戻り値を保存・表示する前に簡単なマスキングを一段かけておくと安心です。

```python
import re

def mask_pii(text: str) -> str:
    text = re.sub(r"[\w.+-]+@[\w-]+\.[\w.-]+", "[email]", text)
    text = re.sub(r"\d{2,4}-\d{2,4}-\d{4}", "[phone]", text)
    return text
```

完璧な PII 検出は別の難題ですが、ログに平文で残さないという一線を引くだけでも事故の芽はだいぶ減ります。

## 次の一手

まずは手元の検証関数を `sniff_mime → strip_metadata → build_content` の順で一本のパイプラインにまとめ、テスト用に EXIF 付きの写真を1枚通して、座標が消えていることを `getexif()` で確かめてみてください。この「渡す前に一度立ち止まる層」があるかないかで、マルチモーダル機能を安心して本番に出せるかが変わってきます。実装の参考になれば幸いです。
