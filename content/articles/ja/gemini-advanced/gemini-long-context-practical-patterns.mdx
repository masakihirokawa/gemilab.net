「100万トークンのコンテキストウィンドウ」という数字は、それだけで魅力的です。コードベース全体を投げ込める、長大なPDFを丸ごと処理できる、複数の文書を横断した分析ができる——そういった期待を持つのは自然なことだと思います。

ただ、実際に大量のテキストを入力して作業していると、「全部渡したのになぜか重要な部分を見落とした回答が返ってくる」という経験に少なからず出会います。これは Gemini の欠陥ではなく、長文コンテキストに共通する構造的な問題です。今回は、その問題のメカニズムと、実務で私が使っている対処パターンをお伝えします。

## 「ロスト・イン・ザ・ミドル」問題とは

大量のテキストを入力したとき、LLMが文書の先頭と末尾に比べ、**中間部分の情報を参照しにくくなる現象**を「ロスト・イン・ザ・ミドル」と呼びます。これは複数の研究で確認されており、Gemini も例外ではありません。

直感的に言うと、コンテキストが長くなるほど「全ての情報に均等に注意を払う」ことが難しくなり、注意が先頭・末尾に集中しやすくなります。コードベース全体（50万トークン）の中央付近にあるバグの原因ロジックを、末尾に書いた「このバグを修正してください」という質問と結びつけるのは、LLMにとって難しい処理です。

## パターン1: 質問を文書の近くに配置する

最もシンプルで効果的な対処法の一つです。「文書→質問」という順序ではなく、「質問→文書」または「文書→（質問の繰り返し）」という構造にします。

```python
# Before（質問が最後）
prompt = f"""
{large_document}

上記の文書から、第3章で述べられているリスク要因を全て列挙してください。
"""

# After（質問を先頭にも置く）
prompt = f"""
以下の文書を読んで、第3章で述べられているリスク要因を全て列挙してください。

{large_document}

再確認：第3章で述べられているリスク要因を全て列挙してください。
"""
```

質問を先頭に置くことで、モデルが文書を読む際に「何を探すか」を意識した状態で処理できます。末尾での繰り返しは、長文処理後に注意が分散してしまった場合のリカバリとして機能します。

実際にこの方法を試してみると、特に「文書の中盤にある情報を正確に抽出してほしい」ときに精度の差が出やすいです。

## パターン2: チャンク分割 + 統合の2段階処理

文書全体を一度に処理するのではなく、チャンクに分割して各チャンクから情報を抽出し、最後に統合するパターンです。

```python
import google.generativeai as genai

def extract_from_chunks(document: str, question: str, chunk_size: int = 50000) -> str:
    # テキストをチャンクに分割
    chunks = [document[i:i+chunk_size] for i in range(0, len(document), chunk_size)]
    
    model = genai.GenerativeModel("gemini-2.5-pro")
    chunk_results = []
    
    for i, chunk in enumerate(chunks):
        prompt = f"""
以下のテキスト（全体の一部）から、次の質問に関連する情報を全て抽出してください。
情報がない場合は「該当なし」と返してください。

質問：{question}

テキスト（{i+1}/{len(chunks)}部分）：
{chunk}
"""
        response = model.generate_content(prompt)
        chunk_results.append(response.text)
    
    # 各チャンクの結果を統合
    merge_prompt = f"""
以下は大きな文書を分割して処理した結果です。
これらを統合して、元の質問に対する完全な回答を作成してください。
重複は除去し、矛盾する情報があれば両方を記載してください。

元の質問：{question}

各部分の抽出結果：
{chr(10).join([f'【部分{i+1}】{r}' for i, r in enumerate(chunk_results)])}
"""
    
    final_response = model.generate_content(merge_prompt)
    return final_response.text
```

このパターンのデメリットはAPIコール数が増えること（チャンク数＋1回）です。ただし、「文書全体を俯瞰した分析」よりも「文書から特定の情報を漏れなく抽出する」ユースケースでは、この方法のほうが精度が安定しています。

## パターン3: 構造化された抽出プロンプト

文書から複数の情報を同時に抽出する場合、自由記述形式で求めるより、JSON形式などの構造化された出力を求めることで精度と一貫性が上がります。

```python
extraction_prompt = f"""
以下の契約書を分析し、下記の形式で情報を抽出してください。
情報が見つからない場合は null を設定してください。

{{
  "contract_parties": {{
    "party_a": "甲の名称",
    "party_b": "乙の名称"
  }},
  "effective_date": "YYYY-MM-DD形式",
  "termination_date": "YYYY-MM-DD形式 または null",
  "payment_terms": {{
    "amount": "金額（数値のみ）",
    "currency": "通貨コード",
    "schedule": "支払いスケジュールの説明"
  }},
  "key_obligations": [
    "甲の主要な義務（箇条書き）"
  ],
  "termination_conditions": [
    "解約条件（箇条書き）"
  ]
}}

契約書：
{contract_text}
"""
```

自由記述で「契約の内容をまとめてください」と聞くと、何を重点的にまとめるかはモデルの判断に委ねられます。構造化された出力形式を指定することで、「何を探すか」が明確になり、長い文書の中から必要な情報を見落としにくくなります。

## パターン4: 文書階層のマップを先に作る

特に長い技術文書やコードベースを扱う場合、最初に文書の構造（見出し一覧、章の概要）だけを処理させ、そのマップを使って後続の質問を絞り込む方法が有効です。

```python
def create_document_map(document: str) -> str:
    """文書の構造マップを生成"""
    map_prompt = f"""
以下の文書の構造を把握するために、各セクションのタイトルと
1〜2文の概要を箇条書きで出力してください。
文書の内容の詳細は含めず、構造と各セクションが何について書かれているかのみ記載してください。

文書：
{document[:200000]}  # 最初の20万文字で構造を把握
"""
    model = genai.GenerativeModel("gemini-2.5-pro")
    return model.generate_content(map_prompt).text

def answer_with_context(document: str, question: str, doc_map: str) -> str:
    """文書マップを活用して関連セクションを特定してから回答"""
    section_prompt = f"""
以下の質問に答えるために、この文書のどのセクションを参照すべきかを特定してください。
セクション番号または見出しで答えてください。

質問：{question}

文書の構造：
{doc_map}
"""
    model = genai.GenerativeModel("gemini-2.5-pro")
    relevant_sections = model.generate_content(section_prompt).text
    
    # 関連セクションを特定した上で回答を求める
    answer_prompt = f"""
{question}

参考：この質問に関連するセクションは「{relevant_sections}」です。
文書の該当部分を特に注意して参照し、回答してください。

文書全体：
{document}
"""
    return model.generate_content(answer_prompt).text
```

この方法は、まず「地図を作る」という処理コストがかかりますが、その後の質問応答精度が安定します。定期的に同じ文書に対して様々な質問をするユースケース（大量の社内文書を参照しながら質問に答えるシステム等）では、コスト対効果が高いパターンです。

## 長文コンテキストが本当に輝く場面

誤解を避けるために補足しておくと、Geminiの長文コンテキストが単純に「大量投入して大量に得る」使い方で力を発揮する場面もあります。

**コードレビューでの全体把握**: コードベース全体を一度に投入して「このコードのアーキテクチャの問題点は何か」「セキュリティ上の懸念はあるか」を問うとき。特定の箇所の抽出ではなく、全体を俯瞰した評価を求める場合は、分割処理より全体投入のほうが文脈理解が深くなります。

**複数文書の比較分析**: 「この3つの契約書の条件の差異は何か」のように、複数の文書を一度に渡して横断的な比較をさせるとき。文書間の関係を正確に把握するには、分割せずに全部渡すほうが効果的です。

**長編コンテンツの一貫性確認**: 小説や技術書の原稿全体を投入して「登場人物の言動に矛盾はないか」「各章の説明が食い違っている箇所はあるか」を確認するとき。

これらのユースケースでは「ロスト・イン・ザ・ミドル」が起きにくい問いかけ方（全体評価・比較・一貫性チェック）をしているため、大量投入の恩恵が素直に出ます。

## 使い分けの判断軸

長文コンテキストの活用で迷ったときは、「これは文書全体を見渡す必要があるか、特定の情報を抽出するのか」を最初に考えてみてください。

全体を俯瞰するタスクは一括投入が有効で、特定情報の抽出・照合はチャンク分割か構造化プロンプトが安定します。どちらか判断しにくい場合は、まず質問を先頭に配置する（パターン1）だけで試してみるのが、コストをかけずに改善できる最初の一手です。

## まず、本当に動いたこと

期待が大きすぎると落とし穴に見えてしまいますが、長大コンテキストが実際に価値を発揮する場面はあります。私が効果を実感したのは以下の場面でした。

**大きなドキュメントの横断的な質問**

仕様書・設計書・会議議事録を合計で数万トークン投入し、「この機能はどこで定義されているか」「この決定の経緯は何か」という質問をする用途では、ほぼ期待通りに動きました。検索インデックスを作らなくても、全部を投入して質問できる——これは実際に時間を節約してくれました。

**コードの通読とリファクタリング提案**

単一のリポジトリで、全体のアーキテクチャを踏まえたリファクタリング提案を求めるケースでも有効でした。部分的にコードを見せるより、関連ファイルをまとめて投入した方が、一貫性のある提案が返ってきます。

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_API_KEY")
model = genai.GenerativeModel("gemini-1.5-pro")

# 複数ファイルを連結して投入する例
def load_repository_context(file_paths: list[str]) -> str:
    parts = []
    for path in file_paths:
        with open(path) as f:
            parts.append(f"# File: {path}\n{f.read()}")
    return "\n\n".join(parts)

context = load_repository_context([
    "src/main.py",
    "src/models.py",
    "src/api/routes.py",
    "src/utils/helpers.py",
])

response = model.generate_content(
    f"{context}\n\n"
    "このコードベース全体を見て、依存関係の問題や"
    "リファクタリングすべき箇所を指摘してください。"
)
print(response.text)
```

## 期待と違った半分

ここからが本題です。「100万トークン使えるなら何でも入れれば解決する」という発想は、実際にはいくつかの壁にぶつかります。

### 問題1: コンテキストが長くなるほど「忘れる」ことがある

長大なコンテキストに入れた情報が、後の回答に反映されないことがあります。特に「コンテキストの中央部分」の情報が抜け落ちやすいことは、研究でも示されています（Lost in the Middle 問題）。

実際に経験したのは、100ページ分のドキュメントを投入して「第50ページの○○について」と聞いたとき、答えが不正確だったケースです。先頭と末尾の情報は比較的正確に参照されましたが、中間の情報は不安定でした。

```python
# 重要な情報を先頭か末尾に配置する工夫
def build_prompt_with_priority(
    context_docs: list[str],
    priority_doc: str,
    question: str
) -> str:
    """
    重要なドキュメントを先頭に配置し、
    残りのコンテキストをその後に並べる
    """
    return (
        f"# 重要ドキュメント（必ず参照すること）\n{priority_doc}\n\n"
        f"# 参考コンテキスト\n" +
        "\n\n".join(context_docs) +
        f"\n\n# 質問\n{question}"
    )
```

### 問題2: トークン数に応じてレイテンシが顕著に増加する

50万トークンを投入すると、最初のトークンが返ってくるまでに20〜40秒かかることがあります。ユーザーが待つインタラクティブなアプリケーションには向きません。

```python
import time

def measure_latency(prompt: str, model_name: str = "gemini-1.5-pro") -> dict:
    model = genai.GenerativeModel(model_name)
    
    start = time.time()
    response = model.generate_content(
        prompt,
        generation_config=genai.GenerationConfig(max_output_tokens=100)
    )
    ttfb = time.time() - start  # Time to First Byte的な概念
    
    return {
        "latency_seconds": round(ttfb, 2),
        "input_token_estimate": len(prompt) // 4,  # 大まかな概算
    }

# 長大コンテキストは非同期バッチ処理に向いている
# ユーザーがリアルタイムで待つ用途には不向き
```

私の経験では、長大コンテキストは「バックグラウンドで処理して結果を返す」用途に向いていて、「チャットのようにすぐ返事が返ってくる」用途には向いていません。

### 問題3: コストが想定より高い

100万トークンというキャパシティは魅力的ですが、実際に50万トークンのコンテキストを頻繁に使うと、APIコストが急速に積み上がります。

```python
# Gemini 1.5 Pro の概算コスト（2024年時点、変動あり）
# 入力: $3.50 / 1M tokens（128K以下）
# 入力: $7.00 / 1M tokens（128K超）

def estimate_cost_usd(input_tokens: int, output_tokens: int) -> float:
    if input_tokens <= 128_000:
        input_cost = (input_tokens / 1_000_000) * 3.50
    else:
        # 128K超は単価が倍になる
        base_cost = (128_000 / 1_000_000) * 3.50
        extra_cost = ((input_tokens - 128_000) / 1_000_000) * 7.00
        input_cost = base_cost + extra_cost

    output_cost = (output_tokens / 1_000_000) * 10.50
    return round(input_cost + output_cost, 4)

# 50万トークン投入した場合の入力コストだけで
print(f"500K tokens: ${estimate_cost_usd(500_000, 0):.2f}")  # ~$2.71
# これを1日100回実行すると...
print(f"100回/日: ${estimate_cost_usd(500_000, 0) * 100:.2f}/日")  # ~$271/日
```

大量のドキュメントを毎回投入するよりも、重要な部分を抽出してから投入する「RAG（検索拡張生成）」との組み合わせが、コストと精度のバランスが取りやすいです。

## 長大コンテキストをうまく使うための考え方

使い込んだ上での私の結論は、「コンテキストが長いほど良い」ではなく「適切な量のコンテキストを、適切な配置で」ということです。

- **先頭と末尾を活用する**: 重要な情報は先頭か末尾に置く
- **バッチ処理向きの用途に使う**: リアルタイム応答が必要な用途には向かない
- **コストを見積もってから**: 50万トークン×高頻度は予想外に高くなる
- **RAGと組み合わせる**: 全部入れるより、関連部分を抽出してから投入する

Gemini の長大コンテキストは、今後もっと使いやすくなっていく技術だと思っています。現時点では「すごいけど、万能ではない」——その認識を持った上で使うことが、うまく活かすためのスタート地点だと感じています。
