Google ADK を使ったエージェント開発を始めたとき、最初につまずくのはたいてい「コードは書けたのに、なぜか動かない」という壁です。公式ドキュメントを読んでも解決しない、Stack Overflow でも情報が少ない — そんな状況で何時間も溶かした経験がある方も多いのではないでしょうか。

この記事では、Google ADK 開発でよく遭遇するエラーを実際のエラーメッセージとともに整理し、原因と対処法を具体的に解説します。

---

## インストール時のエラー

### `pip install google-adk` が失敗する

ADK を初めてインストールするときに遭遇しやすいエラーのひとつが、依存パッケージの競合です。

```
ERROR: Cannot install google-adk because these package versions have conflicting dependencies.
```

**原因**: `google-generativeai` や `google-genai` の古いバージョンが既にインストールされており、ADK が要求するバージョンと競合しています。

**対処法**:

```bash
# 既存のGoogle AI関連パッケージをすべてアンインストール
pip uninstall google-generativeai google-genai google-adk -y

# 仮想環境を新規作成してクリーンな状態でインストール
python -m venv adk-env
source adk-env/bin/activate  # Windows: adk-env\Scripts\activate

pip install google-adk
```

仮想環境を使わずにグローバル環境に ADK をインストールしようとすると、既存プロジェクトの依存関係が壊れることがあります。ADK プロジェクトは専用の仮想環境を用意するのが安全です。

### Python バージョンの問題

```
ERROR: Package 'google-adk' requires a different Python: 3.9.x not in '>=3.10'
```

ADK は Python 3.10 以上が必要です。`python --version` で確認し、古い場合は pyenv や公式インストーラーで更新してください。

```bash
python --version  # 3.10 以上であることを確認
pip install --upgrade pip  # pip も最新化しておく
pip install google-adk
```

## 認証・API キーのエラー

ADK でエージェントを実行しようとすると、認証まわりのエラーが最も頻繁に発生します。

### `DefaultCredentialsError` が出る

```
google.auth.exceptions.DefaultCredentialsError: Could not automatically determine credentials.
```

**原因**: ADK が Google Cloud の認証情報を見つけられていません。環境変数 `GOOGLE_API_KEY` か Application Default Credentials（ADC）のどちらかが必要です。

**対処法（Gemini API キーを使う場合）**:

```python
import os
os.environ["GOOGLE_API_KEY"] = "YOUR_GEMINI_API_KEY"

# または .env ファイルで管理（dotenv 使用）
from dotenv import load_dotenv
load_dotenv()

from google.adk.agents import Agent
```

**対処法（Vertex AI を使う場合）**:

```bash
# Google Cloud CLIで認証
gcloud auth application-default login

# プロジェクトIDも設定
export GOOGLE_CLOUD_PROJECT="your-project-id"
export GOOGLE_CLOUD_LOCATION="us-central1"
```

### モデル名のエラー

```
google.api_core.exceptions.NotFound: 404 models/gemini-pro is not found
```

ADK では `gemini-pro` のような短縮形ではなく、フルモデル名を指定する必要があります。

```python
# ❌ 古い書き方
agent = Agent(model="gemini-pro")

# ✅ 正しい書き方（2026年現在）
agent = Agent(model="gemini-2.5-flash")
# または
agent = Agent(model="gemini-2.5-pro")
```

## ツール定義のエラー

### 型アノテーションがないと引数が渡らない

ADK のツール（Function）は、引数に型アノテーションが必須です。これは最もよくある「動いてるはずなのに出力がおかしい」問題の原因のひとつです。

```python
# ❌ 型アノテーションなし — ADKが引数の型を推論できずエラーか誤動作になる
def search_weather(city):
    return f"{city}の天気を検索中..."

# ✅ 型アノテーションあり — ADKが正しくスキーマを生成できる
def search_weather(city: str) -> str:
    """指定した都市の天気情報を検索する。
    
    Args:
        city: 天気を調べたい都市名（例: 東京、大阪）
    
    Returns:
        天気情報の文字列
    """
    return f"{city}の天気を検索中..."
```

また、docstring の `Args:` セクションも ADK がツールの説明として LLM に渡すため、省略すると Gemini がツールをいつ使うべきか判断できずに無視することがあります。

### 複雑な型が含まれるとエラーになる

```
TypeError: Object of type datetime is not JSON serializable
```

ADK のツール引数は JSON シリアライズ可能な型のみ使えます。`datetime`、`set`、カスタムクラスなどはそのまま使えません。

```python
# ❌ datetimeをそのまま引数にするのは不可
def get_schedule(date: datetime) -> str:
    ...

# ✅ 文字列で受け取り、関数内でパースする
def get_schedule(date_str: str) -> str:
    """スケジュールを取得する。
    
    Args:
        date_str: 日付文字列（例: "2026-04-16"）
    
    Returns:
        スケジュール情報
    """
    from datetime import datetime
    date = datetime.strptime(date_str, "%Y-%m-%d")
    return f"{date.strftime('%Y年%m月%d日')}のスケジュール"
```

## セッション管理のエラー

### `InMemorySessionService` でセッションが引き継がれない

ADK でチャット形式のエージェントを実装するとき、セッションが毎回リセットされてしまう問題が起きることがあります。

```python
from google.adk.sessions import InMemorySessionService

session_service = InMemorySessionService()

# ❌ 毎回新しい session_id を生成してしまっている
import uuid
session_id = str(uuid.uuid4())  # ← これだと毎回別セッションになる

# ✅ ユーザーごとに固定のsession_idを使う
session_id = "user_123_session"  # ユーザーIDやデバイスIDを元に固定する
```

`InMemorySessionService` はプロセスが終了するとデータが消えます。本番環境や開発中に永続化が必要な場合は `VertexAISessionService` か独自のデータベース実装を検討してください。

## マルチエージェントのルーティング問題

複数のサブエージェントを `SequentialAgent` や `ParallelAgent` で組み合わせるとき、意図したエージェントが呼ばれない問題がよく起きます。

### サブエージェントの description が曖昧だとルーティングが失敗する

ADK のオーケストレーターは、サブエージェントの `description` を元にどのエージェントを使うか判断します。説明が曖昧だと、誤ったエージェントが選ばれたり、どのエージェントも選ばれなかったりします。

```python
from google.adk.agents import Agent, SequentialAgent

# ❌ descriptionが曖昧なサブエージェント
search_agent = Agent(
    name="search_agent",
    model="gemini-2.5-flash",
    description="情報を取得するエージェント",  # 何を取得するのか不明
    tools=[search_web]
)

# ✅ 具体的なdescriptionを持つサブエージェント
search_agent = Agent(
    name="search_agent",
    model="gemini-2.5-flash",
    description="ウェブ検索を実行して最新情報を取得するエージェント。ニュース、天気、価格情報など外部情報が必要なタスクに使用する。",
    tools=[search_web]
)
```

`description` は LLM がルーティング判断に使うプロンプトそのものです。「このエージェントは〇〇のタスクを担当する」と明確に書くと、精度が大きく改善します。

### エージェントがループして終了しない

`LlmAgent` がツールを呼び出し続けてループする問題は、適切な終了条件が設定されていないときに起きます。

```python
from google.adk.agents import Agent

agent = Agent(
    name="research_agent",
    model="gemini-2.5-pro",
    instruction="""
    ユーザーの質問に答えてください。
    
    重要: 答えを得られたら、必ず「調査完了: [回答内容]」という形式で最終回答を提供し、
    それ以上ツールを呼び出さないでください。
    """,  # ← 明確な終了指示を instruction に含める
    tools=[search_web, get_weather]
)
```

また、`max_iterations` パラメーターでループ回数の上限を設定しておくと安全です。

## ストリーミング出力の問題

### `runner.run_async` でストリーミングが途切れる

```python
import asyncio
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService

async def run_agent():
    session_service = InMemorySessionService()
    runner = Runner(agent=agent, session_service=session_service)
    
    # ❌ イベントを正しく処理していない
    async for event in runner.run_async(
        user_id="user_1",
        session_id="session_1",
        new_message={"role": "user", "parts": [{"text": "東京の天気は？"}]}
    ):
        print(event)  # ← EventオブジェクトをそのままprintしてもNoneになることがある
    
    # ✅ イベントの種類を確認してから処理する
    async for event in runner.run_async(
        user_id="user_1",
        session_id="session_1",
        new_message={"role": "user", "parts": [{"text": "東京の天気は？"}]}
    ):
        if event.is_final_response():
            print(event.content.parts[0].text)
        elif event.content and event.content.parts:
            # 中間イベント（ツール呼び出し等）の処理
            for part in event.content.parts:
                if hasattr(part, "text") and part.text:
                    print(part.text, end="", flush=True)

asyncio.run(run_agent())
```

## Jupyter Notebook での実行エラー

### `asyncio.run()` が使えない問題

Jupyter Notebook ではすでにイベントループが実行中のため、`asyncio.run()` を呼ぶと以下のエラーが出ます。

```
RuntimeError: This event loop is already running.
```

**対処法**:

```python
# Jupyter Notebook での実行
import nest_asyncio
nest_asyncio.apply()  # イベントループのネストを許可

import asyncio

async def run_agent():
    # ... エージェントの実行コード

# Jupyter では await を直接使えるセルで実行
await run_agent()
```

`nest_asyncio` は `pip install nest_asyncio` でインストールできます。

## デバッグのコツ

ADK のデバッグで役立つのは、ログレベルを上げてエージェントの内部動作を可視化することです。

```python
import logging

# ADKの詳細ログを有効化
logging.basicConfig(level=logging.DEBUG)
logging.getLogger("google.adk").setLevel(logging.DEBUG)
```

これでツール呼び出しの詳細、モデルへのプロンプト送信内容、イベントの流れを確認できます。「なぜこのツールが呼ばれたのか」「なぜ終了条件が満たされないのか」を追跡するときに便利です。

また、公式の ADK Web UI（`adk web`コマンド）はローカルでエージェントの動作を視覚的に確認できる優れたデバッグツールです。エラー再現時は CLI 実行より Web UI の方が状態把握がしやすい場合があります。

## まとめにかえて

ADK のエラーは、大きく「環境・認証」「ツール定義」「セッション管理」「マルチエージェント設計」の4カテゴリに集約されます。エラーメッセージが出たときはまずこの4カテゴリのどれに属するかを確認するだけで、解決の手がかりが見えてきます。

まず試してほしいのは、ログレベルを `DEBUG` にして実際にどんなプロンプトがモデルに送られているかを確認することです。ADK の多くの「謎の動作」は、この一手でほぼ解決できます。

ADK の基本的な使い方については [Google ADK Python マルチエージェント開発ガイド](/articles/gemini-dev/google-adk-python-multi-agent-development-guide) も参考にしてみてください。Function Calling まわりのより詳しいトラブルシューティングは [Gemini Function Calling が動かないときの対処法](/articles/gemini-api/gemini-function-calling-not-working-troubleshooting) にまとめています。
