壁紙アプリのレビュー返信を下書きさせる処理に、思考モードを全部載せにした翌月のことです。請求画面を開いて、API コストが前月の 3 倍になっているのを見て、しばらく手が止まりました。「これで全部うまくいく」と思い込んで、すべてのリクエストに同じ設定を入れていたのは、私の側の落ち度でした。

その後、タスクごとに計測し直して、思考モードが効く場面と効かない場面の線引きが見えてきました。**思考は、答えが分かれるところにだけ買います。** いまはこの一文を設定の基準にしており、気づいたのは請求書を見たあとでした。

## 思考モードの仕組みと料金

Gemini 2.5 Flash の思考モードは、応答を返す前に内部で推論ステップを踏む機能です。通常モードより精度は上がりますが、そのぶん思考トークンが課金され、レイテンシも伸びます。

API では `thinking_config` の `thinking_budget` で制御します。以下は現行の `google-genai` SDK での書き方です。

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="与えられたコードのバグを特定して修正してください。\n\n" + code_content,
    config=types.GenerateContentConfig(
        thinking_config=types.ThinkingConfig(
            thinking_budget=8192,  # 思考に使う最大トークン数
        )
    ),
)

print(response.text)
```

`thinking_budget` は 0（思考なし）から 24576 まで設定できます。0 にすると思考を無効化でき、事実上の通常モードになります。上限や既定値はモデルの更新で変わることがあるため、採用前に公式ドキュメントで現在の値をご確認いただければ幸いです。

## どのタスクで思考モードが効くか

3 か月ほど試行錯誤して、効果が出るタスクには共通の型があると気づきました。

**効果が大きいタスク**

- 複数の実行パスを追うコードレビュー（特定の条件でだけ起きるメモリリークなど）
- 要件が曖昧な仕様書から、矛盾や抜け漏れを拾いつつ実装方針を作る作業
- 実行計画を追いながら改善案を出す SQL の最適化
- ステップを積み重ねる数学的・論理的な計算

**効果が薄い、または逆効果になりうるタスク**

- 単純な要約・翻訳。思考フェーズが長くなるだけで、品質の差はほとんど出ませんでした
- JSON への変換や CSV の整形など、定型フォーマットへのデータ変換
- 会話型チャットボットの応答。レイテンシが増えるだけで、精度の伸びは限定的でした
- 画像の説明文の生成。視覚的な理解は、思考フェーズとの相性があまり良くありませんでした

私の場合、最初に思考モードを外したのは、ストアのレビューを多言語に翻訳する処理でした。品質は変わらず、請求だけが軽くなったのです。

## タスクによる切り替えを実装する

実務では、思考のオン／オフ（と予算）を動的に切り替えるラッパーを一枚はさんでおくと、コストを管理しやすくなります。

```python
from enum import Enum
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")


class TaskComplexity(Enum):
    SIMPLE = "simple"      # 翻訳・要約・フォーマット変換
    MODERATE = "moderate"  # コード生成・説明文作成
    COMPLEX = "complex"    # バグ解析・設計レビュー・複雑な推論


THINKING_BUDGET_MAP = {
    TaskComplexity.SIMPLE: 0,       # 思考なし
    TaskComplexity.MODERATE: 2048,  # 軽い思考
    TaskComplexity.COMPLEX: 8192,   # 深い思考
}


def generate_with_complexity(prompt: str, complexity: TaskComplexity) -> str:
    budget = THINKING_BUDGET_MAP[complexity]
    response = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=prompt,
        config=types.GenerateContentConfig(
            thinking_config=types.ThinkingConfig(thinking_budget=budget)
        ),
    )
    return response.text


# 使用例
summary = generate_with_complexity(article_text, TaskComplexity.SIMPLE)
bug_analysis = generate_with_complexity(code_with_bug, TaskComplexity.COMPLEX)
```

単純なタスクでは `thinking_budget=0` がいちばんコストパフォーマンスの高い設定です。

## 思考の中身を確認する

デバッグで役に立つのが、思考の要約（thought summary）を取り出す方法です。モデルが何を考慮して答えに至ったのかが見えるので、プロンプトに足りない情報を探す手がかりになります。

```python
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=complex_prompt,
    config=types.GenerateContentConfig(
        thinking_config=types.ThinkingConfig(
            thinking_budget=8192,
            include_thoughts=True,  # 思考の要約を応答に含める
        )
    ),
)

for part in response.candidates[0].content.parts:
    if not part.text:
        continue
    if part.thought:
        print("[思考の要約]")
        print(part.text[:500])  # 長い場合は先頭だけ表示
    else:
        print("[最終回答]")
        print(part.text)
```

思考が見当違いの方向を向いていたら、プロンプトに前提や制約を足すと直ることが多いです。

## コスト削減の実測値

同じコードレビューのタスクを、設定ごとに 100 件ずつ実行して比べました。

ここでいうバグ検出率は、「モデルが指摘した箇所のうち、実際に修正が必要だったものの割合」です。私の手元の題材では、budget=2048 が費用に対していちばん釣り合っていました。8192 まで上げると精度は伸びますが、トークンと待ち時間の増え方のほうが大きく、レビューを何十件も回す夜には、待ち時間が地味に効いてきます。題材が変われば数字も変わるはずなので、ご自身のコードで一度測っていただくのが確実です。

## thinking_budget の選び方

安定して使えている目安は次のとおりです。

- **budget=0**: 翻訳・要約・データ変換など、正解がほぼ一つに定まるタスク
- **budget=1024〜2048**: コード生成・説明文の作成など、少し考えたほうがよいが深い推論は要らないタスク
- **budget=4096〜8192**: バグ解析・仕様の検討・リファクタリングの判断など、複数の可能性を比べるタスク
- **budget=16384 以上**: 数学的な証明のように、コストより精度が絶対に優先されるタスク（私はほとんど使いません）

一つのアプリの中で全部を同じ設定にせず、タスクの種類で切り替える設計にすると、コストと精度の両方で納得できる結果になりました。

## 思考モードは「コストをかけて精度を買う」機能

整理すると、思考モードは追加のコストで推論の精度を買うオプションです。全部に掛けるものではなく、精度の差が結果を左右する場所にだけ使う——それが、請求書を見て胃が痛くなった私の結論です。

まずは今の API 呼び出しのログを開いて、いちばんトークンを使っているタスクを一つ選んでみてください。そのタスクに深い推論が本当に要るのかを問い直すと、適切な budget が見えてきます。私もそこから始めました。
