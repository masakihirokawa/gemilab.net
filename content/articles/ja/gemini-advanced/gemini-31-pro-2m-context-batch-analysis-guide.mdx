Gemini 3.1 Pro が 2M トークンのコンテキストウィンドウに対応したとき、「これで何ができるか」より先に「どこまで耐えられるか」が気になりました。

1M トークンが来たときも同じことを思いました。理論上は100万トークン入れられる。でも実際に入れて、ちゃんと「見ていた」かは別の話です。今回も同じ疑問を持ちながら、中規模の Next.js プロジェクト（約80ファイル・合計12万トークン相当）を一度に渡してみました。その体験をそのままお伝えします。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

## 2M トークンで何がどれだけ入るか

まず規模感の整理をします。1トークンはざっくり日本語で1〜2文字、英語のコードで4〜5文字に相当します。

2M（200万）トークンという容量は、たとえば以下のようなものが「余裕で」入ります。

- ソースファイル数百本のモノレポ全体
- PDFで500ページ超のドキュメント群
- 1年分のチャットログや会議録
- 前述の Next.js プロジェクト（12万トークン）なら約16個同時に入る計算

前世代の 1M トークンでも十分に大きいですが、2M になったことで「分割して渡す」という工夫が不要になるプロジェクトの規模が一段広がりました。

## 実際に試したこと: プロジェクト全体を一度に渡す

実験したのは Next.js 16（App Router）+ TypeScript のプロジェクト。ファイル構成は以下の通りです。

```
src/
  app/          （30ファイル）
  components/   （25ファイル）
  lib/          （15ファイル）
  types/        （5ファイル）
package.json, tsconfig.json, etc.
```

これを1つのプロンプトにまとめて渡す Python スクリプトを書きました。

```python
import google.generativeai as genai
from pathlib import Path

def load_project_as_context(project_dir: str, include_extensions: list = None) -> str:
    """
    プロジェクトディレクトリを1つのコンテキスト文字列に変換する
    """
    if include_extensions is None:
        include_extensions = [".ts", ".tsx", ".js", ".json", ".md"]
    
    parts = []
    root = Path(project_dir)
    
    # node_modules, .next, .git を除外
    exclude_dirs = {"node_modules", ".next", ".git", "dist", "build"}
    
    for file_path in sorted(root.rglob("*")):
        # 除外ディレクトリをスキップ
        if any(ex in file_path.parts for ex in exclude_dirs):
            continue
        if file_path.suffix not in include_extensions:
            continue
        if not file_path.is_file():
            continue
        
        try:
            content = file_path.read_text(encoding="utf-8")
            relative_path = file_path.relative_to(root)
            parts.append(f"=== {relative_path} ===\n{content}\n")
        except Exception:
            continue
    
    return "\n".join(parts)

def analyze_project(project_dir: str, question: str) -> str:
    """
    プロジェクト全体を渡して質問する
    """
    model = genai.GenerativeModel("gemini-2.0-flash-exp")  # または gemini-3.1-pro
    
    context = load_project_as_context(project_dir)
    token_count = model.count_tokens(context).total_tokens
    print(f"📊 コンテキスト: {token_count:,} トークン")
    
    prompt = f"""以下はプロジェクト全体のソースコードです。

{context}

---

質問: {question}
"""
    
    response = model.generate_content(prompt)
    return response.text

# 使用例
answer = analyze_project(
    project_dir="./my-nextjs-app",
    question="""このコードベース全体を見て、以下の観点で分析してください：
    
1. セキュリティ上の懸念点（特にAPIキーの扱い、入力バリデーション）
2. パフォーマンス改善の余地がある箇所（不要なリレンダリング、N+1クエリ等）
3. 型安全性が甘い箇所（any型の使用、型アサーションの多用）
4. 依存関係の問題（未使用のimport、循環依存の可能性）

各項目について、具体的なファイル名と行番号を示してください。"""
)

print(answer)
```

## 実際に得られた出力の品質

結果として、「プロジェクト全体を把握した上での回答」という感触は確かにありました。

たとえば「セキュリティ懸念」について聞いたとき、`lib/auth.ts` の処理が `app/api/admin/route.ts` でどう使われているかまで追って、「ここでのバリデーションが甘いと、あちらのAPIが通り抜けるリスクがある」という具体的な連鎖を指摘してくれました。

1M トークン時代に分割して渡していたときは、こういった「ファイル間の関係を追った指摘」が得にくかったです。コンテキストが分断されると、Gemini は手元にある範囲でしか考えてくれません。

一方で、正直に書いておきたい限界もあります。

80ファイルを一度に渡した場合、「プロジェクト全体」を網羅的にスキャンしているとは言い切れません。特に問われていない箇所への言及が少なく、「注目されやすい箇所」に引っ張られる傾向があります。重要度の低いユーティリティ関数は見落とされることがありました。

## 有効な使い方と使い方の工夫

2M コンテキストが特に効くと感じた場面は3つです。

**1. アーキテクチャレベルの質問**
「このプロジェクトのデータフローを整理して」「コンポーネント間の依存関係を図示して」など、全体像が必要な質問に対してはかなり的確な回答が返ってきます。

**2. 「なぜこうなっているか」の調査**
「この型エラーが出る原因を、プロジェクト全体から探して」という依頼が得意です。エラーの文字列とソース全体を同時に渡すと、関連する型定義まで追ってくれます。

**3. リファクタリング前の影響調査**
「`UserContext` を廃止して `useAuthStore` に統一したい。影響を受けるファイルを全て列挙して」という使い方で、漏れが少なかったです。

質問の仕方として、「このプロジェクトを全体的に改善してください」という曖昧な依頼より、「この機能に関係するファイルを特定して、この観点で分析してください」という絞り込みの方が、出力の精度が上がります。2M トークンの容量は「何でも入れる」ためではなく「文脈をきちんと持たせる」ために使う、というのが今のところの実感です。

## 1M → 2M で変わったこと

端的に言うと、「分割して渡す」作業がほぼ不要になりました。これは小さいようで大きい変化です。

分割する手間だけでなく、分割によって生まれる「どの部分を一緒に渡すか」という判断コストがなくなります。プロジェクトを丸ごと渡して「全体を見て答えて」と言えるようになったことは、コードレビューや技術調査のワークフローをシンプルにしてくれました。

プロジェクトが大きくなれば 2M トークンでも足りなくなる日が来ますが、個人開発や中規模プロジェクトの範囲であれば、しばらく余裕を持って使えそうです。
