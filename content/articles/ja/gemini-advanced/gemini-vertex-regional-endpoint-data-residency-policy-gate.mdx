「このアプリ、EU の利用者のテキストはどこで処理されているんですか」— 個人開発のアプリについて、そう問い合わせをもらったとき、私は即答できませんでした。コードでは `google-genai` の既定クライアントをそのまま使っていて、リージョンを指定していなかったからです。既定の `global` エンドポイントは、内部でどこにルーティングされても不思議ではありません。速くて楽ですが、「どこで処理したか」を後から一行でも示せない、というのは運用として弱い状態でした。私自身、AdMob 由来の収益で複数の個人開発アプリを回していて、その一部は海外の利用者にも届きます。だからこそ「処理された場所を説明できない」状態は、他人事ではありませんでした。

データレジデンシは、多くの個人開発者にとって「大企業の話」に見えます。けれども、EU の利用者を一人でも抱えた瞬間から、これは自分の問題になります。厄介なのは、事故が起きてから気づく種類の欠落だということです。ふだんは何も問題なく動き、問い合わせや監査の場面で初めて「記録がない」ことが露呈します。ここでは、Gemini を Vertex AI 経由で使う前提で、リージョンを固定し、暗黙のフォールバックを禁じ、呼び出しを後から説明できる形に残す設計を、動くコードとともに共有します。

## なぜ「global 既定」が後から効いてくるのか

`global` エンドポイントは可用性の面で優れています。あるリージョンが混雑していても、空いている場所へ流してくれます。ところがレジデンシの観点では、この「どこへでも流せる」性質がそのまま説明責任の欠落になります。処理された場所が要求のたびに変わりうるのに、それを記録していなければ、後から「EU 内で処理した」とは言えません。

私の環境で `global` のまま数日ログを取ってみたところ、同じ EU 利用者向けの呼び出しでも、ラウンドトリップの分布が二山になっていました。近い場所へ流れた回と、遠い場所へ流れた回が混ざっていたのだと考えられます。つまり `global` は「速い」のではなく「そのときたまたま近ければ速い」だけで、しかもどちらだったかを手元では区別できていませんでした。

まず押さえておきたいのは、レジデンシは「速度の問題」ではなく「証跡の問題」だということです。速さは副次的な話で、本質は "処理された場所を、後から自分の言葉で説明できるか" にあります。

## データ区分を先に決める（すべてを固定しない）

いきなり全リクエストをリージョン固定にすると、モデル可用性やレイテンシの面で不利を被ります。最初にやるべきは、扱うデータを区分に分けることです。私は三つに割り切りました。

<table>
  <thead>
    <tr><th>区分</th><th>例</th><th>処理場所の要件</th></tr>
  </thead>
  <tbody>
    <tr><td><strong>residency</strong></td><td>EU 利用者が入力した本文・レビュー・問い合わせ</td><td>指定リージョン内で処理。global 不可</td></tr>
    <tr><td><strong>regional-pref</strong></td><td>EU 利用者向けだが機微でない要約・分類</td><td>できれば指定リージョン。不可なら許可リージョンへ</td></tr>
    <tr><td><strong>global-ok</strong></td><td>公開情報の整形・自分用の下書き</td><td>どこでもよい（速度優先）</td></tr>
  </tbody>
</table>

この区分を呼び出し側で明示的に渡すのが出発点です。「どのデータか」を人間が毎回考えるのではなく、入口で一度タグ付けし、あとはコードが機械的にリージョンを選ぶ。判断の場所を一箇所に閉じ込めるのが狙いです。

## リージョン固定クライアントを一枚はさむ

まず、素朴に書いてしまいがちな形を見てから、固定版に置き換えます。

```python
# Before: 既定クライアント。どこで処理されるか指定していない
from google import genai

client = genai.Client()  # Developer API 既定 or global 相当

def summarize(text: str) -> str:
    resp = client.models.generate_content(
        model="gemini-flash-latest",
        contents=text,
    )
    return resp.text
```

これは動きますが、リージョンの概念がコードのどこにもありません。Vertex AI 経由に切り替え、`location` を明示したクライアントを、区分ごとに一度だけ作って使い回します。

```python
# After: 区分→リージョンを解決し、location を固定したクライアントを供給する
from google import genai
from functools import lru_cache

PROJECT = "my-gcp-project"

# データ区分ごとの「第一希望リージョン」と「許可リージョン」
REGION_POLICY = {
    "residency":     {"primary": "europe-west4", "allowed": {"europe-west4", "europe-west1"}, "global_ok": False},
    "regional-pref": {"primary": "europe-west4", "allowed": {"europe-west4", "europe-west1"}, "global_ok": False},
    "global-ok":     {"primary": "global",       "allowed": {"global"},                       "global_ok": True},
}

@lru_cache(maxsize=8)
def _client_for(location: str) -> genai.Client:
    # location ごとにクライアントを1つだけ生成しキャッシュする
    return genai.Client(vertexai=True, project=PROJECT, location=location)

def client_for_class(data_class: str, location: str | None = None) -> genai.Client:
    policy = REGION_POLICY[data_class]
    loc = location or policy["primary"]
    if loc not in policy["allowed"]:
        raise ResidencyError(f"{data_class} はリージョン {loc} を許可していません")
    return _client_for(loc)
```

`genai.Client(vertexai=True, project=..., location=...)` の `location` が、実際に叩く地域エンドポイントを決めます。ここを区分ごとに固定することで、「residency のデータは常に `europe-west4` から呼ぶ」という前提が、設定ではなくコードの通り道として保証されます。`lru_cache` を挟んでいるのは、リージョンごとにクライアントを作り直す無駄を避けるためです。

## グローバルへの暗黙フォールバックを禁じるポリシーゲート

レジデンシで最も危ういのは、エラー時の「とりあえず global で再試行」という一行です。可用性のためのフォールバックは善意で入りますが、residency 区分に対してそれをやると、まさに守りたかった性質を自分で破ることになります。ゲートは fail-closed（迷ったら止める）にします。

```python
class ResidencyError(RuntimeError):
    """residency 制約を破りうる呼び出しを止める"""

def generate(data_class: str, *, model: str, contents, location: str | None = None):
    policy = REGION_POLICY[data_class]
    client = client_for_class(data_class, location)
    used_location = location or policy["primary"]
    try:
        resp = client.models.generate_content(model=model, contents=contents)
        _ledger_write(data_class, used_location, model, status="ok")
        return resp
    except Exception as e:
        # ここで global へ逃がさない。許可リージョン内でのみ再試行する
        for alt in policy["allowed"]:
            if alt == used_location:
                continue
            try:
                resp = _client_for(alt).models.generate_content(model=model, contents=contents)
                _ledger_write(data_class, alt, model, status="ok-failover")
                return resp
            except Exception:
                continue
        _ledger_write(data_class, used_location, model, status="failed")
        if not policy["global_ok"]:
            # residency/regional-pref は global に落とさず、失敗として返す
            raise ResidencyError(f"{data_class}: 許可リージョン内で処理できませんでした") from e
        # global-ok のみ、ここで global への最終フォールバックが許される
        resp = _client_for("global").models.generate_content(model=model, contents=contents)
        _ledger_write(data_class, "global", model, status="ok-global-fallback")
        return resp
```

肝は、フォールバックの探索範囲を `policy["allowed"]` に閉じている点です。可用性は「許可リージョンの中で」確保し、それでも駄目なら residency 区分は素直に失敗させます。失敗を握りつぶして global で応答してしまうより、呼び出し元にエラーを返して人間が判断できる状態にするほうが、この文脈では正しい設計です。私は residency 区分では、この fail-closed を既定として推奨します。

## 「どこで処理したか」を後から言えるように台帳化する

コードで固定できても、記録がなければ「EU 内で処理した」と後から示せません。呼び出しごとに、区分・実際に使ったリージョン・モデル・結果を軽い台帳へ書き出します。SQLite で十分です。

```python
import sqlite3, time, uuid
from pathlib import Path

_DB = Path("data/residency_ledger.db")

def _ledger_init():
    con = sqlite3.connect(_DB)
    con.execute("""
      CREATE TABLE IF NOT EXISTS calls(
        id TEXT PRIMARY KEY, ts REAL, data_class TEXT,
        location TEXT, model TEXT, status TEXT
      )""")
    con.commit(); con.close()

def _ledger_write(data_class: str, location: str, model: str, status: str):
    con = sqlite3.connect(_DB)
    con.execute(
        "INSERT INTO calls VALUES(?,?,?,?,?,?)",
        (uuid.uuid4().hex, time.time(), data_class, location, model, status),
    )
    con.commit(); con.close()
```

この台帳があると、「先月の residency 区分の呼び出しは何件で、そのうち `europe-west4` 以外で処理されたものはゼロだったか」を一本のクエリで言えるようになります。

```sql
SELECT location, status, COUNT(*) AS n
FROM calls
WHERE data_class = 'residency'
  AND ts >= strftime('%s', '2026-06-01')
GROUP BY location, status
ORDER BY n DESC;
```

residency 行に `global` や `ok-global-fallback` が一件でも混ざっていれば、それは設計が破れた証拠です。理想は、この区分の結果が許可リージョンだけで埋まっていること。台帳は「守れている」ことの証明であると同時に、「破れた瞬間」を検知するアラート源にもなります。私は日次でこのクエリを回し、residency に許可外リージョンが出たら通知するようにしています。

## リージョン固定のレイテンシ代を測る

固定には代償があります。どれくらいかを、自分の環境で測ってから決めるべきです。私の EU 利用者向け要約タスク（短文・`gemini-flash-latest` 相当）で、`global` と `europe-west4` 固定を各 500 回ずつ流したときの分布はこうでした。

<table>
  <thead>
    <tr><th>構成</th><th>p50</th><th>p95</th><th>失敗/不可</th></tr>
  </thead>
  <tbody>
    <tr><td>global 既定</td><td>540ms</td><td>1,910ms</td><td>0%（ただし処理地不明）</td></tr>
    <tr><td>europe-west4 固定</td><td>470ms</td><td>980ms</td><td>2%（一部プレビュー系が未提供）</td></tr>
  </tbody>
</table>

EU 利用者に対しては、固定したほうが p50 も p95 も改善しました。`global` が遠い場所へ流れる回が混ざっていた分、テールが伸びていたのだと考えています。一方で固定側には「そのリージョンに目的のモデルが無い」という別種の失敗が現れました。最新のプレビュー系モデルは、リージョンによって提供が遅れることがあります。ここが次の論点です。

## モデルがそのリージョンに無いときの振る舞い

「residency は守りたいが、使いたい最新モデルが `europe-west4` にまだ無い」という衝突は現実に起きます。ここで安易に global へ逃がすのは、可用性を口実に制約そのものを捨ててしまう典型的な落とし穴で、最初のポリシーが無意味になります。私が採っている順序はこうです。

第一に、residency 区分では「許可リージョンで動く一段前の安定モデル」を明示的に第二候補として持ちます。最新を追うより、区分の制約を守るほうを優先するという判断です。第二に、それでも許可リージョンに何も無ければ、その機能は residency 利用者に対して一時的に提供しない（fail-closed）。第三に、この「提供できなかった」件数を台帳に残し、リージョン提供が追いついた時点で戻す。

```python
RESIDENCY_MODEL_FALLBACK = {
    # 第一希望が許可リージョンに無い場合の、安定モデルへの縮退先
    "gemini-flash-latest": "gemini-2.5-flash",
}

def pick_model(data_class: str, wanted: str, location: str) -> str:
    if data_class == "residency" and not _model_available(wanted, location):
        alt = RESIDENCY_MODEL_FALLBACK.get(wanted)
        if alt and _model_available(alt, location):
            return alt
        raise ResidencyError(f"{wanted} も代替も {location} で利用できません")
    return wanted
```

`_model_available` は、起動時に一度だけ各リージョンの利用可能モデルを引いてキャッシュしておくのが実務的です。毎回問い合わせると、それ自体がレイテンシとコストになります。

## 小さく始めるための導入手順

全体を一度に入れ替える必要はありません。私は次の順で足していきました。

最初に、入口でデータ区分をタグ付けするだけの層を足します。この時点ではまだ全部 `global-ok` 扱いで構いません。挙動は変わらないので、安全に入れられます。次に、台帳の書き出しだけを先に有効化し、「いま何が、どこで処理されているか」を一週間ほど観測します。ここで初めて、自分のアプリの実際のデータフローが見えてきます。そのうえで、明らかに residency にすべき入口を一つだけ `residency` へ上げ、ポリシーゲートを効かせる。うまく回ることを確認してから、範囲を広げていきます。

この順序の良いところは、どの段階でも「観測 → 一箇所だけ厳しくする → 確認」を繰り返せることです。レジデンシのような制約は、一度に完璧を目指すと、可用性の低下やモデル不足でかえって足を止めます。台帳で現実を見ながら、守るべき入口から順に固定していくほうが、結局は速く安定します。

同じように「どこで処理したか」を後から言える状態は、EU 利用者に対してだけでなく、自分がアプリを説明する立場になったときの安心にもつながります。実装の参考になれば幸いです。お読みいただき、ありがとうございました。

## まとめ：次の一手

いま `global` のまま Gemini を呼んでいるなら、コードを大きく変える前に、まず呼び出し台帳だけを一週間回してみてください。自分のアプリの residency に相当する入口がどこで、どのくらいの頻度で叩かれているかが、数字で見えてきます。そのうえで、いちばん機微な入口を一つだけ `europe-west4` などへ固定し、global への暗黙フォールバックを断つ。この二歩を踏むだけで、「どこで処理したか答えられない」状態からは確実に抜け出せます。
