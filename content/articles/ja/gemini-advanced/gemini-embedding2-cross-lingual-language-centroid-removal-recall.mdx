4つのサイトで日本語と英語の記事を必ずペアで公開しています。片方だけ存在すると言語切替で 404 になるため、日英は常に同数です。手元の1サイトでいま JA 725 本・EN 725 本。つまり「意味が同じで言語だけが違う文書」が 725 組、正解つきで揃っている状態です。

この対を使って、公開前の重複検知を作ろうとしました。新しく書いた日本語の下書きを埋め込み、既存記事の中から近いものを引く。日英どちらの既存記事も同じインデックスに入れておけば、言語をまたいだ重複も拾えるはずでした。

引いてみると、上位10件が全部日本語記事でした。私自身、最初はインデックスの作り方を間違えたのだと思いました。しかも、その日本語の下書きには**必ず対応する英語版が存在している**にもかかわらず、その対訳は上位に出てきません。内容が完全に一致する相手が、内容の遠い同言語の記事に負けています。

task_type は揃えていました。正規化もしていました。原因はもっと手前にありました。

## コサイン類似度は「何語で書かれているか」も測っている

埋め込みモデルは、渡した文をベクトルにします。そのベクトルには意味だけが入っていてほしいのですが、実際には書かれた言語という属性も一緒に載ります。

多言語モデルは、確かに言語をまたいで意味を近づけるように学習されています。ただ「まったく同じ向きに揃える」ようには学習されていません。結果として、埋め込み空間の中で日本語の文はゆるやかに一箇所に集まり、英語の文は別の一箇所に集まります。

言語の一致が稼ぐ下駄が、意味の差を埋めてしまう。上位10件が日本語で占められていたのは、モデルが間違えたからではありませんでした。私が「意味だけを測っているつもりで、言語も一緒に測っていた」だけです。

この成分をどう扱うかは用途で変わります。同一言語内の検索しかしないなら、言語成分は全ベクトルに等しく載るので順位に影響しません。困るのは、日本語と英語を同じインデックスに混ぜて引く瞬間だけです。私はそこを踏みました。

## 対訳ペアは、そのまま評価データセットになる

先に測り方を用意します。対訳ペアの良いところは、正解のラベル付けが要らないことです。`gemini-3-multitool-agent-guide.mdx` の日本語版から引いたとき、正解は同じ slug の英語版だと最初から決まっています。

100 組ほどあれば傾向は見えます。次のコードは、日英ペアを埋め込んで JA→EN の再現率と MRR を出す最小の計測台です。

```python
import os, json, math, random
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])
MODEL = "gemini-embedding-2"

def embed(texts, task_type):
    """テキスト群を埋め込む。API 側の上限に合わせて分割する。"""
    out = []
    for i in range(0, len(texts), 32):
        chunk = texts[i:i + 32]
        res = client.models.embed_content(
            model=MODEL,
            contents=chunk,
            config=types.EmbedContentConfig(task_type=task_type),
        )
        out.extend([e.values for e in res.embeddings])
    return out

def l2_normalize(v):
    n = math.sqrt(sum(x * x for x in v))
    return [x / n for x in v] if n else v

def cosine(a, b):
    return sum(x * y for x, y in zip(a, b))

# pairs: [{"slug": "...", "ja": "日本語本文の冒頭2000字", "en": "English body ..."}, ...]
pairs = json.load(open("pairs.json"))
random.seed(42)
pairs = random.sample(pairs, min(100, len(pairs)))

ja_vecs = [l2_normalize(v) for v in embed([p["ja"] for p in pairs], "RETRIEVAL_QUERY")]
en_vecs = [l2_normalize(v) for v in embed([p["en"] for p in pairs], "RETRIEVAL_DOCUMENT")]

def evaluate(queries, docs):
    """queries[i] の正解は docs[i]。順位を集計する。"""
    hits = {1: 0, 5: 0, 10: 0}
    rr_sum = 0.0
    for i, q in enumerate(queries):
        scored = sorted(
            ((cosine(q, d), j) for j, d in enumerate(docs)),
            reverse=True,
        )
        rank = next(r for r, (_, j) in enumerate(scored, start=1) if j == i)
        for k in hits:
            if rank <= k:
                hits[k] += 1
        rr_sum += 1.0 / rank
    n = len(queries)
    return {
        "recall@1": hits[1] / n,
        "recall@5": hits[5] / n,
        "recall@10": hits[10] / n,
        "MRR": rr_sum / n,
    }

print("baseline:", evaluate(ja_vecs, en_vecs))
```

この時点では、母集団に英語文書しか入っていません。言語の下駄は全候補に等しくかかるので、ここでの再現率は素直に出ます。私の手元では recall@1 が 0.9 前後、つまり 90% ほどの下書きで対訳が1位に来ていました。

問題は次です。候補に日本語記事も混ぜます。

```python
# 日本語記事も同じインデックスに入れる（自分自身は候補から除く）
ja_docs = [l2_normalize(v) for v in embed([p["ja"] for p in pairs], "RETRIEVAL_DOCUMENT")]

def evaluate_mixed(queries, en_docs, ja_docs):
    hits = {1: 0, 5: 0, 10: 0}
    for i, q in enumerate(queries):
        cands = [(cosine(q, d), ("en", j)) for j, d in enumerate(en_docs)]
        cands += [(cosine(q, d), ("ja", j)) for j, d in enumerate(ja_docs) if j != i]
        cands.sort(reverse=True)
        rank = next(r for r, (_, key) in enumerate(cands, start=1) if key == ("en", i))
        for k in hits:
            if rank <= k:
                hits[k] += 1
    n = len(queries)
    return {f"recall@{k}": v / n for k, v in hits.items()}

print("mixed:", evaluate_mixed(ja_vecs, en_vecs, ja_docs))
```

日本語候補を混ぜた途端に recall@1 が崩れました。混ぜる前と後の差が、そのまま言語成分の大きさです。単一言語のベンチマークで問題なく見えていたインデックスが、多言語にした瞬間に別物になる。この落差を数字にできたことが、この計測台の一番の収穫でした。

## 効かなかった手を先に置いておきます

思いついた順に試した記録です。うまくいかなかった経路を先に共有したほうが、読む方の時間を節約できると考えています。

**task_type の変更**。`SEMANTIC_SIMILARITY` に揃える、双方を `RETRIEVAL_DOCUMENT` にする、といった組み合わせを一通り試しました。順位は多少動きましたが、日本語候補が上位を占める構図は変わりませんでした。task_type はクエリと文書の非対称性を扱うパラメータであって、言語の偏りを扱うものではありません。この使い分けそのものは大切なので、まだの方は[検索精度が伸びないときに最初に task_type を疑う話](/articles/gemini-api/gemini-embedding-2-task-type-mismatch-retrieval-recall-fix)を先に読んでいただくとよいかもしれません。

**次元数を上げる**。`output_dimensionality` を 768 から 1536、3072 と上げてみました。ほぼ変わりません。言語成分は情報が足りなくて生じているのではなく、空間の構造としてそこにあります。解像度を上げても、構造は同じ形で拡大されるだけでした。次元数はストレージとの兼ね合いで決める話であり、[次元を落として保管量を減らす設計](/articles/gemini-api/gemini-embedding-output-dimensionality-256-storage-reduction)の軸とは別物です。

**前処理での正規化**。全角記号を揃える、見出し記号を落とす、といった掃除は品質の底上げにはなりますが、この問題には無関係でした。言語の違いは表記の揺れではありません。

**類似度のしきい値を下げる**。上位N件で切るのをやめて、しきい値で拾えばよいのではと考えました。逆効果でした。しきい値を下げると、関係のない同言語の記事が大量に入ってきます。順位の問題をしきい値で解こうとしても、順序が変わらない以上は何も改善しません。

## 言語ごとの平均ベクトルを引く

効いたのはこれでした。

考え方は単純です。日本語の埋め込み全体に共通して載っているオフセットが言語成分だとすれば、日本語ベクトルの平均は、その共通成分をよく近似します。各ベクトルから自分の言語の平均を引けば、共通部分が消えて、残るのは「その文が同言語の他の文とどう違うか」だけになります。

```python
def centroid(vecs):
    n = len(vecs)
    dim = len(vecs[0])
    return [sum(v[i] for v in vecs) / n for i in range(dim)]

def remove_centroid(vecs, c):
    """言語重心を引いてから再正規化する。再正規化を忘れるとコサインが歪む。"""
    return [l2_normalize([x - ci for x, ci in zip(v, c)]) for v in vecs]

# 重心は「文書側の集合」から言語ごとに作る
c_ja = centroid(ja_docs)
c_en = centroid(en_vecs)

ja_q2 = remove_centroid(ja_vecs, c_ja)     # クエリは日本語なので日本語重心を引く
ja_d2 = remove_centroid(ja_docs, c_ja)
en_d2 = remove_centroid(en_vecs, c_en)

print("centered:", evaluate_mixed(ja_q2, en_d2, ja_d2))
```

私の記事集合では、混合候補での recall@1 が baseline に近い水準まで戻りました。対訳が上位に返ってこない、という当初の症状は消えています。

理屈を知っていれば数行です。ただ、この処理は Gemini の公式ドキュメントに書かれている手順ではありません。埋め込みを受け取ったあと、自分の母集団の性質に合わせて後処理する領域の話です。

### 運用に入れるときの落とし穴

重心はデータに依存します。採用する場合に厄介なのは、コードではなくこちらのほうでした。

<thead>
<tr><th>落とし穴</th><th>起きること</th><th>対処</th></tr>
</thead>
<tbody>
<tr><td>少数サンプルで重心を作る</td><td>重心がノイズを含み、順位が不安定になる</td><td>言語あたり最低 200 件程度の文書から作る</td></tr>
<tr><td>クエリに文書側の重心を引く</td><td>短文と長文で分布が違い、ずれが残る</td><td>クエリ集合が十分あるなら別に持つ。無ければ文書側で代用し、差を必ず測る</td></tr>
<tr><td>再正規化を忘れる</td><td>ノルムが揃わずコサインが意味を失う</td><td>引いた直後に必ず L2 正規化する</td></tr>
<tr><td>モデルを差し替えたのに重心が古い</td><td>まったく別の空間の重心を引き、静かに劣化する</td><td>重心をモデル名つきで保存し、再インデックス時に必ず作り直す</td></tr>
<tr><td>記事が増えても重心を更新しない</td><td>母集団が移動して少しずつずれる</td><td>再インデックスのタイミングで一緒に更新する</td></tr>
</tbody>
</table>

最後の2つが特に危険でした。重心を引く処理はエラーを出しません。古い重心でも計算は通り、結果も返ります。ただ順位だけが静かに悪くなります。私は重心ファイルに `model` と `built_at` と `n_docs` を必ず書き込み、インデックスのメタ情報と突き合わせるようにしました。モデルの世代交代そのものの段取りは[埋め込みモデルを止めずに載せ替える再インデックス設計](/articles/gemini-advanced/gemini-embedding-model-migration-zero-downtime-reindex)の手順に寄せています。

もうひとつ。重心を引くと、同一言語内だけの検索は微妙に精度が落ちる場合があります。言語成分は同言語内では邪魔をしないので、引くことが純粋な情報損失になり得るためです。言語横断の検索と同言語の検索を両方やるなら、素のベクトルと重心を引いたベクトルの両方を持つ選択肢もあります。ストレージは2倍になりますが、埋め込み API の呼び出しは1回のままです。

## 重心除去・翻訳ブリッジ・言語別インデックス

現実解は3つあります。私は最初、翻訳ブリッジしか思いつきませんでした。

<table>
<thead>
<tr><th>方式</th><th>やること</th><th>追加の呼び出し</th><th>追加の遅延</th><th>強み</th><th>弱み</th></tr>
</thead>
<tbody>
<tr><td>言語重心の除去</td><td>言語ごとの平均を引いて再正規化</td><td><strong>なし</strong></td><td>ほぼゼロ（ベクトル演算のみ）</td><td>実装が小さい・実行時コストがかからない</td><td>母集団の管理が要る・同言語検索が微減</td></tr>
<tr><td>翻訳ブリッジ</td><td>クエリを対象言語へ訳してから埋め込む</td><td>生成1回＋埋め込み1回</td><td>生成のレイテンシがそのまま乗る</td><td>精度が素直・言語が増えても考え方が同じ</td><td>クエリごとに費用と遅延・訳の揺れが順位に響く</td></tr>
<tr><td>言語別インデックス＋RRF</td><td>言語ごとに引いて順位で統合</td><td>検索が言語数ぶん</td><td>並列化すれば小さい</td><td>言語間の比較を避けられる・言語別の調整が効く</td><td>各言語の上位を必ず混ぜるので、本当に無関係な言語の記事も入る</td></tr>
</tbody>
</table>

翻訳ブリッジは精度が読みやすい代わりに、クエリのたびに生成が1回走ります。公開前の重複検知のように1日に数十回しか動かない処理なら、この費用はほぼ無視できます。逆に、記事ページを開くたびに走る関連記事の推薦で使うと、体感の遅延がそのまま増えます。

RRF は言語間のスコアを比較しないので発想としては綺麗ですが、私の用途には合いませんでした。「日本語からも英語からも上位3件ずつ」と決めた瞬間、英語に本当に関連記事が無いときでも英語の記事が3件入ってきます。関連が無いことを表現できません。

## 私が選んだ構成と、その理由

用途を2つに割りました。

**公開前の重複検知**は翻訳ブリッジにしました。1日に数回しか走らず、精度が最優先で、遅延は誰も見ていません。下書きの日本語を英語へ訳してから英語インデックスを引き、日本語は日本語インデックスをそのまま引きます。言語をまたいだ比較を最初から発生させない構成です。この用途の全体像は[記事の共食いを公開前に検知するゲート](/articles/gemini-api/gemini-embedding-article-topic-cannibalization-prepublish-gate)側にまとめています。

**記事ページの関連記事**は重心除去にしました。読者を待たせられない場所で、生成を1回挟む判断はできませんでした。重心を引く処理は行列演算だけで終わり、体感できるほどの時間はかかりません。追加の API 呼び出しがゼロというのは、個人開発で毎月の請求を見ている立場からすると、それだけで十分に大きな理由になります。

言い換えると、遅延の予算がある場所では翻訳ブリッジ、無い場所では重心除去、という分け方です。精度が少し落ちる代わりに実行時コストがゼロになる選択肢を、どこで許容するか。そういう線の引き方をしました。

私はこの手の判断を、最初から一本に決めないほうが良いと考えるようになりました。同じ問題でも、呼ばれる頻度が3桁違えば別の問題になります。

## 導入する順序

自分の環境に入れるとしたら、この順で進めます。

1. **対訳ペアを50〜100組固定する**。ランダムに選んで seed を書き留めておきます。以後この集合は変えません。変えると前回との比較が意味を失います。
2. **単一言語の候補で測る**。ここで再現率が低いなら、言語の話ではありません。task_type やチャンク設計を先に見直します。
3. **他言語の候補を混ぜて測る**。1と3の差が、あなたのデータでの言語成分の大きさです。差が小さいなら、ここで終わってかまいません。
4. **重心を作って測り直す**。言語あたり 200 件以上の文書から作り、再正規化を忘れないようにします。
5. **同言語検索の再現率も測る**。重心除去で下がっていないかを確認します。下がり幅が許容できないなら、両方のベクトルを持つ構成を検討します。
6. **重心にモデル名と生成日と件数を刻む**。インデックスのメタ情報と突き合わせて、ずれていたら起動時に落とすようにしておきます。
7. **再インデックスの手順に重心の再生成を含める**。手順書に書いていないものは、いつか必ず抜けます。

## まとめ

多言語のインデックスを作ったら、まず対訳ペアで言語横断の再現率を測ってみてください。すでに日英で同じ内容を持っているなら、評価データセットは今日その場にあります。ラベル付けの手間はゼロです。

単一言語で問題なく見えていたものが、混ぜた瞬間に別の顔をすることがあります。私はそれを、上位10件が全部日本語で埋まった画面で知りました。

自分の環境ではどうなのか。その数字を持っているかどうかが、この先の判断を分けるのだと思います。実装の参考になれば幸いです。お読みいただきありがとうございました。
