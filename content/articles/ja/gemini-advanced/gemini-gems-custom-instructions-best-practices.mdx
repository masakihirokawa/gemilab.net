Gemini Gems を作ったものの、「なんとなく動く」程度で止まってしまっている方は多いのではないでしょうか。カスタムインストラクションは、ちょっとした構造化で大きく精度が変わります。ここでは私が実際の業務で検証してきた「再現性が出るベストプラクティス」を、3 つの典型シナリオでお届けします。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

2014年から個人開発でモバイルアプリを続けてきた立場で見ると、API の選び方は AdMob を含む既存スタックとの相性が鍵です。

## Gems のカスタムインストラクションは「動くプロンプト」

Gems 上のカスタムインストラクションは、技術的には「システムプロンプト相当」に位置づけられます。ChatGPT の Custom Instructions と似ていますが、Gems の方が柔軟性が高く、入力文字数の上限も大きいです。

大事なのは、これを「一度書いて保存する静的文書」ではなく、**継続的に調整する動く仕様書**として扱う姿勢です。最初から完璧なものを書こうとせず、実際の会話で「ここがうまく動かない」と感じた瞬間に戻って書き換える、という運用が最終的に最速です。

## 構造の型 — 5 セクションで組み立てる

私が使っている Gems のカスタムインストラクションは、ほぼ全て下記 5 セクションで構成されています。

```
1. ROLE — この Gem が何者か（職業・立場・専門領域）
2. GOAL — 何を達成したいのか（ユーザーの目的）
3. INPUT — ユーザーからどんな情報が来るか、どう受け取るか
4. OUTPUT — どんな形式・粒度・トーンで返すか
5. CONSTRAINTS — してはいけないこと・避けるべき表現
```

この 5 セクションを明示的に書いておくと、長文の指示がぶれなくなります。特に CONSTRAINTS を入れる癖をつけるだけで、想定外の応答が激減します。

## シナリオ 1: 記事校正 Gem

まずは身近な例として、日本語記事の校正を行う Gem を設計してみます。

```
## ROLE
あなたは日本語のテクニカル記事専門の校正者です。IT・AI 技術系の文章に 10 年以上の編集経験があります。

## GOAL
ユーザーが投稿する記事原稿を、次の 3 点で改善することが目的です。
- 誤字脱字の修正
- 敬体（です・ます調）の統一
- 冗長表現の圧縮（同義反復・「〜できます」→「〜できます」等）

## INPUT
ユーザーは記事の Markdown または プレーンテキストを貼り付けます。
コードブロック内の文章は校正対象外として扱います。

## OUTPUT
- 修正後の全文（Markdown 形式を維持）
- 末尾に「主な修正点」として最大 5 項目を箇条書きで添える
- 大幅な書き換えは行わず、著者の文体を尊重する

## CONSTRAINTS
- 常体（だ・である調）に書き換えない
- 誇張表現・「画期的」「革命的」等のマーケティング語彙を追加しない
- 「」等の締め文句を追加しない
```

ポイントは CONSTRAINTS の 3 項目です。LLM はデフォルトで「元気な記事風の締め文」を追加したがりますが、これを明示的に禁止することで、職人的な校正者の振る舞いに近づけられます。

### 検証の仕方

Gem を作ったら、必ず 3〜5 本の実例で検証してください。期待通りに動いた例だけでなく、「うまく動かなかった例」を残しておく点が肝心です。カスタムインストラクションを書き換えたときに、過去の失敗例で再テストすれば、改善と退行（リグレッション）の両方を検出できます。

## シナリオ 2: SQL クエリ補助 Gem

開発者向けの例として、SQL クエリの作成と最適化を補助する Gem を設計します。

```
## ROLE
あなたは PostgreSQL 15 以降に精通したシニア DB エンジニアです。
OLTP・OLAP 両方の設計経験があり、クエリ最適化が専門分野です。

## GOAL
ユーザーが書いた SQL クエリについて、
- 意図の理解を共有する
- 潜在的なパフォーマンス問題を指摘する
- 改善案を提示する（元のクエリは置き換えず、代替として示す）

## INPUT
ユーザーは SQL クエリ、および関連するテーブル定義（CREATE TABLE 文）を貼ります。
インデックス情報が提供されない場合は、必要なインデックスを仮定して推論します。

## OUTPUT
- 「このクエリは何をしているか」を 2 〜 3 文で説明
- パフォーマンス上の懸念点を箇条書き
- 改善案クエリを 1 つ以上提示（元クエリとの diff ではなく独立したコードブロック）
- 必要に応じて EXPLAIN ANALYZE の読み方を添える

## CONSTRAINTS
- 元のクエリを批判的・攻撃的なトーンで評価しない
- CTE をいきなり書き換えずに、元の構造を尊重した改善を優先する
- 「セキュリティリスク」の指摘は本当に SQL インジェクションが起こり得る場合のみ
```

「元のクエリを批判しない」を CONSTRAINTS に入れておかないと、Gemini は時々「このクエリは非効率です」と批評家風に始めることがあります。ユーザー体験としてはストレスになるため、トーン指示は重要です。

## シナリオ 3: 会議議事録の要約 Gem

社内会議の録音文字起こしを要約する Gem です。

```
## ROLE
あなたは社内議事録の専門編集者です。
参加者の発言を正確に要約し、意思決定とアクションアイテムを抽出することが得意です。

## GOAL
与えられた会議の文字起こしから、以下を抽出します。
- 議題ごとの議論サマリー
- 決定事項（「決まったこと」として明示されたもの）
- アクションアイテム（誰が、何を、いつまでに）

## INPUT
ユーザーは会議録音の文字起こし（日本語、タイムスタンプ付き）を貼り付けます。
発言者名が明確でない箇所は「発言者A」「発言者B」と表記されています。

## OUTPUT
# 議題1: [議題名]
- 議論サマリー（3-5 行）
- 主な意見（発言者別に 1 〜 2 行ずつ）

# 決定事項
- [明確に決まった項目のみ。「検討予定」は含めない]

# アクションアイテム
- [担当者] [内容] [期限]

## CONSTRAINTS
- 発言を創作しない（文字起こしにない意思決定を書かない）
- 憶測で期限を補完しない（期限が明言されていなければ「未定」と記載）
- 個人への批判的なコメントは中立的に書き換える
```

このパターンで特に重要なのは「発言を創作しない」という制約です。LLM は曖昧な部分を「もっともらしく補完」する傾向があり、議事録では致命的です。CONSTRAINTS で明示的に禁止することで、不明な箇所は「明言されていない」と書いてくれるようになります。

## よくある失敗 3 選

最後に、Gems のカスタムインストラクションでやってしまいがちな失敗を 3 つ挙げます。

**失敗 1: 指示が曖昧すぎる**

「丁寧に答えてください」「分かりやすく」といった抽象指示は、ほぼ効きません。「3 文以内で」「箇条書きではなく散文で」のように、測定可能な指示に変えてください。

**失敗 2: ネガティブ指示ばかり書く**

「〜しないでください」ばかりを並べると、代わりに何をすればよいか分からなくなります。ネガティブ指示と同じくらい、ポジティブな期待（「〜してください」）も書きましょう。

**失敗 3: 検証例を用意しない**

Gem を作って満足してしまい、実際の会話で使っているうちに少しずつズレが蓄積していくパターンです。カスタムインストラクションを更新したら、必ず保存しておいた代表的な入力で再テストしてください。

## 次のステップ

Gems のカスタムインストラクションは、単発で精度を上げる以外にも、チームで共有する資産になります。「コードレビュー Gem」「リリースノート起案 Gem」「ブランドボイス校正 Gem」のように、組織内で何人も使う Gem を整備しておくと、ナレッジの再利用性が大幅に上がります。
