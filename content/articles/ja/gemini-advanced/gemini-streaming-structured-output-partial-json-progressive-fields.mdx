AdMob の日次レポートを要約するカードを、自分の管理画面に足したときのことです。Gemini に数値を渡し、`responseSchema` で「見出し・要点・推奨アクション・スコア」を返してもらう、よくある構成でした。

動きはしました。ただ、押してから結果が出るまで、画面は数秒間まっさらのままでした。裏ではトークンが届いているのに、JSONが最後の `}` で閉じるまで `JSON.parse` が投げ続けるので、何も描けなかったのです。

ストリーミングにしているのに、体感は一括取得と変わりませんでした。むしろ「押したのに無反応」に見える分だけ、印象は悪くなっていました。

その真っ白な数秒を、完成したフィールドから順に埋めていく数百ミリ秒へ。個人開発の自分の画面で実際にそう変えられた、部分パースと逆流防止の設計を、私自身のつまずきも含めて動くコードとともに残します。

## 完成待ちが体感を悪くする理由

構造化出力のストリーミングでは、モデルは JSON を頭から少しずつ吐き出します。届くのはこういう断片の連なりです。

<table>
<thead><tr><th>到着段階</th><th>バッファの中身（イメージ）</th><th>JSON.parse</th></tr></thead>
<tbody>
<tr><td>序盤</td><td><code>{"title":"省エネ壁紙</code></td><td>失敗</td></tr>
<tr><td>中盤</td><td><code>{"title":"省エネ壁紙12選","summary":"暗色</code></td><td>失敗</td></tr>
<tr><td>終盤</td><td><code>{...,"score":87}</code></td><td>成功</td></tr>
</tbody>
</table>

標準の `JSON.parse` は、閉じていない文字列やオブジェクトを一切許しません。ですから終盤で全体が閉じるまで、私たちは何も取り出せません。

けれど中身をよく見ると、`title` は序盤の時点で既に確定しています。読者に見せられる情報が手元にあるのに、末尾が閉じていないという一点で握りつぶしている。ここが体感の損失点でした。

やりたいことは単純です。バッファが届くたびに、**その時点で確定している先頭のフィールドだけ**を安全に取り出して、順番に画面へ流す。これだけです。

## 不完全なJSONを安全に補完して読む

方針は、バッファをそのままパースして失敗したら、**閉じられる最小限の補完**をしてからもう一度パースする、というものです。開いたままの文字列・オブジェクト・配列を数えて、足りない分の閉じ括弧を足します。

半端に書かれている末尾の値（打ちかけの数値やキーだけの箇所）は、揺れの原因になるので落とします。完成した部分だけを見せるのが目的だからです。

```typescript
// 開いたままの構造を閉じ、半端な末尾を落として「今わかる範囲」を作る
function completePartial(buf: string): string {
  const stack: string[] = [];
  let inStr = false;
  let esc = false;
  let out = buf;

  for (let i = 0; i < buf.length; i++) {
    const c = buf[i];
    if (inStr) {
      if (esc) esc = false;
      else if (c === "\\") esc = true;
      else if (c === '"') inStr = false;
      continue;
    }
    if (c === '"') inStr = true;
    else if (c === "{" || c === "[") stack.push(c);
    else if (c === "}" || c === "]") stack.pop();
  }

  if (inStr) out += '"';              // 開いたままの文字列を閉じる
  out = out
    .replace(/,\s*$/, "")             // 末尾のカンマを落とす
    .replace(/:\s*$/, ": null")       // 値のないキーは null で埋める
    .replace(/([0-9])\.$/, "$1");     // 打ちかけの小数点を切る

  for (let i = stack.length - 1; i >= 0; i--) {
    out += stack[i] === "{" ? "}" : "]";
  }
  return out;
}

export function safeParse(buf: string): unknown | null {
  try { return JSON.parse(buf); } catch { /* まだ閉じていない */ }
  try { return JSON.parse(completePartial(buf)); } catch { return null; }
}
```

`completePartial` の肝は、文字列の内側を数えないことです。`"{"` のような括弧が値の文字列に含まれていても、`inStr` フラグで無視します。これを忘れると、本文に括弧が入った瞬間に補完が壊れます。

これを Gemini のストリームに繋ぎます。チャンクが届くたびにバッファへ足し、`safeParse` で「今わかる範囲」を取り出します。

```typescript
import { GoogleGenAI } from "@google/genai";

const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY! });

async function streamCard(prompt: string, onField: (k: string, v: unknown) => void) {
  const stream = await ai.models.generateContentStream({
    model: "gemini-flash-latest",
    contents: prompt,
    config: {
      responseMimeType: "application/json",
      responseSchema: {
        type: "object",
        properties: {
          title:   { type: "string" },
          summary: { type: "string" },
          actions: { type: "array", items: { type: "string" } },
          score:   { type: "integer" },
        },
        propertyOrdering: ["title", "summary", "actions", "score"],
        required: ["title", "summary", "actions", "score"],
      },
    },
  });

  let buf = "";
  const emitter = fencedEmitter(onField);
  for await (const chunk of stream) {
    buf += chunk.text ?? "";
    const obj = safeParse(buf);
    if (obj && typeof obj === "object") emitter(obj as Record<string, unknown>);
  }
}
```

## 一度見せた値を後退させない

部分パースには、素直に組むと必ず踏む罠があります。**逆流**です。

`summary` の途中まで届いた段階で `completePartial` は文字列を閉じてしまうので、`"暗色系の"` という半端な文が一瞬 UI に出ます。次のチャンクで `"暗色系の壁紙をまとめました"` に伸びると、表示が書き変わります。これがちらつきになります。

さらにやっかいなのは、補完のタイミングによっては前のチャンクより短い値が一瞬生まれることです。伸びるはずの文字が縮んで見えると、読者は「壊れた」と感じます。

対策はフェンシングです。**確定したフィールドは二度と触らない**、伸びている最中のフィールドは**長くなる方向にしか更新しない**。この二つを守ります。

```typescript
// 確定は据え置き、伸長中は前進のみ許す
function fencedEmitter(onField: (k: string, v: unknown) => void) {
  const settled = new Set<string>();
  const lastLen: Record<string, number> = {};

  return (obj: Record<string, unknown>) => {
    const keys = Object.keys(obj);
    for (let i = 0; i < keys.length; i++) {
      const k = keys[i];
      if (settled.has(k)) continue;

      const v = obj[k];
      if (v === null || v === undefined) continue;

      // 次のキーが見えている＝このフィールドはもう閉じている
      const isSettled = i < keys.length - 1;

      if (typeof v === "string") {
        if ((lastLen[k] ?? 0) > v.length && !isSettled) continue; // 縮む更新は捨てる
        lastLen[k] = v.length;
      }

      onField(k, v);
      if (isSettled) settled.add(k);
    }
  };
}
```

「次のキーが見えていれば、そのひとつ前のフィールドは閉じている」という判定が、ここでの安全弁です。`propertyOrdering` で順序を固定しておくと、この仮定が崩れません。

## propertyOrdering で到着順を設計する

`propertyOrdering` は表示順の飾りではありません。**どのフィールドを最初に見せたいか**を決める設計項目です。

要約カードなら、読者がまず知りたいのは見出しと要点です。数値スコアや推奨アクションの配列は後でかまいません。ですから短くて確定の早いものを前に、長い配列を後ろに置きます。

<thead><tr><th>順序の置き方</th><th>最初に埋まるもの</th><th>体感</th></tr></thead>
<tbody>
<tr><td>title → summary → actions → score</td><td>見出しが最速で出る</td><td>押した手応えがすぐ返る</td></tr>
<tr><td>actions → score → title → summary</td><td>配列が閉じるまで見出しが出ない</td><td>序盤が無反応に見える</td></tr>
</tbody>

配列やネストしたオブジェクトは閉じるのが遅く、補完も難しくなります。**軽くて短いフィールドを前に寄せる**だけで、最初のフィールドまでの時間は目に見えて縮みます。

## 本番で刺さる落とし穴

数か月動かしてみて、実際につまずいた点を残します。

**打ちかけの数値を出さない。** `"score": 8` の段階で 8 を表示し、次に 87 へ書き変わると、読者は数字を誤読します。数値だけは「次のキーが見えて閉じている」と確認できるまで表示を保留するのが安全でした。上の `fencedEmitter` で `isSettled` を待つ理由がここにあります。

**エスケープの途中で閉じない。** `\` が末尾に来た瞬間に文字列を閉じると、`\"` を壊します。`completePartial` の `esc` フラグは、この一文字のために必要です。

**キャンセルを必ず繋ぐ。** 画面を離脱したのにストリームが回り続けると、課金だけが進みます。`AbortController` をストリームに渡し、アンマウントで確実に切ります。

```typescript
const controller = new AbortController();
// ...generateContentStream({ ..., abortSignal: controller.signal })
// 離脱時
controller.abort();
```

**補完結果はログに残さない。** 補完後のJSONは一時的な近似です。永続化や監査ログには、必ず**最後まで閉じた確定バッファ**を使います。途中経過を保存すると、後で「壊れたJSON」に見えて自分が混乱します。

## 個人アプリでどう組み込むか

私はこのパターンを、要約カードのほかにも、壁紙アプリのメタデータ生成プレビューに広げました。タイトルとタグが先に出て、説明文が後から流れ込む。生成を待つ画面が、埋まっていく画面に変わりました。

大きな設計変更は要りません。ストリーミングは既にできているはずですから、足すのは `safeParse` と `fencedEmitter` の二つだけです。`responseSchema` に `propertyOrdering` を一行足して、見せたい順に並べ替える。それで最初のフィールドまでの時間が縮みます。

次の一歩として、まずは自分のアプリで一番「押しても無反応に見える」画面を一つ選び、そこにこの二関数を差し込んでみてください。押した手応えが返ってくる感触は、数字以上に効きます。
