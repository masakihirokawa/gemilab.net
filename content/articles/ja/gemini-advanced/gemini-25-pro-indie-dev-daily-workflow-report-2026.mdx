Gemini 2.5 Pro を本格的に使い始めてから3ヶ月が経ちました。最初の1週間は「すごいな」と思いながらも、チャットにコードを貼り付けて確認する程度の使い方でした。それが今では、開発のリズムそのものが変わっています。

ここでは個人開発の現場で本当に使っているワークフローを7つ、具体的なプロンプトとコード例を交えてお伝えします。「どう使えばいいか分からない」という段階を抜け出すきっかけになれば嬉しいです。

Dolice Labs の 4 サイト並行運用で得た実感として、この問題に普段から向き合ってきた立場で、要点を整理します。

## Pull Request のレビューを10分で終わらせる

以前は GitHub の PR レビューで1時間かけていた作業が、今では10〜15分で終わります。

使い方はシンプルで、`git diff` の出力をそのまま Gemini 2.5 Pro に渡します。

```python
import google.generativeai as genai
import subprocess

# 差分を取得
diff = subprocess.run(
    ["git", "diff", "main...HEAD"],
    capture_output=True, text=True
).stdout

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro-latest")

prompt = f"""
以下のGit差分をレビューしてください。
確認観点:
- バグの可能性がある箇所
- パフォーマンス上の問題
- セキュリティリスク
- 命名や可読性の改善点

diff:
{diff}

深刻度（HIGH/MEDIUM/LOW）を各指摘に付けてください。
"""

response = model.generate_content(prompt)
print(response.text)
# 出力例:
# [HIGH] src/auth.py:42 — ユーザー入力がそのままSQLクエリに結合されています。SQLインジェクションのリスクがあります。
# [MEDIUM] src/api.py:87 — レスポンスボディの検証が行われていません。想定外の型が来た場合にクラッシュする可能性があります。
```

ポイントは「何を見てほしいか」を明示することです。「レビューして」だけだと全体的なコメントになりますが、観点を絞ることでピンポイントの指摘が返ってきます。

私が特に助かっているのは、自分では気づきにくいセキュリティリスクの洗い出しです。入力値の検証漏れや、ログに誤ってシークレット情報が含まれているケースを何度か指摘してもらいました。一人で開発していると、こういうレビューの目線が薄くなりがちなので、地味に重要な使い方だと感じています。

## 「どこが悪いか分からない」デバッグの壁を乗り越える

バグ修正の中でも特に時間を取られるのが、エラーメッセージが出ないタイプの不具合です。「なんか動作がおかしい」というやつです。

こういうときは、スタックトレースや関連コードを丸ごと渡してから、こう聞きます。

```
このコードが期待通りに動いていません。
期待する動作: ユーザーがボタンを押すと即座に画面遷移する
実際の動作: 2回目以降のボタン押下から画面遷移が起きる

怪しい箇所の仮説を3つ挙げて、それぞれの確認方法を教えてください。
（コードを修正するのではなく、仮説と検証手順だけ教えてください）
```

「答えを直接教えてほしい」ではなく「仮説と確認方法」を求めることが重要です。直接答えを求めると、コードを実際に実行しているわけではないので的外れな回答が来ることがあります。仮説ベースで進めると、自分でコードを読む目線が養われますし、最終的に自力で発見できることも増えました。

この使い方は、個人的に最もROIが高いワークフローだと思っています。1時間詰まっていた問題が15分で解決できるようになると、1日のアウトプット量が全然変わります。

## Context Caching でコストを抑えながら長文コードを扱う

大規模プロジェクトのコードベース全体を Gemini に渡してリファクタリングの提案をもらうとき、トークン数が膨らんでコストが気になります。

そこで活用しているのが Context Caching です。変わらないコード（ライブラリのソースや共通モジュール）をキャッシュしておき、質問のたびに再送しないようにする仕組みです。

```python
import google.generativeai as genai

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

# コードベースをキャッシュ（TTL: 1時間）
with open("src/main_module.py", "r") as f:
    source_code = f.read()

cache = client.caches.create(
    model="gemini-2.5-pro-latest",
    contents=[{
        "role": "user",
        "parts": [{"text": f"プロジェクトのソースコード:\n{source_code}"}]
    }],
    ttl="3600s",
    display_name="my-project-cache"
)

print(f"キャッシュ作成: {cache.name}")
# → cachedContents/abcdef123 のような名前が返ってきます

# キャッシュを使って複数回質問（毎回コードを送らなくてよい）
questions = [
    "このコードの依存関係を整理して、循環参照がないか確認してください",
    "パフォーマンスのボトルネックになりそうな箇所を3つ挙げてください",
    "テストしにくい関数を見つけて、改善案を提示してください",
]

for q in questions:
    response = client.models.generate_content(
        model="gemini-2.5-pro-latest",
        contents=q,
        config={"cached_content": cache.name}
    )
    print(f"\n質問: {q}\n回答: {response.text[:200]}...")
```

1回のリファクタリングセッションで10〜20回質問することがあるので、Context Caching を使うと費用が体感で50〜70%ほど抑えられています。コードベース分析の詳細な活用法は[Gemini 2.5 Pro でコードベース全体を分析・リファクタリングする実践ガイド](/articles/gemini-advanced/gemini-25-pro-codebase-full-analysis-refactoring-guide)も参考になります。

## App Store の説明文を5言語に展開する

個人開発では多言語対応が後回しになりがちです。英語版のアプリ説明文は作れても、日本語・中国語・スペイン語・ドイツ語まで手が回らない。

Gemini 2.5 Pro を使うと、ただの翻訳ではなく「その言語のユーザーに響く表現」に書き直してもらえます。

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro-latest")

def generate_aso_description(original_text: str, target_locale: str) -> str:
    prompt = f"""
App Store のアプリ説明文を {target_locale} 向けに作成してください。

要件:
- 直訳ではなく、{target_locale} のユーザーが自然に読める表現にする
- App Store のガイドラインに準拠（誇大表現・他社比較禁止）
- 最初の3行でアプリの価値を伝える（折り畳み表示への対策）
- 4000文字以内

原文（日本語）:
{original_text}
"""
    response = model.generate_content(prompt)
    return response.text

ja_description = """毎日の習慣を記録するシンプルな習慣管理アプリ。
リマインダーと統計機能で、続けることが楽しくなります。
"""

for locale in ["en-US", "zh-TW", "es-ES", "de-DE"]:
    result = generate_aso_description(ja_description, locale)
    print(f"\n=== {locale} ===\n{result[:300]}...")
    # 各ロケールの説明文が自然な表現で生成されます
```

英語ネイティブのユーザーからも「説明文が分かりやすい」というレビューをもらえるようになりました。最終的には自分で読んで手直ししますが、ゼロから書く労力が大幅に減りました。私のアプリは10言語以上に対応していますが、これがなければ到底維持できなかったと思います。

## ドキュメント作成を「書く」から「レビューする」に変える

README や API ドキュメントを書くのは、コーディングよりも時間がかかることがあります。

私が今やっているのは「コードを渡してドキュメントの初稿を作ってもらい、自分はレビュアーに徹する」というスタイルです。

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro-latest")

def generate_readme(code_files: list[str]) -> str:
    all_code = ""
    for filepath in code_files:
        with open(filepath, "r") as f:
            all_code += f"## {filepath}\n```python\n{f.read()}\n```\n\n"

    prompt = f"""
以下のPythonコードに対して、GitHub README.md を作成してください。

必須セクション:
- プロジェクト概要（1〜2文）
- インストール手順
- 使い方（コード例付き）
- 設定項目の説明（環境変数等）

対象読者: Pythonの基礎知識がある開発者

{all_code}
"""
    response = model.generate_content(prompt)
    return response.text

readme = generate_readme(["src/main.py", "src/config.py"])
print(readme)
```

「ドキュメントを書かないといけない」という心理的な重さが、このアプローチで軽くなりました。初稿があれば、あとは気になるところを直すだけです。コードのコメントも同様で、「このクラスにdocstringを追加して」という指示を出すだけで一通り書いてくれます。

## プロファイリングで「なんか遅い」を数値で把握する

「なんか最近レスポンスが遅い」というとき、感覚に頼るのではなく計測して Gemini に診断してもらいます。

```python
import time
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro-latest")

def profile_api_call(prompt: str) -> dict:
    start = time.time()
    response = model.generate_content(prompt)
    elapsed = time.time() - start

    # 計測結果を Gemini 自身に診断してもらう
    diagnosis_prompt = f"""
APIレスポンスの計測結果:
- 応答時間: {elapsed:.2f}秒
- プロンプト文字数: {len(prompt)}文字
- レスポンス文字数: {len(response.text)}文字

この応答時間は適切ですか？
改善できる点（モデル選択・プロンプト設計・キャッシング）があれば具体的に教えてください。
"""
    diagnosis = model.generate_content(diagnosis_prompt)

    return {
        "elapsed_seconds": round(elapsed, 2),
        "response": response.text,
        "diagnosis": diagnosis.text
    }

result = profile_api_call("Pythonの非同期処理のベストプラクティスを教えてください")
print(f"応答時間: {result['elapsed_seconds']}秒")
print(f"診断: {result['diagnosis'][:500]}...")
```

「Gemini に Gemini を評価させる」という少し変なアプローチですが、コスト設計を見直す具体的なフィードバックが返ってくることがあります。Context Caching の効果的な使い方については、[Gemini API Context Caching コスト最適化ガイド](/articles/gemini-api/gemini-api-context-caching-cost-optimization)で詳しく解説しています。

## 朝のスタンドアップメモを Git ログから自動生成する

一人で開発していても「昨日何をやったか・今日何をやるか」を整理する時間は大切です。でも毎朝それを書くのは地味に手間がかかります。

```python
import subprocess
import google.generativeai as genai
from datetime import datetime, timedelta

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro-latest")

def generate_daily_standup() -> str:
    yesterday = (datetime.now() - timedelta(days=1)).strftime("%Y-%m-%d")

    # 昨日のコミット履歴を取得
    commits = subprocess.run(
        ["git", "log",
         "--since", f"{yesterday} 00:00:00",
         "--until", f"{yesterday} 23:59:59",
         "--oneline"],
        capture_output=True, text=True
    ).stdout

    prompt = f"""
昨日のGitコミット履歴から、スタンドアップミーティング用のメモを生成してください。

コミット履歴:
{commits if commits.strip() else "コミットなし（調査・設計日）"}

出力形式:
【昨日やったこと】
・（箇条書きで2〜3項目）

【今日やること】
・（コミット内容から次のステップを推測して2〜3項目）

【懸念点】
・（なければ「特になし」）
"""
    response = model.generate_content(prompt)
    return response.text

print(generate_daily_standup())
# 出力例:
# 【昨日やったこと】
# ・認証モジュールのSQLインジェクション対策を実装
# ・APIレスポンスの型バリデーションを追加
#
# 【今日やること】
# ・修正内容のユニットテスト作成
# ・ステージング環境での動作確認
#
# 【懸念点】
# ・特になし
```

コミットメッセージから「今日やること」を推測してもらうのは少し強引ですが、意外と的確な提案が返ってきます。何より「今日の作業計画を考える」というコストが下がるので、朝の立ち上がりが早くなりました。
