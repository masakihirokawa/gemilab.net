レビュー返信の下書きを振り分けるプロンプトを、週末の夜に三晩続けて手で磨いていたことがあります。直したところは確かによくなるのに、翌週に別の種類の問い合わせが混ざると、前の調整がまるごと無駄になるのです。その繰り返しに、肩の荷が少しも下りないまま疲れていました。

DSPy を試したのは、そんな折です。最初は正直なところ「またフレームワークか」と身構えました。ところが、私が三日かけて詰めたプロンプトと、`MIPROv2` が二十分ほどで組み上げたプロンプトを同じ検証データで並べると、後者のほうが明らかに良い結果を返したのです。手書きでは拾えていなかった「例示の組み合わせ」が、探索で見つかっていました。

そのとき気づいたのは、私の手癖が通用しなくなったということではありません。**プロンプトは書くものから、測って育てるものへ移りつつあり、書く人の仕事は評価関数とラベルのほうへ移る**——そう線を引き直したほうが、仕事が前に進むと分かったのです。

ここでは、その線引きを Gemini API と DSPy の組み合わせで形にします。インストールから本番運用まで一本の流れでお見せしますので、Python の基礎と Gemini API を一度でも触ったことがある方なら、コードを写しながら進められるはずです。

最初にお伝えしたいのは、DSPy が魔法ではないという点です。ラベル付きデータを用意する工程と、評価関数を設計する工程は、これまでどおり人間の仕事として残ります。むしろ、この二つの丁寧さが結果の質をほぼ決めます。後半では、その二つで私が足を取られた箇所を、スクリプト付きで書き残しました。

なお、コード中のモデル名は環境変数で受ける形にしています。Gemini のモデルは入れ替わりが速く、2026 年 9 月の公式 changelog では 2.5 系が過去の利用者に限定されました。手元で動かす前に、いま使えるモデル ID を公式ドキュメントで確かめ、`.env` に書き込んでからお試しください。

## 手書きプロンプトが行き詰まる場面

私の手元には、ストアのレビューの振り分け、問い合わせ文の要約、多言語の訳文チェックなど、小さなプロンプトがいくつも並んでいます。以前はそれぞれを一行ずつ手で直し、A/B で良かったほうを残していました。

このやり方が破綻するのは、だいたい次のうち二つ以上が重なったときです。

- 入力データの性質が変わったとき（例: 問い合わせの種類が増えた場合）
- モデルを切り替えたとき（例: Flash から Pro、あるいは世代をまたぐ移行）
- 評価軸を増やしたとき（例: 正確さに加えて、文字数や口調も同時に守りたい場合）

どれかが起きた瞬間に、過去の微調整は一気に陳腐化します。しかも変更のたびに A/B をやり直す手間が発生します。DSPy は、この手間を「評価関数とデータを用意しておけば、あとは機械が回す」という形に置き換えてくれます。

DSPy（Declarative Self-improving Language Programs）は Stanford NLP が開発した、LLM 呼び出しを関数のように扱うためのフレームワークです。プロンプトは「書くもの」ではなく「データから最適化されるもの」という発想で、PyTorch の `nn.Module` に近い抽象でプログラムを組みます。

私が腹落ちしたのは、プロンプトを高級言語、Optimizer をコンパイラと見立てる理解でした。生成されたアセンブリを人間が手で書き直すのが非効率なように、コンパイラに任せられる探索を手で続けるのは、できなくはなくても割に合いません。

## 最初のパイプラインを組む

動く最小構成から始めます。インストールと Gemini への接続までです。

```bash
# パッケージ名は dspy（旧名の dspy-ai も残っていますが、新規なら dspy で十分です）
pip install -U dspy python-dotenv
```

`.env` には API キーと、使うモデルの ID を書いておきます。

```bash
# .env — 値は自分の環境のものに置き換えてください
GEMINI_API_KEY=YOUR_GEMINI_API_KEY
# 公式ドキュメントで確認した、現在使える Flash 系のモデル ID（LiteLLM 形式で gemini/ を付けます）
GEMINI_FAST_MODEL=gemini/YOUR_FLASH_MODEL_ID
# 判定や本番推論に使う、上位のモデル ID
GEMINI_STRONG_MODEL=gemini/YOUR_PRO_MODEL_ID
```

DSPy から Gemini を呼ぶには、LiteLLM 経由で `gemini/` プレフィックスを付けたモデル名を渡すのがいちばん素直です。

```python
# setup_dspy.py — DSPy と Gemini の接続を確認する最小例
import os
import dspy
from dotenv import load_dotenv

load_dotenv()

lm = dspy.LM(
    model=os.environ["GEMINI_FAST_MODEL"],
    api_key=os.environ["GEMINI_API_KEY"],
    temperature=0.0,
    max_tokens=1024,
)
dspy.configure(lm=lm)

# いちばん単純な Signature（入出力の宣言）
class Translate(dspy.Signature):
    """日本語テキストを自然な英語に翻訳する。"""
    japanese = dspy.InputField(desc="翻訳対象の日本語")
    english = dspy.OutputField(desc="英訳結果")

predictor = dspy.Predict(Translate)
result = predictor(japanese="プロンプトを手書きする時代は終わった。")

print(result.english)
# 出力例: "The era of writing prompts by hand is over."（表現は実行ごとに多少変わります）
```

これが動けば、接続は成功です。注目していただきたいのは、ここまでの実装にプロンプト文字列が一行も出てこないことです。DSPy は Signature の docstring とフィールド定義から送信内容を組み立てており、実際に何が送られているかは `dspy.inspect_history(n=1)` で確認できます。デバッグでは何度も使うことになりますので、早めに指に馴染ませておくと楽です。

### キャッシュが「ゆらぎの測定」を邪魔する

ここで、私が一度つまずいた点を書き残します。`temperature=0.0` にしても、Gemini の出力が実行ごとにまったく同じになるとは限りません。確率の近いトークンが並んだとき、選ばれ方が決定的とは限らないためです。

厳密に同じ結果を求めたい場面では、同じ入力を数回呼んで多数決を取る、あるいは生成設定の `seed` を指定する、といった手が考えられます。ただし seed を固定しても完全一致までは保証されないと考えておくほうが安全です。

もう一つ見落としやすいのが、DSPy の LM クライアントが既定で応答をキャッシュしていることです。同じ入力を二度呼ぶと、二度目は API に行かず、一度目の応答が返ります。ゆらぎを測りたいときは、`dspy.LM(..., cache=False)` で明示的にキャッシュを切っておかないと、「毎回同じ結果が返るので安定している」と誤読してしまいます。

CI でプロンプトのスナップショットテストを書く場合も、この二つ（出力のゆらぎとキャッシュ）を前提に設計しておくと、原因不明の失敗に悩まされずに済みます。

## Signature と Module を分けて考える

DSPy の設計でいちばん感心するのは、**Signature（何を入れて何を出すか）** と **Module（どうやって推論するか）** を切り分けている点です。同じ Signature に別の Module を付け替えられるので、「まず `Predict` で書いて、足りなければ `ChainOfThought` に差し替える」という実験が軽くなります。

```python
# signature_and_module.py — 同じ Signature を異なる Module で処理する
import dspy

class ClassifyInquiry(dspy.Signature):
    """ユーザー問い合わせを payment / bug / feature / other のいずれかに分類する。"""
    inquiry: str = dspy.InputField(desc="ユーザーからの問い合わせ本文")
    category: str = dspy.OutputField(
        desc="4 カテゴリから 1 つ: payment / bug / feature / other"
    )

# 1) Predict: 素直に一発回答を求める。速くて安い
quick_classifier = dspy.Predict(ClassifyInquiry)

# 2) ChainOfThought: 推論の理由も出力させる。紛らわしい問い合わせで効きやすい
thoughtful_classifier = dspy.ChainOfThought(ClassifyInquiry)

sample = "先週のアップデートから、設定画面を開くとアプリがクラッシュします。"

print(quick_classifier(inquiry=sample).category)
# 出力例: "bug"

out = thoughtful_classifier(inquiry=sample)
print(out.reasoning)   # 古いバージョンでは rationale という名前のことがあります
print(out.category)
```

実務では、安価なモデルで `Predict` を回し、判定が怪しいものだけ `ChainOfThought` に回す二段構成にすることが多いです。全件を `ChainOfThought` にすると精度は上がりますが、出力トークンが何倍にも膨らみ、費用に直撃します。私は最初の本番投入でこのトレードオフを見誤り、請求額が想定を大きく超えて胃が痛くなった経験があります。

二段構成は、`dspy.Module` を継承した自作クラスに二つの分類器を持たせると素直に書けます。切り替えの条件には、確率のような取れるかどうか分からない値に頼らず、「許可したカテゴリ以外の文字列が返ってきたら」という検査を使うのが堅実です。

```python
# two_stage.py — 一次判定が許可外ならもう一段だけ深く考える
import dspy

ALLOWED = {"payment", "bug", "feature", "other"}

class TwoStageClassifier(dspy.Module):
    def __init__(self):
        super().__init__()
        self.quick = dspy.Predict(ClassifyInquiry)
        self.careful = dspy.ChainOfThought(ClassifyInquiry)

    def forward(self, inquiry: str):
        first = self.quick(inquiry=inquiry)
        if first.category.strip().lower() in ALLOWED:
            return first
        return self.careful(inquiry=inquiry)
```

ここで大事なのは、Module の中に置いたサブモジュールがすべて最適化の対象になることです。親を `compile` すれば、`quick` と `careful` の両方が同時に調整されます。手書きのプロンプトでは、この「部品ごとの同時調整」はまず再現できません。

## Optimizer で「プロンプトを書かない」へ移る

ここからが DSPy の核心です。Optimizer は少量のラベル付きデータを受け取り、モデルに渡す指示文と Few-shot 例を探索します。組み合わせの探索は、人間が考えるよりも機械のほうがはるかに速く進みます。

当面は次の二つを押さえておけば足ります。

- **BootstrapFewShot**: 訓練データから成功例を拾い、Few-shot として埋め込みます。安価で速いのが利点です
- **MIPROv2**: 指示文と Few-shot 例を同時に探索する上位版です。呼び出しは増えますが、伸びしろも大きくなります

まず `BootstrapFewShot` で、`ClassifyInquiry` を最適化する例です。

```python
# optimize_classifier.py — 少量データで自動最適化する
import os
import dspy
from dotenv import load_dotenv
from dspy.teleprompt import BootstrapFewShot

load_dotenv()
dspy.configure(
    lm=dspy.LM(
        model=os.environ["GEMINI_FAST_MODEL"],
        api_key=os.environ["GEMINI_API_KEY"],
        temperature=0.0,
        max_tokens=256,
    )
)

class ClassifyInquiry(dspy.Signature):
    """ユーザー問い合わせを payment / bug / feature / other のいずれかに分類する。"""
    inquiry: str = dspy.InputField()
    category: str = dspy.OutputField(desc="payment, bug, feature, other のいずれか")

# 訓練例。実運用では数十件から百数十件あると安定しやすくなります
trainset = [
    dspy.Example(inquiry="クレジットカードの請求が二重に来ています。", category="payment").with_inputs("inquiry"),
    dspy.Example(inquiry="ダークモードを追加してほしい。", category="feature").with_inputs("inquiry"),
    dspy.Example(inquiry="アプリが起動直後に落ちます。", category="bug").with_inputs("inquiry"),
    dspy.Example(inquiry="退会手続きを教えてください。", category="other").with_inputs("inquiry"),
    # ...（省略。実際にはもっと必要です）
]

# 評価関数: category が一致していれば真
def exact_match(example, pred, trace=None):
    return pred.category.strip().lower() == example.category.strip().lower()

student = dspy.Predict(ClassifyInquiry)
optimizer = BootstrapFewShot(
    metric=exact_match,
    max_bootstrapped_demos=4,   # 指示に埋め込む「機械が解けた例」の数
    max_labeled_demos=16,       # 参照するラベル済み例の上限
    max_rounds=1,
)
compiled = optimizer.compile(student=student, trainset=trainset)

# 保存して再利用（JSON で保存されます）
compiled.save("compiled_classifier.json")

# 読み込みと推論
loaded = dspy.Predict(ClassifyInquiry)
loaded.load("compiled_classifier.json")
print(loaded(inquiry="プレミアムプランに戻したいです。").category)
```

`compile` の中で起きていることは、初見だとつかみにくいかもしれません。ざっくり言えば、`student` を訓練例に当てて、`exact_match` が真を返した例だけを Few-shot として採用しています。つまり採用されるのは「DSPy 自身が正しく解けた例」で、Signature と相性のよい形で残ります。手で選んだ Few-shot とは、選び方の論理が違うのです。

もっと踏み込みたいときは、`MIPROv2` に差し替えます。

```python
from dspy.teleprompt import MIPROv2

# 指示文の提案には上位モデル、実際の推論には Flash 系、と役割を分けられます
prompt_lm = dspy.LM(model=os.environ["GEMINI_STRONG_MODEL"], api_key=os.environ["GEMINI_API_KEY"])

optimizer = MIPROv2(
    metric=exact_match,
    prompt_model=prompt_lm,
    task_model=dspy.settings.lm,
    auto="light",           # "light" / "medium" / "heavy" で探索の深さを調整
    num_threads=4,
)
compiled = optimizer.compile(
    student=student,
    trainset=trainset,
    requires_permission_to_run=False,
)
```

`MIPROv2` は指示文と Few-shot 例を同時に探索するぶん、`BootstrapFewShot` より伸びやすい反面、API 呼び出しが桁違いに増えます。`auto="light"` でも、一回の `compile` で相当な回数の呼び出しが走ると思っておいたほうが安全です。開発中は Flash 系で回し、本番推論だけ上位モデルに切り替える構成が現実的です。

どちらを使うか迷ったときは、次の順で判断しています。まず `BootstrapFewShot` を一度だけ試し、目標に届いていれば採用します。届かなければ、そのときはじめて `MIPROv2` を回します。タスクの重要度に合わせて Optimizer を選ぶほうが、費用の見通しも立てやすくなります。

## 評価関数を LLM-as-a-Judge で自作する

完全一致で測れるタスクばかりではありません。要約・翻訳・返信文のように自由記述の品質を測るときは、**LLM-as-a-Judge** が使えます。Judge 自体も DSPy の Signature として書けます。

```python
# llm_judge.py — 要約品質を Gemini に判定させる評価関数
import os
import dspy

class SummaryJudge(dspy.Signature):
    """原文と要約を比べて総合品質を 1〜5 の整数で採点する。
    原文にない情報を含む場合は 2 以下、文法の誤りが目立つ場合は 1 点減らす。小数は使わない。"""
    article: str = dspy.InputField(desc="元の本文")
    summary: str = dspy.InputField(desc="評価対象の要約")
    rationale: str = dspy.OutputField(desc="採点の根拠（100 文字以内）")
    score: int = dspy.OutputField(desc="1〜5 の整数")

# 判定には上位モデルを使います。判断のぶれが小さいほうが、最適化の足場として安定するためです
judge_lm = dspy.LM(
    model=os.environ["GEMINI_STRONG_MODEL"],
    api_key=os.environ["GEMINI_API_KEY"],
    temperature=0.0,
    max_tokens=512,
)
judge = dspy.Predict(SummaryJudge)

def summary_metric(example, pred, trace=None):
    with dspy.context(lm=judge_lm):
        result = judge(article=example.article, summary=pred.summary)
    try:
        score = int(float(result.score))   # "4.0" のような小数文字列が来ても落ちないように二段階でキャスト
    except (TypeError, ValueError):
        return 0.0
    # Optimizer には 0〜1 の連続値で返すと扱いやすい
    return max(0.0, min(1.0, (score - 1) / 4.0))
```

要点は `dspy.context(lm=judge_lm)` で、Judge だけ別のモデルに切り替えているところです。推論本体と判定を分けておけば、本体を何百回と最適化する間も、判定側の物差しは動きません。`with` ブロックを抜ければ、グローバルの LM に戻ります。

採点基準を docstring に具体的に書く点も、見逃せません。「総合品質を採点する」とだけ書くと、Gemini は甘めに付けがちです。減点の規則を明文化して初めて、Judge の評価が現実の感覚に近づきます。Judge のプロンプト自体の管理は、[Gemini API プロンプトテンプレート管理の本番システム](/articles/gemini-api/gemini-api-prompt-template-management-production-system)で扱っていますので、Judge を本番に乗せる前に一度ご覧いただければ迷いが減ります。

Judge が長い要約を過大評価していないかも、必ず確かめてください。人手で付けたスコアと Judge のスコアを並べて相関を見る作業です。目安を数字で決めるより、まず自分の目で数十件読み、Judge の `rationale` が納得できる理由を書いているかを確認するほうが、バイアスに早く気づけます。

単一の Judge に頼らず、正確性・文体・簡潔さのように観点ごとに Judge を分け、重み付き平均を取る設計にすると、一つのバイアスが他の観点で薄まります。`metric` 関数の中で複数の Judge を呼んで平均を返すだけですので、実装の手間はほとんど増えません。

## 最適化の前に、ラベルを疑う

ここは、私がいちばん時間を溶かした箇所です。Optimizer は、渡されたラベルを正解として扱います。ラベルに誤りが混じっていると、その誤りを「正しく解けた例」として Few-shot に採用し、**誤りに忠実なプロンプト**を育ててしまいます。

あるとき、精度が思うように伸びない原因を探し回って、結局いちばんの原因は評価関数でもモデルでもなく、人手で付けたラベルの食い違いだったと分かりました。それ以来、最適化の前に必ずラベルの監査を挟んでいます。やることは単純で、**素の `Predict` と人間のラベルが食い違った行を、人が読み直す**だけです。

```python
# audit_labels.py — 最適化の前に、ラベルと機械の判定が食い違う行を洗い出す
import csv
import dspy

def audit_labels(program, examples, out_path="label_suspects.csv"):
    suspects = []
    for ex in examples:
        pred = program(inquiry=ex.inquiry)
        got = pred.category.strip().lower()
        want = ex.category.strip().lower()
        if got != want:
            suspects.append({"inquiry": ex.inquiry, "label": want, "model": got})

    with open(out_path, "w", encoding="utf-8", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=["inquiry", "label", "model"])
        writer.writeheader()
        writer.writerows(suspects)

    print(f"食い違い {len(suspects)} / {len(examples)} 件 → {out_path}")
    return suspects

# 使い方: 素の Predict で監査してから、直したラベルで compile する
# audit_labels(dspy.Predict(ClassifyInquiry), trainset)
```

出力された CSV を開くと、食い違いの正体は大きく三つに分かれます。モデルの誤り、ラベルの誤り、そして「どちらとも言える曖昧な文面」です。三つ目が多いなら、問題はプロンプトではなくカテゴリの定義にあります。**最適化の前に、定義を一行直すほうが、探索を百回回すより効く**ことは珍しくありません。

あわせて、Gemini の Safety Filter が一部の訓練例をブロックしていないかも、この監査で見えてきます。ブロックされた例は Optimizer に「失敗」として扱われ、重要なパターンが学習から落ちます。ブロックの扱いは、[Gemini API のセーフティ設定を本番で重ねて設計する方法](/articles/gemini-api/gemini-api-safety-settings-production-layered-design)にまとめてありますので、食い違いが特定のカテゴリに偏っていたときの手がかりにしてください。

## コンパイル 1 回の費用を、実測で見積もる

DSPy の Optimizer は、想像以上に API を叩きます。導入を決める前に「一回の `compile` で何回呼ばれ、何トークン流れるか」を知っておきたいところです。机上の見積もりより、実際に一度回して数えるのが確実です。

DSPy の `LM` は呼び出しの履歴を `history` に残します。`compile` の前後で長さの差を取れば、呼び出し回数が分かります。

```python
# budget_probe.py — compile 1 回ぶんの呼び出し数とトークン数を実測する
import dspy

# 単価は必ず公式の料金表を見て、自分で入れてください（ここには数字を置きません）
PRICE_IN_PER_MTOK = 0.0   # 入力 100 万トークンあたり
PRICE_OUT_PER_MTOK = 0.0  # 出力 100 万トークンあたり

def probe_compile(optimizer, student, trainset, lms, **kwargs):
    """lms: 最適化に関わる LM（タスク用と、指示文提案用など）のリスト"""
    marks = [len(lm.history) for lm in lms]
    compiled = optimizer.compile(student=student, trainset=trainset, **kwargs)

    calls = tok_in = tok_out = 0
    for lm, start in zip(lms, marks):
        for h in lm.history[start:]:
            usage = h.get("usage") or {}
            calls += 1
            tok_in += usage.get("prompt_tokens", 0)
            tok_out += usage.get("completion_tokens", 0)

    cost = tok_in / 1e6 * PRICE_IN_PER_MTOK + tok_out / 1e6 * PRICE_OUT_PER_MTOK
    print(f"calls={calls}  in={tok_in:,} tok  out={tok_out:,} tok  est_cost={cost:.4f}（単価の通貨単位）")
    return compiled
```

使うときの注意点が二つあります。一つは、`MIPROv2` のように指示文の提案用モデルを別にしている場合、その LM の履歴も `lms` に入れて合算することです。もう一つは、履歴の保持件数には上限があるため、大きな最適化では `dspy.settings` の関連設定を確認しておくことです。キャッシュが効いた呼び出しは記録のされ方が変わる場合がありますので、費用の見積もりに使う実走は `cache=False` で行うと、数字が素直に読めます。

この数字を取っておくと、判断が具体的になります。開発中は 20〜30 件程度の小さなデータで素早く回し、本番前に全データで一度だけ重い設定を走らせます。コストを下げたいときは、探索ループだけ軽いモデルで回し、本番の推論モデルは別に選びます。通常より割安なバッチ処理が使える場面もあります（割引率は公式の料金表で確かめてください）。

トークン数の事前チェックを運用に組み込む方法は、[Gemini の countTokens でバッチ予算を門番にする設計](/articles/gemini-api/gemini-counttokens-batch-budget-gate-model-swap)が参考になります。

## 通して動かす: 実データでの最適化と検証

ここまでの部品を、実データに当てる一本のスクリプトにまとめます。想定は、手元にあるサポートログを訓練・検証・テストに分け、ベースラインと最適化後を同じテストで比べる流れです。

```python
# production_pipeline.py — 実データで最適化し、未見のテストセットで評価する
import json
import os
import random
import dspy
from dotenv import load_dotenv
from dspy.teleprompt import MIPROv2

load_dotenv()
random.seed(42)

lm = dspy.LM(
    model=os.environ["GEMINI_FAST_MODEL"],
    api_key=os.environ["GEMINI_API_KEY"],
    temperature=0.0,
    max_tokens=256,
)
dspy.configure(lm=lm)

class ClassifyInquiry(dspy.Signature):
    """ユーザー問い合わせを payment / bug / feature / other のいずれかに分類する。"""
    inquiry: str = dspy.InputField()
    category: str = dspy.OutputField(desc="payment, bug, feature, other のいずれか")

# support_logs.json: [{"text": "...", "label": "bug"}, ...] を想定
with open("support_logs.json", encoding="utf-8") as f:
    raw = json.load(f)

examples = [
    dspy.Example(inquiry=r["text"], category=r["label"]).with_inputs("inquiry")
    for r in raw
]
random.shuffle(examples)

# 7:2:1 に分割（train / val / test）
n = len(examples)
trainset = examples[: int(n * 0.7)]
valset = examples[int(n * 0.7) : int(n * 0.9)]
testset = examples[int(n * 0.9) :]

def exact_match(example, pred, trace=None):
    return pred.category.strip().lower() == example.category.strip().lower()

def accuracy(program, dataset):
    hits = sum(1 for e in dataset if exact_match(e, program(inquiry=e.inquiry)))
    return hits / len(dataset)

# 1) ベースライン（最適化なし）
baseline = dspy.Predict(ClassifyInquiry)
print(f"baseline  : {accuracy(baseline, testset):.3f}")

# 2) 最適化
optimizer = MIPROv2(metric=exact_match, auto="light", num_threads=4)
compiled = optimizer.compile(
    student=dspy.Predict(ClassifyInquiry),
    trainset=trainset,
    valset=valset,
    requires_permission_to_run=False,
)

# 3) 未見のテストセットで評価（ここだけが「本当の成績」です）
print(f"optimized : {accuracy(compiled, testset):.3f}")

compiled.save("inquiry_classifier_v1.json")
```

出力される二つの数字は、あなたのデータで出た値がすべてです。他人のデータで出た改善幅は、期待値としては参考になっても、約束にはなりません。**本当の成績は、最適化に一度も触れさせていないテストセットでだけ測ります。** この一点を守るだけで、数字への信頼が大きく変わります。

## 踏みやすい落とし穴

私が実際に足を取られた順に、書き残します。

**落とし穴 1: Optimizer が走り切らずに、呼び出しだけが消える**

`MIPROv2` は内部で多くの推論を行うため、途中で `429 Resource Exhausted` が返ると、そこまでの進捗が失われることがあります。レート制限の余裕があるプロジェクトのキーを使い、`num_threads` は控えめ（4 前後）に始めるのが無難です。上げすぎると、すぐ制限に当たります。

**落とし穴 2: 評価関数が緩く、何を最適化したのか分からない**

「キーワードが含まれていれば 1」程度の評価関数でも、DSPy は「最適化しました」と言います。ただしそれは、あなたが指定した目的を満たしただけで、実際の使い心地とは別物です。完全一致に加えて、文字数の制約や禁止語のチェックを合成し、結果を数十件は自分の目で読んでください。

**落とし穴 3: `compile` のあとに Signature を変えて、例が壊れる**

保存した JSON の Few-shot 例は、当時の Signature と紐づいています。フィールド名や型を変えると、読み込み時にエラーになるか、最悪の場合は黙って無視されます。Signature を触ったら `compile` をやり直し、`compiled_classifier_v2.json` のようにファイル名で版を分けておくと、取り違えを防げます。

**落とし穴 4: Structured Output が思ったほど厳密ではない**

LiteLLM 経由で Gemini を呼ぶと、`score: int` と宣言しても `"4.0"` のような小数文字列が返ることがあります。評価関数の中で `int(float(x))` と二段階でキャストするか、docstring に「小数は使わない」と明記すると防げます。スキーマ検証まわりの考え方は、[Gemini API の構造化出力でスキーマ検証が通らないときの直し方](/articles/gemini-api/gemini-api-structured-output-schema-validation-fix)に詳しく書きました。

**落とし穴 5: Few-shot の並び順を侮る**

英語のベンチマークでは順序の影響は小さいと言われがちですが、日本語の分類タスクでは、並び順で結果が変わる場面があると感じています。私は数字で断言できるほどの検証をしていませんので、ここは「あなたのデータで確かめてください」としか言えません。DSPy の既定はランダム順です。`max_bootstrapped_demos` を増やしすぎると順序の影響を受けやすくなるため、まず少なめ（3〜5 件）から始めて、順序を入れ替えた複数の `compile` を比べると、依存の度合いが見えてきます。

## 本番に載せるための三つの工夫

手元で動くことと、本番で回り続けることは別物です。最後に、運用で効いた工夫を三つ書きます。

**工夫 1: `compiled_*.json` を Git で管理する**

`save()` が出力するのは素の JSON で、指示文と Few-shot 例が人間に読める形で入っています。`prompts/` ディレクトリに置いて通常の PR フローに乗せれば、「誰が、どのデータで最適化したか」がコミットログに残ります。本番で精度が落ちたときも、前の版へ戻すのは一手で済みます。

さらに、PR に「最適化前後のテスト精度」を自動で書き込む仕組みがあると、レビューが一気に楽になります。差分が小さければそのまま通し、大きく動いたときだけ人間が読む、という運用です。プロンプトの変更が数字で見えるので、再最適化を怖がらずに頻繁に回せます。

**工夫 2: 最適化と推論でモデルを分け、最終確認は推論モデルで行う**

最適化の探索は軽いモデルで回し、本番の推論は別のモデルで行う構成が費用対効果に優れます。ただし、モデルが違えば精度も多少動きます。デプロイの前に、**本番で使うモデルでテストセットを評価し直す**一手間は省かないでください。

**工夫 3: 定期的に再コンパイルし、閾値を割ったら知らせる**

ユーザーの問い合わせは、時間とともに変わります。数か月前に最適だった結果が、いまも最適とは限りません。スケジュール実行で再最適化のジョブを組み、テスト精度が自分で決めた閾値を下回ったら通知が飛ぶようにしておくと、プロンプトを「書き続ける」仕事が「見張る」仕事に変わります。

ディレクトリは、本番コードの `app/`、版管理した `prompts/`、ラベル済みの `training_data/`、再最適化ジョブの定義、という分け方に落ち着きました。DSPy のコード自体は小さくても、このメタデータをどれだけ丁寧に扱えるかで、運用の品質が決まります。

回帰テストの組み方は、[Gemini API プロンプト回帰テストを Pytest で回すガイド](/articles/gemini-api/gemini-api-prompt-regression-testing-pytest-guide)に、アーキテクチャ全般は[Gemini API 本番アーキテクチャパターン集 2026](/articles/gemini-advanced/gemini-api-production-architecture-patterns-2026)にまとめてあります。チームに展開する前に目を通していただくと、設計判断が早くなります。

## 導入の順序 — 今日から始めるなら

「自分のプロジェクトにも入れたい」と思われた方のために、順序を書いておきます。ここを間違えると、DSPy の恩恵を感じる前に力尽きてしまいます。

1. **手戻りがいちばん多いプロンプトを一つ選ぶ**。分類・抽出・整形のように、正解がはっきりしているものが向いています
2. **評価用のデータを 30〜50 件ラベル付けする**。ここは人間の仕事で、妥協すると後の質に響きます
3. **ラベル監査を回す**。素の `Predict` と食い違う行を読み直し、定義と誤りを直します
4. **既存のプロンプトを Signature に移し、ベースラインを測る**。Few-shot なしの `Predict` のままです
5. **`BootstrapFewShot` を一度だけ回す**。多くの場合、ここで手応えが出ます
6. **届かなければ `MIPROv2`**。それでも届かないなら、疑うのは Signature の設計か評価関数です
7. **本番に載せ、再コンパイルのジョブを組む**

最初の一つは、評価を数値にしやすいタスクから選ぶのが安全です。創作性の高い長文生成は、評価関数の設計だけで時間を使い切って、挫折しやすいためです。

DSPy に切り替えて、いちばん変わったのは、「もう少し工夫すれば上がるはず」という終わりのない磨き込みから離れられたことでした。評価関数とデータさえ手元にあれば、探索は機械が引き受けてくれます。人間は、何を良しとするかの設計に集中できます。

もしいま、Gemini API を使ったプロダクトのプロンプトを週末ごとに微調整しているなら、今夜のうちに 50 件だけラベル付きデータを用意して、ラベル監査と `BootstrapFewShot` を一度ずつ走らせてみていただければと思います。その結果を読み終えたとき、次の週末の使い方が変わっているはずです。
