「質問はちゃんと伝えているはずなのに、Gemini の回答が毎回ズレている気がする」— 個人アプリ開発の合間に Gemini をほぼ毎日触っていて、この感覚には何度もぶつかってきました。プロンプトを長くしても短くしても、どこか噛み合いません。原因はプロンプトの内容ではなく、プロンプトの「型」にあることが多いのです。

Gemini の出力が意図からズレるときに私がまず試している4つの型を順番にご紹介します。どれもコピー&ペーストで試せる軽量なテクニックで、System Instructions や Few-shot のような本格的な設計の手前で効いてくれるものばかりです。

## なぜプロンプトの「型」が重要なのか

Gemini に限らず、大規模言語モデルは入力された文章の構造を手がかりに「何をどう答えるべきか」を判断します。内容は同じでも、並び順や見せ方が違うだけで応答の焦点がずれます。私の経験上、出力のブレの7割くらいはこの構造起因です。

たとえば「この商品レビューを要約して、良い点と悪い点に分けて箇条書きにしてください」という依頼も、次のように書き換えるだけで出力の安定性がまったく変わります。

- 目的を先に言う
- 出力フォーマットを見せる
- 処理手順を分解する
- 肯定形で書く

この4つが、今日紹介する型の骨格です。

## 型1: 役割と目的を最初に宣言する

出力が散らかる・脱線するときにまず効くのが、「誰として、何のために、誰に向けて」を最初に言い切る型です。冒頭の1〜2行で宣言するだけで、Gemini の応答のトーンと粒度が明確に変わります。

```text
あなたはモバイルアプリのグロースハッカーです。
このアプリのユーザーレビュー10件を読み、
個人開発者が「次の1スプリントで着手すべき改善」を決められるように、
優先度付きで要約してください。
```

同じ要約依頼でも、ただ「要約してください」と書くのに比べて、出力は「個人開発者が意思決定に使える情報」に寄ってきます。重要なのは、**役割（who）・目的（why）・読者（for whom）の3点セット**を必ず書くことです。どれか1つでも抜けると、途端にぼんやりした一般論に戻ります。

私は個人開発の収益化に関する相談を Gemini にするとき、必ず冒頭に「あなたは個人開発アプリのマネタイズに詳しいアドバイザーです」と宣言するようにしています。この一行があるかないかで、体感ではアウトプットの使える率が2〜3倍変わります。

### よくある落とし穴

役割を宣言するとき、つい「あなたはプロのライターです」「あなたは優秀なエンジニアです」のような曖昧な肩書きを書きがちですが、これはあまり効きません。**肩書きは具体的な専門領域まで落とし込む**ことが大事です。「プロのライター」より「医療系ウェブ記事の編集経験が10年ある編集者」と書くほうが、出力がはっきり変わります。

## 型2: 出力フォーマットを先に見せる

「箇条書きで」「表形式で」「200字程度で」といった指定をしても、Gemini が思い通りのレイアウトで返してくれないことがあります。そういうときは文章で指示するのではなく、**望む出力の雛形を直接見せる型**に切り替えます。

```text
次のコードレビュー結果を、以下のフォーマットで出力してください。

## 発見した問題
- **問題1**: [問題の1行サマリー]
  - 該当箇所: [ファイル名:行番号]
  - 改善案: [具体的な修正方針]

## 発見した問題
- **問題2**: ...
```

雛形を見せるだけで、Gemini は「ああ、このスキーマに当てはめればいいんだな」と理解して、指定通りの構造で応答してくれます。Few-shot プロンプティングの軽量版と考えてよく、例を2件も3件も並べる必要はありません。

### どこまで具体的に書くべきか

雛形はある程度「中身が分かる」レベルで書きます。プレースホルダーを `[...]` で囲むこと、セクション見出しを Markdown にすること、項目の階層をインデントで明示することがコツです。一方で、実在の値までは書かない（書くと Gemini がその値に引っ張られて、内容が歪むことがあります）。

より詳しいプロンプト技法については [Gemini プロンプトエンジニアリング入門](/articles/gemini-basics/gemini-prompt-engineering-guide) も参考になります。System Instructions や Few-shot の使い分けについて解説しています。

## 型3: 思考ステップを明示的に分解する

複雑な依頼を1つのプロンプトに詰め込むと、Gemini は「全部それなりにやる」に寄り、結果としてどれも中途半端になりがちです。そんなときは**処理の手順を Gemini 側に分解させる**のではなく、こちらで分解してから渡します。

```text
次の営業日報のテキストを処理してください。
処理は3ステップで行います。

ステップ1: 本文から「顧客名」「訪問日」「次回アクション」を抽出する
ステップ2: 次回アクションを「今週中」「今月中」「それ以降」の3つに分類する
ステップ3: ステップ2の結果を表形式で出力する（列: 顧客名 / 次回アクション / 緊急度）

---
[ここに日報本文]
```

このように手順を1・2・3と明示すると、Gemini は手順ごとに思考を整理して応答するので、抜け漏れが劇的に減ります。Chain-of-Thought（思考の連鎖）を外側から設計してあげるイメージです。

私はよく、議事録の要約やアプリのレビュー分析でこの型を使います。「重要なポイントを要約してください」とだけ書くと観点がブレるので、「① 事実を抽出 → ② カテゴリ分け → ③ 優先度付き出力」のように分解しておくと、毎回ほぼ同じ品質の結果が返ってきます。

### ステップは3つ以内に絞る

手順が4つ以上になると、今度は Gemini が途中のステップを省略したり、順序を入れ替えたりすることがあります。ステップを増やしたくなったら、そもそも2〜3回に分けてプロンプトを送ることを検討しましょう。1つの巨大なプロンプトより、短い対話を積み重ねるほうが結果的に精度が高くなる場面は多いです。

## 型4: 否定形ではなく肯定形で指示する

これは意外と見落とされがちですが、効果が大きい型です。「〜しないでください」「〜は避けてください」という否定の指示は、Gemini に対してはあまり強く働きません。代わりに**「〜してください」の肯定形**で同じことを伝えると、従ってくれる確率が上がります。

```text
❌ 否定形:
  専門用語は使わないでください。
  長すぎる文章は避けてください。
  主観的な意見を書かないでください。

✅ 肯定形:
  小学生にも分かる日常的な言葉で書いてください。
  各文を60字以内に収めてください。
  事実と数字だけで構成し、「〜である」「〜となっている」で統一してください。
```

否定形の指示は、Gemini に「何をすべきでないか」は伝わっても、「では代わりに何をすべきか」が伝わりません。結果として、禁止事項を避けようとしながら迷走した出力が返ってきがちです。肯定形に書き換えるとき、**「代わりに何をすればよいか」を明確にする**ことが鍵になります。

私は納品原稿のチェックを Gemini に依頼するとき、「読みにくくしないで」ではなく「漢字とひらがなの比率を6:4に、1文を平均40字以内にしてください」と具体的な目標値を書くようにしています。このほうが、Gemini の応答が定量的で再現しやすいものになります。

## どの型から試すか — 症状別の選び方

4つの型を紹介しましたが、どれから試せばいいのか迷うときは、出力の「どこが残念か」で選び分けられます。

- **出力が一般論っぽくて使えない** → 型1（役割と目的の宣言）
- **出力の形がバラバラで後処理が大変** → 型2（雛形を見せる）
- **複雑な依頼で抜け漏れが多い** → 型3（ステップ分解）
- **指示したことと逆のことをされる** → 型4（肯定形に変換）

実際には複数の型を組み合わせて使うのが基本です。特に、型1（役割宣言）＋ 型2（雛形）の組み合わせは、どんなタスクでもまず効く黄金パターンだと感じています。

API で使うときは、役割宣言を System Instructions 側に分離すると、プロンプト本体がスッキリして保守しやすくなります。この分離設計については [Gemini API のシステム指示とプロンプト設計](/articles/gemini-api/gemini-api-system-instruction-prompt-engineering-showcase) で詳しく解説しています。

## 今日から試せる一歩

もし今、手元に「Gemini の出力が微妙だった過去のプロンプト」があれば、まずは型1（役割と目的の宣言）だけを加えて投げ直してみてください。たいていの場合、それだけで応答の方向性がガラッと変わります。

プロンプトの型を意識しはじめると、Gemini は「気難しいツール」から「使いこなせば頼れるパートナー」に変わっていきます。4つの型はそのための足がかりです。まずは今日の1件だけ、型1を試してみることから始めてみてください。
