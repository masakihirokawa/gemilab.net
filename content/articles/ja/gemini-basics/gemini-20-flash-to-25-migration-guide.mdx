Gemini 2.0 Flash で動いているコードを 2.5 系に上げる作業は、ぱっと見はモデル名を書き換えるだけのタスクに見えます。ですが、実際に移行を進めてみると、パラメータの挙動が微妙に違ったり、プロンプトへの応答の癖が変わっていたりと、地味に引っかかるポイントがいくつか出てきます。

ここでは私が 2.0 Flash から 2.5 Pro / 2.5 Flash に移行する際にチェックしている 6 つのポイントをまとめました。過剰な書き直しを避けつつ、移行後の挙動を安定させることを目的にしています。

2014年からアプリ事業を続けている個人開発者の経験から、この問題に普段から向き合ってきた立場で、要点を整理します。

## ポイント1：モデル名の変更だけで終わらない

まず、最も基本的な部分です。モデル識別子は `gemini-2.0-flash` から `gemini-2.5-flash` または `gemini-2.5-pro` に変わります。Pro と Flash は目的が違うので、移行先の選び方には注意が必要です。

- **コスト重視・応答速度重視**：`gemini-2.5-flash` を選ぶ
- **推論深度・長文読解重視**：`gemini-2.5-pro` を選ぶ

Flash から Flash への移行は連続的ですが、Flash から Pro への移行は「別のモデルに乗り換える」くらいの気持ちで挑んだ方が安全です。トークン単価も応答時間も Pro は別物なので、ここで設計ごと見直す機会として捉えるのが良いでしょう。

私は移行時、いったん Flash から Flash に置き換えて動作確認し、その後に Pro 化する価値があるエンドポイントだけを切り分けて Pro に差し替える、という段階踏みをよくやります。一度に全部やると、どのモデル差が原因で挙動が変わったか判別しにくくなります。

## ポイント2：temperature の感覚が変わる

2.5 系は、同じ temperature 値でも出力の幅が 2.0 Flash とは違います。私が体感している違いは次のとおりです。

- **temperature=0.0** での再現性はどちらも高いが、2.5 の方が一貫性が若干高く感じる
- **temperature=0.7** あたりでは、2.0 Flash の方が出力が荒く、2.5 の方が整った文章を返す
- **temperature=1.0** 近辺は両者で挙動が大きく違い、2.5 の方が「創造的になりすぎない」傾向

要するに、2.5 の方がやや保守的で安定した出力になるので、2.0 Flash で多様性を出すために `temperature=0.9` にしていたようなケースでは、2.5 では少し物足りなく感じることがあります。その場合は同じ値でも感触が変わると覚えておき、用途に応じて再調整してください。

```python
from google import genai
from google.genai import types

client = genai.Client()

# 2.0 Flash 時代のコード
response = client.models.generate_content(
    model="gemini-2.0-flash",
    contents=prompt,
    config=types.GenerateContentConfig(temperature=0.9),
)

# 2.5 Flash に移行
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=prompt,
    config=types.GenerateContentConfig(
        temperature=0.9,
        # 必要なら top_p や top_k で多様性を補強
        top_p=0.95,
    ),
)
```

本番投入前に、主要な evaluation プロンプトで temperature ごとの出力感を A/B で比較しておくと安心です。

## ポイント3：システム指示の置き場所を見直す

2.0 Flash の時代、システム指示を `contents` の最初に入れて動かしている実装をよく見ます。動作はしますが、2.5 系では `system_instruction` を明示的に使う方が応答が安定します。

```python
# 推奨される 2.5 の書き方
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=user_message,
    config=types.GenerateContentConfig(
        system_instruction="あなたは丁寧な日本語で回答するアシスタントです。敬体を使ってください。",
        temperature=0.2,
    ),
)
```

私の実感では、`system_instruction` を使った方が、複数ターンの会話で指示が薄まりにくいです。特に「敬体で回答」「特定のフォーマットで返す」のような挙動の指示は、`system_instruction` に書いた方が持続します。

2.0 Flash 時代のコードで `contents[0]` にシステム指示が混ざっている場合、移行の機会にきれいに分離しておくと、後々のメンテナンス性も上がります。

## ポイント4：JSON モードの指定方法とスキーマ

2.0 Flash で JSON 出力を使っていた場合、`response_mime_type="application/json"` の指定自体は 2.5 でも同じです。ただし、`response_schema` を使った厳密なスキーマ指定の扱いが、2.5 では一段安定するようになっています。

2.0 Flash では、`response_schema` を指定してもたまにフィールドが欠けた JSON が返ってきたり、リスト型が単一オブジェクトとして返ってきたりする事故がありました。2.5 系ではこの揺れがかなり減っています。

```python
from pydantic import BaseModel
from typing import Literal

class Task(BaseModel):
    title: str
    priority: Literal["low", "medium", "high"]
    estimated_hours: float

class TaskList(BaseModel):
    tasks: list[Task]

response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="次のプロジェクト概要からタスクを抽出して JSON で返してください。...",
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=TaskList,
        temperature=0.0,
    ),
)

tasks = response.parsed  # TaskList のインスタンスとして取得
```

移行時は、2.0 Flash で回避していた「たまに壊れた JSON が来る」対策のリトライコードを、2.5 移行後に見直す価値があります。そのまま残しておいても害はありませんが、発火頻度がかなり下がっているので、アラート閾値などは再調整すると気付きやすくなります。

## ポイント5：長文入力の扱いと max_output_tokens

2.0 Flash から 2.5 に移行する大きなメリットのひとつが、長文入力への強さです。2.5 系は 1M トークン級のコンテキストを扱えるので、2.0 Flash で分割送信していた処理をシンプルに書き直せる可能性があります。

ただし、ここで注意したいのが `max_output_tokens` です。入力は長く受け取れるようになっても、出力側の上限は別で決まります。2.0 Flash 時代にデフォルト値のまま運用していた場合、2.5 で長文を投げると、応答が途中で切れて終わることが増えます。

```python
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=very_long_document,
    config=types.GenerateContentConfig(
        max_output_tokens=8192,  # 明示的に長めに取る
        temperature=0.2,
    ),
)
```

用途が長文応答なら、`max_output_tokens` を明示的に 8,192 や 16,384 に引き上げるのを忘れないでください。デフォルト値任せにしていると、Pro の能力を生かしきれません。

## ポイント6：ストリーミング応答の切り替え挙動

ストリーミング応答を使っている場合、2.0 Flash から 2.5 への移行でチャンクの粒度が変わります。2.5 は一度に送ってくるチャンクが少し大きめになる傾向があり、UI 側で文字単位に滑らかに表示している実装だと、多少カクついて見えることがあります。

```python
# ストリーミングの基本は同じ
stream = client.models.generate_content_stream(
    model="gemini-2.5-flash",
    contents=prompt,
)

for chunk in stream:
    if chunk.text:
        # UI 側に流す
        display(chunk.text)
```

気になる場合、受け取ったチャンクを文字単位に分解して擬似的な typewriter 効果を作る、もしくはチャンクのまま表示する割り切りをするか、どちらかに寄せる必要があります。この選択は UX 方針なので、移行を機にチーム内で一度議論しておくとすっきりします。

## ミニマル移行チェックリスト

コード変更の最短ルートとして、私が自分のプロジェクトで使っているチェックリストを共有します。

- モデル識別子を差し替える（Flash → Flash か、Pro に上げるか決める）
- `temperature` の挙動変化を evaluation プロンプトで確認する
- システム指示を `system_instruction` に寄せる
- `response_schema` 使用箇所で、事後リトライの閾値を緩める
- 長文入力を使うなら `max_output_tokens` を明示的に上げる
- ストリーミング表示の見え方を UI 側で確認する

このチェックをひと通り回せば、ほとんどのケースで安全に移行できます。大規模な書き換えは不要で、設定値のチューニングと、呼び出し側の癖の見直しが中心になります。

## 移行後に効果を実感できるポイント

最後に、移行するとどこで嬉しさを感じるかという視点での感想を。私の実務では、2.0 Flash から 2.5 Flash への移行で、特に「指示への追従性」と「JSON 出力の安定性」が改善したと感じました。複雑なシステム指示を書いた時の応答の質が、明らかに一段上がります。

一方、単純な短文生成の速度は Flash 同士でも体感差があまり出ません。速さを求めて Flash を選んでいるなら、2.5 Flash は「ほぼ同じ速さで質が上がった」という感触です。コスト面でも、2.5 Flash は 2.0 Flash に対してバランスがよく、実質的に移行しないメリットがあまりない印象です。

まずは Flash 同士の差し替えから始めて、必要に応じて Pro を局所的に導入していく、というのが私が勧める進め方です。今日からコード 1 行の置き換えで始められますので、試してみてください。
