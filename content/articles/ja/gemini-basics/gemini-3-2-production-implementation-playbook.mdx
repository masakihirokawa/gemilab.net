壁紙アプリのレビュー分類を Gemini に任せ始めた週に、私は請求画面を見て手が止まりました。動作確認のつもりで回したバッチが、すべて Pro で走っていたのです。コードは正しく動いていました。間違っていたのは、モデルの選び方でした。

機能の紹介記事は数多くあります。一方で、実際のアプリに組み込んで毎日回し続けるときの判断は、ドキュメントを読むだけでは見えにくいものでした。これから、私が遠回りしながら引いてきた線を、モデル選定・実装・コスト・監視の順にお伝えしてまいります。

## 3.2 を使い分け前提のモデル群として捉える

最初にお伝えしたいのは、Pro・Flash・Nano は「性能の上下」ではなく「役割の違い」として扱うほうが、運用がはるかに楽になるということです。

Pro は深い推論と長い文脈、Flash は速さと低コストの汎用処理、Nano は端末内で完結させたい処理を受け持ちます。1 つのモデルで全部を賄おうとすると、コストかレイテンシのどちらかが先に音を上げます。私は最初、Pro 1 本で組んで、請求画面の前で固まりました。

なお、世代間の細かな改善幅（Function Calling の安定性やトークン消費の変化など）は、リリースノートの記述を鵜呑みにせず、自分のプロンプトと自分の画像で一度測っておくのが安全です。私の環境の数字は、皆さまの環境にそのまま当てはまるとは限りません。

## モデル選定を 3 つの問いに落とす

迷ったときは、次の 3 つを順に自問します。

1 つ目は、出力がそのままユーザーの目に触れるかどうかです。触れるなら Pro を候補にし、要約・分類・抽出のような内部処理なら Flash で足りることがほとんどでした。端末内で完結させたい処理だけが Nano の出番です。

2 つ目は、待てる時間です。1 秒以内に返したいなら Flash、数秒待てるなら Pro も選べます。

3 つ目は、月額の上限に対する感度です。上限が厳しいなら Flash を既定にして、必要な場面だけ Pro に上げます。

私の手元での割り当ては、次のようになっています。

- レビューや問い合わせの分類（バッチ）— Flash
- アプリ内のチャット（リアルタイム）— Flash を既定に、難しい質問だけ Pro へ
- 深い推論を要する長い文章の下書き — Pro
- オフラインでの簡単な補助 — Nano

この 3 問を通すと、新しい用途でも判断が機械的に決まります。

## モデル名はコードに直書きしない

ここで、一つ失敗をお話しします。

最初の実装では、`gemini-3.2-flash` のようなモデル名を、呼び出し箇所のあちこちに直書きしていました。世代が変わった週、置換漏れが見つかり、一部のバッチだけが古いモデルで動き続けていました。

それ以来、モデル名は設定の 1 か所に集めています。

```typescript
// models.ts — モデル名はここだけで管理する
export const MODELS = {
  fast: process.env.GEMINI_MODEL_FAST ?? 'gemini-3.2-flash',
  deep: process.env.GEMINI_MODEL_DEEP ?? 'gemini-3.2-pro',
} as const;
```

呼び出し側は `MODELS.fast` と書くだけにします。世代交代も、環境変数の差し替えで済みます。

## ストリーミング実装

リアルタイムに返したい経路は、ほぼすべてストリーミングで組みます。基本形は次のとおりです。

```typescript
import { GoogleGenerativeAI } from '@google/generative-ai';
import { MODELS } from './models';

const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);

async function streamResponse(userPrompt: string): Promise<void> {
  const model = genAI.getGenerativeModel({ model: MODELS.fast });
  const result = await model.generateContentStream(userPrompt);

  for await (const chunk of result.stream) {
    process.stdout.write(chunk.text());
  }
}
```

本番では、ここに 3 つを足します。

- タイムアウト: 30 秒ほど出力が止まったら打ち切ります。待ち続ける事故を防ぐためです。
- バッファリング: 1 文字ずつ送らず、数百ミリ秒ごとにまとめてクライアントへ送ります。
- 使用量の記録: 完了後に `usageMetadata` を読み、トークン消費をログに残します。

3 つ目は地味ですが、後のコスト調整の根拠になります。記録がない状態では、どこを削ればよいのかも分かりません。

## Function Calling の実装

外部の関数を呼ばせる構造は、次の形です。

```typescript
const model = genAI.getGenerativeModel({
  model: MODELS.deep,
  tools: [{
    functionDeclarations: [{
      name: 'searchReviews',
      description: 'アプリのレビューから関連するものを検索する',
      parameters: {
        type: 'object',
        properties: {
          query: { type: 'string', description: '検索クエリ' },
          limit: { type: 'number', description: '取得件数（最大10）' },
        },
        required: ['query'],
      },
    }],
  }],
});

const chat = model.startChat();
const result = await chat.sendMessage('直近の「通知が来ない」というレビューを3件');

const functionCall = result.response.candidates?.[0]?.content?.parts?.[0]?.functionCall;
if (functionCall) {
  const args = functionCall.args as { query: string; limit?: number };
  const reviews = await searchReviews(args.query, args.limit ?? 3);

  const followup = await chat.sendMessage([{
    functionResponse: { name: 'searchReviews', response: { reviews } },
  }]);
  console.log(followup.response.text());
}
```

運用で守っている線は 3 つあります。

1 つ目は、最小権限です。モデルが呼べる関数は、読み取り専用と書き込み可能を分け、書き込みには必ず人の確認を挟みます。

2 つ目は、呼び出し回数の上限です。1 セッションで関数を呼び続けてしまう場合に備え、10 回前後でハードリミットをかけます。

3 つ目は、戻り値の扱いです。外部から取り込んだ文字列に指示文のようなものが紛れていると、モデルがそれに従ってしまうことがあります。戻り値は「データ」として渡し、長さと形式を絞ってから返します。

**モデルが決めるのは次の一手まで、実行する権限は私の側に残しておきます。** この線は、設計がどれだけ複雑になっても崩さないようにしています。

## マルチモーダル入力の下ごしらえ

画像や PDF を直接渡せるのは大きな強みです。ただし、そのまま送ると請求に響きます。

```typescript
import * as fs from 'fs';

async function analyzeImage(imagePath: string, question: string): Promise<string> {
  const model = genAI.getGenerativeModel({ model: MODELS.deep });
  const imagePart = {
    inlineData: {
      data: fs.readFileSync(imagePath).toString('base64'),
      mimeType: 'image/jpeg',
    },
  };
  const result = await model.generateContent([question, imagePart]);
  return result.response.text();
}
```

本番に持っていく前に、次の 3 点を見直します。

- 事前の縮小: 大きな画像はトークン消費を押し上げます。Sharp などで長辺を縮めてから送ります。
- 動画は全部送らない: 場面が変わる箇所の代表フレームだけを抜き出します。
- PDF の読み取り結果は検算する: レイアウトが特殊な PDF では取り違えが起きます。金額や日付のように間違えると困る項目は、別の手段で突き合わせます。

壁紙アプリで画像を扱っていると、画質を落としすぎて判定がぶれる場面にも出会います。縮小は「どこまで落としても答えが変わらないか」を一度測ってから決めるのが、結局は近道でした。

## コストを抑える順番

効いた順に並べます。

### まず、モデルの振り分け

入力の長さと質問の種類で、Flash と Pro を自動で振り分けます。

```typescript
function selectModel(userPrompt: string): string {
  const tokens = estimateTokens(userPrompt);
  const needsReasoning = /比較|分析|なぜ|どう違う/.test(userPrompt);
  return tokens > 4000 || needsReasoning ? MODELS.deep : MODELS.fast;
}
```

正規表現による判定は粗いものです。それでも、全件 Pro で回していた時期に比べて、月の請求は目に見えて下がりました。削減幅は用途で大きく変わりますので、まずは自分の使用量ログで比べてみていただければと思います。

### 次に、同じ質問の再利用

似た質問が繰り返される用途では、過去の応答を使い回します。Embedding で類似度を測り、閾値を超えたら再利用する方式です。ただし、元の情報が更新される用途では、保持期間を短く（数時間から 1 日程度）しておかないと、古い答えを返し続けます。

### 最後に、プロンプトの絞り込み

参考情報を多く入れれば答えがよくなる、とは限りません。過去の資料を全文で 20 件渡すより、要約した 5 件を渡したほうが、品質を保ったまま入力を減らせる場面が多くありました。入れるものは、本当に必要なものだけにします。

## 他のモデルとの使い分け

ベンチマークの数字より、自分の用途で試した手触りのほうが当てになります。私の手元での傾向は次のとおりです。

- Gemini: 長い文脈の読み込み、画像や PDF をまとめて扱う処理、多言語の翻訳
- Claude: 長文の構造化、既存コードの読解と説明
- 他社モデル: エージェント的な複雑なタスクで、状況に応じた試用

文章まわりは Claude、画像解析と多言語処理は Gemini、という棲み分けで、両方を残したまま使っています。どれか一つに寄せるより、役割で分けたほうが、請求と品質のどちらも落ち着きました。

## 組み込み事例 — レビューの自動分類

アプリのレビューに、種類のラベルを付ける処理を Flash に任せています。要点は、出力を JSON に固定したことです。

```typescript
const model = genAI.getGenerativeModel({
  model: MODELS.fast,
  generationConfig: {
    responseMimeType: 'application/json',
    responseSchema: {
      type: 'object',
      properties: {
        kind: { type: 'string', enum: ['bug', 'request', 'praise', 'other'] },
        topics: { type: 'array', items: { type: 'string' }, maxItems: 5 },
        confidence: { type: 'number', minimum: 0, maximum: 1 },
      },
      required: ['kind', 'topics', 'confidence'],
    },
  },
});

const result = await model.generateContent(`次のレビューを分類してください:\n\n${reviewText}`);
const classification = JSON.parse(result.response.text());
```

`confidence` が 0.7 を下回ったものは、私が目で確認する列に回します。自動で済ませる部分と、自分で見る部分を分けておくと、分類を信用しすぎずに済みました。

## エラーとリトライ

本番では、一定の割合でエラーが起きます。再試行してよいものと、してはいけないものを分けます。

```typescript
async function callWithRetry<T>(
  fn: () => Promise<T>,
  maxRetries = 3,
  initialDelay = 1000
): Promise<T> {
  let lastError: unknown;
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await fn();
    } catch (e) {
      lastError = e;
      if (!isRetryableError(e) || i === maxRetries - 1) throw e;
      await new Promise(r => setTimeout(r, initialDelay * 2 ** i));
    }
  }
  throw lastError;
}

function isRetryableError(e: any): boolean {
  const status = e?.status ?? e?.response?.status;
  return [429, 500, 502, 503, 504].includes(status);
}
```

429 と 5xx は指数バックオフで再試行します。それ以外の 4xx は、再試行しても結果が変わらないので、すぐに失敗させます。以前、404（モデル名の誤り）まで再試行していて、ログが同じエラーで埋まったことがありました。

## 監視の優先順位

見る順番を決めておくと、慌てずに済みます。

1. エラー率: 5 分の窓で 5% を超えたら通知します。Google 側のダッシュボードに加えて、アプリ側でも独自に数えます。
2. 平均レイテンシ: Flash で 1 秒超、Pro で 5 秒超が続いたら調査します。
3. 日次のコスト: 前の 7 日の平均を大きく超えた日に、その日のうちに気づけるようにします。
4. 振り分けの比率: Flash と Pro の比率が想定と違うときは、ルーティングの不具合か、入力の傾向が変わっています。
