校正用の Gem に同じ原稿を二度流したら、二度とも直し方が違っていました。一度目は語尾だけを丁寧に揃え、二度目は私が残したかった言い回しまで書き換えていたのです。

指示は 500 字を超えていました。「敬体を使うこと」「冗長な表現を削ること」「一人称で書くこと」と、思いつくたびに足していった結果です。細かく書けば書くほど従ってくれるはずだと、私はそれまで素朴に信じておりました。

その思い込みが外れたと気づいたのは、指示を削った翌日でした。校正 Gem を作り直しながら辿った指示設計の線引きを、順に書き残します。

## 指示を足すほど、Gem は迷いました

最初にお伝えしたいのは、**「何をさせる Gem か」が決まっていない状態で条件を重ねても、応答は定まらない**ということです。

私は 500 字の指示を、思い切って 2 文に絞りました。

```
自然な敬体の日本語ブログ記事として校正してください。
前後の脈絡を大事にし、行き過ぎた修正はしないでください。
```

応答は、その日のうちに安定しました。条件が 10 個並んでいたころ、モデルは「どれを優先するか」を毎回その場で決めていたのだと思います。軸が 1 本になれば、迷う余地が減ります。

もちろん、これは私の校正用途で起きたことです。すべての Gem で 2 文が正解になるわけではありません。ただ、指示が長くなってきたときは、文を足す前に「この Gem の仕事は一言で何か」を問い直すようにしています。

## 効いた指示の 5 つの要素

何度か作り直すうちに、指示は 5 つの要素に分けると診断しやすいと分かりました。

1. **役割（Role）**：「ブログ編集者です」のように、判断の拠りどころになる立場を一つ与えます。
2. **主要タスク（Primary Task）**：「〜を校正してください」と、1 文で言い切れる依頼にします。
3. **制約（Constraints）**：「敬体を保つこと」のように、肯定形で書きます。「〜しないでください」を並べると、避けることばかりが前に出てしまうからです。
4. **出力フォーマット（Output Format）**：「修正前と修正後を並べて示す」「JSON のみ返す」など、答えの形を決めます。
5. **背景（Context）**：「読者は開発経験の浅い方です」のように、何を大事にするかの手がかりを渡します。

全部が必須というわけではありません。応答がぶれたとき、どの要素が欠けているかを確かめる、お品書きのような使い方をしております。

## 役割は「行動の癖」まで書きます

役割定義は、いちばん軽く扱われやすい要素です。かつての私もそうでした。

「あなたはプロンプトエンジニアです」だけでは、何をする人なのかがモデルの解釈に委ねられます。そこで、その役割がどう振る舞うかまで書き添えます。

```
あなたは、曖昧な要望を聞き取るプロンプトエンジニアです。
回答の前に、必ず 3 つの質問で要望を掘り下げます。
最後に「この理解でよろしいですか」と確認します。
```

これで、モデルは「確認を重んじる専門家」という一貫した人物として動きます。肩書きではなく、振る舞いを書く——それが役割定義の勘所でした。

制約が役割とぶつかる場合も同じです。「編集者です。ただし学術的な正確性を損なわないでください」と分けて書くと、二つの要請が引っ張り合います。「学術的な正確性を最優先に、記事を親しみやすく整える編集者です」と役割の中へ織り込むと、迷いが減りました。

## 出力フォーマットがいちばん効きました

5 要素のうち、私がいちばん頻繁に手を入れるのは出力フォーマットです。

入力を分類する Gem を作ったとき、最初は「カテゴリ A・B・C のどれですか」と尋ねるだけでした。返ってくる形が毎回違い、受け取る側の処理が書けません。

```
次の JSON 形式のみで回答します。説明文は付けません。

{
  "category": "A" | "B" | "C",
  "confidence": 0.8,
  "reasoning": "理由を 1 文で"
}
```

形を固定したことで、モデルの判断もぶれにくくなりました。自由度に線を引くと、「どんな形が好まれるか」を探す迷いが消えるのだと感じています。

ここで一つ、失敗も書いておきます。「できれば JSON でお願いします」と、希望の形で書いていた時期がありました。モデルは「別の形でもよいのかもしれない」と受け取り、ときどき文章で返してきます。**必須の形は、必須として書く。** 「次の形式のみで回答します」と言い切るだけで、状況が変わりました。

## 私が踏んだ 3 つの落とし穴

指示が長すぎる、役割と制約が混ざる、出力形式が希望止まり——ここまでで触れた 3 つは、どれも私自身が通った道です。まとめると次のとおりです。

- **指示が長すぎる**：長文の中から「本当に大事なこと」をモデルが選び直す形になり、応答が揺れました。長くなりすぎたら、Gem の設計そのものを見直す合図だと受け止めています。
- **役割と制約の混在**：先ほどの編集者の例のように、役割の中に制約を織り込むと整います。
- **出力形式が希望止まり**：「必ず」「のみ」と言い切ります。

3 つとも、削るか言い切るかで直りました。足して直った記憶は、ほとんどありません。

## 指示が反映されていないと感じたときの確認順

書き換えたのに応答が変わらないとき、私はまず指示の中身を疑いたくなります。けれど、先に確かめるべきは別のところでした。

1. **開いている Gem は本当に直したほうか**。複数の Gem を持っていると、別の Gem で試して「効いていない」と思い込むことがあります。画面上部の Gem 名を、まず見ます。
2. **保存されているか**。編集画面を閉じる前に保存したか、開き直して中身を確かめます。
3. **指示の中身が互いにぶつかっていないか**。「プロっぽく」と「親しみやすく」のように、同時に成り立ちにくい表現が並んでいないか読み返します。
4. **会話側の指示が優先されていないか**。Gem で JSON と決めていても、会話の中で「文章で答えて」と頼めば、そちらに従うことがあります。これは仕様として受け止めています。
5. **文字数に上限がないか**。入力欄には上限があり、数字は更新されることがあります。詰め込みすぎて後半が効かなくなっていないか、画面の表示で確かめます。

ブラウザのキャッシュや別のブラウザでの確認も、最後の手段として試す価値はあります。ただ、私の場合は 1 番と 2 番で済んだことが大半でした。指示を疑うのは、そのあとで遅くありません。

書き直しの目安や症状の見分け方は、別の記事の[Gemini Gems カスタムインストラクションを書き直すべきタイミング](/articles/gemini-basics/gemini-gems-instruction-rewrite-timing-and-symptoms)にまとめております。

## 直すのは 1 回に 1 文だけにします

指示は、書いて終わりではありませんでした。

私は週に一度、運用している Gem の応答ログを読み返します。「この入力のときに外れる」という法則が見えたら、指示に 1 文だけ足します。

校正 Gem では、入力が敬体と常体で混ざっているときに、仕上がりまで混ざる時期がありました。そこで「入力が敬体なら敬体で統一し、常体は直してください」という 1 文を加えたところ、解消しました。

**変更は 1 回に 1 つだけ。** 複数を同時に変えると、どれが効いたのか、どれが悪化させたのかが分からなくなります。変更の直後は応答が少し落ち着かないこともあるので、数日ほど様子を見てから次の 1 文に進みます。この遅さが、結局はいちばん速い道でした。

## 用途別の叩き台

最後に、手を動かすときの叩き台を二つ置きます。そのまま使うのではなく、ご自身の用途に合わせて削っていただければ幸いです。

**校正用**

```
役割：ブログ編集者
タスク：入力された文章を、自然な敬体の日本語に校正します。
制約：筆者の言い回しを残し、行き過ぎた修正はしません。
出力：修正前と修正後を並べ、直した理由を一言ずつ添えます。
背景：読者は開発経験の浅い方です。
```

**分類用**

```
役割：問い合わせの振り分け担当
タスク：入力を A・B・C のいずれかに分類します。
出力：JSON のみ（category / confidence / reasoning）。
```

どちらも、5 要素を 1 行ずつに収めています。長くなってきたら、その行のどれかが二つの仕事を抱えていないかを確かめます。

## 最初の 1 週間にやること

次に Gem を作るときは、5 要素を 1 行ずつ、短く書くところから始めていただければと思います。そして 1 週間後、応答ログを読み返し、外れた箇所に 1 文だけ足します。

**指示は足して育てるものではなく、削って、言い切って、1 文ずつ直すもの。** この線引きだけは、Gem が増えても守るようにしています。
