「Geminiに同じ質問をしても、人によって返ってくる答えの質が違う」——この感覚を持ったことはないでしょうか。私自身、同じプロジェクトをClaudeとGeminiに渡したとき、Claudeが期待通りに応えるのに対しGeminiは見当違いの答えを返す、という体験を何度もしてきました。長い間「Geminiが弱い」と片付けていましたが、根本原因はプロンプトの書き方にありました。

Googleは内部的に「RSFC」（Role・Situation・Format・Conditions）という構造化プロンプトフレームワークを推奨しており、これを理解すると同じモデルでも回答品質が明確に変わります。本稿では、RSFCの各要素を噛み砕き、個人開発・業務利用・リサーチの3シーンで実際に使えるテンプレートを提示します。

## なぜGeminiはプロンプトに敏感なのか

Claudeと比較すると、Geminiは文脈の自己補完をあまり行いません。Claudeが「行間を読む」タイプとすれば、Geminiは「書かれた通りに応える」タイプです。これは欠点ではなく設計思想の違いで、指示が具体的であるほど期待通りの出力が得られる構造になっています。

つまり、Geminiには「察してほしい」というプロンプトは効きにくく、「こう応えてほしい」という枠組みを明示することが効きます。RSFCは、その枠組みを漏れなく指定するためのフレームワークです。

## RSFCの4要素

### Role（役割）

Geminiに「あなたは何者として応えるべきか」を与えます。これは単なるキャラ設定ではなく、回答の専門性・粒度・用語選択を決定する最重要要素です。

**悪い例**: `あなたはエンジニアです。`  
**良い例**: `あなたは10年以上のiOSアプリ開発経験を持つシニアエンジニアで、個人開発者と同僚エンジニアの両方に向けて書き分ける能力があります。Swift 6の並行性を本番で使った経験があり、既存プロジェクトからの移行の泥臭さを理解しています。`

良い例の方がなぜ効くかと言うと、「10年」「Swift 6並行性」「既存プロジェクトからの移行」という具体的な経験値が、Geminiの応答語彙を絞り込むからです。抽象的なRoleは抽象的な応答を生みます。

### Situation（状況）

「いま何が起きていて、どんな制約があるのか」を与えます。ここはプロンプトの8割の情報量が集中する場所です。

**悪い例**: `アプリのバグを直したい。`  
**良い例**: `iOS 18でSwift 6に移行した既存の家計簿アプリで、Core Dataのバックグラウンドコンテキスト保存時にクラッシュが発生する。ユーザーからのクラッシュレポートはFirebase Crashlyticsで週10件。crash graph上、家計入力画面からダッシュボード画面に戻った直後に集中している。`

Situationには「誰が困っているか」「いつ発生するか」「頻度はどれくらいか」「再現手順の目星」などを含めます。具体性が足りないと、Geminiは一般論で応えるしかなくなります。

### Format（出力形式）

応答の形を指定します。ここを省くと、Geminiは自由奔放にMarkdownを使って長文を返すので、用途によっては扱いにくくなります。

**悪い例**: `箇条書きで。`  
**良い例**: `以下の形式で応えてください。  
## 原因の仮説（3つまで、信頼度%付き）  
## 再現手順（最小コードを含む）  
## 推奨する調査順序（失敗コストの低い順）  
## 修正案（diff形式、コメント日本語）`

構造を明示的に指定することで、後工程（他の記事への貼り付け、Slack共有、Claude Codeへの投入）がスムーズになります。

### Conditions（条件・制約）

満たすべき条件と、やってはいけないことを列挙します。ネガティブな制約（禁止事項）もここで明示します。

**良い例**:  
```
- コード例は Swift 6 の構文を使うこと
- Swift 5.x の構文は使わない
- async/awaitを優先し、DispatchQueueは使わない
- 日本語コメントを付ける。英語コメントは付けない
- 外部ライブラリを導入する提案は避ける（既存依存のみ）
- 文章は敬体（です/ます調）で統一
```

Conditionsはプロンプトの「契約書」のようなもので、後で応答を評価するときの基準にもなります。

## 個人開発者のための完全テンプレート（3種）

### テンプレート1: コードレビュー用

```
# Role
あなたはTypeScript 5.4・Next.js 16・Tailwind CSSの本番運用経験が5年以上あるシニアレビュアー。アクセシビリティとパフォーマンスの両方を重視する。

# Situation
以下のReactコンポーネントは、当方が個人開発中のダッシュボード `/[locale]/dashboard` のサイドバーに使用する。モバイル（< 768px）ではドロワー化する要件がある。現在、TypeScriptのanyが2箇所使われており、WAI-ARIAの対応も不完全。

```tsx
[コードを貼る]
```

# Format
- レビュー結果を重大度別（Critical / Major / Minor）に分類
- 各指摘について、理由と修正diffを示す
- 修正の優先順位を最後にまとめる

# Conditions
- any使用は必ず指摘
- shadcn/uiを前提とする（別UIライブラリ提案は禁止）
- aria-labelの必要性は具体的に指摘
- 文字数目標は合計1,500字以内
```

### テンプレート2: 仕様検討用

```
# Role
あなたはプロダクトマネージャー兼エンジニアで、個人開発者向けSaaSの機能設計経験が豊富。無料プラン・有料プランの境界を決める判断基準に詳しい。

# Situation
Dolice Labs（4サイトのAI技術ブログ）で、プレミアム記事を月額580円のProプランと永久ライセンス2,480円のPremiumプランで提供している。現在、プレミアム記事を購入した非会員から「SNSで共有したい」という要望が上がっている。

# Format
- ユーザー体験への影響（pros / cons）
- 実装の難易度と所要工数（Small/Medium/Large）
- 収益への影響の定性評価
- 最終推奨（GO / NO GO / 追加検証）

# Conditions
- 収益機会を過度に削る案は避ける
- 既存有料会員への配慮を必ず含める
- Next.js 16 + Cloudflare Workers前提
- 法的・プライバシー観点も最後に一言触れる
```

### テンプレート3: アート活動の企画書生成

```
# Role
あなたは現代アートと広告クリエイティブの両方に通じたコピーライターで、海外展示のステートメント英訳も手掛ける。

# Situation
2026年秋、廣川政樹（アプリ開発者／アーティスト）の個展を東京都内のギャラリーで開催する予定。テーマは「AI時代の自画像」。絵画と映像とインタラクティブ作品を混ぜる。

# Format
- ステートメント（日本語版・400字）
- ステートメント（英語版・250 words）
- キービジュアルの指示書（カラー・構図・タイポグラフィ）
- SNS用短文3パターン

# Conditions
- 過度に難解な現代美術用語は避ける
- 個人開発者としての経歴も自然に織り込む
- 英語版は翻訳調を避けた自然なネイティブ表現
- ハッシュタグは日本語・英語それぞれ5個まで
```

## 業務利用のテンプレート（2種）

### テンプレート4: 競合調査

```
# Role
あなたはBtoC SaaS領域で、国内外の類似サービス調査を年間30件以上こなしているリサーチャー。

# Situation
当方は個人開発の家計簿アプリを日本国内で提供中。ユーザー数月間10万、有料率2%。競合として「Zaim」「マネーフォワード ME」「OsidOri」を定性比較したい。

# Format
| 観点 | Zaim | MF ME | OsidOri | 当社 |
| 料金 | | | | |
| UI特徴 | | | | |
| 差別化要素 | | | | |
| 脅威の度合い | | | | |

最後に「当社が次の3か月で打つべき手」を3つ提示。

# Conditions
- 最新情報の日付を明記
- 推測には「推定」と明示
- 事実と意見を混ぜない
```

### テンプレート5: 社内説明資料

```
# Role
あなたはエンジニア出身のプロジェクトマネージャーで、非技術系経営陣への説明経験が豊富。

# Situation
社内で「RAG（Retrieval-Augmented Generation）」の導入提案をする。経営陣のITリテラシーは中程度、「AI」と言ったら全員がChatGPTをイメージする層。予算は年間300万円以内。

# Format
- A4 2ページ相当の説明文
- 冒頭に「3行サマリ」
- 図解は言語で指示（図は別途作成する前提）
- 最後にFAQ 3つ

# Conditions
- 技術用語は最初の登場時に日本語で言い換える
- RAGがもたらすビジネス価値を数値例で示す
- 導入しない場合のリスクも公平に書く
- ベンダーロックインの懸念も明示
```

## リサーチ用途のテンプレート（1種）

### テンプレート6: 海外情報のファクトチェック付き要約

```
# Role
あなたはテック系英語メディアの要約に10年従事してきた編集者。情報の鮮度と裏取りを最優先する。

# Situation
2026年4月に発表されたClaude Designについて、国内エンジニア向けに要約記事を準備している。公式アナウンス・テック系海外メディア・SNSの3ソースから総合する。

# Format
- サマリ（5文以内）
- 事実（出典URL付き）
- 推測・意見（出典不明のもの）
- 国内への影響予測

# Conditions
- 事実と推測を必ず分けて書く
- 出典が確認できないものは「未確認」と明示
- 英語固有名詞は初出で和訳を添える
- 自分の意見は最後のブロックのみで、本文では抑制する
```

## RSFCを崩すべき場面

RSFCは万能ではありません。次の3パターンでは意図的に崩したほうが良い結果が出ます。

**1. 創作・ブレスト用途**  
短い詩、コンセプト出し、キャッチコピー案など、拡散的思考が欲しい場面では、厳密なFormatがかえって発想を縛ります。`Role`と`Conditions`だけに絞り、`Format: 自由に書いてください`と指定する方が豊かな出力が得られます。

**2. 会話的な試行錯誤**  
仕様が固まっていない段階で、Gemini自身に問いを投げ返してもらいたいとき。`Format`を指定しすぎると、疑問を抱えたまま無理に答えを書いてしまいます。`Role`と`Situation`だけを与え、`Format`には「まず理解に自信がない部分を質問してください」と書くのが有効です。

**3. 既存の長い会話の続き**  
すでに5〜10往復している会話では、毎回RSFCをフル装備するとGeminiが過去の合意を忘れがちです。`今回のターンだけの追加指示`として短く書くほうが、文脈を壊しません。

## モデル選択の早見表

同じRSFCプロンプトを使っても、モデル選択を誤ると結果が変わります。

| 用途 | 推奨モデル | 理由 |
|---|---|---|
| コードレビュー・リファクタリング | Gemini Pro | 長文コンテキストと論理性 |
| 仕様検討・戦略立案 | Gemini Pro | 多角的な視点を出せる |
| 日々のQ&A・ちょっとした文章生成 | Gemini Flash | コストとレスポンス速度 |
| 画像生成・ビジュアル素材 | Nano Banana Pro | 最新の画像生成品質 |
| 大量バッチ処理 | Gemini Flash | トークン単価で優位 |
| 複雑な推論・エージェント | Gemini Pro＋Antigravity | エージェント最適化 |

## 明日から試す一歩

RSFCの4要素を全部同時に覚えるのは負担なので、まずはSituationだけ徹底的に詳しく書く練習から始めるのをおすすめします。「誰が」「いつ」「どこで」「何に困っていて」「何を試して失敗したか」——この5つをプロンプトに含めるだけで、Geminiの応答品質は体感で2段階上がります。

一週間Situationに集中したら、次はFormatを明示的に指定する週、その次はRoleを具体化する週、という風に1要素ずつ習慣化すると定着しやすいです。個人的には、Roleを具体化した時に応答の語彙が一気に職業的になる瞬間が一番感動的でした。
