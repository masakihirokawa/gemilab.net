## implicit caching を確実に効かせる最小例

2 位の記事から、最も基本となる「キャッシュヒットを安定させるためのリクエスト整形」のスニペットを抜粋しておきます。

```python
import os
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

# 同じ system instruction とツール定義を、毎回同じ順序・同じ書式で渡す
SYSTEM_INSTRUCTION = (
    "You are a careful Japanese editor. "
    "Always preserve original meaning and tone."
)

def cached_request(user_text: str) -> str:
    response = client.models.generate_content(
        model="gemini-3.2-pro",
        contents=user_text,
        config=types.GenerateContentConfig(
            system_instruction=SYSTEM_INSTRUCTION,
            temperature=0.2,
        ),
    )
    return response.text

# 同じ system_instruction を保ったまま複数の user_text を処理することで
# implicit caching によるプレフィックス再利用を最大化する。
for line in ["こんにちは。", "良い1日を。", "ありがとう。"]:
    print(cached_request(line))
```

ポイントは `SYSTEM_INSTRUCTION` を呼び出しごとに作り直さず、モジュールレベルで定義することです。一見些細な違いですが、文字列のメモリ上の同一性を維持することで、SDK 内部のシリアライズ結果が安定し、キャッシュヒット率が体感で大きく変わります。

### Q. Gemini 3.2 Pro へすぐに移行すべきでしょうか？

「すぐに移行すべきかどうか」は、現在のプロンプトのテストカバレッジ次第だと考えています。十分なゴールデンセットがあるなら、1 位の記事の手順に沿って 1 週間で乗り換える価値は確実にあります。テストが薄い場合は、まずテスト整備を優先してから移行を始めるのが安全です。

### Q. PWA とブラウザ拡張、どちらを使うべきですか？

PWA はウィンドウ管理が楽、ブラウザ拡張はコンテキスト連携が強い、という棲み分けが現状の私の整理です。4 位の記事で、用途別にどちらが向いているかを整理しています。

### Q. 自然言語データ分析を Looker などに任せず、自前で作る理由は？

3 位の記事のように個人開発の延長で「自分のための秘書」を作る場合、Looker は重く、自然言語インターフェースのカスタマイズ性も制限されます。データ規模が小さいうちは、DuckDB と Streamlit を選ぶほうが明確に身軽です。
