macOS に来た Gemini Spark に、まず頼みたくなったのはフォルダの整理でした。個人開発で溜まっていく画像アセット、書きかけの資料、App Store や Google Play 向けに書き出した成果物が、ひとつのワークスペースに何百と積み上がっています。「これを意味のある構造に並べ直して」と一言で任せられるなら、確かに助かります。

けれど、実際に走らせる前に手が止まりました。整理という作業は、突き詰めれば移動と削除の連続です。そして移動と削除は、多くの場合あとから取り消せません。任せたいのに、任せた瞬間に取り返しがつかなくなるかもしれない。その落差をどう埋めるかを、しばらく考えていました。

ここで共有するのは、Spark のようなローカルのファイルを触るエージェントに整理を委ねるにあたって、私自身が実際に組んだガードレールです。エージェントの賢さを疑うのではなく、不可逆な操作にだけ人間側の検証を挟むという発想です。

## 何が怖かったのかを言葉にする

漠然と「怖い」で止めていては設計になりません。まず、自分が何を恐れているのかを分解しました。

<table>
  <thead>
    <tr><th>恐れていたこと</th><th>具体的に起きうる事故</th><th>取り返しのつきやすさ</th></tr>
  </thead>
  <tbody>
    <tr><td>意図しない削除</td><td>「不要そう」と判断された下書きが消える</td><td>低い（バックアップ次第）</td></tr>
    <tr><td>範囲外への移動</td><td>公開済み成果物が作業用フォルダへ紛れる</td><td>中程度</td></tr>
    <tr><td>静かな上書き</td><td>同名ファイルが別内容で置き換わる</td><td>低い</td></tr>
    <tr><td>把握できない変更</td><td>数百件を一括処理され差分が追えない</td><td>低い</td></tr>
  </tbody>
</table>

こうして並べてみると、怖さの正体は「操作そのもの」ではなく「操作の結果を自分が確認できないこと」だと分かりました。だとすれば、対策は明快です。エージェントに何をさせるかを制限するより先に、エージェントが何をしたかを後から必ず確認できる状態を作ればよいのです。

## 起点は「任せる作業」と「自分で持つ作業」を分けること

ガードレールのコードに入る前に、線引きの原則を決めました。私は次のように分けています。

分類・並べ替え・命名の提案といった「元に戻せる、あるいは提案にとどまる作業」は積極的に任せます。一方で、削除・ワークスペース外への移動・既存ファイルの上書きといった「取り返しのつかない作業」は、エージェントに直接実行させず、必ず人間の承認を経由させます。

この原則をそのまま仕組みに落とすと、三つのガードレールになりました。

1. 実行前にワークスペースの状態を内容ハッシュで記録する
2. 許可した範囲だけを触れるように許可リストで宣言する
3. 実行後に宣言と実際の差分を照合し、違反を承認待ちに回す

順に見ていきます。

## ガードレール①：実行前に内容ハッシュのマニフェストを取る

まず、エージェントを走らせる前のワークスペースの状態を、ファイルパスと内容ハッシュの対応表として固定します。ファイル名だけでは「中身がすり替わった上書き」を検知できないため、内容そのもののハッシュを取るのが要点です。

```python
import hashlib
import json
from pathlib import Path

def build_manifest(root: Path) -> dict[str, str]:
    """ワークスペース配下の全ファイルを {相対パス: 内容ハッシュ} で記録する。"""
    manifest: dict[str, str] = {}
    for path in sorted(root.rglob("*")):
        if not path.is_file():
            continue
        # 一時ファイルや隠しフォルダは対象外にする
        if any(part.startswith(".") for part in path.relative_to(root).parts):
            continue
        digest = hashlib.sha256(path.read_bytes()).hexdigest()
        manifest[str(path.relative_to(root))] = digest
    return manifest

root = Path.home() / "Workspace"
before = build_manifest(root)
Path("manifest_before.json").write_text(json.dumps(before, ensure_ascii=False, indent=2))
print(f"記録したファイル数: {len(before)}")
```

ここで内容ハッシュを使うのは、あとで「移動されたのか、上書きされたのか、消えたのか」を区別するためです。同じハッシュが別のパスに現れれば移動、ハッシュだけ消えれば削除、パスは同じでハッシュが変われば上書き、と判定できます。名前の一致だけを見ていると、この区別はつきません。

## ガードレール②：許可リストで操作範囲を宣言する

次に、エージェントに触れてよい範囲を明示的に宣言します。暗黙のうちに「たぶん大丈夫だろう」と広い権限を渡すのではなく、許可する操作を絞り込む方向で書きます。

```python
from dataclasses import dataclass, field

@dataclass
class Policy:
    # 並べ替えを許可するフォルダ（この配下でのみ移動を認める）
    movable_roots: list[str] = field(default_factory=lambda: ["_inbox", "_sorting"])
    # 絶対に削除・移動させないフォルダ
    protected_roots: list[str] = field(default_factory=lambda: ["_published", "_master"])

    def allows_move(self, rel_path: str) -> bool:
        top = rel_path.split("/", 1)[0]
        return top in self.movable_roots and top not in self.protected_roots

    def is_protected(self, rel_path: str) -> bool:
        top = rel_path.split("/", 1)[0]
        return top in self.protected_roots
```

私のワークスペースでは、整理の対象は取り込み用の `_inbox` と作業中の `_sorting` に限り、公開済みの `_published` と原本の `_master` は保護対象としています。エージェントには「この二つのフォルダの中だけを並べ替えてほしい」と伝え、検証側でもその宣言を強制します。プロンプトでの依頼と、コードでの検証の二重化が肝心です。言葉だけの約束は、破られたときに気づけないからです。

## ガードレール③：実行後の差分を検証して違反を戻す

エージェントの実行後、もう一度マニフェストを取り、前後を照合します。ここが仕組みの心臓部です。保護対象が変化していないか、移動が許可範囲に収まっているか、意図しない削除がないかを機械的に確認し、違反があれば人間の承認待ちに回します。

```python
def audit(before: dict[str, str], after: dict[str, str], policy: Policy) -> list[str]:
    violations: list[str] = []
    before_hashes = set(before.values())

    # 消えたファイル: ハッシュが after のどこにも無ければ「削除」
    for path, digest in before.items():
        if digest not in after.values():
            if policy.is_protected(path):
                violations.append(f"保護対象の削除: {path}")
            elif path not in after:
                violations.append(f"内容の消失（移動でない削除）: {path}")

    # 新しく現れたパス: 許可範囲外への移動・生成を検知
    for path, digest in after.items():
        if path in before:
            if before[path] != digest:
                violations.append(f"既存ファイルの上書き: {path}")
            continue
        if digest in before_hashes:
            # 既存の内容が別パスに現れた = 移動
            if not policy.allows_move(path):
                violations.append(f"許可範囲外への移動: {path}")
        else:
            if policy.is_protected(path):
                violations.append(f"保護フォルダへの新規生成: {path}")
    return violations

after = build_manifest(root)
issues = audit(before, after, Policy())
if issues:
    print("⚠️ ポリシー違反を検知しました。承認待ちに移します。")
    for line in issues:
        print(" -", line)
else:
    print("✅ すべての変更が許可範囲内でした。")
```

本番のワークスペースでいきなり回す前に、まず退避用のコピーで一度試すと、想定外の削除という事故を回避できます。ここは省かないほうがよい注意点です。

この検証を挟む前は、整理を任せたあとに自分でフォルダを開き、なんとなく眺めて「たぶん大丈夫」と納得していました。目視は数十件なら効きますが、数百件になると破綻します。検証を機械に任せてからは、違反の行だけが手元に残り、確認すべき対象が数件に絞られるようになりました。

Before と After を並べると、確認の質が変わったことがはっきりします。

  <thead>
    <tr><th>観点</th><th>Before（目視のみ）</th><th>After（差分検証あり）</th></tr>
  </thead>
  <tbody>
    <tr><td>確認対象</td><td>変更されたと思われる全フォルダ</td><td>違反として抽出された数件のみ</td></tr>

  </tbody>
</table>

## 手元のワークスペースで回してみた結果

実際に、取り込み用フォルダに溜まっていた画像アセットと資料あわせて約480件を対象に、この仕組みを通して整理を回しました。おおまかな実測値は次のとおりです。

<table>
  <thead>
    <tr><th>項目</th><th>実測</th></tr>
  </thead>
  <tbody>
    <tr><td>マニフェスト対象ファイル数</td><td>約480件</td></tr>
    <tr><td>実行前マニフェスト生成の所要</td><td>およそ3秒</td></tr>
    <tr><td>整理後に検出されたポリシー違反</td><td>2件（保護フォルダ隣接への移動提案）</td></tr>
    <tr><td>目視確認に要した対象</td><td>違反の2件のみ</td></tr>
  </tbody>
</table>

目視で追うべき対象は、約480件の変更候補からわずか2件へ、実に99.6%ほど減りました。検出された2件は、公開済みフォルダのすぐ隣に似た名前の一時フォルダを作ろうとした提案でした。悪い操作ではありませんが、私の意図とはずれていました。仕組みがなければ、この2件はおそらく数百件の変更に紛れて見過ごしていたはずです。ガードレールの価値は、事故を止めることそのものより、「確認すべき数件」を浮かび上がらせてくれる点にあると感じています。

## 任せる作業と、自分で持つ作業の線引き

最後に、いま私が使っている線引きを表にまとめます。これは固定の正解ではなく、取り返しのつきやすさで判断するための出発点です。

<table>
  <thead>
    <tr><th>作業</th><th>任せ方</th><th>理由</th></tr>
  </thead>
  <tbody>
    <tr><td>分類・タグ付けの提案</td><td>任せる</td><td>提案にとどまり、元に戻せる</td></tr>
    <tr><td>作業フォルダ内での並べ替え</td><td>検証つきで任せる</td><td>範囲を限定し差分で確認できる</td></tr>
    <tr><td>命名規則の適用</td><td>検証つきで任せる</td><td>上書き検知があれば安全</td></tr>
    <tr><td>不要ファイルの削除</td><td>自分で持つ</td><td>不可逆で、判断に文脈が要る</td></tr>
    <tr><td>公開済み成果物の移動</td><td>自分で持つ</td><td>影響範囲が読みにくい</td></tr>
  </tbody>
</table>

個人的には、取り返しのつかない操作にだけ承認を残す設計を推奨します。エージェントが賢くなるほど、任せられる範囲は広がっていきます。それでも、不可逆な操作にだけは人間の承認を残しておく。この一線を守るための道具が、内容ハッシュのマニフェストと許可リストと差分検証でした。

Spark を本格的に使い込むのはこれからですが、道具を先に用意しておいたおかげで、最初の一歩を落ち着いて踏み出せました。同じようにローカルの整理を任せたい方の設計の参考になれば幸いです。お読みいただきありがとうございました。
