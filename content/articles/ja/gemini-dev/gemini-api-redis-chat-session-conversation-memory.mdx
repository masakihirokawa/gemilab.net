Gemini API の `chat.send_message()` は、`history` を渡せば過去のやり取りを踏まえた応答を返してくれます。公式ドキュメントのサンプルでは `chat = model.start_chat(history=[])` と書かれていて、最初はこれで十分に動きます。ところが Cloud Run や Cloud Functions で動かし始めた途端に、ユーザーから「昨日の続きから話せない」「ログインし直すと AI が自己紹介を繰り返す」といった声が届きます。

原因はシンプルで、`ChatSession` オブジェクトをプロセスメモリに置いたままにしていたからです。コンテナが再起動すれば消え、ロードバランサで別インスタンスに振り分けられれば見つからない。本番運用を始めた初日にぶつかる壁の一つだと思います。

ここではGemini API のチャット履歴を Redis に永続化するときに「そのまま JSON にして `SET` するだけ」の素朴な実装がなぜ破綻しやすいのか、そしてどう作り直せば安定するのかを、実装例とともに整理します。

## なぜインメモリで持ち回してはいけないのか

ローカル開発では `chat` オブジェクトをグローバル変数で保持するコードでも動きます。問題は本番環境の三つの現実です。

一つ目は、**サーバーレス環境のコンテナは短命**だという点です。Cloud Run のインスタンスはリクエストが来なくなれば数分〜数時間でシャットダウンされます。再起動後は当然ながら変数の中身も空です。

二つ目は、**水平スケール時の振り分け**です。同一ユーザーの 1 通目と 2 通目で違うインスタンスに届く可能性があり、それぞれが独立したメモリを持っているので履歴が繋がりません。Sticky セッションで強引に同じインスタンスに固定する方法もありますが、スケールの柔軟性を失います。

三つ目は、**モバイルアプリ側の再接続**です。ユーザーがアプリを落として数時間後に再起動したとき、サーバー側にその状態が残っている保証はありません。「セッションは短命である」という前提で設計するのが、結果的に堅牢です。

Redis は、このすべてを解決する中継地点として適しています。ミリ秒オーダーの読み書き、TTL による自動クリーンアップ、Pub/Sub でのリアルタイム通知まで備えているので、チャットセッションの受け皿としてかなり相性が良いのです。

## 素朴な実装と、その落とし穴

まずは「とりあえず動く」版のコードを見てから、何が足りないのかを見ていきます。

```python
# requirements: google-genai, redis
import json
import os
import redis
from google import genai

r = redis.Redis.from_url(os.environ["REDIS_URL"], decode_responses=True)
client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

def chat_once(session_id: str, user_message: str) -> str:
    # 履歴を取り出す(なければ空配列)
    raw = r.get(f"chat:{session_id}")
    history = json.loads(raw) if raw else []

    chat = client.chats.create(model="gemini-2.5-flash", history=history)
    response = chat.send_message(user_message)

    # 送った後の履歴を丸ごと保存
    new_history = [
        {"role": msg.role, "parts": [{"text": p.text} for p in msg.parts]}
        for msg in chat.get_history()
    ]
    r.set(f"chat:{session_id}", json.dumps(new_history))
    return response.text
```

このコードは動きます。ただ、数日運用すると次の問題が順に顔を出します。

**問題 1: 履歴が無限に伸びる**。1 往復ごとに数百〜数千トークン積み上がり、1 週間も経てば 10 万トークンを超えます。応答レイテンシが急速に悪化し、料金も線形に膨らみます。

**問題 2: TTL がない**。Redis に書き込みっぱなしで、使わなくなったセッションがずっと残ります。メモリ使用量が右肩上がりになり、コストと eviction ポリシー次第では新しいセッションを保存できなくなります。

**問題 3: 同時書き込みで履歴が壊れる**。同じユーザーが二つのタブから同時に送ると、片方の書き込みがもう片方を上書きします。チャット UI のオプティミスティック更新と組み合わさると、表示と実際の履歴がずれます。

**問題 4: Gemini の内部フォーマットに依存している**。`chat.get_history()` が返すオブジェクトを直接シリアライズしているため、SDK のバージョンアップで構造が変わると古いデータが読み込めなくなります。

それぞれを順番に潰していきます。

## 履歴のトリム戦略 - スライディングウィンドウ + 要約

無限に伸びる履歴に対して、私は「最近 N 往復はそのまま残し、それより古いものは要約で置き換える」スライディングウィンドウ方式を推奨しています。会話の直近の文脈を残しつつ、古い背景情報は圧縮して保持できるからです。

```python
from google import genai

MAX_RECENT_TURNS = 10  # 直近 10 往復(= 20 メッセージ)はそのまま
SUMMARY_TRIGGER = 14   # 往復数がこれを超えたら要約を走らせる

def trim_history(history: list, client: genai.Client) -> list:
    """直近 N 往復を残し、それ以前を要約で置き換える"""
    turns = len(history) // 2
    if turns <= SUMMARY_TRIGGER:
        return history

    # 要約対象 = 先頭から (turns - MAX_RECENT_TURNS) 往復ぶん
    cut = (turns - MAX_RECENT_TURNS) * 2
    older = history[:cut]
    recent = history[cut:]

    # 古いメッセージをまとめてテキスト化して Flash に要約させる
    older_text = "\n".join(
        f"{m['role']}: {m['parts'][0]['text']}" for m in older
    )
    summary = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=f"以下の会話を 300 字以内で要約してください。固有名詞と数値は残してください。\n\n{older_text}"
    ).text

    # 要約を user ロールの最初のメッセージとして挿入する
    return [
        {"role": "user", "parts": [{"text": f"[これまでの会話の要約]\n{summary}"}]},
        {"role": "model", "parts": [{"text": "承知しました。続きを進めます。"}]},
        *recent,
    ]
```

要約にあえて `gemini-2.5-flash` を使っているのがポイントです。要約自体は難しいタスクではないので Flash で十分で、メイン応答にプレミアムモデルを使いつつ要約コストを抑えられます。トークン単価の節約については[コンテキストキャッシングでコストを下げる方法](/articles/gemini-api/gemini-api-context-caching-cost-optimization)も合わせて読むと、設計全体の見通しが立てやすいと思います。

## TTL と同時書き込みの扱い

TTL は書き込み時に毎回更新するのが簡単で、かつ「最後に使われてから X 時間経過したセッションは自動で消える」という直感的な挙動になります。

```python
SESSION_TTL = 60 * 60 * 24 * 7  # 7 日間、最終アクセスから起算

r.set(f"chat:{session_id}", json.dumps(new_history), ex=SESSION_TTL)
```

同時書き込み対策は、Redis の `WATCH`/`MULTI`/`EXEC`(楽観的ロック)か、`SET NX` + 専用ロックキーの排他制御で対応します。チャットでは後者の方が扱いやすいことが多い印象です。

```python
import uuid
import time

def with_session_lock(session_id: str, fn, timeout_ms: int = 5000):
    """セッション単位の排他ロックを取ってから fn() を実行する"""
    lock_key = f"chat:lock:{session_id}"
    token = str(uuid.uuid4())
    deadline = time.time() + timeout_ms / 1000

    # SET NX PX でロック取得、失敗したらリトライ
    while time.time() < deadline:
        if r.set(lock_key, token, nx=True, px=10000):  # ロック自体は 10 秒で expire
            try:
                return fn()
            finally:
                # 自分が入れたトークンと一致するときだけ削除(他人のロックを奪わない)
                release = (
                    "if redis.call('get', KEYS[1]) == ARGV[1] then "
                    "return redis.call('del', KEYS[1]) else return 0 end"
                )
                r.eval(release, 1, lock_key, token)
        time.sleep(0.05)

    raise RuntimeError("Failed to acquire chat session lock")
```

Lua スクリプトでトークンを照合してから削除しているのは、処理が長引いて TTL が先に切れ、別のプロセスが同じロックキーを取得した後に、自分が古いロックを誤って削除してしまう事故を防ぐためです。地味ですが本番では重要な一手になります。

## 永続フォーマットを SDK から切り離す

Gemini SDK のオブジェクト構造に直接依存すると、SDK のマイナーアップデートで読み書きが壊れます。自分たちで定義した中間フォーマット(DTO)を挟むのが結局いちばん堅いです。

```python
from dataclasses import dataclass, asdict
from typing import Literal

@dataclass
class StoredMessage:
    role: Literal["user", "model"]
    text: str
    ts: float  # 作成時刻(デバッグ・分析用)

def to_stored(history) -> list[dict]:
    out = []
    for msg in history:
        out.append(asdict(StoredMessage(
            role=msg.role,
            text="".join(p.text for p in msg.parts if hasattr(p, "text")),
            ts=time.time(),
        )))
    return out

def from_stored(stored: list[dict]) -> list[dict]:
    """Gemini API が期待するフォーマットへ戻す"""
    return [
        {"role": m["role"], "parts": [{"text": m["text"]}]}
        for m in stored
    ]
```

こうしておくと、画像やツール呼び出しのような Parts が増えたときも、`StoredMessage` を拡張するだけで済みます。SDK を `google-generativeai` から `google-genai` に移行する際にも、この層があるおかげで書き換え箇所を最小限に抑えられました。

## 組み合わせた本番版のスケルトン

ここまでの対策をまとめると、次のような構造になります。

```python
def chat_persistent(session_id: str, user_message: str) -> str:
    def _run():
        raw = r.get(f"chat:{session_id}")
        stored = json.loads(raw) if raw else []
        history = from_stored(stored)

        # トリムは Redis 書き込み前に済ませる(次回以降が軽くなる)
        history = trim_history(history, client)

        chat = client.chats.create(model="gemini-2.5-pro", history=history)
        response = chat.send_message(user_message)

        # 中間フォーマットで保存 + TTL 更新
        new_stored = to_stored(chat.get_history())
        r.set(
            f"chat:{session_id}",
            json.dumps(new_stored),
            ex=SESSION_TTL,
        )
        return response.text

    return with_session_lock(session_id, _run)
```

レイテンシが気になる規模になったら、`trim_history` の要約呼び出しだけを[Cloud Tasks による非同期ジョブキュー](/articles/gemini-dev/gemini-api-cloud-tasks-async-ai-job-queue-production-guide)へ逃がすのも手です。ユーザー応答には古いままの履歴を使い、裏で要約が完了したら書き戻す設計にすれば、体感速度を損なわずに履歴を圧縮できます。

## よくあるつまずきと対処

- **「要約後に会話が噛み合わない」**: 要約プロンプトで固有名詞・数値・タスクの状態を必ず残すよう指示すると安定します。「ユーザーが注文した商品名は残す」など具体的に書いた方が精度が上がります。
- **「ロックで応答が遅くなる」**: `send_message` 自体は数秒かかるので、その間ロックを握ると同じセッションへの並行リクエストが詰まります。ユーザー体験上はむしろそれで正しい(メッセージ順序が保証される)ため、UI 側で送信ボタンを disabled にするのが素直です。
- **「Redis がダウンしたら全停止する」**: セッションは再現不可能なので、Redis 障害時は「履歴なしで新しい会話として受け付ける」フォールバックを入れておくと、体験の毀損を最小限にできます。エラーハンドリング全般は[Gemini API のエラー処理と本番パターン](/articles/gemini-dev/gemini-api-error-handling-rate-limit-production-patterns)に整理しています。

## まとめと次の一歩

まずは既存のインメモリ実装を見直して、セッションキーと Redis への書き込みを足してみてください。それだけで「再デプロイで履歴が消える」問題の 8 割は解決します。そこから、トリム・TTL・ロック・中間フォーマットの順で一つずつ積み上げていくと、数か月運用しても崩れないチャットレイヤーになっていきます。

会話 AI を本格的にプロダクトへ組み込むなら、設計の引き出しを増やしておくと判断が早くなります。たとえば『[LLM のプロダクト活用[入門]](https://www.amazon.co.jp/dp/4297146088/?tag=pinocchio-22)』や『[実践 AI アプリケーション開発（Chip Huyen 著）](https://www.amazon.co.jp/dp/4814401019/?tag=pinocchio-22)』は、セッション管理・評価・モニタリングといった本番運用の勘所が整理されていて、Redis 周りの設計判断にも示唆があります。
