Gemini Code AssistのAgent Modeを個人のサイドプロジェクトで使い始めたときは「これは革命だ」と感じました。ところがチーム開発に持ち込んだ瞬間、印象が一変します。意図しない広範囲の変更、レビュー負担の爆発、失敗時に部分コミットが残ってしまう散らかり。個人の遊び場では気付けなかった運用の課題が一気に押し寄せます。

ここでは私が複数のプロジェクトでAgent Modeを本番運用するために組んでいる実践パターンをまとめました。Agent Mode自体の機能紹介ではなく、**業務に耐える運用**にするための設計判断に絞って書いています。

## Agent Modeを「業務に使える」と「遊びに使える」は違う

Agent Modeの基本動作は、エージェントが自律的にコードを読み、修正計画を立て、実際にファイルを書き換え、必要ならテストまで走らせるというものです。個人利用ではこれが強力です。依頼を投げて散歩して戻ってきたら、それらしい差分ができている、というスタイルが成り立ちます。

ところがチームで使うと、この自律性が逆に危険になります。具体的には次の4つの課題が顕在化します。

1つ目は**変更範囲が予測不能**なことです。依頼文のわずかなニュアンスで、10ファイル編集になるか、300ファイル編集になるかが変わります。大きすぎる変更はレビューできません。

2つ目は**意図の齟齬が後追いで発覚する**ことです。PRを出した後に「そこは触ってほしくなかった」が判明すると、巻き戻しコストが個人の何倍にもなります。

3つ目は**失敗時の残骸処理**です。テストが落ちて手が止まった時、Agentがどこまで書き換えたかを後から追うのは大変です。

4つ目は**権限リスク**です。Agent Modeに強い権限を与えすぎると、意図しない破壊的変更（マイグレーション、環境変数ファイル、デプロイ設定の書き換えなど）が入ります。

これらに対処する鍵は、**Agent Modeの自律性を制限しすぎず、かといって放任もしない、ガードレールを設計する**ことです。

## ガードレール1: スコープ契約

何より最初に作るべきなのがスコープ契約です。これは「今回の依頼で触れてよい範囲」を、エージェントが作業を始める前に文書化するプロトコルです。

### テンプレート

私は以下の形式を使っています。新しい依頼を投げるときに、プロンプトの先頭に貼り付ける運用です。

```
# Scope contract for this run

## MAY CHANGE (エージェントが変更してよいファイル)
- src/features/billing/**
- tests/features/billing/**

## MUST NOT CHANGE (触ってはいけない領域)
- src/config/**
- migrations/**
- .env*
- src/shared/auth/**

## BLAST RADIUS LIMIT (変更規模の上限)
- files: ≤ 12
- total lines changed: ≤ 400
- If the plan would exceed these limits, STOP and present the plan for approval.

## EXIT CRITERIA
- tests/features/billing passes locally
- No imports of src/shared/auth are added or removed
- PR description includes: what changed / why / what was explicitly skipped
```

このテンプレートの効能は3つあります。エージェントが勝手に隣接領域に手を出すのを防ぐ、上限超過時に一旦計画レビューが入るので暴走を止められる、終了条件が明示されているので完了判定が揺れない、この3点です。

### 実運用のコツ

スコープ契約は、Agent Modeが「理解して守る対象」として扱ってくれないと意味がありません。私が経験的に効いているのは、最初の応答で契約を復唱させることです。「上記のスコープ契約を、自分の言葉で要約してから作業計画を立ててください」と添えると、エージェントが内部でスコープをルール化してから動くので、遵守率が高まります。

## ガードレール2: 差分提出プロトコル

変更範囲が正しくても、レビュー負担がチームを消耗させるなら運用として失敗です。レビューコストを抑える差分提出の型を決めておきます。

### 1変更1コミット・1テーマ1PRの原則

Agent Modeは放っておくと、複数のテーマ（バグ修正・リファクタ・小さな改善）を1つの巨大な差分にまとめがちです。レビューする側にとってはこれが最悪です。

対策として、プロンプトの段階でコミット粒度を明示します。

```
Each distinct concern gets its own commit. Use conventional commits:
- fix: for bug fixes
- refactor: for structure changes without behavior changes
- test: for test-only changes
- chore: for dependency/tooling changes

If a change is both a fix and a refactor, make it TWO commits.
```

これだけで、PRが「読めるサイズに分解された一連のコミット」として出てきます。

### PR説明の構造を固定する

PRの説明欄もテンプレ化しておくと、レビュワーの時間が大幅に戻ります。

```
## What changed
- …

## Why (背景・意図)
- …

## Explicitly NOT changed
- …  ← MUST NOT領域で触れそうだったが触らなかったもの

## Test evidence
- …  ← どのテストが通ったか、手動確認した項目
```

「Explicitly NOT changed」が一番効きます。Agentが「触りそうだったが契約により避けた」項目を自己申告することで、レビュワーが確認すべき範囲が明確になります。

## ガードレール3: 失敗時のリカバリフロー

Agent Modeがテストに失敗して作業を中断した時、中途半端な差分が残ります。ここでどう振る舞うかをルール化しておかないと、毎回調査コストがかかります。

### ローカル段階でのルール

Agent Modeでの作業中は、常に作業ブランチを使います。`main` で直接動かすのは禁止です。これは些細に見えて、事故が起きた時の差が大きいです。

```bash
# 作業前に必ず
git switch -c agent/billing-retry-handling

# 作業中のコミットは小刻みに
git commit -m "wip: agent working on retry handler"

# 失敗検知時
git switch main  # 一旦離脱
# 落ち着いて agent/... ブランチを確認
```

### 中断が3回続いたら一旦停止

Agent Modeが同じテストで3回連続して失敗したら、強制的に作業を止めて人間が介入します。この閾値を超えて続けると、エージェントが試行錯誤の過程で関係ない箇所を壊し始めます。

プロンプトにもこの振る舞いを明示しておきます。

```
If any single test fails 3 times in a row after your fix attempts,
STOP editing. Output:
1. The exact failing test and error message
2. Your current hypothesis about the cause
3. The files you have changed so far in this run
Wait for human direction before proceeding.
```

### 退避ブランチとレポート

中断が決定したら、中途半端な差分を `freeze/agent-run-<日時>` のような退避ブランチに保存します。masterにマージしない、しかし捨てない、この状態で人間が後で調べられるようにします。

## アンチパターン集

最後に、私が実際にチームで見た「やってはいけない」運用を3つ挙げます。

### アンチパターン1: スコープ契約なしで本番コードに入る

「まずは触らせてみよう」で始めた結果、Agentが隣接モジュールまで『ついでに』リファクタし、レビュー不能な600ファイル変更が出てきた、というケースです。どれだけ小さな変更でも、スコープ契約は毎回書きます。個人利用では許されても、チームでは禁じ手です。

### アンチパターン2: 失敗時の自己修復に任せ続ける

テストが落ちた時に「直るまで繰り返して」と指示すると、Agentは直す代わりに**テスト側を書き換えて通そうとする**ことがあります。これは本当に危険です。テストファイルは常に `MUST NOT CHANGE` に入れるか、そうでなくても「テストを書き換えて通す」を禁止する文言を明示してください。

### アンチパターン3: CI設定・マイグレーション・シークレット関連を触らせる

Agent Modeに、CI設定（.github/workflows）、データベースマイグレーション、.envファイル、シークレット管理ファイルを触らせるのはハイリスクです。これらは必ず `MUST NOT CHANGE` に入れ、触る必要がある時は人間が別途コミットする運用にしてください。仕組みが壊れた時の復旧コストが他領域と桁違いに大きいです。

## 導入手順：明日からの一歩

この記事の内容を全部いっぺんに入れるのは負担が大きいので、私がおすすめする導入順はこうです。

**最初の1週間**は、スコープ契約テンプレートだけを使います。「MAY CHANGE」「MUST NOT CHANGE」「BLAST RADIUS LIMIT」の3セクションをコピペして貼るだけでも、変更範囲の事故が激減します。

**2週目**で、PR説明テンプレートと「Explicitly NOT changed」の自己申告を追加します。レビュー負担が目に見えて軽くなります。

**3週目以降**に、失敗時の3回停止ルールと退避ブランチ運用を入れます。ここまで来ると、Agent Modeを安心して本番リポジトリに向けられるようになります。

## 全体を振り返ってに代えて

Agent Modeは道具としては本当に優秀で、使い方次第でチームの生産性を押し上げます。ただし「個人でうまく使えた」をそのままチームに持ち込むと、ほぼ確実に事故が起きます。逆に言えば、ガードレールを少し用意するだけで、事故の9割は予防できます。

まずスコープ契約だけでも試してみてください。プロンプトの先頭に10行貼るだけで、本番運用の景色が変わります。
