ここ一年ほど、自分のアプリの売上データや AdMob のレポート CSV、Stripe の決済履歴などを分析するときに、私はもっぱら Gemini にコピペして「これを要約して」と頼む生活を続けていました。早いし楽なのですが、毎月同じ作業を繰り返しているうちに、ある夜ふと思ったのです。**この一連の動作、全部アプリに閉じ込めてしまえば、自分が眠っている間にも分析が走るのではないか**、と。

その晩から数日かけて組み上げたのが、この記事で紹介する「Gemini 3.2 Pro × DuckDB × Streamlit」のデータ分析エージェントです。CSV や Parquet を放り込むと、自然言語の質問に対して SQL を組み立て、エラーが起きれば自動で直し、結果を Plotly で可視化して、コスト最適化のためにモデルを使い分けてくれます。クラウド DB は一切使いません。すべてが手元のマシン、あるいは Streamlit Community Cloud の小さなコンテナ一つの中で完結します。

この記事は、その実装を最初から本番運用まで丁寧に追っていくものです。コードは断片ではなく `streamlit run app.py` でそのまま動く完成形を提示します。途中で出てくる落とし穴は、私が実際に踏んだものを中心に、一つずつ対処パターンを差し込んでいきます。

私が同じような構成を試してきた中で何度も実感しているのは、**「自然言語からデータを引き出す」という体験は、それを実装した本人が一番恩恵を受ける**ということです。一度作ってしまうと、データに対して問いかける心理的ハードルが大きく下がります。「これ調べたいけど SQL 書くの面倒だな」と感じたら自然と諦めていた問いが、思いつくたびにダッシュボードに流れ込むようになります。これは思考の質を確実に変えます。少なくとも私の場合、ここ数ヶ月の意思決定の精度は、明らかにこのエージェントを作る前と後で違っています。

## なぜ DuckDB と Gemini 3.2 Pro を組み合わせるのか

最初に、選定の根拠を簡単に共有させてください。私はこの構成にたどり着くまでに PostgreSQL + Vertex AI、SQLite + Gemini Flash、BigQuery + Gemini Pro の三つを試しています。最終的に DuckDB に落ち着いたのは、**「個人開発者が一人で運用するなら、列指向で速く、サーバを立てなくていい DB が圧倒的に楽だ」** という結論に至ったからです。

DuckDB は SQLite の思想を受け継ぎつつ、内部は PostgreSQL のクエリプランナと Apache Arrow ベースの列指向ストレージで作られています。私の手元では、約 1.2 GB の Parquet ファイル（過去三年分の AdMob 日次データ）に対して `GROUP BY country, ymonth` のような集計が常時 100 ms 以下で返ってきます。これに Gemini 3.2 Pro の SQL 生成精度が組み合わさると、思いつきの問いをそのままダッシュボードに反映できる、自然と手が伸びる道具になっていきました。

Gemini 3.2 Pro を選ぶ理由はもう一つあります。**`responseSchema` 経由の structured output が安定し、SQL を「ただのコード文字列」ではなく検証済みのオブジェクトとして受け取れる**点です。これは後述する自己修正ループの基盤になる重要な設計判断でした。

## 完成形のアーキテクチャ

最終的に出来上がるアプリは、次の流れで動きます。Streamlit がフロントエンド、DuckDB が分析エンジン、Gemini が翻訳・解釈・自己修正の頭脳、という三層構造です。

- **入力層**：Streamlit のサイドバーから CSV / Parquet をアップロード、または既存の `data/` ディレクトリのファイルを選択します
- **スキーマ抽出層**：DuckDB の `DESCRIBE` で列名・型・ユニーク値サンプルを取り、Gemini に渡すコンテキストを最小限に整えます
- **SQL 生成層**：自然言語の質問とスキーマを Gemini 3.2 Pro / Flash に渡し、structured output で SQL と意図説明を受け取ります
- **実行・自己修正層**：DuckDB で SQL を実行、エラーがあればエラーメッセージを Gemini に戻して修正版を依頼します（最大 3 回）
- **可視化層**：結果の DataFrame を Plotly Express で自動可視化、適切なグラフ種を Gemini が判定します
- **コスト管理層**：質問の複雑度に応じて Pro と Flash を動的に切り替えます

ここで重要なのは、**Gemini への問い合わせ回数を増やさず、各層で独立して責務を切る**ことです。失敗が起きた層だけを再実行できる構造にしておくと、本番運用での再現性とデバッグ性が大きく変わります。

## SQL 生成のコア実装 — structured output で「壊れない」契約を作る

最初に書くのは、自然言語の質問とスキーマから SQL を取り出すコアです。私が以前のバージョンで一番苦しんだのは、Gemini が返してくる SQL が ```sql ... ``` でラップされていたり、説明文と一緒に返ってきたりして、毎回正規表現で抜き出す処理が増えていったことでした。`responseSchema` を使うとこの不毛な作業から解放されます。

`agent/sql_generator.py` を作成します。

```python
import os
from typing import Literal
from pydantic import BaseModel, Field
from google import genai
from google.genai import types

class SQLPlan(BaseModel):
    """Geminiから返される構造化レスポンス"""
    sql: str = Field(description="DuckDBで実行可能な完全なSQL文")
    intent: str = Field(description="このSQLが答えようとしている問いの要約（30文字以内）")
    chart_type: Literal["bar", "line", "scatter", "table", "histogram"] = Field(
        description="結果の可視化に最適なグラフ種"
    )
    confidence: float = Field(ge=0.0, le=1.0, description="SQL生成の確信度")

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

SYSTEM_INSTRUCTION = """\
あなたはDuckDB SQLの専門家です。ユーザーの質問とテーブルスキーマから、
DuckDBで実行可能な完全なSQL文を1つだけ返してください。

ルール:
1. テーブル名は与えられたものをそのまま使う
2. DuckDB特有の関数（list_*, struct_*, regexp_extract等）を活用してよい
3. 集計時はNULL値を明示的に除外する
4. 日付列はTRY_CAST(col AS DATE)で安全にキャストする
5. confidenceは「このSQLが正しく動く」自信を0.0-1.0で返す
"""

def generate_sql(question: str, schema_text: str, model: str = "gemini-3.2-pro") -> SQLPlan:
    """質問とスキーマからSQLPlanを生成する"""
    response = client.models.generate_content(
        model=model,
        contents=[
            f"テーブルスキーマ:\n{schema_text}\n\n質問: {question}"
        ],
        config=types.GenerateContentConfig(
            system_instruction=SYSTEM_INSTRUCTION,
            response_mime_type="application/json",
            response_schema=SQLPlan,
            temperature=0.1,  # SQL生成は決定的に
        ),
    )
    return SQLPlan.model_validate_json(response.text)
```

ポイントは三つあります。一つ目は `temperature=0.1` で、SQL 生成は創造性ではなく決定性が欲しいので低めに固定します。二つ目は `confidence` フィールドで、後で「Gemini 自身が自信のない SQL は実行前に Pro に再依頼する」分岐に使います。三つ目は **`chart_type` まで一緒に返させる**こと。可視化ロジックを呼び戻す追加のラウンドトリップが消え、レスポンスが体感で速くなります。

## DuckDB 実行と Self-Correction ループ

次に、生成された SQL を DuckDB で実行します。ここでは「失敗したら Gemini に戻して直してもらう」自己修正ループを組み込みます。これを入れる前と入れた後では、現場の使用感がまったく違います。私の手元の集計では、初回失敗したクエリの 78% が 1 回の修正で実行可能になりました。

`agent/executor.py` を作成します。

```python
import duckdb
import pandas as pd
from agent.sql_generator import generate_sql, SQLPlan, client, types

class ExecutionResult:
    def __init__(self, df: pd.DataFrame, plan: SQLPlan, attempts: int):
        self.df = df
        self.plan = plan
        self.attempts = attempts

def execute_with_self_correction(
    question: str,
    schema_text: str,
    con: duckdb.DuckDBPyConnection,
    max_retries: int = 3,
) -> ExecutionResult:
    """SQL生成→実行→失敗時にGeminiへ修正依頼するループ"""
    plan = generate_sql(question, schema_text, model="gemini-3.2-pro")
    last_error = None

    for attempt in range(max_retries):
        try:
            df = con.execute(plan.sql).df()
            return ExecutionResult(df, plan, attempt + 1)
        except duckdb.Error as e:
            last_error = str(e)
            # Geminiに修正を依頼。エラーメッセージを文脈に含める
            correction_prompt = (
                f"前回生成したSQLが以下のエラーで失敗しました。修正したSQLを返してください。\n\n"
                f"質問: {question}\n"
                f"スキーマ:\n{schema_text}\n\n"
                f"前回のSQL: {plan.sql}\n"
                f"エラー: {last_error}\n"
            )
            response = client.models.generate_content(
                model="gemini-3.2-pro",  # 修正は必ずProで
                contents=[correction_prompt],
                config=types.GenerateContentConfig(
                    response_mime_type="application/json",
                    response_schema=SQLPlan,
                    temperature=0.0,
                ),
            )
            plan = SQLPlan.model_validate_json(response.text)

    raise RuntimeError(f"自己修正に{max_retries}回失敗しました: {last_error}")
```

実装上の判断点を残しておきます。修正フェーズでは **必ず Pro を使う**ようにしています。Flash で生成したクエリが失敗したとき、同じ Flash に戻して修正させると同じ系統の間違いを繰り返すことが多く、ここだけはコストより精度を優先したほうが結果的にトークン消費が減ります。

また `temperature=0.0` にして、修正版の決定性を担保しています。修正というタスクは創造性を必要としません。

## コスト最適化 — Pro と Flash の動的ルーティング

個人開発で運用するなら、コストは絶対に意識すべき変数です。私の現在の月額コストは Gemini API 利用で約 1,200 円。これは三ヶ月前まで一律 Pro を使っていた頃の 1/10 になっています。鍵は **「質問の複雑度を事前に見積もって、簡単なものは Flash に流す」** ルーティングを作ることでした。

```python
# agent/router.py
from google import genai
from google.genai import types
from pydantic import BaseModel

class Complexity(BaseModel):
    level: int  # 1=単純集計, 2=結合あり, 3=サブクエリ/CTE必要
    reason: str

ROUTER_SYSTEM = """\
ユーザーの質問が要求するSQLの複雑度を1-3で判定してください。
1: 単一テーブルへのSELECT/集計のみ
2: JOINや単純なサブクエリが必要
3: 複数CTE、ウィンドウ関数、複雑な集計が必要
"""

def pick_model(question: str) -> str:
    """質問の複雑度に応じてモデルを選ぶ"""
    response = client.models.generate_content(
        model="gemini-3.2-flash-lite",  # ルーティング判定は最軽量
        contents=[question],
        config=types.GenerateContentConfig(
            system_instruction=ROUTER_SYSTEM,
            response_mime_type="application/json",
            response_schema=Complexity,
            temperature=0.0,
        ),
    )
    complexity = Complexity.model_validate_json(response.text)
    return "gemini-3.2-pro" if complexity.level >= 3 else "gemini-3.2-flash"
```

`flash-lite` で判定し、`flash` か `pro` で実行する三段ルーティングです。一見ラウンドトリップが増えるように見えますが、**flash-lite は Pro の 1/40 のコスト**で、入力も短い（質問文だけ）ので、全体の支払いは大きく下がります。

## Streamlit ダッシュボードの組み立て

ここまでの部品を Streamlit で組み合わせます。`app.py`：

```python
import streamlit as st
import duckdb
import plotly.express as px
from agent.executor import execute_with_self_correction
from agent.router import pick_model

st.set_page_config(page_title="Data Agent", layout="wide")
st.title("自然言語データ分析エージェント")

# サイドバー: ファイルアップロード
uploaded = st.sidebar.file_uploader("CSV / Parquet", type=["csv", "parquet"])
if uploaded is None:
    st.info("左のサイドバーからファイルをアップロードしてください")
    st.stop()

# DuckDB接続（セッション内で共有）
if "con" not in st.session_state:
    st.session_state.con = duckdb.connect(":memory:")
con = st.session_state.con

# ファイルをテーブルに登録
ext = uploaded.name.split(".")[-1]
if ext == "csv":
    con.execute(f"CREATE OR REPLACE TABLE data AS SELECT * FROM read_csv_auto(?)", [uploaded.getvalue()])
else:
    con.execute(f"CREATE OR REPLACE TABLE data AS SELECT * FROM read_parquet(?)", [uploaded.getvalue()])

# スキーマ取得
schema_df = con.execute("DESCRIBE data").df()
schema_text = schema_df.to_markdown(index=False)

# 質問入力
question = st.text_input("質問を入力", placeholder="先月のカテゴリ別売上トップ5を教えて")
if question:
    with st.spinner("Geminiが分析中..."):
        # コストルーティングして実行
        model = pick_model(question)
        result = execute_with_self_correction(question, schema_text, con)

    # 結果表示
    st.subheader(result.plan.intent)
    st.code(result.plan.sql, language="sql")

    # 自動可視化
    df = result.df
    if result.plan.chart_type == "bar" and len(df.columns) >= 2:
        fig = px.bar(df, x=df.columns[0], y=df.columns[1])
        st.plotly_chart(fig, use_container_width=True)
    elif result.plan.chart_type == "line":
        fig = px.line(df, x=df.columns[0], y=df.columns[1])
        st.plotly_chart(fig, use_container_width=True)
    else:
        st.dataframe(df, use_container_width=True)

    st.caption(f"使用モデル: {model} / 試行回数: {result.attempts}")
```

`streamlit run app.py` で起動すると、ローカルブラウザで動くデータエージェントが手に入ります。

## 全体を組み合わせて感じた「設計の効き目」

ここまで紹介した三つの責務分離（生成・実行・修正）が効いてくるのは、**問題が起きたときの調査が一瞬で終わるようになる**点です。たとえば「結果が空で返ってくる」と気づいたとき、`result.plan.sql` を見ればクエリが `WHERE date >= '2025-01-01'` で絞りすぎていた、と数秒でわかります。逆に SQL は正しいのに DuckDB が `out of memory` を返してきた、という別の問題のときは `result.attempts` が 3 回まで上がっていることが先に目に入るので、「これはアプリ側ではなくデータ規模の問題だ」と判断が早くなります。

LLM を本番で使うときに私が一番恐れているのは、**「Gemini は何かを答えてくれているのに、その答えが間違っている」** という状況です。SQL のように検証可能な出力に翻訳しておくと、「動いた」「動かなかった」の二値で正誤が確定するため、デバッグループが回ります。自然言語の答えだけを返す設計だと、間違いが間違いのまま運用に流れ込みます。この設計上の判断は、見えにくいけれど効き目が大きい部分です。

もう一つ書き残しておきたいのは、**`confidence` フィールドの活用**です。Gemini が `confidence < 0.6` を返してきた質問は、実行を一度止めてユーザーに「この理解で合っていますか」と確認を返すフローに分岐させています。これだけで、誤った SQL が静かに走るリスクが体感的に半減しました。LLM に判断させる範囲を広げすぎないこと、確信度が低いときは人間に戻すこと、この線引きを最初から仕込んでおくと、運用に乗せた後の心理的な負担が大きく違います。

## DuckDB ならではの加速ポイント

DuckDB を選んだ恩恵は、ここまで書いたメモリ効率と速度だけではありません。Gemini と組み合わせるうえでも、いくつかの加速点があります。

**Parquet を直接読める**。`SELECT * FROM read_parquet('data/*.parquet')` のようにディレクトリ単位で読み込めるので、月次でファイルが増えていく構成と相性がよいです。Gemini に投げるスキーマを毎回作り直さなくても、テーブル定義は `CREATE OR REPLACE VIEW` で固定しておけば、新しいファイルが入っても自動で取り込まれます。

**`SUMMARIZE` 文が便利**。`SUMMARIZE data` を実行すると、各列の統計量・最小値・最大値・NULL 比率・ユニーク値数が一気に取れます。これを Gemini に渡すコンテキストに含めると、「最頻値が `null` になっている列は分析から外して」のような指示が自然に効きます。私の最新版では、スキーマ抽出時にこの結果も `schema_text` に折り込んでいて、SQL 生成の精度が体感で 10〜15% 上がりました。

**JSON 列を `->` 演算子で直接掘れる**。Stripe のメタデータのように JSON 文字列が入った列がある場合でも、`SELECT metadata->>'$.plan' FROM data` のようにアクセスできます。Gemini にこの構文を学ばせる必要はあるものの、システムプロンプトに「DuckDB 特有の `->` `->>` 演算子を使ってよい」と一行入れておくだけで、自然と使ってくれるようになります。

## 観測性と運用 — 一人運用で「気づける」状態を保つ

個人開発で本番運用するうえで、私が一番気を遣っているのは「何かが壊れていることに、壊れた当日に気づけるか」です。チームで運用しているなら同僚が気づいてくれることもありますが、一人だと自分だけが頼りです。観測の仕組みは最初から薄く入れておくのが結局いちばん安く済みます。

このアプリでは、各クエリ実行時に以下の四つの値を `logs/queries.jsonl` に追記しています。質問文・生成された SQL・実行時間（ミリ秒）・モデル種別・試行回数の五つです。`jsonl` を選んだのは、後から DuckDB で `read_json_auto('logs/queries.jsonl')` をかけて自分のアプリの利用状況を分析できるからで、ここでも DuckDB が活きます。

```python
import json, time
from pathlib import Path

LOG_PATH = Path("logs/queries.jsonl")
LOG_PATH.parent.mkdir(exist_ok=True)

def log_query(question: str, plan: SQLPlan, elapsed_ms: int, model: str, attempts: int):
    LOG_PATH.open("a").write(json.dumps({
        "ts": int(time.time()),
        "q": question,
        "sql": plan.sql,
        "ms": elapsed_ms,
        "model": model,
        "attempts": attempts,
    }, ensure_ascii=False) + "\n")
```

このログを毎週日曜の朝に自分宛のメールで集計しているのですが、見ているのは三つだけです。**「`attempts >= 2` の比率が先週より上がっていないか」「Pro 比率が無意識のうちに上がっていないか」「平均レスポンス時間が伸びていないか」**。この三つさえ追えていれば、致命的な劣化はだいたい初期に捕まえられます。

エラー監視は別系統です。`google-genai` の例外（`google.genai.errors.APIError`）と `duckdb.Error` の二系統だけを Slack に流し、それ以外の `Exception` は標準エラーに出すだけにしています。観測対象を絞ることで、通知の慣れ（毎日鳴っているうちに見なくなる現象）を回避できます。

## エージェントをテストする — 信頼できる状態に育てる

このコードを公開するまで、私は二ヶ月ほど手元で寝かせていました。LLM の出力を含むシステムをどうテストすればいいのかが、最初はよくわからなかったからです。たどり着いた答えはシンプルで、**「決定的な部分を単体テスト、確率的な部分はスナップショット、LLM はブラックボックスとして扱う」** の三つを使い分けるだけでした。

決定的な部分は、思っているより広範囲です。スキーマ抽出ロジック、グラフ種からレンダリングへのマッピング、ファイル保存と読み込み、SELECT 限定のホワイトリスト、コストルータの判定境界——これらはすべて純粋関数として pytest で書けます。私の手元では 30 ケースほどが常時走っていて、リファクタリング時のリグレッションを確実に捕まえてくれます。

```python
# tests/test_router.py
import pytest
from agent.router import pick_model

@pytest.mark.parametrize("question, expected_tier", [
    ("行数は何件？", "flash"),
    ("月別の平均売上は？", "flash"),
    ("コホートごとに30日リテンションを計算し、サインアップ月でウィンドウを切って90日LTVでランキング", "pro"),
])
def test_router_picks_correct_tier(question, expected_tier):
    model = pick_model(question)
    assert expected_tier in model
```

LLM が生成する層（SQL そのもの）には、固定 Parquet と既知の正解結果を持つ 12 個の質問フィクスチャを用意しています。テストはパイプライン全体を実行し、**結果 DataFrame が空でないこと・列数が期待値と合うこと**だけを検証します。SQL がバイト単位で同一かは確認しません。確率的なシステムに対するそんなテストは脆くて意味がありません。実運用で意味があるのは「答えが使い物になっているか」だからです。

このセットで失敗が起きるたびに、失敗した質問をフィクスチャに追加し、プロンプトかシステム指示を直して再実行します。半年運用するうちにフィクスチャは 47 件まで増えました。プロンプトを触るときの心の支えになっています。

## このスタックを選ばないほうがいい場面

逆方向の話も書いておきます。流行に流されて「エージェント SQL」を選ぶと痛い目を見る場面が、確実にあります。

**多テーブルで関係性が複雑な業務データには向きません**。外部キー、ソフトデリート、履歴バージョニングを抱えた 10 テーブル構成は、どの LLM にとっても重すぎます。Gemini はコンパイルは通るが意味的に間違った JOIN を平気で書きます。自己修正ループも意味エラーには気づきません。4〜5 テーブルを超える関係性が必要なら、固定の質問ダッシュボードか、dbt で事前にマートを作っておいて LLM には最終集計だけ書かせるほうが堅実です。

**金融や監査のレポートには使わないでください**。「エージェントが言うには売上は X です」は、SQL を人間が確認しないかぎり、取締役会の資料に載せていい言葉ではありません。このスタックは個人の探索、インディプロダクトの分析、チーム内の好奇心のための道具です。確定申告や投資家向けレポートに載る数字には、SQL を一度書いて Git で管理し、人間がロジックをレビューする運用が必要です。

**本当に大規模なデータ**（数百 GB から PB 級）には別のスタックが必要です。DuckDB は予想以上にスケールしますが、ある時点でオブジェクトストレージ上の列指向、分散実行、ちゃんとしたデータエンジニアリングが欲しくなります。「翻訳役としての Gemini」のパターンはそのまま使えるので、エンジン部分だけ ClickHouse / MotherDuck / BigQuery に差し替える進化路がよいです。

**外部に出したくない PII** を扱う場合も注意が必要です。データ本体は API に流れませんが、スキーマ名は流れます。`medical_diagnosis_icd10` という列名はそれだけで何のテーブルかを語ってしまいます。データ越境や PII の扱いに厳しい制約があるなら、SQL 生成のステップだけローカルモデル（Gemma 3 / Llama など）に移しましょう。パターンは同じで、頭脳だけ差し替える形です。

## 「動く」から「信頼できる」へ育てる

このエージェントは週末で動くものになりました。けれど私が今信頼している状態に到達するまでには、数ヶ月かかっています。その差はほとんど、**「何を間違えがちか」を観察し、その失敗モードを一つずつ潰す**作業の積み重ねでした。

具体的に追加していった補正をいくつか紹介します。

- **通貨を意識した集計の指示**。スキーマテキストに「`amount_usd` 列は USD、`amount_jpy` は JPY」と一行入れるだけで、Gemini が無造作に足し算する事故が消えます
- **タイムゾーンの明示**。同様に「`date` 列は UTC、`tz_local` は JST」と一行。これがないと「昨日」を絞るときに UTC と JST が混ざります
- **ドメイン用語集（glossary.txt）**。「アクティブユーザー」「MRR」「解約」を自分のプロダクトの定義で書き出したファイルをシステム指示に毎回追加します。これがないと教科書的な定義で集計してしまい、私の数え方と合いません

どれも一行二行の変更ですが、それぞれが実際の誤答からの帰還です。時間をかけてこの補正を積んでいくと、エージェントの精度は **「自分が SQL を書いたらこう書く」** に近づいていきます。それこそが、最初に欲しかったものでした。

## 本番で詰まった落とし穴と対処

実装が動いてからも、本番運用で何度かつまずきました。同じ穴に落ちる人が減るように、私の実体験からまとめておきます。

**落とし穴①：Streamlit のセッションが意図せず共有される**。Streamlit はデフォルトでサーバプロセスを共有するため、`st.session_state` の使い方を間違えると別ユーザーの DuckDB コネクションが見えてしまうことがあります。`con = duckdb.connect(":memory:")` を **必ず `st.session_state` 経由でアクセス**するようにしてください。Streamlit Community Cloud にデプロイする前は、シークレットウィンドウで二人分のテストを必ず通します。

**落とし穴②：列名に空白や日本語が混ざるとSQL生成が壊れる**。AdMob や Stripe の CSV はこの罠を確実に踏みます。スキーマ抽出時に `quote_identifier()` で必ずエスケープし、`schema_text` にも引用符付きで含めるようにしてください。

**落とし穴③：100MB を超える Parquet で `read_parquet(?)` がメモリ不足になる**。これは Streamlit が一度ファイル全体をメモリに読むためです。本番では `data/` ディレクトリにファイルを置き、`read_parquet('data/file.parquet')` のようにパス参照で読ませます。`uploaded` を一度ディスクに保存してから `read_parquet` で読み直すパターンが安定します。

**落とし穴④：レート制限（429）で UI が固まる**。Gemini API の自由枠は分間 RPM が決まっており、連続クエリで簡単に当たります。`tenacity` で `retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=2, min=4, max=20))` を `generate_sql` にラップしてください。私の本番では `multiplier=2, min=4, max=20` が体感的に一番自然でした。

**落とし穴⑤：SQL インジェクションを過小評価**。自然言語から SQL を生成する以上、悪意ある入力で `DROP TABLE` を生成される可能性はゼロではありません。実行前に `sql.lower().startswith("select")` で **SELECT 限定**にする防御を必ず入れてください。Gemini に「SELECT 以外を生成するな」と書いても、最終防衛は実行側のホワイトリストです。

## このアプリを毎朝の習慣にする

完成したアプリは、私の場合 `cron` で毎朝 7 時に「昨日の売上トップ10」「異常値の検出」「前年同月比」を実行し、結果を Slack に投げています。Streamlit はそのままダッシュボードとしても使えますし、`streamlit run` を呼ばずに `executor.py` をスクリプトから直接呼ぶ運用もできます。**「思いついたときに開く道具」だけでなく「毎日勝手に動く下働き」**にもなる構造にしておくと、データとの距離が変わります。

技術書で土台を固めたい方には、[実践 Pythonデータサイエンス（Wes McKinney）](https://www.amazon.co.jp/dp/4873119685/?tag=pinocchio-22)が pandas 中心ですが DataFrame 思考の基礎として役立ちます。SQL 側は [達人に学ぶDB設計徹底指南書（ミック）](https://www.amazon.co.jp/dp/4798124702/?tag=pinocchio-22)が、生成されたクエリを「これは適切か」と判断する目を養うのに向いています。

関連する実装パターンとして、[Gemini API × Streamlit で CSV 分析アプリをつくる実装ガイド](/articles/gemini-dev/gemini-api-streamlit-csv-insight-app-production-guide)を先に読むと、Streamlit + Gemini の基礎がさらに固まります。RAG エージェント側の知見は [Gemini 3 Pro × LangGraph データ分析エージェント](/articles/gemini-api/gemini-3-pro-langgraph-data-analysis-agent)で補完できます。

最後に、**この構成は「個人開発者が一人で運用できる範囲」を意図的に守った設計**である、ということだけ書き残しておきます。チームで使う規模になったら、DuckDB の代わりに ClickHouse か MotherDuck、Streamlit の代わりに Next.js + Cloudflare Workers に移すのが自然な進化路だと考えています。けれど一人ではじめるなら、これで十分です。むしろ、軽くて速くて自分で全部把握できる道具のほうが、続けられる気がしています。

このコードと考え方が、同じように「データに振り回されている時間を取り戻したい」と感じている方の、最初の一歩になればと願っています。お読みいただき、ありがとうございました。
