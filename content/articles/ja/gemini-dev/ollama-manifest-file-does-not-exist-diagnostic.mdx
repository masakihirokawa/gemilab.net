Ollamaでモデルを取得しようとすると、このエラーで止まることがあります。

```
Error: pull model manifest: file does not exist
```

「タグ名を直してください」という結論の記事は多いのですが、実際にはタグ名が正しいのに同じエラーが出るケースもあります。ここでは私が仕事場と自宅の両方で何度もぶつかって整理した、**診断フロー**として読める切り分け手順をまとめました。上から順にチェックしていけば、おおよそどの症状に該当するかが10分以内に判別できるはずです。

iOS/Android アプリを 6 本並行運用してきた個人開発者として、この問題に普段から向き合ってきた立場で、要点を整理します。

2014年から個人開発でモバイルアプリを続けてきた立場で見ると、API の選び方は AdMob を含む既存スタックとの相性が鍵です。

## まず最初に：エラーが出た直後の1行

焦って再実行する前に、このコマンドを1回だけ走らせてください。

```bash
ollama --version && ollama list
```

狙いは2つあります。Ollama本体のバージョンを控えておくこと、そしてすでに取得済みのモデルが何かを確認することです。この情報は以降のチェックで何度も参照します。

## チェック1：タグ名の正確性（7割はここで決着）

一番多い原因は、モデル名とタグ名の表記揺れです。Ollamaのモデル名は大文字小文字を区別し、サイズバリエーションのタグまで含めて完全一致が必要です。

```bash
# うまくいかない例
ollama run gemma4
ollama run gemma-4

# 正しい例（サイズ指定タグ必須）
ollama run gemma4:27b
ollama run gemma4:9b
ollama run gemma4:2b
```

ポイントは3つです。モデル名にハイフンを入れない、サイズ指定を省略しない、コロンの前後にスペースを入れない、この3点です。

どのタグが利用可能かを確認するには、[Ollamaのモデルライブラリ](https://ollama.com/library)で該当モデルのページを開き、Tagsタブを見るのが確実です。CLIでも一覧が出ますが、ネットワーク環境によっては空で返ることがあるので、ブラウザで確認するのを私はおすすめしています。

このチェックで解決するなら、以降は読まなくて大丈夫です。解決しないなら次に進んでください。

## チェック2：ネットワーク経路・プロキシ

タグ名が正しいのに同じエラーが出る時、次に疑うのがネットワーク経路です。`manifest: file does not exist` はサーバーが404を返した時にも、プロキシが中継を失敗した時にも同じメッセージになります。

社内ネットワークや学校ネットワークで作業している方は、まずプロキシ経由でも動くかを確認してください。

```bash
# HTTPS プロキシを経由する場合
export HTTPS_PROXY=http://your-proxy.example.com:8080
export HTTP_PROXY=http://your-proxy.example.com:8080

# Ollamaデーモンの再起動が必要
# macOS の場合
pkill ollama
ollama serve &
```

Ollamaはシステム環境変数を継承するので、シェル起動時に `HTTPS_PROXY` が設定されていれば自動で使ってくれます。ただし**すでに起動中のOllamaデーモンには反映されない**ので、再起動を忘れないでください。私はこの落とし穴に2回ハマりました。

家庭のネットワーク経由で出る場合は、レジストリ側（registry.ollama.ai）の一時的な障害の可能性もあります。`curl -I https://registry.ollama.ai` で200が返るか確認してみてください。

## チェック3：ストレージ・権限

ダウンロードの途中でストレージが枯渇したり、権限がない場所に書き込もうとしたりしても、マニフェストの取得失敗として表面化することがあります。

```bash
# Ollamaのモデルストア場所を確認
# macOS: ~/.ollama/models
# Linux: /usr/share/ollama/.ollama/models または ~/.ollama/models
# Windows: %USERPROFILE%\.ollama\models

# 残量を確認
df -h ~/.ollama

# 権限を確認（他ユーザーが root で起動した履歴がないか）
ls -la ~/.ollama/
```

私が一度遭遇したのが、`sudo ollama serve` で起動した履歴のあるマシンで、`~/.ollama/models` がrootオーナーになっていて、一般ユーザーのpullが書き込みで失敗するケースでした。ログには書き込み失敗の詳細は出ず、manifestエラーだけが表示されます。オーナーシップを戻せば解消します。

```bash
sudo chown -R $(whoami) ~/.ollama
```

## チェック4：モデルレジストリの指定

社内で独自のOllamaレジストリを運用していたり、Hugging Face から直接取得するGGUFを指定していたりすると、デフォルトのレジストリと違うパスを見に行くため、タグ名の書式も変わります。

```bash
# Hugging Face から GGUF を直接取得する場合
ollama run hf.co/google/gemma-4-9b-it-gguf:Q4_K_M

# 社内レジストリを使う場合
ollama run registry.internal.example.com/gemma4:27b-custom
```

ここで typo があると `manifest: file does not exist` が出ます。URLのスラッシュ、コロン、タグ部分まで注意深く確認してください。`ollama pull hf.co/...` でpullだけ先に走らせると、ダウンロードの進捗バーが出るかどうかでレジストリまで到達できているかが分かります。

## チェック5：バージョンミスマッチ

Ollama本体のバージョンが古いと、新しめのモデル（Gemma 4 など）のマニフェスト形式を理解できずにエラーが出ることがあります。

```bash
# macOS
brew upgrade ollama

# Linux
curl -fsSL https://ollama.com/install.sh | sh

# バージョン確認
ollama --version
```

経験上、Gemma 4 が公開されてからしばらくの間、古めのOllamaでは manifest エラーで落ちる時期がありました。まずアップデート、そしてデーモン再起動、この順番が確実です。

## 最後の砦：キャッシュを捨てて取り直す

上のどれでも直らない場合の最終手段です。ダウンロード途中のキャッシュが壊れている可能性を潰します。

```bash
# 失敗したモデルのキャッシュを削除
ollama rm gemma4:27b 2>/dev/null

# blob キャッシュもクリア（注意: 他モデルも消える場合がある）
# macOS
rm -rf ~/.ollama/models/manifests/registry.ollama.ai/library/gemma4

# pullし直し
ollama pull gemma4:27b
```

blobファイルまで消すとダウンロードが大きくなるので、まずは manifests ディレクトリ配下だけ削除を試してください。

## 解決後に仕込んでおくと楽になる3つのこと

同じエラーで再度詰まらないよう、私はこの3つを習慣にしています。

**1つ目、`ollama list` を実行するエイリアスを作っておく**。`ol` などの短い別名にしておくと、エラー調査時の最初の1コマンドがすぐ出せます。

**2つ目、よく使うタグを`OLLAMA_DEFAULT_MODEL`のようなメモに残しておく**。記憶に頼るとタイポで時間を溶かします。

**3つ目、Ollamaのバージョンを更新した日付をメモする**。数ヶ月に1度、「前は動いていたのに」という相談が自分に来たときに、どのバージョンから変わったかを振り返れます。

## 最短で決着させたい方向けの1行サマリ

この記事の内容を1行でまとめると、「**タグ名の完全一致を確認 → プロキシ環境ならデーモン再起動 → 権限とストレージ確認 → バージョン確認 → キャッシュクリア**」の順番で切り分ける、ということになります。

Gemma 4をローカルで本格運用するなら、取得後の推論速度最適化やVRAM管理も避けて通れません。そちらに進まれる方は、姉妹記事の[Gemma 4をOllamaやLM Studioで動かすときのよくあるエラーと解決策](/articles/gemini-dev/gemma-4-ollama-lm-studio-local-run-troubleshooting)もあわせて読んでみてください。
