## Gemini APIでアクセシビリティ監査を自動化する意義

Webアクセシビリティの確保は、もはやオプションではありません。2026年4月の改正障害者差別解消法の完全施行を受け、日本国内でも民間企業に合理的配慮の義務化が進んでいます。海外ではADA（アメリカ障害者法）やEAA（欧州アクセシビリティ法）の適用拡大により、WCAG 2.2への準拠が事実上の国際標準となりました。

しかし、WCAG 2.2には78の達成基準があり、手動で全ページをチェックするのは膨大な工数がかかります。ここでGemini APIのマルチモーダル能力が役立ちます。HTMLコードの解析に加え、スクリーンショットの画像認識を組み合わせることで、既存のルールベースツール（axe、Lighthouse）では見つけにくい**視覚的なアクセシビリティの問題**まで検出できるのです。

この記事では、Gemini APIを使ったアクセシビリティ監査システムの構築方法を、Pythonの実装コード付きで解説します。

## WCAG 2.2 の基本と自動チェックの範囲

WCAG 2.2 の達成基準は、大きく4つの原則に分類されます。

- **知覚可能（Perceivable）**: テキスト代替、キャプション、色のコントラスト比
- **操作可能（Operable）**: キーボード操作、十分な時間、発作の防止、ナビゲーション
- **理解可能（Understandable）**: 読みやすさ、予測可能性、入力支援
- **堅牢（Robust）**: HTMLの適合性、支援技術との互換性

このうち、自動ツールでチェックできるのは全体の約30〜40%とされています。残りは人間の判断が必要ですが、Gemini APIのマルチモーダル能力を使えば、従来の自動ツールでは対応できなかった**視覚的レビュー**の一部も自動化でき、カバー範囲を大幅に広げることが可能です。

## HTMLコード解析によるWCAG違反の検出

最初のアプローチとして、HTMLソースコードをGemini APIに送信し、WCAG違反を検出するスクリプトを実装します。

```python
def audit_html_accessibility(url: str) -> dict:
    """URLのHTMLを取得してGemini APIでアクセシビリティ監査を実行"""
    
    # Playwrightでページを取得
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page()
        page.goto(url, wait_until="networkidle")
        html_content = page.content()
        browser.close()
    
    # HTMLが大きすぎる場合は主要部分を抽出
    soup = BeautifulSoup(html_content, "html.parser")
    
    # 不要なスクリプト・スタイルを除去
    for tag in soup(["script", "style", "noscript"]):
        tag.decompose()
    
    clean_html = str(soup)[:30000]  # トークン制限を考慮
    
    prompt = f"""あなたはWCAG 2.2のエキスパートです。
以下のHTMLコードをアクセシビリティの観点から監査し、
JSON形式でレポートを生成してください。

チェック項目:
1. img要素のalt属性の有無と適切さ
2. フォーム要素のlabel関連付け
3. 見出しの階層構造（h1→h2→h3の順序）
4. ランドマークロール（nav, main, footer等）の使用
5. ARIA属性の正しい使用
6. リンクテキストの明確さ（「こちら」「詳細」のような曖昧なテキストの検出）
7. lang属性の設定
8. tabindexの不適切な使用

出力フォーマット:
{{
  "url": "検査対象URL",
  "violations": [
    {{
      "criterion": "WCAG達成基準番号（例: 1.1.1）",
      "severity": "critical / major / minor",
      "element": "問題のあるHTML要素",
      "description": "問題の説明",
      "recommendation": "修正方法"
    }}
  ],
  "passed": ["合格した項目のリスト"],
  "score": "0-100のスコア"
}}

HTML:
{clean_html}"""
    
    response = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=prompt,
        config=types.GenerateContentConfig(
            temperature=0.1,  # 一貫性のある出力のため低めに設定
            response_mime_type="application/json",
        ),
    )
    
    return json.loads(response.text)

# 実行例
# result = audit_html_accessibility("https://example.com")
# print(json.dumps(result, indent=2, ensure_ascii=False))
```

## スクリーンショットを使ったビジュアル監査

Gemini APIの真価は、マルチモーダル入力によるビジュアル監査にあります。HTMLコードだけでは検出できないコントラスト比の問題やフォーカスインジケーターの視認性を、スクリーンショットから判定できます。

```python
def visual_accessibility_audit(url: str) -> dict:
    """スクリーンショットを使ったビジュアルアクセシビリティ監査"""
    
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page(viewport={"width": 1280, "height": 720})
        page.goto(url, wait_until="networkidle")
        
        # フルページスクリーンショット
        screenshot_bytes = page.screenshot(full_page=True)
        
        # モバイルビューのスクリーンショットも取得
        page.set_viewport_size({"width": 375, "height": 812})
        mobile_screenshot = page.screenshot(full_page=True)
        
        browser.close()
    
    # Base64エンコード
    desktop_b64 = base64.b64encode(screenshot_bytes).decode()
    mobile_b64 = base64.b64encode(mobile_screenshot).decode()
    
    response = client.models.generate_content(
        model="gemini-2.5-pro",  # ビジュアル分析にはProモデル推奨
        contents=[
            types.Part.from_bytes(
                data=screenshot_bytes,
                mime_type="image/png",
            ),
            types.Part.from_bytes(
                data=mobile_screenshot,
                mime_type="image/png",
            ),
            """WCAG 2.2のビジュアル面でのアクセシビリティを監査してください。

以下の項目を重点的にチェックしてください:

1. **色のコントラスト比** (WCAG 1.4.3): テキストと背景色のコントラスト比が
   4.5:1以上（通常テキスト）/ 3:1以上（大きなテキスト）を満たしているか
2. **テキストサイズ** (WCAG 1.4.4): テキストが十分な大きさで読みやすいか
3. **タッチターゲット** (WCAG 2.5.8): モバイルビューでボタンやリンクが
   24x24px以上のターゲットサイズを持っているか
4. **色だけに依存しない情報伝達** (WCAG 1.4.1): エラーメッセージやステータスが
   色のみで区別されていないか
5. **視覚的な見出し階層**: 見出しのサイズ・太さが論理的な階層を反映しているか
6. **レスポンシブ対応**: モバイルビューでコンテンツが切れたり重なったりしていないか

1枚目がデスクトップビュー、2枚目がモバイルビューです。
JSON形式でレポートを生成してください。""",
        ],
        config=types.GenerateContentConfig(
            temperature=0.1,
            response_mime_type="application/json",
        ),
    )
    
    return json.loads(response.text)
```

この方法の強みは、axeやLighthouseでは検出が困難な「デザイン上のアクセシビリティ問題」を発見できる点にあります。たとえば、装飾的なフォントの可読性や、ホバーエフェクトの視認性といった、実際の画面を見なければわからない課題を指摘してくれます。

## Lighthouse × Gemini APIの統合で精度を高める

単体のAI分析だけでなく、Lighthouseの結果をGemini APIに渡すことで、より精度の高い改善提案を得られます。

```python
import subprocess

def combined_audit(url: str) -> dict:
    """Lighthouse + Gemini APIの統合監査"""
    
    # Lighthouseの実行（Node.jsが必要）
    result = subprocess.run(
        ["npx", "lighthouse", url,
         "--output=json",
         "--only-categories=accessibility",
         "--chrome-flags=--headless --no-sandbox"],
        capture_output=True, text=True, timeout=60
    )
    
    lighthouse_data = json.loads(result.stdout)
    
    # アクセシビリティ関連の監査結果を抽出
    a11y_audits = lighthouse_data.get("audits", {})
    failed_audits = {
        k: v for k, v in a11y_audits.items()
        if v.get("score") is not None and v["score"] < 1
    }
    
    # Gemini APIに改善計画の立案を依頼
    prompt = f"""以下はLighthouseのアクセシビリティ監査結果です。
失敗した項目について、優先順位付きの改善計画を作成してください。

各改善項目には以下を含めてください:
- 影響度（critical / major / minor）
- 修正にかかる推定工数（時間単位）
- 具体的な修正コード例
- 修正後に期待されるスコア改善

失敗した監査項目:
{json.dumps(failed_audits, indent=2, ensure_ascii=False)[:10000]}

現在のアクセシビリティスコア: {lighthouse_data.get('categories', {}).get('accessibility', {}).get('score', 0) * 100}点
"""
    
    response = client.models.generate_content(
        model="gemini-2.5-flash",
        contents=prompt,
        config=types.GenerateContentConfig(temperature=0.2),
    )
    
    return {
        "lighthouse_score": lighthouse_data.get("categories", {}).get("accessibility", {}).get("score", 0) * 100,
        "failed_count": len(failed_audits),
        "improvement_plan": response.text,
    }
```

Lighthouseが定量的な指標を提供し、Gemini APIがその結果を人間にわかりやすい改善計画に変換するという、互いの強みを活かした構成です。

より実践的なフロントエンド開発とGemini APIの連携方法については、[Gemini × フロントエンド開発完全ガイド](/articles/gemini-workspace/gemini-frontend-dev-complete-guide) で詳しく解説しています。

from datetime import datetime

## よくある質問（FAQ）

### Q1. Gemini APIのアクセシビリティ監査は、axeやLighthouseの代替になりますか？

完全な代替にはなりません。axeやLighthouseは、DOMの構造を正確に解析し、HTMLの仕様に基づいた厳密なルールチェックを行います。一方、Gemini APIの強みは「コードだけでは判断しにくい視覚的な問題の検出」と「検出結果の人間向けレポート化」です。既存ツールとGemini APIを組み合わせることで、監査の網羅性と改善提案の質を同時に向上させるのが最も効果的なアプローチです。

### Q2. どのGeminiモデルを選べばよいですか？

HTMLコードの解析には `gemini-2.5-flash` で十分な精度が得られます。レスポンス速度も速いためCI/CDパイプラインに組み込みやすいのが利点です。スクリーンショットを使ったビジュアル分析には `gemini-2.5-pro` の使用をおすすめします。画像の細部まで正確に解析する能力が高く、コントラスト比やタッチターゲットの判定精度が向上します。

### Q3. 大規模サイト（数百ページ）でも使えますか？

はい。ただし、APIのレート制限とコストに注意が必要です。大規模サイトでは、まずサイトマップから代表的なテンプレートページ（トップページ、一覧ページ、詳細ページ、フォームページ等）を抽出し、テンプレートごとに1ページずつ監査する方法が効率的です。テンプレートの問題を修正すれば、同じテンプレートを使う全ページに改善が波及します。

### Q4. CI/CDに組み込んで自動実行できますか？

GitHub ActionsやCloudflare Pagesのビルドフックに組み込むことで、デプロイ前の自動チェックが実現できます。Critical判定の違反が見つかった場合にビルドを失敗させるゲートとして活用することで、アクセシビリティの回帰を防止できます。

## まとめ

Gemini APIを活用することで、従来のルールベースツールでは対応しきれなかった視覚面のアクセシビリティ監査を自動化し、改善レポートの生成まで一気通貫で行える仕組みを構築できます。HTMLコードの構造チェックとスクリーンショットのビジュアル分析を組み合わせる手法は、Geminiのマルチモーダル能力ならではの活用法です。
