設計書を Gemini に渡して「これで実装して」と頼んだだけでは、思っていたものとは違うコードが返ってくる経験は、AI コーディングを真面目に使っている方なら一度はあるのではないでしょうか。私も個人開発で何度もその壁にぶつかり、同じ設計書でも前置きの書き方一つで成果物が大きく変わることに気づきました。

Gemini 2.5 Pro を業務と個人プロジェクトの両方で使ってきた中で、「これは毎回書いておく価値がある」と実感した5つの前提を順番にご紹介します。設計書そのものを書き直すのではなく、設計書の前に添えるだけで効く小さな工夫です。

## なぜ設計書をそのまま渡すと実装が外れるのか

人間のエンジニア同士なら、設計書の行間に「会社の慣習」「言語の好み」「プロジェクトの歴史」が共有知として詰まっています。ところが Gemini に渡した瞬間、その行間は真っ白になります。だからモデルは自分の中で最も「それっぽい」解釈に寄せて実装します。これが「悪くはないけど、うちのコードベースとは違う」という違和感の正体です。

設計書は仕様を伝えるためのドキュメントであって、判断の余白を埋めるためのドキュメントではありません。その余白を埋める役割を、これから紹介する5つの前提が担います。

## 前提1: 使う言語とバージョンを最初に明示する

意外と忘れがちですが、ここを書かないと Gemini は「2020 年代の典型的な TypeScript」といった平均的な解答を出してきます。結果として古いランタイム機能を使わなかったり、逆に新しい構文を避けて冗長になったりします。

具体的にはプロンプトの先頭にこう書いておくだけで、返ってくるコードの一貫性が明らかに変わります。

```text
前提:
- 言語: TypeScript 5.4
- ランタイム: Node.js 20 (ES modules)
- テストフレームワーク: Vitest 1.x
- Lint: ESLint 9 (flat config)
```

バージョンを書いた瞬間、Gemini はその生態系に合わせた書き方をしてくれます。たとえば Node.js 20 と明示すると `node:fs/promises` のような修飾付き import を自然に選ぶようになります。些細に見えますが、コードレビューで毎回指摘される量が減るため、積み重ねると大きな時間の差になります。

## 前提2: 既存コードとの関係を地図として示す

新規プロジェクトを除き、実装は必ず既存コードの上に乗ります。Gemini はそのコードを見ていないので、「このファイルは既存のこの層と繋がる」「このモジュールは共通のエラー型を使う」といった関係を示す必要があります。

私は次のような短い地図をプロンプトに添えています。

```text
既存コードとの関係:
- src/core/errors.ts: カスタムエラー型 AppError をここから import する
- src/core/logger.ts: ロガーは getLogger() で取得、console.* は使わない
- src/modules/user/: 新機能はこの配下に module として追加する
- 依存の向き: modules → core のみ許可 (逆方向は禁止)
```

これは [Gemini のプロンプト構造を整える4つの型](/articles/gemini-basics/gemini-prompt-four-structures-when-output-mismatch) で紹介されている「文脈を明示的に与える」考え方の応用です。Gemini は自分がどの場所にコードを置くのかを知った瞬間、嘘の import を減らし、既存の作法に寄せた書き方をしてくれます。

## 前提3: エッジケースを「失敗例」で固定する

仕様書に「異常系はエラーを返す」と書いても、Gemini は人間の読み手と同じようにふんわり受け取ります。何を異常と見なすのか、その境界を固定しない限り、出力は毎回少しずつブレます。

対策として、私はエッジケースを「こう入力されたらこう振る舞う」という表ではなく、「こうなった場合は必ず失敗とする」という失敗側の定義で書くようにしています。

```text
失敗として扱うケース:
- email が未入力、または @ を含まない → ValidationError("invalid_email")
- 同じ email が 5 分以内に 3 回以上来ている → RateLimitError("too_many_attempts")
- DB 書き込みが 2 秒で終わらない → TimeoutError("db_write_timeout")
各失敗は AppError のサブクラスとして送出する
```

成功例より失敗例を先に書くのは、正常系は仕様書本文で既に決まっていることが多いからです。失敗の輪郭を先に固定すると、Gemini は安全側に倒したコードを書いてくれます。Function Calling を併用する場合は、失敗のスキーマを [Gemini Function Calling 完全ガイド](/articles/gemini-dev/gemini-function-calling-complete-guide) に書かれている形でツール定義に混ぜておくと、さらに精度が上がります。

## 前提4: 採用してほしくない実装パターンを列挙する

「こう書いてほしい」より「こう書いてほしくない」を書いたほうが効くことは、AI コーディングではよくあります。肯定形の指示は解釈の幅が広いのに対し、否定形は境界がはっきりしているためです。

```text
避けてほしい実装:
- any 型を新たに追加する (既存箇所の any は別タスクで対応)
- try/catch でエラーを握りつぶす (必ず上位に伝搬させる)
- console.log でのデバッグ出力 (logger.debug を使う)
- Date.now() の直接呼び出し (Clock インターフェース経由にする)
```

特にテスト容易性に関わる項目 (時刻・乱数・I/O) は、最初に明示しないと後から修正する手間が大きくなります。Gemini はこのリストを見た瞬間、該当箇所を避けるコードを書くようになり、レビュー時に指摘する回数が減ります。

## 前提5: 検収基準を読める形で書く

最後に、どうなったら完成とみなすかを、実行可能な形に近づけて書きます。自然文で「ちゃんと動けば OK」と書くと、Gemini はテストを書かずに動くコードを返してくることがあります。

私は次のような形で書いています。

```text
検収基準:
- pnpm test が全件 green になる
- src/modules/user/user.test.ts に以下のケースが含まれる:
  - 正常: 新規作成できる
  - 異常: 同じ email は重複登録できない
  - 異常: email 形式が不正な場合は ValidationError
- 型チェック (pnpm typecheck) が通る
- カバレッジはこの範囲で 80% 以上
```

ここまで書くと、Gemini は実装だけでなく対応するテストケースまで一緒に返してきます。「動くコードがあります」と「検収を通るコードがあります」の差を、人間が毎回翻訳しなくて済むのが大きな恩恵です。

## まとめ

Gemini に設計書を任せる前に前提を整えるのは、ドキュメントを書く手間が増えるように見えて、実は後工程のレビュー・修正時間を削る投資です。私の場合、この5つを定型化してから、設計書の一次実装に対する手戻りが体感で半分以下になりました。

まずは「前提1: 言語とバージョン」だけで構わないので、次の実装依頼のプロンプト冒頭に2〜3行足してみてください。返ってくるコードの落ち着き方が変わるはずです。それを基点に、プロジェクトごとに必要な前提を少しずつ足していくと、自分の「設計書テンプレート」が育っていきます。
