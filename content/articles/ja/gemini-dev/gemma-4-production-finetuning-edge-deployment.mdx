Gemma 4はオープンウェイトモデルとして公開されているため、ダウンロードしてすぐに推論に使えます。しかし、プロダクション環境で本当の価値を引き出すには、ファインチューニングによるドメイン特化、量子化によるリソース最適化、そして安定した推論パイプラインの構築が不可欠です。

## 環境準備とモデル選定

ファインチューニングを始める前に、用途に応じた適切なモデルとハードウェアを選びましょう。

**ファインチューニング対象モデルの選定基準**:

- **E4B**: 消費者向けGPU（RTX 3090/4090、16GB VRAM）でQLoRAファインチューニング可能。Google Colab T4でも動作。モバイル展開が前提の場合に最適
- **26B MoE (A4B)**: QLoRAで約16GB VRAMが必要。ただし、MoEの3Dフューズドエキスパートテンソルはbitsandbytesとの互換性に制限あり。A100/H100推奨
- **31B Dense**: フルファインチューニングにはA100 80GB×2以上が必要。LoRA/QLoRAならA100 40GB×1で可能。最高精度が必要な場合に選択

## LoRAファインチューニングの実装

LoRA（Low-Rank Adaptation）は、モデルの元のパラメータを凍結し、小さなアダプター行列のみを学習する手法です。Gemma 4の31B Denseモデルでも、LoRAなら10GB程度の追加メモリで学習できます。

### 基本的なLoRA設定

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model, TaskType
import torch

# モデルのロード（31B Dense の例）
model_name = "google/gemma-4-31b"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)

# LoRA設定
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                  # ランク（8〜64が一般的）
    lora_alpha=32,         # スケーリング係数（通常 r の2倍）
    lora_dropout=0.05,     # ドロップアウト率
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",  # アテンション層
        "gate_proj", "up_proj", "down_proj",       # MLP層
    ],
    bias="none",
)

# LoRAアダプターを適用
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# 出力例: trainable params: 52,428,800 || all params: 31,052,428,800
# → 全パラメータの約0.17%のみを学習
```

### QLoRA でメモリ使用量を削減

QLoRAは4ビット量子化とLoRAを組み合わせ、VRAM使用量をさらに約60%削減します。

```python
from transformers import BitsAndBytesConfig

# 4ビット量子化設定
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",        # NormalFloat4量子化
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,    # 二重量子化でさらに節約
)

# QLoRAモデルのロード
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,
    device_map="auto",
)
model = get_peft_model(model, lora_config)

# メモリ使用量の確認
print(f"GPU Memory: {torch.cuda.memory_allocated() / 1e9:.1f} GB")
# 31B QLoRA → 約18GB（フル精度の約1/7）
```

**⚠️ 26B MoEモデルのQLoRAに関する注意**: Gemma 4の26B MoEモデルは3Dフューズドエキスパートテンソルを使用しており、bitsandbytesの現行バージョンでは量子化できない場合があります。QLoRAを使う場合はE4Bまたは31B Denseモデルを選択するのが安全です。

### Unslothによる高速ファインチューニング

Unslothは手書きのバックプロパゲーションカーネルにより、標準的なHugging Face学習と比較して2〜5倍の速度向上と50〜80%のメモリ削減を実現します。

```python
from unsloth import FastLanguageModel

# Unsloth経由でモデルをロード
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="google/gemma-4-31b",
    max_seq_length=4096,
    load_in_4bit=True,
)

# LoRAアダプターを追加
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_dropout=0.05,
)

# 学習データの準備（Alpaca形式の例）
from datasets import load_dataset
dataset = load_dataset("your-org/your-dataset", split="train")

# 学習の実行
from trl import SFTTrainer
from transformers import TrainingArguments

trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=TrainingArguments(
        output_dir="./gemma4-finetuned",
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,
        num_train_epochs=3,
        learning_rate=2e-4,
        bf16=True,
        logging_steps=10,
        save_strategy="epoch",
        warmup_ratio=0.1,
    ),
    max_seq_length=4096,
)

trainer.train()
# 期待される出力:
# Training Loss: 0.85 → 0.32（3エポックで収束）
# 学習時間: 約2時間（A100 40GB、データセット10K行の場合）
```

### 量子化レベルの選定ガイド

量子化にはトレードオフがあります。用途に合わせて適切なレベルを選びましょう。

- **Q2_K（2ビット）**: E2B向け。サイズ最小、品質低下あり。IoT・ウェアラブル用途
- **Q4_K_M（4ビット）**: E4B・26B向け。サイズと品質のベストバランス。多くの本番環境に推奨
- **Q5_K_M（5ビット）**: 31B向け。品質重視。サーバーサイドデプロイに最適
- **Q8_0（8ビット）**: 品質劣化ほぼなし。VRAM に余裕がある場合に

## Androidエッジデプロイ

Gemma 4のE2B/E4Bモデルは、Androidデバイスでのネイティブ実行に対応しています。

### Google AI Edge Galleryを使う方法

Google AI Edge Galleryは、Gemma 4モデルをAndroidアプリに統合する最も簡単な方法です。

```kotlin
// build.gradle.kts に依存関係を追加
dependencies {
    implementation("com.google.ai.edge:litert-lm:0.1.0")
}

// Kotlin での推論実行
import com.google.ai.edge.litert.lm.LmInference

class GemmaInference(context: Context) {
    private val inference = LmInference.create(
        context,
        modelPath = "gemma4-e4b-q4.task",
        maxTokens = 1024,
    )

    suspend fun generate(prompt: String): String {
        return inference.generateResponse(prompt)
    }

    // ストリーミング出力
    fun generateStream(prompt: String, onToken: (String) -> Unit) {
        inference.generateResponseAsync(prompt) { partialResult ->
            onToken(partialResult)
        }
    }
}
```

### LiteRT-LM による軽量デプロイ

LiteRT-LM（旧TensorFlow Lite）は、より細かい制御が必要な場合に使います。E2Bモデルは2ビット量子化で1.5GB未満のRAMで動作し、ミドルレンジのスマートフォンでも秒間15〜20トークンの生成速度を実現します。

## プロダクション推論パイプラインの構築

本番環境では、単一モデルの推論だけなく、スケーリング、モニタリング、フォールバックを含む推論パイプライン全体を設計する必要があります。

### vLLMによる高スループット推論サーバー

```python
# vLLM を使った推論サーバーの起動
# 26B MoE または 31B Dense 向け

from vllm import LLM, SamplingParams

llm = LLM(
    model="google/gemma-4-26b-a4b",
    tensor_parallel_size=2,     # GPU 2枚で分散推論
    max_model_len=8192,         # 最大シーケンス長
    gpu_memory_utilization=0.9,
    quantization="awq",         # AWQ量子化で効率化
)

# バッチ推論
prompts = ["Explain quantum computing", "Write a Python function for..."]
params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    max_tokens=2048,
)
outputs = llm.generate(prompts, params)

for output in outputs:
    print(output.outputs[0].text)
```

from fastapi import FastAPI, HTTPException

app = FastAPI(title="Gemma 4 Inference API")

## パフォーマンスモニタリングと最適化

プロダクション環境では、推論パフォーマンスの継続的なモニタリングが不可欠です。

### 主要メトリクスの収集

```python
import time
from prometheus_client import Histogram, Counter, Gauge

# Prometheusメトリクス定義
INFERENCE_LATENCY = Histogram(
    "gemma4_inference_latency_seconds",
    "Inference latency in seconds",
    buckets=[0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0],
)
TOKENS_GENERATED = Counter(
    "gemma4_tokens_generated_total",
    "Total tokens generated",
)
GPU_MEMORY_USAGE = Gauge(
    "gemma4_gpu_memory_gb",
    "GPU memory usage in GB",
)

def monitored_inference(prompt, max_tokens=1024):
    start = time.time()

    output = model.generate(prompt, max_tokens=max_tokens)

    latency = time.time() - start
    INFERENCE_LATENCY.observe(latency)
    TOKENS_GENERATED.inc(len(output.tokens))
    GPU_MEMORY_USAGE.set(get_gpu_memory_gb())

    return output
```

### 最適化チェックリスト

本番環境のパフォーマンスを最大化するためのチェックリストです。

- **KVキャッシュの事前確保**: 最大シーケンス長分のKVキャッシュを起動時に確保し、推論中のメモリアロケーションを回避
- **連続バッチ処理**: vLLMの連続バッチ機能を活用し、複数リクエストを効率的に処理
- **動的バッチサイズ**: リクエスト量に応じてバッチサイズを自動調整
- **モデルウォームアップ**: サービス開始前にダミーリクエストで推論パスを初期化
- **グレースフルシャットダウン**: 処理中のリクエストを完了してからサーバーを停止

## エラーハンドリングとフォールバック戦略

プロダクション環境では、モデル推論が失敗した場合のフォールバック戦略が重要です。

```python
class GemmaInferenceWithFallback:
    def __init__(self):
        self.primary = load_model("gemma-4-31b-dense")   # プライマリ
        self.fallback = load_model("gemma-4-26b-a4b")    # フォールバック
        self.max_retries = 3

    async def generate(self, prompt, **kwargs):
        # プライマリモデルで試行
        for attempt in range(self.max_retries):
            try:
                return await self.primary.generate(prompt, **kwargs)
            except (torch.cuda.OutOfMemoryError, TimeoutError):
                if attempt < self.max_retries - 1:
                    await asyncio.sleep(0.5 * (attempt + 1))
                    continue

        # フォールバックモデルに切り替え
        try:
            return await self.fallback.generate(prompt, **kwargs)
        except Exception as e:
            raise InferenceError(f"All models failed: {e}")
```

## FAQ

### Q: ファインチューニングにはどのくらいのデータが必要ですか？

タスクの複雑さによりますが、一般的には1,000〜10,000サンプルで有意な改善が見られます。高品質なデータ100件の方が、低品質なデータ10,000件より効果的です。まずは少量のデータで検証し、必要に応じてデータセットを拡充してください。

### Q: LoRAとフルファインチューニングのどちらを選ぶべきですか？

ほとんどの場合、LoRA（またはQLoRA）で十分です。LoRAは元のモデルの汎用能力を保ちつつドメイン特化できるため、過学習のリスクが低く、学習コストも大幅に削減できます。フルファインチューニングは、モデルの振る舞いを根本的に変えたい場合（言語の追加など）にのみ検討してください。

### Q: エッジデプロイ時のバッテリー消費は問題になりますか？

E2Bモデルの場合、2ビット量子化によりバッテリーへの影響は最小限です。ただし、連続推論を行う場合はバッテリー消費が顕著になるため、推論リクエストのバッチ化やキャッシュ戦略の導入を推奨します。E4Bモデルはより多くの電力を消費するため、バックグラウンド処理として実行する設計が望ましいです。

### Q: 26B MoEモデルのファインチューニングが失敗する場合の対処法は？

MoEモデルの3Dフューズドエキスパートテンソルは一部のツールと互換性がありません。対処法としては、Unslothを使用する（MoE対応が進んでいる）、31B Denseモデルに切り替える、またはNVIDIA NeMo Automodelを使用する方法があります。
