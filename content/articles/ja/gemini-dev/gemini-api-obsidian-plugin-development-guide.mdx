Obsidian でノートを書いていて、「この長いメモ、要約が欲しい」「関連するノートが他にもあった気がする」と感じたことはないでしょうか。ブラウザを開いて AI Studio や Gemini に貼り付けて、戻ってきてコピペする — この行き来を 1 日に何度もやっていると、せっかくの思考の流れが途切れてしまいます。

私が Obsidian で知的作業をしていて気付いたのは、AI を「別アプリ」から「ノートの内側」に持ち込むだけで、書き心地がまるで変わるということです。幸い Obsidian はプラグインシステムが公開されていて、TypeScript で数十行のコードを書けば、自分のノート環境にぴったり合う AI 機能を埋め込めます。

ここでは、Gemini API を Obsidian プラグインに組み込む開発の流れを、雛形コードから配布前のチェックまで通しで辿ります。Obsidian の API を触ったことがない方でも、最初のプラグインを動かすところまで辿り着ける構成にしています。

## Obsidian プラグインの最小構成と TypeScript 雛形

Obsidian のプラグインは、一言でいえば Electron アプリにロードされる ES モジュールです。`main.ts` と `manifest.json`、それから esbuild の設定ファイルが揃えば動きます。ゼロから組むよりも、公式が配布しているサンプルプラグインを起点にする方が圧倒的に早いです。

```bash
# Obsidian の vault 内にあるプラグインフォルダで作業します
cd /path/to/vault/.obsidian/plugins
git clone https://github.com/obsidianmd/obsidian-sample-plugin.git gemini-assist
cd gemini-assist
npm install
npm run dev  # watch モードで main.js がビルドされる
```

`manifest.json` の `id` をユニークな値（例: `gemini-assist`）に書き換えてから Obsidian を再起動すると、設定 → コミュニティプラグインの画面で自作プラグインをオンにできます。ここから先は `main.ts` を書き足していくだけです。

Obsidian のプラグイン API は `Plugin` クラスを継承するシンプルな設計で、`onload` にコマンド登録や設定タブの追加を書き、`onunload` で後片付けをします。最小構成はこれくらいで始められます。

```typescript
import { Plugin, Notice } from "obsidian";

export default class GeminiAssistPlugin extends Plugin {
  async onload() {
    this.addCommand({
      id: "gemini-hello",
      name: "Gemini: Hello from plugin",
      callback: () => new Notice("Plugin is alive"),
    });
  }
  async onunload() {}
}
```

## Gemini API キーを安全に保存する設定タブ

プラグインから Gemini API を呼ぶには API キーが必要ですが、ソースに直書きするとリポジトリに流出します。Obsidian の `loadData` / `saveData` はプラグイン専用の JSON を vault のノートツリーの外に保存してくれるので、そこに入れておくのが基本です。

```typescript
import { App, PluginSettingTab, Setting } from "obsidian";

interface GeminiSettings {
  apiKey: string;
  model: string;
}

const DEFAULT_SETTINGS: GeminiSettings = {
  apiKey: "",
  model: "gemini-2.5-flash",
};

export class GeminiSettingTab extends PluginSettingTab {
  constructor(app: App, private plugin: GeminiAssistPlugin) {
    super(app, plugin);
  }
  display(): void {
    const { containerEl } = this;
    containerEl.empty();

    new Setting(containerEl)
      .setName("Gemini API Key")
      .setDesc("Google AI Studio で発行したキーを貼り付けてください")
      .addText((t) =>
        t.setValue(this.plugin.settings.apiKey).onChange(async (v) => {
          this.plugin.settings.apiKey = v.trim();
          await this.plugin.saveSettings();
        })
      );

    new Setting(containerEl).setName("Model").addDropdown((d) =>
      d
        .addOptions({
          "gemini-2.5-flash": "gemini-2.5-flash（速い）",
          "gemini-2.5-pro": "gemini-2.5-pro（賢い）",
        })
        .setValue(this.plugin.settings.model)
        .onChange(async (v) => {
          this.plugin.settings.model = v;
          await this.plugin.saveSettings();
        })
    );
  }
}
```

`main.ts` 側では `this.settings = Object.assign({}, DEFAULT_SETTINGS, await this.loadData());` で読み込み、`await this.saveData(this.settings)` で書き戻します。個人で使う分にはこれで十分に実用になります。チーム配布を考えるなら、キー自体は OS の資格情報ストアに逃がす設計が望ましいですが、そのあたりは記事末でもう一度触れます。

## 選択範囲を要約する「AI Summarize」コマンドの実装

最初の実用機能として、エディタで選択中のテキストを要約するコマンドを作ってみます。Obsidian の `Editor` オブジェクトから `getSelection()` で選択範囲を取り、Gemini に渡して、結果を下に追記する流れです。

```typescript
import { Editor, Notice } from "obsidian";
import { GoogleGenAI } from "@google/genai";

async function summarize(apiKey: string, model: string, text: string) {
  const ai = new GoogleGenAI({ apiKey });
  const res = await ai.models.generateContent({
    model,
    contents: `次のノートを日本語で 3 行に要約してください。\n\n---\n${text}`,
    config: { temperature: 0.3, maxOutputTokens: 512 },
  });
  return res.text ?? "";
}

// onload 内で登録
this.addCommand({
  id: "gemini-summarize-selection",
  name: "Gemini: 選択範囲を要約",
  editorCallback: async (editor: Editor) => {
    const sel = editor.getSelection();
    if (!sel) {
      new Notice("テキストを選択してから実行してください");
      return;
    }
    try {
      const summary = await summarize(this.settings.apiKey, this.settings.model, sel);
      editor.replaceSelection(
        `${sel}\n\n> [!summary] Gemini\n> ${summary.replaceAll("\n", "\n> ")}\n`
      );
    } catch (e) {
      new Notice(`Gemini エラー: ${(e as Error).message}`);
    }
  },
});
```

ポイントは 3 つあります。1 つ目は「元のテキストを破壊しない」ことです。`replaceSelection` で置換すると元文が消えるため、上の例では元文を保持してから callout 記法で要約を付け足しています。2 つ目は、`Notice` を使ってユーザーにエラーを知らせること。3 つ目は、Gemini の SDK は Node 用ですが Obsidian は Electron なので `@google/genai` がそのまま動く点です。ブラウザビルドと違い CORS を気にせず済むのは、Obsidian プラグイン開発の大きな利点だと感じています。

## ノート間リンクを Gemini に提案させる実践実装

Obsidian の本領は「ノートをつなぐ」ところにあります。Gemini に「いま書いているノートと関連しそうな vault 内のノート」を提案させると、埋もれていた過去のメモが引っ張り出せます。ここでは埋め込みベクトルを使わず、タイトル一覧をコンテキストとして Gemini に渡す軽量な実装を紹介します。

```typescript
import { Editor, TFile } from "obsidian";

this.addCommand({
  id: "gemini-suggest-links",
  name: "Gemini: 関連ノートを提案",
  editorCallback: async (editor: Editor) => {
    const currentText = editor.getValue();
    const titles = this.app.vault
      .getMarkdownFiles()
      .map((f: TFile) => f.basename)
      .slice(0, 300); // コンテキスト爆発を防ぐため上限を決めます

    const ai = new GoogleGenAI({ apiKey: this.settings.apiKey });
    const res = await ai.models.generateContent({
      model: this.settings.model,
      contents: [
        "以下は vault 内のノートタイトル一覧です。",
        "いま編集中のノートと関連が深そうなものを 5 件だけ、理由と一緒に返してください。",
        "出力は `- [[タイトル]] — 理由` の形式に揃えてください。",
        "",
        `## vault のノート\n${titles.map((t) => `- ${t}`).join("\n")}`,
        "",
        `## 編集中のノート\n${currentText.slice(0, 4000)}`,
      ].join("\n"),
      config: { temperature: 0.2 },
    });
    editor.replaceSelection(`\n## 関連ノート（Gemini 提案）\n${res.text}\n`);
  },
});
```

ノート数が 300 を超える vault では、ベクトル検索で絞り込んでから渡す設計に切り替えた方が結果も安定します。埋め込みベクトルでの本格的な類似検索は [Gemini Embeddings で作る本番向けセマンティック検索の実装ガイド](/articles/gemini-api/gemini-embeddings-semantic-search-production) に具体的な実装を書いているので、プラグインに組み込む際はそちらを参考にしてみてください。

また、生成結果をストリーミングで流したい場合は、Obsidian の `Editor` に逐次書き込みながら `generateContentStream` を使う書き方になります。チャンク単位のエラーや中断処理は [Gemini API ストリーミング応答の制御設計ガイド](/articles/gemini-api/gemini-api-streaming-response-control-chunk-error-ux) で詳しく扱っています。

## 配布前に気をつけたい 3 つの落とし穴

個人の vault で動かす分には気になりませんが、コミュニティプラグインとして配布するときに見落としがちなポイントがあります。私が実際にプラグインをレビュー用に準備した際に引っかかった順に並べておきます。

1 つ目は、**API キーを別ユーザーのマシンで扱う責任**です。`saveData` の JSON は vault の `.obsidian/plugins/<id>/data.json` に平文で保存されます。本人の Mac なら問題になりにくいものの、iCloud で複数端末に同期している vault では他端末にも平文で配られてしまいます。対策として、キーはプラグイン設定に保存するのではなく、起動時にパスワード入力を求めてセッション中だけメモリに保持する選択肢を用意するのが現実的です。Obsidian 公式も、機微な情報は `loadData` に入れないことを推奨しています。

2 つ目は、**リクエスト頻度とコストのコントロール**です。Gemini API は従量課金のため、長文ノートでコマンドを連打すると想定外の課金になります。私は保険として、`gemini-2.5-flash` をデフォルトにしつつ、`maxOutputTokens` を 1,024 未満に設定し、入力トークン数が 20,000 を超えたら `Notice` で警告する実装を入れています。AI 連携プラグイン全般に言えることですが、「便利だから無限に呼んでしまう」構造を避けるのは開発者側の責任だと思っています。

3 つ目は、**Obsidian のメインスレッドをブロックしないこと**です。`await` を素直に書いていれば問題は起きにくいのですが、大きなノートをまとめて処理する場合は UI が固まって見えます。長時間処理は必ず `setTimeout(fn, 0)` で小さく切るか、`Notice` でプログレスを出すようにすると、「壊れた」と誤解されにくくなります。

開発ツールに AI を組み込む設計の考え方は、Chrome 拡張でも同じ構図になります。ブラウザ側で似たことをしたい方は、[Gemini API で作る Chrome 拡張 AI アシスタントの開発ガイド](/articles/gemini-dev/gemini-api-chrome-extension-ai-assistant-guide) も合わせて読むと、キー管理・リクエスト制御のパターンが比較できて参考になるはずです。

## まずは 1 コマンドから始めるのがおすすめです

Obsidian プラグイン開発は、最初にサンプルプラグインを動かしてしまえば、残りは TypeScript の実装だけです。今日できる一歩としておすすめなのは、先ほどの「選択範囲を要約」コマンドを自分の vault に入れてみることです。自分が毎日触るノート環境に AI が埋め込まれる感触を一度体験してしまうと、欲しい機能のアイデアが自然に湧いてきます。

配布を視野に入れる段階まで進んだら、MCP サーバー経由で Gemini を呼ぶ構成にすると、キー管理とツール呼び出しをプラグイン側から切り離せます。その設計は [Gemini API で作るカスタム MCP サーバーの TypeScript 実装ガイド](/articles/gemini-dev/gemini-api-custom-mcp-server-typescript-guide) に全体像を書いているので、将来的に複数プラグインで共通化したくなったら読み返してみてください。
