コードは書けるのに、ドキュメントを書くのが後回しになってしまう——これは多くの開発者に共通する課題だと思います。私自身も、個人プロジェクトのコードは整っているのに README が「TODO: あとで書く」のままになっていたことが何度もありました。

Gemini Code Assist のドキュメント生成機能は、この問題をかなり実用的なレベルで解決してくれます。コードを見てコンテキストを理解した上でドキュメントを生成してくれるので、単なるテンプレート埋めではなく、実際の実装内容に即した説明が出てきます。

今回は JSDoc コメントの自動生成から README、API リファレンス、そして変更履歴まで、VS Code での具体的な使い方を整理します。

## Gemini Code Assist のドキュメント生成ができること

まず全体像を整理します。Gemini Code Assist が対応しているドキュメント生成の種類は大きく4つです。

- **関数・クラスへのコメント挿入**（JSDoc / Google Style Python Docstring / JavaDoc 等）
- **README の生成・更新**（プロジェクト全体の概要・セットアップ手順）
- **API リファレンスの生成**（エンドポイント一覧・型定義・使用例）
- **CHANGELOG の生成**（git commit ログを元にした変更履歴）

これらは VS Code の Gemini Code Assist 拡張機能から呼び出せます。拡張機能のチャット画面で `@workspace` コンテキストを使うと、ファイル単体ではなくプロジェクト全体を見た上でドキュメントを生成してくれます。

## JSDoc コメントを一括生成する

最も手軽に効果を感じられるのが、関数への JSDoc コメント自動挿入です。

```typescript
// ドキュメントコメントが何もない関数
export function calculateTax(
  amount: number,
  taxRate: number,
  applyDiscount: boolean = false
): number {
  const base = applyDiscount ? amount * 0.9 : amount;
  return Math.round(base * taxRate * 100) / 100;
}
```

この関数にカーソルを置いて VS Code のコマンドパレットから「Generate Documentation Comment」を実行するか、チャットで以下のように依頼します。

```
この関数に JSDoc コメントを追加してください。
パラメータの型・役割・戻り値の説明と、使用例を1つ含めてください。
```

生成結果の例：

```typescript
/**
 * 指定された金額に対して税額を計算します。
 *
 * @param {number} amount - 税計算前の金額（円）
 * @param {number} taxRate - 適用する税率（例: 0.1 は 10%）
 * @param {boolean} [applyDiscount=false] - true の場合、10% の割引を適用してから税計算を行う
 * @returns {number} 税込み金額（小数点以下四捨五入）
 *
 * @example
 * // 1,000円に10%の税を適用（割引なし）
 * calculateTax(1000, 0.1); // => 100
 *
 * @example
 * // 1,000円に割引を適用してから10%の税を計算
 * calculateTax(1000, 0.1, true); // => 90
 */
export function calculateTax(
  amount: number,
  taxRate: number,
  applyDiscount: boolean = false
): number {
  const base = applyDiscount ? amount * 0.9 : amount;
  return Math.round(base * taxRate * 100) / 100;
}
```

実装の意図（`applyDiscount` が 0.9 を掛けていること、四捨五入の処理）をコードから読み取った上で説明を生成してくれます。

## ファイル全体のコメントを一括追加する

関数が多いファイルに対して一括でコメントを追加したい場合は、チャットで以下のように依頼します。

```
@ファイル名.ts のすべての export された関数とクラスに JSDoc コメントを追加してください。
既存のコメントは上書きせず、コメントがないものだけに追加してください。
```

「既存のコメントは上書きしない」という指定が重要です。この指定がないと、手動で丁寧に書いたコメントが自動生成のものに置き換わることがあります。

## README を生成・更新する

プロジェクトの README を Gemini Code Assist に生成させる場合は、`@workspace` コンテキストを活用します。

VS Code のチャット画面で：

```
@workspace この Next.js プロジェクトの README.md を生成してください。
以下のセクションを含めてください：
1. プロジェクト概要（2〜3文）
2. 動作環境
3. セットアップ手順（コピー&ペーストで動くコマンド）
4. 主要なコマンド一覧
5. 環境変数の説明（.env.example の内容を参照）
6. ディレクトリ構成の説明
```

この形で依頼すると、プロジェクトのコードを走査した上で実際の package.json・tsconfig.json・ディレクトリ構成を参照して README を生成します。

生成された内容の精度を上げるために確認するポイントは以下です。

- **セットアップ手順のコマンドが実際に動くか**: `npm run dev` ではなく `npm run start:dev` が正しい場合など、package.json と一致しているかを確認
- **環境変数の説明が実際の変数と一致しているか**: `NEXT_PUBLIC_API_URL` の説明が正しいかを `.env.example` と照合する
- **バージョン情報が正確か**: Node.js・パッケージのバージョンが最新の状態を反映しているか

## API リファレンスを生成する

バックエンドのルートハンドラーや API エンドポイントに対して、OpenAPI 形式またはシンプルな Markdown 形式のリファレンスを生成できます。

```
@src/app/api の全エンドポイントについて Markdown 形式の API リファレンスを生成してください。
各エンドポイントについて：
- HTTP メソッドとパス
- 説明（1〜2文）
- リクエストの型定義（TypeScript 型で）
- レスポンスの例（実際の値は省いてもよい）
- エラーケース
を含めてください。
```

Next.js の route.ts ファイルを走査して、実際のリクエスト・レスポンスの型から API リファレンスを生成してくれます。特に型定義がしっかりしているプロジェクトでは、かなり正確なリファレンスが出てきます。

## CHANGELOG を git commit から生成する

変更履歴の管理は地味に手間のかかる作業です。git commit のログを元に CHANGELOG を生成するアプローチが実用的です。

```bash
# まず git log を取り出す
git log --oneline --since="2026-01-01" > /tmp/git_log.txt
```

これをチャットに貼り付けて：

```
以下の git log から CHANGELOG.md のエントリを生成してください。
Conventional Commits 形式（feat / fix / docs / chore）でカテゴリ分けし、
読者が理解しやすい日本語の説明に変換してください。

[git log の内容をここに貼り付け]
```

コミットメッセージが「fix: null check」のような短いものでも、前後のコミットの文脈を参照してある程度の説明を補完してくれます。

## 精度を上げるためのコツ

**① 型情報が多いほど精度が上がる**

TypeScript で型定義が充実しているコードは、Gemini が関数の意図を正確に把握しやすくなります。`any` 型が多いコードでは、生成されたドキュメントも曖昧な記述になりがちです。

**② 複雑なビジネスロジックはコメントで補足する**

「なぜこの処理をするのか」という理由は、コードだけでは Gemini も把握できないことがあります。特に重要なロジックには `// この処理は〇〇のため` という1行コメントを手書きで入れておくと、生成されたドキュメントにその意図が反映されます。

**③ 既存の README のスタイルを参照させる**

「この README のスタイルに合わせて」という指定ができます。OSS プロジェクトの README を参考として渡すと、表現のスタイルや構成を合わせてくれます。

```
@workspace README.md を更新してください。
スタイルは https://github.com/vercel/next.js の README を参考にしてください。
```

## 生成後の確認ポイント

自動生成はあくまで「下書き」として扱うのが安全です。特に確認が必要な箇所は以下です。

- **セキュリティに関わる情報が漏れていないか**: API キーの扱いや認証方法についての記述が不正確でないか
- **バージョン固有の情報が正確か**: Gemini が古い情報を持ち込んでいないかを確認する
- **コードサンプルが実際に動くか**: 生成されたサンプルコードを実行して確認する

今日から試したい方は、まず1つの関数に対して JSDoc コメントの自動生成を試してみてください。生成されたコメントを読んで「自分が書くより伝わりやすい」と感じたら、プロジェクト全体への展開を考える価値があります。
