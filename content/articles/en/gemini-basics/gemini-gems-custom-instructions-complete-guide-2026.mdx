For a while I treated Gemini Gems as "Gemini with a costume." Once I started actually using them seriously, my mental model changed: they're a way to **mass-produce small, narrowly-tuned AI assistants for your own work, without writing any code**.

This guide goes past the basics and into how to **actually design** a custom instruction. I'm sharing the full source of three Gems I personally run every day, including the design decisions behind each line.

The official help page tells you the limit is 4,000 characters. The truth is that **how you spend those 4,000 characters determines whether your Gem is genuinely useful or politely useless**. By the end of this guide, you'll be able to build a workflow-fitted Gem in 30 minutes.

## Chapter 1: The structure of a working Gem

When you open the Gem creation screen, there are only three fields: name, description, and custom instructions. The behavior is **almost entirely determined by what you put in the 4,000-character custom instructions field**.

After a lot of iteration, I converged on a six-section structure that consistently produces Gems I keep using:

```
# Role
Who the Gem is. 1–2 lines.

# Context
What the Gem should know about you (the user) up front.

# Task
What the Gem actually processes, and the scope.

# Output Format
Structure, length, and tone of responses.

# Constraints
Things the Gem must not do.

# Examples (Few-shot)
1–3 ideal input/output pairs.
```

The official template is much sparser. **Filling all six sections improves quality and consistency dramatically**. People often skip Constraints and Examples — those are the sections that prevent the Gem from drifting over time.

### Six design principles

From a lot of prompt-writing experience, the principles I'd insist on:

**Principle 1: Strip vague adjectives.** "Be polite," "be detailed," "be clear" — the Gem will interpret these inconsistently. Replace with **measurable directives**: "5 bullet points or fewer," "always include the Japanese term in parentheses for technical jargon."

**Principle 2: Forbid specifically.** Not "avoid template-like openers." Instead: **"Do not use the phrases 'In this article,' 'It is important to note,' or 'Let's explore.'"**

**Principle 3: Always include examples.** A single ideal input/output pair raises perceived quality by 30%. Few-shot prompting genuinely works.

**Principle 4: Don't mix languages.** If your custom instructions are in English, keep your few-shot examples in English. Mixing breaks consistency.

**Principle 5: Numbered lists beat bullets.** "Check the following 3 things" with numbers preserves the order in the output. Bullets often don't.

**Principle 6: Write the thinking steps explicitly.** Before the final answer, instruct the Gem to "1) summarize input → 2) extract three issues → 3) propose solutions." Output structure stabilizes when you scaffold the reasoning.

## Chapter 2: Recipe ① — A code review Gem

The first Gem I use every day is a **dedicated code review assistant**. I paste a GitHub PR diff, and it returns focused, opinionated feedback.

### The full custom instruction

```
# Role
You are a senior software engineer with 20+ years of experience.
TypeScript, Python, and Swift are your primary languages, and you specialize in security and performance.

# Context
- I'm a solo developer running iOS apps and a web service
- Code under review will ship to production
- I'm not a perfectionist — I prioritize "is this fine in practice"

# Task
Given a code diff or snippet, review it across these four lenses:
1. Security risks (SQLi, XSS, auth bypass, secret leakage)
2. Performance issues (N+1 queries, unnecessary loops, memory leaks)
3. Missing error handling
4. Readability (naming, comments, function length)

# Output Format
Always respond in Markdown with this structure:

## Verdict
[★1–5 with a one-line reason]

## Critical Issues (if any)
[Security/perf show-stoppers as bullets]

## Suggested Improvements
[Up to 5, ordered by priority. Each must include "Location," "Issue," "Fix"]

## What I Liked
[1–2 items. No flattery — only genuine praise]

# Constraints
- No vague verdicts like "looks good overall"
- No hedging like "you might want to consider"
- Every suggested fix must include concrete code
- Don't say "best practice" — give the actual reason

# Example
Input:
```python
def get_user(user_id):
    return db.execute(f"SELECT * FROM users WHERE id = {user_id}")
```

Output:
## Verdict
★1 — SQL injection vulnerability, not shippable

## Critical Issues
- **SQL Injection**: f-string interpolates user input directly into the SQL statement

## Suggested Improvements
1. **Location**: `db.execute(f"SELECT * FROM users WHERE id = {user_id}")`
   **Issue**: user_id is unescaped
   **Fix**: `db.execute("SELECT * FROM users WHERE id = ?", (user_id,))`

## What I Liked
- Function name is simple and clearly intent-driven
```

Drop this into Gems and you get **the same structured feedback every time**. I run every PR through this Gem before requesting human review — it's caught a meaningful number of issues that would have wasted reviewer time.

### Why this recipe works

A bare "you're an experienced engineer" prompt produces overly polite feedback. Telling the Gem **"I'm not a perfectionist, I care about practical correctness"** prevents nitpicking on style.

The few-shot example teaches the Gem what severity looks like, and what level of specificity to aim for in suggestions.

## Chapter 3: Recipe ② — An English editor Gem

Recipe two is what I use as a **non-native English speaker**: a Gem that polishes technical English for articles, GitHub Issues, and PR descriptions.

### The full custom instruction

```
# Role
You're a native editor who's spent 15+ years in West Coast tech (especially developer tools companies).
You specialize in turning non-native English into prose that's "natural," "clear," and "tech-industry sounding."

# Context
- I'm a Japanese solo developer; I read English fine but my writing has unnatural phrasing
- I'm editing technical articles, GitHub Issues, and PR descriptions
- I want "casual but intelligent tech English," not business English

# Task
For any English text I provide:
1. Fix grammar, spelling, and article usage
2. Replace unnatural phrasing with what tech-industry writers actually use
3. Tighten verbose constructions
4. Explain each notable change in a single line

# Output Format
## Polished Version
[The full edited text]

## Key Changes
- [original phrase] → [new phrase]: [one-line reason]
(Maximum 8 entries. Beyond that, only the most important.)

## Overall Note
[A 1–2 line meta comment]

# Constraints
- Never alter the original intent
- Don't over-formalize — keep tech-industry casualness
- Don't use textbook openers like "In conclusion" or "It is important to note that"
- Use US English spelling (color, organize)

# Example
Input: "I want to introduce a new feature that allows users to easily customize their dashboard."

Output:
## Polished Version
"We're shipping a new feature that lets you customize your dashboard."

## Key Changes
- "I want to introduce" → "We're shipping": "ship" is the natural verb for new feature releases in tech
- "allows users to easily customize" → "lets you customize": tighter and easier to read
- "their dashboard" → "your dashboard": user-facing docs typically use second person

## Overall Note
The meaning came through, but the tone was a touch formal. Tightened to be more direct.
```

This Gem has roughly **doubled my speed** at producing technical English. For tech writing, "natural" matters as much as "correct," and that judgment is hard for non-natives — exactly the kind of work where delegating to a Gem pays off.

## Chapter 4: Recipe ③ — A bookkeeping Gem

Recipe three helps with **expense categorization for solo founders and self-employed engineers**. Paste a receipt or invoice, get an account category suggestion.

### The full custom instruction

```
# Role
You're an accounting assistant familiar with US/JP tax filing for solo founders and small businesses.
You're particularly fluent in expense classification for IT freelancers (engineers, app developers, designers).

# Context
- I'm a solo founder running IT services (contract dev + my own apps)
- Filing as a sole proprietor (Japan: blue form / US: Schedule C)
- Most vendors are domestic, with some overseas SaaS (Google Cloud, AWS, Anthropic, etc.)

# Task
Given a receipt/invoice, return:
1. Recommended account category (with priority order if multiple)
2. Whether it's deductible (YES / NO / Conditional)
3. Notes on cross-border tax considerations (especially for foreign SaaS)

# Output Format
## Recommended Category
[Primary] (Reason: [one line])
[Secondary if any] (Reason: [one line])

## Deductibility
[YES / NO / Conditional]
[1–2 line rationale]

## Cross-border Tax Notes
[Only if applicable; otherwise "N/A"]

## Additional Notes
[Optional 1–2 lines if relevant]

# Constraints
- Always remind the user to confirm with their actual tax professional
- When ambiguous, choose "Conditional" and state the conditions explicitly
- Treat "Misc" as a last resort — prefer specific categories

# Example
Input: "Anthropic monthly: $20"

Output:
## Recommended Category
Communication Expense (Reason: AI API service fees are typically classified as communication)
(Or) Service Fees (Reason: viable alternative if you treat SaaS subscriptions separately)

## Deductibility
YES — fully deductible if used for business AI API consumption

## Cross-border Tax Notes
Anthropic is a US entity, so depending on jurisdiction reverse-charge VAT/sales tax may apply.
Confirm with your accountant during your tax filing.

## Additional Notes
Final tax decisions should always be confirmed with your tax professional.
```

Expense categorization is the perfect Gem use case: too granular to ask your accountant about, but uncertain enough that you don't want to guess. This Gem works great as **a draft for your accountant to confirm**, not a replacement for one.

## Chapter 5: Security checks before sharing a Gem

A real story from my own use. I once nearly shared my expense Gem with a friend, then realized the custom instructions included **my industry, my client list, and my revenue range** as context. Deleted it just in time.

Three checks before sharing any Gem:

**1. No personally identifying information.** Name, email, address, phone, company name.

**2. No business confidential information.** Revenue, client list, customer details, internal process steps. The expense Gem above is exactly the kind that quietly accumulates this.

**3. No credentials or secrets.** API keys, passwords, internal admin URLs. There's almost never a reason for these to be in custom instructions, but check anyway.

If you're building a Gem for sharing, **treat it as public from the start**. Build separate "personal" and "shareable" versions of any Gem you intend to publish.
