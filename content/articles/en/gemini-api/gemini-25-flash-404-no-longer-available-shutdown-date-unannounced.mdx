It was a summer evening when I opened the [Gemini deprecations page](https://ai.google.dev/gemini-api/docs/deprecations) to plan the order of a migration. I went looking for the `gemini-2.5-flash` row and stopped at the shutdown column. There was no date in it, only `No shutdown date announced`.

And yet the developer forum had a thread from July 9 reporting that a call to `gemini-2.5-flash` came back with a 404 and the message `This model models/gemini-2.5-flash is no longer available` ([thread](https://discuss.ai.google.dev/t/gemini-2-5-flash-and-gemini-2-5-flash-lite-returning-404-no-longer-available-today-july-9-contradicts-oct-16-2026-shutdown-date/174267)). A separate report described `gemini-2.5-pro` answering that it was [no longer available to new users](https://discuss.ai.google.dev/t/gemini-2-5-pro-returns-no-longer-available-to-new-users-contradicts-official-deprecation-date-oct-16-2026/176380).

I first wrote this piece in August, and I've rewritten it for where things stand in late November, because the November 2 changelog finally spelled out what happens to the 2.5 models. The short version: **effective December 1, 2026, API requests to `gemini-2.5-flash` automatically route to `gemini-3.5-flash-lite`, requests to `gemini-2.5-pro` route to `gemini-3.8-flash`, and both are billed at the target model's rates** (checked against the official deprecations page and changelog on November 28, 2026).

So the model doesn't stop answering. A different model starts answering in its place. If your plan is "fix it when the 404 shows up," you'll miss what actually changes on December 1. Below I walk through what the 404 really was, what tends to break under the routing, and how to check what your own keys can see.

The callouts for 2.5 Flash and 2.5 Pro carry one more sentence that matters: access to the 2.5 models is limited to users who have actively used them in the past. That single line explains most of the 404 reports that started in July.

## The shutdown column is a floor, and the 404 came from somewhere else

Above the tables, the deprecations page has a note: `The shutdown dates listed in the table indicate the earliest possible dates on which a model might be retired`. The date is the earliest a model could go away. It is not a promise that it stays up until then.

In August I came close to reading that table backwards. A blank date, I thought, meant I had time. That didn't hold up. While the column was still blank, keys created more recently had already lost access to the 2.5 models.

The two 404 messages mean different things:

- `no longer available` — the model's door is closed for that caller
- `no longer available to new users` — the result depends on whether the caller used the model before

The second one produces an asymmetry that is unpleasant to debug. The long-lived production project still gets through, while a newer CI or staging key gets the 404. Same code, same model ID, different result, so the cause looks like it lives in your code.

I spent the better part of an afternoon suspecting the SDK version, then the region, then how I was building the request. When you split keys by purpose, they end up created at different times, and that was the whole story. The line I draw now is simple.

**Read deadlines from the page; check what actually works, one key at a time.** The table is input for planning, not a guarantee of behavior.

## What happens to the bill (as of November 2026, from the official pricing page)

The routed requests are billed at the target's rates. Paid-tier prices per 1M tokens, in USD:

<table>
<tr><th>From → to</th><th>Input</th><th>Output (incl. thinking)</th><th>What it means</th></tr>
<tr><td><code>gemini-2.5-flash</code></td><td>$0.30 (text / image / video), $1.00 (audio)</td><td>$2.50</td><td>—</td></tr>
<tr><td>→ <code>gemini-3.5-flash-lite</code></td><td>$0.30 (including audio)</td><td>$2.50</td><td>Same rate for text; audio input gets cheaper</td></tr>
<tr><td><code>gemini-2.5-pro</code></td><td>$1.25 (≤200k tokens), $2.50 (&gt;200k)</td><td>$10.00 / $15.00</td><td>—</td></tr>
<tr><td>→ <code>gemini-3.8-flash</code></td><td>$0.75 through Dec 31, 2026; $1.50 from Jan 1, 2027</td><td>$3.75 / $7.50</td><td>Cheaper now, doubles in January</td></tr>
</table>

For text-only work, routing from 2.5 Flash to 3.5 Flash-Lite leaves the per-token rate unchanged. What can still move is how many output tokens you get back. A different model answers the same prompt at a different length, and a longer answer at the same rate is a bigger bill.

Routing from 2.5 Pro to 3.8 Flash looks cheaper on the rate card. But 3.8 Flash is on introductory pricing, and both input and output double on January 1, 2027. The easy trap is a reassuring December invoice followed by a surprising January one.

## Five minutes to see what your keys can see

Rather than guessing, call `models.list` for each key. If you don't want to add dependencies, `curl` is enough:

```bash
curl -s "https://generativelanguage.googleapis.com/v1beta/models?pageSize=200" \
  -H "x-goog-api-key: YOUR_API_KEY" \
  | grep -o '"name": "models/[^"]*"' \
  | sed 's|.*models/||; s|"$||' \
  | sort
```

If `gemini-2.5-flash` isn't in the list, that key can no longer see it.

**One key is not enough.** Run it against production and against CI or staging, and diff the results. A model visible from only one side is the "past users only" rule showing itself.

```python
#!/usr/bin/env python3
"""Compare models.list between a production key and a CI key, and print models visible to only one."""
import json
import os
import sys
import urllib.request

ENDPOINT = "https://generativelanguage.googleapis.com/v1beta/models?pageSize=200"
WATCH = ("gemini-2.5-flash", "gemini-2.5-pro", "gemini-2.5-flash-lite")


def list_models(api_key):
    names = set()
    url = ENDPOINT
    while url:
        req = urllib.request.Request(url, headers={"x-goog-api-key": api_key})
        with urllib.request.urlopen(req, timeout=30) as res:
            body = json.load(res)
        for model in body.get("models", []):
            if "generateContent" in model.get("supportedGenerationMethods", []):
                names.add(model["name"].replace("models/", "", 1))
        token = body.get("nextPageToken")
        url = ENDPOINT + "&pageToken=" + token if token else None
    return names


def main():
    prod_key = os.environ.get("PROD_API_KEY")
    ci_key = os.environ.get("CI_API_KEY")
    if not prod_key or not ci_key:
        print("Set PROD_API_KEY and CI_API_KEY in the environment", file=sys.stderr)
        return 2

    prod = list_models(prod_key)
    ci = list_models(ci_key)
    only_prod = sorted(prod - ci)
    only_ci = sorted(ci - prod)

    print("Models visible to production key: %d" % len(prod))
    print("Models visible to CI key: %d" % len(ci))
    print("Only in production:", ", ".join(only_prod) if only_prod else "none")
    print("Only in CI:", ", ".join(only_ci) if only_ci else "none")
    for name in WATCH:
        print("%-24s prod=%s ci=%s" % (name, name in prod, name in ci))
    return 1 if (only_prod or only_ci) else 0


if __name__ == "__main__":
    raise SystemExit(main())
```

It keeps only models that support `generateContent`, because mixing in embedding and audio models makes the diff hard to read. It exits with 1 when there's a difference, so you can put it on a schedule and only hear about it on the days something changes. The paging loop is there because the model list keeps growing and nothing guarantees it fits on one page.

The output looks like this (the counts and names depend on your keys, so this only shows the shape):

```text
Models visible to production key: N
Models visible to CI key: M
Only in production: gemini-2.5-flash, gemini-2.5-pro
Only in CI: none
gemini-2.5-flash         prod=True ci=False
gemini-2.5-pro           prod=True ci=False
gemini-2.5-flash-lite    prod=True ci=True
```

I haven't yet confirmed how routed models show up in `models.list` after December 1. So after the switch, I'd look at `modelVersion` in the next section as well, not just this list.

## Settings to remove before the routing kicks in

Auto-routing doesn't rewrite your code. The November 2 changelog lists the breaking API changes: function calling and `thought_signature` validation, `thinking_level` replacing `thinking_budget`, and the removal of sampling parameters and prefilled model turns.

Find the likely spots first:

```bash
grep -rInE 'gemini-2\.5-(flash|pro)\b|thinking_budget|top_p|top_k|candidate_count|"?temperature"?' . \
  --include='*.py' --include='*.ts' --include='*.js' --include='*.kt' --include='*.swift' \
  --include='*.json' --include='*.yaml' --include='*.yml' --include='*.toml'
```

Then rewrite them for the target. Here is a before and after with Python's `google-genai`:

```python
# Before: written for 2.5 Flash (from December 1, 3.5 Flash-Lite receives this)
from google import genai
from google.genai import types

client = genai.Client()
resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="Classify this review as bug, request, or comment: I can't save the wallpaper",
    config=types.GenerateContentConfig(
        temperature=0.2,                                          # ignored on 3.x
        thinking_config=types.ThinkingConfig(thinking_budget=0),  # becomes thinking_level on 3.x
    ),
)
print(resp.text)
```

```python
# After: name the target and record which model actually answered
import os
from google import genai
from google.genai import types

MODEL = os.environ.get("GEMINI_MODEL", "gemini-3.5-flash-lite")

client = genai.Client()
resp = client.models.generate_content(
    model=MODEL,
    contents="Classify this review: I can't save the wallpaper",
    config=types.GenerateContentConfig(
        system_instruction="Answer with exactly one word: bug, request, or comment.",
        thinking_config=types.ThinkingConfig(thinking_level="minimal"),
    ),
)
print(resp.text)
print("requested:", MODEL, "served:", resp.model_version)
```

Three things changed. The model ID comes from an environment variable. Instead of pinning output with temperature, the rules live in the system instruction. And `thinking_budget` became `thinking_level`. `minimal` is the default for 3.5 Flash-Lite; the official migration guide suggests leaving it there for high-volume extraction, routing, or classification, and using `medium` or `high` for subagents that call tools.

If you're moving from 2.5 Pro to 3.8 Flash, one detail differs: 3.8 Flash doesn't support `minimal`. You choose `low`, `medium` (the default), or `high`. Code that calls both 2.5 Flash and 2.5 Pro through one shared config object needs to split here.

## Choosing the target yourself

I'd rather pick the target than let the routing pick it, because then I can explain the choice later. A rough guide:

<table>
<tr><th>Current use</th><th>Candidate</th><th>When to pick it</th></tr>
<tr><td>2.5 Flash for high-volume extraction, classification, translation</td><td><code>gemini-3.5-flash-lite</code></td><td>Same as the routing target, so the least to re-verify</td></tr>
<tr><td>2.5 Flash for tool-heavy agents</td><td><code>gemini-3.5-flash-lite</code> (<code>thinking_level</code> medium/high) or <code>gemini-3.6-flash</code></td><td>Step up to 3.6 Flash if Flash-Lite stops tool loops early</td></tr>
<tr><td>2.5 Pro for long reasoning or code</td><td><code>gemini-3.8-flash</code></td><td>Same as the routing target, if January's rates still fit</td></tr>
<tr><td>2.5 Flash-Lite</td><td>Leave it</td><td>It isn't deprecated, so there's no reason to rush</td></tr>
</table>

When in doubt, **name the routing target yourself, explicitly.** The behavior is the same as the routing, but the model in your code and the model answering now match, which shortens the next investigation when something changes again.

## Three common misreadings

The first is "a blank shutdown date means it's fine for now." As the official note says, the date is the earliest possible retirement, and a blank isn't a guarantee. New keys had already lost access while the column was empty.

The second is "if it routes automatically, I don't need to touch the code." The changelog asks you to update the model string before December 1 and to review the breaking changes in the migration guide. The routing keeps you from falling over; it doesn't do the migration for you.

The third is "2.5 Flash-Lite goes at the same time." The deprecations page says `gemini-2.5-flash-lite` is not deprecated and remains available through the API until further notice. Moving it in a hurry just adds verification work.

## Model IDs outlive the code

Fixing the call sites wasn't the end of it. In my case, the leftovers were mostly outside the code:

- Defaults in config files (the code reads an environment variable, but the fallback is stale)
- Recorded responses in tests, with old model IDs baked in, so the tests stay green
- Code samples I'd written for readers, and my own runbooks
- App Store and Google Play descriptions, and feature pages that say "powered by ..."

The second is the troublesome one. A test replaying a recorded response says nothing when the routing changes the output. I wrote about that shape from the freshness side in <a href="/articles/gemini-dev/gemini-recorded-fixture-model-retirement-freshness-gate">green tests and dead production</a>.

The fourth isn't a technical break, but it keeps handing readers an outdated assumption. When I updated the store description for my wallpaper app across languages, the same sentence was sitting in every locale, and finding each one took longer than I expected. I'd add a plain-text search to the migration checklist.

## What you're likely to hit after the switch

The first thing you notice after December 1 probably won't be an error. It'll be a sense that the answers feel a bit different in tone or length. Logging the requested model next to the one that answered is covered in <a href="/articles/gemini-updates/gemini-flash-auto-routing-requested-vs-served-model-log">the morning Flash started sounding different</a>.

If removing temperature narrows your output range more than you'd like, <a href="/articles/gemini-api/gemini-sampling-params-deprecation-diversity-side-migration">the temperature deprecation hurt diversity before determinism</a> is the natural next step.

And decide in advance how you'll treat the 404 once it arrives. A 404 from a closed model isn't the kind of failure that resolves if you wait; exponential backoff only stacks up waiting time. How that waiting failed to show up in the success-side numbers is in <a href="/articles/gemini-api/gemini-retired-model-permanent-error-queue-wait-measured">retrying a retired model never showed up in success latency</a>.

If you do one thing today, run the diff script above with your production key and your CI key, and see which side can still see the 2.5 models. Wherever a key can't, start there and name the target model explicitly. I'd like December 1 to be a morning when nothing happens, and that's still what I'm aiming for.
