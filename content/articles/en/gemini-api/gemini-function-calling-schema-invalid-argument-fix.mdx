You copy a perfectly working OpenAI Function Calling tool definition, paste it into a Gemini API call, and the very first request comes back with `400 INVALID_ARGUMENT: Invalid JSON payload received. Unknown name "..."`. If that's where you are right now, you're in good company. I had to migrate roughly five different toolsets before the pattern finally clicked for me.

Gemini's Function Calling looks OpenAI-compatible at a glance, but the schema dialect it accepts is meaningfully different. There are about ten JSON Schema keywords that Gemini quietly refuses, and most of them happen to be the ones OpenAI users rely on. This article walks through the specific failures I've personally hit, paired with the minimal fix for each. Every snippet is a real change I shipped after seeing the error.

## The root cause: Gemini accepts a subset of OpenAPI 3.0, not full JSON Schema

The first thing worth internalizing is that `tools.functionDeclarations.parameters` expects a **subset of the OpenAPI 3.0 Schema Object**, not JSON Schema Draft-07. That single fact explains nearly every migration headache.

The supported keywords are surprisingly limited:

- `type` (one of `"string"`, `"number"`, `"integer"`, `"boolean"`, `"array"`, `"object"`)
- `description`
- `enum` (primitive types only)
- `properties` / `required` / `items`
- `format` (a narrow allowlist like `"date-time"`)
- `nullable` (when you need to allow `null`)

Anything else listed below will trigger `INVALID_ARGUMENT` if you pass it as-is:

- `additionalProperties`
- `$ref`, `definitions`, `$defs`
- `anyOf`, `oneOf`, `allOf`
- `const`
- `pattern` (silently ignored on some models)
- `minimum` / `maximum` (accepted but reportedly not enforced)

Keep that allowlist in mind, and the rest of this article becomes a lot easier to follow.

## Case 1: `additionalProperties` triggers a 400

If you're mimicking OpenAI's `strict: true` mode by setting `additionalProperties: false`, Gemini responds with:

```
400 INVALID_ARGUMENT: Invalid JSON payload received.
Unknown name "additionalProperties" at 'tools[0].function_declarations[0].parameters'
```

**Before**:

```python
schema = {
    "type": "object",
    "properties": {"city": {"type": "string"}},
    "required": ["city"],
    "additionalProperties": False,  # Gemini does not understand this key
}
```

**After**: just remove it. Gemini's OpenAPI heritage means it never accepts undeclared properties in the first place.

```python
schema = {
    "type": "object",
    "properties": {"city": {"type": "string"}},
    "required": ["city"],
}
```

If you generate schemas with Pydantic or Zod, the safest pattern is to add a small post-processing step that recursively strips `additionalProperties` from the output before sending.

## Case 2: `anyOf` and `oneOf` get rejected

A common Union pattern—accept either a string or a number—is almost always rejected when expressed with `anyOf`.

**Before**:

```python
{"value": {"anyOf": [{"type": "string"}, {"type": "number"}]}}
```

Gemini only understands a single `type`, so the practical move is to either commit to one type or **accept a string and parse on the server side**. I almost always go with the second option, and a clear `description` like "pass numbers as strings (e.g. '42')" reliably steers the model in the right direction.

```python
{
    "value": {
        "type": "string",
        "description": "The value. For numbers, pass as a string (e.g. '42', '3.14').",
    }
}
```

You might feel like you're giving up type safety, but Function Calling already requires you to validate the parsed output downstream, so insisting on type branching at the input layer rarely earns its keep.

## Case 3: Mixed-type values inside `enum` are silently ignored

`enum` is supported, but every value in the array must share the same primitive type.

```python
# ❌ string and integer mixed → the model ignores the enum and free-generates
{"priority": {"type": "string", "enum": ["high", "low", 1, 0]}}

# ✅ stick to a single type
{"priority": {"type": "string", "enum": ["high", "low"]}}
```

The frustrating part is that no error is raised. The model simply starts returning `"medium"` or other off-list values. If you find your enum is being ignored, this type mismatch is the first thing to check.

## Case 4: An `object` declared without `properties`

Declaring `type: "object"` without any `properties` leaves Gemini guessing, and the model often returns an empty `{}` for that field.

```python
# ❌ object with no shape
{"metadata": {"type": "object"}}

# ✅ define at least one property
{
    "metadata": {
        "type": "object",
        "properties": {
            "source": {"type": "string", "description": "Origin of the data"}
        }
    }
}
```

If the field genuinely needs to accept arbitrary JSON, it's more reliable to declare it as `"string"` and instruct the model to pass JSON text, then call `json.loads()` on the server side.

## Case 5: Pydantic-generated schemas contain `$ref`

Pydantic v2's `model_json_schema()` emits nested models as `$ref` references. Gemini cannot resolve those.

```python
from pydantic import BaseModel

class Address(BaseModel):
    city: str

class User(BaseModel):
    name: str
    address: Address

print(User.model_json_schema())
# → contains {"$ref": "#/$defs/Address", ...}
```

**Fix**: dereference `$ref` before sending. A small recursive helper covers most cases:

```python
def dereference(schema: dict, defs: dict) -> dict:
    """Recursively expand $ref and strip Gemini-incompatible keys."""
    if isinstance(schema, dict):
        if "$ref" in schema:
            ref_name = schema["$ref"].split("/")[-1]
            return dereference(defs.get(ref_name, {}), defs)
        return {
            k: dereference(v, defs)
            for k, v in schema.items()
            if k not in ("$defs", "additionalProperties")
        }
    if isinstance(schema, list):
        return [dereference(item, defs) for item in schema]
    return schema

raw = User.model_json_schema()
clean = dereference(raw, raw.get("$defs", {}))
# Pass `clean` to tools.functionDeclarations.parameters
```

This is the same preprocessing step covered in the [Pydantic + Gemini structured output guide](/articles/gemini-api/gemini-api-pydantic-structured-output-type-safe-production); you can reuse it verbatim for Function Calling.

## A minimal sanity-check snippet

Once you've applied the fixes, run this minimal sample (using the `google-genai` Python SDK) to confirm the schema is accepted end-to-end.

```python
from google import genai
from google.genai import types
import os

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

weather_tool = types.Tool(
    function_declarations=[
        types.FunctionDeclaration(
            name="get_weather",
            description="Return the weather for a given city.",
            parameters={
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "City name (e.g. 'Tokyo')"},
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "Temperature unit",
                    },
                },
                "required": ["city"],
            },
        )
    ]
)

response = client.models.generate_content(
    model="gemini-3-pro",
    contents="What's the weather in Tokyo, in Celsius?",
    config=types.GenerateContentConfig(tools=[weather_tool]),
)

print(response.candidates[0].content.parts[0].function_call)
# Expected: name='get_weather' args={'city': 'Tokyo', 'unit': 'celsius'}
```

If this works, your schema is fine. If `function_call` still comes back empty, the issue is usually that the prompt didn't make the tool feel necessary—adding one or two lines to `description` explaining when the tool should be invoked tends to fix it.

## When the schema passes but behavior is still flaky

Once your schema is accepted, three remaining issues account for most flaky behavior.

The first is **model version**. `gemini-2.5-flash` makes noticeably more selection mistakes during Function Calling than `gemini-3-pro`, especially with several tools in parallel. For production, the Pro tier usually earns its cost back.

The second is **thin descriptions**. If the model has nothing to go on beyond the function name and parameter names, it will happily invent argument values. Adding one sentence per field that says "this is what we expect, this is what we don't" makes a surprising difference.

The third is **incomplete error handling on your side**. The companion guides [Gemini API error handling complete guide](/articles/gemini-api/gemini-api-error-handling-troubleshooting) and [Fixing JSON / structured output errors](/articles/gemini-api/gemini-api-json-structured-output-errors-fix) cover the systemic patterns. If you're new to Function Calling itself, the [Function Calling beginner's guide](/articles/gemini-api/gemini-function-calling-guide) gives the broader context that makes this troubleshooting article click.

## What to try next

If you have a freshly migrated OpenAI tool definition, mechanically apply just three fixes—remove `additionalProperties`, replace `anyOf`, dereference `$ref`—and you'll resolve roughly 80% of `INVALID_ARGUMENT` errors. The remaining 20% are usually description or nested-structure issues, which the case-by-case checklist above will guide you through.
