Gemini 2.0 Flash has become my default model for RAG (retrieval-augmented generation). The pricing is low enough that early in a project nobody worries about cost. Then traffic grows, the invoice starts to grow with it, and at some point you're in a budget meeting explaining why a "cheap" model is costing what it is. I've walked this path.

This article lays out the three-tier cache design I use to bring Gemini Flash RAG costs back under control. Putting just the first tier in place typically cuts costs by around 30%, and all three together can halve the bill. The best part: none of it is exotic — you can layer it into an existing pipeline without rewriting the retrieval stack.

## Why three tiers

A single RAG request usually spends money in this order:

1. **Query embedding** — convert the question to a vector
2. **Vector search** — query the vector DB
3. **Prompt completion** — send context + question to the model

Step 3 dominates cost, step 2 is second. A tiered cache lets you skip each step independently when possible:

- **L1: response cache** — identical question, skip the LLM entirely
- **L2: retrieval cache** — semantically similar question, reuse the context docs and skip vector search
- **L3: embedding cache** — exact same query string, skip the embed API

Hits cascade top-down: L1 skips everything, L3 only skips the embed. That's the shape of the savings.

## L1: the response cache — this is the big one

Start here. Many production RAG apps have a striking fraction of duplicate questions — on FAQ-style sites I've seen 30%+ exact-hit rates.

```python
import hashlib
import json
import redis

r = redis.Redis(decode_responses=True)
CACHE_TTL = 60 * 60 * 24 * 7  # 7 days

def make_cache_key(query: str, filters: dict) -> str:
    """Deterministic key from normalized query + filters."""
    payload = json.dumps({"q": query.strip().lower(), "f": filters}, sort_keys=True)
    return "rag:resp:" + hashlib.sha256(payload.encode()).hexdigest()

def rag_query_with_l1(query: str, filters: dict):
    key = make_cache_key(query, filters)
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    result = run_rag_pipeline(query, filters)
    r.setex(key, CACHE_TTL, json.dumps(result))
    return result
```

Three things to get right. Normalize whitespace and case (`strip().lower()`) — otherwise "Python hints?" and "python hints?" collide into two cache entries. Include `filters` (tenant, permissions, language) in the key, because those change the answer. Always set a TTL — stale docs returning fresh-looking answers is a credibility hit.

**Safety note:** if responses can contain customer data, you need tenant ID in the key and careful access control on the cache backend. I once almost shipped a bug where two tenants shared a cache namespace; I caught it in staging, but that's the kind of issue you want to design against upfront.

## L2: the retrieval cache — semantic overlap

L1 only helps on exact matches. "How do I add type hints in Python?" and "Python type hint tutorial?" are different L1 keys and each pay the full LLM cost. L2 uses the query embedding to detect semantic duplicates, then reuses the retrieved context.

```python
import numpy as np
from typing import Optional

QUERY_VECTOR_INDEX = load_query_index()  # small side index (FAISS/Chroma)

SIMILARITY_THRESHOLD = 0.92  # above this, treat as "same question"

def l2_lookup(query_embedding: np.ndarray) -> Optional[dict]:
    result = QUERY_VECTOR_INDEX.query(query_embedding, top_k=1)
    if not result.matches:
        return None
    top = result.matches[0]
    if top.score < SIMILARITY_THRESHOLD:
        return None
    return top.metadata  # prior retrieved docs

def rag_query_with_l1_l2(query: str, filters: dict):
    cached = r.get(make_cache_key(query, filters))
    if cached:
        return json.loads(cached)

    qvec = embed_query(query)  # L3 caches this internally

    l2_hit = l2_lookup(qvec)
    if l2_hit is not None:
        docs = l2_hit["docs"]
    else:
        docs = vector_search(qvec, filters)
        QUERY_VECTOR_INDEX.upsert([(str(uuid.uuid4()), qvec, {"docs": docs})])

    answer = generate_with_context(query, docs)
    result = {"answer": answer, "docs": docs}
    r.setex(make_cache_key(query, filters), CACHE_TTL, json.dumps(result))
    return result
```

The 0.92 similarity threshold is a measured value from my domain (technical Q&A). Yours may land between 0.85 and 0.95. Too low and you end up reusing unrelated context — the answer quality drops and you lose trust.

Yes, you still pay for the LLM call — L2 doesn't skip that. But skipping vector search matters, especially on managed vector DBs that charge per query.

## L3: the embedding cache — cheap, quietly effective

L3 just caches embeddings of identical query strings. It isn't glamorous, but on FAQ sites or autocomplete-style input you'll see the same phrases hit again and again.

```python
def embed_query(query: str) -> np.ndarray:
    normalized = query.strip().lower()
    cache_key = "rag:emb:" + hashlib.sha256(normalized.encode()).hexdigest()
    cached = r.get(cache_key)
    if cached:
        return np.frombuffer(bytes.fromhex(cached), dtype=np.float32)
    vec = genai_embed(normalized)
    r.setex(cache_key, CACHE_TTL, vec.tobytes().hex())
    return vec
```

Embed APIs aren't free per token, and 40% duplication at 10k daily queries will add up to real money by end of month.

## Measure hit rates — always

If you don't measure, you can't tune. Put counters on every tier.

```python
from collections import Counter
stats = Counter()

def record_hit(layer: str):  stats[f"hit:{layer}"] += 1
def record_miss(layer: str): stats[f"miss:{layer}"] += 1

def dump_stats():
    total = sum(stats.values()) or 1
    for k, v in sorted(stats.items()):
        pct = v / total * 100
        print(f"{k}: {v} ({pct:.1f}%)")
```

A week of my own production data:

- L1 hit rate: 34%
- L2 hit rate (of L1 misses): 18%
- L3 hit rate (of L2-eligible requests): 42%

L1 alone removes a third of all LLM calls — it's the biggest single lever. L2's hit rate is threshold-sensitive, so tune over time.

## Pitfalls I've hit

**Stale answers after content updates.** Build an invalidation path for L1 before you need it: tag cache entries with the doc IDs they reference, and invalidate all entries for a doc when it changes.

**Tenant cross-contamination.** Put tenant ID in L1 and L2 keys, full stop. This is the one bug you really don't want to ship.

**Embedding model upgrades.** Swap models and your L2 index is subtly wrong — the old vectors are incompatible with new queries. Either include the model version in L2 keys or drop L2 entirely on the day of the swap.

## Next step

Flash cost reduction moves more through caching than through model swaps. Turn on L1 for a week, watch the hit rate, and you'll know instantly how much optimization headroom your RAG has. That number makes the case for L2 and L3 much easier to build.
