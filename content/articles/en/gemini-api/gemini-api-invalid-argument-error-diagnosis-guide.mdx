An `INVALID_ARGUMENT` (HTTP 400) response from the Gemini API is one of those errors that looks simple but hides a surprising amount of variety. An auth failure is usually easy to narrow down, but this one fires whenever *anything* in your request is something the API cannot accept — and the message rarely spells out which field is the culprit.

I once spent close to 30 minutes combing through `generationConfig` before I realized I had simply typed the model name wrong. This article is the checklist I wish I had that day. Walk through the seven causes below from the top, and you should land on the real problem within a few minutes in most cases.

## Why INVALID_ARGUMENT is harder to diagnose than it looks

Gemini errors are classified by HTTP status plus a `status` field. `INVALID_ARGUMENT` is the catch-all 400 — it means "the API could not accept some part of your request," which covers an enormous surface area.

A typical response looks like this:

```json
{
  "error": {
    "code": 400,
    "message": "Request contains an invalid argument.",
    "status": "INVALID_ARGUMENT"
  }
}
```

When `message` is just `Request contains an invalid argument.`, the server does not give you much to go on. But when it contains something more specific like `Please use a valid role: user, model`, there is almost always a concrete hint inside. Reading the full `message` string carefully — and always logging it on your side — is step zero.

## Three causes in the request basics

In my own work, the majority of INVALID_ARGUMENT errors come from the request basics: the model name, the `generationConfig`, and the order of messages. These are usually "look and you will see it" mistakes, so it pays to knock them out first.

### Cause 1: typos and generation mismatches in the model name

Start by doubting the model name. Gemini iterates fast, and these patterns trip people up all the time:

- `gemini-2.5-pro` written as `gemini-25-pro` (missing period)
- Old pinned versions like `models/gemini-2.5-flash-001` that no longer exist
- Aliases that do not exist, such as `gemini-flash-latest`

```python
# A working model spec (as of April 2026)
import google.generativeai as genai
import os

genai.configure(api_key=os.environ["GEMINI_API_KEY"])

# BAD: gemini-25-pro / gemini-2-5-pro / gemini-pro (deprecated)
# OK:  gemini-2.5-pro / gemini-2.5-flash / gemini-3-pro
model = genai.GenerativeModel("gemini-2.5-pro")
resp = model.generate_content("Hello")
print(resp.text)
# Expected: "Hello! How can I help you today?"
```

A strict "model name is invalid" error can also come back as `NOT_FOUND` (404), but depending on the SDK version it may be collapsed into `INVALID_ARGUMENT`. The fastest check is to open the official model reference and compare the string character by character. If you are dealing with deprecated models, the [Gemini API model deprecation and migration guide](/articles/gemini-api/gemini-api-model-not-found-error-fix-2026) pairs well with this article.

### Cause 2: out-of-range values in generationConfig

The next most common cause is sending values outside the allowed range. `temperature` is 0.0–2.0, `top_p` is 0.0–1.0, and `top_k` must be a positive integer. Apps that pipe UI slider values or environment variables straight into the API often end up here.

```python
# Out-of-range values (returns 400 INVALID_ARGUMENT)
bad_config = {
    "temperature": 3.0,      # BAD: max is 2.0
    "top_p": 1.5,            # BAD: max is 1.0
    "max_output_tokens": 0,  # BAD: must be at least 1
}

# Fixed
good_config = {
    "temperature": 1.0,
    "top_p": 0.95,
    "top_k": 40,
    "max_output_tokens": 2048,
}

model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config=good_config,
)
```

If you accept config from untrusted input, validate before the API call. It is far cheaper than chasing intermittent 400s in production.

### Cause 3: a broken role sequence in `contents`

When you send chat-style messages, Gemini expects `user` and `model` roles to alternate. Two `user` messages in a row, or a conversation that starts with `model`, will trip the API with messages like `Please use a valid role` or `First content must have role user`.

```python
# BAD: two user messages in a row
bad_contents = [
    {"role": "user", "parts": ["Question 1"]},
    {"role": "user", "parts": ["Question 2"]},  # no model turn in between
]

# OK: user -> model -> user
good_contents = [
    {"role": "user", "parts": ["Hello"]},
    {"role": "model", "parts": ["Hello! How can I help?"]},
    {"role": "user", "parts": ["Teach me about Python async"]},
]

resp = model.generate_content(good_contents)
print(resp.text)
```

If you maintain chat history yourself, add a one-line guard that checks the previous role before appending a new message. For more failure modes in this area, see [Fixing common Gemini API chat history errors](/articles/gemini-api/gemini-api-chat-history-management-errors-fix).

## Two causes around multimodal inputs and structured output

Errors also cluster in two places that depend heavily on spec details: attaching files, and asking for JSON back.

### Cause 4: MIME type and size violations when attaching files

The usual suspects for multimodal inputs are:

- Using an unsupported MIME type (for instance `text/x-markdown` is not accepted)
- Sending a file larger than 20 MB as `inline_data`
- Declaring a MIME type that does not match the actual bytes (claiming `image/jpeg` for a PNG)

Large files should be uploaded via the Files API and referenced by the returned object. If you are tangled up on the Files API side, [Common Gemini Files API errors and fixes](/articles/gemini-api/gemini-api-files-api-troubleshooting-guide) covers that in detail.

```python
# Typical BAD code: sending a 20MB+ image inline
import base64

with open("huge_image.png", "rb") as f:
    data = base64.b64encode(f.read()).decode("utf-8")

bad_parts = [
    {"inline_data": {"mime_type": "image/png", "data": data}},
    {"text": "Describe this image"},
]
# -> 400 INVALID_ARGUMENT: Request payload size exceeds limit

# OK: upload via Files API and reference the URI
uploaded = genai.upload_file(path="huge_image.png", mime_type="image/png")
resp = model.generate_content([uploaded, "Describe this image"])
print(resp.text)
```

Keeping a small helper that checks size and sniffs MIME before every upload is one of the cheapest wins — in practice it cuts production 400s roughly in half.

### Cause 5: mismatched response_mime_type and response_schema

When you want JSON back, errors often come from the `response_mime_type` / `response_schema` pair. Any value other than `application/json` will cause the whole schema to be rejected.

```python
# BAD: typo in mime_type
bad = {
    "response_mime_type": "applications/json",  # typo
    "response_schema": {"type": "OBJECT", "properties": {}},
}

# OK
good = {
    "response_mime_type": "application/json",
    "response_schema": {
        "type": "object",
        "properties": {
            "title": {"type": "string"},
            "score": {"type": "number"},
        },
        "required": ["title"],
    },
}

model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config=good,
)
```

Malformed schemas — not valid JSON Schema, or mixed with OpenAPI dialect — also raise INVALID_ARGUMENT. For a deeper look, pair this section with [Fixing Gemini API structured output errors](/articles/gemini-api/gemini-api-json-structured-output-errors-fix).

## Two causes at the function-calling and deployment boundaries

Finally, two categories that tend to show up only in production — not in local testing.

### Cause 6: format violations in systemInstruction or tool declarations

Function Calling brings its own small minefield of formatting rules for `tools`, `functionDeclarations`, and `systemInstruction`:

- `systemInstruction` passed as a raw string when the model expects `{parts: [...]}` (or vice versa)
- `functionDeclarations` with `parameters` that are not OpenAPI-style JSON Schema
- Tool `name` fields containing `-` or spaces (stick to alphanumerics and underscores)

If the message says `Function declaration "xxx" is invalid`, this is the area to audit. Restricting function names to `[A-Za-z0-9_]+` and always starting parameter schemas with `type: "object"` prevents the majority of these.

### Cause 7: region, model, and feature restrictions

A subtle class of INVALID_ARGUMENT comes from region and feature limits:

- Calling a model via Vertex AI in a region where it is not enabled
- Using features like `thinking_config` or certain tool types with a model that does not support them
- Sending production traffic to a preview-only model

The tell-tale sign is "works locally, breaks on Cloud Run / Cloudflare Workers." The deployed region or runtime differs, and the same code hits a limit the dev box never sees. Inspect your production logs for the actual endpoint, region, and model-feature combination.

## Three habits that shorten the investigation

Three small habits have paid for themselves many times over when hunting these errors:

1. **Always log the full `message`.** Strings like `Please use a valid role` or `Request payload size exceeds limit` are the concrete clues. Do not swallow them in a generic error handler.
2. **Build a minimal repro.** Strip arguments from the failing request one by one until the error disappears. A hand-crafted `curl` or `httpx` call gives you the cleanest picture.
3. **Keep every config change reversible.** Put model name, `generationConfig`, and schema changes in their own commits so `git bisect` can point at the exact change that broke things.

## Start with a seven-point visual check

`INVALID_ARGUMENT` is wide, but it is never unknowable — one of these seven causes is almost always the answer. When a new 400 surfaces, walk through the list above from the top and compare each point against the actual request. Most of the time, the fix lands on the model name, the `generationConfig`, or the `contents` ordering. The faster you narrow it down, the faster the rest of your app can move.
