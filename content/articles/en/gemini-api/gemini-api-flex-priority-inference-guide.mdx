On April 3, 2026, Google introduced two new service tiers to the Gemini API: **Flex Inference** and **Priority Inference**. Alongside the existing Standard tier, developers can now fine-tune the balance between cost and reliability to match their specific use case. This guide walks you through how each tier works, when to use them, and how to implement them with real code examples.

## Understanding Gemini API Inference Tiers

When you send a request to the Gemini API, it gets routed to a compute queue based on priority settings. Until now, all requests used the single Standard tier. Starting April 2026, you can choose from three options:

- **Flex**: 50% cheaper than Standard. Designed for latency-tolerant workloads.
- **Standard**: The default. A balanced option for most use cases.
- **Priority**: 75–100% more expensive than Standard. Built for mission-critical, real-time applications.

Understanding these tiers lets you stretch your API budget further, or ensure rock-solid response times for user-facing features — sometimes both, by mixing tiers strategically within the same application.

## Flex Inference — Cut Costs by 50%

### How Flex Works

Flex Inference offers **50% of the Standard rate**, with the trade-off that responses may take anywhere from 1 to 15 minutes. Unlike the Batch API, Flex requests are synchronous — you use the same endpoints and familiar request patterns. However, when Standard traffic spikes, Flex requests may be interrupted or delayed, so client-side retry logic is essential.

### When to Use Flex

- **LLM-as-a-judge evaluations**: Running regression tests, leaderboard scoring, or automated quality checks
- **Background agents**: CRM updates, content moderation, profile enrichment — tasks where a few minutes of delay is fine
- **Research and experimentation**: Processing large volumes of tokens on a tight budget
- **Batch-style workflows**: Generating draft content, data transformation, log analysis

### Flex Inference in Python

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")

model = genai.GenerativeModel("gemini-2.5-pro")

# Simply set service_tier to "flex"
response = model.generate_content(
    "Summarize and analyze the attached quarterly sales report.\n\n[Report content here]",
    generation_config={
        "service_tier": "flex"  # Enable Flex tier
    }
)

print(response.text)
# Response arrives in 1–15 minutes at ~50% of the standard cost
```

### Flex Inference in JavaScript

```javascript
import { GoogleGenerativeAI } from "@google/generative-ai";

const genAI = new GoogleGenerativeAI("YOUR_GEMINI_API_KEY");
const model = genAI.getGenerativeModel({ model: "gemini-2.5-pro" });

const result = await model.generateContent({
  contents: [{ role: "user", parts: [{ text: "Please summarize this long document." }] }],
  generationConfig: {
    serviceTier: "flex"  // Note: camelCase in JavaScript
  }
});

console.log(result.response.text());
```

### Implementing Retry Logic for Flex (Recommended)

Because Flex can be interrupted during high-traffic periods, you should always include retry logic in production:

```python
import time
import google.generativeai as genai
from google.api_core import exceptions

def generate_with_flex_retry(prompt: str, max_retries: int = 3) -> str:
    """Generate content with Flex tier and automatic retry on interruption."""
    model = genai.GenerativeModel("gemini-2.5-pro")

    for attempt in range(max_retries):
        try:
            response = model.generate_content(
                prompt,
                generation_config={"service_tier": "flex"}
            )
            return response.text
        except exceptions.ServiceUnavailable:
            if attempt < max_retries - 1:
                wait_time = 30 * (attempt + 1)  # 30s, 60s, 90s
                print(f"Flex request interrupted. Retrying in {wait_time}s...")
                time.sleep(wait_time)
            else:
                raise

    return ""

# Example usage
result = generate_with_flex_retry("Generate 5 product description variations.")
print(result)
# Expected: Response arrives within seconds to minutes, at 50% cost
```

## Priority Inference — Maximum Reliability for Critical Apps

### How Priority Works

Priority Inference routes your request to **the highest-priority compute queue**, ensuring minimal latency and the highest throughput reliability. Requests are never dropped — if traffic exceeds dynamic limits, Priority gracefully downgrades to Standard rather than returning a 503 error. The cost is 75–100% higher than Standard, charged per token.

### When to Use Priority

- **Customer service chatbots**: Users are waiting in real time and expect fast, consistent responses
- **Real-time fraud detection**: Payment processing and transaction approval pipelines
- **Premium user features**: High-SLO capabilities in paid tiers of your product
- **Urgent alert systems**: Security or healthcare workflows where any delay matters

### Priority Inference in Python

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")

model = genai.GenerativeModel("gemini-2.5-pro")

# Set service_tier to "priority"
response = model.generate_content(
    "Respond immediately to this user support message: " + user_message,
    generation_config={
        "service_tier": "priority"  # Enable Priority tier
    }
)

print(f"Response: {response.text}")
```

### Detecting Downgrades via Response Headers

When using Priority, it's good practice to monitor whether your request was actually served at the Priority level:

```python
import requests

headers = {
    "Authorization": f"Bearer YOUR_GEMINI_API_KEY",
    "Content-Type": "application/json"
}

payload = {
    "contents": [{"parts": [{"text": "Urgent: generate an immediate response for this critical task."}]}],
    "generationConfig": {
        "serviceTier": "priority"
    }
}

response = requests.post(
    "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-pro:generateContent",
    headers=headers,
    json=payload
)

# Check the x-gemini-service-tier header
actual_tier = response.headers.get("x-gemini-service-tier", "unknown")
print(f"Tier actually used: {actual_tier}")
# "priority" = served at full priority
# "standard" = gracefully downgraded

if actual_tier != "priority":
    # Trigger alerts or fallback logic if needed
    print("⚠️ Request was downgraded from Priority to Standard.")

data = response.json()
print(data["candidates"][0]["content"]["parts"][0]["text"])
```

## Choosing the Right Tier for Your Use Case

Here's a practical breakdown to help you decide:

**Choose Flex when:**
- Processing happens in the background, not in front of a waiting user
- Delays of 1–15 minutes are acceptable
- You're running evaluations, experiments, or batch-style workflows
- You're comfortable implementing retry logic on the client side

**Choose Standard when:**
- Building general web apps or running development/test environments
- Response times of a few seconds to tens of seconds are sufficient
- You want a balanced trade-off between cost and reliability

**Choose Priority when:**
- A user is actively waiting for a response in real time
- Interruptions or slowdowns would damage user experience or business outcomes
- You need to meet high SLO guarantees for a premium product feature
- Reliability and speed matter more than cost

## Cost Strategy: Mix Tiers for Maximum Efficiency

The smartest approach in production is to route different parts of your workflow to different tiers. Consider an application processing 1 million tokens per month:

- Running everything on Standard = baseline cost of 1x
- Moving 40% of background tasks to Flex = ~0.8x total cost (20% savings)
- Adding Priority for 20% of real-time interactions = ~0.84x total cost, with much better UX for key flows

The result: meaningful cost reduction on non-critical tasks, while delivering premium performance where users actually feel it.

## Real-World Architecture: Mixing Tiers in Production

To make tier selection concrete, here's how a typical AI-powered SaaS application might route requests across the three tiers:

**Tier routing by feature type:**

- Chat interface (user-facing, real-time): **Priority** — users expect instant responses
- Document summarization (user-initiated, async): **Standard** — a few seconds is fine
- Nightly data enrichment jobs: **Flex** — runs at 2am, latency doesn't matter
- Automated quality evaluation (CI/CD): **Flex** — batch-style, cost matters most
- Fraud scoring (payment flow): **Priority** — sub-second is critical

This hybrid approach can realistically cut total API spend by 15–30% while simultaneously improving the user experience for high-value interactions. Implementing it doesn't require a major refactor — just add the `service_tier` parameter to each request based on its routing category.

A practical pattern for managing this at scale is to define a thin wrapper around your model client that maps feature flags to tier settings:

```python
from enum import Enum
import google.generativeai as genai

class InferenceTier(str, Enum):
    FLEX = "flex"
    STANDARD = "standard"
    PRIORITY = "priority"

def get_tier_for_feature(feature: str) -> InferenceTier:
    """Route features to appropriate inference tiers."""
    priority_features = {"chat", "fraud_detection", "live_translation"}
    flex_features = {"nightly_enrichment", "evaluation", "report_generation"}

    if feature in priority_features:
        return InferenceTier.PRIORITY
    elif feature in flex_features:
        return InferenceTier.FLEX
    return InferenceTier.STANDARD

def generate_for_feature(prompt: str, feature: str) -> str:
    """Generate content with tier automatically selected by feature."""
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.5-pro")
    tier = get_tier_for_feature(feature)

    response = model.generate_content(
        prompt,
        generation_config={"service_tier": tier.value}
    )
    return response.text

# Examples
chat_reply = generate_for_feature("How do I reset my password?", "chat")
nightly_data = generate_for_feature("Enrich this user profile: ...", "nightly_enrichment")
```

This approach keeps tier management centralized and easy to adjust as your usage patterns evolve.

## FAQ

**Q1. If a Flex request gets interrupted, does the API retry automatically?**

No, automatic retries are not included with Flex. The tier is "best-effort" by design — when Standard traffic increases, Flex requests may be interrupted without a fallback. You need to implement retry logic on the client side, ideally with exponential backoff (e.g., waiting 30s, 60s, 90s between retries).

**Q2. Can a Priority request still end up on the Standard tier?**

Yes, in some cases. When Priority traffic exceeds Google's dynamic limits, requests are gracefully downgraded to Standard instead of returning a 503 error. You can detect this by checking the `x-gemini-service-tier` response header. If your application has strict latency requirements, build monitoring around this header.

**Q3. Do all Gemini models support Flex and Priority tiers?**

As of April 2026, the major Gemini 3, Gemini 3.1, and Gemini 2.5 model families support both tiers. For the latest list of supported models, check the [official documentation](https://ai.google.dev/gemini-api/docs/flex-inference). Note that Flex and Priority currently apply only to synchronous API calls — the Batch API is separate and not affected by these service tier settings.

**Q4. Does the inference tier affect the quality of the generated output?**

No, output quality is identical across all tiers. Flex, Standard, and Priority all use the same underlying model — only the compute queue routing differs. The only thing that changes is response latency.
