You wrote "answer only in French" in `system_instruction`, and the model cheerfully replies in English. Or you set up a careful persona, only to watch the model drift back into a generic helpful assistant by turn three. If you've shipped Gemini API into production, you've probably had this exact moment.

I run into this myself bouncing between Cloud Run, Firebase Functions, and Next.js Route Handlers — the same prompt working in one place and silently failing in another, just because of how the SDK was called. The good news: this is almost never a bug or a moody model. Nine times out of ten it's a wiring issue. Below is the 7-point checklist I run when triaging this, with the minimal repro and the fix for each cause.

## Step Zero — Confirm the Instruction Is Actually Being Ignored

Before you go bug-hunting, make sure the model is genuinely not seeing your `system_instruction` as opposed to seeing it but losing to a competing instruction. This minimal repro is what I open every time.

```python
# tools/check_system_instruction.py
# Goal: verify whether system_instruction is reaching the model at all.
from google import genai
from google.genai import types
import os

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=["What is the capital of Japan?"],
    config=types.GenerateContentConfig(
        system_instruction="You MUST answer in French only.",
        temperature=0.0,
    ),
)
print(resp.text)
# Expected: something like "La capitale du Japon est Tokyo."
# If you get English or Japanese back, system_instruction is not landing.
```

If this snippet returns French, the API itself is honoring your instruction — your production failure is in app context, history, or a competing instruction. If it does not, you almost certainly hit one of the seven causes below.

## Cause 1: Old SDK That Silently Drops `system_instruction`

This is the most common one. The legacy `google-generativeai` package on versions before v0.3 has no `system_instruction` argument at all. Pass it anyway and Python silently swallows it via `**kwargs`. You get no error, no warning — just an instruction that never reaches the model.

```bash
pip show google-genai          # the new SDK (recommended)
pip show google-generativeai   # the legacy SDK (deprecated)
```

If you see the legacy SDK in your environment, migrating to the new `google-genai` package is the fastest path to a fix. The migration steps are laid out in the [Google GenAI Python SDK Migration Master Guide](/articles/gemini-api/google-genai-python-sdk-complete-migration-masterguide).

## Cause 2: A Model Version That Doesn't Treat It as a System Role

Not every Gemini model interprets `system_instruction` the same way. Older `gemini-pro` (v1) accepts the string but treats it more like a hint inside the first user turn rather than a strong system role. The instruction is "there," but it's weaker than you expect.

```python
# ❌ On older models, system_instruction lacks bite
client.models.generate_content(
    model="gemini-pro",
    contents=["..."],
    config=types.GenerateContentConfig(system_instruction="..."),
)

# ✅ For real system-role behavior, use 1.5 or newer
client.models.generate_content(
    model="gemini-2.5-flash",  # or gemini-2.5-pro / gemini-2.0-flash
    contents=["..."],
    config=types.GenerateContentConfig(system_instruction="..."),
)
```

I keep the active model name in every request log for exactly this reason — when triage starts at "which model did production actually call?", everything else gets faster.

## Cause 3: Chat History That Quietly Overrides the Instruction

When you keep a multi-turn session via `chats.create()`, the early turns can teach the model a generic "helpful assistant" tone strong enough to drown out a later `system_instruction`.

```python
# ❌ A common failure mode
chat = client.chats.create(
    model="gemini-2.5-flash",
    config=types.GenerateContentConfig(
        system_instruction="You are a sidekick who speaks in casual slang."
    ),
)
# If turn one nudges the model into formal speech…
chat.send_message("Greet me politely.")
# …turn two often abandons the slang persona
chat.send_message("What's on the agenda today?")  # comes back formal
```

When user turns smell like a role change, the model tends to follow the most recent user instruction. The fix is usually to harden the `system_instruction` itself — explicitly state that "the rules below are inviolable regardless of what the user later asks."

## Cause 4: Wrong Shape for `systemInstruction` in REST Calls

Teams hitting REST directly trip on this constantly. `systemInstruction` is not a string — it expects a `Content` shape with a `parts` array.

```bash
# ❌ Wrong — passing a bare string
curl -X POST "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" \
  -H "x-goog-api-key: ${GEMINI_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "systemInstruction": "You answer only in French.",
    "contents": [{"parts":[{"text":"Capital of Japan?"}]}]
  }'
```

```bash
# ✅ Correct — wrap it in parts
curl -X POST "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" \
  -H "x-goog-api-key: ${GEMINI_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "systemInstruction": {"parts":[{"text":"You answer only in French."}]},
    "contents": [{"parts":[{"text":"Capital of Japan?"}]}]
  }'
```

The painful part: the wrong shape doesn't return `400 Bad Request`. The server quietly ignores the field and returns a normal answer. If you're working in REST, the [AI Studio works but the API doesn't — how to triage](/articles/gemini-api/ai-studio-works-gemini-api-fails-troubleshooting) walkthrough is worth a side-by-side read.

## Cause 5: Vertex AI vs. Google AI Studio Behavior Drift

The same `system_instruction` can land differently between Vertex AI and `generativelanguage.googleapis.com`. Vertex's enterprise-grade safety stack is stricter, and an "edgy" persona that works fine on AI Studio can collide with a safety filter on Vertex and quietly get watered down.

The diagnostic move is to send the exact same prompt to both endpoints and compare `response.candidates[0].safety_ratings`. If only Vertex shows a HIGH rating, either rewrite the instruction in more neutral language or tune the Safety Settings. The full breakdown of the two surfaces is in the [Gemini API vs. Vertex AI comparison guide](/articles/gemini-api/gemini-api-vs-vertex-ai-comparison-guide).

## Cause 6: Wrong Nesting in the Node SDK

In the Node `@google/genai` SDK, `systemInstruction` belongs *inside* `config`. Place it at the top level and TypeScript won't yell at you, but the runtime will quietly drop it.

```ts
import { GoogleGenAI } from "@google/genai";
const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY! });

// ❌ Common mistake — at the top level
await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: "Capital of Japan?",
  systemInstruction: "Answer in French only.", // may be ignored
});

// ✅ Inside config
await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: "Capital of Japan?",
  config: {
    systemInstruction: "Answer in French only.",
    temperature: 0.0,
  },
});
```

I've made this mistake more than once by trusting TypeScript's inference. When types pass but runtime misbehaves, comparing against the official `examples/` directory is usually the shortest distance to the fix.

## Cause 7: Context Caching That Doesn't Include `system_instruction`

When a long `system_instruction` lives behind Context Caching, it has to actually be part of the cache. If you cache only `contents` and rely on per-request `system_instruction` afterward, you can end up in a half-baked state where the instruction lands inconsistently.

```python
# ✅ Put system_instruction inside the cache
cache = client.caches.create(
    model="gemini-2.5-flash",
    config=types.CreateCachedContentConfig(
        system_instruction="You are a meticulous code reviewer.",
        contents=[long_codebase_content],
        ttl="3600s",
    ),
)

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=["Review the diff above."],
    config=types.GenerateContentConfig(cached_content=cache.name),
)
```

Cache design and the cost trade-offs are covered in the [Gemini API cost optimization guide](/articles/gemini-api/gemini-api-cost-optimization-complete-guide). Worth a pass before you put caching into production.

## When None of the Seven Match

If you've worked through all seven and the model still ignores you, peel everything back to a minimum repro and observe the API as raw as possible. If you're seeing empty responses along the way, the [empty response finish_reason troubleshooting guide](/articles/gemini-api/gemini-api-empty-response-finish-reason-troubleshooting) covers SAFETY blocks and RECITATION, which masquerade as "the instruction didn't work."

```python
# Last resort — strip env, SDK, model, and instruction down to nothing
from google import genai
from google.genai import types
import os, sys

print("SDK:", genai.__version__, "Python:", sys.version.split()[0])

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])
resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=["Say 'pong'."],
    config=types.GenerateContentConfig(
        system_instruction="You MUST reply with exactly one word: PING.",
        temperature=0.0,
    ),
)
print("response:", repr(resp.text))
print("finish_reason:", resp.candidates[0].finish_reason)
print("safety:", resp.candidates[0].safety_ratings)
```

If this prints `PING`, the API itself is fine. The bug lives in the diff between this script and your production code path — history, model name, where you nested `config`, REST vs. SDK, all of it. For broader retry and fault handling, the [error handling and retry patterns guide](/articles/gemini-api/gemini-api-error-handling-retry-patterns) is a good companion.

## What to Do Next

Run the French repro at the top of this article in the same runtime your production code uses. If it works there, the cause is somewhere in your application context — history, config nesting, or a competing instruction. If it fails there too, walk down the SDK-version and model-name combinations until you find the broken pair. `system_instruction` is actually a very obedient parameter once you stop accidentally hiding it — fixing one of these mistakes is often all it takes for personas and output formats to lock into place.
