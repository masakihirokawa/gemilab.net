Testing code that calls the Gemini API runs into one problem almost immediately: **generative AI responses aren't deterministic**. A conventional assertion like this will fail unpredictably:

```python
assert response.text == "Python is a general-purpose programming language."
```

The common first instinct is to mock the API calls. But mocks just test the mock — they won't catch it when the actual API response structure changes.

Snapshot testing is a better fit for this problem.

## What Is Snapshot Testing?

Snapshot testing works by recording the expected output on the first run, then comparing against that record on every subsequent run.

```
First run  → save the response as a snapshot
Later runs → compare against the saved snapshot
```

The key insight for AI APIs: you're not asserting exact text content, you're asserting **structure and key fields**. This lets you verify that the response shape hasn't broken even when the generated text varies.

[syrupy](https://github.com/syrupy-project/syrupy) is the standard library for snapshot testing in Python.

## Setup

```bash
pip install syrupy pytest
```

Add a snapshot fixture to `conftest.py`:

```python
# conftest.py
import pytest
from syrupy.assertion import SnapshotAssertion

@pytest.fixture
def snapshot(snapshot):
    return snapshot
```

## Basic Snapshot Test

Start with a simple test that saves the response structure as a snapshot:

```python
# test_gemini_basic.py
import pytest
import google.generativeai as genai

def test_gemini_response_structure(snapshot):
    """Verify the response structure hasn't changed."""
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.0-flash")
    
    response = model.generate_content(
        "What is 2 + 2?",
        generation_config=genai.types.GenerationConfig(
            temperature=0,       # set for reproducibility
            max_output_tokens=100
        )
    )
    
    # Snapshot the structure, not the text
    snapshot_data = {
        "has_text": response.text is not None,
        "finish_reason": str(response.candidates[0].finish_reason),
        "safety_ratings_count": len(response.candidates[0].safety_ratings),
    }
    
    assert snapshot_data == snapshot
```

Run with `--snapshot-update` on the first execution to create the snapshot file:

```bash
pytest test_gemini_basic.py --snapshot-update
```

This creates `__snapshots__/test_gemini_basic.ambr`. On all subsequent runs, drop the flag:

```bash
pytest test_gemini_basic.py
```

## Practical Pattern: Schema Validation

For real applications, the most useful pattern is validating the JSON schema (field presence and types) rather than content:

```python
# test_gemini_structured.py
import pytest
import json
import google.generativeai as genai

def test_gemini_json_output_schema(snapshot):
    """Verify the JSON output schema is maintained."""
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.0-flash")
    
    prompt = """
    Analyze the sentiment of this text and respond in JSON format:
    Text: "I really enjoyed using this product."
    
    Required JSON fields: sentiment (positive/negative/neutral), confidence (0.0-1.0), explanation
    """
    
    response = model.generate_content(
        prompt,
        generation_config=genai.types.GenerationConfig(
            temperature=0,
            response_mime_type="application/json"
        )
    )
    
    parsed = json.loads(response.text)
    
    # Validate schema only — not values
    schema_snapshot = {
        "has_sentiment": "sentiment" in parsed,
        "sentiment_valid": parsed.get("sentiment") in ["positive", "negative", "neutral"],
        "has_confidence": "confidence" in parsed,
        "confidence_is_float": isinstance(parsed.get("confidence"), float),
        "has_explanation": "explanation" in parsed,
    }
    
    assert schema_snapshot == snapshot
```

## Why temperature=0 Isn't Enough

Setting `temperature=0` doesn't make Gemini fully deterministic — the internal sampling isn't guaranteed to produce identical text every time. This means testing text content directly is unreliable even with `temperature=0`.

Design your snapshots around structure and metadata instead:

```python
def test_gemini_response_metadata(snapshot):
    """Test metadata, not text content."""
    # ...
    
    metadata_snapshot = {
        # deliberately exclude response.text
        "finish_reason": str(response.candidates[0].finish_reason),
        "model_used": "gemini-2.0-flash",
        "has_prompt_feedback": hasattr(response, "prompt_feedback"),
    }
    
    assert metadata_snapshot == snapshot
```

## Caching API Calls with vcrpy

Calling the real API on every test run costs money and time. `pytest-recording` with `vcrpy` solves this by recording responses on the first run and replaying them on subsequent runs:

```bash
pip install pytest-recording vcrpy
```

```ini
# pytest.ini
[pytest]
addopts = --record-mode=none   # use cache by default
```

```python
@pytest.mark.vcr
def test_gemini_with_cache(snapshot):
    genai.configure(api_key="YOUR_GEMINI_API_KEY")
    model = genai.GenerativeModel("gemini-2.0-flash")
    
    response = model.generate_content("What is the capital of Japan?")
    
    snapshot_data = {
        "has_response": response.text is not None,
        "finish_reason": str(response.candidates[0].finish_reason)
    }
    
    assert snapshot_data == snapshot
```

Record the first run with `--record-mode=new_episodes`, then rely on the cached cassette files for all future runs.

## When to Update Snapshots

Update your snapshots when:

- You upgrade the Gemini API version and the response structure changes
- You intentionally change a prompt in a way that alters the output schema
- You add new fields to validate

Updating is one flag:

```bash
pytest --snapshot-update
```

Always review the diff afterward to make sure no unintended changes snuck in:

```bash
git diff __snapshots__/
```

## What to Test and What Not to Test

Gemini API testing works best when you're clear about what you're protecting:

- **Text content** — don't snapshot this; it changes legitimately
- **Response structure** — snapshot testing is ideal
- **Error handling** — standard assertions work well
- **Latency and cost** — requires benchmark tests, not unit tests

Use snapshot tests as structural monitors and combine them with other approaches for content verification. Once that division is clear, the design decisions become straightforward.
