"It worked on my machine" is the oldest cliche in software, and nothing revives it faster than shipping a Gemini-powered API to a serverless platform. You push, you wait, the function boots, and suddenly you are staring at a 500 error with almost no context. I have burned a full afternoon on this myself — the first time I moved a personal app's API to Cloudflare Workers, nothing worked until I stopped treating the stack trace as the problem and started working through the real sources one by one.

The good news: once you have seen this failure mode a few times, you realize the cause is almost always one of three things. Environment variables are not loaded. The runtime is not what you think it is. Or the platform's time budget is shorter than Gemini's actual response time. Nine times out of ten, working through those three in order will get you back to green.

## Isolate First: Confirm the Same Code Is Actually Running

Debugging serverless code is painful because logs lag and stack traces are truncated. Before you start chasing the wrong problem, drop a minimal health-check endpoint into your app so you have a reliable observation point.

```ts
// app/api/gemini-health/route.ts (Next.js App Router)
import { GoogleGenerativeAI } from "@google/generative-ai";

export async function GET() {
  const apiKey = process.env.GOOGLE_API_KEY;
  if (\!apiKey) {
    return Response.json(
      { ok: false, reason: "GOOGLE_API_KEY is not defined" },
      { status: 500 }
    );
  }

  try {
    const genai = new GoogleGenerativeAI(apiKey);
    const model = genai.getGenerativeModel({ model: "gemini-2.5-flash" });
    const t0 = Date.now();
    const result = await model.generateContent("reply with just: ping");
    return Response.json({
      ok: true,
      text: result.response.text(),
      ms: Date.now() - t0,
      keyPrefix: apiKey.slice(0, 6), // never expose the full key
    });
  } catch (e: unknown) {
    const err = e as Error;
    return Response.json({ ok: false, name: err.name, message: err.message }, { status: 500 });
  }
}
```

Hit this endpoint from production. Whatever lands in `reason` or `message` is your real starting point. The `keyPrefix` field also tells you whether the deployed environment has a different key than you expect — a surprisingly common cause of "auth errors" that are not really auth errors.

## Cause 1: Environment Variables Are Not Loaded in Production

In my experience this accounts for more than half of serverless failures. Locally, `.env.local` is loaded automatically; on the platform, you have to put the variables in a separate place and sometimes redeploy for them to take effect.

### On Vercel

Go to Settings → Environment Variables and register `GOOGLE_API_KEY` (or whatever key name you use). The critical detail: **Preview and Production are separate scopes**. Setting it only for Production and then wondering why Preview deploys fail is a textbook pattern.

Also, on Vercel **changes to environment variables do not propagate to existing deployments**. Updating the Environment settings does not re-plumb the currently-running instances; you need to trigger a new deploy. The fastest paths are `vercel --prod` from the CLI or pushing an empty commit if you use the GitHub integration.

### On Cloudflare Workers

Never put the key in `wrangler.toml` as plaintext — it ends up in your repo. Use secrets instead.

```bash
# Register a secret for your Worker
wrangler secret put GOOGLE_API_KEY
# Paste the value when prompted

# List the secrets currently attached
wrangler secret list
```

Workers have a subtly different API contract: env vars come in through the function argument (`export default { fetch(req, env) { env.GOOGLE_API_KEY } }`), not through `process.env`. If you ported code from Next.js without adapting this, `process.env.GOOGLE_API_KEY` will be `undefined` and you will see an obscure 500 with no useful message.

### On AWS Lambda

Set variables in the Lambda console under Configuration → Environment variables, or wire them up through SAM / Serverless Framework / CDK. KMS-backed encryption is a nice perk on AWS, but be aware that some SDK versions only read `process.env` during cold start. Re-reading `process.env` on every request — instead of caching the key in a module-level constant at import time — avoids a surprise when you rotate the key and one warm container keeps using the old value.

## Cause 2: The Edge Runtime Does Not Support Node-Only SDKs

The second most common cause. Vercel Edge Functions and Cloudflare Workers run on a V8 isolate, not a Node.js process, so standard-library modules like `fs`, `crypto` (parts of it), and `stream` are partially or completely unavailable.

The official Gemini SDKs behave differently here. `@google/generative-ai` for JavaScript/TypeScript is designed to work on the Edge runtime. `@google-cloud/vertexai` assumes Node.js and will break. The Python `google-generativeai` package is not a good fit for Vercel's Edge Python runtime; stick to Node.js functions for serverless Gemini code unless you have a strong reason otherwise.

Also check whether your Next.js route handler has quietly opted into the Edge runtime:

```ts
// This line puts you on the Edge runtime
export const runtime = "edge";

// Explicitly stay on Node.js if you do not need Edge
export const runtime = "nodejs";
```

If you do not have a concrete reason to run on the Edge, go back to `nodejs`. Edge gives you faster cold starts but takes a lot away in exchange — particularly around streaming and long-running requests.

If you must stay on the Edge, the most robust pattern is to skip the SDK and call Gemini as a REST API via `fetch`.

```ts
// Works on the Edge runtime
export const runtime = "edge";

export async function POST(req: Request) {
  const { prompt } = await req.json();
  const url =
    "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent" +
    `?key=${process.env.GOOGLE_API_KEY}`;

  const res = await fetch(url, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      contents: [{ parts: [{ text: prompt }] }],
    }),
  });

  if (\!res.ok) {
    return Response.json({ error: await res.text() }, { status: res.status });
  }
  return Response.json(await res.json());
}
```

SDKs are convenient, but on the Edge they become a black box that fails in cryptic ways. A direct `fetch` call is more verbose, and dramatically easier to debug when something goes wrong.

## Cause 3: You Are Hitting the Platform's Timeout Ceiling

A request that takes 15 seconds locally and feels fine will routinely return 504 in production. That is almost always the platform's timeout kicking in, not a Gemini problem.

Rough ceilings by platform: Vercel Serverless Functions are 10 seconds on the Hobby plan, 60 seconds on Pro, up to 300 seconds with Fluid Compute. Cloudflare Workers give you 10ms of CPU time on the free plan and 30 seconds on the Paid plan (wall-clock time for I/O is effectively unbounded). AWS Lambda defaults to 3 seconds and can be raised to 15 minutes.

Gemini 2.5 Pro regularly takes 20–40 seconds on complex prompts. Running it naively on a Vercel Hobby project is almost guaranteed to fail. You have three good options.

### Option 1: Stream the Response

Streaming flips the failure mode. The response starts flowing as soon as the first token arrives, so the function returns within the platform's window even if generation continues for a while.

```ts
import { GoogleGenerativeAI } from "@google/generative-ai";

export async function POST(req: Request) {
  const { prompt } = await req.json();
  const genai = new GoogleGenerativeAI(process.env.GOOGLE_API_KEY\!);
  const model = genai.getGenerativeModel({ model: "gemini-2.5-pro" });

  const stream = await model.generateContentStream(prompt);

  const readable = new ReadableStream({
    async start(controller) {
      const encoder = new TextEncoder();
      for await (const chunk of stream.stream) {
        controller.enqueue(encoder.encode(chunk.text()));
      }
      controller.close();
    },
  });

  return new Response(readable, {
    headers: { "Content-Type": "text/plain; charset=utf-8" },
  });
}
```

### Option 2: Use a Smaller Model Where You Can

Not every step needs Gemini 2.5 Pro. Short summarizations, classification, and routing are usually 3–5x faster and an order of magnitude cheaper on Gemini 2.5 Flash. Reserve Pro for the parts of the pipeline that genuinely benefit from its reasoning, and route everything else through Flash. You solve both the timeout problem and your token budget in one move.

If you want a framework for model selection, [Gemini 2.5 Pro vs Flash: Production Error Handling](/articles/gemini-api/gemini-api-production-error-handling-rate-limit-guide) walks through the trade-offs.

### Option 3: Move Long Work Off the Request Path

Anything that predictably exceeds 30 seconds — long-form generation, bulk analysis — should not run inside the request/response cycle at all. On Vercel, use `waitUntil` for background work and return results via webhook or DB polling. On Cloudflare Workers, reach for Queues or Durable Objects. Designing this in from the start is always cheaper than bolting it on later.

## Small Tricks That Pay Off

Serverless logs are laggy, and they are often your only window into production behavior. Logging three cheap details at startup has saved me hours more than once:

```ts
console.log("[gemini-api] key prefix:", process.env.GOOGLE_API_KEY?.slice(0, 6));
console.log("[gemini-api] sdk version:", require("@google/generative-ai/package.json").version);
console.log("[gemini-api] runtime:", typeof EdgeRuntime \!== "undefined" ? "edge" : "node");
```

With those three lines you can tell immediately whether your env var silently changed, whether your SDK version is different than you expect, and whether you are accidentally running on a different runtime.

For a broader grounding in serverless architecture, [Serverless Architectures on AWS (Peter Sbarski)](https://www.amazon.co.jp/dp/1617295825/?tag=pinocchio-22) remains one of the best introductions to the mental model — many of its lessons transfer directly to Cloudflare Workers and Vercel.

## What to Do Right Now

If your deployment is broken at this moment, start with environment variables. Run `wrangler secret list` or open the Vercel dashboard and confirm `GOOGLE_API_KEY` is actually registered in both Preview and Production. That single check resolves the majority of these incidents.

If that is not the culprit, drop the health-check endpoint from above into your app and work through runtime and timeout in that order. Nine times out of ten the problem is something local to your environment, not Gemini itself. The fix is usually three lines of configuration, not a rewrite.
