On a Monday morning I opened App Store Connect and found the weekend's reviews waiting: English, German, French, Korean. By the time I had read each one and worked out a reply in its own language, my coffee had gone cold and the first hour of the day was gone.

When you run several apps, that scene repeats almost weekly. So I set up Gemini API to draft the replies and post them semi-automatically. Along the way I ran into an undocumented behavior I now call the "8-second rule." If you're stuck at the same spot, I hope this saves you some time.

Here's the short version up front: **generating the replies turned out to be the easy part. Confirming that a posted reply was actually live took most of my effort.**

## Why I Wanted to Automate Review Replies

The apps I run, including Beautiful HD Wallpapers (iOS/Android) and Ukiyo-e Wallpapers, collect reviews from all over the world. Replying quickly and politely matters, but the more reviews came in, the more obvious the limits of doing it by hand became.

Multiple languages were the heavy part. A German reviewer deserves a reply in German. Running it through a translation tool, rereading it for naturalness, then pasting and posting — that loop quietly stretched the time per review.

My starting question was simple: if Gemini can detect the review's language and answer in the same one, could I hand off the drafting step entirely?

## The Basic Implementation

The setup is Python. I pull reviews from the Google Play Developer API and the App Store Connect API, generate a reply with Gemini, review it, and post it.

The key is to delegate language detection to Gemini. Pass the review text as-is, tell it to reply in the same language, and a Japanese review gets a Japanese reply while a German review gets a German one. No separate language-detection call, so there's less to build.

```python
import os
from google import genai

# The API key is read from the GEMINI_API_KEY environment variable
client = genai.Client()
MODEL = "gemini-2.5-flash"  # check the official model list for the current name before use

def generate_reply(review_text: str, app_name: str, rating: int) -> str:
    """Write a reply in the review's language, tuned to the star rating."""
    prompt = f"""Write a reply to the following app review.

App name: {app_name}
Rating: {rating} stars
Review:
{review_text}

Requirements:
- Reply in the same language as the review
- Natural, human tone — not a form letter
- High rating (4-5 stars): express genuine thanks, welcome continued use
- Low rating (1-3 stars): acknowledge the issue, briefly describe improvement intent
- Keep it under 150 characters
- Reference specific content from the review rather than giving a generic response

Output only the reply text."""

    response = client.models.generate_content(model=MODEL, contents=prompt)
    return response.text.strip()
```

I used to write this with `google.generativeai`, but `google-genai` (`from google import genai`) is the current SDK. If you copy the older style you'll start seeing deprecation warnings, so I've switched the code here.

Mind the length, too. Google Play caps replies at 350 characters, and asking for "under 150" in the prompt leaves headroom. Just before posting, I count the characters and send anything over the limit back for regeneration.

I also tried Claude Haiku and GPT-4o Mini with the same prompt. The quality gap wasn't big enough to decide anything, and Gemini Flash's response time was steadier for short multilingual output. Even at a few thousand replies a month, the API bill stays in the low hundreds of yen.

## The Trap: App Store's 8-Second Rule

Google Play worked smoothly from the start. App Store Connect was different: past a certain number of replies in one run I got 403 errors, or sometimes silent failures where nothing happened at all.

The replies looked successful in my log but never showed up on screen. After about ten rounds of that, I finally suspected something rate-limit-like was at work. Varying the delay showed that leaving 8 seconds or more between replies made it stable. I cap each session at 35 replies as a safety margin.

I searched the official docs and found nothing about this. I treat it as an implicit limit on Apple's side.

```python
import time
import requests

API_URL = "https://api.appstoreconnect.apple.com/v1/customerReviewResponses"

def post_reply_to_app_store(review_id: str, reply_text: str, token: str) -> bool:
    """Post a reply via the App Store Connect API. A 201 means accepted."""
    payload = {
        "data": {
            "type": "customerReviewResponses",
            "attributes": {"responseBody": reply_text},
            "relationships": {
                "review": {"data": {"type": "customerReviews", "id": review_id}}
            },
        }
    }
    headers = {"Authorization": f"Bearer {token}", "Content-Type": "application/json"}
    r = requests.post(API_URL, json=payload, headers=headers, timeout=30)
    return r.status_code == 201

def batch_reply_app_store(reviews: list, replies: list, token: str):
    WAIT_SECONDS = 8       # the interval that settled down in testing
    MAX_PER_SESSION = 35   # cap with a safety margin

    targets = list(zip(reviews, replies))[:MAX_PER_SESSION]
    for i, (review_id, reply_text) in enumerate(targets):
        ok = post_reply_to_app_store(review_id, reply_text, token)
        print(f"{'OK' if ok else 'NG'} [{i + 1}/{len(targets)}] {review_id[:8]}...")
        if i < len(targets) - 1:
            time.sleep(WAIT_SECONDS)
```

When I shortened the gap to 6 seconds or less, failures started appearing past roughly 30 replies. At 8 seconds it's been stable. Google Play has no equivalent wait requirement; back-to-back posting was fine.

## Don't Trust "Success": Read the Reply Back

Even with the 8-second wait, I wasn't fully at ease. I'd already seen a 201 status for a reply that never showed up.

So I added a step that reads the reply back after posting. The App Store Connect API has an endpoint for the response attached to a review.

```python
def reply_is_visible(review_id: str, token: str) -> bool:
    """Check that the posted reply can be read back from the review."""
    url = f"https://api.appstoreconnect.apple.com/v1/customerReviews/{review_id}/response"
    r = requests.get(url, headers={"Authorization": f"Bearer {token}"}, timeout=30)
    return r.status_code == 200 and bool(r.json().get("data"))
```

If the read-back fails, I don't re-post on the spot. I put the review on an "unconfirmed" list and check it in the next session before sending again. Hammering the API in place just increases the number of times you hit the limit.

**Record success by what you could read back, not by what the server told you.** The more I automate, the more I hold onto that line.

## Language Quality Varies — and You Can Nudge It

After a few months of running this, I noticed the naturalness of the replies differs by language. English, Japanese, and Spanish read well. German and French sometimes kept a mechanical stiffness, and replies to low ratings tended to over-apologize.

The fix is to add supplementary instructions only for the languages that need them. That worked more clearly than applying one instruction to every language. I adjusted the wording while a German-speaking acquaintance read the output, and it settled on what I use now.

```python
LANGUAGE_HINTS = {
    "de": "Schreiben Sie auf natürlichem Deutsch. Vermeiden Sie übermäßige Entschuldigungen.",
    "fr": "Répondez en français naturel et chaleureux, sans style trop formel.",
    "ko": "자연스러운 한국어로 답변해 주세요. 지나치게 공식적인 표현은 피해주세요.",
}
```

## Keeping a Human in the Loop

Since adding this, my reply time went from a few hours a week to about 30 minutes. I still read every generated reply before it goes out.

With translation and drafting gone, I can focus on one question: would this sentence feel rude to this user right now? That was an unexpected side benefit. Review replies are where I meet my users, and I'd rather keep the final judgment in my own hands.
