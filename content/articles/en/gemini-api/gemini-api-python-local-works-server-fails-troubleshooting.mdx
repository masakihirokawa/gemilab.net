"Everything works perfectly on my machine, but the moment I deploy to the server, it breaks." If you've spent any time building with the Gemini API in Python, you've probably run into this frustration. The error messages look different from what you saw locally, and the same code behaves differently — making it hard to pinpoint the cause.

This guide walks through the most common failure patterns, organized by root cause, with concrete code examples and fixes for each. Understanding *why* local and production environments diverge will make your next deployment a lot smoother.

## Why Local and Production Behave Differently

Before diving into specific errors, it helps to understand the three main sources of divergence between local development and production.

**Environment differences** are the most common culprit. Your local machine has a specific Python version, a set of installed packages, and system-level configurations that production servers often don't share. A minimal Docker image or a serverless runtime starts much closer to a blank slate.

**Missing environment variables** are the second most common issue. Locally, you might load secrets from a `.env` file or set them via `export`. Those don't follow you to the server unless you explicitly configure them there.

**Network and timeout configuration** differs too. The latency characteristics between your laptop and Google's API endpoints differ from those of a cloud server, and default timeouts that work fine locally can cause silent failures in production.

Let's look at each failure pattern in detail.

## Error 1: Environment Variables Not Loaded

### Symptom

In production you see `google.auth.exceptions.DefaultCredentialsError` or discover that `GOOGLE_API_KEY` is `None`, even though the same code works fine locally.

### Root Cause

Locally, you're probably loading secrets from a `.env` file using `python-dotenv`. That file doesn't exist on the server, and if the production environment doesn't have the variable set natively, `load_dotenv()` silently loads nothing.

```python
# ❌ Works locally, but GOOGLE_API_KEY will be None in production
from dotenv import load_dotenv
import os
import google.generativeai as genai

load_dotenv()  # Does nothing if .env doesn't exist

api_key = os.environ.get("GOOGLE_API_KEY")
# api_key is None in production — no error yet, but configure() will fail later
genai.configure(api_key=api_key)
```

### Fix

In production, use your platform's native secret management instead of `.env` files. Add an explicit check so failures are loud and immediate.

```python
# ✅ Fail fast if the API key is missing
import os
import google.generativeai as genai

api_key = os.environ.get("GOOGLE_API_KEY")
if not api_key:
    raise RuntimeError(
        "GOOGLE_API_KEY is not set. "
        "Check your production environment variable configuration."
    )

genai.configure(api_key=api_key)
```

How to set the variable depends on your platform:

- **Railway / Render**: Set it in the dashboard under "Environment Variables"
- **Heroku**: `heroku config:set GOOGLE_API_KEY=YOUR_API_KEY`
- **AWS Lambda**: Add it under "Configuration → Environment Variables" in the console
- **Cloud Run**: `gcloud run deploy --set-env-vars GOOGLE_API_KEY=YOUR_API_KEY`

Never hardcode the API key in your source code. It will be caught by GitHub Secret Scanning and similar tools.

## Error 2: asyncio Event Loop Conflicts

### Symptom

Inside an async handler in FastAPI or another async framework, you see `RuntimeError: This event loop is already running` or requests hang indefinitely.

### Root Cause

Mixing the synchronous Gemini client with an async framework can cause the event loop to conflict. The `google-genai` SDK provides a proper async interface (`client.aio`), but it's easy to miss when migrating code from a synchronous script.

```python
# ❌ Calling a sync method inside an async FastAPI handler can cause conflicts
from fastapi import FastAPI
import google.generativeai as genai

app = FastAPI()

@app.get("/chat")
async def chat(message: str):
    model = genai.GenerativeModel("gemini-2.5-flash")
    response = model.generate_content(message)  # sync call in async context
    return {"response": response.text}
```

### Fix

Use the async client (`client.aio`) when working inside async frameworks. The pattern is straightforward once you know it exists.

```python
# ✅ Use the async interface for FastAPI integration
from fastapi import FastAPI
from google import genai
import os

app = FastAPI()
client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

@app.get("/chat")
async def chat(message: str):
    # Await the async method — no event loop conflict
    response = await client.aio.models.generate_content(
        model="gemini-2.5-flash",
        contents=message,
    )
    return {"response": response.text}
```

If you genuinely need to call synchronous Gemini code from an async handler, wrap it with `asyncio.get_event_loop().run_in_executor()` to push it onto a thread pool instead.

## Error 3: Timeout and Connection Drops

### Symptom

Requests that respond instantly on your laptop result in `ReadTimeout` or `ConnectionError` in production — especially with longer prompts or thinking-mode models.

### Root Cause

Models like Gemini 2.5 Pro can take tens of seconds to generate a response, particularly with thinking enabled. Default timeout values on production load balancers (often 30–60 seconds) can cut the connection before the model finishes.

```python
# ❌ Default timeout — fine for short requests, breaks for long ones
from google import genai
import os

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])
# gemini-2.5-pro with thinking can take a long time — default timeout may cut it
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="Analyze this complex problem in detail...",
)
```

### Fix

Set an explicit timeout on the HTTP client, and use streaming for long-running requests. Streaming sends partial responses as they're generated, which prevents the connection from appearing idle to intermediary proxies.

```python
# ✅ Explicit timeout + streaming for long responses
from google import genai
import httpx
import os

http_client = httpx.Client(timeout=httpx.Timeout(300.0))  # 5 minutes
client = genai.Client(
    api_key=os.environ["GOOGLE_API_KEY"],
    http_client=http_client,
)

# Stream the response — partial chunks arrive continuously, preventing idle timeouts
for chunk in client.models.generate_content_stream(
    model="gemini-2.5-pro",
    contents="Analyze this complex problem in detail...",
):
    if chunk.text:
        print(chunk.text, end="", flush=True)
# Expected: output appears incrementally, no timeout for long responses
```

If you're on Cloud Run, also extend the request timeout at the infrastructure level:

```bash
# Cloud Run defaults to 60 seconds — extend it for long Gemini requests
gcloud run deploy my-service \
  --timeout=300 \
  --image=gcr.io/my-project/my-image
```

## Error 4: Docker Container SSL and DNS Failures

### Symptom

Inside a Docker container you see `SSL: CERTIFICATE_VERIFY_FAILED` or `Name or service not known` (DNS resolution failure) when the same code works outside the container.

### Root Cause

Minimal base images like `python:3.12-slim` don't always include CA certificates or complete DNS configuration. Missing packages in `requirements.txt` can also cause silent failures that only show up at runtime.

```dockerfile
# ✅ Install CA certificates to fix SSL errors in slim images
FROM python:3.12-slim

# CA certificates fix SSL verification errors in minimal images
RUN apt-get update && apt-get install -y \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# Copy requirements first to leverage Docker layer caching
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Pass the API key at runtime, not build time — never bake secrets into images
CMD ["python", "main.py"]
```

Make sure your `requirements.txt` explicitly lists all dependencies:

```
# requirements.txt
google-genai>=0.8.0
httpx>=0.27.0
```

## Error 5: Serverless Environments (Lambda, Cloud Run)

### Symptom

On AWS Lambda, only the first request after a cold start fails, or requests time out because Lambda's default execution limit (3 seconds) is too short.

### Fix

Initialize the client at **module scope** so it's reused across invocations when Lambda reuses the container. Always extend the Lambda timeout well beyond the default.

```python
# ✅ Module-level client initialization — reused on warm starts
import os
from google import genai

# This runs once per container lifetime, not once per request
client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

def lambda_handler(event, context):
    message = event.get("message", "")

    try:
        response = client.models.generate_content(
            model="gemini-2.5-flash",
            contents=message,
        )
        return {
            "statusCode": 200,
            "body": response.text,
        }
    except Exception as e:
        # Log the error type for debugging — don't expose internal details
        print(f"Gemini API error: {e}")
        return {
            "statusCode": 500,
            "body": f"An error occurred: {type(e).__name__}",
        }
```

Set the Lambda timeout to **30–60 seconds** when using the Gemini API. For Gemini 2.5 Pro with thinking mode, err on the higher end.

## Pre-Deployment Checklist

Before deploying, run through these checks to catch the most common issues early:

- Is `GOOGLE_API_KEY` set in the server's environment? (Verify with `echo $GOOGLE_API_KEY`)
- Does the server's `google-genai` version match your local version? (`pip show google-genai`)
- Can the server reach `generativelanguage.googleapis.com`?
- Are load balancer / proxy timeouts longer than your expected response time?
- If using an async framework, are you using `client.aio`?
- Does your Docker image include CA certificates?

For authentication error details, see [Gemini API Authentication Error Solutions](/en/articles/gemini-api/gemini-api-authentication-error-solutions). For rate limiting, see [Gemini API 429 Error Troubleshooting](/en/articles/gemini-api/gemini-api-quota-429-error-troubleshooting).

## Final Thought

The "works locally, breaks on the server" problem almost always traces back to environment differences — and the single fastest check is whether your API key is actually set in the production environment. Start there, and you'll resolve most cases within minutes.

As a longer-term practice, add a `/healthz` endpoint that verifies the API key is present and can reach Gemini before accepting traffic. A small upfront investment in observability saves a lot of late-night debugging.
