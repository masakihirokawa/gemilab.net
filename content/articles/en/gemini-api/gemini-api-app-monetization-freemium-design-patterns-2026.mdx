When you add an AI feature to an app, a question follows almost immediately: *how do I make money from this?*

Gemini API is powerful. Integrating it transforms user experience. But it also introduces something traditional app development never had — a per-request cost that scales with your userbase. When I first integrated Gemini into apps I'd been monetizing with AdMob, the first month's API bill was nearly three times what I'd budgeted for.

That experience made something clear: monetizing AI features isn't just about adding a subscription paywall. It's a design problem — one that touches architecture, pricing, user psychology, and cost engineering at the same time. This article is a distillation of what I've learned.

## Real Cost Modeling: Know Your Numbers First

Design decisions made without accurate cost projections are guesses. Let's anchor everything in real numbers.

As of April 2026, Gemini 2.5 Pro API pricing (beyond the free tier) is approximately $1.25 per million input tokens (under 200K context), $2.50 per million above that, and $10.00 per million output tokens. Gemini 2.5 Flash runs at roughly 1/5 to 1/8 of these rates.

```python
# Monthly API cost estimator — run this before designing anything
def calculate_monthly_cost(
    daily_active_users: int,
    requests_per_user_per_day: float,
    avg_input_tokens: int,
    avg_output_tokens: int,
    days: int = 30,
    model: str = "pro",  # "pro" or "flash"
) -> dict:
    """
    Estimate monthly Gemini API cost from usage parameters.
    Use this to set hard limits on free-tier behavior.
    """
    # Per-million-token rates (2026 pricing)
    rates = {
        "pro":   {"input": 1.25, "output": 10.00},
        "flash": {"input": 0.15, "output": 0.60},
    }
    rate = rates.get(model, rates["pro"])

    total_requests = daily_active_users * requests_per_user_per_day * days
    input_mtok  = (total_requests * avg_input_tokens)  / 1_000_000
    output_mtok = (total_requests * avg_output_tokens) / 1_000_000

    total_cost = (input_mtok * rate["input"]) + (output_mtok * rate["output"])

    return {
        "total_requests":  int(total_requests),
        "total_cost_usd":  round(total_cost, 2),
        "cost_per_user_month_usd": round(total_cost / max(daily_active_users, 1), 4),
    }

# Scenario 1: Small app — 100 DAU, 1 req/day, 500 in / 200 out tokens, Pro model
r1 = calculate_monthly_cost(100, 1, 500, 200, model="pro")
print(f"Small  (100  DAU, Pro):   ${r1['total_cost_usd']:>8.2f}/mo  (${r1['cost_per_user_month_usd']}/user)")
# Output: Small  (100  DAU, Pro):   $    6.75/mo  ($0.0675/user)

# Scenario 2: Mid-size — 1,000 DAU, 3 req/day, 1,000 in / 500 out tokens, Pro
r2 = calculate_monthly_cost(1000, 3, 1000, 500, model="pro")
print(f"Mid    (1k   DAU, Pro):   ${r2['total_cost_usd']:>8.2f}/mo  (${r2['cost_per_user_month_usd']}/user)")
# Output: Mid    (1k   DAU, Pro):   $  585.00/mo  ($0.585/user)

# Scenario 2b: Same DAU, Flash instead of Pro
r2f = calculate_monthly_cost(1000, 3, 1000, 500, model="flash")
print(f"Mid    (1k   DAU, Flash): ${r2f['total_cost_usd']:>8.2f}/mo  (${r2f['cost_per_user_month_usd']}/user)")
# Output: Mid    (1k   DAU, Flash): $   76.50/mo  ($0.0765/user)

# Scenario 3: Growing — 5,000 DAU, 5 req/day, 2,000 in / 1,000 out tokens, Pro
r3 = calculate_monthly_cost(5000, 5, 2000, 1000, model="pro")
print(f"Growth (5k   DAU, Pro):   ${r3['total_cost_usd']:>8.2f}/mo  (${r3['cost_per_user_month_usd']}/user)")
# Output: Growth (5k   DAU, Pro):   $9750.00/mo  ($1.95/user)
```

The scenario 3 number is the one that causes panic: $9,750 per month for 5,000 DAU. That's unsustainable on AdMob revenue alone. But notice scenario 2b — the same mid-tier volume on Flash costs $76.50 instead of $585. This single observation shapes the entire freemium design.

## Freemium Boundary Design

"What should be free, and what should be paid?" — this is the core question. Get it wrong and you either burn money serving free users, or you wall off so much that nobody converts.

Here are the three principles I've found actually work.

### Principle 1: Charge for depth of experience, not frequency of requests

The classic failure mode is "3 free requests per day." Users hit the limit, get frustrated, and uninstall before they ever consider paying. Request caps create friction without demonstrating value.

Instead, differentiate by the *quality and depth* of the AI output:

- **Free tier**: AI summarizes the document in 3 bullet points (simple, fast)
- **Paid tier**: AI delivers a structured analysis with root causes, risk factors, recommended actions, and ROI framing

Same underlying feature. The free version proves the concept. The paid version delivers the work product someone would actually use on the job. Users stay engaged with the free tier while clearly seeing what the paid tier offers.

### Principle 2: Bind model selection to subscription tier

This is the cleanest mechanism for cost control I've found. Free users get Flash (low cost, fast), paid users get Pro (high quality, higher cost).

```python
import os
import asyncio
from google import genai

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

def get_model_for_tier(user_tier: str) -> str:
    """
    Map subscription tier to Gemini model.
    This makes your cost structure predictable — free users
    cannot trigger Pro-level API spend.
    """
    return {
        "free":    "gemini-2.5-flash",  # ~1/7 the cost of Pro
        "pro":     "gemini-2.5-pro",
        "premium": "gemini-2.5-pro",   # + Thinking Budget unlocked
    }.get(user_tier, "gemini-2.5-flash")

async def analyze_document(content: str, user_tier: str) -> dict:
    """
    Document analysis with tier-adaptive model selection,
    output token limits, and system prompt complexity.
    """
    model = get_model_for_tier(user_tier)

    # Limit output tokens for free tier — reduces cost + creates upgrade incentive
    max_output_tokens = 1024 if user_tier == "free" else 8192

    # Simple system prompt for free, detailed for paid
    if user_tier == "free":
        system_instruction = (
            "You are a helpful assistant. Summarize the document in 3 key points."
        )
    else:
        system_instruction = (
            "You are a senior business analyst. Analyze the document thoroughly: "
            "identify the core problem, root causes, risk factors, "
            "and provide prioritized action items with estimated ROI impact."
        )

    config = genai.types.GenerateContentConfig(
        system_instruction=system_instruction,
        max_output_tokens=max_output_tokens,
        temperature=0.7,
    )

    # Enable Thinking Mode only for premium tier
    if user_tier == "premium":
        config.thinking_config = genai.types.ThinkingConfig(thinking_budget=1024)

    try:
        response = await client.aio.models.generate_content(
            model=model,
            contents=content,
            config=config,
        )
        return {"result": response.text, "model": model, "tier": user_tier}
    except Exception as e:
        raise RuntimeError(f"Analysis error: {e}") from e
```

With this pattern, free user growth doesn't compound your costs the same way. Each free API call costs ~1/7 of a paid call. And every time a free user experiences the quality gap firsthand (not just reads about it), conversion likelihood goes up.

### Principle 3: Frame limits as monthly usage, not daily caps

"You have 3 remaining analyses this month" converts better than "You've used your 3 daily requests." Monthly framing gives users breathing room and creates a natural upgrade trigger: the moment someone runs out mid-project, they're highly motivated to upgrade because the cost of *stopping* feels real.

Pair this with a visible usage counter in the UI — "7 of 10 monthly analyses used" — and you create a low-pressure but persistent conversion signal.

## Rate Limiting and Cost Control

Good user-facing design is only half the battle. You also need backend enforcement so that abuse scenarios, retry storms, and edge cases don't translate into unexpected API bills.

### Edge-Layer Rate Limiting with Cloudflare Workers + KV

```typescript
// Cloudflare Workers + KV rate limiter
// Tier-aware, per-user, resets on a rolling window

interface RateLimitEntry {
  count: number;
  resetAt: number;  // Unix epoch ms
}

interface Env {
  RATE_LIMIT_KV: KVNamespace;
  GEMINI_API_KEY: string;
}

const LIMITS = {
  free:    { maxRequests: 10,  windowMs: 86_400_000 },   // 10/day
  pro:     { maxRequests: 100, windowMs: 86_400_000 },   // 100/day
  premium: { maxRequests: 500, windowMs: 86_400_000 },   // 500/day
} as const;

async function checkRateLimit(
  env: Env,
  userId: string,
  tier: keyof typeof LIMITS,
): Promise<{ allowed: boolean; remaining: number; resetAt: number }> {
  const limit = LIMITS[tier];
  const key   = `rl:${userId}`;
  const now   = Date.now();

  const entry = await env.RATE_LIMIT_KV.get<RateLimitEntry>(key, "json");

  if (\!entry || entry.resetAt < now) {
    const fresh: RateLimitEntry = { count: 1, resetAt: now + limit.windowMs };
    await env.RATE_LIMIT_KV.put(key, JSON.stringify(fresh), {
      expirationTtl: Math.ceil(limit.windowMs / 1000) + 60,
    });
    return { allowed: true, remaining: limit.maxRequests - 1, resetAt: fresh.resetAt };
  }

  if (entry.count >= limit.maxRequests) {
    return { allowed: false, remaining: 0, resetAt: entry.resetAt };
  }

  entry.count += 1;
  await env.RATE_LIMIT_KV.put(key, JSON.stringify(entry), {
    expirationTtl: Math.ceil((entry.resetAt - now) / 1000) + 60,
  });
  return { allowed: true, remaining: limit.maxRequests - entry.count, resetAt: entry.resetAt };
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    if (request.method \!== "POST") return new Response("Method Not Allowed", { status: 405 });

    // Extract userId + tier from JWT (implementation omitted)
    const userId = "user_123";
    const tier   = "pro" as keyof typeof LIMITS;

    const { allowed, remaining, resetAt } = await checkRateLimit(env, userId, tier);

    if (\!allowed) {
      return new Response(
        JSON.stringify({
          error: "Rate limit exceeded",
          resetAt: new Date(resetAt).toISOString(),
          upgradeUrl: "https://yourapp.com/upgrade",
        }),
        {
          status: 429,
          headers: {
            "Content-Type": "application/json",
            "X-RateLimit-Remaining": "0",
            "Retry-After": String(Math.ceil((resetAt - Date.now()) / 1000)),
          },
        },
      );
    }

    // Proxy to Gemini API (implementation omitted)
    return new Response(JSON.stringify({ result: "..." }), {
      status: 200,
      headers: { "X-RateLimit-Remaining": String(remaining) },
    });
  },
};
```

The key insight here: by checking the rate limit at the Cloudflare edge — before the request ever reaches your origin or the Gemini API — abuse attempts cost you zero in API spend. For more on rate limiting strategies, see the [Gemini API Rate Limiting Guide](/en/articles/gemini-api/gemini-api-rate-limiting-quota-management).

## Subscription + API Tier: Keeping Them in Sync

The mechanism for connecting payment state to API behavior is a Stripe webhook that writes to your user store, and a middleware layer that reads tier on every API request.

```python
# FastAPI + Firestore: Stripe webhook updates user tier in real time

from fastapi import FastAPI, Request, HTTPException
from google.cloud import firestore
import stripe, os
from datetime import datetime, timezone

app = FastAPI()
stripe.api_key = os.environ["STRIPE_SECRET_KEY"]
db = firestore.Client()

PRICE_TO_TIER: dict[str, str] = {
    "price_pro_monthly":     "pro",
    "price_pro_yearly":      "pro",
    "price_premium_monthly": "premium",
    "price_premium_yearly":  "premium",
}

@app.post("/webhook/stripe")
async def handle_stripe_webhook(request: Request) -> dict:
    payload    = await request.body()
    sig_header = request.headers.get("stripe-signature", "")

    try:
        event = stripe.Webhook.construct_event(
            payload, sig_header, os.environ["STRIPE_WEBHOOK_SECRET"]
        )
    except stripe.error.SignatureVerificationError:
        raise HTTPException(400, "Invalid webhook signature")

    if event["type"] == "checkout.session.completed":
        session      = event["data"]["object"]
        email        = session.get("customer_email", "")
        price_id     = session.get("metadata", {}).get("price_id", "")
        expires_unix = session.get("expires_at")

        if email and price_id in PRICE_TO_TIER:
            tier = PRICE_TO_TIER[price_id]
            expires_at = (
                datetime.fromtimestamp(expires_unix, tz=timezone.utc)
                if expires_unix else None
            )
            await _set_user_tier(email, tier, active=True, expires_at=expires_at)

    elif event["type"] == "customer.subscription.deleted":
        sub      = event["data"]["object"]
        customer = stripe.Customer.retrieve(sub["customer"])
        email    = customer.get("email", "")
        if email:
            await _set_user_tier(email, "free", active=False)

    return {"ok": True}

async def _set_user_tier(
    email: str,
    tier: str,
    active: bool,
    expires_at: datetime | None = None,
) -> None:
    """
    Write subscription state to Firestore.
    The API middleware reads subscription_tier + subscription_expires_at
    on every request to determine model access.
    """
    data: dict = {
        "subscription_tier":   tier,
        "subscription_active": active,
        "updated_at":          firestore.SERVER_TIMESTAMP,
    }
    if expires_at:
        data["subscription_expires_at"] = expires_at

    query = db.collection("users").where("email", "==", email).limit(1)
    for doc in query.stream():
        doc.reference.update(data)
        return

    # User not yet created (webhook arrived before registration)
    db.collection("pending_tier_updates").add({"email": email, **data})
```

One critical subtlety: when a user cancels, Stripe fires `customer.subscription.deleted` — but Stripe cancellations are typically end-of-period, not immediate. If you downgrade to `free` the moment that webhook fires, you're cutting off a user who has already paid for the remainder of the billing period. Store `subscription_expires_at` from `current_period_end`, and check that field (not just `subscription_active`) in your access middleware.

## Avoiding the Three Most Common Mistakes

**Mistake 1: Long system prompts for all users**

A 2,000-token system prompt adds ~$0.0025 (Pro rate) to *every* request as a fixed overhead. At 10,000 requests/day that's $750/month in pure prompt overhead. Keep free-tier system prompts under 300 tokens. Use the richer prompt to differentiate paid tiers, not just as boilerplate applied universally.

**Mistake 2: Retry storms without exponential backoff**

Naive retry logic on transient API errors can turn a single user's request into 20+ API calls.

```python
import asyncio
import random
from google import genai
from google.api_core.exceptions import ResourceExhausted, ServiceUnavailable

async def gemini_with_backoff(
    client: genai.Client,
    model: str,
    prompt: str,
    max_retries: int = 3,
) -> str:
    """
    Always use this wrapper. Never retry Gemini API calls in a tight loop.
    Jitter prevents thundering-herd during partial outages.
    """
    last_exc: Exception | None = None
    for attempt in range(max_retries):
        try:
            resp = await client.aio.models.generate_content(
                model=model, contents=prompt
            )
            return resp.text
        except (ResourceExhausted, ServiceUnavailable) as exc:
            last_exc = exc
            if attempt == max_retries - 1:
                break
            delay = (2 ** attempt) + random.uniform(0.0, 1.0)  # 1s, 2s, 4s + jitter
            await asyncio.sleep(delay)
        except Exception as exc:
            raise RuntimeError(f"Gemini error (non-retriable): {exc}") from exc

    raise RuntimeError(f"Gemini call failed after {max_retries} retries: {last_exc}")
```

**Mistake 3: Sending the full chat history on every turn**

Chat history that grows unbounded is a silent cost bomb. At 50 conversation turns, a single request might carry 30,000+ input tokens. Implement a sliding window:

```python
def build_chat_context(
    messages: list[dict],
    max_turns: int = 8,
    summary: str = "",
) -> list[dict]:
    """
    Keep only the most recent N turns in the API call.
    Prepend a summary of older turns if available.
    
    Generating and caching the summary is a separate background job;
    this function just assembles the context window.
    """
    if len(messages) <= max_turns * 2:
        return messages  # Short conversation — send everything

    recent = messages[-(max_turns * 2):]

    if not summary:
        return recent  # No summary yet; just drop old messages

    context_injection = {
        "role": "user",
        "parts": [{"text": f"[Prior conversation summary]: {summary}"}],
    }
    return [context_injection] + recent
```

## Production Architecture on Cloudflare Workers

Here's the architecture that ties everything together:

```
[Mobile / Web Client]
        |  HTTPS + JWT
        ↓
[Cloudflare Workers — Edge Layer]
  ├─ Verify JWT → extract userId, tier
  ├─ Rate limit check  (Workers KV)
  ├─ Tier lookup cache (Workers KV, 5-min TTL)
  └─ Proxy to Gemini API with model selection
              |
        [Gemini API]
  ├─ gemini-2.5-flash   ← free tier
  └─ gemini-2.5-pro     ← paid tiers

[Firebase Firestore]  ←── Stripe Webhook → _set_user_tier()
  └─ users/{uid}.subscription_tier / expires_at
```

Everything that can be decided at the edge is decided at the edge — before any origin hit or API call. Abuse and overages are blocked cheapest possible point. For more on this architecture, see the [Cloudflare Workers + Gemini API Edge Guide](/en/articles/gemini-api/gemini-api-cloudflare-workers-edge-ai).

## Flex Priority: 50% Cost Reduction for Background Work

For processing that doesn't require an immediate response — batch reports, background summarization, scheduled analysis — Gemini's Flex Priority inference mode offers approximately 50% cost savings at the expense of higher latency.

```python
# Flex Priority via Vertex AI — ideal for background/async tasks

import vertexai
from vertexai.generative_models import GenerativeModel, GenerationConfig
import os

vertexai.init(project=os.environ["GCP_PROJECT_ID"], location="us-central1")

def generate_async_report(document_text: str, user_id: str) -> str:
    """
    Generate a detailed report in the background.
    Uses Flex Priority for ~50% cost reduction.

    Suitable for:
    - "Send me the full analysis by email" features
    - Nightly batch summarization
    - Non-blocking insight generation

    Not suitable for:
    - Real-time chat responses
    - Anything the user is actively waiting for
    """
    model = GenerativeModel(
        model_name="gemini-2.5-pro",
        generation_config=GenerationConfig(
            max_output_tokens=4096,
            temperature=0.7,
        ),
    )

    # Flex Priority: higher latency tolerance → lower cost
    response = model.generate_content(
        contents=document_text,
        request_options={"timeout": 180},  # More generous timeout for flex
    )

    return response.text
```

Pairing Flex Priority with Context Caching can push combined savings to 60–70% on repeated large-context requests. For caching strategies, see the [Context Caching Cost Optimization Guide](/en/articles/gemini-api/gemini-api-context-caching-cost-optimization).

## Pricing the Subscription: Working Backwards from Costs

A simple rule I use: the subscription price should be at least 10× the per-user monthly API cost. If a paid user costs you $0.60/month in API calls, the floor for a paid tier is $6/month (or roughly ¥900).

For a ¥500/month Pro plan (roughly $3.30), the math works like this:

- App Store fee (30%): ¥150
- Gemini API cost (Pro, ~5 req/day): ¥60–80
- Infrastructure cost: ¥20–30
- **Net margin per user**: ¥240–270 (~50%)

This only holds because free users are served by Flash (7× cheaper), and paid users' cost is bounded by the rate limiter. Remove either constraint and the margins collapse.

## Takeaway: Treat Cost as a Design Constraint

The pattern I've seen across AI-powered app failures is almost always the same: someone builds the feature first, adds a payment button second, and discovers too late that the unit economics don't work.

The right order is:

1. Run the cost model (use the script in this article)
2. Design the freemium boundary (depth of experience, not request count)
3. Bind model selection to tier
4. Add edge-layer rate limiting before anything goes live
5. Wire up the Stripe webhook to keep tiers in sync
6. Apply Flex Priority to all non-realtime processing

The moment you treat Gemini API cost as a first-class design constraint — the same way you'd treat database schema or network latency — building profitable AI apps becomes a tractable engineering problem rather than a financial surprise.

Start with the cost model. Everything else follows from there.

## Measuring Freemium Conversion: What to Track

Building the technical infrastructure is only half the job. You also need instrumentation to know whether your freemium design is working. Here are the four metrics that matter most for Gemini API-powered apps.

**1. Free-to-paid conversion rate by feature touch**

Don't track conversion as a monolithic number. Break it down by which feature a free user last touched before upgrading. If 40% of upgrades happen right after a user hits the output token limit on a document analysis, that's a signal to make that limit more visible — and the upgrade path frictionless at that exact moment.

```python
# Example: logging feature interactions with upgrade context
# Store these events in Firestore or BigQuery for analysis

from google.cloud import firestore
from datetime import datetime, timezone

db = firestore.Client()

def log_feature_event(
    user_id: str,
    user_tier: str,
    feature_name: str,
    hit_limit: bool,
    tokens_used: int,
) -> None:
    """
    Log every Gemini API feature interaction.
    hit_limit=True marks events where the user encountered
    a freemium boundary — high-value signals for conversion optimization.
    """
    db.collection("feature_events").add({
        "user_id":     user_id,
        "user_tier":   user_tier,
        "feature":     feature_name,
        "hit_limit":   hit_limit,
        "tokens_used": tokens_used,
        "timestamp":   datetime.now(tz=timezone.utc),
    })
```

**2. API cost per free user vs. revenue per paid user**

You want this ratio to be at least 1:10. If a free user costs you $0.05/month in Flash calls, and a paid user generates $5/month net (after fees and API cost), the economics work. If free users are accidentally getting Pro-model calls (common when tier logic has a bug), this ratio deteriorates fast.

**3. Rate limit hit rate**

Track what percentage of free users hit their daily limit. If it's below 5%, your limit is too generous — you're giving away value that could convert. If it's above 40%, your limit is too restrictive — you're frustrating users before they see enough value to convert. The sweet spot is typically 15–25%: enough friction to motivate upgrading, not so much that users churn.

**4. Churn rate by usage intensity**

Heavy users who pay are your most valuable cohort. Track whether high-usage paid users churn at lower rates than low-usage ones. If they do — and they almost always do — it tells you that the features driving heavy usage are your moat. Protect and enhance those features first.

## Handling Currency and Regional Pricing

If your app has users in multiple countries, flat global pricing is leaving money on the table (and sometimes creating affordability barriers that suppress conversion). Gemini API costs are USD-denominated, but your users may be paying in JPY, EUR, BRL, or INR.

```python
# Regional pricing configuration example
# Set prices based on purchasing power parity while keeping unit economics intact

REGIONAL_PRICING = {
    "JP": {"pro_monthly": 580,  "currency": "JPY", "symbol": "¥"},
    "US": {"pro_monthly":  5,   "currency": "USD", "symbol": "$"},
    "EU": {"pro_monthly":  5,   "currency": "EUR", "symbol": "€"},
    "IN": {"pro_monthly": 199,  "currency": "INR", "symbol": "₹"},
    "BR": {"pro_monthly": 25,   "currency": "BRL", "symbol": "R$"},
}

def get_pricing_for_region(country_code: str) -> dict:
    """
    Return region-appropriate pricing.
    Falls back to USD pricing for unlisted countries.
    """
    return REGIONAL_PRICING.get(country_code, REGIONAL_PRICING["US"])
```

The Gemini API cost stays the same regardless of what currency your user pays in, so regional pricing is a pure revenue-side optimization. The practical implication: if your Japanese users pay ¥580/month ($3.90 USD) and your US users pay $5/month, your API cost per user is identical — but your JP conversion rate may be higher because ¥580 feels proportionally cheaper in the local market.

Stripe supports regional pricing through Price objects with currency-specific amounts, making this implementable without changing your backend architecture.

## Context Caching as a Cost Multiplier

If your AI feature involves a large, repeated context — a long document that users query multiple times, a system prompt with extensive instructions, a reference corpus — Context Caching can dramatically cut your cost structure.

```python
# Context Caching: upload once, reference many times
# Ideal for: document Q&A, long system instructions, reference data

import os
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

async def create_document_cache(document_content: str) -> str:
    """
    Upload a large document to Gemini's cache.
    Subsequent queries against this document cost significantly less
    because the cached tokens are priced at ~25% of normal input rates.

    Returns: cache_name (string ID to reference in future calls)
    Minimum cache size: 32,768 tokens (~25,000 words)
    TTL: 1 hour by default (adjustable up to several days)
    """
    cache = await client.aio.caches.create(
        model="gemini-2.5-pro",
        config=types.CreateCachedContentConfig(
            contents=[document_content],
            system_instruction=(
                "You are an expert analyst. Answer questions about the "
                "provided document with precision and cite specific sections."
            ),
            ttl="3600s",  # 1 hour TTL
        ),
    )
    return cache.name  # Store this in your DB alongside the document

async def query_cached_document(
    cache_name: str,
    user_question: str,
) -> str:
    """
    Query a cached document. Input tokens for the cached portion
    are charged at a reduced rate — approximately 75% less than
    uncached input tokens.
    """
    response = await client.aio.models.generate_content(
        model="gemini-2.5-pro",
        contents=user_question,
        config=types.GenerateContentConfig(
            cached_content=cache_name,
            max_output_tokens=2048,
        ),
    )
    return response.text
```

The business model implication of Context Caching is significant for document-centric apps. If you have a paid feature where users repeatedly query a long contract, financial report, or technical specification, caching the document means the first query pays full input cost, and every subsequent query pays ~25% of input cost. For a user who asks 20 questions about a 100,000-token document, you reduce input costs by roughly 75% starting from the second question. This makes deep document analysis features far more viable at modest price points. ## Testing Your Freemium Boundary: A Structured Approach

Freemium boundaries shouldn't be set and forgotten. The right limit depends on your specific user behavior, and the only way to know what converts best is to test systematically.

A structured approach:

**Week 1–2 (Baseline)**: Launch with a conservative limit (e.g., 5 free requests/day for a feature that costs you $0.01/request). Track conversion rate and churn.

**Week 3–4 (Increase limit)**: Raise the free limit by 50% (e.g., 7–8 requests/day). Does conversion rate drop significantly? If it drops less than the limit increase, you were too restrictive before. If it drops proportionally or more, the original limit was better.

**Week 5–6 (Feature quality test)**: Instead of changing the limit, improve the output quality for paid users. Does conversion improve without changing the free limit? If so, the limiting factor is perceived value, not friction.

The key discipline is changing only one variable at a time. Many developers change both the limit and the UI simultaneously, making it impossible to attribute results to either change.

## Graceful Degradation and Fallback Strategies

Production AI APIs have occasional downtime or latency spikes. Your monetization design needs to account for these scenarios — a failed API call that generates an error instead of a result will erode user trust and increase churn.

```python
import asyncio
import time
from google import genai
from google.api_core.exceptions import ResourceExhausted, DeadlineExceeded

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

async def analyze_with_graceful_degradation(
    content: str,
    user_tier: str,
    timeout_seconds: float = 30.0,
) -> dict:
    """
    Attempt Pro model for paid users, fall back to Flash on timeout/error.
    Flash fallback ensures paid users always get *something* even during
    Pro capacity issues — and we note the degradation for potential credit.
    """
    primary_model = "gemini-2.5-pro" if user_tier \!= "free" else "gemini-2.5-flash"
    fallback_model = "gemini-2.5-flash"  # Always available as fallback
    degraded = False

    try:
        response = await asyncio.wait_for(
            client.aio.models.generate_content(
                model=primary_model,
                contents=content,
                config=genai.types.GenerateContentConfig(
                    max_output_tokens=4096 if user_tier \!= "free" else 1024,
                ),
            ),
            timeout=timeout_seconds,
        )
        model_used = primary_model
    except (asyncio.TimeoutError, DeadlineExceeded, ResourceExhausted):
        # Fall back to Flash — lower quality but available
        response = await client.aio.models.generate_content(
            model=fallback_model,
            contents=content,
            config=genai.types.GenerateContentConfig(max_output_tokens=1024),
        )
        model_used = fallback_model
        degraded = True

    return {
        "result":    response.text,
        "model":     model_used,
        "degraded":  degraded,
        # If degraded=True, consider issuing a usage credit to the user
    }
```

When a paid user gets a degraded response, log the event and issue a usage credit (one extra free request) as compensation. This turns a potential support issue into a positive touchpoint. Users who receive proactive credits churn at measurably lower rates.
