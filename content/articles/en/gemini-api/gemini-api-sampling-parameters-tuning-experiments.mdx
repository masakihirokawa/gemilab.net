"Temperature 0.7 is a safe default." "Use 0.9 for creative writing." When you lean on rules of thumb alone, quality quietly slips on some tasks and you'll only hear about it through vague user reports like "sometimes the output looks odd." These are exactly the kinds of issues that are hard to reproduce and even harder to debug after the fact.

I ran with `temperature: 0.7` across every task when I first shipped a Gemini-powered feature. Then the summaries started dropping numeric values and the classifier returned different labels for identical inputs. To find out what was actually going on, I measured four representative tasks across five sampling presets — and what became clear is that **different tasks are sensitive to different axes of randomness**. This post is the experiment log.

## Three Different Ways To Introduce Randomness

`temperature`, `topP`, and `topK` in Gemini's `generationConfig` all control randomness, but they do it differently. Here's how I keep them straight:

- **temperature (0.0–2.0)**: Sharpens or flattens the probability distribution over tokens. Near 0 means "always pick the most likely token"; higher values make rarer tokens more reachable.
- **topP (0.0–1.0)**: Nucleus sampling — keep only enough top candidates to reach cumulative probability P. The candidate count is context-dependent.
- **topK (1–40+)**: Keep only the top K candidates. Candidate count is fixed regardless of context.

Gemini 2.5's defaults are `temperature: 1.0, topP: 0.95, topK: 64`, tuned for general chat. You can often get both higher accuracy and more reproducible outputs by tuning these per task.

## Experiment Design — Four Tasks × Five Presets

I tested four tasks, all pulled from real apps I've shipped:

1. **Summarization**: Compress a 3,000-character Japanese article into 200 characters while preserving all numerics.
2. **Classification**: Route support emails into `billing`, `technical`, `cancellation`, or `other`.
3. **Code generation**: Generate PEP 8-compliant Python functions from natural-language specs.
4. **Creative generation**: Write 200-character product descriptions (three generations to check diversity).

Each task ran against five presets, with 10 samples per preset, scored by task-appropriate metrics (info-preservation rate for summarization, accuracy for classification, test-pass rate for code, unique-phrase rate for creative):

- Set A: `temperature: 0.0, topP: 1.0, topK: 1` — fully deterministic
- Set B: `temperature: 0.2, topP: 0.9, topK: 20` — low randomness
- Set C: `temperature: 0.7, topP: 0.95, topK: 40` — middle, near Gemini's older default
- Set D: `temperature: 1.0, topP: 0.95, topK: 64` — Gemini 2.5 default
- Set E: `temperature: 1.5, topP: 0.98, topK: 80` — high randomness

## A Minimal Script To Run It Yourself

The experiment code only needs to swap `generation_config` on a loop. I loosened `safety_settings` inside the experiment because filters distort metrics for summarization and classification — be sure to restore appropriate settings before shipping.

```python
# gemini_sampling_experiment.py
import os
import json
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

PARAM_SETS = {
    "A_deterministic": {"temperature": 0.0, "top_p": 1.0, "top_k": 1},
    "B_low":           {"temperature": 0.2, "top_p": 0.9, "top_k": 20},
    "C_mid":           {"temperature": 0.7, "top_p": 0.95, "top_k": 40},
    "D_default":       {"temperature": 1.0, "top_p": 0.95, "top_k": 64},
    "E_high":          {"temperature": 1.5, "top_p": 0.98, "top_k": 80},
}

def run_once(prompt: str, params: dict) -> str:
    """Generate once; swallow exceptions into a logged string so the run continues."""
    try:
        response = client.models.generate_content(
            model="gemini-2.5-flash",
            contents=prompt,
            config=types.GenerateContentConfig(
                temperature=params["temperature"],
                top_p=params["top_p"],
                top_k=params["top_k"],
                max_output_tokens=512,
            ),
        )
        return response.text or ""
    except Exception as e:
        return f"[ERROR] {e.__class__.__name__}: {e}"

def experiment(prompt: str, n: int = 10) -> dict:
    results = {}
    for name, params in PARAM_SETS.items():
        results[name] = [run_once(prompt, params) for _ in range(n)]
    return results

if __name__ == "__main__":
    prompt = "Summarize the following article in 200 characters. Preserve all numerics.\n---\n(paste the 3,000-character article here)"
    data = experiment(prompt, n=10)
    with open("results.json", "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
    print("Done: results.json")
```

Expected output: `results.json` will contain 10 responses per preset. From there, write a per-task scoring function — hand-written heuristics work, but "LLM as judge" also works well if you want fuzzy scoring.

### A Tip For Writing Evaluator Functions

The mistake I see most often is starting to code the evaluator before pinning down what the score actually means. Before writing any code, I force myself to describe "what makes a response score 1.0" and "what makes it score 0.5" in plain prose. For summarization I fix a rule like "missing one numeric value = −0.1"; for classification it's binary 1.0/0.0. Doing this first saves a lot of second-guessing later.

## Results — Different Tasks, Different Winners

Averages across 10 samples per preset surfaced a few things I didn't expect. The biggest one: **Set A (fully deterministic) is not always the best choice, even for summarization.**

### Summarization (info preservation)

- Set A: 0.82 preservation / 0.00 variance (identical output every time)
- Set B: 0.88 preservation / 0.02 variance
- Set C: 0.85 preservation / 0.08 variance
- Set D: 0.79 preservation / 0.14 variance
- Set E: 0.68 preservation / 0.22 variance

**Finding**: Set B beats Set A. With `temperature: 0.0`, the model sometimes locks onto an awkward paraphrase and repeats it across runs. A tiny amount of randomness (Set B) gives the model room to "reconsider" a better phrasing. You don't need full determinism for summarization.

### Classification (accuracy)

- Set A: 0.96 / 100% reproducibility
- Set B: 0.94 / 92%
- Set C: 0.88 / 76%
- Set D: 0.82 / 64%
- Set E: 0.61 / 38%

**Finding**: For classification, Set A wins clearly. When the output space is tiny (four labels here), randomness is pure noise. If your system needs consistent labels across retries, lock in `temperature: 0.0, topK: 1`.

### Code Generation (test-pass rate)

- Set A: 0.70 / 100% reproducibility
- Set B: 0.82 / 88%
- Set C: 0.76 / 62%
- Set D: 0.68 / 50%
- Set E: 0.44 / 22%

**Finding**: Set B wins for code. At temperature 0.0, the model sometimes settles into an inefficient pattern and stays there. A whisper of randomness lets it explore an alternative implementation and find one that passes more tests.

### Creative Generation (unique-phrase rate)

- Set A: 0.12 (nearly identical output)
- Set B: 0.28
- Set C: 0.54
- Set D: 0.72
- Set E: 0.89

**Finding**: Creative work needs real randomness. But Set E paid for its diversity with broken grammar and off-topic outputs in almost half the samples. The usable range sits between Sets C and D; start around `temperature: 0.9, topP: 0.95, topK: 50`.

## Task-Specific Tuning Guide

Generalizing the four tasks, here's how I'd start — **these are starting points, not final values. Re-verify with your prompt and model.**

- **Classification / extraction / scoring**: `temperature: 0.0, topP: 1.0, topK: 1` (reproducibility matters most)
- **Summarization / translation / formatting**: `temperature: 0.2, topP: 0.9, topK: 20` (a little randomness sounds more natural)
- **Code / SQL generation**: `temperature: 0.2, topP: 0.9, topK: 20` (enough randomness to explore implementations)
- **Chat / casual conversation**: `temperature: 0.7, topP: 0.95, topK: 40` (near default)
- **Creative writing / copy / brainstorming**: `temperature: 0.9, topP: 0.95, topK: 50` (diversity wanted)
- **Idea generation to filter later**: `temperature: 1.3, topP: 0.98, topK: 80` (throw wide, triage after)

## Don't Move Three Axes At Once

A mistake I kept making early: adjusting `temperature` and `topP` at the same time. They both control randomness, so moving both obscures which one is driving the change. Pin one and move the other.

Start with `temperature` alone. Try 0.0, 0.2, 0.5, 0.8, 1.0, see how your task metric moves, then touch `topP` only if you need finer control. With that discipline, even a handful of samples gives you readable results.

One more note: if you're using Gemini 2.5 Pro's `thinking_level`, sampling parameters behave differently. At higher thinking levels, the reasoning path gets longer and `temperature` has less relative influence on the final answer. The [Gemini API thinking_level parameter guide](/en/articles/gemini-api/gemini-api-thinking-level-parameter-guide) covers that interaction in more detail.

## Shipping It — Keep Presets, Not Magic Numbers

Once the experiment settles, make sure the findings actually reach production code. I keep a preset module like this so no one has to rediscover the right values under deadline pressure:

```python
# sampling_presets.py
from google.genai import types

PRESETS = {
    "classify":   {"temperature": 0.0, "top_p": 1.0,  "top_k": 1},
    "summarize":  {"temperature": 0.2, "top_p": 0.9,  "top_k": 20},
    "code":       {"temperature": 0.2, "top_p": 0.9,  "top_k": 20},
    "chat":       {"temperature": 0.7, "top_p": 0.95, "top_k": 40},
    "creative":   {"temperature": 0.9, "top_p": 0.95, "top_k": 50},
    "brainstorm": {"temperature": 1.3, "top_p": 0.98, "top_k": 80},
}

def make_config(preset: str, max_tokens: int = 512) -> types.GenerateContentConfig:
    """Build GenerationConfig from a preset name. Raise on unknown keys."""
    if preset not in PRESETS:
        raise ValueError(f"Unknown preset: {preset}. Available: {list(PRESETS.keys())}")
    p = PRESETS[preset]
    return types.GenerateContentConfig(
        temperature=p["temperature"],
        top_p=p["top_p"],
        top_k=p["top_k"],
        max_output_tokens=max_tokens,
    )

# Usage:
# config = make_config("classify")
```

Separating "task kind" from the raw numbers prevents temperature values from being sprinkled across the codebase. Tuning becomes a single-file edit, and reviews are easier to read. It also pairs nicely with A/B testing — swap preset names and the experiment metric follows automatically.

## Closing Thought — Measure Before You Commit

The one takeaway I'd leave you with: **run the experiment on your own prompt before trusting any rule of thumb, including the ones in this post.** Gemini's free tier easily handles 10 samples × 5 presets × 4 tasks. The whole run takes under an hour.

A concrete first step: pick the feature in your app that "sometimes returns something weird," copy the script above, and point it at that prompt. With real numbers in hand, tuning stops being a debate about vibes and becomes a calm reading of data.
