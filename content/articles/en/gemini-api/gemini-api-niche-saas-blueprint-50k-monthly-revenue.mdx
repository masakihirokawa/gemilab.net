## Why niche, not general-purpose

The first design trap when building a Gemini-API-based SaaS is choosing a **broad, general-purpose target.** AI chat, AI writing assistants, AI coding helpers — these categories are already dominated by major players offering near-free or free service. As an indie developer, competing there is effectively impossible.

What I've seen actually work, after years of running my own apps, is **niche SaaS targeted at a specific profession, hobby, or lifestyle.** Concrete examples: a tool for cram-school instructors to AI-assist student-paper grading, a tool for indie novelists that catches typos while preserving their personal voice, a tool for individual real-estate investors that auto-summarizes property listings into one-line briefs. The unifying property: a clearly bounded audience that mainstream general-purpose AI doesn't quite serve.

This article is a blueprint for taking that kind of niche SaaS to **~$350/month (about $7/month × ~50 active subscribers)** with Gemini API as the core. We're not aiming at $10K MRR. We're aiming at the level of revenue an indie developer can realistically reach in three months.

## Reference architecture — the minimum viable stack

For niche SaaS, the stack I keep returning to is:

- **Frontend**: Next.js 16 + Cloudflare Pages
- **API layer**: Cloudflare Workers
- **AI calls**: Gemini API (2.5 Flash or Flash Lite)
- **State**: Cloudflare KV
- **Billing**: Stripe Checkout (Subscription mode)
- **Email**: Resend

Total fixed monthly cost: $0–$10. Cloudflare's free tier, Gemini's free tier, and Stripe's per-transaction fees (~3.6%) are essentially the only ways money leaves the system.

### Why Cloudflare Workers specifically

Two reasons. First, **edge execution** dramatically reduces perceived latency. Users connect to a Worker close to them; that Worker calls Gemini and returns the response. The user-perceived round-trip feels noticeably faster than a centrally-hosted backend.

Second, Workers have first-class integration with KV and Durable Objects, which is exactly where you'll want to put quota counters and member state. Keeping everything on one platform meaningfully reduces operational load — important for a solo developer.

## Don't graduate from Free Tier on user count — graduate on revenue

A common misconception is "graduate from Free Tier when you hit the user limit." This sounds reasonable but is actually too late from a profit perspective.

The correct trigger is **graduate when revenue meaningfully exceeds the cost of the Pay-as-you-go tier you're moving to.** Concretely:

Phase 1 ($0–$70/month MRR): Free Tier only. API cost = $0. Profit = revenue.

Phase 2 ($70–$200/month MRR): Approaching Free Tier rate limits — switch to Pay-as-you-go. API cost ramps to $10–$25/month.

Phase 3 ($200–$350/month MRR): Ship Context Caching and the daily quota system aggressively. API cost caps out around $25–$40/month even as revenue grows.

The whole point of the phasing is to **deliberately decouple revenue growth from API cost growth** by switching to cost-aware patterns at exactly the moment you can afford the engineering time.

## The three-layer quota design

Once you're at $350/month MRR, a single hostile user or an unexpected heavy user can spike your monthly bill by 2–3×. The defense is a **three-layer quota: per-user × daily × monthly, plus a global daily budget.**

### Implementation skeleton

```typescript
const DAILY_CAP = 50_000;
const MONTHLY_CAP = 1_000_000;
const GLOBAL_DAILY_BUDGET = 500_000;

async function quotaGate(env: Env, userId: string, estimatedTokens: number) {
  const today = new Date().toISOString().slice(0, 10);
  const month = today.slice(0, 7);

  // Layer 1: per-user × daily
  const userDayKey = `q:u:${userId}:${today}`;
  const userDayUsed = parseInt((await env.KV.get(userDayKey)) ?? "0", 10);
  if (userDayUsed + estimatedTokens > DAILY_CAP) {
    throw new QuotaError("Daily quota exceeded");
  }

  // Layer 2: per-user × monthly
  const userMonthKey = `q:um:${userId}:${month}`;
  const userMonthUsed = parseInt((await env.KV.get(userMonthKey)) ?? "0", 10);
  if (userMonthUsed + estimatedTokens > MONTHLY_CAP) {
    throw new QuotaError("Monthly quota exceeded");
  }

  // Layer 3: global × daily (last-resort emergency cap)
  const globalKey = `q:g:${today}`;
  const globalUsed = parseInt((await env.KV.get(globalKey)) ?? "0", 10);
  if (globalUsed + estimatedTokens > GLOBAL_DAILY_BUDGET) {
    throw new QuotaError("Global daily budget reached");
  }

  await Promise.all([
    env.KV.put(userDayKey, String(userDayUsed + estimatedTokens), { expirationTtl: 60 * 60 * 26 }),
    env.KV.put(userMonthKey, String(userMonthUsed + estimatedTokens), { expirationTtl: 60 * 60 * 24 * 32 }),
    env.KV.put(globalKey, String(globalUsed + estimatedTokens), { expirationTtl: 60 * 60 * 26 }),
  ]);
}
```

Layer 3 is the emergency last line of defense. Without it, an unexpected viral moment or a coordinated abuse pattern can multiply your monthly bill ten-fold before you can react.

## Context Caching at scale

Most niche-SaaS use cases share a common shape: **a long, domain-specific system prompt sent on every request.** Grading rubrics, style guides, classification taxonomies. This is exactly the case Context Caching was designed for.

### Cache granularity

The pattern that works in production is to **split caches into "shared across all users" and "per-user":**

```typescript
// Shared: rubrics, guidelines, output format
const sharedCache = await ai.caches.create({
  model: "gemini-2.5-flash",
  contents: SHARED_SYSTEM_PROMPT,
  ttl: "86400s", // 24h
});

// Per-user: history, preferences
const userCache = await ai.caches.create({
  model: "gemini-2.5-flash",
  contents: userSpecificContext,
  ttl: "3600s", // 1h
});

const response = await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: userInput,
  cachedContent: [sharedCache.name, userCache.name],
});
```

Long TTL on the shared cache, short TTL on the per-user cache, is the operational balance that survives in real workloads.

## Stripe integration — minimum viable

For niche SaaS, plain Stripe Checkout in Subscription mode is enough. Don't reach for complex billing logic before you've shipped.

### Creating the Checkout Session

```typescript
const session = await stripe.checkout.sessions.create({
  mode: "subscription",
  line_items: [
    {
      price_data: {
        currency: locale === "ja" ? "jpy" : "usd",
        recurring: { interval: "month" },
        unit_amount: locale === "ja" ? 1000 : 9,
        product_data: {
          name: locale === "ja" ? "Pro プラン" : "Pro Plan",
          description: locale === "ja"
            ? "AI 添削機能の月額利用"
            : "Monthly access to the AI proofreader",
          images: ["https://example.com/images/stripe-product.png"],
        },
      },
      quantity: 1,
    },
  ],
  success_url: `${origin}/${locale}/thanks?session_id={CHECKOUT_SESSION_ID}`,
  cancel_url: `${origin}/${locale}/pricing`,
  metadata: { plan_type: "pro", locale },
});
```

Always include `product_data.images`. Without it, Stripe Checkout displays your description thinly and conversion drops measurably.

### Minimal webhook handling

```typescript
if (event.type === "checkout.session.completed") {
  const session = event.data.object as Stripe.Checkout.Session;
  const email = session.customer_email ?? session.customer_details?.email;
  if (email) {
    await env.KV.put(
      `member:${email}`,
      JSON.stringify({ plan: "pro", expiresAt: Date.now() + 31 * 24 * 60 * 60 * 1000 }),
      { expirationTtl: 60 * 60 * 24 * 35 }
    );
  }
}

if (event.type === "invoice.paid") {
  const invoice = event.data.object as Stripe.Invoice;
  const email = invoice.customer_email;
  if (email) {
    await env.KV.put(
      `member:${email}`,
      JSON.stringify({ plan: "pro", expiresAt: Date.now() + 31 * 24 * 60 * 60 * 1000 }),
      { expirationTtl: 60 * 60 * 24 * 35 }
    );
  }
}
```

Handling `invoice.paid` separately is what extends access on monthly renewals. Skipping this is how second-month users end up locked out despite being current on their billing.

## A retention move unique to niche SaaS — make their love of the niche visible

The retention dynamics of niche SaaS are different from generic SaaS in one important way: **users care deeply about the niche.** Designs that make that affection visible to them produce dramatically better retention.

### The monthly personal email

For a grading-assistance tool: "This month you reviewed 78 student papers, 12 more than last month. The 'understanding student intent' weakness from last month's data shows clear improvement this month."

After shipping this monthly email, my churn rate dropped 30–40% across the apps where I tested it. Gemini API makes the per-user generation effectively free at this scale:

```typescript
async function generateMonthlyReview(env: Env, userId: string, stats: UserStats) {
  const prompt = `Given the following user statistics, write an encouraging monthly review under 200 characters.\n\n${JSON.stringify(stats, null, 2)}`;
  return await callGemini(env, prompt, { maxOutputTokens: 256 });
}
```

## Three traps niche SaaS founders fall into

Three failure modes I've personally lived through, in order of how often they catch new niche-SaaS founders.

First: **niching down too far.** "Cram-school instructors who teach math to 4th-graders at solo tuition centers" is too narrow — total addressable market is too small to reach $350/month. Start with the broader version of the niche, and let real usage data show you which sub-niche is naturally pulling. Refine from there.

Second: **prompts that quietly inflate output cost.** "Grade this paper" vs. "Following this rubric, output the following fields in JSON format" — same task, but output token counts can differ by 3–5×. Output structure controls cost.

Third: **listening to users *too much*.** Niche-SaaS users are passionate, so they generate feature requests at high volume. Implementing all of them blurs the niche until no one is sure who the product is for anymore. **Hold the line at five core features. Defer everything else with "We're considering it for the next version."**
