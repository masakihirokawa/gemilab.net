# Gemini API Embedding Error Guide: Fix RAG Accuracy Issues, Dimension Mismatches & Rate Limits

Building a RAG system or semantic search pipeline with Gemini's Embedding API seems straightforward — until it isn't. Vectors won't insert into your database. Searches return irrelevant results. Batch processing crashes halfway through. Sound familiar?

Most of these problems have clear root causes and clean fixes. This guide covers the errors developers run into most often with Gemini Embedding models, along with working Python code to resolve them.

## Gemini Embedding Models — What You're Working With

Before diving into errors, here's a quick reference for the current models:

- **text-embedding-004**: 768 dimensions. The general-purpose workhorse, best for most use cases.
- **gemini-embedding-exp-03-07**: Experimental model with configurable dimensions up to 3072.
- **embedding-001**: Previous generation. Avoid for new projects.

A large percentage of issues come from mixing embeddings from different models, or creating vector database collections with wrong dimension settings.

## Error #1: Dimension Mismatch on Vector DB Insert

**Symptom**: `InvalidDimensionException: Embedding dimension 768 does not match collection dimensionality 1536` (or similar).

This is the most common error. It happens when you create a vector database collection with one dimension setting, then try to insert embeddings from a model with different dimensions.

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_API_KEY")

# Always verify the actual output dimensions first
def check_embedding_dimensions(model: str = "text-embedding-004") -> int:
    result = genai.embed_content(
        model=f"models/{model}",
        content="test",
        task_type="RETRIEVAL_DOCUMENT"
    )
    dims = len(result["embedding"])
    print(f"Model: {model} → Dimensions: {dims}")
    return dims

actual_dims = check_embedding_dimensions()  # → 768 for text-embedding-004
```

**For Pinecone:**

```python
import pinecone

EMBEDDING_DIMS = 768  # must match your model's output

pc = pinecone.Pinecone(api_key="YOUR_PINECONE_KEY")
pc.create_index(
    name="gemini-docs",
    dimension=EMBEDDING_DIMS,  # set this correctly before inserting
    metric="cosine",
    spec=pinecone.ServerlessSpec(cloud="aws", region="us-east-1")
)
```

**Important**: If you change embedding models, you must recreate the index from scratch. Existing embeddings from a different model are incompatible and will silently produce wrong results even if the dimensions happen to match.

## Error #2: Low Retrieval Accuracy in RAG

**Symptom**: Texts that should be highly similar score near zero. Unrelated documents rank higher than relevant ones.

This is almost always a `task_type` misconfiguration. Gemini Embedding has a `task_type` parameter that optimizes the embedding for its intended purpose, and using the wrong type significantly degrades retrieval quality.

```python
# Wrong: No task_type defaults to SEMANTIC_SIMILARITY
# This is suboptimal for RAG retrieval
result = genai.embed_content(
    model="models/text-embedding-004",
    content=text
)

# Correct: Use different task types for documents vs. queries
def embed_document(text: str) -> list[float]:
    """Embed text being stored in the database."""
    result = genai.embed_content(
        model="models/text-embedding-004",
        content=text,
        task_type="RETRIEVAL_DOCUMENT"  # for content being indexed
    )
    return result["embedding"]

def embed_query(query: str) -> list[float]:
    """Embed a user search query."""
    result = genai.embed_content(
        model="models/text-embedding-004",
        content=query,
        task_type="RETRIEVAL_QUERY"  # for search queries — this matters!
    )
    return result["embedding"]
```

**task_type reference:**

- `RETRIEVAL_DOCUMENT` — Content being stored in a database (documents, passages)
- `RETRIEVAL_QUERY` — User queries searching for similar content
- `SEMANTIC_SIMILARITY` — Comparing two specific texts for similarity
- `CLASSIFICATION` — Text classification downstream tasks
- `CLUSTERING` — Clustering tasks

If you already have a database with mixed task_types, you'll need to re-embed everything consistently. The document and query embeddings must be generated with the matching pair of types to work correctly.

## Error #3: 429 Rate Limit During Batch Processing

**Symptom**: Processing hundreds or thousands of texts fails mid-way with `429 Resource Exhausted`.

```python
import time
import google.generativeai as genai
from google.api_core import exceptions

def embed_batch_with_retry(
    texts: list[str],
    model: str = "text-embedding-004",
    task_type: str = "RETRIEVAL_DOCUMENT",
    batch_size: int = 100,     # max 100 texts per API call
    inter_batch_delay: float = 0.5,
    max_retries: int = 3
) -> list[list[float]]:
    """Batch embedding with automatic rate limit handling."""
    
    all_embeddings = []
    total_batches = (len(texts) + batch_size - 1) // batch_size
    
    for batch_num, i in enumerate(range(0, len(texts), batch_size), 1):
        batch = texts[i:i + batch_size]
        print(f"Processing batch {batch_num}/{total_batches}...")
        
        for attempt in range(max_retries):
            try:
                results = genai.embed_content(
                    model=f"models/{model}",
                    content=batch,    # pass a list for batch processing
                    task_type=task_type
                )
                all_embeddings.extend(results["embedding"])
                
                # Pace requests to stay under rate limits
                if i + batch_size < len(texts):
                    time.sleep(inter_batch_delay)
                break
                
            except exceptions.ResourceExhausted:
                wait = inter_batch_delay * (2 ** attempt)
                print(f"Rate limit hit. Waiting {wait:.1f}s... (attempt {attempt + 1}/{max_retries})")
                time.sleep(wait)
            
            except Exception as e:
                raise RuntimeError(f"Unexpected error on batch {batch_num}: {e}") from e
    
    return all_embeddings

# Usage — handles any number of texts
documents = ["text 1", "text 2", ...]
embeddings = embed_batch_with_retry(documents)
```

**Free tier tip**: The free tier has strict requests-per-minute limits. Increasing `inter_batch_delay` or moving to a paid plan is the most reliable solution for high-volume processing.

## Error #4: Input Text Too Long

**Symptom**: `400 Request payload size exceeds the limit` when embedding long documents.

The `text-embedding-004` model accepts approximately 2,048 tokens of input — roughly 800–1,200 words in English. Long PDFs or documents need to be chunked first.

```python
def chunk_and_embed(
    text: str,
    max_chars: int = 1000,
    overlap: int = 100,
    task_type: str = "RETRIEVAL_DOCUMENT"
) -> list[dict]:
    """Split long text into chunks and embed each one."""
    
    chunks = []
    start = 0
    
    while start < len(text):
        end = start + max_chars
        chunk_text = text[start:end]
        
        # Try to split at sentence boundaries rather than mid-sentence
        if end < len(text):
            for sep in [". ", "\n\n", "\n"]:
                last_sep = chunk_text.rfind(sep)
                if last_sep > max_chars // 2:
                    chunk_text = chunk_text[:last_sep + len(sep)]
                    end = start + len(chunk_text)
                    break
        
        result = genai.embed_content(
            model="models/text-embedding-004",
            content=chunk_text,
            task_type=task_type
        )
        
        chunks.append({
            "text": chunk_text,
            "start": start,
            "end": end,
            "embedding": result["embedding"]
        })
        
        start = end - overlap  # overlap preserves context at boundaries
    
    return chunks

# Usage
long_document = "A very long document..."
chunks = chunk_and_embed(long_document)
print(f"Split into {len(chunks)} chunks, each with embeddings ready")
```

**Choosing chunk size**: For most use cases, 500–800 characters (or roughly 100–200 words) works well. Larger chunks preserve more context but may dilute the embedding signal. Smaller chunks are more precise but may miss broader meaning. Test with your actual data to find the right balance.

## Frequently Asked Questions

**Q: Is embedding accuracy worse for non-English languages?**
A: `text-embedding-004` is multilingual and performs well across many languages. However, cross-language retrieval (querying in English against Japanese documents) can be inconsistent. For best results, keep queries and documents in the same language.

**Q: How do I migrate from embedding-001 to text-embedding-004?**
A: Since the dimensions differ (768 vs. potentially different for embedding-001), you must recreate your vector database index and re-embed all documents. Plan for downtime during migration, or maintain parallel indexes during the transition.

**Q: Should I cache embedding results?**
A: Yes, absolutely. Re-embedding unchanged texts wastes API quota. Store embeddings in your vector database with the source text hash as a key, and skip re-embedding if the hash matches.

## Summary

The most common Gemini Embedding issues and their fixes:

- **Dimension mismatch** → Check model output dimensions before creating your vector DB collection; recreate the index if you change models
- **Poor RAG accuracy** → Use `RETRIEVAL_DOCUMENT` for stored content and `RETRIEVAL_QUERY` for search queries — don't mix them
- **429 rate limit errors** → Use batch processing (up to 100 texts per request) with exponential backoff retry
- **Text too long** → Chunk documents into 800–1,000 character segments with 100-character overlap before embedding

Getting `task_type` right is the single change that delivers the biggest accuracy improvement in most RAG setups. If your search results are poor, that's the first thing to verify.
