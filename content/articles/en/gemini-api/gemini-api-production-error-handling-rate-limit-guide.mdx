Demo code works instantly. The problems appear when real traffic hits. Rate limit errors on the first day in production, unexpected costs at month end, timeouts that weren't an issue locally — these are the friction points that don't show up until you're past the prototype stage.

## Understanding Rate Limit Types

Gemini API enforces limits on multiple dimensions. Confusing them leads to wrong fixes.

**RPM (Requests Per Minute):** Request count per minute. Burst traffic triggers this most often.

**TPM (Tokens Per Minute):** Token throughput per minute. Long-form processing (document summarization, video analysis) hits this even at low request counts.

**RPD (Requests Per Day):** Daily request cap. Critical on Free tier and Tier 1.

On the Free tier, Gemini 2.5 Pro allows 15 RPM and 1M tokens per day. That's enough for development but not for production with real users. Move to at least Tier 1 (billing enabled) before going live.

## Exponential Backoff Retry Implementation

Retrying immediately after a rate limit error makes things worse — it puts more load on the server and extends how long the limit lasts. Exponential backoff with jitter is the correct approach.

```python
import google.generativeai as genai
import time
import random
from typing import Optional

genai.configure(api_key="YOUR_GEMINI_API_KEY")

def gemini_with_retry(
    model_name: str,
    contents: list,
    max_retries: int = 5,
    base_delay: float = 1.0,
    max_delay: float = 60.0
) -> Optional[genai.types.GenerateContentResponse]:
    """Call Gemini API with exponential backoff retry."""
    
    model = genai.GenerativeModel(model_name)
    
    for attempt in range(max_retries):
        try:
            return model.generate_content(contents)
            
        except genai.types.generation_types.StopCandidateException as e:
            # Safety filter or content policy block — retrying won't help
            print(f"Generation stopped: {e}")
            return None
            
        except Exception as e:
            error_str = str(e).lower()
            
            if "429" in error_str or "resource exhausted" in error_str:
                if attempt == max_retries - 1:
                    print(f"Max retries exceeded: {e}")
                    raise
                
                # Exponential backoff + jitter to avoid thundering herd
                delay = min(base_delay * (2 ** attempt), max_delay)
                jitter = random.uniform(0, delay * 0.1)
                wait_time = delay + jitter
                print(f"Rate limited (attempt {attempt + 1}/{max_retries}): waiting {wait_time:.1f}s")
                time.sleep(wait_time)
                continue
            
            elif "500" in error_str or "503" in error_str:
                if attempt == max_retries - 1:
                    raise
                wait_time = base_delay * (2 ** attempt)
                print(f"Server error: retrying in {wait_time:.1f}s")
                time.sleep(wait_time)
                continue
            
            # All other errors: don't retry
            raise
    
    return None

response = gemini_with_retry(
    "gemini-2.5-pro-latest",
    ["Your prompt here"],
    max_retries=5
)
if response:
    print(response.text)
```

The jitter prevents multiple clients from all retrying at exactly the same moment — the "thundering herd" problem that turns a brief rate limit into a sustained outage.

## Which Errors to Retry and Which to Not

Not all errors benefit from retrying. Trying to retry a malformed request just wastes quota.

**Retry these:**
- `429 RESOURCE_EXHAUSTED` — rate limit, use exponential backoff
- `500 INTERNAL_SERVER_ERROR` — transient server issue
- `503 SERVICE_UNAVAILABLE` — temporary service disruption

**Don't retry these:**
- `400 INVALID_ARGUMENT` — your request is malformed; fix the code
- `403 PERMISSION_DENIED` — API key lacks necessary permissions
- `404 NOT_FOUND` — model name is wrong
- `StopCandidateException` — content was blocked by safety filters; the prompt needs to change

```python
def classify_error(error: Exception) -> str:
    error_str = str(error).lower()
    
    if "429" in error_str or "resource_exhausted" in error_str:
        return "rate_limit"       # Retryable
    elif "500" in error_str or "503" in error_str:
        return "server_error"     # Retryable
    elif "400" in error_str:
        return "invalid_request"  # Fix the code
    elif "403" in error_str:
        return "auth_error"       # Check API key
    else:
        return "unknown"
```

## Token Counting Before Large Requests

Gemini 2.5 Pro supports up to 1M tokens in context, but latency increases significantly with context size. A prompt that takes 2 seconds at 100K tokens might take 6–8 seconds at 500K tokens. Checking token count before sending avoids surprises.

```python
def count_tokens_before_send(model_name: str, contents: list) -> int:
    """Count tokens before sending. count_tokens doesn't consume API quota."""
    model = genai.GenerativeModel(model_name)
    token_count = model.count_tokens(contents)
    total = token_count.total_tokens
    
    if total > 500_000:
        print(f"⚠️ Large request: {total:,} tokens")
        print("  Expect increased latency")
    
    return total

count = count_tokens_before_send("gemini-2.5-pro-latest", ["Your long document..."])
print(f"Token count: {count:,}")
```

`count_tokens` is an API call but doesn't consume generation quota or cost anything. Use it freely for validation.

## Usage Tracking for Cost Control

```python
import time
from dataclasses import dataclass, field

@dataclass
class UsageStats:
    """Track API usage across multiple calls."""
    requests: int = 0
    input_tokens: int = 0
    output_tokens: int = 0
    errors: int = 0
    start_time: float = field(default_factory=time.time)
    
    def add_response(self, response: genai.types.GenerateContentResponse):
        self.requests += 1
        if hasattr(response, "usage_metadata"):
            self.input_tokens += response.usage_metadata.prompt_token_count
            self.output_tokens += response.usage_metadata.candidates_token_count
    
    def print_summary(self):
        elapsed = time.time() - self.start_time
        # Gemini 2.5 Pro pricing (April 2026)
        # Input: $1.25/1M tokens (under 200K), Output: $10/1M tokens
        input_cost = (self.input_tokens / 1_000_000) * 1.25
        output_cost = (self.output_tokens / 1_000_000) * 10.0
        
        print(f"=== Usage Summary ===")
        print(f"Elapsed: {elapsed:.1f}s")
        print(f"Requests: {self.requests} ({self.errors} errors)")
        print(f"Input tokens: {self.input_tokens:,}")
        print(f"Output tokens: {self.output_tokens:,}")
        print(f"Estimated cost: ${input_cost + output_cost:.4f}")

stats = UsageStats()
response = gemini_with_retry("gemini-2.5-pro-latest", ["Your prompt"])
if response:
    stats.add_response(response)
stats.print_summary()
```

## Production Settings Often Overlooked

**Set explicit timeouts.** By default, requests don't time out. In production, a hung request blocks resources indefinitely:

```python
response = model.generate_content(
    contents,
    request_options={"timeout": 120}  # 120 second timeout
)
```

**Model fallback strategy.** Some tasks that need Gemini 2.5 Pro during peak hours can be served by Flash with acceptable quality. Tiering requests by importance and routing lower-priority ones to Flash reduces both cost and exposure to Pro-tier rate limits.

**Log everything initially.** Start with verbose logging of every error type and count. The distribution of errors in production rarely matches what you'd expect, and you can't optimize what you can't see.

The first step toward a stable production integration is knowing which errors you're actually hitting. Once that's visible, the right fixes become obvious.
