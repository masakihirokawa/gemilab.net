One morning while glancing at the analytics dashboard for one of the wallpaper apps I run, I noticed that 0.3% of my Gemini API calls were taking longer than 8 seconds. The median sat at 1.2 seconds — looking at averages alone, nothing seemed wrong. But once an AdMob interstitial ad and an AI response started overlapping in the wrong order, the perceived weight of the app changed dramatically. I am Masaki Hirokawa, an indie developer and artist running Dolice Labs and an app business that has shipped over 50 million downloads since 2014. The same tail-latency problem showed up across both, and I eventually landed on an old idea from distributed systems literature: request hedging. This article is a field memo from that work.

## Tail Latency Is Invisible at the Median

If you only watch average response times for Gemini API, you will miss the 99th percentile — the moments where your users are actually frustrated. I had two separate weeks where Day 7 retention dipped 2.1 percentage points, and every time I dug in, those days mapped one-to-one to "afternoons when p99 crossed 7 seconds."

The median barely moves. Only the tail drops, and retention quietly recovers. Cost goes up about 8%. That trade-off is the canonical shape of request hedging.

## Where the Idea Comes From

The technique traces back to Dean & Barroso's "The Tail at Scale" (2013). If a request hasn't returned within some threshold, you fire a second copy at a different replica. Whichever completes first wins; the loser is discarded. LLM APIs route across many serving instances internally, so when one call lands on a slow instance, the other call often hits a healthier one. That is why hedging works at all on a managed API you do not control.

In my deployment, when I call Gemini 2.5 Flash, if the first request hasn't responded within 1,800 ms I dispatch a second one. The 1,800 ms threshold is derived from the observed p95 — fire just before the slow tail would normally kick in.

## A Minimal Implementation in TypeScript

The whole thing is surprisingly short. Here is the production-shaped version, stripped of internal KV and retry layers:

```typescript
import { GoogleGenerativeAI } from "@google/generative-ai";

const client = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);

export async function hedgedGenerate(
  prompt: string,
  options: {
    hedgeAfterMs: number;  // e.g. 1800
    model?: string;        // e.g. "gemini-2.5-flash"
    maxAttempts?: number;  // default 2 (i.e. at most 2 in flight)
  }
): Promise<string> {
  const model = client.getGenerativeModel({
    model: options.model ?? "gemini-2.5-flash",
  });

  const abortControllers: AbortController[] = [];

  const launch = async (attemptIndex: number): Promise<string> => {
    const ctrl = new AbortController();
    abortControllers.push(ctrl);
    try {
      const res = await model.generateContent({
        contents: [{ role: "user", parts: [{ text: prompt }] }],
        // @ts-expect-error: signal is passed through to the underlying fetch
        requestOptions: { signal: ctrl.signal },
      });
      return res.response.text();
    } catch (e) {
      if (ctrl.signal.aborted) throw new Error("aborted-loser");
      throw e;
    }
  };

  const winners: Promise<string>[] = [launch(0)];

  // After hedgeAfterMs, fire the second request
  const hedgeTimer = new Promise<string>((_, reject) => {
    setTimeout(() => {
      winners.push(launch(1).catch(reject));
    }, options.hedgeAfterMs);
  });

  const winner = await Promise.race([winners[0], hedgeTimer]);
  // Once we have a winner, abort the loser unconditionally
  abortControllers.forEach((c) => {
    if (!c.signal.aborted) c.abort();
  });
  return winner;
}
```

Three details matter. First, you have to abort the loser. Forget this step and you will be billed twice on every hedged request. Second, do not hard-code the threshold — compute it from observed p95, which I cover below. Third, cap concurrency at 2. Going to 3+ saturates the latency benefit while costs climb linearly. My production setting is fixed at 2.

## Adaptive Hedging — Tracking p95 in Real Time

A static threshold backfires the moment traffic gets bursty. During peak hours every request hedges and your bill explodes. Rolling p95 with a hard floor keeps overhead near the 8% I quoted earlier.

```typescript
class P95Tracker {
  private samples: number[] = [];
  private readonly windowSize = 200;

  record(latencyMs: number) {
    this.samples.push(latencyMs);
    if (this.samples.length > this.windowSize) this.samples.shift();
  }

  hedgeThresholdMs(): number {
    if (this.samples.length < 50) return 2500; // warmup default
    const sorted = [...this.samples].sort((a, b) => a - b);
    const idx = Math.floor(sorted.length * 0.95);
    return Math.max(1200, sorted[idx]); // never go below 1.2s
  }
}
```

The 1.2s floor is empirical. Drop below it and the hedge rate climbs over 30%, which destroys the cost math.

## Fitting Inside the AdMob Interstitial Window

In my apps the average interstitial ad runs 4.8 seconds before the user dismisses it. If I can finalize the Gemini response in the background during that window, I can render content the instant the ad closes. When p99 was 6.8 seconds, 2.6% of sessions saw a "still generating…" spinner after the ad. Post-hedging, that dropped to 0.4%.

That ad-window framing is a useful design constraint for any indie developer monetizing with AdMob. Take the seconds you get from an ad (4.8s for me), subtract a 1-second safety buffer, and you have your effective p99 budget. I set 3.5s as my internal SLO and back the hedge threshold out from there.

## When Hedging Is the Wrong Tool

Hedging is not a general fix. Three cases where I explicitly avoid it.

Function calling. Hedged requests can cause the same tool to fire twice, which is dangerous for any side-effectful function. I disabled hedging on the function-calling path and switched it to streaming responses instead.

Streaming itself. With streaming, the time-to-first-token is short by design, and racing two streams produces two half-formed responses competing for the UI. Backpressure handling fits streaming; hedging does not.

Calls that hit the context cache. A cache hit drops median latency near 0.4s, so hedging cannot help — and recomputing the cache key on the loser path actively hurts. Cache-eligible calls route around the hedge wrapper entirely.

## Operational Gotchas From Six Weeks of Running This

Three things bit me in production.

Quota counters double up. Even though I abort the loser, Gemini's quota service still counts the call. In a month where my hedge rate was 12%, the billed request count was 1.18x baseline, not the naive 1.12x. If you operate near your RPM ceiling, you have to back hedge rate out of that headroom. I added a circuit that disables hedging entirely once RPM hits 75% of the ceiling.

Log aggregation gets messy. Naive metrics double-count latency by counting both winners and losers. I tag every OpenTelemetry span with `hedge.role = "winner" | "loser"` and filter for `role = "winner"` in the dashboard. That single change made the latency graph readable again.

Cost forecasting is harder than it looks. Hedge rate is not stationary. In my deployment, weekday 2pm hits 18%, weekday 3am hits 4%, and the monthly average lands at 8% — but the worst day was 14%. I run a separate guardrail that cuts hedging off if the projected monthly overage exceeds the budget envelope.

## When to Adopt This in an Indie Project

Final recommendation. Hedging is worth adopting when three conditions all hold: monthly Gemini spend above roughly $40, p99/p50 ratio above 4x, and a concrete UX requirement like an ad-window to fit inside. If those three line up, I am not aware of another single change that cuts p99 by more than half at only ~8% cost increase.

Conversely, for a brand-new small chatbot, the higher-leverage moves are still caching and picking the right model tier (Flash vs Pro). I run hedging on the highest-traffic Dolice Labs property and skip it on experimental apps that haven't earned the complexity.

If you want to try this, measure your own p95 and p99 for a week first. Cloud Monitoring or Cloudflare Analytics Engine will let you wire that up in about thirty minutes. If your p99/p50 ratio sits above 4x, take the implementation above and run it as-is. I am still tuning the optimal threshold for my own deployment, and I'd be glad if these notes save someone else from rediscovering the same gotchas the hard way.
