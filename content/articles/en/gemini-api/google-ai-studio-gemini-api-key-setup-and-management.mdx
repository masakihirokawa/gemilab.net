The first hurdle most people hit with the Gemini API is "how do I get a key?" Google AI Studio's interface is clean, but if you have not used Google Cloud before, the right setup is not obvious. And once you have an `AIzaSy...` key in hand, the next questions are bigger: where do I store it, do I need to pay, and what do I do if it leaks?

This guide covers all of that, written from the angle of a solo developer running several services in parallel. I have made most of the management mistakes already on the Dolice Labs sites, so the lessons here come from cleaning those up.

## Issuing Your First Key

The shortest path:

1. Open [Google AI Studio](https://aistudio.google.com/apikey)
2. Sign in with a Google account
3. Click "Create API key"
4. Pick an existing Google Cloud project, or create a new one
5. Copy the key immediately and store it somewhere safe

Two non-obvious points:

**Point 1**: The full key is shown once. After you close that screen, only the prefix is visible. If you forget to copy, you will have to issue a new one. Drop it straight into a password manager or `.env` file before doing anything else.

**Point 2**: Each key is bound to a Google Cloud project, and the binding is permanent. Decide what the key is for before issuing it. Keep test and production keys in *separate* projects — more on that below.

## Free Tier vs. Paid

The Gemini API has a free tier that is generous enough for personal experimentation. The behaviors differ in ways worth knowing up front.

| Aspect | Free Tier | Paid Tier |
|---|---|---|
| Per-minute rate limits | Tight | Configurable per project / model |
| Per-day requests | Capped per model | Effectively much higher |
| Data handling | May be used for training | Not used for training |
| Model availability | Newest models sometimes restricted | Full support |
| Support | Community only | Support tickets available |

For commercial services, the "may be used for training" point alone is enough reason to switch to paid. Linking a Google Cloud billing account flips you over.

## A Separation Pattern That Scales

My rule is **one project, one key**. It feels like overhead at first; it pays back the moment something goes wrong.

```
Recommended key matrix for a solo developer

├── Project A (claudelab.net)
│   ├── Dev key:   AIzaSy...dev1
│   └── Prod key:  AIzaSy...prod1
│
├── Project B (gemilab.net)
│   ├── Dev key:   AIzaSy...dev2
│   └── Prod key:  AIzaSy...prod2
│
└── Project C (sandbox / experiments)
    └── Shared key: AIzaSy...sandbox
```

Three reasons this matters.

First, **blast radius**. If a key accidentally lands in a public repo, only one project is exposed.

Second, **cost attribution**. Once production traffic is real, you want to know exactly how much each site costs. Per-project keys make the Google Cloud billing breakdown match your mental model.

Third, **rate-limit isolation**. A single shared key means a viral spike on one site can starve every other service. Separation prevents that cascade.

## Storage — `.env` or Secret Manager?

Hardcoding keys is non-negotiable. The realistic options:

### Option 1: `.env` Files (small solo projects)

The simplest path.

```bash
# .env — never commit this
GEMINI_API_KEY=YOUR_GEMINI_API_KEY
```

```python
import os
from google import genai

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])
```

Make sure `.gitignore` covers `.env` (I use `.env*` so it catches `.env.local`, `.env.production`, etc.).

### Option 2: Platform Secrets (CI/CD, serverless)

For deployed services, use the platform's secret manager. Cloudflare Workers: `wrangler secret put GEMINI_API_KEY`. GitHub Actions: repo or environment secrets. Read them as environment variables in code.

### Option 3: Google Secret Manager (multi-user / strict access)

When more than one person touches the keys, or when you need access logs and IAM-level control, Google Secret Manager is the right choice.

Start at Option 1 and graduate as the project's needs grow.

## When a Key Leaks

It will happen eventually — pushed to GitHub by mistake, left in a log, shared in a chat. What matters is what you do in the next sixty seconds.

### Three-Step Triage

1. **Disable the key immediately.** Delete it from Google AI Studio or Google Cloud Console. The leaked key stops working instantly.
2. **Issue a replacement.** Within the same project, create a new key and rotate it into your production secrets.
3. **Check usage history.** In Google Cloud Console billing, look for unusual spikes in the hours before you noticed the leak.

If the key was pushed to GitHub, `git revert` is not enough — the value lives forever in history. Tools like BFG Repo-Cleaner can rewrite history, but the key still has to be disabled. "I removed it from history" is not a recovery strategy.

### Preventing Leaks Up Front

GitHub Secret Scanning detects strings that match `AIzaSy...` and other Gemini key patterns automatically. I had this fire once on a Dolice Labs repo, which was sobering. Since then, I make sure every code example in articles uses placeholders, never realistic-looking values.

```python
# ❌ Don't — Secret Scanning will flag this pattern
api_key = "AIzaSyA0B1C2D3E4F5G6H7I8J9K0L1M2N3O4P5"

# ✅ Do — use a placeholder
api_key = "YOUR_GEMINI_API_KEY"
```

## Monitoring Per-Key Usage

Once you have several keys, "how much is each one spending right now?" becomes a real question. Google Cloud Console → APIs and Services → Credentials shows the last 30 days of usage per key.

Once a week I update a small spreadsheet that tracks every key's usage. Anything that has spiked unexpectedly gets debugged immediately — usually it is an infinite loop or a duplicate call somewhere.

## Next Step

If you do not yet have a key, head to [Google AI Studio](https://aistudio.google.com/apikey), issue one, and store it in `.env`. If you already use the API, take five minutes to verify that your dev and prod environments are not sharing the same key. That single check has saved me real money more than once.
