I once had a friend tell me that he woke up one morning to find a bill for hundreds of dollars on his Gemini API account. The cause was an API key he had accidentally committed to a personal GitHub repository, which was then picked up by automated scanning tools. As indie developers, we handle every part of the stack ourselves, so closing the obvious entry points for leaks is one of the kindest things we can do for our future selves.

This article lists five concrete checks for operating Gemini API keys safely in personal projects, with working code and setup steps. None of them require heavy tooling — you should be able to work through the entire list in under 30 minutes.

The goal is not to turn you into a security specialist. It is to make sure that a tired evening, a quick demo push to GitHub, or a forgotten configuration step does not end with an unrecoverable bill or an exposed key. Most of what follows is about getting the defaults right so the risky paths become harder to walk down by accident.

## Why Indie Projects Are Especially Exposed

At larger companies, secret management systems, monitoring pipelines, and billing alerts are usually in place before a single line of application code is written. On a solo project, you have to pick each of those pieces yourself, and it is tempting to skip them when you are focused on shipping features.

Three pitfalls show up most often:

- Pushing a local `.env` file to GitHub without noticing
- Letting the frontend talk directly to the Gemini API, so the key is visible in browser DevTools
- Skipping monthly spend caps and only noticing the problem after a large bill arrives

These are not beginner mistakes — experienced developers hit them any time they cut corners at the end of a tired evening. That is why you want the guardrails baked into your project structure rather than your willpower.

## Check 1 — Lock Down `.gitignore` and Environment Variables

The first check is to make sure your API key is never tracked by Git in the first place. When you create a new project, decide the following three things before your initial commit.

1. Store the key in `.env.local` (or `.env`) and never hardcode it in source files
2. Add `.env*` to your `.gitignore`, with `.env.example` being the only file you commit
3. Always read the key through `process.env.GEMINI_API_KEY`

A minimal setup looks like this and is portable across Next.js, Vite, and plain Node.js projects.

```bash
# .gitignore
.env
.env.local
.env.*.local

# .env.example (safe to commit)
GEMINI_API_KEY=your-api-key-here
```

```ts
// Server-side usage in Node.js or Next.js
import { GoogleGenAI } from "@google/genai";

// Read from env; avoid any literal key in source
const apiKey = process.env.GEMINI_API_KEY;
if (!apiKey) {
  throw new Error("GEMINI_API_KEY is not set");
}

const ai = new GoogleGenAI({ apiKey });
```

Even if the repo is private today, you never know when you might want to open source it or invite a collaborator. It is far easier to keep the key out of history from day one than to scrub it later.

If you do accidentally commit a key, the priority order is: revoke the key first, issue a new one, then add the entry to `.gitignore`. Purging the Git history is secondary — revocation is what actually stops abuse. Automated scanners often pick up exposed keys within minutes, so every second you spend trying to rewrite history is time the leaked key remains active in the wild.

## Check 2 — Do Not Call Gemini Directly From the Browser

A surprisingly common pattern is calling the Gemini API straight from a React or Vue app, especially on personal projects where the "no backend" constraint feels liberating. When you do that, the key ends up embedded in the JavaScript bundle and is visible to anyone who opens DevTools.

You do not need a heavy backend to fix this. A lightweight proxy on Cloudflare Workers, Vercel API Routes, or Firebase Functions is enough to hide the key while keeping the same user experience.

Here is a Vercel API Route example.

```ts
// app/api/generate/route.ts (Next.js App Router)
import { GoogleGenAI } from "@google/genai";
import { NextRequest } from "next/server";

const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY! });

export async function POST(req: NextRequest) {
  const { prompt } = await req.json();

  // Simple input validation goes a long way
  if (typeof prompt !== "string" || prompt.length > 2000) {
    return new Response("Invalid prompt", { status: 400 });
  }

  const result = await ai.models.generateContent({
    model: "gemini-2.5-flash",
    contents: prompt,
  });

  return Response.json({ text: result.text });
}
```

```ts
// Frontend goes through the proxy, not Gemini directly
const res = await fetch("/api/generate", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ prompt: "Hello" }),
});
const { text } = await res.json();
```

This small change keeps your key out of the browser's network tab. It also gives you a natural place to enforce an input length limit and a basic rate limit, so that a malicious user cannot run you up a huge bill by looping requests.

## Check 3 — Set Usage Alerts and Spend Caps From Day One

Even if a key does leak, a preconfigured spend cap keeps the damage bounded. I recommend checking both Google AI Studio and the Google Cloud Console before you push anything to production.

- In Google Cloud Console, open "Billing" → "Budgets & alerts" and set a monthly cap (for example, 10 USD or 50 USD)
- For projects with a high expected load, consider usage caps that hard-stop traffic after the budget is hit
- Include related services like Vertex AI in the same budget

Alerts double as a safety net for your own bugs. Every solo developer has written an infinite loop at some point, and it is much better to hear about it from a budget alert than from a statement at the end of the month.

A reasonable starting point is two thresholds on the same budget: a "soft" alert at 50% of your expected monthly spend, and a "hard" alert at 100%. The soft alert gives you room to investigate and adjust usage before you hit the ceiling, and the hard alert is a clear signal that something unexpected is happening and deserves immediate attention.

## Check 4 — Rotate Keys on a Schedule and Plan for Incidents

Going one step further, I suggest rotating API keys every three months or so. Humans forget, so put the rotation on a calendar or reminder rather than relying on memory.

It also helps to decide, in advance, what you will do the moment you discover a leak. My checklist is roughly this.

1. Delete the exposed key from Google AI Studio immediately (this is the only step that actually stops abuse)
2. Issue a new key and update the environment variables on every deployed environment
3. Review the last 24 hours of usage in the Cloud Console and report suspicious activity to Google if needed
4. Identify the leak path — Git history, client-side bundle, logs — and close it with a structural fix

Keeping the list short is deliberate. When something goes wrong, you want a procedure you can actually follow under stress, not a 20-item document you have to re-read. If you add anything to the list later, add it only after you have practiced the existing steps once or twice.

## In Summary — 30 Minutes, 5 Items, Today

API key security is not glamorous, but it is the foundation of a sustainable indie project. You do not need to be perfect. Running through these five items today will already close most of the realistic risks.

- Is `.env*` in your `.gitignore`?
- Are there any hardcoded API keys left in your source?
- Does the browser ever call the Gemini API directly?
- Do you have a monthly budget alert set up in Google Cloud?
- Have you written down your incident response steps somewhere you can find them?

If any of these answers is "not yet," treat it as a small task for the rest of today. Once the safety net is in place, you can put your attention back on building features with a clearer head.
