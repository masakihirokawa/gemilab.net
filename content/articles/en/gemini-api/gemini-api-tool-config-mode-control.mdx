You register a set of tools with Gemini, ship the agent, and then a user types "thanks, that helped" — and your `search_products` function fires anyway, burning an unnecessary API call. If you have spent any real time with Function Calling in Gemini, you have probably seen this happen. The first time I ran into it, my instinct was to wrap the response in an `if` statement and filter unwanted calls on the client side. That works, but it misses the point: the Gemini API already exposes a cleaner way to control this on the model side.

That mechanism is `tool_config`. The three modes — `AUTO`, `ANY`, and `NONE` — let you switch between the "autonomous agent" feel you usually want and the "strict structured extraction" behavior you sometimes need, without swapping models or rewriting prompts. It is a short configuration block, and yet it is one of the most under-used features in the Gemini API.

This article walks through what each mode actually does, where they shine, and a few practical habits I have adopted to keep function calling predictable in production code.

## tool_config is a switch for "who decides when to call a function"

By default, Gemini decides for itself. If the user's input looks like it needs a tool, the model returns a Function Call; otherwise, it replies in natural language. The field `tool_config.function_calling_config.mode` flips who gets to make that decision.

- **AUTO**: The model decides. This is the default and the right choice for general-purpose agents.
- **ANY**: The model must call one of the provided functions. Free-form text replies are disabled. Ideal when you want guaranteed structured output.
- **NONE**: The model is forbidden from calling any tool. Useful for phases of a session where you want to keep the conversation strictly conversational.

If you want the model to feel like a thoughtful collaborator, you pick AUTO. If you want it to behave like a JSON extraction service, you pick ANY. If you want it to listen without reaching for tools — think onboarding questions or clarifications — you pick NONE. Thinking of the three modes as "delegate, force, forbid" has helped me keep the choice intuitive across different parts of the same product.

## The "it called my function for no reason" problem in AUTO

The most common complaint I hear about AUTO is exactly the scenario above: users type polite acknowledgments, and the agent decides to reach for a tool. The root cause is usually that Gemini has been trained to err on the side of being helpful, and it treats nearly every turn as a potential opportunity to use a tool.

The fix is not to abandon AUTO. The fix is to tell the model, in the `system_instruction`, when a tool *should* be used. Reserve `tool_config` for the final safety net. I have watched teams write 200 lines of post-processing code to filter unwanted Function Calls when a three-sentence instruction would have prevented them in the first place.

```python
# Requires: google-genai>=0.6.0, Python 3.10+
# pip install google-genai
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_GEMINI_API_KEY")

search_products = types.FunctionDeclaration(
    name="search_products",
    description="Search the e-commerce catalog by keyword.",
    parameters=types.Schema(
        type="OBJECT",
        properties={"query": types.Schema(type="STRING")},
        required=["query"],
    ),
)
tools = [types.Tool(function_declarations=[search_products])]

config_auto = types.GenerateContentConfig(
    tools=tools,
    tool_config=types.ToolConfig(
        function_calling_config=types.FunctionCallingConfig(mode="AUTO"),
    ),
    system_instruction=(
        "You are a shopping assistant. Call search_products only when the user "
        "clearly wants to find products. Respond in natural language for greetings, "
        "thanks, and small talk."
    ),
)

resp = client.models.generate_content(
    model="gemini-2.5-flash",
    contents="Thanks, that was really helpful\!",
    config=config_auto,
)
# Expected: no function_call in the response — just a short natural reply.
print(resp.candidates[0].content.parts[0])
```

Pairing a specific `system_instruction` with `mode="AUTO"` is the baseline I reach for in any production agent. The `tool_config` setting alone will not save you from vague instructions, but vague instructions by themselves will not save you from unwanted calls either. They have to work together.

## ANY mode: using Gemini as a structured extractor

ANY mode becomes a lot more interesting when you stop thinking of it as "force the model to call something" and start thinking of it as "use the function signature as a return type." Because a function call in ANY mode is guaranteed, you effectively get Gemini to emit typed output that matches your declaration. I often prefer this over `responseSchema` + JSON parsing because the Python side lines up cleanly with dataclasses or TypedDicts, and the failure modes are easier to reason about when something goes wrong.

```python
extract_todos = types.FunctionDeclaration(
    name="extract_todos",
    description="Extract a list of action items from meeting notes.",
    parameters=types.Schema(
        type="OBJECT",
        properties={
            "todos": types.Schema(
                type="ARRAY",
                items=types.Schema(
                    type="OBJECT",
                    properties={
                        "task": types.Schema(type="STRING"),
                        "owner": types.Schema(type="STRING"),
                        "due": types.Schema(type="STRING", description="YYYY-MM-DD"),
                    },
                    required=["task", "owner"],
                ),
            )
        },
        required=["todos"],
    ),
)

config_any = types.GenerateContentConfig(
    tools=[types.Tool(function_declarations=[extract_todos])],
    tool_config=types.ToolConfig(
        function_calling_config=types.FunctionCallingConfig(mode="ANY"),
    ),
)

resp = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=(
        "Extract action items from the following meeting notes:\n"
        "- Yamada: submit quote by Friday\n"
        "- Sato: review API spec, due next Monday\n"
    ),
    config=config_any,
)

fc = resp.candidates[0].content.parts[0].function_call
# Expected: fc.name == "extract_todos"
#           fc.args["todos"] contains two structured items.
print(fc.args)
```

Because the model cannot fall back to "I'll just answer in prose," you stop getting surprise refusals on edge cases where the input is short, messy, or written in a non-canonical format. I have shipped extraction pipelines that used to require a validator-retry loop around `responseSchema` and replaced them with a single ANY-mode call — the overall error rate dropped and the code that consumes the result became trivial.

## Shrinking the candidate set with allowed_function_names

ANY guarantees *a* function call, but if you have registered several tools, the model still picks which one. In a shopping agent with both `search_products` and `add_to_cart`, there is a clear phase — before the user has chosen an item — where calling `add_to_cart` would be nonsensical. That is where `allowed_function_names` earns its keep.

```python
config_any_restricted = types.GenerateContentConfig(
    tools=[types.Tool(function_declarations=[search_products, add_to_cart])],
    tool_config=types.ToolConfig(
        function_calling_config=types.FunctionCallingConfig(
            mode="ANY",
            allowed_function_names=["search_products"],
        ),
    ),
)
# add_to_cart is removed from consideration for this phase of the conversation.
```

`allowed_function_names` also works with AUTO, which is a nice way to keep a large tool registry and still hand the model a subset that is appropriate for the current step. It makes incremental rollouts of new tools much safer: you declare them, but only expose them when the state machine says it is time. In practice, I keep a small "tool phase" enum in the agent's state and map each phase to an `allowed_function_names` list. When something goes wrong in production, the root cause is usually an agent that transitioned into the wrong phase — not the model picking a bad tool.

## A short checklist before you ship

`tool_config` is powerful, but it is one layer in a larger design. Before I treat an agent as ready, I run through a few questions:

- **Is the division of labor between `system_instruction` and `tool_config` clear?** Use natural language to describe *when* a tool should be used, and reserve `tool_config` for the hard constraint. It also holds up better when prompts evolve. I went deeper on this in [the Gemini system_instruction design showcase](/articles/gemini-api/gemini-api-system-instruction-prompt-engineering-showcase).
- **Do you switch modes by phase?** A realistic pattern is AUTO while gathering intent, then ANY once enough context is available to extract structured data.
- **Do you handle the "no call" case?** In AUTO, the model can legitimately decide not to call anything. Loop over `parts` and check for `function_call` every turn — this single habit wipes out a surprising amount of defensive code. If you hit mysterious failures, [my troubleshooting notes on Function Calling not firing](/articles/gemini-api/gemini-function-calling-not-working-troubleshooting) may help.
- **Have you validated streaming?** Function calls usually arrive at the tail of a stream; rendering tokens optimistically will make your UI flicker. See [streaming + function calling implementation tips](/articles/gemini-api/gemini-api-streaming-function-calling-guide) for patterns I use.
- **Do you have a "no-op tool" for NONE transitions?** If you flip to NONE in one phase and back to AUTO in another, make sure the conversation history is consistent — leftover tool-call partials from an earlier phase can confuse the model once calling is re-enabled.

If you want to keep leveling up the broader intuition, [Prompt Engineering for LLMs by Louis-François Bouchard](https://www.amazon.co.jp/dp/4814400950/?tag=pinocchio-22) is a book I keep nearby — it frames when to delegate to the model and when to impose rules, which is exactly the mindset `tool_config` asks of you.

## What to try next

Find one place in your existing AUTO agent where you absolutely need structured output — meeting notes to action items, support tickets to categories, free-form user bios to a profile schema — and rewrite just that step as ANY mode with a single function. You will notice two things immediately: debugging bad outputs gets much easier, and your non-AI teammates will be able to reason about that step because the "return type" now lives in a function signature. Once that feels natural, introduce `allowed_function_names` to tighten the loop as your agent's state machine grows, and you will find that the places where you used to write defensive post-processing become unnecessary one by one.
