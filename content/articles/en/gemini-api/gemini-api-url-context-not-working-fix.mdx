You paste a URL into the prompt, and the answer comes back as the kind of generic summary you could have written without the page. No exception in the logs. HTTP 200. A perfectly fluent response — that simply never mentions what the article actually says.

When I first hit this, I spent the evening rewording the prompt. It didn't help. The problem was never the wording: either the tool hadn't run, or it had run and the fetch had failed.

**Check the fact of retrieval before you judge the quality of the answer.** That's the line I work from now.

The official URL Context documentation is the primary source for setup. This guide covers what to check, in what order, when it doesn't work — starting with the documented limits.

## Start with the documented limits

Before triaging anything, rule out what the tool is simply not designed to read. The official documentation lists the following (as I confirmed at the time of writing; model lists and numbers can change).

<tr><td>URLs per request</td><td>Up to 20</td></tr>

This table settles about half of all cases. If you were passing a <code>localhost</code> URL during development, or pointing the tool at a page behind login, no code change will help. **What sits outside the spec has to be brought inside it.**

## Three checks to run first

Run them in order.

**1. Is the tool declared correctly?**

The declaration syntax depends on your SDK version. The official docs currently show <code>tools=[{"type": "url_context"}]</code> for the Interactions API. If you're still on <code>generate_content</code>, make sure your form matches the documentation for your SDK. If you mix in Function Calling, also check that the tools array hasn't been malformed so that URL Context is quietly ignored.

**2. Are the URLs plain text in the prompt?**

URL Context picks up URLs that appear in the prompt body. Wrapping them in custom tags or JSON-encoding them can defeat detection. Write `https://example.com/article` as-is.

**3. Are you logging retrieval metadata on every call?**

Before doubting answer quality, look at which URLs were actually fetched and with what status. An empty result means the tool didn't run, or no URL was detected.

```python
from google import genai
from google.genai import types

client = genai.Client()

response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="Summarize the three key points of: https://ai.google.dev/gemini-api/docs/url-context",
    config=types.GenerateContentConfig(
        tools=[types.Tool(url_context=types.UrlContext())],
    ),
)

# Inspect metadata first (field names can differ by SDK version)
meta = response.candidates[0].url_context_metadata
if meta is None or not meta.url_metadata:
    print("Metadata is empty: the tool did not run")
else:
    for entry in meta.url_metadata:
        print(entry.retrieved_url, entry.url_retrieval_status)
print("---")
print(response.text)
```

On success, each URL shows <code>URL_RETRIEVAL_STATUS_SUCCESS</code>. Anything like <code>_ERROR</code> points to the site-side causes below.

The metadata can come back as <code>None</code>, so check for emptiness first, as above — otherwise you get an <code>AttributeError</code> exactly when you need a clear signal.

## Symptom-by-symptom triage

**Symptom A: The answer ignores the page and stays generic**

If the metadata is empty, the tool never ran. In order of suspicion:

- The instruction is weak ("use this as reference") and the model didn't see a need to fetch
- The URL is a shortener (bit.ly and similar) that wasn't expanded
- A <code>system_instruction</code> tells the model not to use external resources

Making the instruction explicit — "Fetch the following URL before answering" — can change behavior. Expand shorteners yourself rather than relying on the model.

**Symptom B: The URL appears in metadata, but the status is an error**

The URL was detected but the fetch failed.

- The site's <code>robots.txt</code> refuses crawlers
- The page requires authentication (logged-in screens, internal wikis)
- A WAF treats the request as bot traffic
- A JavaScript-rendered page whose initial HTML is nearly empty

Internal tools and restricted pages are out of scope by design, as the table shows. Export the content to a public page, or pass it as a file through the Files API.

**Symptom C: Timeouts or very slow responses**

The documented ceiling is 20 URLs per request, but that doesn't mean you should fill it. The more URLs, the likelier one slow fetch drags the whole call, and the more input tokens you pay for. I confirm success with a few URLs first, then widen, and split larger jobs across requests. As an indie developer running my own apps, I apply the same rule when I have it summarize store policies or SDK release notes. The right number depends on the sites you read, so measure your own from the logs.

For handling the timeout itself, see [Fixing Gemini API DEADLINE_EXCEEDED errors](/articles/gemini-api/gemini-api-deadline-exceeded-error-fix-guide).

## Sites that consistently fail

Even when the spec says "should work," some domains reliably fail once you run this in production.

- **Major news sites**: Some answer crawlers with 401/403 by policy. RSS feeds or partner APIs are the proper route
- **X and LinkedIn timelines**: Login-required, so no
- **Public pages that render with JavaScript**: The URL is public but the body may not be in the initial HTML
- **Paywalled articles**: Unsupported by the spec

For JS-rendered pages, render with your own headless browser, save the HTML, and pass it through the Files API.

## Sometimes URL Context is the wrong tool

Before forcing something to work, ask whether it fits the task.

- Fetching the same URL on every call: a cache layer of your own is faster and cheaper in input tokens
- Information whose automated retrieval is restricted legally or by terms: don't use it
- Structured extraction: design it together with <code>responseSchema</code> or similar from the start
- Search-driven research: Grounding fits better, and the two can sit in the same <code>tools</code> list

For a worked Grounding setup, see [Grounding with structured output for real-time data extraction](/articles/gemini-api/gemini-api-grounding-structured-output-realtime-data-extraction).

## A defensive wrapper for production

```python
def fetch_with_url_context(client, model, prompt: str, urls: list[str]) -> dict:
    """Summarize with URL Context and return per-URL fetch results."""
    full_prompt = f"{prompt}\n\nReference URLs:\n" + "\n".join(urls)

    resp = client.models.generate_content(
        model=model,
        contents=full_prompt,
        config=types.GenerateContentConfig(
            tools=[types.Tool(url_context=types.UrlContext())],
            temperature=0.2,
        ),
    )

    meta = resp.candidates[0].url_context_metadata
    entries = meta.url_metadata if meta and meta.url_metadata else []
    fetched = [
        {"url": m.retrieved_url, "status": str(m.url_retrieval_status)}
        for m in entries
    ]
    failed = [f for f in fetched if "SUCCESS" not in f["status"]]
    # URLs you asked for that never appear in the results count as failures too
    seen = {f["url"] for f in fetched}
    missing = [u for u in urls if u not in seen]
    return {"text": resp.text, "fetched": fetched, "failed": failed, "missing": missing}
```

The key is <code>missing</code>. Pass five URLs, get results for three, and watching only <code>failed</code> will miss it. Return what was and wasn't retrieved to the caller, so the UI can say "this source couldn't be retrieved and was skipped." **A silent two-out-of-five failure is the scariest mode this tool has.**

## Habits for observability

URL Context problems rarely show up in development. They surface once traffic grows.

First, log the retrieval status as a structured field rather than inside free text. One dashboard panel with the per-domain error rate makes regressions visible early.

Second, restrict target domains with an allowlist. User input can otherwise carry unexpected URLs into the tool. Keep it to your own docs and trusted references.

Third, alert on "URLs were provided but the metadata has zero entries." That isn't a soft error — it's the tool not running.

## Checklist

Go top to bottom and fix the first item that fails.

- You log the retrieval metadata on every call
- The tool declaration matches your SDK's documented form
- URLs are plain text in the prompt (no tags, no JSON encoding)
- No URL shorteners
- No <code>localhost</code>, internal-network or login-required pages
- No paywalled content, YouTube, Workspace files, or video/audio
- No <code>system_instruction</code> forbidding external references
- The page isn't JavaScript-only rendered
- Per-URL status, plus URLs missing from the results, go back to the caller

Don't touch the prompt or switch models until all nine pass.

## Your next step

One thing you can do today: add a log line to your existing call that fires when the metadata is empty. What it shows will explain about half the problem.

Once things are stable, you can take URL Context further — for example [pulling only the deprecation notices for models you use from an official changelog](/articles/gemini-api/gemini-url-context-deprecation-radar-changelog-grounded-impact-diff). Clearing "it doesn't work" one cause at a time becomes the groundwork for everything built on top.
