If you've built an app and wanted to show users more relevant content, you've probably put off building a recommendation system because it seemed to require machine learning expertise. The good news: with Gemini Embedding API, you don't need to train any models.

The Embedding API converts text into vectors — numeric representations of meaning. Content that's semantically similar ends up with vectors pointing in similar directions. Build a user profile from the vectors of content they've viewed, compare it against your full catalog, and you have a working recommender.

From hands-on experience building wallpaper and audio apps, just a few vectorized viewing events are enough to produce recommendations that feel meaningfully personalized.

## System Design: How Content-Based Filtering Works with Gemini Embedding

There are three main recommendation approaches. **Collaborative filtering** recommends what similar users liked — powerful but suffers from cold-start problems when you have few users. **Content-based filtering** recommends content similar to what a user has already engaged with — this is what we'll build. **Hybrid approaches** combine both.

Content-based filtering with Gemini Embedding works like this:

```
[User behavior log]
  ↓  list of viewed content IDs
[Gemini Embedding API]
  ↓  vectorize each content item (768 dimensions)
[User profile vector]
  ↓  average of all viewed content embeddings
[Cosine similarity]
  ↓  compare profile against full catalog in one matrix operation
[Recommendations]
  ↓  return top-N results
```

A key advantage: recommendations begin after a user's very first action. New users aren't left in a cold-start void — you just fall back to popular content until a profile forms.

```python
# embedder.py
from google import genai
from google.genai.types import EmbedContentConfig
import numpy as np
import time
from config import GEMINI_API_KEY, EMBEDDING_MODEL

client = genai.Client(api_key=GEMINI_API_KEY)

def embed_text(text: str, task_type: str = "RETRIEVAL_DOCUMENT") -> list[float]:
    """
    Convert text to an embedding vector.

    task_type matters for recommendation quality — always specify it:
      - RETRIEVAL_DOCUMENT: content being indexed (catalog side)
      - RETRIEVAL_QUERY: user profile or search query (query side)
      - SEMANTIC_SIMILARITY: symmetric similarity comparisons
    """
    try:
        response = client.models.embed_content(
            model=EMBEDDING_MODEL,
            contents=text,
            config=EmbedContentConfig(task_type=task_type)
        )
        return response.embeddings[0].values
    except Exception as e:
        if "429" in str(e) or "RESOURCE_EXHAUSTED" in str(e):
            print("Rate limited — retrying after 5s")
            time.sleep(5)
            return embed_text(text, task_type)
        raise

def embed_texts_batch(texts: list[str], task_type: str = "RETRIEVAL_DOCUMENT") -> list[list[float]]:
    """
    Embed multiple texts in batches.
    Gemini Embedding API supports up to 100 items per request.
    """
    embeddings = []
    BATCH_SIZE = 100

    for i in range(0, len(texts), BATCH_SIZE):
        batch = texts[i:i + BATCH_SIZE]
        try:
            response = client.models.embed_content(
                model=EMBEDDING_MODEL,
                contents=batch,
                config=EmbedContentConfig(task_type=task_type)
            )
            embeddings.extend([e.values for e in response.embeddings])
        except Exception as e:
            if "429" in str(e) or "RESOURCE_EXHAUSTED" in str(e):
                print("Rate limit on batch — waiting 10s, falling back to single")
                time.sleep(10)
                for text in batch:
                    embeddings.append(embed_text(text, task_type))
            else:
                raise

    return embeddings
```

Skipping `task_type` is the single most common mistake in embedding-based systems. Omitting it can reduce recommendation relevance by 20–30% with no obvious error — it's a silent quality issue.

## Indexing Your Content Catalog

```python
# content_indexer.py
import sqlite3
import numpy as np
from embedder import embed_texts_batch

def init_db(db_path: str = "recommendations.db") -> sqlite3.Connection:
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()
    cur.executescript("""
        CREATE TABLE IF NOT EXISTS content_embeddings (
            id TEXT PRIMARY KEY,
            title TEXT NOT NULL,
            text_for_embedding TEXT NOT NULL,
            embedding BLOB NOT NULL,
            category TEXT DEFAULT '',
            created_at TEXT DEFAULT CURRENT_TIMESTAMP
        );
        CREATE TABLE IF NOT EXISTS user_profiles (
            user_id TEXT PRIMARY KEY,
            profile_embedding BLOB NOT NULL,
            viewed_content_ids TEXT NOT NULL,
            updated_at TEXT DEFAULT CURRENT_TIMESTAMP
        );
        CREATE TABLE IF NOT EXISTS embedding_cache (
            text_hash TEXT PRIMARY KEY,
            embedding BLOB NOT NULL,
            created_at TEXT DEFAULT CURRENT_TIMESTAMP
        );
    """)
    conn.commit()
    return conn

def index_contents(contents: list[dict], db_path: str = "recommendations.db"):
    """
    Vectorize and store content items (incremental — skips existing IDs).

    contents: [{"id": "slug", "title": "...", "description": "...", "category": "..."}]
    """
    conn = init_db(db_path)
    cur = conn.cursor()

    existing_ids = {row[0] for row in cur.execute(
        "SELECT id FROM content_embeddings"
    ).fetchall()}
    new_contents = [c for c in contents if c["id"] not in existing_ids]

    if not new_contents:
        print(f"No new content ({len(existing_ids)} items already indexed)")
        conn.close()
        return

    print(f"Vectorizing {len(new_contents)} new items...")

    texts = [
        f"{c['title']}\n{c.get('description', '')}"
        for c in new_contents
    ]
    embeddings = embed_texts_batch(texts, task_type="RETRIEVAL_DOCUMENT")

    for content, emb, text in zip(new_contents, embeddings, texts):
        cur.execute("""
            INSERT OR REPLACE INTO content_embeddings
            (id, title, text_for_embedding, embedding, category)
            VALUES (?, ?, ?, ?, ?)
        """, (
            content["id"], content["title"], text,
            np.array(emb, dtype=np.float32).tobytes(),
            content.get("category", "")
        ))

    conn.commit()
    conn.close()
    print(f"✅ Indexed {len(new_contents)} items")
```

SQLite works well up to around 100K content items for solo or small-team apps. If you're storing ~$0 extra infrastructure cost is a real advantage at this scale.

## Dynamic User Profile Updates

```python
# user_profiler.py
import json
import sqlite3
import numpy as np
from datetime import datetime

def update_user_profile(
    user_id: str,
    viewed_content_id: str,
    db_path: str = "recommendations.db",
    max_history: int = 50
):
    """
    Update a user's profile when they view content.

    max_history caps how many recent views influence the profile.
    Without this cap, a user's tastes from years ago dominate forever.
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    row = cur.execute(
        "SELECT embedding FROM content_embeddings WHERE id = ?",
        (viewed_content_id,)
    ).fetchone()

    if not row:
        print(f"Content '{viewed_content_id}' not indexed — skipping")
        conn.close()
        return

    profile_row = cur.execute(
        "SELECT viewed_content_ids FROM user_profiles WHERE user_id = ?",
        (user_id,)
    ).fetchone()

    viewed_ids = json.loads(profile_row[0]) if profile_row else []

    if viewed_content_id not in viewed_ids:
        viewed_ids.append(viewed_content_id)
    if len(viewed_ids) > max_history:
        viewed_ids = viewed_ids[-max_history:]

    # Recompute profile as the mean of all viewed content embeddings
    embeddings_to_average = []
    for cid in viewed_ids:
        r = cur.execute(
            "SELECT embedding FROM content_embeddings WHERE id = ?", (cid,)
        ).fetchone()
        if r:
            embeddings_to_average.append(np.frombuffer(r[0], dtype=np.float32))

    if embeddings_to_average:
        new_profile = np.mean(embeddings_to_average, axis=0)

        # L2-normalize so dot product == cosine similarity at retrieval time
        norm = np.linalg.norm(new_profile)
        if norm > 0:
            new_profile = new_profile / norm

        cur.execute("""
            INSERT OR REPLACE INTO user_profiles
            (user_id, profile_embedding, viewed_content_ids, updated_at)
            VALUES (?, ?, ?, ?)
        """, (
            user_id,
            new_profile.tobytes(),
            json.dumps(viewed_ids),
            datetime.now().isoformat()
        ))

    conn.commit()
    conn.close()
```

L2-normalization at write time means retrieval is just a dot product — no division needed at query time. This roughly triples retrieval speed and simplifies the math.

## Recommendation Engine and FastAPI Endpoint

```python
# recommender.py
import sqlite3
import numpy as np
import json
from dataclasses import dataclass

@dataclass
class RecommendedContent:
    id: str
    title: str
    category: str
    similarity: float

def get_recommendations(
    user_id: str,
    n: int = 10,
    exclude_viewed: bool = True,
    category_filter: str | None = None,
    db_path: str = "recommendations.db"
) -> list[RecommendedContent]:
    """
    Return top-N recommendations for a user.
    Returns empty list if no profile exists — caller handles fallback.
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    profile_row = cur.execute(
        "SELECT profile_embedding, viewed_content_ids FROM user_profiles WHERE user_id = ?",
        (user_id,)
    ).fetchone()

    if not profile_row:
        conn.close()
        return []

    user_profile = np.frombuffer(profile_row[0], dtype=np.float32)
    viewed_ids = set(json.loads(profile_row[1])) if exclude_viewed else set()

    query = "SELECT id, title, category, embedding FROM content_embeddings"
    params: list = []
    if category_filter:
        query += " WHERE category = ?"
        params.append(category_filter)

    rows = cur.execute(query, params).fetchall()
    conn.close()

    ids, titles, categories, emb_list = [], [], [], []
    for cid, title, cat, emb_bytes in rows:
        if cid in viewed_ids:
            continue
        ids.append(cid)
        titles.append(title)
        categories.append(cat)
        emb_list.append(np.frombuffer(emb_bytes, dtype=np.float32))

    if not emb_list:
        return []

    # Matrix dot product — handles 100K items in <100ms on a single core
    matrix = np.array(emb_list)          # (N, 768)
    similarities = matrix @ user_profile  # (N,)

    top_indices = np.argsort(similarities)[::-1][:n]

    return [
        RecommendedContent(
            id=ids[i], title=titles[i],
            category=categories[i], similarity=float(similarities[i])
        )
        for i in top_indices
    ]
```

## Common Mistakes and How to Avoid Them

**1. Omitting task_type**

This is the most common mistake — and the hardest to detect because there's no error. The Embedding API generates differently-oriented vectors depending on task_type. Indexing with `RETRIEVAL_DOCUMENT` and querying with `RETRIEVAL_QUERY` is correct. Using the same task_type for both, or omitting it entirely, silently degrades recommendation quality. Fixing it requires re-vectorizing your entire catalog.

**2. Unbounded viewing history**

Without `max_history`, a user's interests from two years ago dominate their profile forever. Cap it at 50–100 recent items. Recent views should carry more weight than distant ones.

**3. Popular content monopolizing recommendations**

If the same popular articles appear in every user's feed, the recommendation system loses its value. Add category diversity logic: if a category already has 3 items in the top results, penalize additional items from the same category.

**4. New content never surfacing**

Newly published content has zero views, so it never appears in recommendations organically. Add an "exploration bonus" — boost items published within the last 7 days by +0.05 in score. This creates a natural mix of fresh and proven content.

**5. SQLite write conflicts under concurrent load**

Multiple simultaneous requests writing to `user_profiles` will hit lock timeouts with default SQLite settings. Always specify `timeout=10` in `sqlite3.connect()`, or migrate to PostgreSQL + pgvector when traffic grows.

## Cost Optimization with Embedding Cache

At $0.00002 per 1K tokens, costs are low — but caching makes them even lower.

```python
# embedding_cache.py
import hashlib
import sqlite3
import numpy as np
from google import genai
from google.genai.types import EmbedContentConfig
from config import GEMINI_API_KEY, EMBEDDING_MODEL

client = genai.Client(api_key=GEMINI_API_KEY)

def get_cached_or_embed(
    text: str,
    task_type: str = "RETRIEVAL_DOCUMENT",
    db_path: str = "recommendations.db"
) -> list[float]:
    """
    Return cached embedding if available, otherwise call the API.
    Cache key includes task_type to prevent cross-contamination.
    """
    text_hash = hashlib.sha256(f"{task_type}:{text}".encode()).hexdigest()

    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    row = cur.execute(
        "SELECT embedding FROM embedding_cache WHERE text_hash = ?",
        (text_hash,)
    ).fetchone()

    if row:
        conn.close()
        return list(np.frombuffer(row[0], dtype=np.float32))

    response = client.models.embed_content(
        model=EMBEDDING_MODEL,
        contents=text,
        config=EmbedContentConfig(task_type=task_type)
    )
    embedding = response.embeddings[0].values

    cur.execute(
        "INSERT OR IGNORE INTO embedding_cache (text_hash, embedding) VALUES (?, ?)",
        (text_hash, np.array(embedding, dtype=np.float32).tobytes())
    )
    conn.commit()
    conn.close()

    return embedding
```

For a 100-article catalog with unchanged titles and descriptions, the total initial indexing cost is under $0.01. Profile updates read from the DB — no additional API calls needed.

Your embedding vectors migrate cleanly between phases as long as you keep the model and task_type consistent.

## Integrating the Recommendation API into a Mobile App

For mobile apps, the recommendation flow typically looks like this: log view events whenever a user opens a content item, and fetch recommendations for the home feed or a "More like this" section. Here's a minimal Swift example using URLSession.

```swift
// RecommendationService.swift
import Foundation

struct RecommendedItem: Decodable {
    let id: String
    let title: String
    let category: String
    let score: Double
}

struct RecommendationResponse: Decodable {
    let userId: String
    let recommendations: [RecommendedItem]
    let fallback: Bool
    
    enum CodingKeys: String, CodingKey {
        case userId = "user_id"
        case recommendations
        case fallback
    }
}

class RecommendationService {
    private let baseURL = "https://your-api.example.com"
    private let userId: String
    
    init(userId: String) {
        self.userId = userId
    }
    
    /// Log a view event — fire-and-forget, no need to await
    func logView(contentId: String) {
        guard let url = URL(string: "\(baseURL)/events/view") else { return }
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        
        let body = ["user_id": userId, "content_id": contentId]
        request.httpBody = try? JSONEncoder().encode(body)
        
        // Detach from main thread — we don't care about the response
        URLSession.shared.dataTask(with: request).resume()
    }
    
    /// Fetch personalized recommendations
    func fetchRecommendations(
        n: Int = 10,
        category: String? = nil,
        completion: @escaping ([RecommendedItem]) -> Void
    ) {
        guard let url = URL(string: "\(baseURL)/recommendations") else {
            completion([])
            return
        }
        
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        
        var body: [String: Any] = ["user_id": userId, "n": n]
        if let category { body["category"] = category }
        request.httpBody = try? JSONSerialization.data(withJSONObject: body)
        
        URLSession.shared.dataTask(with: request) { data, _, error in
            guard let data, error == nil,
                  let response = try? JSONDecoder().decode(RecommendationResponse.self, from: data)
            else {
                DispatchQueue.main.async { completion([]) }
                return
            }
            DispatchQueue.main.async { completion(response.recommendations) }
        }.resume()
    }
}
```

Call `logView` every time a user opens content, and `fetchRecommendations` when loading a "For You" section. View logging is fire-and-forget — no need to wait for a response before rendering the UI.

## Adding Diversity to Recommendations

Pure cosine-similarity recommendations tend to converge on whatever the user viewed most recently. If someone reads five articles about Python, their next ten recommendations will all be Python-related. This narrows the experience.

Two practical approaches to inject diversity:

**Category interleaving** — enforce that no single category occupies more than a certain percentage of the top-N results:

```python
# diversity.py
from recommender import RecommendedContent
from collections import defaultdict

def apply_category_diversity(
    recommendations: list[RecommendedContent],
    max_per_category: int = 3,
    total: int = 10
) -> list[RecommendedContent]:
    """
    Cap how many items from the same category appear in the final list.
    Items are still sorted by similarity within their category slot.
    """
    category_counts: dict[str, int] = defaultdict(int)
    diversified = []

    for item in recommendations:
        if category_counts[item.category] < max_per_category:
            diversified.append(item)
            category_counts[item.category] += 1
        if len(diversified) >= total:
            break

    return diversified
```

**Recency boost** — surface newly published content even if it hasn't been viewed much yet:

```python
# recency_boost.py
from datetime import datetime, timezone
from recommender import RecommendedContent
import sqlite3

def apply_recency_boost(
    recommendations: list[RecommendedContent],
    db_path: str = "recommendations.db",
    boost_days: int = 7,
    boost_amount: float = 0.05
) -> list[RecommendedContent]:
    """
    Add a score boost to content published within the last `boost_days` days.
    Encourages new content to surface before it accumulates viewing history.
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    boosted = []
    now = datetime.now(timezone.utc)

    for item in recommendations:
        row = cur.execute(
            "SELECT created_at FROM content_embeddings WHERE id = ?",
            (item.id,)
        ).fetchone()

        score = item.similarity
        if row and row[0]:
            try:
                created = datetime.fromisoformat(row[0]).replace(tzinfo=timezone.utc)
                age_days = (now - created).days
                if age_days <= boost_days:
                    score += boost_amount * (1 - age_days / boost_days)
            except ValueError:
                pass  # Malformed date — skip boost

        boosted.append(RecommendedContent(
            id=item.id, title=item.title,
            category=item.category, similarity=score
        ))

    # Re-sort after boost adjustments
    boosted.sort(key=lambda x: x.similarity, reverse=True)
    conn.close()
    return boosted
```

In production, combine both: apply recency boost first, then category diversity. The order matters — boosted items may jump categories.

## Monitoring Recommendation Quality in Production

Cosine similarity scores tell you if recommendations are technically working, but not if they're actually useful. Add basic engagement tracking:

```python
# engagement_tracker.py
import sqlite3
from datetime import datetime

def record_recommendation_click(
    user_id: str,
    recommended_content_id: str,
    position: int,  # 0-indexed position in recommendation list
    db_path: str = "recommendations.db"
):
    """
    Track when a user clicks a recommended item.
    Use this data to compute CTR by position and tune max_history / boost parameters.
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    cur.execute("""
        CREATE TABLE IF NOT EXISTS recommendation_clicks (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            user_id TEXT NOT NULL,
            content_id TEXT NOT NULL,
            position INTEGER NOT NULL,
            clicked_at TEXT DEFAULT CURRENT_TIMESTAMP
        )
    """)
    cur.execute("""
        INSERT INTO recommendation_clicks (user_id, content_id, position)
        VALUES (?, ?, ?)
    """, (user_id, recommended_content_id, position))

    conn.commit()
    conn.close()

def get_ctr_by_position(db_path: str = "recommendations.db") -> dict[int, float]:
    """
    Compute click-through rate by list position.
    Healthy recommendation systems typically see CTR drop off sharply after position 3.
    """
    conn = sqlite3.connect(db_path, timeout=10)
    cur = conn.cursor()

    # This assumes you also log impressions separately
    # Simplified: just return click counts by position as a proxy
    rows = cur.execute("""
        SELECT position, COUNT(*) as clicks
        FROM recommendation_clicks
        GROUP BY position
        ORDER BY position
    """).fetchall()
    conn.close()

    return {row[0]: row[1] for row in rows}
```

Two metrics to watch weekly: the ratio of recommended clicks to total clicks (should rise as the system learns), and whether position-0 CTR is meaningfully higher than position-5 (if not, your ranking logic may need tuning).

## When to Move Beyond Embedding-Based Recommendations

This system works well for content-based recommendations with a moderate catalog. You'll want to consider additional approaches when:

- **Users complain the recommendations feel repetitive** — this is a sign you need stronger diversity logic or collaborative filtering layered on top.
- **A large fraction of your catalog never surfaces** — consider a dedicated "discovery" section that surfaces items outside the user's current profile, generated by a random walk over the catalog graph.
- **You need real-time reaction to trending content** — embedding-based profiles lag behind sudden interest spikes. Consider a hybrid where 70% of the feed comes from profile-based recommendations and 30% from a trending signal.

The good news is this architecture is designed for incremental improvement. You can add collaborative filtering, trending signals, or A/B testing without rebuilding the embedding layer.

For further reading on Gemini Embedding patterns, the [Gemini Embedding API fundamentals guide](/en/articles/gemini-api/embeddings-api-guide) covers additional use cases including semantic deduplication and clustering.

## Handling Edge Cases in Production

A few edge cases will catch you off-guard if you don't plan for them.

**User clears their history or opts out of personalization.** You need a way to delete a user's profile. Keep this simple:

```python
def delete_user_profile(user_id: str, db_path: str = "recommendations.db"):
    """Remove a user's profile — call this when they request data deletion."""
    conn = sqlite3.connect(db_path, timeout=10)
    conn.execute("DELETE FROM user_profiles WHERE user_id = ?", (user_id,))
    conn.commit()
    conn.close()
```

This satisfies GDPR/privacy requirements for user data deletion. The embedding cache is keyed by content text, not user data, so it doesn't need to be cleared.

**Content gets deleted or updated.** When an article is removed, its embedding stays in the database and can still appear in recommendations. Add a soft-delete column or run a nightly cleanup:

```python
def remove_content(content_id: str, db_path: str = "recommendations.db"):
    """
    Remove a content item from the index.
    Existing user profiles are not affected — the removed item will simply
    not appear in future recommendations since it's no longer in the catalog.
    """
    conn = sqlite3.connect(db_path, timeout=10)
    conn.execute(
        "DELETE FROM content_embeddings WHERE id = ?", (content_id,)
    )
    conn.commit()
    conn.close()
```

When content text is updated significantly, re-embed and replace the stored vector. Minor edits (typo fixes) don't warrant re-embedding.

**Cold start for content, not just users.** A brand-new content item has no views and won't appear in collaborative signals. This is distinct from the recency boost problem — it affects the catalog itself. One solution: when indexing a new item, compute its similarity to existing popular items and pre-populate a "similar items" cache that bypasses the user-profile-based flow until the item accumulates real views.

**Sparse catalogs in specific categories.** If a user has exclusively viewed content in the "beginner" category but you're serving recommendations from "advanced" content, similarity scores will be low and results will feel random. Consider always returning a minimum number of items from the user's most-viewed category, regardless of the global ranking.

These edge cases don't need to be solved on day one. The embedding layer stays stable — you're just adding filtering logic around it.
