RAG (Retrieval-Augmented Generation) is one of the most practical ways to connect an LLM to external knowledge. The pattern is simple in principle: retrieve relevant document chunks, inject them into the prompt as context, generate an answer. The implementation details, however, are where most production systems fall apart.

The common failure modes are familiar: retrieval returns loosely relevant chunks that confuse rather than inform the model; the context window fills up with content the model can't use effectively; the system is too slow or too expensive to run at scale. This article addresses all three, working through a complete Gemini API RAG implementation from document ingestion through production optimization.

## Architecture Overview: What the Gemini API Handles

A RAG system has two distinct phases. The **indexing phase** splits documents into chunks, converts each chunk to an embedding vector, and stores those vectors in a vector store. The **retrieval and generation phase** embeds the user's query, finds similar chunks via vector search, and passes those chunks as context to the generative model.

Gemini API handles two of these steps: the Embedding API converts text to vectors, and Gemini 2.5 Pro generates the final answer. Here's the foundation:

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")

def embed_text(text: str, task_type: str = "RETRIEVAL_DOCUMENT") -> list[float]:
    """
    Embed text using the Gemini Embedding API.
    
    task_type options:
      RETRIEVAL_DOCUMENT — for document chunks being indexed
      RETRIEVAL_QUERY    — for user search queries
      SEMANTIC_SIMILARITY — for general similarity tasks
    """
    result = genai.embed_content(
        model="models/text-embedding-004",
        content=text,
        task_type=task_type
    )
    return result["embedding"]

# Index a document chunk
chunk = "Gemini 2.5 Pro supports a context window of over 1 million tokens."
doc_vector = embed_text(chunk, "RETRIEVAL_DOCUMENT")

# Embed a query — note the different task_type
query = "How large is Gemini's context window?"
query_vector = embed_text(query, "RETRIEVAL_QUERY")

print(f"Embedding dimensions: {len(doc_vector)}")  # 768
```

The `task_type` distinction matters. Using different task types for documents and queries enables asymmetric embeddings — the model learns to align query representations with document representations rather than treating them identically. In practice, this improves retrieval accuracy noticeably compared to using the same task type for both.

## Chunk Strategy: Getting the Splits Right

Chunking is the single most important factor in retrieval quality, yet it's often treated as an afterthought. Chunks that are too large include irrelevant content that dilutes the relevance signal; chunks that are too small lose the surrounding context the model needs to answer correctly.

```python
from typing import List
import re

def chunk_by_semantic_boundary(
    text: str,
    max_chunk_size: int = 800,
    overlap: int = 100
) -> List[dict]:
    """
    Split text at semantic boundaries (headings, paragraph breaks)
    rather than at arbitrary character counts.
    
    overlap preserves context continuity across chunk boundaries.
    """
    sections = re.split(r'\n#{1,3}\s+|\n\n+', text)
    chunks = []
    current_chunk = ""
    chunk_index = 0
    
    for section in sections:
        section = section.strip()
        if not section:
            continue
        
        if len(current_chunk) + len(section) <= max_chunk_size:
            current_chunk += ("\n\n" + section) if current_chunk else section
        else:
            if current_chunk:
                chunks.append({
                    "index": chunk_index,
                    "text": current_chunk,
                    "char_count": len(current_chunk)
                })
                chunk_index += 1
                overlap_text = current_chunk[-overlap:] if len(current_chunk) > overlap else current_chunk
                current_chunk = overlap_text + "\n\n" + section
            else:
                # Section alone exceeds max size — force split
                for i in range(0, len(section), max_chunk_size - overlap):
                    chunks.append({
                        "index": chunk_index,
                        "text": section[i:i + max_chunk_size],
                        "char_count": min(max_chunk_size, len(section) - i)
                    })
                    chunk_index += 1
                current_chunk = ""
    
    if current_chunk:
        chunks.append({
            "index": chunk_index,
            "text": current_chunk,
            "char_count": len(current_chunk)
        })
    
    return chunks
```

A practical guideline: for dense technical content (API docs, specifications), use 400–600 characters per chunk. For prose (meeting notes, articles, reports), 800–1,200 characters works better. The `overlap` parameter is important — a 100-character overlap at chunk boundaries prevents answers that depend on a sentence that spans two chunks from being missed entirely.

## Vector Store Setup With ChromaDB

For indexing and searching the embeddings, I'll use ChromaDB as the vector store. It requires no infrastructure setup for development and scales well enough for collections up to a few million chunks.

```python
import chromadb

chroma_client = chromadb.PersistentClient(path="./chroma_db")

collection = chroma_client.get_or_create_collection(
    name="knowledge_base",
    metadata={"hnsw:space": "cosine"}  # cosine similarity
)

def index_documents(documents: List[dict]) -> None:
    """
    Process documents: chunk → embed → store.
    documents: [{"id": str, "text": str, "metadata": dict}]
    """
    all_ids, all_embeddings, all_docs, all_metas = [], [], [], []
    
    for doc in documents:
        chunks = chunk_by_semantic_boundary(doc["text"])
        for chunk in chunks:
            chunk_id = f"{doc['id']}_chunk_{chunk['index']}"
            vector = embed_text(chunk["text"], "RETRIEVAL_DOCUMENT")
            
            all_ids.append(chunk_id)
            all_embeddings.append(vector)
            all_docs.append(chunk["text"])
            all_metas.append({
                **doc.get("metadata", {}),
                "source_id": doc["id"],
                "chunk_index": chunk["index"],
                "char_count": chunk["char_count"]
            })
    
    # Add in batches of 100
    batch_size = 100
    for i in range(0, len(all_ids), batch_size):
        collection.add(
            ids=all_ids[i:i+batch_size],
            embeddings=all_embeddings[i:i+batch_size],
            documents=all_docs[i:i+batch_size],
            metadatas=all_metas[i:i+batch_size]
        )
    
    print(f"Indexed {len(all_ids)} chunks")

def search(query: str, n_results: int = 5, metadata_filter: dict = None) -> List[dict]:
    """Retrieve the most similar chunks for a query"""
    query_vec = embed_text(query, "RETRIEVAL_QUERY")
    
    results = collection.query(
        query_embeddings=[query_vec],
        n_results=n_results,
        where=metadata_filter,
        include=["documents", "metadatas", "distances"]
    )
    
    return [
        {
            "text": doc,
            "metadata": meta,
            "similarity": 1 - dist  # convert cosine distance to similarity
        }
        for doc, meta, dist in zip(
            results["documents"][0],
            results["metadatas"][0],
            results["distances"][0]
        )
    ]
```

For production systems beyond a few million chunks, consider Pinecone or Weaviate for managed vector search, or Vertex AI Vector Search if you're already in the Google Cloud ecosystem. The embedding and retrieval code above stays the same — only the vector store client changes.

## Improving Retrieval Quality: Query Expansion and Reranking

Basic vector search has a ceiling on retrieval quality. Two techniques reliably push past that ceiling.

### Query Expansion

Users often express the same information need in different ways. Expanding a query into multiple phrasings before searching captures matches that a single query would miss.

```python
def expand_query(original_query: str) -> List[str]:
    """Use Gemini to generate query variants for broader retrieval"""
    model = genai.GenerativeModel("gemini-2.5-pro-preview-05-06")
    
    response = model.generate_content(
        f"""Rephrase the following question in 3 different ways that preserve the meaning.
Output each rephrasing on its own line, with no numbering or explanation.

Question: {original_query}"""
    )
    
    variants = [q.strip() for q in response.text.strip().split("\n") if q.strip()]
    return [original_query] + variants[:3]

def search_with_expansion(query: str, n_results: int = 5) -> List[dict]:
    """Search across expanded queries, deduplicate by chunk ID"""
    queries = expand_query(query)
    
    seen_ids = set()
    all_results = []
    
    for q in queries:
        for result in search(q, n_results=n_results):
            chunk_id = (
                result["metadata"].get("source_id", "") +
                str(result["metadata"].get("chunk_index", 0))
            )
            if chunk_id not in seen_ids:
                seen_ids.add(chunk_id)
                all_results.append(result)
    
    return sorted(all_results, key=lambda x: x["similarity"], reverse=True)[:n_results]
```

### Cross-Encoder Reranking

Vector search (bi-encoder) is fast but approximate. A cross-encoder evaluates query-document pairs jointly, producing a more accurate relevance score at the cost of higher latency. The pattern is to use vector search for candidate retrieval, then rerank with a cross-encoder:

```python
from sentence_transformers import CrossEncoder

cross_encoder = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query: str, results: List[dict], top_k: int = 3) -> List[dict]:
    """Rerank retrieved chunks using a cross-encoder"""
    if not results:
        return []
    
    pairs = [(query, r["text"]) for r in results]
    scores = cross_encoder.predict(pairs)
    
    ranked = sorted(zip(results, scores), key=lambda x: x[1], reverse=True)
    return [
        {**result, "rerank_score": float(score)}
        for result, score in ranked[:top_k]
    ]
```

In my testing, the combination of query expansion (broader recall) and cross-encoder reranking (higher precision) improves retrieval quality more than either technique alone, at the cost of some additional latency. For applications where answer quality is paramount, it's worth it.

## Answer Generation With Hallucination Mitigation

The prompt design for answer generation has a significant impact on hallucination rates. The key is constraining the model to use only the retrieved context.

```python
def generate_answer(
    query: str,
    context_chunks: List[dict],
    model_name: str = "gemini-2.5-pro-preview-05-06"
) -> dict:
    """Generate an answer grounded in retrieved context chunks"""
    model = genai.GenerativeModel(model_name)
    
    # Format context with explicit source labels
    context_text = "\n\n---\n\n".join([
        f"[Source {i+1}] {chunk['text']}"
        for i, chunk in enumerate(context_chunks)
    ])
    
    prompt = f"""Answer the question using ONLY the information in the source documents below.

Rules:
- Do not use any knowledge beyond what is in the sources
- Cite your sources using [Source N] references
- If the sources don't contain enough information to answer, say "The provided documents don't contain enough information to answer this question"

Source Documents:
{context_text}

Question: {query}

Answer:"""
    
    response = model.generate_content(
        prompt,
        generation_config={"temperature": 0.1}  # low temperature for factual tasks
    )
    
    return {
        "answer": response.text,
        "sources": [
            {
                "source_id": chunk["metadata"].get("source_id"),
                "chunk_index": chunk["metadata"].get("chunk_index"),
                "similarity": chunk.get("similarity"),
                "preview": chunk["text"][:200]
            }
            for chunk in context_chunks
        ]
    }
```

Two details matter here: the explicit "do not use knowledge beyond the sources" instruction suppresses the model's tendency to fill gaps with confident-sounding fabrications, and the "if sources don't contain enough information" fallback prevents the model from making up an answer when the retrieval failed to find relevant content.

Setting `temperature` to 0.1 for factual retrieval tasks is a consistent improvement over the default. The model's creative variation is not useful when you want it to faithfully report what's in the sources.

## Production Optimization: Caching and Async Processing

Two optimizations make the most practical difference in production: embedding caching and asynchronous pipeline execution.

```python
import asyncio
import hashlib
import time

# In-memory embedding cache — use Redis for multi-process deployments
_embedding_cache: dict[str, list[float]] = {}

def embed_with_cache(text: str, task_type: str = "RETRIEVAL_QUERY") -> list[float]:
    """Cache embedding results to avoid redundant API calls"""
    cache_key = hashlib.md5(f"{task_type}:{text}".encode()).hexdigest()
    if cache_key in _embedding_cache:
        return _embedding_cache[cache_key]
    
    vector = embed_text(text, task_type)
    _embedding_cache[cache_key] = vector
    return vector

async def rag_pipeline_async(query: str, n_results: int = 5) -> dict:
    """Full async RAG pipeline: expand → search → rerank → generate"""
    start = time.time()
    loop = asyncio.get_event_loop()
    
    # Query embedding and expansion run concurrently
    query_vec_task = loop.run_in_executor(
        None, lambda: embed_with_cache(query, "RETRIEVAL_QUERY")
    )
    expansion_task = loop.run_in_executor(None, lambda: expand_query(query))
    
    _, expanded_queries = await asyncio.gather(query_vec_task, expansion_task)
    
    # Parallel search across expanded queries
    search_tasks = [
        loop.run_in_executor(None, lambda q=q: search(q, n_results))
        for q in expanded_queries
    ]
    results_list = await asyncio.gather(*search_tasks)
    
    # Deduplicate and rerank
    seen, all_chunks = set(), []
    for results in results_list:
        for r in results:
            key = r["metadata"].get("source_id", "") + str(r["metadata"].get("chunk_index", 0))
            if key not in seen:
                seen.add(key)
                all_chunks.append(r)
    
    top_chunks = rerank(query, all_chunks, top_k=3)
    
    # Generate answer
    result = await loop.run_in_executor(
        None, lambda: generate_answer(query, top_chunks)
    )
    
    return {**result, "elapsed_seconds": round(time.time() - start, 2)}
```

In production measurements, embedding caching hits roughly 30% of queries in typical document QA workloads — users frequently rephrase or repeat similar questions. That 30% hit rate directly reduces API costs and eliminates that portion of latency entirely. For multi-process deployments, swap the in-memory dict for a Redis cache with a TTL appropriate for your document update frequency.

## Evaluation: Measuring What Actually Matters

Before shipping a RAG system, establishing baseline metrics against a small gold standard dataset is worth the investment.

**Recall@K** measures whether the correct answer chunk appears in the top K retrieved results. Build 30–50 query/answer pairs where you know which document chunk contains the answer, then measure what fraction of those queries retrieve the right chunk in the top 5 results. This tells you whether your retrieval is working.

**Faithfulness** measures whether the generated answer is grounded in the retrieved sources. The most practical approach is using Gemini itself as an evaluator: pass the answer and the source chunks to the model and ask whether the answer contains claims not supported by the sources. This "LLM-as-judge" approach correlates well with human evaluation at a fraction of the cost.

**Answer Relevance** measures whether the answer actually addresses the question. Again, LLM-as-judge works well here — ask the model to score how well the answer responds to the original question on a 1–5 scale.

A system with high faithfulness and low recall is one where the retrieval is failing; the model is careful but doesn't have the right information. A system with high recall and low faithfulness is one where retrieval works but the model is going off-script. Knowing which problem you have tells you where to focus optimization effort.

RAG systems reward iteration. Start with the basic pipeline — chunk, embed, search, generate — get it working end-to-end, then add query expansion, reranking, and caching based on where your evaluation metrics show the most room for improvement. The patterns in this article are the refinements that have made the most consistent difference in production systems.

## Handling Edge Cases in Production

Several failure modes appear consistently in real-world RAG deployments. Planning for them upfront is cheaper than debugging them in production.

### When Retrieval Returns No Useful Chunks

Sometimes the vector search returns chunks with low similarity scores — technically the closest results in the database, but not actually relevant to the query. Passing these into the generation prompt produces confidently-worded non-answers.

```python
def search_with_threshold(
    query: str,
    n_results: int = 5,
    min_similarity: float = 0.65
) -> List[dict]:
    """
    Filter out retrieved chunks below a similarity threshold.
    Returns an empty list rather than irrelevant results.
    """
    results = search(query, n_results=n_results)
    filtered = [r for r in results if r.get("similarity", 0) >= min_similarity]
    return filtered

def generate_with_fallback(query: str, n_results: int = 5) -> dict:
    """RAG with graceful fallback when retrieval finds nothing relevant"""
    chunks = search_with_threshold(query, n_results=n_results, min_similarity=0.65)
    
    if not chunks:
        return {
            "answer": "I couldn't find relevant information in the knowledge base to answer this question. Please try rephrasing or check whether this topic is covered in the available documents.",
            "sources": [],
            "retrieval_status": "no_relevant_chunks"
        }
    
    result = generate_answer(query, chunks)
    result["retrieval_status"] = "success"
    return result
```

The right threshold for `min_similarity` varies by embedding model and content domain — 0.65 is a reasonable starting point, but calibrate it against your evaluation dataset. A threshold that's too high causes the system to refuse answerable questions; too low lets in noise that degrades answer quality.

### Multi-Document Attribution

For use cases where users need to trace an answer back to its source document (compliance, research, legal workflows), structured attribution is essential:

```python
from dataclasses import dataclass

@dataclass
class CitedAnswer:
    answer_text: str
    citations: List[dict]  # Which sources support which claims
    confidence: str        # "high", "medium", "low"

def generate_with_citations(
    query: str,
    context_chunks: List[dict]
) -> CitedAnswer:
    """Generate an answer with explicit per-claim citations"""
    model = genai.GenerativeModel("gemini-2.5-pro-preview-05-06")
    
    context_text = "\n\n".join([
        f"[Document {i+1}, ID: {chunk['metadata'].get('source_id', 'unknown')}]\n{chunk['text']}"
        for i, chunk in enumerate(context_chunks)
    ])
    
    prompt = f"""Answer the question below using only the provided documents.
For each factual claim in your answer, indicate which document it comes from using [Doc N].
If you are uncertain about a claim, indicate this explicitly.

Documents:
{context_text}

Question: {query}

Answer with citations:"""
    
    response = model.generate_content(
        prompt,
        generation_config={"temperature": 0.1}
    )
    
    # Determine confidence based on retrieval quality
    avg_similarity = (
        sum(c.get("similarity", 0) for c in context_chunks) / len(context_chunks)
        if context_chunks else 0
    )
    confidence = "high" if avg_similarity > 0.8 else "medium" if avg_similarity > 0.65 else "low"
    
    return CitedAnswer(
        answer_text=response.text,
        citations=[
            {
                "doc_id": chunk["metadata"].get("source_id"),
                "chunk_index": chunk["metadata"].get("chunk_index"),
                "similarity": chunk.get("similarity"),
                "text_preview": chunk["text"][:150]
            }
            for chunk in context_chunks
        ],
        confidence=confidence
    )
```

## Scaling the Index: Incremental Updates

In production, documents change. A document ingestion pipeline needs to handle updates without requiring full re-indexing.

```python
def update_document(doc_id: str, new_text: str, metadata: dict = None) -> None:
    """
    Update a document in the index by removing old chunks and adding new ones.
    This is simpler than trying to do in-place updates on individual chunks.
    """
    # Remove all existing chunks for this document
    existing = collection.get(where={"source_id": doc_id})
    if existing["ids"]:
        collection.delete(ids=existing["ids"])
        print(f"Removed {len(existing['ids'])} existing chunks for {doc_id}")
    
    # Re-index with the new content
    index_documents([{
        "id": doc_id,
        "text": new_text,
        "metadata": metadata or {}
    }])
    print(f"Re-indexed {doc_id}")

def delete_document(doc_id: str) -> None:
    """Remove all chunks for a document from the index"""
    existing = collection.get(where={"source_id": doc_id})
    if existing["ids"]:
        collection.delete(ids=existing["ids"])
        print(f"Deleted {len(existing['ids'])} chunks for {doc_id}")
```

The pattern of delete-then-reindex is simpler and more reliable than trying to compute and apply diffs at the chunk level. The cost of re-embedding a single updated document is usually low enough that it's not worth the complexity of incremental chunk-level updates.

## Summary: What to Prioritize at Each Stage

The order in which to invest in RAG improvements depends on where you are in the development cycle.

At **prototype stage**: get the basic pipeline working — index a small document set, run searches, generate answers. Verify the system returns sensible results before adding complexity.

At **quality improvement stage**: add semantic chunking (rather than fixed-size splits), implement query expansion, and measure Recall@K against a small gold standard set. These three changes typically produce the largest improvement in retrieval quality.

At **production readiness stage**: add cross-encoder reranking, embedding caching, the similarity threshold filter, and the graceful fallback. Measure faithfulness alongside retrieval quality. Set up monitoring for query latency and cache hit rates.

At **scale stage**: evaluate whether ChromaDB still meets your performance requirements, consider managed vector store services, and implement incremental document updates if your knowledge base changes frequently.

Each stage builds on the previous one. The patterns in this article are designed to be added incrementally — you don't need all of them on day one, but knowing they exist helps you plan the architecture to accommodate them when you do.

## Advanced Patterns: Hybrid Search and Metadata Filtering

As your RAG system matures, two additional patterns become valuable: hybrid search (combining vector similarity with keyword search) and metadata-based filtering.

### Hybrid Search: Combining Semantic and Keyword Retrieval

Pure vector search is strong on semantic meaning but can miss exact term matches — especially for proper nouns, product names, error codes, or other terms where exact string matching matters more than semantic similarity. Hybrid search combines both:

```python
from rank_bm25 import BM25Okapi
import numpy as np

class HybridSearcher:
    """
    Combines BM25 keyword search with vector similarity search.
    Useful when your documents contain exact terms that need precise matching.
    """
    
    def __init__(self, collection, alpha: float = 0.5):
        """
        alpha: weight for vector search (1-alpha for BM25)
        alpha=1.0 → pure vector search
        alpha=0.0 → pure BM25
        alpha=0.5 → equal weight (good starting point)
        """
        self.collection = collection
        self.alpha = alpha
        self._bm25 = None
        self._bm25_docs = []
        self._bm25_ids = []
    
    def build_bm25_index(self):
        """Build BM25 index from all documents in the collection"""
        all_docs = self.collection.get(include=["documents", "ids"])
        self._bm25_ids = all_docs["ids"]
        self._bm25_docs = all_docs["documents"]
        tokenized = [doc.lower().split() for doc in self._bm25_docs]
        self._bm25 = BM25Okapi(tokenized)
    
    def search(self, query: str, n_results: int = 5) -> List[dict]:
        if self._bm25 is None:
            self.build_bm25_index()
        
        # BM25 scores
        bm25_scores = self._bm25.get_scores(query.lower().split())
        bm25_norm = bm25_scores / (bm25_scores.max() + 1e-10)
        
        # Vector similarity scores
        query_vec = embed_with_cache(query, "RETRIEVAL_QUERY")
        vector_results = self.collection.query(
            query_embeddings=[query_vec],
            n_results=len(self._bm25_ids),
            include=["documents", "metadatas", "distances", "ids"]
        )
        
        vector_scores = np.zeros(len(self._bm25_ids))
        id_to_idx = {id_: i for i, id_ in enumerate(self._bm25_ids)}
        for id_, dist in zip(vector_results["ids"][0], vector_results["distances"][0]):
            if id_ in id_to_idx:
                vector_scores[id_to_idx[id_]] = 1 - dist
        
        # Combine scores
        combined = self.alpha * vector_scores + (1 - self.alpha) * bm25_norm
        top_indices = np.argsort(combined)[::-1][:n_results]
        
        return [
            {
                "text": self._bm25_docs[i],
                "chunk_id": self._bm25_ids[i],
                "combined_score": float(combined[i]),
                "vector_score": float(vector_scores[i]),
                "bm25_score": float(bm25_norm[i])
            }
            for i in top_indices
        ]

# Usage
hybrid = HybridSearcher(collection, alpha=0.6)  # 60% vector, 40% BM25
results = hybrid.search("error code E404 in authentication flow")
```

Hybrid search is particularly valuable for customer support, code documentation, and any domain with dense technical terminology. The right `alpha` value depends on your content — documents with lots of unique identifiers benefit from more BM25 weight.

### Metadata Filtering for Scoped Retrieval

When your knowledge base contains documents from different sources, departments, or time periods, metadata filtering lets users (or the system) scope retrieval to relevant subsets:

```python
def search_scoped(
    query: str,
    department: str = None,
    after_date: str = None,
    document_type: str = None,
    n_results: int = 5
) -> List[dict]:
    """
    Retrieve chunks from a scoped subset of the knowledge base.
    Useful for multi-tenant systems or versioned documentation.
    """
    where_conditions = []
    
    if department:
        where_conditions.append({"department": {"$eq": department}})
    if document_type:
        where_conditions.append({"doc_type": {"$eq": document_type}})
    if after_date:
        where_conditions.append({"created_date": {"$gte": after_date}})
    
    # ChromaDB uses $and for multiple conditions
    where_clause = (
        {"$and": where_conditions} if len(where_conditions) > 1
        else where_conditions[0] if where_conditions
        else None
    )
    
    return search(query, n_results=n_results, metadata_filter=where_clause)

# Example: search only engineering docs created after 2026-01-01
results = search_scoped(
    "deployment configuration for production",
    department="engineering",
    after_date="2026-01-01",
    document_type="runbook"
)
```

Metadata filtering is also a practical security measure in multi-tenant systems — ensuring that users can only retrieve documents they're authorized to access is more reliable when enforced at the retrieval layer than when left to the generation model to self-police.

## Lessons From Real Deployments

A few things from production RAG systems that aren't obvious from tutorials:

**Query logs are your best debugging tool.** Logging every query, the retrieved chunks, and the generated answer creates a dataset you can review to identify systematic retrieval failures. After a week of production traffic, patterns in failed retrievals usually point directly to gaps in chunking strategy or missing document coverage.

**The similarity threshold needs tuning per domain.** A threshold calibrated on general text often performs poorly on specialized domains (legal, medical, financial). When moving to a new domain, always recalibrate against a small domain-specific evaluation set before going live.

**Context length has diminishing returns.** Passing 10 chunks into the context isn't necessarily better than passing 3 well-selected chunks. The model's ability to use long contexts effectively depends on how well the content is organized. In my experience, 3–5 carefully reranked chunks outperforms 8–10 chunks without reranking.

**Monitor embedding API latency separately from generation latency.** When the system feels slow, the bottleneck is usually embedding (sequential calls) rather than generation. Caching and parallel execution of query embedding + expansion is usually where the most latency reduction is available.

Building a RAG system with Gemini API is genuinely practical — the combination of text-embedding-004 for retrieval and Gemini 2.5 Pro for generation is one of the strongest available. The patterns in this article reflect the refinements that consistently matter in production: good chunking, query expansion, cross-encoder reranking, similarity thresholds, embedding caching, and structured evaluation. Layer them in progressively as your system matures.

## Complete End-to-End Example

Putting it all together, here's a minimal but complete RAG system that incorporates the key patterns from this article:

```python
import asyncio
import hashlib
import time
from typing import List
import google.generativeai as genai
import chromadb

# Configuration
genai.configure(api_key="YOUR_GEMINI_API_KEY")
EMBEDDING_MODEL = "models/text-embedding-004"
GENERATION_MODEL = "gemini-2.5-pro-preview-05-06"
MIN_SIMILARITY_THRESHOLD = 0.65

# Initialize stores
chroma_client = chromadb.PersistentClient(path="./rag_db")
collection = chroma_client.get_or_create_collection(
    name="documents",
    metadata={"hnsw:space": "cosine"}
)
_cache: dict[str, list[float]] = {}

class GeminiRAG:
    """Complete RAG system: ingest → index → retrieve → generate"""
    
    def embed(self, text: str, task_type: str = "RETRIEVAL_DOCUMENT") -> list[float]:
        key = hashlib.md5(f"{task_type}:{text}".encode()).hexdigest()
        if key not in _cache:
            result = genai.embed_content(
                model=EMBEDDING_MODEL,
                content=text,
                task_type=task_type
            )
            _cache[key] = result["embedding"]
        return _cache[key]
    
    def ingest(self, doc_id: str, text: str, metadata: dict = None):
        """Chunk, embed, and index a document"""
        chunks = chunk_by_semantic_boundary(text)
        ids, vecs, docs, metas = [], [], [], []
        
        for chunk in chunks:
            chunk_id = f"{doc_id}_{chunk['index']}"
            ids.append(chunk_id)
            vecs.append(self.embed(chunk["text"], "RETRIEVAL_DOCUMENT"))
            docs.append(chunk["text"])
            metas.append({"source_id": doc_id, "chunk_index": chunk["index"],
                         **(metadata or {})})
        
        collection.add(ids=ids, embeddings=vecs, documents=docs, metadatas=metas)
    
    def retrieve(self, query: str, k: int = 5) -> List[dict]:
        """Embed query, search, filter by threshold"""
        qvec = self.embed(query, "RETRIEVAL_QUERY")
        results = collection.query(
            query_embeddings=[qvec], n_results=k,
            include=["documents", "metadatas", "distances"]
        )
        chunks = [
            {"text": d, "metadata": m, "similarity": 1-dist}
            for d, m, dist in zip(
                results["documents"][0],
                results["metadatas"][0],
                results["distances"][0]
            )
        ]
        return [c for c in chunks if c["similarity"] >= MIN_SIMILARITY_THRESHOLD]
    
    def generate(self, query: str, chunks: List[dict]) -> str:
        """Generate a grounded answer from retrieved chunks"""
        if not chunks:
            return "The available documents don't contain relevant information for this question."
        
        context = "\n\n---\n\n".join([
            f"[Source {i+1}] {c['text']}" for i, c in enumerate(chunks)
        ])
        
        model = genai.GenerativeModel(GENERATION_MODEL)
        response = model.generate_content(
            f"""Answer using ONLY the source documents. Cite sources as [Source N].
If the answer isn't in the sources, say so explicitly.

Sources:
{context}

Question: {query}""",
            generation_config={"temperature": 0.1}
        )
        return response.text
    
    def ask(self, query: str) -> dict:
        """Full RAG pipeline: retrieve → rerank → generate"""
        start = time.time()
        chunks = self.retrieve(query, k=8)
        top_chunks = rerank(query, chunks, top_k=3) if chunks else []
        answer = self.generate(query, top_chunks)
        
        return {
            "answer": answer,
            "chunks_retrieved": len(chunks),
            "chunks_used": len(top_chunks),
            "sources": [c["metadata"].get("source_id") for c in top_chunks],
            "latency_seconds": round(time.time() - start, 2)
        }

# Usage
rag = GeminiRAG()

# Ingest documents
rag.ingest("guide_001", "Gemini 2.5 Pro supports 1M token context...", 
           metadata={"category": "technical", "version": "2.5"})

# Ask a question
result = rag.ask("What is the context window size for Gemini 2.5 Pro?")
print(result["answer"])
print(f"Latency: {result['latency_seconds']}s | Sources: {result['sources']}")
```

This class encapsulates the core patterns — caching, threshold filtering, reranking — in a form that's easy to extend. Add query expansion by calling `expand_query()` inside `ask()`, swap ChromaDB for Pinecone by changing the `retrieve()` method, or add async support with the `asyncio` patterns shown earlier.

RAG systems are rarely "done." The production journey is one of incremental measurement and refinement: indexing more documents, improving chunking for your specific content types, tuning retrieval thresholds, and evolving the evaluation suite as you learn more about how users query the system. The architecture here is designed to support that evolution.
