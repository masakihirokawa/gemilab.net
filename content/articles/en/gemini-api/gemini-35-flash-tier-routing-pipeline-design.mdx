The day Gemini 3.5 Flash went generally available, the first thing I did was rewrite every model name in my automated pipeline to point at the top tier. When the newest, smartest model is announced, the pull to send everything there is hard to resist.

A few days later I noticed my projected API bill had nearly doubled. Polishing article prose, classifying a post into five tags, and catching a typo in a heading were all being thrown at the same top tier.

When you run several sites as an indie developer, monthly cost is decided less by "can I use the smartest model" and more by "which tier did I assign to which job." Now that the lightweight Flash tiers are stable at GA, this is the moment to rebuild the design around routing by stage rather than defaulting everything upward.

## Break one generation into stages

"Write one article" is, in practice, a chain of small stages. In my pipeline a single generation splits into four.

### Classify and extract

Category detection, tag assignment, keyword extraction from reference data. These return short, structured answers and need almost no depth of reasoning.

### Draft

Outlining the headings and producing a first-pass draft of each section. High in volume, but every word here gets rewritten later. Speed and price matter more than polish.

### Finalize

Shaping the prose to the house voice, closing logical gaps, making the tone consistent for the reader. This stage decides the article's value, so I spend a reasoning-heavy top tier here without hesitation.

### Verify

Typos, banned words, bare URLs, and JA/EN parity. Most of this is regex; a model is called only where meaning actually has to be judged.

Once the stages are visible, only one of the four — finalize — truly needs reasoning power. The rest can be chosen on speed and unit price.

What matters is that the highest-frequency stages sit on the cheapest tiers. Classify and draft run many times per article; finalize runs once. The expensive tier is confined to the least frequent stage.

## Put a router in front

Turn the table into code and you stop deciding which model to call every time. I keep a thin router that takes a stage name and returns a model name.

```python
from enum import Enum

class Stage(str, Enum):
    CLASSIFY = "classify"
    DRAFT = "draft"
    FINALIZE = "finalize"
    VERIFY = "verify"

# Stage -> model. Keep tier names swappable via environment variables.
STAGE_MODEL = {
    Stage.CLASSIFY: "gemini-flash-lite-latest",
    Stage.DRAFT:    "gemini-flash-latest",
    Stage.FINALIZE: "gemini-pro-latest",
    Stage.VERIFY:   "gemini-flash-latest",
}

def model_for(stage: Stage) -> str:
    # Unknown stages fall to the cheapest tier, never the top one.
    return STAGE_MODEL.get(stage, "gemini-flash-lite-latest")
```

The key choice is that an unknown stage falls to the cheapest tier rather than the top. A routing miss goes straight onto the bill, so the default is always the safe side.

The caller only declares a stage.

```python
def run_stage(client, stage: Stage, prompt: str) -> str:
    model = model_for(stage)
    resp = client.models.generate_content(model=model, contents=prompt)
    return resp.text
```

## Escalate only on failure

The weakness of stage routing is when a cheap tier misses the quality bar. Sending every stage back to the top tier when that happens defeats the whole split.

What I use instead is a conditional escalation: re-run only the stage that failed verification, one tier up, exactly once.

```python
def run_with_escalation(client, stage, prompt, validate) -> str:
    out = run_stage(client, stage, prompt)
    if validate(out):
        return out
    # Only on failure: re-run one tier up, exactly once.
    escalated = {
        Stage.CLASSIFY: "gemini-flash-latest",
        Stage.DRAFT:    "gemini-pro-latest",
    }.get(stage)
    if escalated is None:
        raise ValueError(f"escalation exhausted for {stage}")
    resp = client.models.generate_content(model=escalated, contents=prompt)
    return resp.text
```

Limiting the retry to "once" and "one tier" is what holds the line. Unbounded escalation means every hard input avalanches into the top tier and spend spikes. I pass a regex-based machine check as `validate` so the model never grades its own pass or fail.

## Estimate the cost gap from call counts

Judge the design by the monthly estimate, not by feel. Assume four articles per site per day across four sites — sixteen a day — with per-article calls like this:

- Classify / extract: 3 calls
- Draft: 4 calls
- Finalize: 1 call
- Verify: 2 calls

Set the cheapest tier to 1 unit and multiply by the table. Sending every stage to the top tier (assume 20x) costs (3+4+1+2) × 20 = 200 units per article. Routing by stage costs 3×1 + 4×4 + 1×20 + 2×4 = 47 units.

For the same sixteen articles a day, the relative cost is 200 versus 47 — roughly a quarter. That ratio matched the doubled bill I felt when everything was on the top tier. Swap in your own per-tier prices and the same arithmetic gives your real numbers.

## Operational traps the price sheet does not show

Run tier routing long enough and issues surface that the price sheet alone never reveals.

One is the default model changing. When a Flash tier becomes the default, calls that do not name a model explicitly shift their output character quietly. If you run a voice profile or template detection, review output right after a default moves. Naming the model in the router every time confines that impact inside the router.

The other is dated deprecations. Models with a fixed shutdown date — like the image preview models — fail silently one day unless you put the cutover deadline on your operations calendar. When I see a deprecation notice, I write the date as a comment in the router table so the missed cutover becomes physically visible.

## Where to start, by situation

If you are sending every stage to the top tier today, start with the highest-frequency stage. Usually that is classify or draft. Dropping just that to a Flash tier shaves the cost peak with almost no change in perceived quality.

Keep finalize on the top tier to the end. This stage creates the value a reader pays to read, so moving it to a cheap tier is backwards.

For verify, separate the regex part from the part that needs a model and shrink model calls to the minimum. Most machine checks pass without a model at all.

I run the several sites of Dolice Labs solo, funding this API budget with AdMob revenue. That is exactly why I watch "which tier I assigned to which stage" in the monthly numbers, rather than "can I use the smartest model."

Take one generation in your own pipeline, break it into stages, and move just the highest-frequency one down to a Flash tier. The difference on next month's bill will tell you, better than anything, whether to keep going.
