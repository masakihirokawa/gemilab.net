Have you ever asked Gemini for "just the executable Python function, please" only to receive a response wrapped in ` ```python ... ``` ` that you couldn't pipe straight into `exec()`? This was the very first wall I hit when building an automated code-generation pipeline.

The official docs say "output format can be controlled via prompting", but Gemini's pre-training data is heavily biased toward Markdown with code fences. No matter how firmly you phrase the instruction, a non-zero percentage of responses will come back decorated. This article walks through the three-layer pattern I've settled on: **prompt hardening + regex stripping + JSON schema**.

## Why the fences keep appearing

LLMs are fine-tuned to follow instructions, but they can't fully overwrite the priors learned from their training corpus. Nearly every Python snippet on Stack Overflow, GitHub, or technical blogs is surrounded by ` ```python ... ``` ` or bare ` ``` ... ``` `. Gemini 3.x inherits a strong prior that "code should be decorated".

Even at `temperature=0`, if your instruction is written in natural language ("please return raw code"), the model still has some ambiguity to resolve. Whether fences are "helpful" or "extra" depends on context, and the model sometimes guesses wrong. This behavior shows up even in newer models like `gemini-2.5-pro-latest` and `gemini-3.1-pro`, so waiting for a model upgrade is not a strategy. It also appears regardless of whether you call through the Google AI Studio SDK, the REST endpoint at `generativelanguage.googleapis.com`, or Vertex AI — the bias lives in the model weights, not in any particular client library. If your pipeline depends on clean code output, you need a defensive strategy at the application layer.

One more thing worth flagging: the fence rate varies depending on the task. Requests that mention a specific language or framework in natural prose ("write a Python function", "give me a TypeScript component") trigger fences more often than requests framed as "reply with this JSON schema" or "fill in this skeleton". Observing this helps you decide how hard to lean on each of the three layers below.

## Layer 1: System Instructions (start here)

The first lever is the system instruction. In my experience, placing rules in `system_instruction` rather than the user prompt is noticeably more effective. Here's the `google-genai` v1 Python SDK version.

```python
# Tell Gemini to refuse Markdown fences as firmly as possible
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

SYSTEM_INSTRUCTION = """You are a Python code generator. Obey these rules:
1. Your response must be valid raw Python source code, ready to be saved as a .py file
2. Never emit triple backticks (```python or ```), not even inside explanations
3. Do not include any prose before or after the code — no preamble, no postamble
4. If you need comments, use Python # comments inside the code
"""

response = client.models.generate_content(
    model="gemini-2.5-pro-latest",
    contents="Write a function gcd(a, b) that returns the greatest common divisor of two integers.",
    config=types.GenerateContentConfig(
        system_instruction=SYSTEM_INSTRUCTION,
        temperature=0.2,
    ),
)
print(response.text)
# Expected: def gcd(a, b): ... (no fences)
```

In practice this cuts the fence-rate to under 10%, but it never quite reaches zero. For production use, always pair it with the regex stripper below.

## Layer 2: Regex post-processing

Handle the remaining few percent defensively. Your stripper needs to cope with nested fences, language-less fences, leading/trailing whitespace, and missing final newlines.

```python
import re

def strip_code_fence(text: str) -> str:
    """Safely remove Markdown code fences from an LLM response.

    Handles:
    - ```python\\ncode\\n```
    - ```\\ncode\\n```
    - ```py\\ncode```
    - Cases with prose before or after the fenced block
    """
    if not text:
        return text

    s = text.strip()

    # Whole-string fence (the common case)
    pattern = re.compile(
        r"^```[a-zA-Z0-9_+-]*\s*\n?"  # opening fence (optional language tag)
        r"(.*?)"                       # body (non-greedy)
        r"\n?```\s*$",                 # closing fence
        re.DOTALL,
    )
    m = pattern.match(s)
    if m:
        return m.group(1).strip()

    # Fallback: strip stray opening/closing fences if the whole-string match failed
    s = re.sub(r"^```[a-zA-Z0-9_+-]*\s*\n?", "", s)
    s = re.sub(r"\n?```\s*$", "", s)
    return s.strip()

# Sanity check
samples = [
    "```python\ndef gcd(a, b):\n    return a if b == 0 else gcd(b, a % b)\n```",
    "```\nprint('hello')\n```",
    "Here is the code:\n```python\nx = 1\n```\nLet me know if that works.",
    "def plain(): pass",
]
for s in samples:
    print(repr(strip_code_fence(s)))
```

`re.DOTALL` makes `.` span newlines, and the non-greedy `.*?` captures only the body. The two-stage design (whole-match first, then partial cleanup) keeps the function robust when the model wraps explanation around the code.

## Layer 3: Structured output via JSON schema

The most bulletproof approach is to receive the code as a string field inside a JSON object. With `response_mime_type="application/json"` and a `response_schema`, Gemini is physically constrained to emit JSON and nothing else.

```python
from google import genai
from google.genai import types
from pydantic import BaseModel

class CodeResult(BaseModel):
    language: str
    code: str
    explanation: str  # keep prose out of the code field

client = genai.Client(api_key="YOUR_API_KEY")

response = client.models.generate_content(
    model="gemini-2.5-pro-latest",
    contents="Write a Python function that returns the greatest common divisor of two integers.",
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=CodeResult,
    ),
)

result = CodeResult.model_validate_json(response.text)
# result.code now contains raw source, no fences
print(result.code)
```

A nice side effect is that code and explanation land in separate fields. When you log responses, you can persist just the `code` field as a real `.py` file without any postprocessing.

The tradeoff is JSON escaping overhead: newlines inside the code become `\\n` literals, so always parse with Pydantic or `json.loads` rather than using `response.text` directly.

## The nastiest pitfall: code that *contains* triple backticks

The trickiest case is when the code you want to generate itself contains `"""` or ` ``` `. Think Markdown parsers, LLM prompt templates, or any tool that manipulates fenced content. Here the Layer 2 regex can accidentally swallow part of the body.

**Whenever the generated code might legitimately contain fence characters, Layer 3 (JSON schema) is effectively the only safe choice.** Because the string is JSON-encoded, the model's ` ``` ` characters get escaped (to `"\u0060\u0060\u0060"` or similar), and your fence-stripping logic can't collide with them.

## Verifying and monitoring in production

If you silently let a few stray fences slip through, they tend to surface later as "runtime errors spiked out of nowhere" incidents. I keep structured logs around the stripper and review them weekly.

```python
import logging

logger = logging.getLogger(__name__)

def process_code_response(raw: str) -> str:
    stripped = strip_code_fence(raw)
    if stripped != raw:
        # Fences were stripped = model ignored our instructions
        logger.info(
            "code_fence_stripped",
            extra={
                "raw_length": len(raw),
                "stripped_length": len(stripped),
                "had_language_tag": "```python" in raw or "```py" in raw,
            },
        )
    # Defensive double-check: warn if any residual fences remain
    if stripped.startswith("```") or stripped.rstrip().endswith("```"):
        logger.warning("code_fence_residual", extra={"snippet": stripped[:120]})
    return stripped
```

Tracking the `code_fence_stripped` rate before and after prompt tweaks gives you a quantitative read on your system-instruction changes. In my own setup, a single added line in the instruction cut the rate in half — the kind of signal that moves prompt engineering from guesswork to iteration.

## Handling responses with multiple code blocks

When you ask Gemini to "walk me through the implementation step by step", a single response can contain several fenced blocks. Whether you want the first block, the last one, or all of them joined depends on the task.

```python
def extract_all_code_blocks(text: str) -> list[str]:
    # Return every Python code block in the response, preserving order
    pattern = re.compile(
        r"```(?:python|py)?\s*\n(.*?)\n```",
        re.DOTALL,
    )
    return [m.strip() for m in pattern.findall(text)]

# Usage branches by count
blocks = extract_all_code_blocks(response.text)
if len(blocks) == 1:
    code = blocks[0]
elif len(blocks) > 1:
    # Pipeline-style: concatenate as sequential steps
    code = "\n\n".join(blocks)
else:
    # No fences at all — fall back to the stripper
    code = strip_code_fence(response.text)
```

For tutorial generation with step-by-step narration, collect every block with `extract_all_code_blocks`. For single-function generation, just take the first block. Picking the right combination up front saves you from having to special-case responses downstream.

## Picking the right layer

In production, decide by task stakes:

- Throwaway scripts or one-off CLI tooling: Layer 1 + Layer 2 are plenty.
- Production features that take user input and generate code to save or execute: go with Layer 3 (JSON schema).
- Any case where the generated code may itself contain fence characters: Layer 3 without exception.

Start by dropping `strip_code_fence` into your current project. That single function alone will eliminate most of the daily "why doesn't the copied code run" friction and lower the bar for plugging Gemini into real automation pipelines.
