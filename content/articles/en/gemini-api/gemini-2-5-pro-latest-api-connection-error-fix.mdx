"`gemini-2.5-pro-latest` returns 404." Every developer who works with the Gemini API hits this eventually. The SDK docs list the `-latest` alias, but the actual request comes back with `models/gemini-2.5-pro-latest is not found`. Without understanding *why*, most people pin a specific version inline — and then can't track future model updates.

This guide walks through how the `-latest` aliases actually behave, when 404 and 400 errors fire, and how I structure model selection in production so a Google-side model rotation doesn't page me at midnight.

## First: `-latest` is not available for every model

The Generative Language API has several `-latest` aliases. `gemini-1.5-pro-latest` and `gemini-1.5-flash-latest` reliably exist and resolve to the most recent snapshot.

But `gemini-2.5-pro-latest` is hit-or-miss depending on API version, project setup, and even region. That inconsistency is what trips most people up.

Here's the typical 404 response:

```json
{
  "error": {
    "code": 404,
    "message": "models/gemini-2.5-pro-latest is not found for API version v1beta",
    "status": "NOT_FOUND"
  }
}
```

When this happens, one of these is the cause:

1. **API version mismatch**: `v1` and `v1beta` expose different model lists.
2. **Gemini 2.5 not enabled on the project yet**: New projects sometimes need explicit activation in AI Studio.
3. **The alias simply doesn't exist for your region/SDK**: Only the canonical name `gemini-2.5-pro` is accepted.

## Listing what your project can actually call

The most reliable diagnostic is to enumerate models for *your specific* API key:

```bash
curl "https://generativelanguage.googleapis.com/v1beta/models?key=${GEMINI_API_KEY}" \
  | jq '.models[] | select(.supportedGenerationMethods[]? == "generateContent") | .name'
```

Whatever this list returns is what you can use. If `gemini-2.5-pro-latest` is missing, the alias is unavailable in your environment — period.

You'll likely see canonical names like:

```
"models/gemini-2.5-pro"
"models/gemini-2.5-flash"
"models/gemini-2.0-flash"
"models/gemini-1.5-pro-latest"
```

Use `gemini-2.5-pro` directly instead of the alias.

## v1 vs v1beta

The two API versions expose different model sets. The stable `v1` has fewer features but a stable model list. `v1beta` exposes the latest features (richer Function Calling schemas, Code Execution) but the model names move around.

My production rule: pin the canonical name (no `-latest` suffix) under `v1` for production apps. Save `v1beta` for tools and prototypes. The convenience of `-latest` becomes a liability when Google rotates model behavior under it.

## When you see 400 instead of 404

Different problem, different causes. Three patterns I see most often:

**Pattern A: outdated `generationConfig` shape**

If you put `temperature` at the top level instead of inside `generationConfig`, newer models reject it.

```javascript
// ❌ Old shape — works on some models, deprecated
const response = await model.generateContent({
  contents: [{ role: "user", parts: [{ text: prompt }] }],
  temperature: 0.7
});

// ✅ Recommended
const response = await model.generateContent({
  contents: [{ role: "user", parts: [{ text: prompt }] }],
  generationConfig: { temperature: 0.7, maxOutputTokens: 2048 }
});
```

**Pattern B: outdated `safetySettings` threshold values**

Gemini 2.5 sometimes requires `HARM_BLOCK_THRESHOLD_UNSPECIFIED`. To turn safety off, use `BLOCK_NONE` — `OFF` is not a valid value.

**Pattern C: putting `system_instruction` inside `contents`**

In Gemini 2.5, system instructions belong in the dedicated field. A `role: "system"` entry inside `contents` returns 400.

```javascript
// ✅ Correct
const result = await genAI.getGenerativeModel({
  model: "gemini-2.5-pro",
  systemInstruction: "You are a careful and friendly assistant."
}).generateContent(prompt);
```

## The production model-selection pattern I use

```typescript
// config/gemini.ts
const PRIMARY_MODEL = "gemini-2.5-pro";
const FALLBACK_MODEL = "gemini-2.5-flash";
const LEGACY_FALLBACK = "gemini-1.5-pro-latest";

export async function generateWithFallback(prompt: string) {
  for (const modelName of [PRIMARY_MODEL, FALLBACK_MODEL, LEGACY_FALLBACK]) {
    try {
      const model = genAI.getGenerativeModel({ model: modelName });
      return await model.generateContent(prompt);
    } catch (e: any) {
      if (e.status === 404 || e.status === 400) {
        console.warn(`[Gemini] ${modelName} failed -> trying next`);
        continue;
      }
      throw e;
    }
  }
  throw new Error("All Gemini models failed");
}
```

Three principles:

1. **Don't make `-latest` your primary in production.** Pin canonical names.
2. **Keep the same-generation Flash as fallback.** When Pro is degraded, Flash is usually still up.
3. **Keep a previous-gen alias as last resort.** `gemini-1.5-pro-latest` has been remarkably stable.

## Final checks if 404 still won't go away

If you've cleared the items above and still see 404, work through:

- Is your API key bound to the right project? (Easy to misroute when you have several.)
- Is the Generative Language API enabled on that project?
- Is billing active? (Some models stop responding when free quota is exhausted.)
- Region restrictions? (Some models reject requests from specific regions, undocumented.)

Region restriction is the trap people miss most. VPN traffic, or a server in one region calling a model that's effectively gated to another, can produce a 404 with no indication of *why*.

## Start here

Run the curl model-list call against your API key. That single command tells you whether `-latest` works in your environment. From there, structure your production code with explicit fallbacks and you'll stop being surprised by Google's model rotations.
