API calls timeout when processing takes minutes instead of seconds. Deep Research, complex reasoning chains, multi-step workflows — these tasks all exceed typical request-response model constraints.

**Gemini Interactions API Background Execution** lets your client receive an Interaction ID immediately and disconnect, while the server continues processing asynchronously. This guide covers implementation patterns, polling strategies, and how to choose between Background Execution and Batch Mode.

## Interactions API and Background Execution Basics

The Gemini Interactions API provides stateful conversation management and tool execution in a single interface. As of March 2026, setting `background=True` enables asynchronous execution.

### Background Mode Characteristics

- **Immediate response**: Returns Interaction ID without waiting for completion
- **Server-side processing**: Client can disconnect without blocking
- **State management**: `store=true` (default) preserves conversation context
- **Polling support**: Separate endpoint checks completion and retrieves results

Standard synchronous request:

```python
# Synchronous Interactions API call
response = client.models.generate_content(
    model="gemini-2.5-pro",
    contents=[{"role": "user", "parts": [{"text": "Run complex analysis"}]}],
)
# Client blocks until response completes
print(response.text)
```

With Background Execution:

```python
# Asynchronous execution (detailed implementation below)
interaction = client.models.interactions.create(
    model="gemini-2.5-pro",
    contents=[{"role": "user", "parts": [{"text": "Execute Deep Research"}]}],
    background=True
)
# Returns interaction_id immediately
print(f"Interaction ID: {interaction.id}")
# Client continues with next operation
```

## Implementing Background Execution

### Step 1: Starting a Background Task

```python
import anthropic
import time

client = anthropic.Anthropic(api_key="YOUR_GEMINI_API_KEY")

def start_background_task(prompt: str, model: str = "gemini-2.5-pro") -> dict:
    """
    Launch a long-running task with Background Execution

    Args:
        prompt: User instruction
        model: Model identifier

    Returns:
        Dictionary with:
        - interaction_id: ID for polling
        - created_at: Task creation timestamp
    """
    response = client.models.interactions.create(
        model=model,
        contents=[
            {
                "role": "user",
                "parts": [{"text": prompt}]
            }
        ],
        background=True,  # Enable asynchronous mode
        store=True,       # Preserve conversation state
    )

    return {
        "interaction_id": response.name,  # Format: "interactions/..."
        "created_at": response.create_time
    }

# Usage example
result = start_background_task("Conduct deep research-based analysis")
print(f"Started task: {result['interaction_id']}")
```

### Step 2: Polling for Progress

```python
def poll_background_task(interaction_id: str, max_wait_seconds: int = 600) -> dict:
    """
    Poll background task status until completion

    Args:
        interaction_id: ID returned from start_background_task
        max_wait_seconds: Maximum polling duration (default: 10 minutes)

    Returns:
        Dictionary with:
        - status: "COMPLETED", "PROCESSING", "FAILED", "TIMEOUT"
        - output: Result text when completed
        - error: Error message if failed
    """
    start_time = time.time()
    poll_count = 0

    while True:
        elapsed = time.time() - start_time
        if elapsed > max_wait_seconds:
            return {"status": "TIMEOUT", "error": "Max wait time exceeded"}

        # Exponential backoff for polling intervals
        poll_count += 1
        wait_time = min(2 ** poll_count, 30)  # Cap at 30 seconds

        try:
            # Check Interactions API for status
            interaction = client.models.interactions.get(
                name=interaction_id
            )

            # Evaluate completion status
            if interaction.state == "COMPLETED":
                # Extract output from final message
                if interaction.messages:
                    last_msg = interaction.messages[-1]
                    if last_msg.parts:
                        return {
                            "status": "COMPLETED",
                            "output": last_msg.parts[0].text
                        }
                return {"status": "COMPLETED", "output": ""}

            elif interaction.state == "FAILED":
                return {
                    "status": "FAILED",
                    "error": interaction.error or "Unknown error"
                }

            elif interaction.state == "PROCESSING":
                print(f"Processing... (elapsed: {elapsed:.1f}s)")
                time.sleep(wait_time)
                continue

        except Exception as e:
            return {"status": "ERROR", "error": str(e)}

# Usage example
task_result = start_background_task("Statistical analysis of large dataset")
print(f"Task started: {task_result['interaction_id']}")

poll_result = poll_background_task(task_result['interaction_id'])
if poll_result['status'] == 'COMPLETED':
    print(f"Result: {poll_result['output']}")
else:
    print(f"Task failed: {poll_result.get('error')}")
```

## Background Execution vs Batch API

Background Execution and Batch API serve different purposes despite surface similarities.

### Background Execution Profile

- **Latency**: Seconds to minutes
- **Max duration**: ~30 minutes
- **Use cases**: Deep Research, complex reasoning, some real-time needs
- **Pricing**: Standard rates
- **Scale**: Medium batches (tens to hundreds of requests)

### Batch API Profile

- **Latency**: N/A (24-hour processing)
- **Max duration**: Unlimited
- **Use cases**: Large dataset processing, cost optimization priority, scheduled runs
- **Pricing**: 50% discount
- **Scale**: Massive batches (thousands to millions)

### Decision Flow

```
Is task already initiated?
├─ YES → Consider Background Execution
│        Results needed in 30 minutes?
│        ├─ YES → Background Execution
│        └─ NO  → Also consider Batch
└─ NO  → Processing large volume?
         ├─ YES (>1000) → Batch API
         ├─ NO (<1000)  → Background Execution
         └─ Cost priority?
            ├─ YES → Batch API
            └─ NO  → Background Execution
```

Quick decision matrix:

- **Need results in 5-30 minutes** → Background Execution
- **Can wait 24 hours, need 50% savings** → Batch API
- **Processing 100K+ requests** → Batch API required

## Error Handling and Retry Strategy

```python
import random

def robust_background_execution(
    prompt: str,
    max_retries: int = 3,
    backoff_factor: float = 2.0
) -> dict:
    """
    Execute with error handling and retry logic
    """
    for attempt in range(max_retries):
        try:
            # Launch task
            task = start_background_task(prompt)

            # Poll for completion
            result = poll_background_task(task['interaction_id'])

            if result['status'] == 'COMPLETED':
                return {"success": True, "data": result['output']}
            elif result['status'] == 'FAILED':
                # Check if error is retryable
                error_msg = result.get('error', '')
                if is_retryable_error(error_msg):
                    raise Exception(f"Retryable error: {error_msg}")
                else:
                    return {"success": False, "error": error_msg}

        except Exception as e:
            if attempt < max_retries - 1:
                wait_time = (backoff_factor ** attempt) + random.uniform(0, 1)
                print(f"Attempt {attempt + 1} failed: {e}. Retrying in {wait_time:.1f}s...")
                time.sleep(wait_time)
            else:
                return {"success": False, "error": str(e)}

    return {"success": False, "error": "Max retries exceeded"}

def is_retryable_error(error_msg: str) -> bool:
    """Determine if error warrants retry"""
    retryable_keywords = [
        "timeout",
        "temporary",
        "unavailable",
        "rate_limit",
        "transient"
    ]
    return any(kw in error_msg.lower() for kw in retryable_keywords)

# Usage example
result = robust_background_execution("Complex analysis task")
if result['success']:
    print(f"Output: {result['data']}")
else:
    print(f"Failed: {result['error']}")
```

## Pricing and Optimization

Background Execution pricing (gemini-2.5-pro):

- **Input tokens**: $0.075 per 1M tokens
- **Output tokens**: $0.30 per 1M tokens
- **Context window**: 1M tokens max
- **Time limit**: 30 minutes maximum

Cost reduction strategies:

- **Remove unnecessary context**: Trim old history during polling
- **Staged processing**: Split large tasks into multiple smaller steps
- **Route to Batch API**: Send non-urgent large-scale work to Batch API

```python
def estimate_cost(input_tokens: int, output_tokens: int, model: str = "gemini-2.5-pro") -> float:
```

## Frequently Asked Questions

**Q: What polling frequency should I use?**

A: Start with 5-second intervals and use exponential backoff up to 30 seconds. Always set a maximum wait time (typically 30 minutes) to prevent infinite loops.

**Q: Are webhooks supported for completion notifications?**

A: Currently, Interactions API only supports polling. Webhook functionality is in development — check official documentation regularly.

**Q: What if the client crashes during Background Execution?**

A: Save the `interaction_id` and resume polling from another client later. State management preserves conversation context.

**Q: Is Background Execution only for Deep Research?**

A: No. Any task requiring multiple tool calls, complex reasoning, or database queries benefits from Background Execution if it takes more than a few seconds.

**Q: Can I run multiple Background Tasks simultaneously?**

A: Yes. Manage multiple `interaction_id` values and poll them concurrently for better throughput.
