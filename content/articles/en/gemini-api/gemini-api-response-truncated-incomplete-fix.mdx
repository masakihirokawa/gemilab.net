You ask Gemini to write a script, and it stops halfway through — no error, no warning, just silence. This is one of the most common frustrations when starting with the Gemini API, and the fix is usually simpler than it looks once you know where to check.

This guide walks through the three main reasons responses get truncated, with working Python code for each fix. By the end, you'll have a reliable diagnostic flow you can use whenever a response looks incomplete.

## Three Reasons Responses Get Cut Off

Incomplete responses from the Gemini API almost always fall into one of these categories:

**1. `max_output_tokens` limit reached** — the most common cause by far  
**2. Safety filter triggered** — the response was blocked mid-generation  
**3. Streaming implementation issue** — chunks are being dropped or the loop exits too early  

The `finish_reason` field tells you which one you're dealing with, so that's always the first thing to check.

## Always Check finish_reason First

The `finish_reason` field on each candidate response tells you exactly why generation stopped. Make a habit of logging this value in development — it will save you a lot of head-scratching.

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro")

response = model.generate_content(
    "Write a Python web scraper with detailed explanations for each step."
)

# Always inspect finish_reason
for candidate in response.candidates:
    reason = candidate.finish_reason.name if hasattr(candidate.finish_reason, 'name') else str(candidate.finish_reason)
    print(f"finish_reason: {reason}")
    print(f"output tokens used: {response.usage_metadata.candidates_token_count}")
    print(f"total tokens: {response.usage_metadata.total_token_count}")
```

Here's what each value means:

- `STOP` — Normal completion; the model finished naturally
- `MAX_TOKENS` — Hit the `max_output_tokens` ceiling → **this is why responses get cut off**
- `SAFETY` — Blocked by a safety filter
- `RECITATION` — Copyrighted content detected
- `OTHER` — Unknown/unspecified reason

If you see `MAX_TOKENS`, the next section is your fix. If you see `SAFETY`, skip to Cause 2. If the `finish_reason` is `STOP` but output still looks incomplete, jump to Cause 3 — your streaming code may be dropping chunks.

## Cause 1: max_output_tokens Limit — The Most Common Culprit

When `finish_reason` is `MAX_TOKENS`, the model simply ran out of room. Without an explicit setting, the API uses a conservative default that's often too low for code generation, document drafting, or anything requiring long-form output.

### Fix A: Set max_output_tokens explicitly

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel(
    "gemini-2.5-pro",
    generation_config=genai.GenerationConfig(
        max_output_tokens=8192,  # Raise the ceiling for longer outputs
        temperature=0.7,
    )
)

response = model.generate_content(
    "Write a Python web scraper with detailed explanations for each step."
)

for candidate in response.candidates:
    reason = candidate.finish_reason.name if hasattr(candidate.finish_reason, 'name') else str(candidate.finish_reason)
    print(f"finish_reason: {reason}")

print(response.text)
```

Gemini 2.5 Pro supports up to 65,536 output tokens. For most use cases, setting `max_output_tokens` between 4,096 and 16,384 covers the typical range of long outputs without hitting API-level limits.

One practical note: higher `max_output_tokens` values don't automatically mean the model writes more. The model still stops when it judges the response to be complete. You're just raising the ceiling — the model won't hit it unless the output actually needs to be that long.

### Fix B: Split long outputs using continuation requests

For very long outputs — complete scripts, multi-section documents — requesting continuation via the chat API often produces better results than asking for everything at once. The chat history gives the model full context when you ask it to continue, so transitions between sections tend to be smoother.

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro")

chat = model.start_chat()

# First request — scope the initial output clearly
response1 = chat.send_message(
    "Write a Python web scraper. Start with imports and the core class structure only."
)
print("=== Part 1 ===")
print(response1.text)

# Inspect finish_reason before deciding whether to continue
for candidate in response1.candidates:
    reason = candidate.finish_reason.name if hasattr(candidate.finish_reason, 'name') else str(candidate.finish_reason)
    print(f"\nfinish_reason: {reason}")
    
    if reason == "MAX_TOKENS":
        print("\n=== Part 2 (continuation) ===")
        response2 = chat.send_message("Continue where you left off.")
        print(response2.text)
    elif reason == "STOP":
        print("\n✅ Complete — no continuation needed")
```

I prefer this pattern over setting extremely high `max_output_tokens` values. Scoped requests tend to produce cleaner output, and you can review each piece before requesting more. It also keeps token usage predictable.

## Cause 2: Safety Filter Triggered

When `finish_reason` is `SAFETY`, the content was flagged during generation. Here's how to get more detail on which safety category triggered it:

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro")

try:
    response = model.generate_content("Your prompt here")
    
    for candidate in response.candidates:
        reason = candidate.finish_reason.name if hasattr(candidate.finish_reason, 'name') else str(candidate.finish_reason)
        
        if reason == "SAFETY":
            print("⚠️ Blocked by safety filter")
            # Identify which category triggered the block
            for rating in candidate.safety_ratings:
                print(f"  - {rating.category.name}: {rating.probability.name}")
        else:
            print(response.text)
            
except Exception as e:
    print(f"Error: {e}")

# Check prompt_feedback too — sometimes the prompt itself is blocked
# before any response is generated
if hasattr(response, 'prompt_feedback') and response.prompt_feedback:
    print(f"Prompt feedback: {response.prompt_feedback}")
```

For technical content involving security topics, networking, or anything that might look ambiguous to a classifier, adding context to your prompt usually resolves it. Phrases like "for educational purposes," "from a defensive security perspective," or "in a sandboxed testing environment" help the model understand the intent and often pass the safety filter without any other changes.

If you're building a production application and the default safety thresholds are too restrictive for your use case, the Gemini API allows you to adjust `safety_settings` per request. That's a bigger topic — refer to the official API documentation for the full list of adjustable thresholds and their allowed ranges.

## Cause 3: Streaming Implementation Dropping Chunks

If you're using the streaming API and the output looks incomplete despite a `STOP` finish_reason, the implementation itself may be the problem. Chunks can appear to be lost if the iterator exits early or if `resolve()` is never called.

### The wrong way vs. the right way

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro")

# ❌ Common mistake: iterating without calling resolve()
def incomplete_streaming(prompt):
    response = model.generate_content(prompt, stream=True)
    for chunk in response:
        if chunk.text:
            print(chunk.text, end="")
    # After the loop, response.usage_metadata and finish_reason
    # may be empty or inaccurate — resolve() was never called

# ✅ Correct implementation: collect all chunks, then call resolve()
def proper_streaming(prompt):
    response = model.generate_content(prompt, stream=True)
    full_text = ""
    
    for chunk in response:
        if chunk.text:
            print(chunk.text, end="", flush=True)
            full_text += chunk.text
    
    # resolve() finalizes the response object — required for accurate metadata
    response.resolve()
    
    print("\n--- Stream complete ---")
    print(f"Input tokens:  {response.usage_metadata.prompt_token_count}")
    print(f"Output tokens: {response.usage_metadata.candidates_token_count}")
    print(f"Total tokens:  {response.usage_metadata.total_token_count}")
    
    for candidate in response.candidates:
        reason = candidate.finish_reason.name if hasattr(candidate.finish_reason, 'name') else str(candidate.finish_reason)
        print(f"finish_reason: {reason}")
        
        if reason == "MAX_TOKENS":
            print("⚠️ Token limit reached. Send a continuation request if needed.")
    
    return full_text

result = proper_streaming("Explain Python async/await with practical examples.")
```

Calling `response.resolve()` after the loop is the key step. Without it, the `usage_metadata` and `candidates` fields won't reflect the final state of the response — which means you can't reliably check `finish_reason` or token counts. Every streaming implementation should include this call.

## Count Tokens Before You Send

When you're not sure how much output headroom you need, counting the input tokens first gives you a useful baseline for deciding how to set `max_output_tokens`.

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_GEMINI_API_KEY")
model = genai.GenerativeModel("gemini-2.5-pro")

prompt = "Write a Python web scraper with detailed explanations for each step."

# Count input tokens before sending the request
token_count = model.count_tokens(prompt)
print(f"Input tokens: {token_count.total_tokens}")

# Set max_output_tokens based on expected output size
response = model.generate_content(
    prompt,
    generation_config=genai.GenerationConfig(
        max_output_tokens=6144,
    )
)

print(f"Output tokens used: {response.usage_metadata.candidates_token_count}")
print(f"finish_reason: {response.candidates[0].finish_reason}")
```

A rough rule of thumb: English text runs around 1–2 tokens per word, and structured output like code or JSON tends to use more tokens per visible character. If you're working with Japanese text, expect roughly 2–3 tokens per character — noticeably more than English, which affects how you size your `max_output_tokens` budget.

For high-volume applications, pre-counting tokens also helps with cost estimation before you commit to sending a large batch of requests.

## Quick Diagnostic Checklist

When a Gemini API response looks truncated, run through this in order:

**Step 1**: Check `finish_reason` on the response candidates  
**Step 2**: If `MAX_TOKENS` → increase `max_output_tokens` or switch to continuation requests  
**Step 3**: If `SAFETY` → adjust prompt framing or review safety settings  
**Step 4**: If using streaming → confirm `response.resolve()` is called after the loop  
**Step 5**: If `STOP` but still seems incomplete → use `count_tokens` to verify actual output size  

The vast majority of truncation issues are resolved by simply increasing `max_output_tokens`. Start there, then work down the list.
