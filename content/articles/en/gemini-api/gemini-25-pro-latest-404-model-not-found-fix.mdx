"The API call that worked yesterday is suddenly returning 404." That complaint is showing up a lot lately, and it almost always involves a model name ending in `-latest`. A request to `generativelanguage.googleapis.com/v1beta/models/gemini-2.5-pro-latest:generateContent` comes back with `{ "error": { "code": 404, "message": "models/gemini-2.5-pro-latest is not found..." } }`, and nothing on the client side has changed.

The cause is almost never a broken API — it's a model-naming convention that shifted between the 1.5 and 2.5 generations. This article walks through why the 404 happens, what identifier you should actually be using, and how to pin a version correctly in production code.

## What's actually happening

Gemini API accepts three kinds of model identifiers, each with different semantics.

**Fully versioned**, like `gemini-2.5-pro-001`. This points at a specific release and never drifts.

**Base name**, like `gemini-2.5-pro`. The API resolves this to "the current stable release of this model family" — which is the recommended default for 2.5.

**`-latest` alias**, like `gemini-2.5-pro-latest`. This was broadly used in the 1.5 era, but **Gemini 2.5 handles `-latest` inconsistently**. For several models the alias no longer resolves, and that's exactly the 404 people are seeing.

So the 404 isn't "the API broke". It's "the identifier you asked for isn't a recognized model name anymore."

## Find the right model name for your project

The most reliable fix is to ask the API what it will accept. Call `ListModels` with your key:

```bash
curl "https://generativelanguage.googleapis.com/v1beta/models?key=$GEMINI_API_KEY"
```

The response lists every model identifier available to this project under `models[].name`. If you see `models/gemini-2.5-pro` but not `models/gemini-2.5-pro-latest`, then the `-latest` form simply isn't valid here.

If you don't want to inspect the full list, just try the base name first — drop `-latest` — and retry. That clears the 404 in almost every case I've seen.

## Why `-latest` is problematic

`-latest` means "always the newest version", which for production is quietly dangerous: model behavior can change under you with no code change on your end. Google's own guidance for the 2.5 generation routes stable traffic through the **base name** instead, and treats the `-latest` alias as legacy.

I hit this the hard way in my own apps. Porting code from 1.5 Pro to 2.5 Pro, I swapped `1.5` → `2.5` in the model string and called it done — only to find `gemini-2.5-pro-latest` returned 404. The correct migration was to the base name, and the fix took one character change.

## How to pin versions in production

For indie apps and internal tooling, `gemini-2.5-pro` (base name) is the right default. It gets you stable-version routing without locking you to a specific build.

For regulated domains — finance, healthcare, anything that needs reproducible behavior — use a fully versioned ID like `gemini-2.5-pro-001`. You only upgrade when you're ready.

If you pin a version, schedule a periodic check against `ListModels` to catch deprecation: each model entry carries a `deprecationDate` field, and you want to migrate before it fires rather than after.

## When you can't reach `generativelanguage.googleapis.com` at all

If the failure is "request times out" rather than "404 returned", the cause is different.

The most common culprit: your key is a **Vertex AI** key, not a **Gemini Developer API** key. Two separate products, two separate hosts (`aiplatform.googleapis.com` vs `generativelanguage.googleapis.com`). Keys issued in AI Studio target the Developer API; `gcloud` credentials target Vertex. Mixing them up produces connection errors that look like networking issues but are actually endpoint mismatches.

The second is corporate proxies and firewalls blocking TLS to `generativelanguage.googleapis.com`. `curl -v` reveals whether the handshake completes. If it dies mid-connect, talk to your network team.

## Python / Node.js SDK gotcha

If you're using `google-generativeai` (Python) or `@google/genai` (Node.js), the model name is passed directly. Check that argument:

```python
import google.generativeai as genai
genai.configure(api_key=API_KEY)
# 404
model = genai.GenerativeModel("gemini-2.5-pro-latest")
# Works
model = genai.GenerativeModel("gemini-2.5-pro")
```

Also update the SDK: older versions had quirks resolving base names, and those have mostly been fixed in recent releases.

## The checklist when you see a 404

- Does the model name end in `-latest`? (try without it)
- Does the base name (e.g. `gemini-2.5-pro`) work?
- Have you called `ListModels` to see what your key actually sees?
- Is the key a Developer API key or a Vertex AI key?
- On a corporate network, does `generativelanguage.googleapis.com` resolve and connect?

Run through these five in order and most Gemini API 404s are solved in minutes. Standardize production code on either base names or pinned versions, and the problem stops surfacing when models roll forward.
