"I spent an hour tuning this prompt inside Google AI Studio. It worked every single time. Then I copied the snippet into my project and it started returning 404." This is probably the single most common question I get from people starting with the Gemini API. I've been there myself — even copy-pasting from Studio's `Get code` button, my first call came back with a mysterious `model not found`.

The good news is that "works in Studio, breaks on the API" almost always falls into one of a handful of patterns. Once you know the diagnosis path, you can usually isolate the cause in a few minutes. This guide walks through the checks I actually run in the order I run them, based on real debugging sessions.

## Why Studio and the raw API behave differently

It helps to start from the right mental model: Studio and the API don't call the model in the exact same way. They share the same model names, but Studio hides a lot of defaults and guardrails that you have to supply explicitly when calling `generativelanguage.googleapis.com` yourself.

Studio runs inside your logged-in Google session and can sometimes expose preview or internal-only models. Your API key, on the other hand, is bound to a specific Google Cloud project and can only reach the GA models enabled for that project. Defaults for `temperature`, `topP`, `maxOutputTokens`, system instructions, and safety settings are all populated for you by the Studio UI — your code has to pass them in or inherit the SDK defaults, which are not always the same.

In short: **"it ran in Studio" does not imply "it will run with no extra configuration in code."** Holding that assumption up front is what keeps the rest of the debugging short.

## Start here: diff your code against Studio's "Get code"

Before you change anything, open Studio, select your working prompt, and click `Get code` in the top right. Studio can export a working Python, Node.js, or cURL snippet. Pick the one that matches your implementation language and use it as the reference.

Then compare four fields against your own code:

- **Model name**: is the string exactly `gemini-2.5-pro` (or whatever Studio shows)?
- **System instructions**: is the exact same text being passed through?
- **generationConfig**: do `temperature`, `topP`, and `maxOutputTokens` match the values in Studio's right-hand sidebar?
- **safetySettings**: if you relaxed anything (e.g. `BLOCK_NONE`), is that being sent from code too?

Don't touch your higher-level application logic until those four lines up. In my experience, about 70–80% of "works in Studio" cases dissolve at this step.

## Pattern 1: The model name looks right but isn't

The most common root cause is a subtle mismatch in the model ID. These three look nearly identical and get confused constantly:

- `gemini-2.5-pro` — the stable GA model available through your API key
- `gemini-2.5-pro-latest` — an alias that tracks the newest build (not always available in every region)
- `gemini-2.5-pro-preview` — preview builds, often visible only inside Studio

Studio sometimes marks preview models with a small `(preview)` badge that's easy to miss when copying. If you see `model not found`, the best first move is to fall back to the stable GA ID. I cover the family of naming issues in more depth in [Diagnosing "model not found" errors on the Gemini API](/articles/gemini-api/gemini-api-model-not-found-error-fix-2026) — worth a read if the problem keeps moving.

One more thing: the set of callable models differs between the direct Gemini API, Vertex AI, and Gemini CLI. If the error reads `models/... is not found for API version v1beta`, the culprit may be the API version (`v1beta` vs `v1`) rather than the model itself.

```python
# ❌ Copied straight from Studio — still pointing at a preview build
from google import genai
client = genai.Client(api_key="YOUR_API_KEY")
res = client.models.generate_content(
    model="gemini-2.5-pro-preview-01-15",  # Preview often isn't reachable from the API
    contents="Summarize today's news",
)

# ✅ Switch to the stable GA model that your API key can actually reach
res = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="Summarize today's news",
)
print(res.text)
# Expected output: a short news summary
```

## Pattern 2: Wrong project, wrong key, wrong region

The second big bucket is authentication. Studio runs inside your browser session, so it masks a surprising amount of project-level misconfiguration. It is perfectly possible to have an API key that points to a different project, one where the Generative Language API was never enabled at all.

Walk this checklist:

- In Studio, open `Get API key` and confirm the key you're using in code lives under the same project as your Studio session.
- Head to Google Cloud Console, pick that project, and confirm **Generative Language API** appears under `APIs & Services` → `Enabled APIs`.
- If you're on a Workspace account, ask IT whether admin-level policies are restricting Gemini API access.

Also remember that some features roll out on a regional schedule. If the error you see is `PERMISSION_DENIED` or `FAILED_PRECONDITION`, it's usually a project or region problem rather than a prompt problem. For a deeper walkthrough of auth-related failures, [Gemini API authentication error solutions](/articles/gemini-api/gemini-api-authentication-error-solutions) is a good companion read.

## Pattern 3: Empty response, no error — the silent Safety Filter

Here is the most frustrating variant: no exception, no 4xx response, but `response.text` comes back as an empty string. Ninety percent of the time this is the Safety Filter blocking the output and the SDK quietly returning an empty candidate instead of raising.

Studio tends to ship with slightly looser filter defaults for some categories, while direct API calls default to moderate-or-stricter thresholds. The same prompt can therefore cross different lines in the two environments. The fastest fix is to make the filter settings explicit and always log both `prompt_feedback` and the candidate's `finish_reason`.

```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_API_KEY")

res = client.models.generate_content(
    model="gemini-2.5-pro",
    contents="Write the opening of a noir thriller with mild violence",
    config=types.GenerateContentConfig(
        safety_settings=[
            types.SafetySetting(
                category="HARM_CATEGORY_DANGEROUS_CONTENT",
                threshold="BLOCK_ONLY_HIGH",
            ),
        ],
    ),
)

# Two fields to print whenever you see an empty response
print("finish_reason:", res.candidates[0].finish_reason)
print("safety_ratings:", res.candidates[0].safety_ratings)
print("text:", res.text or "(blocked)")
```

A `finish_reason` of `SAFETY` points at the Safety Filter, `MAX_TOKENS` means you hit the output cap, and `OTHER` usually hints at Grounding or Function Calling paths. For more granular tuning guidance, [Fixing blocked responses from the Gemini API Safety Filter](/articles/gemini-api/gemini-api-safety-filter-blocked-response-fix) covers the thresholds in detail.

## Closing the loop: reproduce the failure in Studio

If none of the above lands, my go-to move is to flip the direction of the comparison. Instead of trying to make the API match Studio, push Studio to reproduce the *failure*. You bisect the configuration space until Studio also breaks.

- Open a fresh Studio session with the same model and prompt.
- Start matching your code's configuration one field at a time: system instructions, `temperature`, `safetySettings`, tool configs.
- The moment Studio returns an empty response or errors, the last change you made is the culprit.

This is also the reproduction path support engineers will ask you to run anyway, so documenting it pays off twice. It cleanly separates "this is an API-only bug" from "this is a prompt-design issue that just happened to slip through in Studio" — and once you know which, the fix is usually obvious.

A good starting point, honestly, is to revert your code to the exact output of Studio's `Get code`, get a zero-diff working call, and only then layer your application logic back in piece by piece. The extra five minutes usually saves an hour of guessing.
