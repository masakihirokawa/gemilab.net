## "Gemini API is cheap" — true, but only with discipline

The Gemini API is, in absolute terms, cheaper than Claude or OpenAI for many workloads — especially the Flash family. That's a real advantage for indie developers. But "cheap" can become "three or four times more expensive than you forecasted" if your usage patterns drift unattended. When I first launched a chat-style service on Gemini Flash, I made the elementary mistake of resending the entire conversation history on every turn. My projected $10/month became $40/month within two weeks.

This article shows the minimum viable design for **earning ~$200/month while spending ~$20/month on API costs.** This is not a $1K MRR or a $10K MRR plan. The realistic targets are *break-even* and a *modest positive margin* — that's where most indie products actually need to start.

## Start by computing per-user gross margin

Before naming a price, compute per-user cost. Skipping this is how indie SaaS lose money faster as they grow.

```
Per-user monthly cost = average daily token consumption × 30 × Gemini per-token rate
```

For Gemini 2.5 Flash, with ~10K input+output tokens per user per day, monthly per-user cost typically lands at $0.20–$0.55. At a $5/month subscription, gross profit per user is ~$4.50, with a gross margin of 85–90%.

The hidden detail that matters: **input tokens and output tokens are priced very differently.** As of writing, Gemini 2.5 Flash charges around $0.30 per million input tokens and around $2.50 per million output tokens — roughly an 8× ratio. **Designing prompts to keep outputs short** is the single most impactful cost optimization you can make.

## Exploit the Free Tier hard for the first three months

The Gemini API's most underrated weapon for indie developers is its generous Free Tier. As of April 2026, Gemini 2.5 Flash Lite offers 15 requests per minute and 1,500 requests per day at no cost.

The shortest path to break-even is to **architect the first three months entirely inside the Free Tier**, on purpose. Concretely:

First, **fix model selection to Flash Lite at launch.** Flash Lite trades top-end quality for latency and cost, but for text summarization, classification, tag extraction, and short Q&A, the quality is more than sufficient.

Second, **cap each user at 5 requests per day.** 1,500 requests/day ÷ 5 = 300 users on the Free Tier. For a $200/month target ($5 × 40 active subscribers), almost any indie developer stays inside Free Tier limits during the early months.

Third, **batch periodic work to once per day, globally.** Features like a daily news digest don't need a per-user request. Run one job per day, generate the content once, and serve the result to all users.

## Three patterns that prevent cost blowups

Even after you outgrow the Free Tier, three patterns will keep your bill near $20/month for a long time.

### Pattern 1 — Context Caching

The Gemini API supports Context Caching, which charges roughly a quarter of the standard per-token rate for cached input. For chatbots with a fixed system prompt, switching to cached system prompts cuts cost in half in practice.

```typescript
import { GoogleGenAI } from "@google/genai";

const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY });

const cache = await ai.caches.create({
  model: "gemini-2.5-flash",
  contents: longSystemPrompt,
  ttl: "3600s",
});

const response = await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: userMessage,
  cachedContent: cache.name,
});
```

### Pattern 2 — Hard cap on `maxOutputTokens`

Without an explicit `maxOutputTokens`, Gemini will sometimes return verbose responses that quietly inflate cost. Set an explicit cap whenever output length is predictable.

```typescript
const response = await ai.models.generateContent({
  model: "gemini-2.5-flash-lite",
  contents: prompt,
  config: { maxOutputTokens: 256 },
});
```

256 tokens is roughly 180 words of English or 180–200 characters of Japanese — plenty for summaries and short answers.

### Pattern 3 — Per-user daily token cap

Even on a paid plan, a single heavy user can consume the bulk of your monthly budget. In my own services, I cap any plan at 50,000 tokens per day per user.

```typescript
const DAILY_TOKEN_CAP = 50_000;

async function checkAndIncrement(userId: string, tokens: number) {
  const today = new Date().toISOString().slice(0, 10);
  const key = `quota:${userId}:${today}`;
  const current = parseInt((await kv.get(key)) ?? "0", 10);
  if (current + tokens > DAILY_TOKEN_CAP) {
    throw new Error("Daily quota exceeded");
  }
  await kv.put(key, String(current + tokens), { expirationTtl: 60 * 60 * 26 });
}
```

## The shortest path to ~$200/month

For a Gemini-API-based indie product, the three realistic routes to ~$200/month are:

| Route | Per-unit price | Required customers | Speed to start |
|---|---|---|---|
| Subscription ($5/mo) | $5 | 40 active subs | Medium |
| One-time purchase ($19) | $19 | ~10 sales/month | High |
| Add-on for existing users | 5% conversion | 300 free users × 5% × $5 | Highest |

My recommendation: if you already run any free app or service, do **option 3 (add an AI feature for existing users)**. If you're starting from absolute zero, do **option 2 (one-time purchase)**. Subscriptions feel attractive but have high operational drag, and the distance to your first $200 feels longer than it should.

## Decide what *not* to do

The single most underrated lever for an indie developer trying to break even is the list of things you decide *not* to build. For the first three months on Gemini API, skip all of these:

- A real authentication system (Stripe Checkout email + cookie is enough)
- Multi-tenant design (consumer-facing single-tenant is fine)
- Streaming responses (non-streaming is fine on Free Tier)
- Localization beyond your two strongest languages
- Native mobile apps (web-first works)

Each of these is a real engineering project. None of them need to exist before your first $200/month in revenue. Add them only after the revenue is reliable.
