If you have run the Gemini API in production for a while, you have probably caught yourself squinting at a dashboard and asking: why is positive feedback dropping this week? Why do support tickets feel subtly different in tone? And when you dig into the logs, the answer often comes back as: "we tweaked the prompt three weeks ago, but the model is still `gemini-2.5-pro`". Nothing in that sentence tells you which part of the change hurt quality. I ran into this myself on a personal chat app where I shortened a system instruction to cut tokens, and certain users got visibly worse responses for half a day before I could roll back.

This article lays out how to avoid that trap — a prompt versioning and A/B testing setup built with nothing but Firestore and the Gemini API, presented as working code. You do not need a managed evaluation platform; a solo developer or a small team can absolutely run this.

## Can You Explain Why User Satisfaction Dropped Yesterday?

Prompt changes almost always have a good reason. You want shorter answers. You want Japanese keigo consistency. You want higher tool-call success rates. You want to move from Pro to Flash to save cost. All reasonable. But if you roll those changes into production without measuring whether each change actually did what you hoped, quality drifts quietly. The hard part is that chat-style workloads rarely have a single correct answer, so unit tests do not catch regressions. The code does not error. It just starts disappointing users in ways you cannot grep for.

What you need is a way to treat every prompt as a named, immutable version, run multiple versions side by side against real traffic, and graduate the winner only when the numbers say so.

## Three Reasons Prompts Need a First-Class "Version" Concept

### Reason 1: Silent Model-Side Updates

Hosted LLMs occasionally update their underlying checkpoint. You are still calling `gemini-2.5-pro`, but a particular week's responses come out longer, or more assertive, or just slightly different in tone. That is normal. What matters is that your metrics should be able to tell the difference between "the prompt changed" and "the model changed", and the only way to do that is to log with enough granularity that you can slice by both dimensions.

### Reason 2: Context Bloat and the Slow-Burn Quality Decline

Most production System Instructions grow. You add "also handle this edge case", then "and be careful about that one", and six months later you have a multi-thousand-token monster. Even with a 2M context window, instructions start to compete with each other and the model begins silently reprioritizing. Without versioning, you cannot tell which of those additions is carrying its weight and which is actively making things worse.

### Reason 3: Regressions From Parallel Edits (Even Solo)

Even as a one-person team, you will forget last week's reasoning. In [a Gemini 2.5 Pro system instructions operations guide](/en/articles/gemini-api/gemini-25-pro-system-instructions-mastery-guide) I made the case that System Instructions should be stored in a way that makes "who wrote this, when, and why" answerable months later. A Git commit message does not capture the relationship between a UI string and a prompt clause. A dedicated registry does.

## The Architecture We Are Building

The finished system has four parts. We will build them one at a time.

- **Prompt Registry**: a small Firestore-backed store where each prompt variant lives as a document. A `status` field decides whether it serves traffic or sits in the waiting room.
- **Traffic Splitter**: a deterministic function that hashes user ID and `prompt_key` to pick a variant. The same user always gets the same variant, so comparisons do not decay into noise.
- **Metrics Collector**: a thin wrapper around the Gemini client that guarantees every call is logged with variant ID, latency, token counts, and any error class.
- **Evaluation Loop**: a daily or weekly batch that samples production logs, rescores them with LLM-as-judge, and reports per-variant means so you can catch regressions.

The design decision that matters most is treating `variant = prompt + model + sampling parameters` as a single atomic unit. Versioning the prompt alone is useless if someone can flip the model under you.

## Step 1: A Prompt Registry in Firestore

Put a `prompt_variants` collection in Firestore and wrap it in a thin Python class. A 60-second cache TTL is plenty — prompt edits do not happen many times per second.

```python
# prompt_registry.py
# Store multiple prompt variants as Firestore documents
from google.cloud import firestore
from dataclasses import dataclass
import time

@dataclass
class PromptVariant:
    variant_id: str         # e.g. v3 / v3-rewrite
    model: str              # e.g. gemini-2.5-pro / gemini-2.5-flash
    system_instruction: str
    temperature: float
    thinking_budget: int    # 0 disables thinking
    weight: int             # traffic share (integer; only active variants count)
    status: str             # active / shadow / archived

class PromptRegistry:
    def __init__(self, collection: str = "prompt_variants"):
        self._db = firestore.Client()
        self._collection = collection
        self._cache: dict[str, list[PromptVariant]] = {}
        self._cache_refreshed_at = 0.0
        self._cache_ttl = 60  # seconds

    def _refresh(self, prompt_key: str) -> None:
        docs = (self._db.collection(self._collection)
                .where("prompt_key", "==", prompt_key)
                .where("status", "in", ["active", "shadow"])
                .stream())
        self._cache[prompt_key] = [PromptVariant(**doc.to_dict()) for doc in docs]
        self._cache_refreshed_at = time.time()

    def get_variants(self, prompt_key: str) -> list[PromptVariant]:
        if (time.time() - self._cache_refreshed_at) > self._cache_ttl:
            self._refresh(prompt_key)
        if prompt_key not in self._cache or not self._cache[prompt_key]:
            raise RuntimeError(f"prompt_key not found or empty: {prompt_key}")
        return self._cache[prompt_key]

# Expected behavior:
#   registry = PromptRegistry()
#   variants = registry.get_variants("chat_reply")
#   -> [PromptVariant(variant_id=v3, weight=80, status=active, ...),
#       PromptVariant(variant_id=v3-rewrite, weight=20, status=active, ...)]
```

Notice the two non-archived states: `active` participates in user traffic, while `shadow` does not but is still scored offline. Having a "waiting room" lets you build confidence about a candidate variant before you risk any user impact.

## Step 2: Deterministic Traffic Splitting

The single most important property of an A/B split is that the same user sees the same variant every time. If you randomize on every request, the same user asking the same question three times sees three different answers — both your UX and your comparison collapse. Python's built-in `hash()` is salted per process, which means it is useless for determinism. Use a real hash like SHA-256.

```python
# traffic_split.py
# Hash (user_id, prompt_key) with SHA-256 and carve out weight-proportional buckets
import hashlib
from typing import Iterable
from prompt_registry import PromptVariant

def pick_variant(user_id: str, prompt_key: str,
                 variants: Iterable[PromptVariant]) -> PromptVariant:
    actives = [v for v in variants if v.status == "active"]
    if not actives:
        raise RuntimeError("No active variants configured")
    total = sum(v.weight for v in actives)
    if total <= 0:
        raise ValueError("Sum of weights must be positive")

    seed = f"{prompt_key}:{user_id}".encode()
    bucket = int(hashlib.sha256(seed).hexdigest(), 16) % total

    cumulative = 0
    for v in actives:
        cumulative += v.weight
        if bucket < cumulative:
            return v
    return actives[-1]  # fallback for floating point edge cases

# Expected behavior:
#   The same user_id + prompt_key yields the same variant across process restarts
#   Aggregated over many users, distribution matches the weight ratio (e.g. 80/20)
```

`prompt_key` is part of the seed deliberately. Without it, the same user would fall into the same side of every A/B test in the system — "chat_reply" and "summary" would both put user 1234 into the `v3-rewrite` bucket, and you would accidentally correlate the two experiments. Mixing `prompt_key` into the hash keeps each task independent.

## Step 3: Push All Metrics Through One Thin Wrapper

If "remember to log" lives scattered across your codebase, someone will forget it. Route all Gemini calls through one wrapper that always logs variant ID, latency, and tokens. This pairs nicely with the metrics schema discussed in [a Gemini API production observability setup](/en/articles/gemini-api/gemini-api-observability-production-monitoring) — your dashboards can consume either source interchangeably.

```python
# gemini_client.py
# Every Gemini call is variant-aware and produces exactly one log row
import time, uuid
from google import genai
from google.cloud import firestore
from prompt_registry import PromptRegistry
from traffic_split import pick_variant

_client = genai.Client()
_registry = PromptRegistry()
_logs = firestore.Client().collection("prompt_logs")

def generate(user_id: str, prompt_key: str, user_input: str) -> tuple[str, str]:
    variants = _registry.get_variants(prompt_key)
    variant = pick_variant(user_id, prompt_key, variants)

    log_id = uuid.uuid4().hex
    started = time.monotonic()
    error = None
    usage = {}
    text = ""
    try:
        resp = _client.models.generate_content(
            model=variant.model,
            contents=user_input,
            config={
                "system_instruction": variant.system_instruction,
                "temperature": variant.temperature,
                "thinking_config": {"thinking_budget": variant.thinking_budget},
            },
        )
        text = resp.text or ""
        um = resp.usage_metadata
        if um:
            usage = {
                "prompt_tokens": um.prompt_token_count,
                "output_tokens": um.candidates_token_count,
                "cached_tokens": getattr(um, "cached_content_token_count", 0) or 0,
            }
    except Exception as e:
        # Keep the class name and a short message; route full stack traces elsewhere
        error = f"{type(e).__name__}: {str(e)[:200]}"
        raise
    finally:
        # Always emit a log row. An error-rate spike is the first regression signal.
        _logs.document(log_id).set({
            "log_id": log_id,
            "user_id": user_id,
            "prompt_key": prompt_key,
            "variant_id": variant.variant_id,
            "model": variant.model,
            "user_input": user_input,
            "output_text": text,
            "latency_ms": int((time.monotonic() - started) * 1000),
            "error": error,
            "usage": usage,
            "created_at": firestore.SERVER_TIMESTAMP,
        })
    return text, log_id

# Expected behavior:
#   text, log_id = generate("u_1234", "chat_reply", "Reply briefly in English.")
#   A single document appears in prompt_logs with variant_id, latency_ms, tokens
```

Using `finally` to write the log is deliberate. Error cases are exactly the rows you need to detect "did this new variant just start throwing more 500s than the old one", so do not conditionally skip them.

## Step 4: Regression Detection Through Offline Evaluation

With logs accumulating, you sample daily or weekly and score each variant. Human scoring does not scale, so you score with Gemini too — but **use a stronger model to judge than the one that produced the response**. Self-evaluation with the same checkpoint is known to be biased toward the status quo. If the production model is `gemini-2.5-flash`, score with `gemini-2.5-pro`.

```python
# eval_regression.py
# Sample production logs, LLM-as-judge, report per-variant means
import json, statistics
from google import genai
from google.cloud import firestore

_client = genai.Client()
_db = firestore.Client()

JUDGE_SYSTEM = """You are a strict evaluator of response quality.
Score the response on integers 1-5 (5 is best) along these axes:
- accuracy: factually correct
- helpfulness: serves the user's actual goal
- conciseness: not padded
Output only JSON with exactly these three keys. No prose."""

def judge(user_input: str, output_text: str) -> dict:
    resp = _client.models.generate_content(
        model="gemini-2.5-pro",
        contents=f"[QUESTION]\n{user_input}\n\n[RESPONSE]\n{output_text}",
        config={
            "system_instruction": JUDGE_SYSTEM,
            "response_mime_type": "application/json",
            "temperature": 0.0,
        },
    )
    try:
        return json.loads(resp.text)
    except (json.JSONDecodeError, TypeError):
        return {"accuracy": 0, "helpfulness": 0, "conciseness": 0, "parse_error": True}

def evaluate(prompt_key: str, sample: int = 200) -> dict:
    logs = (_db.collection("prompt_logs")
            .where("prompt_key", "==", prompt_key)
            .order_by("created_at", direction=firestore.Query.DESCENDING)
            .limit(sample)
            .stream())
    buckets: dict[str, list[int]] = {}
    for log in logs:
        d = log.to_dict()
        if d.get("error") or not d.get("output_text"):
            continue
        score = judge(d["user_input"], d["output_text"])
        if score.get("parse_error"):
            continue
        buckets.setdefault(d["variant_id"], []).append(score["accuracy"])

    return {
        vid: {
            "n": len(s),
            "mean": round(statistics.mean(s), 2),
            "stdev": round(statistics.stdev(s), 2) if len(s) > 1 else 0.0,
        }
        for vid, s in buckets.items() if s
    }

# Expected output:
#   evaluate("chat_reply")
#   -> {"v3": {"n": 160, "mean": 4.21, "stdev": 0.58},
#       "v3-rewrite": {"n": 40, "mean": 3.67, "stdev": 0.81}}
#   If the new variant's mean drops materially, archive it and roll back.
```

If you want a sharper call than "the new mean is lower", compute the standard error of the difference with $\sqrt{s_a^2/n_a + s_b^2/n_b}$ and require the mean gap to be at least twice that. That is not a formal t-test, but it is a robust rule of thumb for shipping decisions. For a more disciplined evaluation dataset, [a Gemini API prompt evaluation pipeline guide](/en/articles/gemini-api/gemini-api-prompt-evaluation-optimization-pipeline) walks through how to curate fixtures that stay stable across evaluation runs.

## Pitfalls That Have Ruined Real Experiments

Getting the plumbing right is not enough. Here are four configuration mistakes that have ruined experiments for me — worth internalizing before you ship this.

### Pitfall 1: Versioning Prompt and Model Through Separate Flags

One week I had a prompt flag serving `v3-rewrite` to 20% and, independently, a model flag sending 50% of all traffic to Flash. The samples for `v3-rewrite` ended up split across Flash and Pro, and the scores were noisier than I could explain. Collapsing `variant = prompt + model + sampling` into a single document makes that kind of accidental multi-factor experiment physically impossible.

### Pitfall 2: Calling the Winner Before the Sample Is Big Enough

Twenty log rows with a 0.3-point advantage to the new variant feels convincing for about thirty seconds, and then you ship it, and then production regresses. My team-of-one rule is **at least 200 total samples and at least 50 per arm** before any decision. Gemini responses are stochastic; widened confidence intervals mock you if you underestimate them.

### Pitfall 3: Cache Strategy Colliding With A/B Splitting

If you are using [Gemini API context caching for cost control](/en/articles/gemini-api/gemini-api-context-caching-cost-optimization), each variant gets its own cache. Hit rate drops proportionally to the number of variants, and your cost spikes. Keep the shared portion of System Instructions in the cached block and push per-variant differences into the per-request contents, or simply keep shadow variants below 10-20% weight so cache pressure stays manageable.

### Pitfall 4: Ignoring Temporal and Language Skew Across Users

Hashing only on user ID bakes in whatever temporal or language distribution your traffic happens to have. You might discover that the "winner" of the experiment really just saw weekend Japanese users while the loser saw weekday English users. Mix `lang:ja` or a region marker into the `prompt_key` used for hashing and evaluate per language — the comparison gets much cleaner and you stop debugging phantom differences.

## The Minimum Viable Path to Get This Running

Building all four parts at once feels like a project. It is not necessary. **Start by shipping Step 3 alone, with `variant_id="default"` hardcoded**, and let logs accumulate for a week. You will immediately get a latency distribution, a token-consumption profile, and an error-rate baseline — enough raw material to decide which part of the pipeline to tighten first. The registry and traffic splitter can land when the next candidate variant actually shows up.

## A Deeper Look at How the Pieces Fit Together at Runtime

It helps to mentally walk through a single request once, because the order of operations matters more than the code length suggests. When a user hits your chat endpoint, the wrapper first consults the Prompt Registry for the `prompt_key` in play — the registry returns a list of candidate variants. The traffic splitter hashes the user ID together with the `prompt_key` and picks one variant deterministically. From that point on, every piece of information attached to the log row is known up front: the variant ID, the model, the temperature, the thinking budget. No matter what the model returns, you already know which experimental arm the row belongs to.

The Gemini API call then fires. Whether it succeeds or fails, the wrapper's `finally` block writes one log document. This single-write-per-call guarantee is the property that makes downstream analysis honest. If you ever find yourself wanting to log selectively — "only successful responses" or "only ones longer than 100 tokens" — stop. Selective logging turns the downstream metrics into a fun-house mirror, because the very responses that failed are the ones you most want to study.

At the end of a day or a week, the evaluation job reads a window of those logs, rescores them with the judge model, and aggregates by variant ID. Mean, standard deviation, and sample count per variant give you the signals to decide whether to promote, extend, or archive a candidate. Everything else — dashboards, rollback playbooks, user-facing feature flags — can be layered on top of this core without changing its contract.

## Why Firestore Is a Good Fit For This Specific Problem

You might reasonably ask whether Firestore is the right choice. For prompt registries in particular, it is — and knowing why helps you avoid reaching for heavier tools. Prompts are read far more than they are written. A single prompt variant might be read millions of times across requests while only being written by a human a handful of times. Firestore's document model fits this naturally: variants are small, self-contained blobs with a clear schema, and per-document reads are fast enough that the 60-second TTL cache is plenty.

The log data has the opposite profile — write-heavy, read-rarely, append-only — but Firestore handles this category too as long as you do not index every field. Index only `prompt_key`, `variant_id`, and `created_at`, and keep fields like `user_input` and `output_text` unindexed. Your write amplification stays low, and query costs remain predictable. If your traffic outgrows Firestore's write rate for logs, migrate the log sink to BigQuery via a Cloud Function trigger — the registry can comfortably stay in Firestore indefinitely.

One subtle trap: Firestore bills by document reads, so if the `get_variants` call happens inside every single request without a cache, costs add up fast. The 60-second in-process cache in the reference implementation is not a premature optimization. It is the thing that makes the design viable at scale.

## Rolling Out A Variant: The Promotion Lifecycle I Use

There is a lifecycle each variant goes through before it owns 100% of traffic. Understanding it prevents you from ad-hoc promoting a variant because "the numbers looked pretty good this afternoon".

First, a new variant enters the registry with `status: "shadow"` and `weight: 0`. No real user ever sees it. A separate batch job takes recent production inputs, replays them against the shadow variant, and feeds the output to the judge. This gives you an apples-to-apples comparison on real inputs without risking user experience. If the shadow variant scores within a credible range of the current champion, it graduates.

Second, the variant is promoted to `status: "active"` but capped at a small `weight`, typically 10% in my setup. Real users see it, but the blast radius of a bad variant is contained. I let this run for at least 48 hours, or until I have 200+ samples on the new arm, whichever comes later. Traffic spikes and weekend-vs-weekday behavior both distort short windows, so patience during this phase pays for itself.

Third, if the per-variant mean and error rate look healthy, I split to 50/50 for another period. This phase is where subtle regressions hiding in the long tail of user behavior tend to surface. Once the 50/50 phase also looks clean, the new variant takes 100% weight and the old one moves to `status: "archived"`.

Finally — and this part is easy to forget — I keep the archived variant's document around. It is not free to reconstruct "what exactly were we running three months ago?" by digging through Git commits, especially when a SaaS customer emails about a behavior change. Archived documents are cheap and they are the only reliable forensic artifact for past production behavior.

## Building The Operational Dashboard

Code is only half of the system; the other half is the dashboard you look at every morning. The three charts that have given me the most signal are: per-variant error rate over time, per-variant P50/P95 latency, and per-variant token distribution. Response quality is crucial but slower-moving — you typically look at it weekly, not hourly. Error rate and latency, by contrast, are your leading indicators that a new variant has broken something.

Wire these to whatever dashboard tool you already use — Cloud Monitoring, Grafana Cloud, Looker Studio, or a simple homegrown Firestore aggregation. The tool matters less than the habit. I keep a browser tab open to this dashboard during any new variant rollout and refresh it before I step away from the desk. Seeing error rate double on the new arm two minutes after a rollout has saved me more than once.

For users on Cloud Run in particular, pairing this system with structured logging makes a big difference. Emit each log document as a structured Cloud Logging entry in parallel, so you can use Cloud Logging's analytics while keeping Firestore as the system of record. Duplication here is a feature, not a cost concern, because log volume is small relative to the rest of your bill.

## What To Do When The Evaluation Disagrees With User Feedback

Occasionally the judge model will declare variant A the winner, and user feedback channels will tell you variant B is better. This happens enough that it needs a playbook. The first thing to check is whether the judge's criteria actually match your product's goals. A judge scoring strictly on factual accuracy will miss the fact that users prefer warmer, more conversational responses for a mental-wellness app. Rewrite the judge's system instruction, rerun the evaluation, and see if the disagreement persists.

The second thing to check is sample composition. The judge sees whatever the sampling step pulled from Firestore. If that happens to be biased toward a particular user cohort — say, power users who tend to ask harder questions — the scores do not generalize. Add stratified sampling across cohorts and rerun.

If the disagreement still stands after both corrections, trust the user feedback. Judges are scaffolding; users are the ground truth. Archive the "winning" variant and go back to the drawing board on the prompt itself. You will learn something important about the gap between your evaluation rubric and your actual product values.

## A Few Extensions Worth Adopting Early

Once the core four components are running, a few small additions pay off disproportionately. The first is capturing the raw request ID returned by the Gemini API. The Gemini client provides an identifier on the response that lets Google Cloud Support correlate an outlier you are investigating with their server-side logs. Adding one more field to the log schema costs nothing and saves hours during the odd incident.

The second is recording latency breakdown. The `latency_ms` captured in the wrapper covers the whole call, but during thinking-mode debugging you also want time-to-first-token, time-to-last-token, and server-side thinking time separately. The Gemini SDK exposes these through streaming callbacks; piping them into the log document gives you the power to debug whether a new variant is slower because of thinking depth or because of output length.

The third is versioning the judge itself. Yes, you should. If you change the judge's rubric halfway through a quarter, you are no longer comparing variants against a stable baseline — you are comparing them against a moving target. Keep the judge under the same registry discipline: a variant for the judge, with a status field, and a change log.

## Why This Matters More For Solo And Small-Team Developers

Large AI labs can afford dedicated evaluation teams. Small teams and solo developers cannot. That imbalance sometimes leads to the assumption that serious evaluation is out of reach for independent builders, and therefore they should just ship changes and hope for the best. I believe the opposite. Small teams can ship this entire system in a weekend, and the return on investment is enormous because there is no one else watching quality for you. Every regression that gets caught before it reaches users is one less apology email, one less negative review, one less churn event.

The components described here are intentionally modest. They are designed to fit on a single Cloud Run service or even a single local script, with Firestore as the only external dependency. You are not committing to a data lake, a feature store, or a Kubernetes operator. You are committing to a discipline: never change a prompt without a way to measure whether the change worked. Once that discipline is in place, your product's quality drifts upward over time instead of sideways.

If you are the kind of builder who iterates fast and cares about users, this kind of infrastructure rewards you twice — once because the numbers tell you what to change next, and a second time because they give you the confidence to change things at all.
