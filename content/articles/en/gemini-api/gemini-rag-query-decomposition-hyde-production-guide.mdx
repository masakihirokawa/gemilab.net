If you've shipped a RAG system and noticed that the moment a user asks something even slightly abstract, the answers go off the rails — you are not alone. The first wall I hit after launching a search assistant on top of Gemini was exactly this: documents that share surface keywords kept rising to the top, while the documents that actually contained the answer sat quietly in the long tail. Swapping embedding models or bumping dimensions only nudges the ceiling. Past a certain point, single-shot retrieval just plateaus.

This article walks through two techniques that pushed past that plateau for me — **query decomposition** and **HyDE (Hypothetical Document Embeddings)** — and shows how to combine them on the Gemini API for production. Rather than parading buzzwords, we will look at *why* the order of operations matters, *where* it tends to break, and *how* to keep latency and cost in check, all alongside code you can run. By the end, you should have a clear mental model for when to reach for each technique, when to skip it, and how to evaluate whether the added complexity pays for itself in your domain.

## Why single-query RAG plateaus

The fundamental problem with vector-search RAG is that the user's question and the answer-bearing document do not necessarily share a vocabulary. Imagine a user asking, "What's the penalty if I cancel the contract?" while the actual answer in the contract reads, "In the case of mid-term termination, liquidated damages will be calculated as three months of fees." Semantically these are siblings, but at the token level they barely overlap. Embeddings absorb some of that gap, but in domains heavy with jargon — legal, medical, tax, internal jargon at a particular company — similar-meaning documents are not necessarily trained to land close in vector space. The training data simply doesn't contain enough paired examples of "user-style question" and "contract-style declaration" for the model to align them.

A second problem appears the moment a question contains multiple sub-questions. "How do I add multi-currency payments with Stripe, and how should I handle the tax side?" is really two axes — payment plumbing and accounting. A single embedding for that combined query forces the retriever to choose documents that are shallow on both, instead of going deep on each. Documents that cover one axis brilliantly get knocked out by mediocre documents that name-drop both. This is the most underestimated failure mode I see in real production RAG systems, because individual user questions often look "easy" on inspection until you realize they're carrying a hidden second concern.

A third, more subtle issue is **the asymmetry between question framing and document framing**. Users ask in conversational, sometimes informal language; documents are written in formal, declarative prose. Even when keywords overlap, the surrounding context vectors land in different neighborhoods. This asymmetry compounds as your corpus grows — a small corpus might paper over it, but as your knowledge base scales past a few thousand documents, the noise floor rises and the right answer gets buried.

Query decomposition and HyDE attack the plateau from two different directions. One reshapes the query so each retrieval call is easier to satisfy. The other rewrites the query into something that looks like an answer document. Used together, they widen recall in a way that single-shot retrieval cannot match.

## Query decomposition: rewrite the question into searchable units

Query decomposition splits the user's question into multiple independent sub-queries. The point is *not* simple sentence splitting — the goal is to rewrite each sub-query so that on its own, it can pinpoint the answer document.

Three rules guide my decomposition prompts in production. First, look for **compound questions**. The Stripe-and-taxes example carries two distinct concerns in one sentence, and they should always be split. Second, look for **abstractions you can lower**. "I want to be more efficient" hits almost nothing; "Generate a monthly report automatically with Apps Script" hits a small, focused cluster of documents. Third, look for **prerequisites that deserve their own query**. "How do I build a fallback strategy?" benefits from also retrieving "What is a fallback strategy?" and merging the two result sets. The third rule is often skipped because it feels redundant, but in domains where users are mid-learners — knowing the term but not its full meaning — adding the prerequisite query reliably surfaces foundational documents that anchor the answer.

A fourth rule worth considering once you go past prototype: **preserve original-query lookup**. Always include the unmodified original question as one of the retrieval branches, because in some cases — short factual questions, exact-match needs — decomposition only adds noise. The original query acts as a safety net that catches retrieval failures the decomposition prompts miss.

### Decompose with Gemini structured output

Gemini 2.5 Flash with structured output is a near-perfect fit. You get the decomposed queries back as a typed object, latency is a few hundred milliseconds, and the cost stays low enough to run on every request. I've benchmarked this prompt at roughly 250 ms p50 and 600 ms p95 with Flash, which is well within budget for an interactive RAG application.

```python
# query_decomposition.py
# Role: split the user's question into independent sub-queries.
# Why bind types with Pydantic: pass the result safely to the retrieval
# pipeline downstream and detect malformed decomposition early.
import os
from pydantic import BaseModel, Field
from google import genai

class DecomposedQueries(BaseModel):
    sub_queries: list[str] = Field(
        ..., description="Independent, searchable sub-queries. Up to 4."
    )
    reasoning: str = Field(
        ..., description="A short rationale for this decomposition."
    )

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

DECOMPOSE_INSTRUCTION = """
You are a preprocessing assistant for RAG retrieval.
Rewrite the user's question into up to 4 sub-queries that are independent,
searchable, and likely to pinpoint a unique answer document.
- Replace abstract words with specific domain terms when possible.
- Each sub-query should cover exactly one concern.
- If the original question already has a single concern, return one sub-query.
"""

def decompose(query: str) -> DecomposedQueries:
    try:
        resp = client.models.generate_content(
            model="gemini-2.5-flash",
            contents=[DECOMPOSE_INSTRUCTION, f"Question: {query}"],
            config={
                "response_mime_type": "application/json",
                "response_schema": DecomposedQueries,
                "temperature": 0.0,
            },
        )
        return resp.parsed
    except Exception as e:
        # Fallback: search with the original query alone
        print(f"[decompose] fallback to single query: {e}")
        return DecomposedQueries(sub_queries=[query], reasoning="fallback")

if __name__ == "__main__":
    out = decompose("I want to enable multi-currency payments with Stripe. How do I handle taxes?")
    print(out.model_dump_json(indent=2))
```

Expected output:

```json
{
  "sub_queries": [
    "Concrete configuration steps to enable multi-currency payments in Stripe",
    "How foreign-currency revenue is treated under Japanese consumption tax and corporate tax",
    "Accounting treatment of FX gains and losses for Stripe multi-currency settlements"
  ],
  "reasoning": "The original question contained two distinct concerns: payment configuration and tax handling..."
}
```

`temperature=0.0` is intentional. You want the same question to produce the same decomposition every time, so that downstream caches still hit and your per-query cost and latency stay flat. A nondeterministic decomposition step also makes evaluation a nightmare — you can't tell whether a regression came from a code change or just from temperature variance. Pinning the temperature is the cheapest way to keep the system debuggable.

## HyDE: rewrite the question to look like the answer

HyDE (Hypothetical Document Embeddings) was famously called "a cheating idea that just works." The mechanic is simple. Instead of embedding the question directly, you ask Gemini to draft a *hypothetical answer* and embed that.

Why does this help? Because question text and answer text rarely share a vocabulary. "What is the cancellation fee?" and "Mid-term termination of this contract incurs a charge equal to three months of monthly fees" feel identical to a human, but live in slightly different neighborhoods of embedding space. HyDE lets Gemini hypothesize, "If I were writing the answer to this question, it would read like this," and then it uses that hypothetical answer as the search query, jumping directly into the answer-side cluster.

There's a second-order benefit that often gets missed: HyDE injects domain vocabulary that the question itself was missing. If a user asks "Is my password protected enough?" they don't say "key derivation function" or "salt rounds" — but a Gemini-drafted hypothetical answer about password security probably will. Those terms are exactly what your security documentation uses, and that vocabulary alignment is what bridges the gap that pure embedding distance cannot.

In my experience, HyDE shines when the domain has heavy idiomatic phrasing (legal, medical, tax), when **users ask questions but documents are written declaratively** (FAQ, contract search), and when the question is short and abstract ("How much does it cost?", "How do I do this?"). On the other hand, when the question already contains terms that match the documents word-for-word — product codes, SKUs, function names — HyDE can actually hurt by introducing noise. Branching is the safe choice, and we will revisit that.

### Implementing HyDE on Gemini

```python
# hyde_retrieval.py
# Role: generate a hypothetical answer from the query and use its embedding.
# Why Flash: HyDE output is not the final answer, just a stepping stone.
# Pro is overkill; Flash keeps latency and cost down.
import os
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

HYDE_PROMPT = """
You assist a knowledge-base retrieval system.
For the question below, write a 200-character (or less) hypothetical
answer in the declarative style typical of internal documentation.
Accuracy is not required — prioritize covering relevant vocabulary.
"""

def hyde_text(query: str) -> str:
    try:
        resp = client.models.generate_content(
            model="gemini-2.5-flash",
            contents=[HYDE_PROMPT, f"Question: {query}"],
            config={"temperature": 0.3, "max_output_tokens": 256},
        )
        return resp.text or query
    except Exception as e:
        print(f"[hyde] fallback to original query: {e}")
        return query

def embed(text: str) -> list[float]:
    resp = client.models.embed_content(
        model="gemini-embedding-001",
        contents=text,
        config=types.EmbedContentConfig(task_type="RETRIEVAL_QUERY"),
    )
    return resp.embeddings[0].values

def hyde_search(query: str, vector_store) -> list[dict]:
    # Search with both the original and HyDE-generated text, merge later
    original_vec = embed(query)
    hyde_vec = embed(hyde_text(query))
    return [
        {"source": "original", "results": vector_store.search(original_vec, k=10)},
        {"source": "hyde", "results": vector_store.search(hyde_vec, k=10)},
    ]
```

Setting `task_type="RETRIEVAL_QUERY"` matters. Gemini Embedding returns task-tuned vectors — you index documents with `RETRIEVAL_DOCUMENT` and query with `RETRIEVAL_QUERY`. Forgetting to align the task types costs a few percentage points of recall on every benchmark I've run. It's the kind of bug that you don't catch in unit tests because the system still works — it just works *worse*. Audit your indexing pipeline to confirm it uses `RETRIEVAL_DOCUMENT`, and your query path to confirm it uses `RETRIEVAL_QUERY`. For a deeper dive on the embedding side, see [Pushing Gemini RAG to production quality with embeddings + reranker](/en/articles/gemini-api/gemini-embeddings-rerank-rag-precision-production).

A note on `temperature=0.3` for HyDE generation: unlike decomposition where determinism is paramount, HyDE benefits from a small amount of variance because vocabulary diversity is the goal. Setting it too low (0.0) makes Gemini converge on the same phrasing and lose some recall benefit. Setting it too high (>0.5) introduces noise and topic drift. The 0.2–0.4 range has been the sweet spot in my benchmarks.

## Wire decomposition and HyDE in parallel, not in series

When I first built this stack, I wired it sequentially: decompose, then for each sub-query run HyDE, then search. It works, but latency adds up linearly. With four sub-queries × HyDE generation + two embedding calls + two vector searches, p95 climbed close to three seconds. Painful.

**Production demands parallelism.** In Python, that means `asyncio.gather`; in Node.js, `Promise.all`. The "HyDE generation + embedding + search" trio for each sub-query runs concurrently, and total latency drops to roughly the cost of a single branch — usually around 500 ms with Flash. Concurrency is also kind to your error-handling budget, because a slow HyDE call no longer blocks the rest of the pipeline, and a per-branch timeout (say, 800 ms) lets you degrade gracefully when one sub-query stalls.

```python
# hybrid_pipeline.py
# Role: end-to-end production pipeline — decompose, HyDE, parallel search, RRF merge.
# Why Reciprocal Rank Fusion: it merges rankings without depending on absolute
# score scales — simple, robust, and fine for production.
import asyncio
import os
from collections import defaultdict
from google import genai
from google.genai import types

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])

async def gen_hyde(query: str) -> str:
    try:
        resp = await client.aio.models.generate_content(
            model="gemini-2.5-flash",
            contents=[HYDE_PROMPT, f"Question: {query}"],
            config={"temperature": 0.3, "max_output_tokens": 256},
        )
        return resp.text or query
    except Exception:
        return query

async def aembed(text: str, task: str) -> list[float]:
    resp = await client.aio.models.embed_content(
        model="gemini-embedding-001",
        contents=text,
        config=types.EmbedContentConfig(task_type=task),
    )
    return resp.embeddings[0].values

async def search_branch(sub_query: str, vector_store) -> list[tuple[str, int]]:
    # 1) Embed and search the original sub-query.
    # 2) Generate HyDE, embed and search that.
    hyde, _ = await asyncio.gather(gen_hyde(sub_query), asyncio.sleep(0))
    orig_vec, hyde_vec = await asyncio.gather(
        aembed(sub_query, "RETRIEVAL_QUERY"),
        aembed(hyde, "RETRIEVAL_QUERY"),
    )
    orig_hits, hyde_hits = await asyncio.gather(
        vector_store.asearch(orig_vec, k=10),
        vector_store.asearch(hyde_vec, k=10),
    )
    return [(d["doc_id"], r) for r, d in enumerate(orig_hits)] + \
           [(d["doc_id"], r) for r, d in enumerate(hyde_hits)]

def reciprocal_rank_fusion(rankings: list[list[tuple[str, int]]], k: int = 60) -> list[str]:
    scores: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        for doc_id, rank in ranking:
            scores[doc_id] += 1.0 / (k + rank)
    return [d for d, _ in sorted(scores.items(), key=lambda x: -x[1])]

async def hybrid_retrieve(query: str, decompose_fn, vector_store, top_k: int = 8):
    decomposed = decompose_fn(query)  # synchronous is fine — Flash is fast enough
    rankings = await asyncio.gather(*[
        search_branch(sub, vector_store) for sub in decomposed.sub_queries
    ])
    fused = reciprocal_rank_fusion(rankings)
    return fused[:top_k]
```

With four sub-queries, wall-clock latency stays close to the cost of one branch. RRF merges the rankings using rank position alone, which is a feature: when you have multiple retrievers (vector, BM25, keyword), their score scales rarely match, and naïve sum-of-scores blows up the moment one stream's scores drift. RRF doesn't care — it works on ordinal information. The constant `k=60` is the value the original RRF paper recommended, and despite many alternatives in the literature, I've never found a domain where tweaking it produced a meaningful gain in production. Save your tuning budget for higher-leverage parameters.

## Pitfalls that bite in production

This design looks tidy on paper but reveals problems the moment real users hit it. Here are the ones that cost me time, and what I do now.

**Over-decomposition kills recall.** Gemini will sometimes split a question into four hyper-specific sub-queries that, individually, are too narrow to retrieve the document the user actually needs — even though the original question would have surfaced it. Two defenses help: cap `max_items=4` in the schema, and have a precheck where Gemini decides whether the question is single-concern; if so, skip decomposition entirely. I also add a heuristic safety net — if the user query is fewer than 12 words, skip decomposition and use the original query plus HyDE only. Short queries rarely contain compound concerns.

**HyDE going off the rails.** Sometimes Gemini writes a hypothetical answer with such confidence that it invents domain terminology that doesn't exist, dragging the search in the wrong direction. The fix that consistently works for me is to **cap HyDE output to 200–300 characters**. The longer the hypothetical answer, the more Gemini reaches for "voice" — and that voice introduces unrelated context. Keep HyDE short and you preserve its real value: vocabulary expansion. A second mitigation is to never let HyDE *replace* the original-query branch, only supplement it. As long as the original is in the merge, a bad HyDE branch only shifts ranks slightly; it doesn't erase the correct answer.

**Cost creep.** A single user request now triggers one decomposition + N HyDE generations + 2N embedding calls + the final answer generation. With Flash and embedding pricing, this is cheap per request, but at 10K queries per day it stops being negligible. Three levers to pull: cache decomposition and HyDE results (Redis works fine, with the original query as the key) for repeat questions; lean on [Gemini API context caching for cost optimization](/en/articles/gemini-api/gemini-api-context-caching-cost-optimization) to amortize fixed prompt segments; and don't run the full pipeline while the user is still typing — only fire on submit. A fourth lever, if you're at scale: route easy queries (high-confidence single-concern questions) through a lightweight branch that skips HyDE entirely. A small classifier — even a heuristic on query length and presence of question marks — can shave 30–40% of pipeline calls in many production workloads.

**No way to evaluate decomposition quality.** Decomposition is invisible to the user, so silent regressions can go undetected. I sample sub-queries from production logs daily and have Gemini grade them with a separate prompt — an LLM-as-Judge variant. The pattern is described in [Gemini-based LLM-as-a-Judge evaluation pipelines for production](/en/articles/gemini-api/gemini-llm-as-judge-evaluation-production-guide). The judge prompt asks four questions: are sub-queries independent, do they preserve the user's intent, is each sub-query specific enough to retrieve a document, and is anything important missing? I store the scores alongside the decomposition in Redis, and alert when the rolling average dips by more than 10% over a 24-hour window.

**Streaming UX coexistence.** RAG frontends usually stream the final answer, but this pipeline introduces a 300–500 ms blocking phase for retrieval. The pattern that works for me is a two-stage UI: show a "Searching..." placeholder while retrieval runs, then begin streaming the generation the moment search finishes. Users perceive the system as responsive, and you don't have to architect speculative decoding. The placeholder doesn't even need to animate — just a static "Searching your knowledge base..." line is enough to make users feel the system is doing something.

**Silent embedding-model upgrades.** This one bit me hard. Switching embedding models (or upgrading them between minor versions) without re-indexing your corpus produces a subtle accuracy regression that's hard to attribute. Embedding models are not interchangeable, even across patch versions of the same family. Always re-index when you change the embedding model, and log the model version with every indexed chunk. When you eventually need to debug a recall regression, that field is gold.

## Build a small evaluation set before tuning anything

Quality only improves once you can measure it. The minimum I keep is a 30–50 sample evaluation set: real user queries paired with the document IDs that should appear in the top-k. With that, I run four conditions side-by-side — (a) baseline single-query, (b) decomposition only, (c) HyDE only, (d) decomposition + HyDE — and measure nDCG@10 and recall@10.

Empirically, moving from baseline to (d) lifts recall@10 by 15–25% and nDCG@10 by 10–18% in my work. The split between the gains varies hugely by domain, though. Short-and-abstract Q&A tends to benefit more from HyDE alone; complex business questions with multiple concerns are dominated by decomposition. The only way to know which lever moves your numbers is to actually run the eval — which is why investing the time to build the eval set first is, paradoxically, the fastest path forward.

A practical tip on building the eval set: don't try to design queries from scratch. Pull them from real user logs, deduplicate near-identical ones, and have a domain expert annotate the gold document IDs. Synthetic queries generated by Gemini are tempting but tend to be too clean — they don't reproduce the messy phrasing real users bring to your system. The 30 hard-won real queries beat 300 synthetic ones for tuning quality. One nuance worth surfacing: as your eval set ages, refresh roughly a third of the queries every quarter. User behavior drifts with product changes, marketing campaigns, and seasonal factors, and an eval set frozen for too long stops representing the live distribution. I label each eval query with the month it was added, and rotate out the oldest ones whenever they no longer match the patterns I see in production logs.

A second underappreciated practice is to keep two separate eval sets — a "stable" set that never changes, used for tracking long-term trajectory, and a "rolling" set that refreshes regularly. The stable set tells you "are we better than we were six months ago?"; the rolling set tells you "are we serving today's users well?" The two answers are not always the same, and seeing them diverge is itself diagnostic information.

## A practical caching layer that compounds the cost wins

Once the pipeline is stable, the biggest remaining cost lever is caching, and the layered approach matters more than which cache backend you pick. I keep three caches in production, each at a different granularity. The **decomposition cache** stores `query → DecomposedQueries` keyed by a normalized version of the user query (lowercased, whitespace-collapsed, punctuation-stripped). It hits often because users ask near-identical questions throughout the day. TTL of 24 hours is usually fine — decomposition logic only changes when you redeploy.

The **HyDE cache** stores `sub_query → hypothetical_text` and sits one layer down. Sub-queries normalize even better than full questions because decomposition is deterministic at `temperature=0.0`, so two slightly different user questions often produce overlapping sub-queries. A 7-day TTL works well here. The third cache is the **embedding cache** — a simple `text → vector[]` mapping. This one is the cheapest hit but the highest volume, so I push it to a fast in-memory store (Redis with `allkeys-lru` eviction) rather than a SQL backend. With these three layers, repeat-query cost drops by 60–80% in my workloads, and tail latency improves more than the cost number suggests because cached queries also skip the network round-trip to Gemini.

A subtle gotcha: if you cache HyDE output, you must invalidate the cache when you change the HyDE prompt. I version my prompts with a short hash and prefix all cache keys with it. When I push a new prompt, the old keys naturally expire as no new requests hit them. Forgetting this version prefix once cost me half a day of debugging stale outputs after a prompt update.

## Observability: the metrics worth wiring up

Even with a clean pipeline, observability is what keeps it healthy. The metrics I always wire up: **decomposition count distribution** (histogram of how many sub-queries each request generated, watch for drift toward four), **HyDE generation latency p50/p95/p99**, **branch failure rate per stage** (decomposition timeouts, HyDE timeouts, embedding failures, vector-store failures), **fusion top-k stability** (do the same fused top-3 documents appear when the same query is replayed five minutes later?), and **end-to-end retrieval recall** measured against a sliding eval set.

The fusion-stability metric is one I underrate at first. The pipeline has multiple sources of variance — HyDE temperature, network jitter, vector-store internal sharding — and even with a deterministic decomposition step, occasional rank fluctuations are normal. But sudden drops in fusion stability (say, the same query producing wildly different top-3 sets across replays) are a leading indicator that something downstream has degraded — usually a vector-store rebalancing event or an embedding model patch update. Catching it via observability is much cheaper than catching it via user complaints.

For tracing, OpenTelemetry over Gemini is now well-supported. Each retrieval branch becomes its own span, and the parent span captures the fused result. When a query goes wrong, you can replay the trace and see at which branch the answer document started ranking poorly, which is invaluable for prompt-tuning work.


## When to skip this stack entirely

Not every RAG system needs decomposition + HyDE. If your queries are mostly short, factual, and use the same terminology as your documents — think product-catalog search, code symbol lookup, or documentation search where users know the function names — adding these layers can reduce accuracy and definitely increases cost and latency. Run the eval before adopting. If your baseline is already at 90%+ recall@10, the marginal gain from this stack rarely justifies the operational complexity.

Conversely, the strongest signals that this stack will help are: average query length above 12 words, frequent compound questions, document corpus written in highly formal or jargon-heavy prose, and recall@10 stuck in the 60–75% range despite multiple embedding-model experiments. If all four apply, you should expect meaningful gains.

If you only do one thing tomorrow, make it this: assemble a 30-question evaluation set and measure your current baseline recall@10. Whether decomposition or HyDE will move the needle for your domain is unknowable in the abstract — but with an eval set, every change becomes a number you can defend, and you'll see exactly where the next plateau sits. Every line of code in this article assumes you are running it inside that loop. I hope it helps your RAG dig out the answers it has been missing.
