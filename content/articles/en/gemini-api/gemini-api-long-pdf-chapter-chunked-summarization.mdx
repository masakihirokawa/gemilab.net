"I stuffed a 500-page PDF into Gemini 2.5 Pro's 2-million-token context, and the summary got progressively sloppier until it gave up around the end." That's me, about a week ago, building a tool that was supposed to extract per-section key points from a long technical spec. Lesson learned: fitting something into context is not the same as getting consistent output across it.

Long context lets you submit a lot of input, but the output doesn't spread its attention evenly across everything you submitted. In this post I want to share the "chapter-chunk, parallel-summarize, then re-merge" pattern I ended up with, along with a Python implementation and the places I stumbled.

## The one-shot approach quietly fails

My first cut was the obvious one: pass the whole PDF to `generate_content`. It worked fine on a 20–50 page sample. On the actual 500-page spec, something different happened:

- The first 30% of chapters were summarized in fine detail.
- The middle started losing resolution.
- The last 20% was reduced to one-liners like "The appendix contains configuration examples and references."

What I think is going on: even if the model can technically attend across the full window, the information density of its output thins out toward the back of a very long input. This is a practical ceiling that sits well below the theoretical context length. I touched on similar behavior in [Practical patterns for using Gemini's long context](/articles/gemini-advanced/gemini-long-context-practical-patterns), but it shows up especially clearly in summarization tasks.

The takeaway for me was that "if it fits, just send it all and let prompting handle the rest" stops being a reliable default once documents cross a certain size.

## Why chapter-level chunks beat fixed-length chunks

The naive alternative is fixed-length chunks (say, 4,000 tokens each). It works, but for structured documents like books and specs it slices the argument in unnatural places. You end up with summaries that reference "the discussion above" when the discussion above was in a different chunk.

What I reach for in production is chapter-level chunking based on the PDF's outline (bookmarks / table of contents):

- Cuts land on semantically meaningful boundaries.
- Each chapter summary naturally gets a real title.
- The chapter is a clean unit for parallel API calls.

PDFs without a readable outline (scans, old exports) need a different approach, which I cover near the end. The main implementation below assumes the outline is available.

## Python implementation

This is the minimal working version I use. It uses `pypdf` to extract the outline and the `google-genai` SDK for the Gemini calls.

```python
# pip install google-genai pypdf
# Required env var: GOOGLE_API_KEY="YOUR_API_KEY"
import asyncio
import os
from dataclasses import dataclass
from pypdf import PdfReader
from google import genai

client = genai.Client(api_key=os.environ["GOOGLE_API_KEY"])
MODEL = "gemini-2.5-pro"

@dataclass
class Chapter:
    title: str
    start: int  # 0-indexed page
    end: int    # exclusive
    body: str

def extract_chapters(pdf_path: str) -> list[Chapter]:
    """Split a PDF into chapters based on its outline."""
    reader = PdfReader(pdf_path)
    outlines = reader.outline
    # Top-level entries only (skip nested sub-sections).
    top_level = [o for o in outlines if not isinstance(o, list)]
    chapters: list[Chapter] = []
    for i, entry in enumerate(top_level):
        start = reader.get_destination_page_number(entry)
        end = (
            reader.get_destination_page_number(top_level[i + 1])
            if i + 1 < len(top_level)
            else len(reader.pages)
        )
        body = "\n".join(reader.pages[p].extract_text() or "" for p in range(start, end))
        chapters.append(Chapter(title=entry.title, start=start, end=end, body=body))
    return chapters

async def summarize_chapter(ch: Chapter) -> str:
    """Produce a focused summary of one chapter."""
    prompt = (
        f"The text below is the '{ch.title}' chapter of a technical document.\n"
        "Summarize the chapter's claims in up to five bullet points.\n"
        "Stay within the chapter; do not reference other chapters.\n\n"
        f"Body:\n{ch.body}"
    )
    # The Python SDK is synchronous, so we offload to a thread.
    resp = await asyncio.to_thread(
        client.models.generate_content,
        model=MODEL,
        contents=prompt,
    )
    return resp.text.strip()

async def summarize_pdf(pdf_path: str) -> str:
    chapters = extract_chapters(pdf_path)
    # Cap concurrency to stay inside rate limits.
    semaphore = asyncio.Semaphore(4)

    async def bounded(ch: Chapter) -> tuple[str, str]:
        async with semaphore:
            return ch.title, await summarize_chapter(ch)

    results = await asyncio.gather(*(bounded(c) for c in chapters))

    # Re-merge: ask the model what the document as a whole is saying.
    joined = "\n\n".join(f"## {title}\n{summary}" for title, summary in results)
    merge_prompt = (
        "Below is a chapter-by-chapter summary of a technical document.\n"
        "Write a 300-word synthesis of what this document is trying to tell its reader.\n"
        "Do not just list chapter points; extract the unifying argument.\n\n"
        f"Chapter summaries:\n{joined}"
    )
    final = client.models.generate_content(model=MODEL, contents=merge_prompt)
    return f"{joined}\n\n---\n\n# Synthesis\n{final.text.strip()}"

if __name__ == "__main__":
    out = asyncio.run(summarize_pdf("./spec.pdf"))
    print(out)
```

The shape is: extract chapters, summarize each chapter in parallel (bounded by a semaphore), then run one more Gemini call to synthesize across the per-chapter summaries. On a 500-page, ~40-chapter PDF this stays inside the free-tier rate limits at concurrency 4 and finishes in 2–3 minutes on my machine.

## Why the final re-merge actually matters

The last step — `merge_prompt` — is what makes this pattern worth the extra API calls. Concatenating chapter summaries alone gives you a slightly verbose table of contents. Asking the model to re-read its own summaries and name the throughline is what surfaces the document's actual argument.

Compared to the one-shot approach, this two-pass design buys you:

- Even resolution across chapters (no thinning toward the end).
- A small, well-shaped input for the final pass (chapter summaries × 40 ≈ a few thousand tokens), where accuracy tends to be much steadier.
- A caching boundary that lines up with chapters, which I'll come back to in a moment.

The obvious downside is cost. You make roughly one call per chapter plus one merge call, so on a 40-chapter document you're looking at 41 API calls instead of 1.

## Costs and when context caching earns its keep

Whether the extra calls matter depends on how you plan to use the document.

- **One-shot summary.** Even with chapter-level parallelism, the total input tokens are close to the naive one-shot approach (the text gets sent once across the chapter calls). Output tokens go up a bit because each chapter produces its own summary, but billing stays roughly linear. I happily use the chunk pattern for one-off summaries.
- **Repeated queries on the same PDF.** If you plan to ask follow-up questions ("expand the chapter 3 points", "pull out all cited references"), you'll want to combine this with [context caching](/articles/gemini-api/context-caching-guide). Cache the full PDF once, use chapter summaries as a cheap index, and fetch deeper detail on demand.

For the actual numbers, you'll need to measure on your workload — model pricing shifts often enough that I'd rather not quote specifics. The [complete guide to Gemini API cost optimization](/articles/gemini-api/gemini-api-cost-optimization-complete-guide) is a good starting point for reasoning about the trade-offs.

## When the outline isn't there

Real documents don't always cooperate. You'll hit PDFs with no outline at all, image-only scans, and outlines that are either too shallow or too deep. Here's how I handle each:

- **No outline.** Scan the extracted text for heading-like patterns (e.g., regex for "Chapter N" or "Section N.N") and build a pseudo-outline. If that also fails, fall back to fixed-length chunks of 4,000–6,000 tokens — not ideal, but predictable.
- **Image-only PDF.** Gemini can ingest the PDF directly as a multimodal input, so you don't need an OCR pass. Large documents, however, just move the context problem to the model; my rule of thumb is to cap each call at a page range and treat the range as a synthetic "chapter." The [PDF analysis basics article](/articles/gemini-api/gemini-api-pdf-analysis-guide) goes into more detail.
- **Outline too deep.** Keep the top-level headings (chapters) and collapse sub-sections into the chapter body. Going below 30–50 chunks tends to make prompts harder to write, not easier.

## Pitfalls I keep running into

A few specific traps worth calling out, because they've bitten me more than once:

- **Concurrency that's too high.** Running more than 8–10 concurrent calls against the free tier will eventually trigger 429s that surface as partial results. The semaphore pattern in the code above is deliberately conservative; raise it only after you confirm your quota.
- **Trusting `extract_text()` on academic PDFs.** Papers with multi-column layouts or heavy math often produce garbled text. Before you suspect the model, print the raw chapter body and eyeball it. If it looks like soup, you need a better PDF extractor (or the multimodal approach) before chunking will help.
- **Asking for bullets when the chapter is argumentative.** "Five bullet points" is a good default for reference material, but for chapters that build a sustained argument you'll get better results asking for a short paragraph. I keep two prompt variants and pick per document.

## Next step

If you have a 200+ page PDF sitting around, count the chapters and try the code above as-is. The qualitative difference between "one-shot back half gets vague" and "per-chapter summaries at a consistent grain" is hard to convey in text — you really have to see it.

Once the chapter boundary logic is stable, everything else in this pattern becomes mechanical. I've been using it daily for book notes, stacks of meeting transcripts, and paper surveys, and it continues to earn its keep.
