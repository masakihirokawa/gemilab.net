When `ollama pull gemma4:4b` returns `Error: pull model manifest: file does not exist`, the most common Stack Overflow answer is "update Ollama." Half the time that is correct, but in my experience the other half — where updating doesn't fix it — is more interesting.

The error means "Ollama looked for the model name on Ollama Library and couldn't find it," but five distinct underlying causes lead to that symptom. Let's walk through them in order.

## What the Error Actually Means

`pull model manifest: file does not exist` appears when Ollama hits `https://registry.ollama.ai/v2/library/<model>/manifests/<tag>` with a GET request and gets back a 404. The server is responding — it's telling you "that model + tag combination does not exist."

You can verify what Ollama actually requested:

```bash
# If you ran: ollama pull gemma4:4b
# Ollama is hitting:
# https://registry.ollama.ai/v2/library/gemma4/manifests/4b

# Confirm with curl
curl -I https://registry.ollama.ai/v2/library/gemma4/manifests/4b
# 404 -> the name does not exist as you typed it
# 200 -> the issue is on Ollama's side
```

This single check rules out two of the five causes immediately.

## Cause 1: Wrong Model Name (Most Common)

The official Gemma series names on Ollama Library have shifted with releases. As of April 2026, the correct names are:

| What you tried | What it actually is | Notes |
|---|---|---|
| gemma4 | gemma4 or gemma3:4b | Bare "gemma4" without size tag often unavailable |
| gemma4:4b | gemma3:4b (older) or gemma4:4b (newer) | Depends on release timing |
| gemma-4 | (does not exist) | Hyphen is invalid |
| gemma:4 | (does not exist) | Version-only tags don't exist |

The most reliable check is the [Ollama Library search page](https://ollama.com/library) — search for `gemma` and confirm the exact tag currently available. After I made that a habit before any pull, this error nearly disappeared from my workflow.

Working examples:

```bash
# Pull alone
ollama pull gemma3:4b

# Run directly (auto-pulls if missing)
ollama run gemma3:4b
```

## Cause 2: Outdated Ollama Version

Older Ollama versions don't recognize newer model families. The Gemma 4 series is officially supported in Ollama 0.5.0 and later.

```bash
# Check current version
ollama --version

# Update on macOS / Linux
curl -fsSL https://ollama.com/install.sh | sh

# Windows: re-download from the official installer
# https://ollama.com/download
```

After updating, restart the Ollama service. A stale background process from the old version can mask the upgrade.

```bash
# macOS
ollama stop
# Quit the Ollama app, then relaunch

# Linux (systemd)
sudo systemctl restart ollama
```

## Cause 3: Network Reachability to the Registry

If your environment can't reach `registry.ollama.ai`, no pull will work. Common scenarios:

**Corporate firewall**: Ask IT to allowlist `registry.ollama.ai` and `*.ollama.ai`. If you go through a proxy, set environment variables:

```bash
export HTTPS_PROXY=http://your-proxy:port
export HTTP_PROXY=http://your-proxy:port
ollama pull gemma3:4b
```

**Region restrictions**: Direct access to Ollama Library is restricted in some regions (notably mainland China). The "import from local GGUF" path below becomes the practical solution.

**DNS resolution failure**: Rare, but corporate DNS sometimes can't resolve `registry.ollama.ai`.

```bash
# Verify DNS
nslookup registry.ollama.ai
dig registry.ollama.ai
```

## Cause 4: The Tag Was Deprecated

Ollama Library tags can be removed when newer versions ship. If a command that worked recently suddenly fails, this is the suspect.

```bash
# Verify available tags on the web
# https://ollama.com/library/gemma3/tags
```

If you must keep using a deprecated tag, back up the locally cached manifest from `~/.ollama/models/manifests/registry.ollama.ai/library/<model>/`.

## Cause 5: Import a GGUF File Locally (Offline Path)

When nothing above works, or when you need to operate offline, download a GGUF directly from Hugging Face and import it into Ollama:

```bash
# 1. Download the GGUF (example: Hugging Face)
mkdir -p ~/models/gemma3-4b
cd ~/models/gemma3-4b
# After confirming the license
curl -L -O https://huggingface.co/google/gemma-3-4b-it-gguf/resolve/main/gemma-3-4b-it-Q4_K_M.gguf

# 2. Create a Modelfile
cat > Modelfile <<'EOF'
FROM ./gemma-3-4b-it-Q4_K_M.gguf

PARAMETER temperature 0.7
PARAMETER top_p 0.9
PARAMETER top_k 40
PARAMETER num_ctx 4096

TEMPLATE """{{ if .System }}<start_of_turn>system
{{ .System }}<end_of_turn>
{{ end }}{{ if .Prompt }}<start_of_turn>user
{{ .Prompt }}<end_of_turn>
{{ end }}<start_of_turn>model
{{ .Response }}<end_of_turn>
"""
EOF

# 3. Register with Ollama
ollama create gemma3-local -f Modelfile

# 4. Run
ollama run gemma3-local
```

This path works without any registry dependency. Note that the TEMPLATE format differs per model family — always check the Hugging Face model card.

## Diagnostic Order: One Minute Each

1. Run `curl -I https://registry.ollama.ai/v2/library/gemma3/manifests/4b` — confirm 200
2. Verify the correct tag at the [Ollama Library Gemma page](https://ollama.com/library/gemma3) and re-pull with the right name
3. `ollama --version` — if below 0.5.0, update
4. If on a corporate proxy, set `HTTPS_PROXY`
5. Still failing — import a GGUF file manually

In my experience, causes 1 (wrong name) and 2 (outdated version) account for 80% of cases. The remaining 20% split across causes 3 through 5.
