If you have ever handed a design document to Gemini and said "go build this," you already know the feeling — the code comes back doing roughly what the spec said, and yet it is not quite what you wanted. I hit that wall again and again on my own projects, and eventually noticed that the same spec produced wildly different results depending on the few lines of context I attached before it.

This post is a small catalogue of five prerequisites I have started writing on top of every spec I give to Gemini 2.5 Pro. They do not change the spec itself — they change what the spec means to the model. I am not going to rewrite specs for you, only talk about the preamble that sits above them.

## Why a Spec Alone Falls Short

When two human engineers trade a spec, a lot goes unsaid. Company conventions, language preferences, the history of the codebase — all of it lives in the margins. The moment the same spec lands inside Gemini's context, those margins are blank. The model fills them with the most statistically likely interpretation, which is why the output often feels "fine, but not ours."

A spec is a contract for behavior, not an answer key for judgment calls. It describes what the code should do, but not how it should fit into a codebase that already has a voice of its own. The five prerequisites below are what I use to fill in the judgment side of that contract. None of them require fancy prompt engineering — they are just the unsaid parts made explicit.

## Prerequisite 1: Pin the Language and Version

This is the easiest one to forget. If you do not state the language and its version, Gemini will drift toward an average interpretation — some generic TypeScript from the early 2020s, vaguely modern Python, the kind of code that works everywhere and nowhere in particular.

A three-line header fixes most of it.

```text
Context:
- Language: TypeScript 5.4
- Runtime: Node.js 20 (ES modules)
- Test framework: Vitest 1.x
- Lint: ESLint 9 (flat config)
```

Once the ecosystem is named, the rest of the code snaps to it. Declaring Node.js 20 tends to produce `node:fs/promises` style imports without any extra nudging. Declaring ES modules removes the `require` / `import` confusion. These are small things, but they add up across a codebase, and they remove the repetitive review comments that would otherwise pile up. I have also found that listing the lint config by name ("ESLint 9 flat config") nudges the model away from legacy patterns that would fail the CI check anyway.

## Prerequisite 2: Sketch the Map of the Existing Code

Outside of greenfield projects, every new piece of code lands on top of something. Gemini cannot see that something, so you have to describe its shape.

I keep this short — a paragraph of orientation is usually enough.

```text
Relationship to existing code:
- src/core/errors.ts: import the custom AppError class from here
- src/core/logger.ts: get the logger via getLogger(); never use console.*
- src/modules/user/: new features live as modules under this directory
- Dependency direction: modules -> core only; never the reverse
```

This is an applied version of the "make the context explicit" idea from [four prompt structures that fix mismatched Gemini output](/en/articles/gemini-basics/gemini-prompt-four-structures-when-output-mismatch). The moment Gemini knows where the code is going to live, fabricated imports mostly disappear and the style lines up with the surrounding codebase. The dependency direction line is the one I value most — without it, you occasionally get a core module that imports from a feature module, which is a quiet way to create a cycle you will regret later.

## Prerequisite 3: Nail Down Edge Cases with Failure Examples

A spec that says "handle errors appropriately" reads the same to Gemini as it does to a human — vague. Unless you fix the boundary between success and failure, the output will drift each time you regenerate.

My trick is to describe edge cases not as a neat input/output table, but as a short list of things that must fail.

```text
Treat as failures:
- email missing or without "@" -> ValidationError("invalid_email")
- same email seen >= 3 times within 5 minutes -> RateLimitError("too_many_attempts")
- DB write does not complete within 2s -> TimeoutError("db_write_timeout")
Each failure extends AppError.
```

I lead with failures because the happy path is usually well specified in the main document. Pinning down what counts as a failure first pushes Gemini toward safer code. If you are also using function calling, mixing these failure shapes into the tool schema (as described in the [complete Gemini function calling guide](/en/articles/gemini-dev/gemini-function-calling-complete-guide)) sharpens the contract further and makes the failure vocabulary consistent across the whole agent loop.

## Prerequisite 4: List the Patterns You Don't Want

Counterintuitively, "please don't do X" often beats "please do Y" when you are nudging an AI coder. Positive instructions leave room for interpretation; negative ones draw a clean boundary.

```text
Avoid:
- Introducing new "any" types (existing "any" is out of scope)
- Swallowing errors in try/catch (always let them propagate)
- console.log for debug output — use logger.debug
- Calling Date.now() directly — go through the Clock interface
```

The testability items — time, randomness, I/O — are the ones I never skip. If you let them slip in, you will be refactoring later to make anything testable. When Gemini sees this list, it routes around those anti-patterns and the number of review comments on the first draft drops noticeably. A side benefit is that this list doubles as onboarding material for any human collaborator joining the project later; you already wrote down the things your team quietly agrees never to do.

## Prerequisite 5: Write Acceptance Criteria That Can Be Read Line by Line

The last block is the one that turns "code that might work" into "code that will pass review." I phrase acceptance criteria as close to machine-checkable form as I can.

```text
Done when:
- pnpm test passes with no failures
- src/modules/user/user.test.ts covers:
  - happy path: user can be created
  - duplicate email is rejected
  - malformed email raises ValidationError
- pnpm typecheck passes
- Coverage for the touched area is >= 80%
```

With this block in place, Gemini tends to return both the implementation and the matching tests. You stop doing the silent translation between "there is code" and "there is code that will clear review" on every iteration. It also makes it much easier to ask for a regeneration — instead of "this is not quite right," you can point to the specific line of the acceptance criteria that was not met, and Gemini will focus its fix there.

## When to Skip All of This

None of these prerequisites are free. They take a few minutes to write and add noticeable tokens to every request. For a throwaway script or a quick experiment, I skip them without guilt. The heuristic I use: if the code is going to live long enough that I would review someone else's version of it, the prerequisites pay off. If I am just exploring an API for twenty minutes, they get in the way.

## Wrapping Up

Writing preambles before the spec looks like extra documentation work. In practice it is a trade — a few minutes up front against hours of rework on the back end. After I standardised these five prerequisites, the amount of rework on first-draft implementations dropped by roughly half for me, which is a number I can feel on a Friday evening.

If you want to try this without overcommitting, start with Prerequisite 1 alone. Paste two or three lines declaring your language, runtime, and test framework on top of your next spec, and watch how the output settles down. From there you can grow your own template, one prerequisite at a time, until it fits the projects you actually build.
