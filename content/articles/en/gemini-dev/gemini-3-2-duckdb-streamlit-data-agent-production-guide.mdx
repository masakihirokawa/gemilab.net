For about a year now, whenever I needed to dig into my own app revenue, AdMob CSV reports, or Stripe payment history, I'd just paste the data into Gemini and ask "what does this say?". It was fast and easy. The first few times it felt almost magical — being able to skip the SQL and pandas hopping around and just hand a chunk of data to an AI. But after running through the same ritual every single month, one quiet evening it occurred to me: **if I just wrap this entire dance into an app, the analysis can run while I'm asleep.** Past me would have shrugged at the idea — surely the manual flow is fast enough. But every action you do twice in a month is worth automating once, and revenue analysis is the one thing I do many more times than twice.

That night I started building what this article documents — a "Gemini 3.2 Pro × DuckDB × Streamlit" data analysis agent. Drop in a CSV or Parquet file, ask a question in plain language, and it composes a SQL query, auto-corrects on failure, visualizes the result with Plotly, and dynamically picks between models to keep your bill sane. No cloud database is involved. Everything runs on your laptop, or in a single small Streamlit Community Cloud container.

This article walks through the implementation from scratch to production. I won't show snippets — I'll show the complete code that runs with `streamlit run app.py`. The pitfalls I describe along the way are ones I actually fell into, with the patterns I now use to avoid them.

What I've come to feel, after running variations of this setup for months, is that **building your own "ask data in natural language" agent quietly changes how you think.** The psychological friction of querying your own data drops to almost zero. Questions you'd previously have given up on ("I want to know X but writing SQL feels like too much trouble right now") flow naturally into the dashboard. That's a real cognitive shift, and at least in my own work the quality of decisions before and after this agent has been visibly different.

## Why DuckDB and Gemini 3.2 Pro Together

Let me share the reasoning behind this stack first. Before landing here I tried PostgreSQL + Vertex AI, SQLite + Gemini Flash, and BigQuery + Gemini Pro. I ended up at DuckDB because **for an indie developer running everything alone, a column-oriented database that needs no server is dramatically less work.**

DuckDB inherits SQLite's "embed it everywhere" philosophy, but its internals are a PostgreSQL-style query planner over Apache Arrow columnar storage. On my laptop, a `GROUP BY country, ymonth` aggregation against a 1.2 GB Parquet file (three years of daily AdMob data) consistently returns under 100 ms. Combine that responsiveness with Gemini 3.2 Pro's SQL generation accuracy and you end up with a tool you actually reach for, the way you reach for a notebook.

Gemini 3.2 Pro pulls its weight for one more reason: **`responseSchema` makes structured output rock-solid, so SQL arrives as a validated object rather than a "code-shaped string"**. That's the foundation for the self-correction loop we'll build later. In earlier prototypes I was using `gemini-2.5-flash` and feeding the raw text response into a regex parser. About 4% of responses had quirks — extra commentary, escaped quotes, the occasional Markdown fence — that broke the parser. With `responseSchema` set against a Pydantic model, that failure mode dropped to effectively zero, and my mental model of the pipeline became "Gemini hands me an object" rather than "Gemini hands me a hopefully-clean string."

There's also a quieter benefit to the Pro tier specifically: it consistently produces correct DuckDB-flavored SQL — using `list_*`, `struct_*`, `regexp_extract` style functions rather than reaching for PostgreSQL-only syntax. With Flash, I'd see roughly one in five queries use a function that DuckDB doesn't implement. With Pro that number is closer to one in fifty, which means the self-correction loop almost never has to step in for Pro-generated queries. The cost-savings angle and the accuracy angle line up: route easy questions to Flash for speed and price, but trust Pro on the hard ones.

## The Finished Architecture

Here's the flow you'll have running by the end. Streamlit handles the frontend, DuckDB does the analytical work, and Gemini does the translation, interpretation, and self-correction — three layers, cleanly separated.

- **Input layer:** Upload a CSV/Parquet via the Streamlit sidebar, or pick from a local `data/` directory
- **Schema extraction:** DuckDB's `DESCRIBE` pulls column names, types, and sample unique values to keep the context to Gemini lean
- **SQL generation:** Pass the question and schema to Gemini 3.2 Pro/Flash, get back a structured-output object with the SQL and an intent description
- **Execution + self-correction:** Run the SQL in DuckDB; on error, hand the error back to Gemini for a fixed version (up to 3 attempts)
- **Visualization:** Auto-render the resulting DataFrame with Plotly Express; chart type is decided by Gemini in the same response
- **Cost management:** Route between Pro and Flash based on the complexity Gemini estimates for the query

The discipline that pays off here is **separating responsibilities so each layer can be retried independently when it fails.** That single design choice changes how reproducible and debuggable the system is in production.

A practical example: when DuckDB raises a column-not-found error mid-query, you don't have to regenerate everything from the question. You only re-run the SQL generation step with the error appended. When the visualization step picks the wrong chart type, you don't have to re-execute the SQL — you only re-render. The boundaries between these layers are where retry logic lives. Without them, every failure becomes a full restart and your operating costs balloon.

## SQL Generation Core — Building an Unbreakable Contract with Structured Output

The first thing to build is the core that turns a natural-language question plus a schema into a SQL query. The pain point I kept running into in earlier versions was that Gemini would wrap SQL in ```sql ... ``` fences, or return explanations next to it, forcing me to write more and more regex hacks to extract the actual query. `responseSchema` releases you from that grind permanently.

Create `agent/sql_generator.py`:

```python
import os
from typing import Literal
from pydantic import BaseModel, Field
from google import genai
from google.genai import types

class SQLPlan(BaseModel):
    """Structured response from Gemini"""
    sql: str = Field(description="A complete SQL statement executable in DuckDB")
    intent: str = Field(description="A short summary of what the SQL is answering (under 30 chars)")
    chart_type: Literal["bar", "line", "scatter", "table", "histogram"] = Field(
        description="Best chart type for visualizing the result"
    )
    confidence: float = Field(ge=0.0, le=1.0, description="Confidence that the SQL is correct")

client = genai.Client(api_key=os.environ["GEMINI_API_KEY"])

SYSTEM_INSTRUCTION = """\
You are an expert in DuckDB SQL. Given a user's question and a table schema,
return exactly one complete SQL statement that will run in DuckDB.

Rules:
1. Use the table name exactly as given
2. Feel free to use DuckDB-specific functions (list_*, struct_*, regexp_extract, etc.)
3. Always exclude NULL values explicitly when aggregating
4. Use TRY_CAST(col AS DATE) for safe date casting
5. Set confidence between 0.0 and 1.0 reflecting how sure you are the SQL works
"""

def generate_sql(question: str, schema_text: str, model: str = "gemini-3.2-pro") -> SQLPlan:
    """Generate a SQLPlan from a question and schema."""
    response = client.models.generate_content(
        model=model,
        contents=[
            f"Schema:\n{schema_text}\n\nQuestion: {question}"
        ],
        config=types.GenerateContentConfig(
            system_instruction=SYSTEM_INSTRUCTION,
            response_mime_type="application/json",
            response_schema=SQLPlan,
            temperature=0.1,  # Keep SQL generation deterministic
        ),
    )
    return SQLPlan.model_validate_json(response.text)
```

Three things to highlight here. First, `temperature=0.1` — for SQL generation you want determinism, not creativity. Second, the `confidence` field is what we'll use later to fall back to Pro when Gemini itself isn't sure. Third — and this is the small win that matters — **asking for `chart_type` in the same response** removes a whole round-trip later. The UI feels noticeably snappier because of it.

## DuckDB Execution and the Self-Correction Loop

Next, run the generated SQL in DuckDB. We wrap it in a self-correction loop: when execution fails, the error gets handed back to Gemini for a fix. Before adding this loop my agent felt fragile; afterwards it felt solid. In my own logs, **78% of queries that failed on the first try succeed within one correction attempt.**

Create `agent/executor.py`:

```python
import duckdb
import pandas as pd
from agent.sql_generator import generate_sql, SQLPlan, client, types

class ExecutionResult:
    def __init__(self, df: pd.DataFrame, plan: SQLPlan, attempts: int):
        self.df = df
        self.plan = plan
        self.attempts = attempts

def execute_with_self_correction(
    question: str,
    schema_text: str,
    con: duckdb.DuckDBPyConnection,
    max_retries: int = 3,
) -> ExecutionResult:
    """Generate SQL → execute → on failure, ask Gemini to fix it."""
    plan = generate_sql(question, schema_text, model="gemini-3.2-pro")
    last_error = None

    for attempt in range(max_retries):
        try:
            df = con.execute(plan.sql).df()
            return ExecutionResult(df, plan, attempt + 1)
        except duckdb.Error as e:
            last_error = str(e)
            correction_prompt = (
                f"The SQL you generated failed with the following error. "
                f"Return a fixed version.\n\n"
                f"Question: {question}\n"
                f"Schema:\n{schema_text}\n\n"
                f"Previous SQL: {plan.sql}\n"
                f"Error: {last_error}\n"
            )
            response = client.models.generate_content(
                model="gemini-3.2-pro",  # Always use Pro for corrections
                contents=[correction_prompt],
                config=types.GenerateContentConfig(
                    response_mime_type="application/json",
                    response_schema=SQLPlan,
                    temperature=0.0,
                ),
            )
            plan = SQLPlan.model_validate_json(response.text)

    raise RuntimeError(f"Self-correction failed after {max_retries} attempts: {last_error}")
```

Two design decisions worth calling out. The correction step **always uses Pro** — when Flash fails, asking Flash to fix it tends to produce the same family of mistake. Switching to Pro just for the correction step is the rare case where prioritizing accuracy over cost actually saves tokens overall. And `temperature=0.0` for the correction itself: corrections aren't a creative task.

## Cost Optimization — Dynamically Routing Between Pro and Flash

If you're running this as an indie developer, cost is non-negotiable. My current monthly Gemini API spend on this agent is roughly $8. Three months ago when I was using Pro for every query, it was about ten times that. The lever was building **a router that estimates the SQL complexity up front and sends easy questions to Flash.**

```python
# agent/router.py
from google import genai
from google.genai import types
from pydantic import BaseModel

class Complexity(BaseModel):
    level: int  # 1=simple aggregation, 2=joins, 3=CTEs/window functions
    reason: str

ROUTER_SYSTEM = """\
Estimate the complexity of the SQL needed to answer the user's question, on a 1-3 scale.
1: SELECT/aggregation against a single table
2: JOINs or simple subqueries
3: Multiple CTEs, window functions, or complex aggregations
"""

def pick_model(question: str) -> str:
    """Choose a model based on estimated complexity."""
    response = client.models.generate_content(
        model="gemini-3.2-flash-lite",  # Cheapest model for routing decisions
        contents=[question],
        config=types.GenerateContentConfig(
            system_instruction=ROUTER_SYSTEM,
            response_mime_type="application/json",
            response_schema=Complexity,
            temperature=0.0,
        ),
    )
    complexity = Complexity.model_validate_json(response.text)
    return "gemini-3.2-pro" if complexity.level >= 3 else "gemini-3.2-flash"
```

It's a three-tier router: `flash-lite` decides, `flash` or `pro` executes. The extra round-trip looks expensive on paper, but **flash-lite is roughly 1/40 the cost of Pro** and only sees the short question text, so the total bill drops dramatically.

## Wiring It All Up in Streamlit

Putting the pieces together in `app.py`:

```python
import streamlit as st
import duckdb
import plotly.express as px
from agent.executor import execute_with_self_correction
from agent.router import pick_model

st.set_page_config(page_title="Data Agent", layout="wide")
st.title("Natural Language Data Agent")

# Sidebar: file upload
uploaded = st.sidebar.file_uploader("CSV / Parquet", type=["csv", "parquet"])
if uploaded is None:
    st.info("Upload a file from the sidebar to begin.")
    st.stop()

# DuckDB connection (shared within session)
if "con" not in st.session_state:
    st.session_state.con = duckdb.connect(":memory:")
con = st.session_state.con

# Register the file as a table
ext = uploaded.name.split(".")[-1]
if ext == "csv":
    con.execute("CREATE OR REPLACE TABLE data AS SELECT * FROM read_csv_auto(?)", [uploaded.getvalue()])
else:
    con.execute("CREATE OR REPLACE TABLE data AS SELECT * FROM read_parquet(?)", [uploaded.getvalue()])

# Pull schema
schema_df = con.execute("DESCRIBE data").df()
schema_text = schema_df.to_markdown(index=False)

# Question input
question = st.text_input("Ask anything", placeholder="What were last month's top 5 categories by revenue?")
if question:
    with st.spinner("Gemini is thinking..."):
        model = pick_model(question)
        result = execute_with_self_correction(question, schema_text, con)

    st.subheader(result.plan.intent)
    st.code(result.plan.sql, language="sql")

    df = result.df
    if result.plan.chart_type == "bar" and len(df.columns) >= 2:
        fig = px.bar(df, x=df.columns[0], y=df.columns[1])
        st.plotly_chart(fig, use_container_width=True)
    elif result.plan.chart_type == "line":
        fig = px.line(df, x=df.columns[0], y=df.columns[1])
        st.plotly_chart(fig, use_container_width=True)
    else:
        st.dataframe(df, use_container_width=True)

    st.caption(f"Model used: {model} / Attempts: {result.attempts}")
```

Run `streamlit run app.py` and you have a local data agent in your browser.

## Why the Three-Layer Split Pays Off

The thing that's quietly most valuable about separating generation, execution, and correction is that **debugging takes seconds instead of minutes**. When the result comes back empty, glance at `result.plan.sql` and you'll see the query filtered too aggressively with `WHERE date >= '2025-01-01'`. When the SQL is correct but DuckDB returns `out of memory`, `result.attempts` already tells you the agent looped, so you immediately know it's a data-volume problem, not an app problem.

What I fear most when running LLMs in production is **"Gemini is answering, but the answer is wrong"** — silent failure. Translating natural language into a verifiable artifact like SQL collapses correctness into a binary: either it ran, or it didn't. That makes a debugging loop possible. Designs that return only natural-language answers let mistakes slip into operations dressed as success.

The other quiet win is the `confidence` field. When Gemini returns `confidence < 0.6` I pause execution and surface "Did I understand this correctly?" back to the user. That single guardrail roughly halved the rate at which wrong SQL silently runs in my setup. The discipline is **don't widen the LLM's authority too much; bounce low-confidence cases back to a human.** Bake that line in early and the operational anxiety drops significantly.

I'll add one more thought about the `intent` field. When Gemini summarizes its own interpretation of the question into a 30-character sentence, that summary serves a second purpose: it becomes the chart title displayed above the result. Reading the chart title back, you immediately know whether Gemini understood your question. If it didn't — say you asked "best months last year" and the intent reads "monthly totals across all years" — you reword the question without bothering to read the SQL. That feedback loop makes the system feel less like a black box and more like a colleague that paraphrases your question before answering.

## Where DuckDB Quietly Helps

Choosing DuckDB pays off in ways beyond raw speed when paired with Gemini.

**It reads Parquet directly.** `SELECT * FROM read_parquet('data/*.parquet')` reads an entire directory, which fits naturally with monthly-growing file layouts. Define your view once with `CREATE OR REPLACE VIEW` and new files get picked up automatically — no need to regenerate the schema text you send Gemini.

**`SUMMARIZE` is gold.** `SUMMARIZE data` returns per-column statistics, mins/maxes, NULL ratios, and unique counts in one call. Feeding that into the schema context lets Gemini make smarter decisions like "skip this column because it's mostly NULL." In my latest iteration I include this in `schema_text` and SQL accuracy improved roughly 10–15% perceptually.

**JSON columns are first-class.** Stripe metadata stored as JSON strings can be queried as `SELECT metadata->>'$.plan' FROM data`. Add one line to the system prompt — "DuckDB supports the `->` and `->>` JSON operators" — and Gemini starts using them naturally.

## Observability — Staying Aware When You Run Solo

The thing I worry about most, running solo in production, is "will I notice on the same day something breaks?" On a team a coworker often catches it first; alone, you're it. Adding a thin observation layer from day one is the cheapest insurance.

This app appends five values per query to `logs/queries.jsonl`: question text, generated SQL, execution time in ms, model used, and number of attempts. JSONL is the right shape because **DuckDB can later query the log itself with `read_json_auto('logs/queries.jsonl')`** — the agent quietly observes itself.

```python
import json, time
from pathlib import Path

LOG_PATH = Path("logs/queries.jsonl")
LOG_PATH.parent.mkdir(exist_ok=True)

def log_query(question: str, plan: SQLPlan, elapsed_ms: int, model: str, attempts: int):
    LOG_PATH.open("a").write(json.dumps({
        "ts": int(time.time()),
        "q": question,
        "sql": plan.sql,
        "ms": elapsed_ms,
        "model": model,
        "attempts": attempts,
    }, ensure_ascii=False) + "\n")
```

Every Sunday morning a small script aggregates last week's log and emails me three numbers: **the share of queries with `attempts >= 2`, the share of queries that hit Pro, and the average response time.** As long as those three are stable, the system is healthy. Catastrophic regressions usually show up first as one of these numbers drifting.

Error monitoring is a separate channel. Only `google.genai.errors.APIError` and `duckdb.Error` go to Slack; other exceptions go to stderr only. Narrowing the alert surface keeps me from going blind to notifications that fire constantly.

## Testing the Agent — How to Trust What You Built

I sat on this codebase for two months before sharing it, mostly because I wasn't sure how to test something whose output is generated by a model. The answer turned out to be simpler than I expected: **test what's deterministic, snapshot what isn't, and treat the LLM as a black box during testing.**

The deterministic surface is bigger than you'd think. The schema extraction logic, the chart-type-to-rendering mapping, the file save/load cycle, the SELECT-only whitelist, and the cost router's decision boundary are all pure functions you can unit-test. I have around 30 pytest cases covering these layers, and they catch most of the regressions that creep in when I refactor.

```python
# tests/test_router.py
import pytest
from agent.router import pick_model

@pytest.mark.parametrize("question, expected_tier", [
    ("How many rows are there?", "flash"),
    ("Show me the average revenue by month", "flash"),
    ("For each user cohort, compute the 30-day retention windowed by signup month and rank cohorts by 90-day LTV", "pro"),
])
def test_router_picks_correct_tier(question, expected_tier):
    model = pick_model(question)
    assert expected_tier in model
```

For the LLM-generated layer (the SQL itself), I use a small fixture set of 12 questions with known correct results from a fixed Parquet file. The test runs the full pipeline and asserts that **the result DataFrame is non-empty and has the expected column count.** I don't test that the SQL is byte-identical between runs — that's a brittle test against a probabilistic system. I test that the answer remains useful, which is what actually matters in production.

When something fails this test set, I add the failing question to the fixtures, fix the prompt or system instruction, and rerun. Over six months this suite has grown to 47 cases and acts as my safety net when I tweak the prompt.

## When Not to Use This Stack

I want to be straight about where this design breaks down, because following the herd into "agentic SQL" without thinking about fit will burn you.

**Don't use this if your data lives in many tables with complex relationships.** A 10-table schema with foreign keys, soft deletes, and historical versioning is asking too much of any LLM. Gemini will produce SQL that compiles but joins on the wrong key, and the self-correction loop won't catch semantic errors. For relational complexity beyond 4–5 tables, you're better off with a fixed-question dashboard or a tool like dbt with an LLM only generating final aggregations against pre-modeled marts.

**Don't use this for high-stakes financial or compliance reporting.** "The agent says revenue was $X" is not a quote you want in a board deck unless you've manually validated the SQL. This stack is for personal exploration, indie product analytics, and internal team curiosity — not for numbers that go on tax filings or investor reports. For those, write the SQL once, version-control it, and have humans review the logic.

**Don't use this if your data is genuinely huge** (think hundreds of GB or petabytes). DuckDB scales further than people expect — to a few hundred GB on a laptop with enough RAM — but at some point you'll want columnar storage on object stores, distributed execution, and proper data engineering. Gemini-as-translator still applies; just swap DuckDB for ClickHouse, MotherDuck, or BigQuery as your engine.

**Don't use this for highly sensitive PII you can't send to Gemini.** Even though only the schema (not the data) is sent to the API, schema names sometimes leak intent — a column named `medical_diagnosis_icd10` already tells Gemini what the table is about. If you have hard data residency or PII-handling constraints, run a local model (Gemma 3, Llama, etc.) for the SQL generation step. The pattern still works; you're just swapping the brain.

## Iterating from "It Works" to "I Trust It"

The first version of this agent was usable in a weekend. The version I trust took several months. The gap between those two states is mostly about **building intuition for what the agent gets wrong**, then patching those failure modes one at a time.

Some patches worth describing:

- **Currency-aware aggregations.** I add a hint to the schema text like "amount_usd column is in USD; amount_jpy is in JPY" so Gemini doesn't blindly sum across currencies. The hint is one line; it eliminated a class of subtly wrong answers.
- **Date timezone clarification.** Same trick: a line in the schema text saying "date column is UTC; tz_local is JST". Without this, Gemini happily mixed tz_local with date when filtering "yesterday."
- **Domain glossary.** I keep a `glossary.txt` with definitions of "active user," "MRR," "churn" specific to my product. This file is appended to every prompt's system instruction. Without it, Gemini uses textbook definitions that don't match how I count things.

These are small additions, but each one came from a real wrong answer that I noticed in the wild. Over time the agent's accuracy converges on "the way I'd query the data myself," which is what I wanted from the start.

## Production Pitfalls and Fixes

The agent worked end-to-end early, but production tripped me up several times. Sharing the holes I fell into so fewer of you have to.

**Pitfall 1: Streamlit sessions sharing state by accident.** Streamlit reuses the server process by default, so if you misuse `st.session_state` another user can end up sharing your DuckDB connection. **Always access `con` through `st.session_state`.** Before deploying to Streamlit Community Cloud, test with two browser windows — one normal, one in incognito.

**Pitfall 2: Spaces or Japanese characters in column names break SQL generation.** AdMob and Stripe CSVs hit this trap reliably. When extracting the schema, run column names through `quote_identifier()` and include the quoted form in `schema_text`.

**Pitfall 3: `read_parquet(?)` runs out of memory on files over 100 MB.** Streamlit reads the entire upload into memory first. In production, write the upload to disk and read it with `read_parquet('data/file.parquet')` by path. The "save then read" pattern stays stable at much larger scales — I've personally pushed it to about 6 GB without trouble. There's a subtler variant of this trap: even if the Parquet itself fits in memory, DuckDB's query result might not. Wrapping the result with `LIMIT 10000` in the system prompt as a default safety net protects against the case where Gemini writes a query that legitimately wants to return millions of rows. You can always remove the limit later when you know the query is well-bounded.

**Pitfall 4: Rate-limit (429) errors freezing the UI.** Gemini's free-tier RPM is finite and hit easily by repeated queries. Wrap `generate_sql` with `tenacity`'s `retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=2, min=4, max=20))`. Those numbers feel right in my own deployment.

**Pitfall 5: Underestimating SQL injection.** Generating SQL from natural language means a malicious prompt could in principle yield `DROP TABLE`. Always whitelist execution to SELECT-only with `sql.lower().startswith("select")`. Telling Gemini "don't generate non-SELECT statements" is helpful but never the last line of defense. If you accept untrusted input — say you're letting end users of a SaaS product ask questions of their own data — open a fresh DuckDB connection per request, attach only that user's data, and don't grant the connection any write capabilities. Defense in depth: prompt-level rule, code-level whitelist, connection-level scoping. Skip any of the three and you'll regret it eventually.

But to start alone, this is enough. Frankly, lighter tools that you can hold entirely in your own head tend to be the ones you actually keep using.

I hope this writeup, and the code that comes with it, helps someone reclaim a little time from data work the way mine has. Thank you for reading.
