Open DevTools in a recent Chrome build and type `await LanguageModel.availability()`. When your machine meets the requirements, the response comes back as `"available"` — and at that moment the browser in front of you has quietly become an inference engine running Gemini Nano.

Chrome's built-in AI APIs have matured noticeably over the past six months. I've been shipping a small web tool that relies on them in production, and the experience of "serving lightweight summarization and classification without any backend" has been genuinely fun to build around. This guide walks through the practical implementation patterns for the Prompt API and Summarizer API, grounded in what actually works today.

## When built-in AI is the right call

Compared with calling Gemini on the server, running inference on-device has a specific shape of strengths and weaknesses:

- **Good fits**: Input you'd rather never leave the user's device, UX where perceived latency matters more than raw accuracy, side projects where you want zero API cost, and features that should keep working offline.
- **Poor fits**: Long-context tasks over hundreds of thousands of tokens, high-stakes reasoning (complex math, non-trivial coding), and anything that needs current world knowledge.

In my own projects I've limited it to UX-enhancing tasks where a mediocre response is still okay: tidying up a user's draft, summarizing clipboard contents into three lines, switching an avatar based on sentiment. Anything where correctness actually matters still goes to cloud-side Gemini 2.5 Pro or Flash.

## Environment requirements (as of April 2026)

Before any of this works, the browser needs:

- A recent Chrome build (128+ recommended; Chrome 135 at the time of writing)
- Windows 10/11, macOS 13+, modern Linux, or ChromeOS
- At least 22 GB of free storage (the model is about 2 GB, but the download needs headroom)
- 4 GB+ GPU VRAM, or a device where Gemini Nano has been pre-provisioned
- An internet connection — only for the initial model download

Android Chrome support has been rolling out gradually, but this guide assumes the desktop build.

### One-time enablement

1. Visit `chrome://flags/#prompt-api-for-gemini-nano` and switch to "Enabled"
2. Set `chrome://flags/#optimization-guide-on-device-model` to "Enabled BypassPerfRequirement"
3. Restart Chrome
4. Open `chrome://components/`, confirm that "Optimization Guide On Device Model" shows a non-zero version, and click "Check for update" if needed

The first download took about ten minutes on my laptop. You can watch progress on the components page, or surface it in-app via the `monitor` callback we'll see shortly.

## The minimum viable Prompt API call

Let's start with the simplest pattern: one prompt in, one response out. Drop this into an HTML file, open it in Chrome, and trigger the button — no build tooling required.

```html
<!doctype html>
<meta charset="utf-8" />
<title>Prompt API Minimum</title>
<button id="run">Summarize</button>
<textarea id="input" rows="6" cols="60">
I recently wired Chrome's built-in AI into a side-project web tool, and I can now ship a small AI feature without paying a cent in server costs. The UX feels snappier and the privacy story is easier to explain to users.
</textarea>
<pre id="output"></pre>
<script type="module">
const $input = document.querySelector("#input");
const $output = document.querySelector("#output");

document.querySelector("#run").addEventListener("click", async () => {
  // 1. Availability check — "available" / "downloadable" / "downloading" / "unavailable"
  const status = await LanguageModel.availability();
  if (status === "unavailable") {
    $output.textContent = "Prompt API is not supported on this device.";
    return;
  }

  // 2. Create a session (monitor reports download progress if needed)
  const session = await LanguageModel.create({
    monitor(m) {
      m.addEventListener("downloadprogress", (e) => {
        $output.textContent = `Fetching model: ${(e.loaded * 100).toFixed(1)}%`;
      });
    },
    initialPrompts: [
      { role: "system", content: "You are a summarizer. Respond in two sentences or fewer." },
    ],
  });

  // 3. Send a prompt
  const result = await session.prompt($input.value);
  $output.textContent = result;

  // 4. Always release resources when you're done
  session.destroy();
});
</script>
```

Expected result: something like "The author wired Chrome's built-in AI into a side-project tool, removing server costs while tightening privacy. The UX feels snappier."

Three things are worth highlighting. **Always call `availability()` first** — it's cheap and saves you from confusing `NotSupportedError` stack traces. **Pass the system message through `initialPrompts`**; the older `create({ systemPrompt })` shape was deprecated earlier in 2026. And **call `destroy()` when you're finished** so the runtime can reclaim GPU memory.

## Streaming for perceived speed

For anything longer than a sentence, streaming dramatically improves the feel of the feature. The Prompt API exposes an async iterator through `promptStreaming()`:

```js
async function streamRewrite(text) {
  const session = await LanguageModel.create({
    initialPrompts: [
      { role: "system", content: "Rewrite the given text in warm, natural English, preserving meaning." },
    ],
  });

  const stream = session.promptStreaming(text);
  let full = "";
  for await (const chunk of stream) {
    full += chunk; // As of late 2025, chunks are deltas — not the cumulative string
    document.querySelector("#output").textContent = full;
  }
  session.destroy();
  return full;
}
```

Older blog posts sometimes used a naive `=` assignment in the loop because early builds streamed the entire accumulated string on each tick. That's no longer the case: you receive genuine incremental deltas. If you copy code from a 2024 article and see duplicated output, that's almost always the reason.

## Multi-turn sessions

A single session carries its own conversation state. Each `prompt()` call takes prior turns into account. Gemini Nano has a smaller context window than cloud models, though, so you'll want a plan for trimming or resetting long conversations.

```js
const session = await LanguageModel.create({
  initialPrompts: [
    { role: "system", content: "Classify the input as risk level: low, medium, or high. Reply with the single word only." },
  ],
});

console.log(await session.prompt("I'm meeting a friend after work tomorrow."));
// → "low"
console.log(await session.prompt("Taking a red-eye flight, napping at the airport only."));
// → "medium"

// When the history grows long, clone into a fresh session and discard the old one
const fresh = await session.clone();
session.destroy();
```

`session.tokensLeft` gives you the remaining budget. A pragmatic pattern is to rotate sessions with `clone()` whenever `tokensLeft` drops below, say, 200.

## Summarizer API — the right tool for a narrow job

If all you need is a summary, the dedicated Summarizer API produces noticeably more stable results than freeform prompting and spins up faster. I use it for blog-post TL;DRs and it reliably produces something I can ship with a light edit.

```js
const summarizer = await Summarizer.create({
  type: "tl;dr",        // also: "key-points" / "teaser" / "headline"
  format: "plain-text", // "markdown" formats output as bullet points
  length: "short",      // "medium" / "long"
  sharedContext: "Technical blog posts — preserve the key insight so a busy reader still gets value.",
});

const text = document.querySelector("#article").innerText;
const summary = await summarizer.summarize(text);
console.log(summary);

summarizer.destroy();
```

`sharedContext` is a metadata hint describing the kind of text this instance will handle. Labeling it as "technical blog posts," "customer reviews," or "meeting notes" meaningfully nudges the tone of the result.

### Picking between Prompt API and Summarizer API

A pattern I have converged on: reach for Summarizer first. Its narrower contract means the output is more predictable, it reuses a specialized inference path, and you write less prompt engineering. Only drop back to the general Prompt API when you actually need free-form generation, classification with custom labels, or multi-turn interaction. Building this way has kept my code smaller and my eval suite simpler.

Another small win: Summarizer accepts a `sharedContext` once and reuses it across many `summarize()` calls. If you are batching a list of items (reviews, comments, chat logs), create one summarizer at the top of the handler and iterate — avoid the anti-pattern of spinning up a fresh instance per item.

## Traps I've stepped on

A few hard-won notes from my own projects:

- **`availability()` gets stuck on `"downloadable"`**: `LanguageModel.create()` needs to run inside a user gesture (click, keypress). Calling it on page load won't start the download — the browser intentionally gates it.
- **`NotSupportedError: The model execution service is not available`**: Either `chrome://components/` shows a stale model version, or the `optimization-guide-on-device-model` flag never got toggled. Both are easy to miss.
- **Parallel `prompt()` calls on one session fail with `InvalidStateError`**: One session handles one request at a time. For parallelism, create multiple sessions via `session.clone()` or `LanguageModel.create()`.
- **Safety filters can return empty strings**: Inputs that trip safety heuristics come back blank. Always guard with `result.trim().length === 0` and show a fallback message in production code.
- **Offline first-run isn't supported**: Once the model is cached it works offline, but the first call on a brand-new profile needs the network. Combine `navigator.onLine` with `availability()` to show meaningful error states.

## Feature detection and graceful fallback

Not every visitor has a compatible browser. The realistic pattern is **feature detection plus a server-side fallback**:

```js
async function getAvailableAI() {
  if (typeof LanguageModel === "undefined") return "none";
  const status = await LanguageModel.availability().catch(() => "unavailable");
  if (status === "available") return "on-device";
  if (status === "downloadable" || status === "downloading") return "on-device-pending";
  return "server";
}

const mode = await getAvailableAI();
if (mode === "on-device") {
  // Use the built-in Prompt API
} else if (mode === "server") {
  // Fall back to a server route backed by the Gemini API
  await fetch("/api/summarize", { method: "POST", body: text });
}
```

This two-track design keeps the feature available everywhere while opportunistically taking the fast path. For the server side, the patterns in [Gemini 2.5 Pro API Complete Guide 2026](/articles/gemini-api/gemini-25-pro-api-complete-guide-2026) and [Gemini Nano On-device AI Primer](/articles/gemini-dev/gemini-nano-on-device-ai-guide) translate cleanly.

## Measuring performance in practice

A rough sanity check I keep returning to: how does on-device compare with a cloud call on the same task?

- **First-token latency**: On a mid-range laptop, built-in Gemini Nano typically starts streaming in 100–300 ms from a warm session. A cloud Gemini 2.5 Flash call, including the round trip, usually lands in 400–900 ms. The gap gets more pronounced on flaky mobile networks.
- **Throughput**: Cloud Flash generates faster on a per-token basis. For short responses the user never notices, but for anything over a couple of hundred tokens, the cloud pulls ahead.
- **Cold start**: A freshly loaded session on device can take a few seconds before the first prompt. Pre-warming the session on user intent (hover, focus) is a pattern worth adopting.
- **Cost per request**: On-device is free. That is the feature. Once a task clears the accuracy bar, keeping it local tends to win purely on economics.

I keep a small log of these numbers per feature and re-measure whenever Chrome pushes a model update. Performance characteristics have moved meaningfully across versions.

## Where Prompt API does not belong

A few scenarios I have burned time on and now avoid:

- **Strict structured output** such as valid JSON against a long schema. Gemini Nano can do short JSON, but anything with many required fields drifts. Use the cloud Function Calling API for those cases.
- **Long-document workflows** that would need aggressive chunking. The ergonomic limit for a reliable single prompt is far below the cloud context window. If you find yourself building a chunker, you are probably fighting the wrong battle.
- **Regulated content generation** where you need an auditable trail. On-device responses do not produce server-side logs by default. If compliance cares, the cloud is the right home.

Knowing the boundary keeps the integration feeling light instead of turning into a workaround graveyard.

## Pre-ship checklist

The checks I run before deploying anything that uses built-in AI to `chrome.dev`:

- Non-compatible browsers still work via the server fallback
- Download progress is visible to the user via `monitor`
- `destroy()` is called on `beforeunload` (and on component unmount in SPAs)
- If prompts can include personal data, the UI clearly states that processing stays local
- Long-running sessions rotate via `clone()` before `tokensLeft` gets uncomfortably low
