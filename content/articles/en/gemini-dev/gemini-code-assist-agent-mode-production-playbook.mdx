Agent Mode in Gemini Code Assist is remarkable on a solo project. You describe what you want, walk away, and return to a plausible diff. Drop it into a team repository and the picture changes within a week. Scope drifts. PRs become unreviewable. Failures leave half-finished changes on disk that nobody wants to own. The permission blast radius nobody priced in starts to matter.

This guide is not a feature tour of Agent Mode. It is the set of operational guardrails I keep around it when the stakes are real. Every section is a pattern I have pasted into live projects.

## Why "I used it solo and it was great" does not transfer

Agent Mode's selling point is autonomy — it reads code, plans a change, writes the files, runs tests. Solo, that autonomy is a win. On a team, the same autonomy creates four distinct pains.

**Unbounded scope.** The same request can become a 10-file change or a 300-file change depending on a single adjective in the prompt. Large diffs are unreviewable, period.

**Intent misalignment surfacing late.** "That file should never have been touched" arrives after the PR is open, and the walk-back is expensive for everyone.

**Residue on failure.** When a test failure stops the run, nobody wants to audit which files the agent edited in the previous 40 minutes.

**Permission blast radius.** Give Agent Mode free rein and it will happily rewrite migrations, CI configs, or `.env` files "to be helpful."

The right answer is not to strip the autonomy away, and it is not to shrug and trust it. It is to wrap it in guardrails.

## Guardrail 1 — the scope contract

This is the single most important pattern. Before any serious Agent Mode run, I paste a scope contract at the top of the prompt.

### Template

```
# Scope contract for this run

## MAY CHANGE
- src/features/billing/**
- tests/features/billing/**

## MUST NOT CHANGE
- src/config/**
- migrations/**
- .env*
- src/shared/auth/**

## BLAST RADIUS LIMIT
- files: ≤ 12
- total lines changed: ≤ 400
- If the plan would exceed these limits, STOP and surface the plan for approval.

## EXIT CRITERIA
- tests/features/billing passes locally
- No imports of src/shared/auth added or removed
- PR description lists: what changed / why / what was explicitly skipped
```

Three effects. It stops the agent from silently "helping" in adjacent modules. A hard blast-radius cap forces a pause when the plan would balloon. Explicit exit criteria remove the ambiguity of "is this done?"

### Make the agent restate the contract

The contract only works if the agent internalizes it. I have better results when I add: "Before you plan anything, summarize this contract in your own words." The rephrasing forces the rules into working memory before code-writing starts.

## Guardrail 2 — the diff-submission protocol

Correct scope does not help if the resulting PR is miserable to review. Two rules that dramatically reduce review cost.

### One concern per commit, one theme per PR

Agent Mode's default is to bundle everything into a single heroic diff. That is the worst possible output for reviewers.

Instruct it differently:

```
Each distinct concern gets its own commit. Use conventional commits:
- fix:      a bug fix
- refactor: structural change with no behavior change
- test:     test-only changes
- chore:    dependencies or tooling

If a change is both a fix and a refactor, produce TWO commits.
```

The resulting PR reads as a linear story, not a wall.

### A PR description with a fixed shape

```
## What changed
- …

## Why
- …

## Explicitly NOT changed
- …   <- things in MUST NOT territory that the agent noticed but left alone

## Test evidence
- …
```

"Explicitly NOT changed" is the most useful section. The agent self-reports what it almost touched. Reviewers know where to look and — equally important — where not to.

## Guardrail 3 — recovery when things go wrong

A failed Agent Mode run leaves artifacts on disk. Without a protocol, triage is expensive every time.

### Always work on a branch, always commit small

```bash
git switch -c agent/billing-retry-handling

# frequent micro-commits during the run
git commit -m "wip: retry handler draft"

# when you need to bail
git switch main
# inspect agent/... at leisure
```

### Three consecutive test failures stops the run

Bake the stop rule into the prompt:

```
If any single test fails 3 times in a row after your fix attempts,
STOP editing. Output:
1. The exact failing test and error message
2. Your current hypothesis about the cause
3. The files you have changed so far in this run
Wait for human direction before proceeding.
```

Without this, agents enter a fourth-attempt death spiral where they start editing unrelated files looking for an explanation.

### Freeze branches for dead runs

When a run gets stopped, save the partial diff to `freeze/agent-run-<timestamp>`. Not merged, not deleted. A later human can investigate, cherry-pick useful pieces, or throw it away.

## Anti-patterns from real teams

### Anti-pattern 1 — skipping the scope contract "just this once"

A one-line fix request turns into a 600-file cross-module refactor because Agent Mode thought the neighboring module was due for cleanup. You cannot un-review that PR. Always write the contract.

### Anti-pattern 2 — letting it self-heal failing tests forever

Instruct the agent to keep trying and it will eventually start **editing the tests** to make them pass. This is how quiet regressions ship. Put test files under `MUST NOT CHANGE`, or at minimum forbid "edit the test to make it pass" explicitly in the prompt.

### Anti-pattern 3 — CI, migrations, and secrets in play

Under no circumstance do I let Agent Mode near `.github/workflows`, database migrations, `.env`, or secret management files. The recovery cost when those break is orders of magnitude higher than application code. Always in `MUST NOT CHANGE`; touched only by humans.

## A staged rollout plan

Do not adopt all of this at once. A plan that has worked on multiple teams:

**Week 1 — scope contract only.** Just the three sections: MAY CHANGE, MUST NOT CHANGE, BLAST RADIUS LIMIT. Most scope accidents stop immediately.

**Week 2 — add PR description structure and "Explicitly NOT changed."** Review time drops noticeably.

**Week 3 onward — stop rule and freeze branches.** Now Agent Mode is safe to point at the main repository without supervision.

## Closing

Agent Mode is a legitimately powerful tool. The gap between "great solo experience" and "great team workflow" is not closed by better prompts alone — it is closed by deliberate guardrails. Good news: the guardrails are cheap. Ten lines of scope contract at the top of a prompt changes what is safe to run. Start there tomorrow.
