Since Gemma 4's release, running it locally has become one of the most popular ways to experiment with a high-performance open model at zero cost. But getting it to actually run smoothly is a different story. Between cryptic error messages, freezing downloads, and frustratingly slow inference, the setup process can throw you off before you even get started.

This guide focuses on the specific errors that come up most often — whether you're using Ollama or LM Studio — and gives you actionable fixes rather than vague advice. If you've spent time searching for what "model manifest: file does not exist" actually means, or why your GPU isn't being used despite installing all the right drivers, this guide is for you.

## Before You Start: Hardware Reality Check

One thing that saves a lot of frustration is matching your model size to your hardware before downloading anything. Gemma 4 comes in three main sizes, each with different RAM and VRAM requirements:

- **2B**: Runs comfortably on most modern laptops (8GB RAM minimum)
- **9B**: Works well on machines with 16GB RAM or a GPU with 8GB+ VRAM
- **27B**: Needs 32GB+ RAM for CPU inference, or a GPU with 16GB+ VRAM for full GPU offload

On Apple Silicon (M1/M2/M3/M4), unified memory means RAM and VRAM are shared — a 32GB M3 Mac can comfortably handle the 27B model in 4-bit quantization.

If you're on a 16GB Windows machine with an 8GB GPU, stick with the 9B or use a quantized variant of the 27B (`q4_K_M`). Trying to force the 27B on underpowered hardware leads to crashes and frustration, not a working setup.

## Ollama: The Three Errors You're Most Likely to Hit

### Error 1: `pull model manifest: file does not exist`

This one tends to catch people who type the model name from memory:

```bash
ollama run gemma4
# Error: pull model manifest: file does not exist
```

**Why it happens**: Ollama is strict about model tags. `gemma4` by itself isn't a valid tag — you need to specify a size variant like `gemma4:27b` or `gemma4:2b`. The model registry requires an exact match, including the size suffix.

**Fix**: Check what's available first, then use the correct tag:

```bash
# See available Gemma 4 models and their tags
ollama search gemma4

# Run the 27B variant
ollama run gemma4:27b

# Or the lightweight 2B version
ollama run gemma4:2b

# Check what's already downloaded locally
ollama list
```

Running `ollama list` after downloading a model confirms the exact tag you have locally — handy when you're not sure what's been installed. The output will show the full model name including tag, size on disk, and when it was last modified.

---

### Error 2: Download Stalls Midway

Gemma 4's 27B model is a large file — often 15GB or more depending on the quantization level. Downloads can stall, especially on slower or unstable connections:

```
pulling manifest...
pulling xxxxxxxx: 34% ▕████████      ▏ 5.9 GB/17.4 GB  ...stopped
```

**Fix**: Ollama supports resuming interrupted downloads. Just rerun the same command:

```bash
ollama run gemma4:27b
```

Ollama checks the existing partial download and picks up from where it left off. This works reliably in most cases. If the process was killed abruptly, a partial file may remain in a corrupt state. In that case, delete the model and start fresh:

```bash
ollama rm gemma4:27b
ollama run gemma4:27b
```

If downloads keep stalling at the same percentage, try switching to a different quantized variant. The `q4_K_M` version is roughly half the size of the `fp16` version and downloads faster, making it a better starting point for most hardware:

```bash
# Quantized 4-bit version (smaller download, good quality tradeoff)
ollama run gemma4:27b-it-q4_K_M
```

---

### Error 3: Not Enough Memory to Load the Model

```
Error: model requires more system memory (24 GB) than is available (16 GB)
```

Note that this refers to system RAM, not GPU VRAM specifically — Ollama uses CPU inference as a fallback when there's insufficient GPU memory, and that requires the full model to fit in RAM.

**Fix option 1**: Switch to a smaller model size:

```bash
# 27B too large? Try 9B instead
ollama run gemma4:9b
```

**Fix option 2**: Use a quantized version that requires less memory. The `q4_K_M` suffix indicates 4-bit quantization, which dramatically cuts memory usage with a modest quality tradeoff:

```bash
ollama run gemma4:27b-it-q4_K_M
```

**Fix option 3**: If you want GPU acceleration and have limited VRAM, adjust how many transformer layers are offloaded to the GPU. Ollama lets you control this via environment variable:

```bash
# Offload as many layers as possible to GPU
OLLAMA_NUM_GPU=999 ollama run gemma4:27b

# Or specify a fixed number (e.g., 20 out of 43 total layers)
OLLAMA_NUM_GPU=20 ollama run gemma4:27b
```

The layers that don't fit on the GPU will fall back to CPU. This hybrid approach (partial GPU offload) is slower than full GPU inference but much faster than CPU-only, and it works on many mid-range setups.

## LM Studio: Fixes for the Most Common Problems

### The Model Won't Load (or Crashes on Startup)

You click "Load," nothing happens, or the app crashes within seconds. This is one of the most common issues for first-time users.

**Check 1 — GPU Offload Layers setting**

In the Model Settings panel, find the GPU Offload Layers slider. Setting it to 0 forces CPU-only inference — which is stable but slow. For GPU acceleration, push it higher. But too high will exceed your VRAM and cause crashes.

Practical starting point for Gemma 4 27B on an 8GB VRAM GPU:
- GPU Offload Layers: 15–20 (out of 43 total layers)
- Context Length: 4096 (lower than default saves memory significantly)

Start conservative and increase the layer count until you find the balance between speed and stability.

**Check 2 — File integrity**

An incomplete or corrupted download leads to a model that simply won't load, often without a helpful error message. In the "My Models" tab, right-click the model and choose "Reveal in Finder / Explorer." Compare the file size to what's listed on the Hugging Face model page. A mismatch means you need to re-download.

LM Studio also has a built-in model downloader that handles verification automatically — using it is more reliable than downloading GGUF files manually and placing them in the models folder.

---

### Inference is Extremely Slow (Under 1 Token/Second)

If output is crawling at 1 token per second or slower, you're almost certainly running on CPU inference. Getting this right is usually just a settings issue.

**On Mac (Apple Silicon)**: LM Studio supports MPS (Metal Performance Shaders) natively, so GPU acceleration should kick in automatically. If it isn't working, close the app completely, relaunch, and reload the model. Occasionally a restart is all it takes.

**On Windows with NVIDIA GPU**: Make sure you downloaded the CUDA build of LM Studio — available on the download page labeled "With CUDA." The standard installer doesn't include CUDA support.

You can verify which inference mode is active by checking the inference log in LM Studio's console:

```
[INFO] GPU layers: 0/43   ← CPU-only (slow)
[INFO] GPU layers: 43/43  ← Full GPU offload (fast)
[INFO] GPU layers: 20/43  ← Hybrid CPU+GPU
```

If GPU layers stay at 0 despite correct settings, a driver update may be needed. For NVIDIA, the CUDA toolkit version also matters — LM Studio typically requires CUDA 11.8 or later.

---

### Garbled Output or Responses Cutting Off Mid-Sentence

Gemma 4 is a multilingual model, but LM Studio's default prompt template may not be tuned for it. Using the wrong template can cause incomplete responses, repetition, or garbled characters.

**Fix**: In the Chat screen, change the **Preset** to "Gemma Instruct" — this matches the format Gemma 4 was trained with. If that's not available, "ChatML" is a reasonable fallback.

Adding a system prompt also significantly improves response consistency:

```
You are a helpful assistant. Always respond concisely and in complete sentences.
```

If you're working with non-English text, specify the language explicitly in the system prompt. Gemma 4 handles multiple languages well when given clear instructions, but without them it may default to English even when prompted in another language.

## Can't Connect to the Ollama API (`localhost:11434`)

When calling the Ollama API from Python or another client after running the model, some users hit connection errors:

```python
import requests

response = requests.post("http://localhost:11434/api/generate", json={
    "model": "gemma4:9b",
    "prompt": "Hello",
    "stream": False
})
# ConnectionRefusedError: [Errno 111] Connection refused
```

**Cause 1 — Ollama server isn't running as a background service**

Running `ollama run` starts both the server and the model in a single process. When the session ends, the server stops. To keep the server running independently:

```bash
# Start the server in background mode
ollama serve

# On Linux with systemd
systemctl start ollama
systemctl enable ollama  # auto-start on boot
```

**Cause 2 — Blocked by firewall or restricted to localhost**

By default, Ollama only listens on `localhost`. Connections from other machines or Docker containers won't work. To accept connections from any interface:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

Use this only on trusted networks — exposing Ollama to the internet without authentication is a security risk.

**Quick sanity check with curl before writing any client code**:

```bash
curl http://localhost:11434/api/generate \
  -d '{
    "model": "gemma4:9b",
    "prompt": "What is 1+1?",
    "stream": false
  }'
```

A valid JSON response confirms the server is up and the model is loaded. If this works but your Python client doesn't, the issue is in your client code, not Ollama itself — check the port number and endpoint path first.

## When Nothing Above Works: A Checklist

If you've worked through all the above and it's still not working, go through this list:

- **Update Ollama or LM Studio** — older versions may not support Gemma 4's newer quantization formats or GGUF variants
- **Check the GGUF format version** — if you downloaded a GGUF manually from Hugging Face, confirm it's GGUF v3 compatible with your tool version
- **Disk space** — the 27B model needs roughly 15–20GB after quantization. Check with `df -h` on Linux/Mac or Disk Management on Windows
- **Read the logs** — LM Studio writes logs to `~/.cache/lm-studio/logs/`. Error messages there are usually more detailed than what the UI shows
- **Try a different quantization level** — if `q4_K_M` crashes, try `q8_0`; if `q8_0` crashes, try `q4_0`. Quality differences are small, stability differences can be significant
