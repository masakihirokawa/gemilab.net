If you spend real time in Obsidian, you have probably noticed how often a tool like Gemini could help — summarizing a long meeting note, surfacing older notes that relate to what you are writing, turning a rough brain dump into a clean outline. The awkward part is that most of us do this by copying text out of Obsidian, pasting it into a browser tab, and copying the answer back. The context you just loaded into your head leaks away with every alt-tab, and the friction compounds over a working day.

What changes the experience is not a bigger model, but moving the AI **inside** the note you are writing. Obsidian exposes a plugin API, and with a few hundred lines of TypeScript you can wire the Gemini API directly into your own vault. This walkthrough covers the full path — from a minimal plugin shell to a working "suggest related notes" command — along with the pitfalls that matter once you plan to share it with anyone other than yourself.

I should note up front that nothing here depends on a paid Obsidian Sync subscription, and the Gemini API's free tier is generous enough to run everything below for months on a personal vault. The only prerequisites are a Google AI Studio account for the key, Node.js on your machine, and a working TypeScript toolchain — the sample plugin sets the last one up for you.

## The minimum viable plugin

An Obsidian plugin is an ES module that the Electron host loads at startup. You need three files: `main.ts`, `manifest.json`, and a bundler config (esbuild by default). Starting from the official sample plugin skips most of the setup and gives you a working hot-reload loop in a minute.

```bash
# Work inside your own vault so the plugin hot-reloads
cd /path/to/vault/.obsidian/plugins
git clone https://github.com/obsidianmd/obsidian-sample-plugin.git gemini-assist
cd gemini-assist
npm install
npm run dev  # watch mode builds main.js on save
```

Rename the `id` in `manifest.json` to something unique (for example `gemini-assist`), restart Obsidian, and enable the plugin from Settings → Community plugins. From here on you only need to extend `main.ts` — every save rebuilds `main.js`, and toggling the plugin off and on reloads it inside the app.

The plugin base class is intentionally small. You register commands and setting tabs in `onload`, and clean up anything long-lived in `onunload`. Keeping `onunload` honest matters more than it sounds: without it, every time a user disables and re-enables your plugin during testing you leave background timers and event listeners behind, which is the single easiest way to exhaust the main process.

```typescript
import { Plugin, Notice } from "obsidian";

export default class GeminiAssistPlugin extends Plugin {
  async onload() {
    this.addCommand({
      id: "gemini-hello",
      name: "Gemini: Hello from plugin",
      callback: () => new Notice("Plugin is alive"),
    });
  }
  async onunload() {}
}
```

## Storing the Gemini API key without hard-coding it

You need an API key to call Gemini, and hard-coding one is a reliable way to leak it into a public repository. Obsidian's `loadData` / `saveData` helpers give every plugin a private JSON file outside the vault's note tree, which is the right place for user-scoped settings during development.

```typescript
import { App, PluginSettingTab, Setting } from "obsidian";

interface GeminiSettings {
  apiKey: string;
  model: string;
}

const DEFAULT_SETTINGS: GeminiSettings = {
  apiKey: "",
  model: "gemini-2.5-flash",
};

export class GeminiSettingTab extends PluginSettingTab {
  constructor(app: App, private plugin: GeminiAssistPlugin) {
    super(app, plugin);
  }
  display(): void {
    const { containerEl } = this;
    containerEl.empty();

    new Setting(containerEl)
      .setName("Gemini API Key")
      .setDesc("Paste the key you generated in Google AI Studio.")
      .addText((t) =>
        t.setValue(this.plugin.settings.apiKey).onChange(async (v) => {
          this.plugin.settings.apiKey = v.trim();
          await this.plugin.saveSettings();
        })
      );

    new Setting(containerEl).setName("Model").addDropdown((d) =>
      d
        .addOptions({
          "gemini-2.5-flash": "gemini-2.5-flash (fast)",
          "gemini-2.5-pro": "gemini-2.5-pro (smart)",
        })
        .setValue(this.plugin.settings.model)
        .onChange(async (v) => {
          this.plugin.settings.model = v;
          await this.plugin.saveSettings();
        })
    );
  }
}
```

On the plugin side you load settings with `Object.assign({}, DEFAULT_SETTINGS, await this.loadData())` and persist them with `await this.saveData(this.settings)`. The `Object.assign` pattern is important — without it, upgrading a plugin that adds a new setting will read back `undefined` for that field and crash on the first command. For personal use this is enough. For distribution you probably want the key to live in the OS credential store instead, which I come back to at the end.

## A useful first command: "Summarize selection"

The first command worth shipping is one that summarizes whatever text you have selected in the editor. Obsidian's `Editor` gives you `getSelection()`, and the Gemini SDK does the rest. I deliberately pick a simple, single-shot example here — you will feel the difference as soon as it runs inside Obsidian for the first time.

```typescript
import { Editor, Notice } from "obsidian";
import { GoogleGenAI } from "@google/genai";

async function summarize(apiKey: string, model: string, text: string) {
  const ai = new GoogleGenAI({ apiKey });
  const res = await ai.models.generateContent({
    model,
    contents: `Summarize the following note in three sentences.\n\n---\n${text}`,
    config: { temperature: 0.3, maxOutputTokens: 512 },
  });
  return res.text ?? "";
}

// Register inside onload
this.addCommand({
  id: "gemini-summarize-selection",
  name: "Gemini: Summarize selection",
  editorCallback: async (editor: Editor) => {
    const sel = editor.getSelection();
    if (!sel) {
      new Notice("Select some text first.");
      return;
    }
    try {
      const summary = await summarize(this.settings.apiKey, this.settings.model, sel);
      editor.replaceSelection(
        `${sel}\n\n> [!summary] Gemini\n> ${summary.replaceAll("\n", "\n> ")}\n`
      );
    } catch (e) {
      new Notice(`Gemini error: ${(e as Error).message}`);
    }
  },
});
```

Three things in this snippet are worth calling out. First, the command keeps the original selection and appends a callout block below it rather than overwriting — destructive replacements feel wrong the first time a user tries a preview, and "undo" never quite restores the text cleanly in a Markdown document with mixed whitespace. Second, errors land in `Notice` so the user actually sees them; swallowing a rejected promise inside `editorCallback` is the easiest way to ship a command that silently does nothing on rate limits. Third, because Obsidian runs on Electron, the Node-flavored `@google/genai` SDK works without CORS tricks. That alone makes Obsidian a more forgiving environment than a Chrome extension, where every call has to be routed through a background service worker.

## Suggesting related notes across the vault

Obsidian's strength is the graph of links between notes, so having Gemini surface notes you had forgotten about is one of the most satisfying uses of the plugin system. For a first version we can skip embeddings and feed titles as plain text — less accurate than vector search, but zero infrastructure and nothing new to maintain.

```typescript
import { Editor, TFile } from "obsidian";

this.addCommand({
  id: "gemini-suggest-links",
  name: "Gemini: Suggest related notes",
  editorCallback: async (editor: Editor) => {
    const currentText = editor.getValue();
    const titles = this.app.vault
      .getMarkdownFiles()
      .map((f: TFile) => f.basename)
      .slice(0, 300); // cap context for vaults with thousands of notes

    const ai = new GoogleGenAI({ apiKey: this.settings.apiKey });
    const res = await ai.models.generateContent({
      model: this.settings.model,
      contents: [
        "Below is a list of note titles in a vault.",
        "Pick five titles that are likely related to the note currently being edited, with a short reason.",
        "Return them as `- [[title]] — reason` on separate lines.",
        "",
        `## Vault titles\n${titles.map((t) => `- ${t}`).join("\n")}`,
        "",
        `## Current note\n${currentText.slice(0, 4000)}`,
      ].join("\n"),
      config: { temperature: 0.2 },
    });
    editor.replaceSelection(`\n## Related notes (Gemini)\n${res.text}\n`);
  },
});
```

For vaults with more than three hundred notes you will want to narrow the list with a real similarity search first, otherwise the prompt bloats and recall drops quickly. A complete walkthrough of building one with Gemini embeddings lives in [Semantic search in production with Gemini Embeddings](/en/articles/gemini-api/gemini-embeddings-semantic-search-production); plugging it in front of the call above is straightforward and usually cuts the prompt in half.

If you want the response to stream into the editor instead of appearing all at once, swap `generateContent` for `generateContentStream` and keep a cursor updating on each chunk. Chunk-level error handling, cancellation, and the sharp edges of interleaving writes with the user's own typing are covered in [Streaming response control with the Gemini API](/en/articles/gemini-api/gemini-api-streaming-response-control-chunk-error-ux).

## Three gotchas to fix before you share it

Everything above works on your own machine, but once you hand the plugin to other people a few rough edges start to matter. These are the three that I have consistently hit when preparing a plugin for community review. Each of them is trivial to fix once you notice it, and each of them is easy to miss when you are the only user.

The first is **API key storage on someone else's device**. `saveData` writes JSON to `.obsidian/plugins/<id>/data.json` in plaintext. On a personal laptop that is fine. If the vault is synced to other machines through iCloud or a cloud folder, the key travels with it — including to devices the user may not even remember are syncing. A safer pattern is to keep the key out of `loadData` entirely and prompt for it at startup so it only lives in memory for the session. Obsidian's own plugin guidelines recommend against storing secrets in plugin data, and reviewers on the community plugin queue flag this more and more often.

The second is **spend control**. Gemini is usage-priced, and long notes plus a user who enjoys the command will run up real charges surprisingly fast. I default to `gemini-2.5-flash`, cap `maxOutputTokens` around 1,024, and trigger a `Notice` warning if the input passes twenty thousand tokens. Anything a user can trigger by muscle memory deserves a guardrail, and a Notice that says "this request will use ~35,000 tokens, continue?" converts frustrated bug reports into informed choices.

The third is **not blocking Obsidian's main thread**. Awaiting a single API call is fine, but processing every note in a vault in a tight loop will freeze the UI and the whole app with it. Break long jobs into batches with `setTimeout(fn, 0)` or yield to the event loop between chunks, and show progress through `Notice` or a modal progress bar. Without that, users assume the plugin is broken — and in a real sense it is, because Obsidian stops handling their keystrokes while you are iterating.

The same three patterns — key storage, spend control, and main-thread etiquette — apply to any AI integration that lives inside another app. If you are building inside a Chrome extension instead, [Building a Chrome extension AI assistant with the Gemini API](/en/articles/gemini-dev/gemini-api-chrome-extension-ai-assistant-guide) covers the same shape of problem in the browser's sandbox.

## Start with one command you will actually use

The fastest way past "I should learn the Obsidian API" is to pick one command you know you want — "summarize selection" is the lowest-friction choice — and put it into your own vault today. Once you feel the AI living next to your notes instead of behind a browser tab, the next ideas tend to write themselves: a "draft meeting notes" command, a "rewrite in my voice" command, a "link this to last week's journal" command.

One last note on feedback: the Obsidian community's plugin review process on GitHub is unusually thorough and kind. When I submitted a plugin for inclusion, the reviewer caught two issues I had missed and suggested a cleaner way to handle shutdown — both without any of the gatekeeping some ecosystems are known for. If you do decide to publish, treat that review thread as a free code-review pass from someone who ships plugins professionally.

When the plugin grows beyond a couple of commands, factoring the Gemini calls into an MCP server keeps tool calls and key handling out of every new plugin you write. [Building a custom MCP server for the Gemini API in TypeScript](/en/articles/gemini-dev/gemini-api-custom-mcp-server-typescript) shows that pattern end to end — come back to it when you start copying the same API code between plugins.
