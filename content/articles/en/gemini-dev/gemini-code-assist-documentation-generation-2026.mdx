Most developers are good at writing code and not so good at writing documentation about it. The README sits at "TODO: fill this in later" for months. The JSDoc comments never materialize. I've been there plenty of times with my own projects.

Gemini Code Assist's documentation generation addresses this in a genuinely practical way. Because it actually reads your code before generating anything, the output reflects your real implementation rather than producing generic filler text.

This guide covers the four main documentation tasks it handles well — inline code comments, README generation, API references, and CHANGELOG — along with the prompts and workflow details that make each one usable.

## What Gemini Code Assist Can Generate

To set expectations up front, here are the four documentation types covered in this guide:

- **Inline code comments** (JSDoc, Google Style Docstrings, JavaDoc, etc.)
- **README generation and updates** (project overview, setup steps, command reference)
- **API references** (endpoint summaries, type definitions, usage examples)
- **CHANGELOG generation** (from git commit history)

All of these work through the Gemini Code Assist extension in VS Code. Using `@workspace` context in the chat panel gives it visibility into the full project rather than just the open file.

## Generating JSDoc Comments

The most immediately useful feature is generating JSDoc comments for functions. Take this:

```typescript
// No documentation at all
export function calculateTax(
  amount: number,
  taxRate: number,
  applyDiscount: boolean = false
): number {
  const base = applyDiscount ? amount * 0.9 : amount;
  return Math.round(base * taxRate * 100) / 100;
}
```

With the cursor inside the function, either use the command palette ("Generate Documentation Comment") or ask in the chat:

```
Add a JSDoc comment to this function.
Include parameter types and descriptions, the return value, and one usage example.
```

Generated output:

```typescript
/**
 * Calculates the tax amount for a given price.
 *
 * @param {number} amount - The pre-tax amount in currency units
 * @param {number} taxRate - The tax rate to apply (e.g., 0.1 for 10%)
 * @param {boolean} [applyDiscount=false] - When true, applies a 10% discount before calculating tax
 * @returns {number} The calculated tax amount, rounded to two decimal places
 *
 * @example
 * // 10% tax on 1000, no discount
 * calculateTax(1000, 0.1); // => 100
 *
 * @example
 * // 10% tax with discount applied first
 * calculateTax(1000, 0.1, true); // => 90
 */
export function calculateTax(
  amount: number,
  taxRate: number,
  applyDiscount: boolean = false
): number {
  const base = applyDiscount ? amount * 0.9 : amount;
  return Math.round(base * taxRate * 100) / 100;
}
```

It picks up the discount logic (the `0.9` multiplier) and the rounding behavior from the implementation, which is what you actually want documented.

## Batch-Adding Comments to a File

For files with multiple undocumented functions, batch generation saves significant time:

```
Add JSDoc comments to all exported functions and classes in @filename.ts.
Don't overwrite existing comments — only add to functions that have none.
```

The "don't overwrite existing comments" instruction is important. Without it, you risk losing carefully written comments you've already created.

## Generating a README

For README generation, the `@workspace` context is what makes it work well:

```
@workspace Generate a README.md for this Next.js project.
Include these sections:
1. Project overview (2-3 sentences)
2. Requirements
3. Setup steps (commands that actually work, copy-paste ready)
4. Key commands
5. Environment variable documentation (reference .env.example)
6. Directory structure with brief explanations
```

With workspace context, it scans `package.json`, `tsconfig.json`, directory structure, and your existing configuration files before generating. That's what makes it possible to get a README with accurate setup commands rather than generic boilerplate.

After generation, verify these specifically:

- **Setup commands**: Does `npm run dev` match what's in `package.json`, or should it be `npm run start:dev`?
- **Environment variables**: Do the descriptions match the actual variables in `.env.example`?
- **Version requirements**: Are Node.js and package version requirements current?

## Generating an API Reference

For backend API routes, you can generate either OpenAPI-style or plain Markdown references:

```
@src/app/api Generate a Markdown API reference for all endpoints.
For each endpoint include:
- HTTP method and path
- Description (1-2 sentences)
- Request type definition (TypeScript)
- Example response (placeholder values are fine)
- Error cases
```

This works best when your route handlers have strong TypeScript types. The more specific the types, the more accurate the generated reference becomes. Loose `any` types produce vague documentation — which is a good incentive to keep types tight.

## Generating CHANGELOG from Git History

CHANGELOG maintenance is tedious. Automating it from git history is straightforward:

```bash
# Export the relevant commit range
git log --oneline --since="2026-01-01" > /tmp/git_log.txt
```

Paste the output into the chat and ask:

```
Generate CHANGELOG entries from this git log.
Categorize by Conventional Commits format (feat / fix / docs / chore).
Write each entry in clear English that non-developer readers can understand.

[paste git log here]
```

Even short commit messages like "fix: null check" get expanded into readable descriptions when there's surrounding context to work from. The output still needs editing, but it provides a solid starting draft.

## Improving Output Accuracy

**Strong types produce better documentation**

TypeScript projects with thorough type coverage give Gemini more to work with. When types are vague or missing, the generated descriptions tend to be vague too. This is one more reason to keep types explicit.

**Add intent comments for non-obvious logic**

The "why" behind a piece of logic often isn't inferrable from code alone. For anything that would confuse a new team member, a one-line `// This handles X because Y` comment gives Gemini the context to write accurate documentation.

**Reference an existing style**

You can tell Gemini to match an existing documentation style:

```
@workspace Update README.md.
Match the style of the Next.js project README at https://github.com/vercel/next.js
```

This produces output that feels consistent with well-established project conventions rather than something generic.

## What to Review After Generation

Auto-generated documentation should be treated as a draft, not a final artifact. Key things to check:

- **Security-adjacent information**: Any description of API key handling, authentication flows, or sensitive configuration should be verified for accuracy
- **Version-specific details**: Gemini may carry in slightly outdated version numbers or deprecated APIs — cross-check against current docs
- **Code samples**: Run any generated code examples to confirm they actually work

The fastest way to start is to pick one function in a current project and ask for JSDoc. If the output is more useful than what you'd have written manually, expand from there. Most people find the answer is yes.
