"I keep building SaaS products and getting stuck in commodity competition with everyone else." If you've felt that, you're in the same place I was for over a year. Generic writing tools, generic task managers — every time, the same loop: price pressure, scattered usage feedback, no clear product north star.

What broke me out of it was switching to **vertical depth**: pick one industry, pick one workflow inside that industry, and go all the way down. If horizontal SaaS is "wide and shallow," vertical SaaS is "narrow and deep" — and the narrow-and-deep posture is where Gemini 2.5 Pro's long-context reasoning and structured outputs actually shine.

This article is the implementation and operating playbook for taking a Gemini 2.5 Pro micro-SaaS to a realistic $1,500/month target through vertical depth. Working code, the reasoning behind each pattern, and the trade-offs I had to accept.

## Why Horizontal SaaS Burns You Out and Vertical Niches Don't

Horizontal SaaS exhausts founders because **users want different things**. "AI text generation" looks like one product; in practice marketers want tweet copy, editors want column outlines, and accountants want contract clauses. Trying to serve all of them softens every output edge until your product is "kind of useful but never the obvious choice."

Vertical SaaS solves this by deliberately narrowing the audience. "Trial-balance assistant for staff at small-firm tax accountants in Japan" instantly removes a hundred features and adds a few that nobody else implements: domain-specific Japanese accounting vocabulary in the prompt, output formatted close to the standard worksheet, diff against the prior month. Horizontal tools won't reach that depth — and that's your moat.

There's a second advantage that's underrated: **word of mouth carries inside an industry**. Most professional verticals have a community surface — three to five named accounts is enough for your product to start showing up in chats. You don't have to outspend incumbents on ads, which is exactly the game indie devs lose.

## How to Pick a Niche — Three Decision Criteria

The single biggest decision in this whole strategy is *which* industry. The three criteria I now use:

**1. You either know the industry already, or you can learn the basics in a week.**

Without baseline domain knowledge, you can't even write a useful spec. Pick an industry where you have personal exposure, family or friend connections, or enough public material to ramp in seven days.

**2. The target users sit at a computer for 3+ hours per day.**

Industries where workflows are still paper-and-stamp heavy raise the SaaS adoption hurdle dramatically. Pick verticals where the workday is digital.

**3. There's a workflow that repeats 10+ times per month.**

Charging for a once-a-month task is hard. Charging $30–$50/month for a workflow that runs 10+ times a month is realistic — and "structured repeats" is exactly what Gemini 2.5 Pro is good at.

Niches I've seen work: tax accountants and labor consultants, web agencies producing client reports, real-estate firms generating property descriptions, and clinics summarizing intake forms. None of them are reachable by horizontal tools at the necessary depth.

## Pattern 1: Use Gemini 2.5 Pro Structured Output to Match the Industry's Format

In a vertical, the **format** of your output is half the trust. Gemini 2.5 Pro's `responseSchema` lets you force the answer into industry-specific shape rather than freeform prose.

```typescript
// Structured trial-balance check for Japanese tax accountants
import { GoogleGenerativeAI, SchemaType } from "@google/generative-ai";

interface BalanceCheck {
  warnings: { account: string; reason: string; severity: "info" | "warn" | "error" }[];
  suggested_actions: string[];
  next_review_date: string;
}

async function checkTrialBalance(env: Env, csv: string): Promise<BalanceCheck> {
  const genai = new GoogleGenerativeAI(env.GEMINI_API_KEY);
  const model = genai.getGenerativeModel({
    model: "gemini-2.5-pro",
    generationConfig: {
      responseMimeType: "application/json",
      responseSchema: {
        type: SchemaType.OBJECT,
        properties: {
          warnings: {
            type: SchemaType.ARRAY,
            items: {
              type: SchemaType.OBJECT,
              properties: {
                account: { type: SchemaType.STRING },
                reason: { type: SchemaType.STRING },
                severity: { type: SchemaType.STRING },
              },
              required: ["account", "reason", "severity"],
            },
          },
          suggested_actions: {
            type: SchemaType.ARRAY,
            items: { type: SchemaType.STRING },
          },
          next_review_date: { type: SchemaType.STRING },
        },
        required: ["warnings", "suggested_actions", "next_review_date"],
      },
    },
  });

  try {
    const result = await model.generateContent(
      `Review the following trial balance (CSV) from a tax accountant's perspective and flag any suspicious accounts.\n\n${csv}`
    );
    const text = result.response.text();
    return JSON.parse(text) as BalanceCheck;
  } catch (error) {
    console.error("checkTrialBalance failed:", error);
    // Fallback: empty structure so the UI doesn't crash
    return { warnings: [], suggested_actions: [], next_review_date: "" };
  }
}
```

The detail that matters: the **field names map 1-to-1 to the user's working vocabulary**. A tax accountant says "warnings" and "suggested actions" in their daily work. Naming the schema with their words is what builds trust on the first run. Generic names like `summary` or `text` look amateurish to a domain user immediately.

The empty-fallback on error is non-negotiable in a vertical. When Gemini hiccups, the UI must read as "no issues found" rather than crashing. A blank fallback with logged error is far better than a 500.

## Pattern 2: Per-User Quota with Cloud Run + Cloudflare KV

Even in a vertical, you need fair quota enforcement. Cloud Run for the app surface plus Cloudflare KV for monthly counters is cheap and survives scale.

```typescript
interface UsageQuota {
  monthlyLimit: number;
  used: number;
  resetAt: string;
}

async function consumeQuota(env: Env, userId: string): Promise<{ allowed: boolean; quota: UsageQuota }> {
  const key = `quota:${userId}:${new Date().toISOString().slice(0, 7)}`; // YYYY-MM
  const raw = await env.QUOTA.get(key, "json") as UsageQuota | null;
  const quota: UsageQuota = raw ?? {
    monthlyLimit: 100,
    used: 0,
    resetAt: nextMonthStart(),
  };
  if (quota.used >= quota.monthlyLimit) {
    return { allowed: false, quota };
  }
  quota.used += 1;
  await env.QUOTA.put(key, JSON.stringify(quota), { expirationTtl: 60 * 60 * 24 * 35 });
  return { allowed: true, quota };
}

function nextMonthStart(): string {
  const d = new Date();
  d.setMonth(d.getMonth() + 1, 1);
  d.setHours(0, 0, 0, 0);
  return d.toISOString();
}

export async function handle(req: Request, env: Env): Promise<Response> {
  const userId = await authenticate(req, env);
  if (!userId) return new Response("Unauthorized", { status: 401 });

  const { allowed, quota } = await consumeQuota(env, userId);
  if (!allowed) {
    return new Response(
      JSON.stringify({ error: "monthly_quota_exceeded", quota }),
      { status: 429, headers: { "Content-Type": "application/json" } }
    );
  }

  const csv = await req.text();
  const result = await checkTrialBalance(env, csv);
  return new Response(JSON.stringify(result), { headers: { "Content-Type": "application/json" } });
}
```

The trick that simplifies everything: keying by `YYYY-MM`. You never write a "reset on month change" cron. The next month's key just doesn't exist yet, so the counter starts at zero naturally. Setting KV TTL to 35 days means old counters auto-expire without bookkeeping.

## Pattern 3: Industry-Specific Onboarding via Gemini Conversation

The biggest differentiator in a vertical is **the first 90 seconds**. A generic "Welcome! What's your name?" form loses domain users instantly. A Gemini-powered onboarding conversation that uses industry vocabulary builds trust in three turns.

```typescript
async function onboardingStep(env: Env, userInput: string, history: { role: string; content: string }[]) {
  const genai = new GoogleGenerativeAI(env.GEMINI_API_KEY);
  const model = genai.getGenerativeModel({ model: "gemini-2.5-pro" });
  const systemContext = `
You are the onboarding agent for a SaaS product built for tax accountancy firms in Japan.
Address the user using terminology they actually use day-to-day (試算表, 月次, 決算月, 関与先 etc.).
Ask exactly one question at a time. Aim to complete onboarding in three turns or fewer.
`.trim();

  const messages = [
    { role: "user", parts: [{ text: systemContext }] },
    ...history.map(h => ({ role: h.role, parts: [{ text: h.content }] })),
    { role: "user", parts: [{ text: userInput }] },
  ];

  try {
    const result = await model.generateContent({ contents: messages });
    return result.response.text();
  } catch (error) {
    console.error("onboarding failed:", error);
    return "Sorry — could you tell me that one more time?";
  }
}
```

Forcing the language match is what tips first impressions. Generic onboarding can't reach the depth of "this product gets my work."

## Pricing and Milestones Toward $1,500/Month

In a vertical, price comes from **the cost of the work being replaced**. If a staff member at a tax firm spends 2–3 hours per client per month doing the manual version of this check, that's $40–$60 of labor. Charging $34/month doesn't even register as expensive.

The pricing table I lean on:

- Starter: $19/month (50 runs)
- Standard: $34/month (150 runs — the actual target tier)
- Plus: $69/month (500 runs)

Milestones toward $1,500/month:

- Month 1: 3 Starters + 2 Standards = $125
- Month 3: 10 Standards + 1 Plus = $409
- Month 6: 20 Standards + 4 Plus = $956
- Month 9: 35 Standards + 6 Plus = $1,604

Reaching this curve isn't an ad-spend problem. It's a **two-to-three-hours-per-week-talking-to-domain-users** problem. Word of mouth inside the industry is the channel; you just have to be present and visible there.

## Common Mistakes I've Seen in Verticals

**1. Adding features for users outside the niche.** Twitter feedback from adjacent industries feels good but quietly dilutes the very depth that makes you defensible. **Only act on requests from paying users in your target industry.**

**2. Underestimating regulation.** Tax law, medical practice law, privacy law — every vertical has compliance edges. **Design which data leaves the boundary** (and which stays anonymized) before you write the prompt. PII in prompts is a one-incident reputation killer in a tight industry.

**3. Discounting too early.** When the first three customers are slow to convert, the temptation to "just offer half off" is real. But discounted prices spread inside small industries and **can't be raised back up**. If you must discount, scope it: first month only, annual contract only — something structurally justifiable.

## Closing — Picking a Niche Is Picking the Field of Play

From where I stand now, $1,500/month is genuinely **faster** to reach in a vertical than in horizontal SaaS. Horizontal asks you to outrun better-funded competitors. Vertical asks you to be the obvious answer for a small group — which is much more achievable for an indie.
