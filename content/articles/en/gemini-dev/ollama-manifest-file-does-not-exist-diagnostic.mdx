You type `ollama run gemma4:27b`, and Ollama answers:

```
Error: pull model manifest: file does not exist
```

Most articles will tell you to fix the tag name. Sometimes that is the answer. Often it is not, and you are left running the same command with slight variations for half an hour. This post is the diagnostic flow I wish I had the first time this happened to me. Five checks, in order, will land you on the real cause within ten minutes.

## Before you do anything else

Resist the urge to retry. Run this first:

```bash
ollama --version && ollama list
```

You want two facts on hand: your Ollama version and which models are already pulled. Every later step references one of these.

## Check 1 — tag name exactness (solves about 70% of cases)

Ollama's model identifiers are strict about casing and size tags. These all fail:

```bash
ollama run gemma4
ollama run gemma-4
ollama run Gemma4:27B
```

These succeed:

```bash
ollama run gemma4:27b
ollama run gemma4:9b
ollama run gemma4:2b
```

Three rules: no hyphen in the base name, never drop the size tag, no spaces around the colon. For the authoritative tag list, open the model page on [ollama.com/library](https://ollama.com/library) and look at the **Tags** tab. The CLI also returns a list, but it occasionally comes back empty behind restrictive networks — the browser is always a safer source of truth.

If this solves it, you are done. If not, move on.

## Check 2 — network path and proxies

When the tag is correct and the error persists, the message is usually the server returning 404 *or* your proxy failing mid-stream. Both surface as the same "manifest does not exist" line.

On a corporate or campus network, configure a proxy and restart the daemon:

```bash
export HTTPS_PROXY=http://your-proxy.example.com:8080
export HTTP_PROXY=http://your-proxy.example.com:8080

# macOS — restart the daemon so it picks up the env
pkill ollama
ollama serve &
```

Critical gotcha: **a running Ollama daemon does not pick up proxy variables set in a new shell**. You have to restart it. I have tripped over this twice.

If you are on a home connection, the registry itself could be having a bad minute. `curl -I https://registry.ollama.ai` should return 200.

## Check 3 — storage and permissions

A full disk or a locked models directory can surface as a manifest error rather than a clearer IO error.

```bash
# where models live
# macOS:    ~/.ollama/models
# Linux:    /usr/share/ollama/.ollama/models or ~/.ollama/models
# Windows:  %USERPROFILE%\.ollama\models

df -h ~/.ollama
ls -la ~/.ollama/
```

One case I have hit: a machine where someone had once run `sudo ollama serve`, leaving `~/.ollama/models` owned by root. Pulls by the normal user silently failed at the write step and only the manifest error bubbled up. Fix:

```bash
sudo chown -R $(whoami) ~/.ollama
```

## Check 4 — registry path mismatch

If your team runs a private registry, or you are pulling GGUF directly from Hugging Face, the tag format changes and a single typo reproduces the exact same error.

```bash
# Hugging Face GGUF
ollama run hf.co/google/gemma-4-9b-it-gguf:Q4_K_M

# Private registry
ollama run registry.internal.example.com/gemma4:27b-custom
```

Watch the slashes, the colon, and the quantization tag. Isolate the pull with `ollama pull <full-path>` — if you see a progress bar at all, you reached the registry, and the remaining problem is purely the tag/quant suffix.

## Check 5 — Ollama version drift

An older Ollama may not understand the manifest format used by a freshly released model. Around the Gemma 4 launch there was a short window where older Ollama binaries failed this way.

```bash
# macOS
brew upgrade ollama

# Linux
curl -fsSL https://ollama.com/install.sh | sh

ollama --version
```

Upgrade, then restart the daemon. Skipping the restart is the single most common reason "the upgrade didn't fix it."

## Last resort — nuke the cache and retry

When none of the above applies, a half-downloaded manifest cache could be the real culprit.

```bash
ollama rm gemma4:27b 2>/dev/null

# blow away the manifest directory only
# macOS
rm -rf ~/.ollama/models/manifests/registry.ollama.ai/library/gemma4

ollama pull gemma4:27b
```

Only remove the `manifests/` subtree first. Deleting `blobs/` means re-downloading gigabytes, so save that for truly stuck cases.

## After you fix it — three habits that keep it fixed

- Alias `ollama list` to something short like `ol`. The first debugging command should cost you two keystrokes, not fifteen.
- Keep a note of the exact tags you rely on. Memory will fail you and cost a quiet half hour.
- Write down the date every time you update Ollama. When a teammate says "it worked last month," you will want that timeline.

## The one-line version

Tag exactness → proxy + daemon restart → permissions and storage → registry path → Ollama version → cache nuke. In that order.
