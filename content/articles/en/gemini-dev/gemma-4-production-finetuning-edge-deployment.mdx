Gemma 4's open weights mean you can download and run inference immediately. But extracting real value in production requires more — domain-specific fine-tuning, resource-efficient quantization, and a robust inference pipeline that handles failures gracefully.

This guide walks through the complete production lifecycle for Gemma 4, from fine-tuning to monitoring, with concrete code you can adapt for your own deployments.

## Environment Setup and Model Selection

Before fine-tuning, choose the right model and hardware for your use case.

**Model selection criteria for fine-tuning:**

- **E4B:** Fits on consumer GPUs (RTX 3090/4090, 16GB VRAM) with QLoRA. Also works on Google Colab T4. Best when mobile deployment is the end goal
- **26B MoE (A4B):** Needs ~16GB VRAM with QLoRA. However, its 3D fused expert tensors have limited compatibility with bitsandbytes. A100/H100 recommended
- **31B Dense:** Full fine-tuning requires 2+ A100 80GB GPUs. LoRA/QLoRA works on a single A100 40GB. Choose this when maximum accuracy matters

## LoRA Fine-Tuning Implementation

LoRA (Low-Rank Adaptation) freezes the original model weights and trains only small adapter matrices. Even with Gemma 4's 31B Dense model, LoRA adds only ~10GB of memory overhead for training.

### Basic LoRA Configuration

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model, TaskType
import torch

# Load the model (31B Dense example)
model_name = "google/gemma-4-31b"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)

# LoRA configuration
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,                  # Rank (8-64 is typical)
    lora_alpha=32,         # Scaling factor (usually 2x rank)
    lora_dropout=0.05,     # Dropout rate
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",  # Attention layers
        "gate_proj", "up_proj", "down_proj",       # MLP layers
    ],
    bias="none",
)

# Apply LoRA adapter
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# Expected output: trainable params: 52,428,800 || all params: 31,052,428,800
# → Only ~0.17% of total parameters are trained
```

### QLoRA for Reduced Memory Usage

QLoRA combines 4-bit quantization with LoRA, cutting VRAM usage by an additional ~60%.

```python
from transformers import BitsAndBytesConfig

# 4-bit quantization config
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",        # NormalFloat4 quantization
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,    # Double quantization saves more
)

# Load model with QLoRA
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,
    device_map="auto",
)
model = get_peft_model(model, lora_config)

# Check memory usage
print(f"GPU Memory: {torch.cuda.memory_allocated() / 1e9:.1f} GB")
# 31B QLoRA → ~18GB (about 1/7 of full precision)
```

**Note on 26B MoE QLoRA:** Gemma 4's 26B MoE uses 3D fused expert tensors that the current version of bitsandbytes cannot quantize. For QLoRA, stick with E4B or 31B Dense.

### Accelerated Fine-Tuning with Unsloth

Unsloth uses hand-written backpropagation kernels to achieve 2–5x speedup and 50–80% memory reduction compared to standard Hugging Face training.

```python
from unsloth import FastLanguageModel

# Load model via Unsloth
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="google/gemma-4-31b",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapter
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_dropout=0.05,
)

# Prepare training data (Alpaca format example)
from datasets import load_dataset
dataset = load_dataset("your-org/your-dataset", split="train")

# Run training
from trl import SFTTrainer
from transformers import TrainingArguments

trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=TrainingArguments(
        output_dir="./gemma4-finetuned",
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,
        num_train_epochs=3,
        learning_rate=2e-4,
        bf16=True,
        logging_steps=10,
        save_strategy="epoch",
        warmup_ratio=0.1,
    ),
    max_seq_length=4096,
)

trainer.train()
# Expected output:
# Training Loss: 0.85 → 0.32 (converges over 3 epochs)
# Training time: ~2 hours (A100 40GB, 10K training examples)
```

## Quantization and Model Export

When deploying fine-tuned models, quantization tailored to the target environment is essential.

### GGUF Conversion for Ollama / llama.cpp

```bash
# Merge LoRA adapter and convert to GGUF
python -m llama_cpp.convert \
  --model ./gemma4-finetuned \
  --outfile gemma4-custom-Q4_K_M.gguf \
  --outtype q4_k_m

# Run with Ollama
cat > Modelfile << EOF
FROM ./gemma4-custom-Q4_K_M.gguf
PARAMETER temperature 0.7
PARAMETER top_p 0.9
SYSTEM "You are a helpful assistant specialized in..."
EOF

ollama create my-gemma4 -f Modelfile
ollama run my-gemma4 "Hello, how can you help?"
```

### Quantization Level Selection Guide

Each quantization level involves trade-offs between size and quality:

- **Q2_K (2-bit):** For E2B. Smallest size, noticeable quality loss. IoT and wearable use cases
- **Q4_K_M (4-bit):** For E4B and 26B. Best balance of size and quality. Recommended for most production deployments
- **Q5_K_M (5-bit):** For 31B. Quality-focused. Ideal for server-side deployment
- **Q8_0 (8-bit):** Nearly no quality degradation. Use when VRAM is abundant

## Android Edge Deployment

Gemma 4's E2B and E4B models support native execution on Android devices.

### Using Google AI Edge Gallery

Google AI Edge Gallery is the easiest way to integrate Gemma 4 into Android apps.

```kotlin
// Add dependency in build.gradle.kts
dependencies {
    implementation("com.google.ai.edge:litert-lm:0.1.0")
}

// Kotlin inference
import com.google.ai.edge.litert.lm.LmInference

class GemmaInference(context: Context) {
    private val inference = LmInference.create(
        context,
        modelPath = "gemma4-e4b-q4.task",
        maxTokens = 1024,
    )

    suspend fun generate(prompt: String): String {
        return inference.generateResponse(prompt)
    }

    // Streaming output
    fun generateStream(prompt: String, onToken: (String) -> Unit) {
        inference.generateResponseAsync(prompt) { partialResult ->
            onToken(partialResult)
        }
    }
}
```

## Building a Production Inference Pipeline

Production environments require more than a single model endpoint — you need scaling, monitoring, and fallback mechanisms.

### High-Throughput Inference with vLLM

```python
# Launch a vLLM inference server
# For 26B MoE or 31B Dense

from vllm import LLM, SamplingParams

llm = LLM(
    model="google/gemma-4-26b-a4b",
    tensor_parallel_size=2,     # Distribute across 2 GPUs
    max_model_len=8192,         # Maximum sequence length
    gpu_memory_utilization=0.9,
    quantization="awq",         # AWQ quantization for efficiency
)

# Batch inference
prompts = ["Explain quantum computing", "Write a Python function for..."]
params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    max_tokens=2048,
)
outputs = llm.generate(prompts, params)

for output in outputs:
    print(output.outputs[0].text)
```

### Production API with Docker + FastAPI

```python
# api_server.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import asyncio

app = FastAPI(title="Gemma 4 Inference API")

class InferenceRequest(BaseModel):
    prompt: str
    max_tokens: int = 1024
    temperature: float = 0.7

class InferenceResponse(BaseModel):
    text: str
    tokens_used: int
    latency_ms: float

@app.post("/generate", response_model=InferenceResponse)
async def generate(request: InferenceRequest):
    import time
    start = time.time()

    try:
        output = await asyncio.to_thread(
            run_inference,
            request.prompt,
            request.max_tokens,
            request.temperature,
        )
        latency = (time.time() - start) * 1000

        return InferenceResponse(
            text=output["text"],
            tokens_used=output["tokens"],
            latency_ms=round(latency, 2),
        )
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

# Health check endpoint
@app.get("/health")
async def health():
    return {"status": "healthy", "model": "gemma-4-26b-a4b"}
```

## Performance Monitoring and Optimization

Continuous monitoring of inference performance is critical in production.

### Collecting Key Metrics

```python
import time
from prometheus_client import Histogram, Counter, Gauge

# Prometheus metrics
INFERENCE_LATENCY = Histogram(
    "gemma4_inference_latency_seconds",
    "Inference latency in seconds",
    buckets=[0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0],
)
TOKENS_GENERATED = Counter(
    "gemma4_tokens_generated_total",
    "Total tokens generated",
)
GPU_MEMORY_USAGE = Gauge(
    "gemma4_gpu_memory_gb",
    "GPU memory usage in GB",
)

def monitored_inference(prompt, max_tokens=1024):
    start = time.time()

    output = model.generate(prompt, max_tokens=max_tokens)

    latency = time.time() - start
    INFERENCE_LATENCY.observe(latency)
    TOKENS_GENERATED.inc(len(output.tokens))
    GPU_MEMORY_USAGE.set(get_gpu_memory_gb())

    return output
```

### Optimization Checklist

Key optimizations for maximizing production performance:

- **Pre-allocate KV cache:** Reserve memory for the maximum sequence length at startup to avoid runtime allocations
- **Continuous batching:** Use vLLM's continuous batching to process multiple requests efficiently
- **Dynamic batch sizing:** Automatically adjust batch size based on request volume
- **Model warm-up:** Run dummy inference requests before serving traffic to initialize the inference path
- **Graceful shutdown:** Complete in-flight requests before stopping the server

## Error Handling and Fallback Strategy

A solid fallback strategy prevents downtime when primary inference fails.

```python
class GemmaInferenceWithFallback:
    def __init__(self):
        self.primary = load_model("gemma-4-31b-dense")   # Primary
        self.fallback = load_model("gemma-4-26b-a4b")    # Fallback
        self.max_retries = 3

    async def generate(self, prompt, **kwargs):
        # Try primary model
        for attempt in range(self.max_retries):
            try:
                return await self.primary.generate(prompt, **kwargs)
            except (torch.cuda.OutOfMemoryError, TimeoutError):
                if attempt < self.max_retries - 1:
                    await asyncio.sleep(0.5 * (attempt + 1))
                    continue

        # Fall back to secondary model
        try:
            return await self.fallback.generate(prompt, **kwargs)
        except Exception as e:
            raise InferenceError(f"All models failed: {e}")
```

## FAQ

### How much training data do I need for fine-tuning?

It depends on task complexity, but 1,000–10,000 high-quality samples typically produce meaningful improvements. 100 well-curated examples often outperform 10,000 noisy ones. Start small, validate results, then scale your dataset as needed.

### Should I use LoRA or full fine-tuning?

LoRA (or QLoRA) is sufficient for most use cases. It preserves the base model's general capabilities while adding domain specialization, with lower overfitting risk and dramatically reduced training cost. Consider full fine-tuning only when you need fundamental behavioral changes, such as adding a new language.

### Is battery consumption a concern for edge deployment?

For the E2B model with 2-bit quantization, battery impact is minimal. However, continuous inference will drain the battery noticeably — implement request batching and caching strategies. The E4B model consumes more power and is best run as a background process.

### What if fine-tuning fails on the 26B MoE model?

The MoE model's 3D fused expert tensors are incompatible with some tools. Your options are: use Unsloth (which has better MoE support), switch to the 31B Dense model, or use NVIDIA NeMo Automodel for fine-tuning.
