When Gemini 1.5 Pro launched with a million-token context window, my first thought was: "I can finally feed it an entire codebase." I tried it. Half of it worked the way I hoped. The other half didn't.

This article is an honest account of both halves.

## What Actually Worked Well

Long-context isn't a gimmick — there are real use cases where it delivers. These are the ones I found genuinely valuable.

**Cross-document question answering**

Loading specification documents, design docs, and meeting notes totaling tens of thousands of tokens and asking "where is this feature defined?" or "what was the rationale behind this decision?" works reliably. Not having to build a search index first, just loading everything and asking — this saved real time.

**Codebase-wide refactoring suggestions**

For a single repository where I wanted architecture-aware refactoring suggestions, loading all the related files together produced noticeably more coherent proposals than showing partial code. Context about how the pieces connect actually matters for this kind of task.

```python
import google.generativeai as genai

genai.configure(api_key="YOUR_API_KEY")
model = genai.GenerativeModel("gemini-1.5-pro")

def load_repository_context(file_paths: list[str]) -> str:
    parts = []
    for path in file_paths:
        with open(path) as f:
            parts.append(f"# File: {path}\n{f.read()}")
    return "\n\n".join(parts)

context = load_repository_context([
    "src/main.py",
    "src/models.py",
    "src/api/routes.py",
    "src/utils/helpers.py",
])

response = model.generate_content(
    f"{context}\n\n"
    "Looking at this entire codebase, identify dependency issues "
    "and areas that would benefit most from refactoring."
)
print(response.text)
```

## The Half That Didn't Work as Expected

This is the more useful part to understand before you commit to a long-context approach.

### Problem 1: Information in the Middle Gets Lost

Information placed in the middle of a long context is retrieved less reliably than information at the beginning or end. This is the "Lost in the Middle" phenomenon that's been documented in research — and I encountered it directly.

I loaded 100 pages of documentation and asked about something from page 50. The answer was noticeably less accurate than questions about the first or last sections. The model had the information — it was in the context — but couldn't reliably surface it.

```python
def build_prompt_with_priority(
    context_docs: list[str],
    priority_doc: str,
    question: str
) -> str:
    """
    Place the most important document at the beginning.
    Critical information in the middle of a long context
    is less reliably retrieved.
    """
    return (
        f"# Priority Document (refer to this first)\n{priority_doc}\n\n"
        f"# Additional Context\n" +
        "\n\n".join(context_docs) +
        f"\n\n# Question\n{question}"
    )
```

For tasks where specific information needs to be reliably retrieved, placement matters. Put critical content at the beginning or end, not buried in the middle.

### Problem 2: Latency Grows With Context Length

Loading 500K tokens means waiting 20–40 seconds for the first response token. For interactive applications where users are waiting, this is a dealbreaker.

```python
import time

def measure_latency(prompt: str, model_name: str = "gemini-1.5-pro") -> dict:
    model = genai.GenerativeModel(model_name)
    
    start = time.time()
    response = model.generate_content(
        prompt,
        generation_config=genai.GenerationConfig(max_output_tokens=100)
    )
    elapsed = time.time() - start
    
    return {
        "latency_seconds": round(elapsed, 2),
        "approx_input_tokens": len(prompt) // 4,
    }

# Long context is well-suited for batch/async processing
# Not suitable for real-time conversational interfaces
```

The use cases where long context works well are mostly asynchronous: process a large document, return results when ready. The use cases where it struggles are synchronous: user asks a question, user waits for the answer.

### Problem 3: Cost Adds Up Faster Than Expected

The capacity is impressive; the cost of using it frequently is less so.

```python
# Approximate Gemini 1.5 Pro pricing (verify current rates)
# Input: $3.50/1M tokens (up to 128K)
# Input: $7.00/1M tokens (above 128K)
# Output: $10.50/1M tokens

def estimate_cost_usd(input_tokens: int, output_tokens: int) -> float:
    if input_tokens <= 128_000:
        input_cost = (input_tokens / 1_000_000) * 3.50
    else:
        # Pricing doubles past 128K input tokens
        base = (128_000 / 1_000_000) * 3.50
        extra = ((input_tokens - 128_000) / 1_000_000) * 7.00
        input_cost = base + extra

    output_cost = (output_tokens / 1_000_000) * 10.50
    return round(input_cost + output_cost, 4)

# 500K token input alone:
print(f"500K tokens: ${estimate_cost_usd(500_000, 0):.2f}")  # ~$2.71 per call
# At 100 calls/day:
print(f"100 calls/day: ${estimate_cost_usd(500_000, 0) * 100:.2f}/day")  # ~$271/day
```

For high-frequency applications, loading 500K tokens per call is expensive. The more practical pattern is combining long context with retrieval: use search to find relevant sections first, then load only those into the context. You get most of the benefit at a fraction of the cost.

## How to Use Long Context Effectively Given Its Actual Behavior

After working with it across several projects, here's how I'd frame it:

Long context is a capability with real constraints, not a universal solution. The constraints are:

- **Position bias is real.** Critical information should be at the beginning or end.
- **It's batch-processing technology.** Don't build synchronous user-facing features around it.
- **Cost scales fast with input length.** Model the numbers before committing to high-frequency usage.
- **RAG is complementary, not competing.** Retrieve the relevant sections, then load them — often better results at lower cost.

Gemini's long-context capability will keep improving. Right now, the most useful mental model is "powerful but not unlimited" — understanding where its actual boundaries are is what lets you use it effectively rather than being surprised by them.
