The promise of a million-token context window is hard to resist. Feed in an entire codebase. Process a dense PDF without chunking. Cross-reference multiple documents in a single call. These are genuinely compelling use cases.

But spend enough time working with large inputs and a pattern emerges: important information in the middle of the document gets overlooked. The model produces a confident, detailed answer that somehow misses the exact paragraph you needed it to find. This isn't a Gemini defect — it's a structural challenge that affects all LLMs at scale. Here's what's happening, and what actually helps.

## The Lost-in-the-Middle Problem

Research has consistently shown that LLMs attending to long input tend to focus more reliably on information at the beginning and end of the context. Content buried in the middle receives less "attention" in the technical sense — which translates to a higher rate of omission and error when the relevant information sits in that zone.

Intuitively: asking Gemini to find a specific bug-causing function near the middle of a 500K-token codebase, based on a question appended at the very end, requires the model to form a connection between two distant parts of the context. That connection is harder to make reliably than if the question and the relevant code were positioned closer together.

## Pattern 1: Position the Question Near the Content

The simplest intervention with meaningful impact: restructure from "document → question" to "question → document" or "question → document → question repeat."

```python
# Before (question at the end)
prompt = f"""
{large_document}

List all risk factors described in Chapter 3 of the document above.
"""

# After (question at both ends)
prompt = f"""
Read the following document and list all risk factors described in Chapter 3.

{large_document}

Reminder: List all risk factors described in Chapter 3.
"""
```

Placing the question at the top means the model processes the document while already knowing what it's looking for. The repetition at the bottom acts as a recovery mechanism for the diffusion of attention that happens after processing long content.

The effect is most pronounced when the target information sits in the document's middle section — which is exactly where retrieval tends to break down.

## Pattern 2: Two-Stage Chunk Extraction and Merge

Rather than processing the full document in one pass, extract relevant information from each chunk independently, then synthesize the results.

```python
import google.generativeai as genai

def extract_from_chunks(document: str, question: str, chunk_size: int = 50000) -> str:
    chunks = [document[i:i+chunk_size] for i in range(0, len(document), chunk_size)]
    
    model = genai.GenerativeModel("gemini-2.5-pro")
    chunk_results = []
    
    for i, chunk in enumerate(chunks):
        prompt = f"""
Extract all information relevant to the following question from this text excerpt.
If no relevant information is present, respond with "None found."

Question: {question}

Text (part {i+1} of {len(chunks)}):
{chunk}
"""
        response = model.generate_content(prompt)
        chunk_results.append(response.text)
    
    # Merge chunk results into a final answer
    merge_prompt = f"""
The following are extractions from different sections of a large document.
Synthesize them into a complete answer to the original question.
Remove duplicates. If there are contradictions, note both versions.

Original question: {question}

Section extractions:
{chr(10).join([f'[Part {i+1}] {r}' for i, r in enumerate(chunk_results)])}
"""
    
    final_response = model.generate_content(merge_prompt)
    return final_response.text
```

The tradeoff is additional API calls (number of chunks + 1). For use cases that prioritize recall — "find every mention of X across this document" — the chunk approach produces more consistent results than single-pass processing of the full text.

## Pattern 3: Structured Output Extraction

When extracting multiple specific fields from a document, specifying a structured output format significantly improves both accuracy and consistency compared to open-ended requests.

```python
extraction_prompt = f"""
Analyze the following contract and extract information in the exact JSON format below.
Use null for any fields where information cannot be found.

{{
  "contract_parties": {{
    "party_a": "Name of first party",
    "party_b": "Name of second party"
  }},
  "effective_date": "YYYY-MM-DD",
  "termination_date": "YYYY-MM-DD or null",
  "payment_terms": {{
    "amount": "numeric value only",
    "currency": "currency code",
    "schedule": "description of payment schedule"
  }},
  "key_obligations": [
    "List of primary obligations"
  ],
  "termination_conditions": [
    "List of termination conditions"
  ]
}}

Contract:
{contract_text}
"""
```

Open-ended requests like "summarize this contract" leave the model to decide what matters. Structured output specifications act as an explicit checklist — the model knows exactly what to look for, which reduces omissions in long documents.

## Pattern 4: Build a Document Map First

For very long technical documents or codebases, an effective approach is to first generate a structural map of the document, then use that map to focus subsequent queries.

```python
def create_document_map(document: str) -> str:
    map_prompt = f"""
To understand this document's structure, list each section with its heading
and a 1-2 sentence description of its contents.
Do not include detailed content — just structure and what each section covers.

Document:
{document[:200000]}
"""
    model = genai.GenerativeModel("gemini-2.5-pro")
    return model.generate_content(map_prompt).text

def answer_with_context(document: str, question: str, doc_map: str) -> str:
    section_prompt = f"""
Which sections of this document are most relevant to answering the following question?
Identify by section heading or number.

Question: {question}

Document structure:
{doc_map}
"""
    model = genai.GenerativeModel("gemini-2.5-pro")
    relevant_sections = model.generate_content(section_prompt).text
    
    answer_prompt = f"""
{question}

Note: The most relevant sections are: {relevant_sections}
Pay particular attention to those sections when formulating your answer.

Full document:
{document}
"""
    return model.generate_content(answer_prompt).text
```

The upfront cost of building the map pays off when you need to ask many different questions against the same document. For systems that serve ongoing queries against a fixed corpus — internal knowledge bases, documentation assistants — this pattern produces noticeably more stable results.

## When Full-Context Single-Pass Actually Works Best

To be fair: there are real use cases where loading everything in at once and asking a broad question is the right approach.

**Architecture and code review**: "What are the main structural weaknesses in this codebase?" or "Are there security concerns?" These questions ask for a holistic evaluation, not extraction of a specific item. Keeping the full codebase together allows the model to reason about relationships between components that chunking would obscure.

**Multi-document comparison**: "What are the key differences in payment terms between these three contracts?" Cross-document comparison is harder when the documents are processed separately — the model needs them together to make accurate comparisons.

**Consistency checking**: "Are there any contradictions between chapters?" or "Do any character behaviors conflict across this manuscript?" Finding inconsistencies requires holding the full content in view simultaneously.

These use cases share a property: the question is inherently about the whole, not about locating a specific piece. That's when the large context window earns its keep without much prompting engineering overhead.

## Choosing the Right Approach

When you're unsure which pattern to apply, the deciding question is: **am I trying to understand the whole, or find something specific within it?**

Holistic evaluation → single-pass, full context input works well.  
Specific extraction or retrieval → chunk processing or structured prompts produce more reliable results.

If you're not sure, Pattern 1 (placing the question at both the top and bottom) costs nothing and consistently improves results. That's the first thing to try before reaching for a more complex approach.
